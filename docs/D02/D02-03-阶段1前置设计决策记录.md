## 二、D-01：P-7 / U-01 迁移批次的存储位置

### 1. 原始依据

- `D02-01 §3.5`：`migration_batches`（13 列）与 `migration_items`（15 列）完整 DDL；六条使用约束，第 1 条即"业务表**零迁移列**"。
- `D02-01 §3.5.1`：`rollback_status` 状态机（`none→四类`、`eligible→rolled_back/protected`、四终态无出边）+ `migration_batches.status` 批次状态机。
- `D02-01 §3.5.2`：`migration_edges`（五元组主键）与 E1–E7 七条约束。
- `D02-01 §4.1`：三张运维表排在建表序 0/1/17，**最先建**；`legacy_artifacts` 排 16。
- `D02-01 §3.5` 末段：三张表"不计入 D01 的 212 列"，不参与任何创作语义。

### 2. 当前问题

D02-01 已给出表结构，但**"批次"到底以什么为权威、回滚如何凭批次精确定位、业务表凭什么不加列"这三件事没有在同一处写清**，P-7 因此仍挂"❌ 未确认"。具体缺口：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 未明说"批次信息只存在于 `migration_batches` 一行" | 实施时容易被理解成"业务行也要记批次" |
| 2 | 未明说三张表分工边界（谁记批次、谁记行、谁记依赖） | 三表职责重叠，最终会有人往 `migration_items` 里塞图结构 |
| 3 | 未回答"回滚如何定位到目标行" | 只能靠 `target_pk` 全表扫，或误以为有外键 |
| 4 | 未回答"续跑凭什么判断已做过" | 可能重复插入 |

### 3. 可选方案

#### 方案 A：业务表加 `migration_batch_id` 列（被否决）

- **实现**：给 14 张目标表各加一列，迁移写入时填批次号；回滚 `DELETE ... WHERE migration_batch_id=?`。
- **优点**：回滚 SQL 极简，一条语句定位；人肉排查直观。
- **缺点**：① 直接违反 `D02-01 §3.5` 约束 1 与 D01 冻结契约（D01 的表结构是审核对象，加列即改 D01）；② 历史 66 段/179 行资产的 `migration_batch_id` 无法回填（迁移前不存在该列，回填值只能是"事后编的"）；③ 未来每个批次都要写 14 张表，任一张漏写就出现"无主行"；④ 业务查询会看到一列与创作无关的运维字段，投影层要额外过滤。
- **数据库影响**：14 张表结构变更，manifest 全部对不上。
- **代码影响**：所有 INSERT 白名单都要加列，写入路径 3 条以上。
- **兼容性影响**：旧库升级需 14 次 `ALTER`，且不可回退（SQLite 删列需重建表）。
- **维护成本**：高——批次概念渗进业务层。
- **回滚难度**：高（列删不掉）。
- **结论**：✗。**这正是审核明确禁止的方向。**

#### 方案 B：三张独立运维表（D02-01 现有设计，推荐）

- **实现**：`migration_batches` 一行一批；`migration_items` 一行一个目标行（主键 `(batch_id, target_table, target_pk)`）；`migration_edges` 一行一条父子边（五元组主键）。业务表**零改动**。
- **优点**：① 完全不动 D01；② 批次→行的定位由主键天然保证（点查，不是扫描）；③ 迁移与回滚的全部状态集中在一处，可单独备份/清理；④ 已通过 V3–V9 九轮审核（状态机、幂等、保护传播、悬空链接边、多父关系）。
- **缺点**：① 运维表与业务表之间**没有外键**，只能靠应用层保证一致（`D01-05 §8` 本就是"不加外键"的全局约定）；② 回滚需要对每行单独 `DELETE`，批量性能不如一条 `WHERE batch_id=?`；③ 三张表的关系（批次 / 行 / 依赖）需要文档讲清，否则实施者会混用。
- **数据库影响**：新增 3 张表，不碰任何业务表；不计入 D01 的 212 列。
- **代码影响**：迁移脚本、回滚脚本、巡检脚本读写这三张表；业务代码零改动。
- **兼容性影响**：无（业务表结构一字不改）。
- **维护成本**：中——脚本要维护，但边界清晰。
- **回滚难度**：低（删批次行 + 按 items 逐行删；有 §12.4 六步与四类状态兜底）。

#### 方案 C：单表 `migration_log`（批次与行合并，被否决）

- **实现**：一张表，每行带 `batch_id` + `target_table` + `target_pk`，批次元信息用"`target_table='__batch__'` 的特殊行"表示。
- **优点**：表更少。
- **缺点**：① 批次元信息（`backup_path` / `backup_sha256` / `rollback_preview` / 四类计数）与行记录字段完全不同，塞一表会有大量 NULL；② 特殊行会被 `WHERE target_table=?` 的普通查询误命中；③ 状态机要区分"批次状态"与"行回滚状态"，同表两套语义必然混。
- **数据库影响**：1 张表但字段最宽。
- **代码影响**：所有查询都要带 `target_table<>'__batch__'` 的防御条件。
- **兼容性 / 维护 / 回滚**：均劣于 B。
- **结论**：✗。省一张表换来两类语义混居，不划算。

### 4. 推荐方案

**方案 B**，理由三条：

1. **契约成本为零**——业务表零改动，D01 的冻结文本一行不用改，这正是 P-7 要解决的核心顾虑。
2. **定位精度由主键保证**——`(batch_id, target_table, target_pk)` 是主键，回滚定位是点查；`migration_edges` 解决"子行消失后仍能认出父行"（V7 的教训：`count=0` 不能证明从未有过子行）。
3. **已被九轮审核打磨**——状态机（§3.5.1）、幂等（V4）、保护传播（V6）、双数据源（V8）、多父合法（V9）都在这一套表上验证过；换方案等于把这九轮的结论全部作废。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 批次信息存在哪里 | **只在 `migration_batches`**，一行一个批次，`id` 为 `mig-YYYYMMDD-NN` |
| 三表分工 | `migration_batches` = 批次级元信息与状态；`migration_items` = **每个目标行一条**（迁移维度 + 回滚维度双状态）；`migration_edges` = **父子依赖边**（迁移时写、回滚只读） |
| 是否给业务表加 `migration_batch_id` | **不加，永不添加**。业务表零迁移列是硬约束，不因"方便"开口子 |
| 历史数据如何关联批次 | 通过 `migration_items` 的 `(batch_id, target_table, target_pk)`；`source_table` / `source_pk` / `source_kind` 记来源侧（如 `plan_beat` / `seg_idx:7`） |
| 回滚如何精确定位 | `SELECT target_table, target_pk FROM migration_items WHERE batch_id=? AND rollback_status='eligible'`，逐行按 `(target_table, target_pk)` 点删；**没有任何"按表删"或"按项目删"的入口** |
| 如何保持独立 | 运维表**不被业务 SQL 引用**；业务代码不 import 迁移模块；运维表可整表备份/清空而不影响业务；`kind='ops'` 在 manifest 中单列 |

### 6. 实施约束（阶段 1 必须遵守）

| # | 约束 |
|---|---|
| M1 | 三张表建表顺序：`migration_batches` → `migration_items` → … → `migration_edges`（§4.1 序 0/1/17），全部 `IF NOT EXISTS` |
| M2 | 业务表**零迁移列**：`PRAGMA table_info` 中不得出现 `migration_batch_id` / `batch_id` / `migrated_*` 一类列（manifest 校验 + 巡检脚本各查一次） |
| M3 | `migration_items.migrated_content_hash` 写一次后**永不更新**（§3.5 约束 2）；任何"重新盖章"的写法视为缺陷 |
| M4 | 回滚只处理 `rollback_status IN ('none','eligible')`；四个终态不读目标行（V4 的幂等前提） |
| M5 | `migration_edges` 只在迁移写行同事务内写入，回滚只读不删（E1/E2）；边与记录的关联必须用三元组（E5），读取必须 LEFT JOIN 并显式检查未匹配（E6） |
| M6 | 运维表**不进入** `changelog` 的记录范围（`ENTITY_TABLE` 不含它们），避免污染内容变更日志 |

### 7. 验收标准

| # | 判据 | 判定方式 |
|---|---|---|
| 1 | 14 张业务表列名 = manifest 的 `expect`，且不含任何迁移列 | `verify-manifest` 输出 `missing=0`、`unknownExtra=0` |
| 2 | 一个批次回滚后，`migration_items` 中该批次全部行进终态或仍为 `eligible`（无 `none` 残留） | `SELECT COUNT(*) WHERE batch_id=? AND rollback_status='none'` = 0 |
| 3 | 回滚不触碰未登记行 | 回滚前后 `COUNT(*)` 差 = 本批次 `rolled_back` 数 |
| 4 | `migrated_content_hash` 在同一批次内二次运行不变 | 两次执行后取 hash 比对，差异 = 0 |
| 5 | 业务表零迁移列巡检 | `PRAGMA table_info(<14 表>)` 全表扫描，命中数 = 0 |

### 8. 对上游文档的影响

## 三、D-02：P-8 / U-02 `render_tasks` 状态枚举

### 1. 原始依据

- `D01-05 §4.10`：`render_tasks`（14 列），`status TEXT DEFAULT 'pending'`，**无枚举注释**；`idx_rt_unit ON (unit_id, status)` 已存在。
- `D01-05 §4.11`：`render_attempts`（10 列），`status TEXT DEFAULT ''`，同样无枚举。
- `D02-01 §7.2`：隔离队列选定"`render_tasks.status='blocked'` + `error`"，并注明"需 U2 枚举含 `blocked`"。
- `D02-01 阶段 5`：任务清单含"隔离（`status='blocked'`）""中断续跑（`interrupted` → 重排未完成单元）"，单测要求"状态机（task/queue 两套不混）""`done≠succeeded` 断言"。
- `D02-01 §11.1` 阶段 5 判据：**5 单元 1 失败 → 4 成功 + 1 `blocked`**。
- 现有实现（实测）：`queue_items.status` 实际取值 **`waiting` / `running` / `done` / `failed` / `cancelled`**（`lib/core/db.js` 的 `Queue.finish/fail/cancel/cancelWaitingByJob`）；`jobs.status` 实际取值 **`running`（默认）/ `done` / `failed` / `cancelled`**（`lib/agent/job-runner.js`）。

> **文档与代码的一处不一致，先记下来**：`D02-01 §5.6` 把 `jobs` 状态写成 `idle/running/done/failed/cancelled/interrupted`，而代码里只出现 4 个（`running/done/failed/cancelled`），没有 `idle`（那是 `projects.status`）也没有 `interrupted`（中断目前表现为"进程没了、行停在 `running`"）。这不影响本轮决策，但阶段 5 不要照抄那张表。

### 2. 当前问题

| # | 缺口 | 后果 |
|---|---|---|
| 1 | `status` 没有枚举，也没有状态机 | 每个模块各写各的字符串，最终出现 `'success'` / `'succeeded'` / `'ok'` 三种同义值 |
| 2 | `queue_items.done` 与"任务成功"没有明确区分 | 队列项 `done` 只代表"这次执行调用返回了"，调用返回错误也算 `done`——直接当成功会导致"页面显示成功、实际没产物" |
| 3 | 没有"阻塞"与"失败"的区分 | 质检不过（可修）与引擎连续报错（不可修）混成一类，用户不知道该重试还是该改镜 |
| 4 | 没有"中断"的表达 | 进程被 kill 后 task 永远停在 `running`，无人回收（现有 `jobs` 就是这样） |
| 5 | 重试与 `render_attempts` 的关系未定义 | 无法回答"重试了几次""第几次成功的" |

### 3. 可选方案

#### 方案 A：最小 4 态（`pending/running/succeeded/failed`）

- **实现**：只区分"没跑/在跑/成了/败了"，阻塞与中断都归入 `failed`（用 `error` 前缀区分）。
- **优点**：状态最少，前端一个 switch 就够。
- **缺点**：① 违背 `D02-01 §7.2` 与 §11.1 的 `blocked` 判据（"5 单元 1 失败 → 1 `blocked`"）；② 中断与真失败混在一起，恢复器无法判断"该重排还是该放弃"；③ 质检不过的单元会被永久当失败，用户修完镜也无法让它重新排队。
- **数据库影响**：无。
- **代码影响**：最小。
- **兼容性**：好。
- **维护成本**：低，但把复杂度推给了每个读状态的地方（各自解析 `error` 前缀）。
- **回滚难度**：低。
- **结论**：✗，与已冻结的阶段 5 验收冲突。

#### 方案 B：7 态（`pending/running/succeeded/failed/blocked/cancelled/interrupted`，推荐）

- **实现**：见 §5 的状态表与转移表；`blocked` 表示"被上游/质检挡住，需要人改东西"；`interrupted` 表示"执行中进程消失，结果未知"。
- **优点**：① 每个状态对应一个**明确的后续动作**（重排 / 换参重跑 / 人工修 / 放弃）；② 与 `D02-01 §7.2`、阶段 5 判据逐条对齐；③ 中断可被恢复器识别并重排，不需要"扫全表猜"。
- **缺点**：① 状态多，前端要写 7 个分支；② `blocked` 是"非终态但不可自动重试"，比终态更容易被误实现成"自动重试"（需要一条显式规则钉住）。
- **数据库影响**：无结构变更，只冻结取值；建议加 `CHECK` 约束？——**不加**（`D01-05` 没写 `CHECK`，加约束就是改 DDL；改用应用层 + 巡检）。
- **代码影响**：`lib/core/render/task.js`（阶段 5 新建）实现单一状态机，其他模块只读。
- **兼容性**：`render_tasks` 是新表，无历史行，无兼容负担。
- **维护成本**：中。
- **回滚难度**：低（阶段 5 回滚只关开关、保留行）。

#### 方案 C：状态 + 子状态（`status` + `phase`）

- **实现**：`status` 5 态 + 复用 `error` 或新增字段表达子原因。
- **优点**：状态机边少。
- **缺点**：① `render_tasks` 没有 `phase` 列（`jobs` 才有），要表达就得加列 = 改 D01；② 塞进 `error` 字符串等于"用自由文本当枚举"，无法查询、无法建索引。
- **结论**：✗。

### 4. 推荐方案

**方案 B**。核心理由：**状态的用途不是"显示"，而是"决定下一步动作"**。7 个状态各自只有一个默认动作，多一个状态就少一处 `if (error.includes(...))` 的猜谜。

### 5. 最终决策

#### 5.1 完整枚举（`render_tasks.status`，7 态）

| 状态 | 业务含义 | 默认下一步动作 | 终态 |
|---|---|---|---|
| `pending` | 任务已创建，尚未被派发（可能已入队等待） | 调度器派发 | 否 |
| `running` | 有一次 attempt 正在执行 | 等结果 / 超时回收 | 否 |
| `succeeded` | 至少一次 attempt 成功且产物路径非空 | 停止；可被选片 | **是** |
| `failed` | 重试耗尽，或遇到不可重试错误 | 停止；需人工决定是否新建 task | **是** |
| `blocked` | 被上游或质检挡住（包缺失 / 切分失败 / QC fail） | **等人工修复后显式重排**，不自动重试 | 否 |
| `cancelled` | 用户/系统主动取消 | 停止 | **是** |
| `interrupted` | 执行中进程消失，结果未知 | 恢复器重排（→ `pending`） | 否 |

#### 5.2 合法转移表（唯一权威）

| 当前 | 允许转移到 | 触发条件 | 必须同时写入 |
|---|---|---|---|
| `pending` | `running` | 队列项 lease 获取成功（`queue_items.waiting→running`） | `started_at`、当前 `attempt` 行 |
| `pending` | `blocked` | 建任务/派发前预检失败：`package_id` 不存在、`prompt_packages.qc_status='fail'`、单元被切分标注不可渲染 | `error` = 错误码 |
| `pending` | `failed` | 参数非法（`seed<0`、`track` 不在 `{seedance,h3}`）等确定性错误 | `error`、`finished_at` |
| `pending` | `cancelled` | 用户取消 / 项目停止 | `finished_at` |
| `running` | `succeeded` | 当前 attempt 成功且 `output_path` 非空 | attempt 置 `succeeded`；`finished_at` |
| `running` | `pending` | 当前 attempt 失败，且 `attempt_no < max_attempts`（可重试） | attempt 置 `failed`；`queue_items.fail({retryAt})` |
| `running` | `failed` | 当前 attempt 失败且达上限，或错误码属不可重试集（见 5.4） | attempt 置 `failed`；`error`、`finished_at` |
| `running` | `blocked` | 产物存在但质检 `fail`（`qc_reports.level='fail'`） | `error` = QC 码；产物保留 |
| `running` | `interrupted` | 进程消失：租约过期且无活跃 worker 认领 | 当前 attempt 置 `cancelled` + `error='interrupted'` |
| `running` | `cancelled` | 用户取消（含 `Queue.cancelByJob`） | attempt 置 `cancelled` |
| `blocked` | `pending` | 人工修复后显式重排（API `POST /tasks/:id/retry`） | `error` 清空、记录重排时间 |
| `blocked` | `cancelled` | 用户放弃 | `finished_at` |
| `interrupted` | `pending` | 恢复扫描（启动时 / 定时） | 无（attempt 已在上一次转移时记账） |
| `interrupted` | `failed` | 重排次数超上限或人工判定失败 | `error='recovery_exhausted'`、`finished_at` |
| `interrupted` | `cancelled` | 用户放弃 | `finished_at` |
| `succeeded` / `failed` / `cancelled` | **无出边** | — | — |

**非法转移（必须在代码里显式拒绝，不得"顺手允许"）**：

| 非法转移 | 为什么必须拒 |
|---|---|
| 任何终态 → 任何状态 | 终态是事实记录；重跑的正确做法是**新建 task**，不是复活旧行（与 `rollback_status` 的"四终态无出边"同一条原则） |
| `pending → succeeded` | 没有 attempt 支撑的成功不可信 |
| `interrupted → succeeded` | 必须先经 `running` 走一次真实执行 |
| `blocked → succeeded` | 阻塞意味着"没有可用的产物"，直接成功等于把质检失败洗白 |
| `running → running` | 重复派发；同一时刻一个 task 只允许一个活跃 attempt |
| `failed → pending` | 见上：重跑请新建 task（`blocked` 是唯一允许被人工"救回"的非终态） |

#### 5.3 `render_attempts.status`（4 态，配套冻结）

`running` / `succeeded` / `failed` / `cancelled`。语义是"这一次调用"的结果，与 task 状态**不是同一层**：一个 task 可以有 N 条 attempt，task 的终态由最后一条 attempt + 重试预算决定。

**历史迁移特例**：`D02-01 §5.7` 已规定 `shot_videos → render_attempts` 时 `status='done'`。本轮不改那条（历史数据是"有路径即完成"的既成事实），但**新链路只写 4 态中的值**，`'done'` 视为历史专用值，出现在新行即为缺陷（巡检可查）。

#### 5.4 重试规则

| # | 规则 |
|---|---|
| RT-1 | **重试 = 新建 attempt + task 回 `pending`**。不覆盖旧 attempt，不复用 `attempt_no` |
| RT-2 | `attempt_no` 从 1 起、按 task 内递增；唯一性由 `UNIQUE(task_id, attempt_no)` 保证（阶段 5 建索引，D01 未声明该唯一键 → 见 §6 约束 T5 的处理方式） |
| RT-3 | 队列去重键：`dedupe_key = task:<task_id>:a<attempt_no>`。同一 attempt 不会有两个活跃队列项（现有 `Queue.enqueue` 的 `dedupe_key` + `status IN ('waiting','running')` 已实现该语义） |
| RT-4 | **可重试错误集**：引擎超时、5xx、限流、`NETWORK_*`、产出文件缺失（`output_path` 为空但远端报成功）。**不可重试**：参数非法、`package` 不存在、`track` 非法、内容审核拒绝 |
| RT-5 | 退避：`retryAt = now + min(2^n * 5s, 5min)`，写 `queue_items.not_before`，**不改** task 状态以外的任何行 |
| RT-6 | 重试预算只由 `attempt_no` 与策略上限决定，不引入 `retry_count` 列（D01 无此列，且 attempt 表本身就是计数） |

#### 5.5 失败隔离

| # | 规则 |
|---|---|
| FI-1 | task 失败只写自身 `status`/`error`/`finished_at`，**不改** `render_units.status`、不改同项目其他 task |
| FI-2 | 同一 unit 允许多个 task 并存（历史 + 重跑），但**同一时刻只允许一个非终态 task**；建任务入口检查，冲突返回 `TASK_ALREADY_ACTIVE`（不加 DB 唯一索引：终态行必须能并存） |
| FI-3 | 一个 task 失败不得让同批其他 task 变成 `cancelled`；批量入口只在"用户显式停止"时才批量取消 |
| FI-4 | `blocked` 的 task 不计入失败率统计（它表示"等人"，不是"引擎不行"） |

#### 5.6 中断与恢复

| 步骤 | 动作 |
|---|---|
| 1 | 进程启动时扫描 `status='running'` 的 task |
| 2 | 对每个 task 查其活跃队列项：`queue_items WHERE status='running' AND lease_until > now` 且该队列项 `payload.task_id` 指向它 |
| 3 | 无活跃队列项 → 判定中断：当前 attempt 置 `cancelled` + `error='interrupted'`，task 置 `interrupted` |
| 4 | 恢复器把 `interrupted` → `pending`（同一轮或下一轮），派发时新建 attempt（`attempt_no+1`） |
| 5 | 同一次启动内最多重排 `R` 次（`R=2`）；超过则 `interrupted → failed`（`error='recovery_exhausted'`），交人工 |
| 6 | **不得**在启动时把新链路的队列项标 `cancelled` —— 现有 `initSchema` 末尾（`lib/core/db.js` 约 445–449 行）对**全部** `waiting/running` 队列项做了 `cancelled`，阶段 5 必须让新链路走"重排"分支，且**不改旧链路行为** |

> 第 6 条是这一节最容易出事的地方：现有启动清理是"全表取消"，新链路若直接复用，所有未完成任务会在每次重启时被静默作废——而且看起来"符合现有行为"。区分方式见 §6 的 T7。

#### 5.7 `queue_items.status` 与 `render_tasks.status` 的关系（三层不混）

| 层 | 表 | 回答的问题 | 状态集 |
|---|---|---|---|
| 调度层 | `queue_items` | "这次调用有没有被某个 worker 领走、有没有返回" | `waiting` / `running` / `done` / `failed` / `cancelled` |
| 业务任务层 | `render_tasks` | "这个单元到底生成成功没有、要不要重试" | 见 5.1（7 态） |
| 尝试层 | `render_attempts` | "第 N 次调用具体发生了什么" | 4 态 |

**四条硬规则**：

| # | 规则 | 反例 |
|---|---|---|
| Q1 | `queue_items.status='done'` **不等于** task 成功 | 引擎返回 200 但 `output_path` 为空 / 内容审核拒绝 → queue `done`、task `failed` |
| Q2 | queue `failed` **不必然**导致 task `failed` | 首次 `failed` 且可重试 → task 回 `pending`，不是 `failed` |
| Q3 | task 状态**只能由 task 模块**写；调度器只写 queue 状态 | 调度器直接 `UPDATE render_tasks SET status='failed'` 属于跨层写入，禁 |
| Q4 | 三层状态**不得合并成一张视图对外**当权威 | 可以出一张"聚合看板"视图，但写路径只能走各自层 |

### 6. 实施约束

| # | 约束 |
|---|---|
| T1 | 7 态取值定义为常量集（`TASK_STATUS`），全仓库只此一处；SQL 里出现字面量字符串的地方必须引用同一常量 |
| T2 | 不新增 `CHECK` 约束（不改 D01 DDL）；改由"单一写入口 + 巡检脚本"保证。巡检：`SELECT DISTINCT status FROM render_tasks` 必须 ⊆ 7 态，且新行不得出现 `'done'` |
| T3 | 状态转移只能经 `render/task.js` 的 `transition(taskId, from, to, patch)`；该函数内联合法转移表，非法转移抛 `ILLEGAL_TRANSITION` 并记 `error` |
| T4 | 每次转移必须带 `from` 做**条件更新**：`UPDATE ... SET status=? WHERE id=? AND status=?`，`changes=0` 即视为并发冲突（另一方已改），不得重试覆盖 |
| T5 | `attempt_no` 的唯一性：D01 未声明 `UNIQUE(task_id, attempt_no)`。阶段 5 建**普通索引** `idx_ra_task ON render_attempts(task_id, attempt_no)`（只为查询性能，不承担唯一性）；唯一性由"单写入口 + 同事务内 `COUNT(*)+1` 取号"保证；**不加唯一索引**，登记为 D01 V8 候选（U-15）。**若审核认为"给 D01 表加索引也属契约变更"，则本索引一并取消**，退化为按 `task_id` 现有索引 + 应用层排序——不影响任何状态机规则 |
| T6 | task `succeeded` 的判据必须包含 `output_path` 非空，不允许只看引擎返回码 |
| T7 | 启动清理必须分流：队列项 `payload.task_id` 存在 → 走"中断回收"（5.6）；不存在 → 保持现有"取消"行为。**不得用一个 `UPDATE` 同时处理两类** |
| T8 | task 的 `error` 字段只存**错误码**（如 `ENGINE_TIMEOUT` / `QC_FAIL`），详细文本进日志；避免 `error` 变成自由文本枚举 |

### 7. 验收标准

| # | 判据 |
|---|---|
| 1 | 5 个单元入队，1 个持续失败 → 4 个 `succeeded` + 1 个 `blocked`（若为 QC fail）或 `failed`（若引擎报错达上限），其余不受影响（对应 §11.1 阶段 5） |
| 2 | 构造"queue `done` 但无产物" → task 必须 `failed`，且断言 `queue.status='done' AND task.status<>'succeeded'` 可同时成立 |
| 3 | `render_tasks` 全表 `DISTINCT status ⊆ 7 态`，且无 `'done'` |
| 4 | 把一条 `succeeded` 行手工置回 `pending` 的 API 不存在；`transition` 对 `succeeded→pending` 抛 `ILLEGAL_TRANSITION` |
| 5 | 强杀进程后重启：`running` 的 task 变 `interrupted` 并在同一轮重排为 `pending`；**旧链路**的队列项仍按原逻辑 `cancelled` |
| 6 | 同一 task 重复派发：第二个队列项被 `dedupe_key` 挡住，`attempt_no` 不跳号 |

### 8. 对上游文档的影响

**无结构变更**。本决策把 `D01-05 §4.10` 里"`status TEXT DEFAULT 'pending'`（枚举待定）"的待定项冻结为 7 态；`D01-05` 的 DDL 一行不改。D02-01 §7.2 / 阶段 5 / §11.1 的 `blocked` 判据由此获得枚举依据。

**两处需要阶段 5 任务书吸收的差异**：① `D02-01 §5.6` 的 `jobs` 状态表与代码不一致（见 §1）；② `attempt_no` 唯一键缺失（U-15，登记 D01 V8 候选，本轮不改）。

## 四、D-03：P-9 / U-11 / C-4 `render_tasks` 与 `jobs` 的关联

### 1. 原始依据

- `D01-05 §4.10`：`render_tasks` **14 列**，逐列核对无 `job_id`：`id / project_id / unit_id / package_id / engine / track / params / seed / status / error / cost_amount / cost_unit / started_at / finished_at`。
- `D01-06`（约 1832 行）：`render` 的输入是 `(packageId, params, seed?)` —— **`params` 是送给引擎的调用参数**，不是业务元数据袋。
- `D02-01 §5.6`："`jobs` 保留为流水线运行记录，`render_tasks` 是单元生成记录，两者**并存不互转**；新链路发起任务时**同时**写 `jobs` 与 `render_tasks`"，并明确"该关联只能靠运维表或在 `render_tasks.params` 里塞 `job_id`，登记 U-11"。
- `D02-01 附录 C-4`：同一缺口的另一编号，"① 放 `params` JSON；② 或建议 D01 V8 加 `job_id`"。
- 现有实现（实测）：`jobs` 16 列（`id/project_id/type/status/phase/detail/progress/checkpoint/log_path/error/started_at/finished_at/updated_at`）；`queue_items` 有 `job_id` 列与 `idx_queue_job`。

### 2. 当前问题

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 无法按 job 聚合 task | 任务列表页只能按 unit 平铺，用户看不出"这批是同一个流水线跑出来的" |
| 2 | 断点续跑无从下手 | `jobs.checkpoint` 存的是**任务参数**、运行中从不更新（D02-00 已实测），不能当断点游标；只能靠 task 表反查，但反查缺关联 |
| 3 | 取消 job 时找不到它的 task | 只能按 `project_id` 粗放取消，会误伤同项目其他批次的 task |

### 3. 可选方案

#### 方案 A：`job_id` 放进 `render_tasks.params` JSON

- **实现**：建任务时 `params = {"...engines":..., "job_id":"job_x"}`；查询用 `json_extract(params,'$.job_id')=?`。
- **优点**：零 DDL、零新表，当天就能写。
- **缺点**（逐条都可实测）：
  1. **语义错误**：`params` 按 `D01-06` 是渲染入参，会被传给引擎。`job_id` 混在里面等于把内部运维标识发给第三方模型服务；有些 API 对未知字段直接 400。
  2. **无完整性**：`job_id` 可以随便填、可以事后被改写（`params` 是 `TEXT`，没有任何约束），也无法阻止一个 task 出现两个不同 job 的历史值。
  3. **方言不一致**：SQLite 用 `json_extract(params,'$.job_id')`，PostgreSQL 用 `params->>'job_id'`；要建索引还得写**表达式索引**（SQLite 支持，PG 支持），两套 DDL，而 `db-driver.js` 只做 `INTEGER→BIGINT` 级别的翻译，承担不了。
  4. **类型漂移**：JSON 里 `"job_id": 123` 与 `"job_id": "123"` 在 SQLite 比较里不等，运维排查会踩。
  5. **与 D01 的意图冲突**：`D01-06` 的 hash / 编译链都按"`params` 是入参"设计，往里面塞关系字段，将来做 `compiledHash` 复核时会成为噪声源。
- **数据库影响**：无。
- **代码影响**：所有按 job 查询处都要写 JSON 提取 + 防御类型。
- **兼容性**：表面最好（不改表）。
- **维护成本**：**高**——每个查询各写一遍 JSON 路径，且没有一处能保证正确。
- **回滚难度**：低（但错数据难清）。
- **结论**：✗。

#### 方案 B：`render_tasks` 增加 `job_id` 列（本轮不可执行）

- **实现**：`ALTER TABLE render_tasks ADD COLUMN job_id TEXT DEFAULT ''`，加 `idx_rt_job`。
- **优点**：**模型上最干净**——一列一关系、可索引、可 `WHERE job_id=?`、可直接 `NOT NULL` 校验；也是 D01 V8 若修订时的首选。
- **缺点**：① `render_tasks` 的 14 列是 D01-05 冻结 DDL，加列 = 改 D01（本轮任务书 §9 明确禁止）；② manifest 的 `expect` 由 D01 DDL 生成，加列后 manifest 与 D01 不一致，阶段 1 的"18 表列名 = manifest"判据会自相矛盾；③ 需要一轮 D01 V8 审核，阶段 1 不能等。
- **数据库影响**：1 列 + 1 索引。
- **代码影响**：小。
- **兼容性**：无历史行（新表），无兼容负担。
- **维护成本**：最低。
- **回滚难度**：SQLite 删列需重建表 → 中。
- **结论**：**技术上最优，流程上不可行**。登记为 D01 V8 候选（U-16），本记录不推动。

#### 方案 C：独立关系表 `render_task_jobs`（推荐）

- **实现**：

```sql
-- D02 实施侧关系表（不属于 D01 的 14 张业务表，不计入 212 列）
CREATE TABLE IF NOT EXISTS render_task_jobs (
  task_id    TEXT PRIMARY KEY,          -- 一个 task 只能属于一个 job（1:1 归属）
  job_id     TEXT NOT NULL,             -- 一个 job 可以有 N 个 task（1:N 聚合）
  created_at INTEGER
);
CREATE INDEX IF NOT EXISTS idx_rtj_job ON render_task_jobs(job_id);
```

- **优点**：① 不改 D01 一个字符；② `task_id` 作主键 → **"一个 task 属于两个 job"在数据库层就不可能**；③ `idx_rtj_job` 让"某 job 的全部 task"是普通 B-tree 查询；④ 与 `render_unit_shots`（D01 自己用的关联表）风格一致，不是新发明；⑤ 与 `migration_edges` 的经验一致：关联关系单独一张表，回滚/清理时边界清晰。
- **缺点**：① 多一张表（21 张里的 1 张）；② 查 task 列表要 `LEFT JOIN`（未登记的 task 也必须能显示，所以是 LEFT 不是 INNER）；③ 写入必须与 task 创建同事务，否则出现"task 存在但没归属"。
- **数据库影响**：1 表 + 1 索引。
- **代码影响**：`render/task.js` 的 `create()` 内写两行（task + relation），同事务；查询层加一个 `listByJob(jobId)`。
- **兼容性**：无（新表）。
- **维护成本**：低——只有一处写、一处读。
- **回滚难度**：低（删表即可，task 不受影响；反之删 relation 不影响 task 与产物）。
- **结论**：✓。

### 4. 推荐方案

**方案 C**。三条理由：

1. **它把"1:N"写进了结构，而不是写进了注释**——`task_id` 主键保证每个 task 最多一个 job；`job_id` 普通索引允许一个 job 挂 N 个 task。方案 A 两者都保证不了。
2. **它把"不是引擎参数"的东西从引擎参数里拿出来了**。`params` 会随渲染请求发给模型服务，`job_id` 不该出现在那里。
3. **它是唯一在"不改 D01"前提下同时满足"可索引 + 可校验 + 双方言"的方案**。方案 B 更好，但要等 V8，而阶段 1 不能等。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 一个 Job 能否创建多个 RenderTask | **能**。这是常态：一个流水线 job 会为多个 unit 各建一个 task |
| 一个 RenderTask 能否属于多个 Job | **不能**。`render_task_jobs.task_id` 为主键，数据库层拒绝第二个归属 |
| 生命周期是否相同 | **不同**。job 是流水线（分钟级，可能被用户随时停）；task 是单元生成（一次调用，秒到分钟）。**task 的生命周期长于它所属的 job 记录**（job 行被删后，task 与其产物仍有效） |
| Job 失败是否意味着所有 Task 失败 | **否**。已 `succeeded` 的 task 产物有效，不回退；未完成的 task 由取消逻辑处理（见下），不因 job 记录变 `failed` 就批量改写 task |
| 如何查某 Job 的全部 Task | `SELECT t.* FROM render_tasks t JOIN render_task_jobs r ON r.task_id=t.id WHERE r.job_id=?`（含 `status` 过滤时走 `idx_rt_unit` 或直接 `idx_rtj_job` 后回表） |
| 断点续跑靠什么 | 靠 task 表 + relation，**不靠** `jobs.checkpoint`（它存的是参数、运行中不更新）。恢复流程：`job_id → task_ids → 其中 status ∈ {pending,running,blocked,interrupted}` → 重排/回收 |
| 旧 Job 逻辑是否仍可用 | **是**。`jobs` 表结构、`job-runner.js`、旧任务列表页全部不变；新链路只是"额外多写一行 relation" |
| 关联是否需要索引 | **需要**：`idx_rtj_job ON render_task_jobs(job_id)`；`task_id` 由主键自带索引 |
| 取消/删除 Job 时如何处理 task | 见下方三档 |

**取消/删除 Job 的三档处理**（这是本节最容易做错的地方）：

| 场景 | `waiting` 队列项 | `running` 队列项 | 非终态 task | 终态 task 与产物 |
|---|---|---|---|---|
| 用户"停止"job | `Queue.cancelWaitingByJob`（现有） | 按现有 `cancelByJob` 语义取消 | 置 `cancelled`（`error='job_cancelled'`） | **不动** |
| job 执行失败（异常结束） | 保持（可能是下一个 job 的） | — | **不改**，让它们各自按超时/中断规则收敛 | **不动** |
| 删除 job 行 | 同"停止" | 同"停止" | 置 `cancelled` | **不动**；`render_task_jobs` 中该 job 的行**同事务删除** |

> 为什么"删除 job 行时连同 relation 一起删"：relation 是 **job 视角**的聚合，job 行都不在了，聚合没有意义；而 task 自身仍可通过 `unit_id` / `project_id` 被查到，不会失联。反过来若保留，就会留下一批 `job_id` 指向不存在行的悬空关系——那正是我们在迁移侧花九轮去消灭的东西。

### 6. 实施约束

| # | 约束 |
|---|---|
| J1 | `render_task_jobs` 建在 `render_tasks` 之后（§十一 顺序 12.1），全部 `IF NOT EXISTS` |
| J2 | 写 task 与写 relation **必须同一事务**；任一步失败整体回滚，禁止"task 已建、relation 后补" |
| J3 | `job_id` 允许为空字符串吗？**不允许**。无 job 归属的 task（如手工单测、历史迁移）**不写 relation 行**，而不是写一行 `job_id=''`——"没有关系"用"没有行"表达，不用空串表达 |
| J4 | 查询一律 `LEFT JOIN`：未登记 relation 的 task 必须仍能列出（否则历史迁移的 task、单测 task 会从列表里消失） |
| J5 | 禁止在 `render_tasks.params` 里写 `job_id`（巡检：`params` 出现 `job_id` 键即视为缺陷） |
| J6 | 删除 project 时必须清 `render_task_jobs`（`DELETE WHERE task_id IN (SELECT id FROM render_tasks WHERE project_id=?)`），与现有 `Projects.remove` 的 8 张从表清理同事务 |
| J7 | 不得把 `jobs` 与 `render_tasks` 合并成一张表（生命周期、粒度、状态集三者都不同） |

### 7. 验收标准

| # | 判据 |
|---|---|
| 1 | 一个 job 建 5 个 task → `SELECT COUNT(*) FROM render_task_jobs WHERE job_id=?` = 5 |
| 2 | 尝试给同一 task 插第二条 relation → 主键冲突，被拒（`UNIQUE_VIOLATION`） |
| 3 | 某 job 的 task 列表 = 该 job 建的 task 集合（与 task 表按 `project_id` 粗筛的结果做差集，差 = 0） |
| 4 | 未登记 relation 的 task 仍出现在任务列表（`LEFT JOIN` 生效） |
| 5 | `render_tasks.params` 全表扫描，含 `job_id` 键的行数 = 0 |
| 6 | 删除 job 后：relation 行 = 0、task 行仍在、`render_attempts.output_path` 指向的文件仍在 |

### 8. 对上游文档的影响

**无**。`D01-05 §4.10` 的 14 列一字不改；`D02-01 附录 C-4` 由"待决策"变为"已决策：关系表"，但**不改 D02-01 正文**（C-4 那一行本就标注"待审核"）。

**登记 D01 V8 候选 U-16**：`render_tasks.job_id` 一列仍是模型上更优的形态；若将来 V8 修订，可用"加列 + 迁移 relation 数据 + 删 relation 表"收敛。

## 五、D-04：P-10 / U-12 / C-5 `selected` 标记的存储位置

### 1. 原始依据

- `D01-05 §4.11`：`render_attempts` **10 列**，逐列核对无 `selected`：`id / task_id / attempt_no / seed / output_path / duration_real / status / error / started_at / finished_at`。
- `D01-05 §5.7`：`shot_videos.selected` 是"用户选了哪条"，属**单元级决策**；`render_attempts` 无此列、`render_units` 也无此列 → 登记 **U-12**；首版迁移把 `selected=1` 写进 `migration_items.reason`，**保留证据不丢**。
- `D02-01 附录 C-5`：同一缺口的另一编号。
- 现有实现（实测，`lib/core/db.js` 的 `ShotVideos`）：`shot_videos.selected INTEGER DEFAULT 0`；`setSelected(shotId, videoId)` 是**两条 UPDATE**——先把该镜全部置 0，再把目标置 1；`selectedForShot()` 查 `selected=1` 且 `LIMIT 1`，查不到时回落到"第一条候选"。

### 2. 当前问题

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 新链路无处存"用户选了哪条" | 只能在迁移时写进 `migration_items.reason`（运维表），新产生的选择干脆没地方记 |
| 2 | 现有实现**无唯一约束** | `selected=1` 可以同时存在多行；`selectedForShot` 的 `LIMIT 1` 是在"掩盖"而不是"保证"唯一 |
| 3 | 现有实现**两步 UPDATE 非原子语义** | 第一步成功、第二步失败（或 crash）→ 该镜变成"零选中"，且没人发现 |
| 4 | 选片与任务状态没有边界 | 容易把"用户选了"当成"任务成功"，或把"取消选中"当成"删除产物" |

### 3. 可选方案

#### 方案 A：`render_attempts` 增加 `selected` 列

- **实现**：加 `selected INTEGER DEFAULT 0` + 部分唯一索引（`WHERE selected=1`）。
- **优点**：与现有 `shot_videos` 心智一致；一次 UPDATE 就够。
- **缺点**：① 加列 = 改 D01（本轮禁止）；② **选片的语义主体是 unit 而不是 attempt**——用户选的是"这个单元用哪条"，attempt 只是承载物；把标记放 attempt 上，等于用"N 行里有一行是 1"来表达"一个单元一个选择"，唯一性需要部分唯一索引（SQLite `WHERE selected=1` 支持、PG 也支持，但**两套 DDL**，且 `db-driver` 不翻译）；③ "谁被选中"分散在 attempt 行上，取消选中要扫全表。
- **数据库影响**：1 列 + 1 部分索引。
- **代码影响**：小。
- **兼容性**：无历史行。
- **维护成本**：中（部分索引 + 清零逻辑）。
- **回滚难度**：中（重建表）。
- **结论**：✗（本轮不可执行，且模型不如 C）。

#### 方案 B：`render_tasks.params.selected_attempt_id`

- **实现**：选片时改 task 的 `params` JSON。
- **优点**：零 DDL。
- **缺点**：① 与 D-03 方案 A 同病——`params` 是渲染入参，改它等于"为了记一个用户选择而重写引擎参数"，一旦重新编译/重派发就可能被覆盖；② 一个 unit 可能有多个 task，`selected` 挂在 task 上会让"单元级选择"随 task 分裂；③ 无唯一性、无类型、方言依赖 JSON 提取。
- **结论**：✗。

#### 方案 C：独立表 `render_selections`（推荐）

- **实现**：

```sql
-- D02 实施侧关系表：一个单元当前选中的 attempt（单一事实来源）
CREATE TABLE IF NOT EXISTS render_selections (
  unit_id     TEXT PRIMARY KEY,      -- 一个单元只能有一条"当前选择"
  attempt_id  TEXT NOT NULL,         -- 指向 render_attempts.id
  selected_at INTEGER,
  selected_by TEXT DEFAULT '',       -- 'user' / 'agent' / 'auto'
  note        TEXT DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_rs_attempt ON render_selections(attempt_id);
```

- **优点**：① **唯一性由主键保证**（不是靠"清零 + 置一"两道 UPDATE）；② 语义主体正确——主键是 `unit_id`，与"这是单元级决策"一致；③ 换选择是一条 upsert（`INSERT ... ON CONFLICT(unit_id) DO UPDATE`，SQLite 3.24+ 与 PG 9.5+ 同语法），天然原子；④ 不改 D01；⑤ 取消选中 = 删一行，**不碰 attempt、不碰文件**。
- **缺点**：① 多一张表；② 需要应用层校验"attempt 属于该 unit"（无外键）；③ 选择历史要额外记（见 5.4）。
- **数据库影响**：1 表 + 1 索引。
- **代码影响**：`render/selection.js`（新建，约 5 个函数）；成片/QC 读一处。
- **兼容性**：无。
- **维护成本**：低。
- **回滚难度**：低（删表；attempt 与文件全在）。

### 4. 推荐方案

**方案 C**。核心判断：**选片是"单元的一个属性"，不是"某次尝试的一个标志"**。把主键放在 `unit_id` 上，唯一性就是结构性的；放在 `attempt.selected` 上，唯一性只能靠索引或应用层"记得清零"——现有 `shot_videos` 已经证明了后者的代价（两条 UPDATE、`LIMIT 1` 兜底）。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 选片属于 Task、Attempt 还是 RenderUnit | **属于 RenderUnit**（业务主语）；**存储上指向 Attempt**（具体产物）。表主键 = `unit_id` |
| 一个 Task 能否同时选择多个 Attempt | **不能**。选择不挂在 task 上，因此"一个 task 多选"这个概念不存在；一个 unit 只有一条当前选择 |
| 重新选择如何保证只有一个有效 | `INSERT INTO render_selections(unit_id,attempt_id,...) VALUES(...) ON CONFLICT(unit_id) DO UPDATE SET attempt_id=excluded.attempt_id, selected_at=excluded.selected_at`。主键 `unit_id` 保证任何时刻至多一行 |
| 被选的 Attempt 是否必须属于当前 Task | **必须属于该 unit 的某个 task**（可跨 task）。写入前校验 `attempt -> task -> unit_id` 一致，且 `attempt.status='succeeded'`、`output_path` 非空；否则 `SELECTION_INVALID_ATTEMPT` |
| Attempt 被删除/失效时如何处理 | ① 删除 attempt 前先查 `render_selections`，被选中则**拒绝删除**（`ATTEMPT_SELECTED`）；② attempt 的 `output_path` 指向的文件丢失时，选择行**保留**（记录事实），但读侧返回 `stale=true`，由用户重选；③ **任何情况下不自动删除 attempt 行与产物文件** |
| 选片历史如何追溯 | 每次 set/clear 写一条 `change_logs`（`entity='render_selection'`）。这需要把该实体加入 `changelog.ENTITY_TABLE`（D02-01 阶段 1 已规划"扩表"） |
| 选择结果是否影响任务状态 | **不影响**。`succeeded` 只表示"生成成功"，`selected` 只表示"用户采用"。两者正交，任一方向都不得互相推导 |
| 如何传递给 QC 与成片 | QC 按 `attempt_id` / `unit_id` 出报告（`qc_reports.target_type='video'`）；成片读 `render_selections` 取 `attempt_id` 写进 `timelines.entries[].attempt_id`；**未选中的单元**允许 `attempt_id=''` 表示缺口（`D02-01 §7.3` 已有此约定） |

### 6. 实施约束

| # | 约束 |
|---|---|
| S1 | 表建在 `render_attempts` 之后（§十一 顺序 13.1）；`IF NOT EXISTS` |
| S2 | 写选择**只经** `render/selection.js`，禁止别处直接 `UPDATE render_attempts SET ...` 表达选择 |
| S3 | 校验顺序：attempt 存在 → attempt.status='succeeded' → attempt.output_path 非空 → attempt 的 task 的 unit_id == 入参 unit_id。四条全过才写 |
| S4 | 取消选中 = `DELETE FROM render_selections WHERE unit_id=?`。**不得**借此删 attempt、删文件、改 task 状态 |
| S5 | 不得为"取消选中"提供任何级联删除路径（不做 `ON DELETE CASCADE`，本项目全局不加外键） |
| S6 | 删除 project 时清 `render_selections`：`DELETE WHERE unit_id IN (SELECT id FROM render_units WHERE project_id=?)`，与 `Projects.remove` 同事务 |
| S7 | 前端"选片"按钮的可用条件 = `attempt.status='succeeded'` 且文件存在；不做"选一条失败的"这种入口 |

### 7. 验收标准

| # | 判据 |
|---|---|
| 1 | 对同一 unit 连续选 3 个不同 attempt → `SELECT COUNT(*) FROM render_selections WHERE unit_id=?` 恒为 1，且 `attempt_id` 是最后一次 |
| 2 | 选一个属于别的 unit 的 attempt → `SELECTION_INVALID_ATTEMPT`，表内无变化 |
| 3 | 选一条 `status='failed'` 的 attempt → 同上拒绝 |
| 4 | 删除被选中的 attempt → 被拒（`ATTEMPT_SELECTED`）；先清选择再删 → 成功，且 `output_path` 指向的文件仍在 |
| 5 | 取消选中后：attempt 行数不变、磁盘文件数不变、task.status 不变 |
| 6 | 一次 set + 一次 clear 后，`change_logs` 中 `entity='render_selection'` 恰好 2 条 |
| 7 | 未选中的单元仍能出片（`timelines.entries[].attempt_id=''`），成片时长断言仍通过（阶段 6 判据） |

### 8. 对上游文档的影响

**无**。`D01-05 §4.11` 的 10 列不改；`D02-01 附录 C-5` 由"待决策"变为"已决策：独立表"，不改正文。

## 六、D-05：P-11 / U-13 `structured_spec` 的存储位置

### 1. 原始依据

- `D01-05`（约 272 / 950 / 1110 / 1300 行）：`structured_spec` 是**项目级分流开关**——"两条路径按 `structured_spec` 分流，互不交叉"；"同一项目内不会出现两份都能写"；"先把 3 个读取入口切到 `listShotsCompat()`，再开 flag"。
- `D02-01 §8.1`：三条并行原则（旧项目零改动、新项目先只写、读取永远有回退）。
- `D02-01 §8.2`：表格里写的是 `projects.structured_spec`（"**D02 唯一新增的业务列**"，默认 `0`），备注又说"本方案倾向塞 `context`（`{"structured_spec":true}`）"——**同一节里两种口径**，这就是 U-13。
- `D02-01 §12.5.1`：关闭开关的六条行为（停止新建、已产生数据全留、旧链路经投影可读、可再开启）。
- 阶段 0 已交付 `ensureColumn()`（`lib/core/db.js`）：先查 `PRAGMA table_info` 再 `ALTER`，幂等、失败抛出——"给现有表补一列"的成本已经付过一次（`shots.blocking`）。

### 2. 当前问题

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 落点二选一未定 | 阶段 3 的写入入口无法开工（不知道读哪里判断分流） |
| 2 | `context` 的写入语义不唯一 | 见下：`context` 有三条写路径，其中一条是**整段覆盖** |
| 3 | 无统一读取入口 | 一旦允许各模块自己读，必然出现"某个模块读到旧快照"导致同一项目一半走新路一半走旧路 |

**实测的 `context` 写入语义**（这是本决策的关键证据）：

| 写路径 | 行为 | 对 flag 的风险 |
|---|---|---|
| `Projects.setContextKey(id,key,value)`（`db.js` 约 585 行） | 事务内重读最新行 → 改一个键 → 整段写回 | 安全（逐键合并） |
| `PUT /api/projects/:id/context` | 只接受 `CONTEXT_KEYS = ['bible','style','continuity']` 三个键，逐键调 `setContextKey` | 安全（白名单挡住了 flag） |
| `Projects.update(id, fields)`（`db.js` 约 562–570 行） | `const m = {...p, ...fields}` → `context = JSON.stringify(m.context ?? {})` | **危险**：调用方只要传了自己的 `context` 对象，整段被替换，未列出的键全丢 |

也就是说：`context` 今天是"创作上下文"（人物圣经/风格/连续性，由 Agent 与前端写），**不是配置位**；把生命周期开关放进去，等于让它和 LLM 可写的内容共享一个可被整段覆盖的袋子。

### 3. 可选方案

#### 方案 A：`projects` 增加独立列（推荐）

- **实现**：`ALTER TABLE projects ADD COLUMN structured_spec INTEGER NOT NULL DEFAULT 0`（用 `ensureColumn`，幂等）；读取经单一入口 `isStructuredSpec(projectId)`。
- **优点**：① **类型与默认值由数据库保证**（`NOT NULL DEFAULT 0`），不会出现 `"true"` / `1` / `true` 三种写法；② 可直接 `WHERE structured_spec=1` 做批量巡检与灰度清单，无需 JSON 提取、无方言差异；③ 不会被任何 `context` 写路径覆盖；④ 阶段 0 已经验证过"补列 + 幂等"这条路（`shots.blocking`）；⑤ `D02-01 §8.2` 表格本身就是列方案，本决策只是**否决同一节的备注**，不是另起设计。
- **缺点**：① `projects` 是现有表，加列严格说是改现有表结构（但 D02-01 已把它定性为"项目级实施状态位"，不是 D01 业务模型字段）；② 历史库需要一次 `ALTER`（幂等，且 14 行数据零影响）。
- **数据库影响**：1 列，`NOT NULL DEFAULT 0`，历史 14 行自动为 0。
- **代码影响**：`lib/core/structured-spec.js`（新建，读/写/列清单）；`Projects.get()` 的返回体自然带上该列（`SELECT *`）。
- **兼容性**：**旧项目零改动**（默认 0 = 走旧路）。
- **维护成本**：低。
- **回滚难度**：低（列留着不用即可；不删列）。

#### 方案 B：放进 `projects.context` JSON

- **实现**：`context.structured_spec = true`；读取 `JSON.parse(context).structured_spec`。
- **优点**：零 DDL；`projects.context` 已存在且在 `toProject()` 里已解析成对象。
- **缺点**：① **无类型**：`"true"` / `"1"` / `1` 都"看起来像真"，判定要靠 `=== true` 之类的约定；② **可被整段覆盖**（`Projects.update` 路径，见上表），一旦丢失，项目会**静默退回旧链路**——用户表现为"新功能突然没了"，且无报错；③ 查询/灰度需要 JSON 提取（SQLite `json_extract`、PG `->>`），两套写法；④ 与 Agent 可写的内容混居，`save_context` 的整段写回会带上它；⑤ 无法 `NOT NULL`、无法默认值。
- **数据库影响**：无。
- **代码影响**：每个读取点都要解析 + 类型归一。
- **兼容性**：表面最好。
- **维护成本**：**高**（隐患是"静默降级"，最难排查的一类 bug）。
- **回滚难度**：低（但数据可能已被覆盖，无从恢复）。
- **结论**：✗。

#### 方案 C：全局配置 + 项目覆盖两层（`config.json` 默认 + 列覆盖）

- **实现**：`config.json` 给全局默认，项目列给单项目覆盖。
- **优点**：可一键"全局默认开/关"。
- **缺点**：**两处权威**＝没有权威。排查"这个项目为什么走了新路"要先看 config 再看列；且 `D02-01 §8.2` 的 `IC_STRUCTURED_READ` 已经承担了"全局读开关"的职责，再加一层全局默认会与之打架。
- **结论**：✗（本轮）。全局能力已由环境变量承担，不需要第二层。

### 4. 推荐方案

**方案 A**。一句话：**开关是"行为位"，它的读取必须不可能失败**。列 + `NOT NULL DEFAULT 0` 让"读不到"这件事不成立；JSON 让"读不到"变成"静默走旧路"，这是最难被发现的一种故障。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 项目级还是全局 | **项目级**。全局读开关另有 `IC_STRUCTURED_READ`（阶段 7 才用），两者职责不同：列决定"写不写新表"，环境变量决定"读不读新表" |
| 新项目默认值 | **0（关）**。阶段 3 起，由创建/开启入口显式置 1；**不允许"新建即开"** |
| 旧项目升级后默认值 | **0**。`ensureColumn` 的 `DEFAULT 0` 让 14 行历史项目自动为 0，**不做任何回填** |
| 是否允许单项目开关 | **允许**，且这是唯一粒度。批量开关由脚本对多行执行 `UPDATE`，不引入批量字段 |
| Agent / API / 前端 / 兼容层如何读 | 全部经 `lib/core/structured-spec.js` 的 `isStructuredSpec(projectId)`；兼容投影 `listShotsCompat` 内部也调它，**不自己解析 context** |
| 关闭开关后新表已有数据 | **一行不删**（§12.5.1 六条）：停新建、保留数据与引用、旧链路经投影继续可读、可再开启 |
| 是否需要迁移历史项目 | **不需要**。历史项目保持 0；阶段 7 若要迁，按项目 opt-in |
| 如何避免各模块读值不一致 | ① 单一入口模块；② 禁止直接访问 `project.context.structured_spec`（巡检 grep）；③ 读值必须来自**当场查询**，不得缓存到长生命周期对象（Agent 的 `ctx.project` 是快照，阶段 3 要在写入口重读） |

### 6. 实施约束

| # | 约束 |
|---|---|
| F1 | 列定义固定为 `structured_spec INTEGER NOT NULL DEFAULT 0`；用 `ensureColumn(db,'projects','structured_spec', ...)` 补列，**不写 `try { ALTER } catch {}`** |
| F2 | 新库 `initSchema` 的 `projects` DDL 直接包含该列（与 `ensureColumn` 二者幂等共存，和 `shots.blocking` 同款处理） |
| F3 | 只允许 `structured-spec.js` 读写该列；其他模块 import 该模块，不得内联 SQL |
| F4 | 写入只接受布尔；`setStructuredSpec(id, true/false)` 内部转 0/1，拒绝其他值 |
| F5 | 关闭开关**不得**触发任何 DELETE / 数据清理（§12.5.1、§12.5.2 边界） |
| F6 | 开关变更写 `change_logs`（`entity='project'`，走 `Projects.update`），保留审计 |
| F7 | `context` 中**禁止**出现 `structured_spec` 键（巡检：`SELECT COUNT(*) FROM projects WHERE context LIKE '%structured_spec%'` = 0） |

### 7. 验收标准

| # | 判据 |
|---|---|
| 1 | 全新库 `PRAGMA table_info(projects)` 含 `structured_spec`，且 `dflt_value='0'`、`notnull=1` |
| 2 | 历史库副本跑 `initSchema` 两次：`projects` 列数只增 1（**21→22**，实测当前为 21 列），两次后列集合一致，14 行 `structured_spec` 全为 0 |
| 3 | 置 1 后重启进程，读回仍为 1（不依赖内存） |
| 4 | `Projects.update(id,{context:{bible:'x'}})` 之后，`structured_spec` **仍为原值**（证明两者互不覆盖） |
| 5 | 关开关后：`story_shots`/`shot_actions`/`render_units` 行数差 = 0（§11.1 阶段 3 判据） |
| 6 | 全库 `context LIKE '%structured_spec%'` 命中 0 行 |

### 8. 对上游文档的影响

**不新增表/列之外的结构**。`D02-01 §8.2` 的表格（列为准）与备注（倾向 context）自相矛盾，本决策**采纳表格、否决备注**；`D02-01` 正文不改，P-11 由"⏳ 倾向 context"改为"已决策：列"由本记录承担，阶段 1 任务书引用本记录即可。

**对 D01 无影响**：`projects` 是现有表，该列是 D02 的实施状态位，不是 D01 的创作语义字段。

## 七、C-1：多场景章节的 anchors 归属

### 1. 原始依据

- `D01-05 §4.1`：`scene_states` 14 列，主键语义为 `(project_id, scene_key)`（`uq_scene_state` 唯一索引），即**一场一条基线**。
- `D02-01 §5.4`：`plan.anchors.furniture/positions/directions/doors` → `scene_states.fixtures/entries/axis_lock/env`，"若该章只有 1 个 `scene_name` → 直接填；多场景 → **无法归属**"。
- `D02-01 附录 C-1`：给出三条待选（单场景直接填 / 多场景留空 + `need_review` / 建议 D01 V8 给 anchors 加 `scene_key`）。
- 实测（本轮，见 §1.4）：**5 个 plan 中 1 个是多场景章**（`a053dabd` 第 1 章的 anchors 里出现 **9 个不同的 `【场景】` 标签**）；另 1 个在库项目 `0e2c1207` 的 anchors **无场景标签**（单场景）。

### 2. 当前问题

`plan.anchors` 是**章级一份**，而 `scene_states` 是**场景级一行**。`anchors` 里没有 `scene_key` 字段，场景信息以自由文本形式混在字符串里：

```
positions[0] = "【赛道】斯洛恩：西侧金属护栏边，背靠护栏，面朝东北…"
positions[1] = "【发布会】斯洛恩：台下记者席第二排（南侧偏西），面朝北…"
```

要把它拆成 `scene_states` 的行，只有两条路：**解析 `【…】` 标签**（= 猜，且标签是模型自由写的，不保证一致），或**不拆**。

### 3. 可选方案

#### 方案 ①：单场景章自动写；多场景章由程序按 `【…】` 标签拆分

- **实现**：解析 `anchors` 各数组元素里的 `【标签】`，按标签分组，每组写一行 `scene_states`。
- **优点**：迁移"看起来"覆盖率最高（5 章全落）。
- **缺点**：① 标签是**模型写的自然语言**，实测同一章里就出现 `发布会` 与 `发布会·冲突` 两个标签——它们是不是两个场景？程序无法判断；② 拆错后 `scene_states` 里会出现"半个场景的家具表"，后续连续性求解会拿它当权威 → **错误会向下游扩散到镜级校验**；③ 无法回滚成"没拆过"（拆出来的行看起来和真的一样）；④ 与 `D02-01 §5.4` 的"多场景 → 无法归属"直接冲突。
- **数据库影响**：每章最多 N 行（N 不可控）。
- **代码影响**：需要写一个"场景标签解析器"，且没有验收标准（怎么算拆对了？）。
- **维护成本**：高——每次模型换个标签写法就要改解析。
- **结论**：✗。**不得为了提高迁移数量而伪造场景归属。**

#### 方案 ②：单场景自动写；多场景不写、原文留存、标 `need_review`（推荐）

- **实现**：`anchors` 中不存在 `【…】` 标签（或标签数 ≤ 1）→ 视为单场景，派生 `scene_key` 写一行；否则不写 `scene_states`，把该章 plan 原文存 `legacy_artifacts`，并在 `migration_items` 记 `migration_status='skipped'`、`reason='anchors_multi_scene_need_review'`。
- **优点**：① 单场景零猜测（本就只有一个场景）；② 多场景**不制造假数据**，保留"待人工确认"的事实；③ 可回滚（没写过就没有假行）；④ 与 D01 的 `scene_states` 契约完全兼容。
- **缺点**：① 迁移覆盖率看起来低（1/2 在库章）；② 需要一个"待复核清单"的出口（否则 `need_review` 只是躺在库里）。
- **数据库影响**：`scene_states` 只写确定的行。
- **代码影响**：判定逻辑 20 行；`legacy_artifacts` 的 `artifact_kind` 增加一个取值 `anchors_plan`。
- **维护成本**：低。
- **回滚难度**：低。
- **结论**：✓。

#### 方案 ③：建议 D01 V8 给 `anchors` 加 `scene_key`

- **实现**：在 plan 结构里要求模型输出 `scene_key`，`scene_states` 直接按它落库。
- **优点**：从源头解决——场景归属变成结构化字段，不再靠解析文本。
- **缺点**：① 改的是 **plan 的写作契约**（`set_storyboard` 的输入 / 六项锁的产出），属 D01 与 Agent 工具的联合变更；② 已有 plan 仍然没有 `scene_key`，历史迁移照样要"猜或不猜"；③ 阶段 1 不能等 V8。
- **结论**：**方向正确，但不是本轮能做的事**。登记为 **U-18**（plan 是否应带 `scene_key`），交 D01 V8 讨论。

#### 方案 ④：不写 `scene_states`，改用独立存储（把 anchors 原样存成"章级基线表"）

- **实现**：新增一张 `chapter_anchors` 表，按章存原样 JSON，`scene_states` 完全不用。
- **优点**：零解析、零猜测。
- **缺点**：① 等于**在 D01 之外另立一套场景基线**，连续性求解不知道该读哪一份；② 与 `scene_states` 的语义重复（都是"场景/章的空间基线"）；③ 多一张表却没有解决"场景级"这个根本诉求。
- **结论**：✗（本轮）。若将来确认"章级锚点"是独立概念，再议。

### 4. 推荐方案

**方案 ②**。判断标准不是"迁了多少"，而是"**迁错的代价**"：`scene_states` 是连续性求解的权威输入，一行错的场景基线会让后续所有"人物瞬移 / 道具消失"的判定失真，而这类错误在界面上表现为"AI 说这里有问题"——用户根本不知道是迁移时猜错了场景。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 单场景章 | **自动写 `scene_states`**。判定：`anchors` 全文中 `【…】` 标签去重后 ≤ 1 |
| `scene_key` 从哪来 | **派生**：`scene_key = 'ch:' + chapter_id + ':s1'`（确定性、幂等；重复迁移不会产生第二行）。`scene_id` 留空 |
| 多场景章 | **不写 `scene_states`**；plan 原文进 `legacy_artifacts(artifact_kind='anchors_plan')`；`migration_items` 记 `skipped` + `reason='anchors_multi_scene_need_review'` |
| 是否允许程序/LLM 推断归属 | **不允许**。任何"按 `【…】` 标签自动拆分"的实现都视为缺陷 |
| 是否需要改 D01 | **不需要**（`scene_states` 的 `scene_key` 是自由文本，派生的 key 合法） |
| 对阶段 2 的影响（**实测数字**） | 在库 2 章中：**1 章可自动写**（`0e2c1207`，7 beats），**1 章需人工复核**（`a053dabd`，13 beats，9 个场景标签）。另外 3 个 plan 的 `project_id` 不在 `projects` 表（孤儿目录），**一并不建**（`D02-01 §3.4` 已定） |

### 6. 实施约束

| # | 约束 |
|---|---|
| A1 | 场景标签判定只做"计数"，不做"语义聚类"：`【a】` 与 `【a·冲突】` 算**两个**标签 → 判为多场景 → 走 `need_review`（宁可少写） |
| A2 | 派生 `scene_key` 的规则写进一个函数（`sceneKeyForChapter(chapterId)`），全仓库唯一 |
| A3 | 多场景章的 `legacy_artifacts` 写入与 `migration_items.skipped` 必须在**同一事务**内（否则出现"归档了但没记跳过"） |
| A4 | `need_review` 清单必须可查：`SELECT target_pk, reason FROM migration_items WHERE batch_id=? AND migration_status='skipped' AND reason='anchors_multi_scene_need_review'` |
| A5 | 不得为多场景章写"空 `scene_states` 行"（`fixtures='[]'` 那种）——空行会被下游当成"这个场景没有家具"，与"没有这个场景"是两件事 |
| A6 | 若将来人工复核完成，只能**新增** `scene_states` 行（或走独立清理任务重迁），不得篡改 `migration_items` 的 `skipped` 结论 |

### 7. 验收标准

| # | 判据 |
|---|---|
| 1 | `0e2c1207` 第 1 章迁移后 `scene_states` 恰好 1 行，`scene_key='ch:<chapter_id>:s1'` |
| 2 | `a053dabd` 第 1 章迁移后 `scene_states` **0 行**，`legacy_artifacts` 有 1 条 `anchors_plan`，`migration_items` 有 1 条 `skipped` + 上述 reason |
| 3 | 重复执行迁移：`scene_states` 行数不变（派生 key 幂等） |
| 4 | 全库不存在 `【` 被拆成多行的 `scene_states`（即标签解析器根本没实现） |
| 5 | 3 个孤儿 plan 不产生任何 `scene_states` / `render_adaptations` 行 |

### 8. 对上游文档的影响

## 八、C-2：G0 四项锁（mode / aspect / base / assetMode）的存储位置

### 1. 原始依据

- `D01-05 §4.14`：`render_adaptations` **18 列**，逐列核对无 `mode` / `aspect` / `base` / `assetMode`。相关列只有 `seam_policy TEXT DEFAULT '{}'`（注释："段缝策略 JSON，**参与 adaptationHash**"）。
- `D01-06`（约 1557–1580 行）：`adaptationHash` 的 payload **是固定字段集**：`hashKind` / `adaptationVersion` / `track` / `profileVer` / `profileParams{max,shortFloor,minSlice,tailHoldMax}` / `seamPolicy`（取 `adaptation.seam_policy_json`）/ `units[]`。**没有 G0 四项锁**。
- `D01-05`（约 802 行）：四个 `profile_*` 参数必须快照并进 hash，理由是"改 `tailHoldMax` 后重算 hash 不变，等于参数变了但方案指纹没变"。同一条逻辑对 G0 锁同样成立——`mode/aspect/base/assetMode` 直接改变**提示词编译形态**（`Ref2VA`/`T2VA`、画幅、模型底座、素材模式），换任一值，编译产物就不同。
- `D02-01 §5.4`：`plan.mode/aspect/base/assetMode` → `render_adaptations`"**无处可放**；只能进 `seam_policy` JSON 或丢弃"。
- `D02-01 附录 C-2`：暂采用"塞 `seam_policy`"，并**明确标为技术债**。
- 实测（本轮）：5 个 plan **全部四项齐全**（`Ref2VA` / `16:9` 或 `9:16` / `BASE_LIVE` / `M2`），无缺失样本。

### 2. 当前问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | 四项锁无处存 | 只能借 `seam_policy`，而该列的语义是"段缝策略"（`hard_cut` / `tail_frame`） |
| 2 | 借用的后果 | `seam_policy` 会变成"什么都装的 JSON 袋"；下一项没地方放的配置也会往里塞，三次之后就没人说得清里面有什么 |
| 3 | hash 不覆盖锁 | `adaptationHash` 的 payload 里没有 G0 锁；若两个 adaptation 只有锁不同，**hash 会相同** |
| 4 | 与"锁属于版本化快照"的判断冲突 | 四项锁是切分/编译的输入，不是项目的实时配置；它们必须随方案冻结 |

### 3. 可选方案

#### 方案 ①：塞进 `seam_policy`（D02-01 的临时方案）

- **实现**：`seam_policy = {"seam":"tail_frame","source":"plan","g0":{"mode":"Ref2VA","aspect":"16:9","base":"BASE_LIVE","assetMode":"M2"}}`。
- **优点**：零 DDL；四项锁自动进 `adaptationHash`（因为 `seamPolicy` 在 payload 里）——这是它唯一的实质优势。
- **缺点**：① **语义污染**：`seam_policy` 从"段缝"变成"段缝 + 全局配置"，字段名与内容不符；② 读取方要"知道去 `g0` 子键里找锁"，没有类型、没有校验；③ 将来清理时无法判断"这个 JSON 里哪些键是 seam、哪些是锁"；④ 与任务书"不得把 `seam_policy` 永久变成通用配置容器"直接冲突。
- **数据库影响**：无。
- **代码影响**：编译/切分都要解析 JSON。
- **维护成本**：随时间上升（每加一项配置就多一个子键）。
- **结论**：✗（作为临时过渡可以，作为**最终决策**不行）。

#### 方案 ②：D01 V8 给 `render_adaptations` 加 `g0_locks JSON` 列

- **实现**：`g0_locks TEXT DEFAULT '{}'`，并在 `adaptationHash` 的 payload 中**显式加入** `g0Locks`（即同时改 D01-05 与 D01-06）。
- **优点**：**模型上最干净**——一行一个快照，锁与方案同生共死；hash 天然覆盖（改一次 hash 定义即可）。
- **缺点**：① 两处 D01 改动（DDL + hash 定义），是一次**真正的架构修订**，需要 V8 审核；② 阶段 1 不能等；③ 一旦定稿，`render_adaptations` 会从 18 列变 19 列，manifest、`D01-05` 的列数注释、D02-01 的建表序都要跟着改。
- **结论**：**方向正确，流程上本轮不可执行**。登记为 U-19（D01 V8 候选），与 D-03 的 job_id（U-16）、D-04 的 selected（U-17）同批。

#### 方案 ③：独立表 `adaptation_locks`（推荐）

- **实现**：

```sql
-- D02 实施侧扩展表：G0 锁按 (adaptation, key) 存，写入后不可变
CREATE TABLE IF NOT EXISTS adaptation_locks (
  adaptation_id TEXT NOT NULL,          -- → render_adaptations.id
  lock_key      TEXT NOT NULL,          -- mode / aspect / base / assetMode
  lock_value    TEXT NOT NULL,
  created_at    INTEGER,
  PRIMARY KEY (adaptation_id, lock_key)
);
```

- **优点**：① 不改 D01（表、列、hash 定义都不动）；② 语义干净：`seam_policy` 只管 seam；③ 可扩展（将来第五项锁加一行，不改表结构）；④ 可按 lock_key 建索引做统计（如"哪些方案是 9:16"）；⑤ 与 D-03/D-04 的选择一致——**D02 侧一律用"显式关系/扩展表"，不用 JSON 袋**。
- **缺点**：① 多一张表；② 一条 adaptation 变 5 行（1 主 + 4 锁），写要同事务；③ **`adaptationHash` 仍不覆盖锁**（这是本方案必须正面回答的缺口，见 §5）；④ 不能与 D-03/D-04 的关系表合并成一张"通用 EAV 表"——三种关系的主键维度不同（`task`↔`job`、`unit`↔`attempt`、`adaptation`↔`key`），合并后每个查询都要带 `type` 过滤，等于把强类型关系退化成 KV 袋。
- **数据库影响**：1 表（约 4 行/方案）。
- **代码影响**：`adapt/adaptation.js` 的 `create()` 多写 4 行；编译侧读一次。
- **维护成本**：低。
- **回滚难度**：低（删表；方案行不受影响）。
- **结论**：✓。

#### 方案 ④：把锁写进 plan 文件路径，只存路径

- **实现**：`render_adaptations` 存 `seam_policy.source_path` 指向原 plan 文件，锁从文件读。
- **优点**：零新表。
- **缺点**：① 文件是**可变外部状态**，plan 被改就与方案快照不一致；② 方案要能"独立复算"（D01-05 对 `profile_*` 的同一条要求），依赖文件就做不到；③ 文件可能被删（`data/` 会被清理）。**"快照"必须落在库里，不能落在可能消失的文件里。**
- **结论**：✗。

### 4. 推荐方案

**方案 ③**，并且必须补一条**补偿措施**（否则它比方案 ① 更弱）：既然 `adaptationHash` 不覆盖锁，就必须用"**锁不可变 + 锁变更即新版本**"来保证"同版本 ⇒ 同锁"。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 四项锁是否属于 adaptation 的版本化快照 | **是**。它们是切分与编译的输入，必须随方案冻结；**不是**项目实时配置 |
| 修改锁后是否要新版本 | **要**。锁变更 ⇒ `adaptation_version + 1` 的新行（`uq_ra_ver` 保证同 `(chapter,track,profile_ver)` 下版本唯一），旧行 `status='superseded'` + `superseded_by` 指向新行；**旧行的 `adaptation_locks` 永不 UPDATE** |
| 编译器读哪一份锁 | **读 `adaptation_locks`（按 `adaptation_id`）**。不读 plan 文件、不读 `projects` 上的实时配置、不读 `seam_policy` |
| 历史方案缺失锁时怎么办 | **四项必须齐全才建 adaptation**。缺任一 → 该章不建 adaptation，plan 原文进 `legacy_artifacts`，`migration_items` 记 `skipped` + `reason='g0_locks_incomplete'`。**不得用默认值补齐**（默认值是猜测） |
| 是否需要兼容旧版 plan | 需要"容忍缺失"，但**不容忍猜测**：缺失即降级为不建方案（本库实测 0/5 缺失，风险为零） |
| 如何避免锁值与当前项目配置不一致 | 锁是**快照**；项目配置（`video_aspect_ratio` / `video_model` 等）变了不回头改旧锁，而是产生新 adaptation。读侧若要"当前配置"，那是另一件事，不允许拿它覆盖快照 |
| hash 不覆盖锁怎么办 | 补偿三条：① 锁与方案**同事务写入**；② 锁表**只 INSERT，不 UPDATE**（由 `adaptation_id + lock_key` 主键 + 代码禁 UPDATE 保证）；③ 锁变更强制**新版本**，而 `adaptationVersion` 在 hash payload 内 → 两个"只有锁不同"的方案必然 `adaptation_version` 不同 → hash 不同 |

### 6. 实施约束

| # | 约束 |
|---|---|
| G1 | `adaptation_locks` 建在 `render_adaptations` 之后、`render_units` 之前（§十一 顺序 8.1） |
| G2 | 每个 adaptation **恰好 4 行**，`lock_key ∈ {mode, aspect, base, assetMode}`；缺一或多一即为缺陷（巡检 SQL：`GROUP BY adaptation_id HAVING COUNT(*) <> 4`） |
| G3 | 写 adaptation 与写 4 行锁**同一事务**；失败整体回滚 |
| G4 | `adaptation_locks` **禁止 UPDATE / DELETE**（除按批次回滚或删项目）；改锁只能建新 adaptation |
| G5 | `seam_policy` 只允许出现 seam 相关键（`seam` / `source` / `tailHold` 之类）；出现 `g0` / `mode` / `aspect` / `base` / `assetMode` 即缺陷（巡检：`seam_policy LIKE '%g0%'` = 0） |
| G6 | 编译入口校验：`adaptation_locks` 行数 ≠ 4 → 抛 `G0_LOCKS_INCOMPLETE`，**不得"缺省补齐后继续编译"** |
| G7 | 删项目时清 `adaptation_locks`：`DELETE WHERE adaptation_id IN (SELECT id FROM render_adaptations WHERE project_id=?)` |

### 7. 验收标准

| # | 判据 |
|---|---|
| 1 | 迁移后每个 adaptation 对应 4 行锁，值与 plan 原文逐字一致（`a053dabd`：`Ref2VA / 9:16 / BASE_LIVE / M2`；`0e2c1207`：`Ref2VA / 16:9 / BASE_LIVE / M2`） |
| 2 | 全库 `SELECT adaptation_id FROM adaptation_locks GROUP BY adaptation_id HAVING COUNT(*)<>4` = 0 行 |
| 3 | 改锁的路径只有"新建 adaptation"：对锁行执行 `UPDATE` 的代码不存在（code review + 巡检） |
| 4 | 构造"锁=16:9"与"锁=9:16"的两个方案（不同版本）→ `adaptationHash` 不同（由 `adaptationVersion` 差异带来，可断言） |
| 5 | `seam_policy` 中不含 `g0` 等键（全表扫描 0 行） |
| 6 | 缺一项锁的 plan（构造）→ 不建 adaptation，`migration_items.skipped` 有记录 |

### 8. 对上游文档的影响

**无**。`D01-05 §4.14` 的 18 列与 `D01-06` 的 `adaptationHash` payload **一字不改**；`D02-01 附录 C-2` 的"暂采用 `seam_policy`"由本决策取代，不改正文。

**登记 U-19**（D01 V8 候选，**可能构成 A 级**）：把 G0 锁纳入 `adaptationHash` 才是最彻底的解法。若 V8 修，建议 `render_adaptations` 加 `g0_locks JSON` 并把 `g0Locks` 加入 hash payload，同时删掉 `adaptation_locks` 表。**本记录不推动该修订**，仅登记。

## 九、M-01：Manifest 的正式存放路径

### 1. 原始依据

### 2. 当前问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 路径在 `data/`（被 gitignore） | 换机器/CI 没有 manifest，阶段 1 的验收判据无法执行 |
| 2 | D02-01 内部两处路径不一致 | 实施者不知道信哪个 |
| 3 | 阶段 0 的临时位置（`scripts/stage0/`） | 与"阶段 1 的 21 表清单"职责不同，若继续沿用，会变成"阶段 0 的清单被当权威" |
| 4 | 手抄列名的风险 | D01 历史上列数错过三次（`render_adaptations` 14→17→18）；本轮实测又发现**历史库 `projects` 的列顺序与新库不同**（`video_model` / `seam` 因 `ALTER` 补列而排在末尾），说明"按位置/列数比对"一定会错 |

### 3. 可选方案

#### 方案 A：`lib/core/schema-manifest.json`（推荐）

- **实现**：JSON 入库；生成器 `scripts/schema/gen-manifest.mjs` 从 **D01-05 的 DDL 文本**解析出每张表的列名；校验器 `scripts/schema/verify-manifest.mjs` 比对数据库。
- **优点**：① 不被 gitignore；② 与 `lib/core/` 同目录，改 DDL 的人一定会看到它；③ 测试与脚本都能按相对路径读到；④ 阶段 0 的 `verify-manifest` 逻辑可直接迁移（算法不变，只换路径）。
- **缺点**：① `lib/` 下多一个非代码文件（Next 打包时若被 import 会进 bundle，实测体量 < 50KB，可接受）；② 需要约定"只由生成器写，不许手改"。
- **结论**：✓。

#### 方案 B：保留 `data/schema-manifest.json` + `.gitignore` 加白名单

- **实现**：`!data/schema-manifest.json`。
- **优点**：与 D02-01 §4.5 字面一致。
- **缺点**：① `data/` 是**运行时数据目录**（14 个项目、库文件、备份都在里面），往里放"随代码走的规范文件"是概念混淆；② 白名单只放行一个文件，后续再加就会有人顺手放宽整个目录；③ 备份/清理脚本以 `data/` 为范围时容易把 manifest 带进备份或删掉。
- **结论**：✗。

#### 方案 C：`scripts/schema/schema-manifest.json`（与生成器同目录）

- **实现**：manifest 与 gen/verify 脚本放一起。
- **优点**：职责集中，不污染 `lib/`。
- **缺点**：① 运行时若想做结构自检（阶段 7 可选增强），要跨目录读；② 与"验收基准"的定位相比，"脚本目录"更像实现细节，容易被当成可再生的临时产物。
- **结论**：△ 可接受的次优。若审核倾向"不往 `lib/` 放数据"，改这个即可，其余约束不变。

### 4. 推荐方案

**方案 A**（`lib/core/schema-manifest.json`）。理由：manifest 是**验收基准**，它的位置应该让人"改 DDL 时必然撞见"；`lib/core/` 与 `db.js` 同目录，这一点最强。方案 C 可作退路。

### 5. 最终决策

| 问题 | 决定 |
|---|---|
| 正式路径 | **`lib/core/schema-manifest.json`**；唯一权威，手改无效（生成器覆盖） |
| 生成脚本位置 | **`scripts/schema/gen-manifest.mjs`**（从 `docs/D01/D01-05-*.md` 的 SQL 代码块解析列名 + 从 `lib/core/db.js` 解析现有表的 `expect`） |
| 是否纳入 Git | **是**。`.gitignore` 不动 `lib/`，无需白名单 |

| 如何避免手工维护出错 | ① `expect` 必须是**生成产物**，禁止手写；② 校验按**列名集合**比对（不按列数、不按位置）——实测历史库 `projects` 列顺序与新库不同，按位置必错；③ 单元测试断言"`tables` 中 14 张业务表的 `expect` 与 DDL 解析结果逐字一致" |
