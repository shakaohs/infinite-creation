## 二、D49-01：候选有效性守卫（本轮唯一的代码行为变更）

### 2.1 规则（写死在投影器，不靠调用方声明）

段上存在 `shot_videos` 候选时，投影只允许**完全幂等**的重投影：

| 维度 | 判定 | 处置 |
|---|---|---|
| A 组 17 列内容 | 与库内逐列相同 | 允许（`unchanged`） |
| A 组内容 | 有任一列不同 | **拒绝** `UNIT_SEGMENT_CANDIDATE_CONFLICT`（`reason=content_changed`） |
| 归属镜集合 | 与段的现有 owners 完全一致 | 允许 |
| 归属镜集合 | 增加 / 减少 / 合并 / 拆分 / 替换 | **拒绝**（`ownership_changed`，`reason∈{segment_grew, segment_split, ownership_mixed, ownership_changed}`） |
| 候选不存在 | — | 按冻结投影规则正常更新（不受本轮影响） |

**为什么不是"覆盖 + 报告"**：候选的 `input_hash` 由段的 A/B 组内容算出，内容一变候选就与段对不上；保留候选再覆盖内容，等于让下游把旧视频当成新内容的产物。
**为什么不是"换段 id 规避"**：换 id 只会把候选变成孤儿段，是把"错误关联"换成"静默丢失"，同样不可接受（D02-49 §二明令禁止）。

### 2.2 实现位置

| 位置 | 作用 |
|---|---|
| `project-units.js` `decideSegmentId()` | 段身份裁决阶段的**归属交集**判定：段有候选且与本组有交集 ⇒ 直接拒绝（增/减/合并/拆分四种） |
| `project-units.js` `assertCandidateSafe()` | plan 阶段（任何写入之前）逐段校验：内容差异 + 归属集合一致性 |
| `project-units.js` `candidateConflict()` | 错误码与 `detail` 形状的唯一构造点 |

`detail` 字段（固定）：`segment_id`、`candidates`、`ownership_changed`、`content_changed`、`changed_fields`、`current_owners`、`group_shot_ids`、`reason`。

### 2.3 修复前后行为差异（相对 `9844c5c`）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 单镜内容修改 + 候选 | 覆盖段 A 组，返回 `reused_with_candidates.content_changed=true` | **拒绝**，段/候选/`segment_id`/审计全不变 |
| 多镜段中单镜内容修改 + 候选 | 覆盖（整段内容重算） | **拒绝** |
| 两段合并（其中一段有候选） | 按"归属 ⊆ 组"判为同一段 ⇒ 覆盖 | **拒绝** `ownership_changed` |
| 一段拆分 | 换 `alt` 身份，旧段变孤儿（候选保留但不再被引用） | **拒绝** `segment_split` |
| 原段归属镜增加 | 覆盖 | **拒绝** |
| 原段归属镜减少 | 覆盖 | **拒绝**（内容随之变短 ⇒ `content_changed`） |
| 内容完全相同的重投影 + 候选 | 允许 | 允许（不变） |
| 候选不存在 | 正常更新 | 正常更新（不变） |
| 旧段失去全部归属 + 候选（D02-48 场景） | 换新 id，旧段/候选不动 | **不变**（有专项回归 `D49-09` 防误伤） |

> **与 D02-48 报告的关系**：D02-48 §九 的 `C01-16`（"内容修改 ⇒ 段 id 不变、候选关联显式保留并报告"）**已被本轮 §二推翻**。该用例已按新策略改写为"拒绝 + 删掉候选后可正常更新"的对照，原断言未被弱化而是被替换为更强的 fail-closed 断言。

### 3.4 为什么本轮**不**接线（三条理由，缺一条都不成立）

1. **语义不成立**：分镜阶段资产以**名称**引用，且资产可能尚未创建（LLM 常写"无"占位）。`writeShotAssets` 的 AS-1 要求"0 命中必须拒绝"，接上去会把"资产还没建"变成"分镜写不进去"，整批回滚。
2. **写语义会误删**：`writeShotAssets` 是**整组替换**。分镜 upsert 常常只带部分 role（例如只改人物），接线后未提交的 scene/prop 绑定会被删掉 —— 这是静默的数据损失。
3. **冻结边界**：B-06 明确"该分支只写 `story_shots`"。改这条边界属于阶段职责调整，不是缺陷修复。

1. 定义**按 role 分组的增量绑定**语义（或明确"一次提交即整组替换"的调用契约）；
2. 定义**资产名 → 资产 id** 的解析时机与失败策略（资产阶段绑定，而不是分镜阶段）；

## 四、U-36-2 决策包（待批准，未实施）

### 4.1 冻结条款核对

| 条款 | 原文要点 |
|---|---|
| D02-40 §4.2 表「投影 → `story_shots`」 | 只允许 UPDATE，**仅 `segment_id`**（字段范围合法） |
| D02-40 §4.2 注（U-36-2） | "建议把 `segment_id` 写入 `VOLATILE.story_shot`……**不由本任务书单方面决定**" |
| D02-40 §6.2 A2 | `story_shots` 的 `VOLATILE` = `updated_at`、`voice_ids`；update 审计"待实现"⇒ 实际口径为**应有** |
| D02-40 §6.2 A6 | **`shots` 表**的 create/update/delete 一律"应无"审计（投影产物不得刷日志） |
| 阶段 C 验收（§3.3） | 投影上线；A6 日志增量 0（针对 `shots`） |

**一处必须纠正的口径**：任务书把方案 B 的代价描述为"影响 A6 零增量判断"。核对后：A6 约束的是 `shots`（段行），`story_shots.segment_id` 属 **A2**。方案 B 不会破坏 A6；它影响的是 **A2 日志的可读性**与首投日志量。本报告按此更正后的口径做影响分析。

### 4.2 方案 A：把 `segment_id` 加入 `VOLATILE.story_shot`

| 维度 | 影响 |
|---|---|
| 改动点 | `lib/core/changelog.js` 的 `VOLATILE.story_shot`（冻结审计矩阵 §6.2 的一行） |
| 优点 | 投影回写指针不产生 A2 内容日志；"谁改了创作内容"这个问题不被派生写入污染 |
| 代价 | `segment_id` 的变更历史**不再可审计**；只能由当前状态 + 投影规则重算，无法还原"某镜曾经属于哪一段" |
| 风险 | 低。`segment_id` 不参与 `segmentInputHash`/`qcDependencyHash`，不影响指纹与求解 |
| 授权要求 | **需要**：改 §6.2 冻结矩阵，必须独立批准（可能触发决策升版） |

### 4.3 方案 B：保留（恢复）`segment_id` 的 A2 审计

| 维度 | 影响 |
|---|---|
| 改动点 | 投影回写从"直写 SQL"改为 `recordChange({entity:'story_shot', action:'update', ...})`（或经 `updateStoryShot`） |
| 优点 | 符合 A2"update 应有审计"的冻结口径；指针变更历史可查、可回溯 |
| 代价 | 首次投影每镜 1 条 A2 update；重投影不产日志（仅值变化才写）；`change_logs` 中出现大量"段归属"记录 |
| 风险 | 中低。① `change_logs` 体积与 UI 噪声上升；② 日志回放/漂移检测需确认不把派生指针变化当成内容漂移（结构化项目回滚本为 409，风险有限）；③ `segment_id` 变化会带 `updated_at`，若将来开放结构化回滚需额外处理 |
| 授权要求 | **不需要**改冻结条款（A2 本就说"应有"），但属于行为变更，仍需用户确认 |

### 4.4 推荐与代价

**推荐方案 A**，理由按重要性排序：

1. **语义正确**：`segment_id` 是投影派生的归属指针，不是创作内容。把它记成内容更新会让"内容变更历史"失真 —— 审计的价值在于区分"谁改了创作"和"系统重算了指针"，混在一起等于两者都不可读。
2. **A2 的真实保护对象不受影响**：A 组 17 列、B 组 5 列的变更仍逐条审计；`segment_id` 的变更可由投影输入重算（幂等派生）。
3. **B 的收益被高估**：请留意"仅值变化才写"的实现已把 B 的日志量压到"归属真变化的次数"，所以 B 的代价不是"刷屏"，而是"一类派生写入混进内容审计"。这既不构成 A 的必要理由，也不构成 B 的优势。

**接受 A 的代价**：放弃"某镜曾经指向哪个段"的直接历史。若将来出现"候选与段归属"纠纷需要取证，只能依赖 `shot_videos.shot_id` 的现存关联 + 投影日志（当前无）。**这是本方案唯一的实质损失，请批准时一并确认。**

**附加条件（无论选哪个）**：保留"仅在值变化时写"的幂等约束；`projectSceneUnits` 返回的 `segmentWrites` 作为非审计轨迹继续提供。

**当前状态**：**未实施**。`changelog.js` 与投影审计方式保持 `9844c5c` 的原样；等待用户明确批准后再动。
