### 1.4 三个必须先说清的事实

#### ① `shots` 一行 = 一个生成段，不是镜头

三条独立证据：

- 【代码】`lib/core/storyboard-import.js:770` `buildSegment()` 把同一段内的 N 个子镜压成一行，`duration = Σ 子镜时长`；
- 【代码】`lib/agent/tools.js:249` 的 `set_storyboard` 工具描述原文：「一个生成段（一个分镜）只写一次 blocking，镜行（sub_shots）里禁止再复述绝对左右」；
- 【实测】`shots.duration` 分布：`min 4 / max 30`，与"每镜 2.5–7.5 秒"的创作品味不符，而与 H3(15s) / SD2.5(30s) 的**单次生成上限**吻合。

**镜**只以文本行存在于 `sub_shots`，且【实测】有三种格式：

| 格式 | 条数 | 样例 |
|---|---:|---|
| `[镜头N]` 标记 | 13 | `00:00-00:05 [镜头1] 中景…` |
| 中文分段 | 37 | `0-3s：…` |
| 无分段 | 16 | 连续描述，无时间码 |

→ **D01 要建的 `story_shots`（镜级）在现有库里没有对应物，只能从文本反解。**

#### ② "段"的元信息在文件系统里，不在数据库

【代码】`lib/agent/tools.js:1976` `saveStoryboardPlan(ctx.projectId, title, plan)` → 写 `data/projects/<id>/context/storyboard-plan.json`。

```json
{ "mode":"Ref2VA", "aspect":"9:16", "base":"BASE_LIVE", "assetMode":"M2", "seam":"tail_frame",
  "anchors": { "positions":[...], "directions":[...], "furniture":[...], "doors":"..." },
  "beats": [ { "shotRange":"1-3", "durationSec":28, "emotion":"...", "intensity":9, "seam":"..." } ] }
```

【实测】目前 5 个项目有该文件（`data/projects/*/context/storyboard-plan.json`）。

**这已经是 `render_units` + `render_unit_shots` 的雏形**：`beats[].shotRange` 就是"这个单元覆盖镜 1–3"，`durationSec` 就是 `unit_duration`。但它有三个致命差别：

| 差别 | 后果 |
|---|---|
| 存文件，不在库 | 无法 join、无法事务、无法按单元查产物 |
| 无版本 | 改一次覆盖一次（只留 `.bak-<ts>`），`adaptation_version` 无法追溯 |
| 无 track | 一个项目一个 `video_model`，无法"同分镜双模型并存" |

#### ③ 全项目零 hash、零动作结构、零质检表

【代码】`grep -rn "sourceSpecHash\|adaptationHash\|compiledHash\|specHash" lib app studio/src` → **0 命中**。
【代码】`grep -rn "createHash\|sha256" lib` → 只有 `lib/core/subtitle.js:452`（音频完整性校验），与分镜无关。
【实测】14 张 D01 目标表在库中**一张都不存在**（§3.2）。
【代码】无 `shot_actions`、无 `state_in/out`、无 `qc_reports` 概念。

```js

Jobs.create({ ..., checkpoint: { subject: shotId, render: ..., skill } })// 238
// 实测库里 interrupted 的三条：
//   type=create | phase=分镜视频 | cp={"subject":"第1章","chapter":"第1章"} | progress={}
```

### 4.3 `render_tasks` / `queue_items` / `scheduler` 三层边界

审核要求把这三者分开。现状是**一层缺失、一层是纯基础设施、一层是能力**：

| 层 | 是什么 | 现有载体 | 现状 | D01 对应 |
|---|---|---|---|---|
| **业务任务实体** | "为某个单元生成一条视频"这件事本身。要永久可查、可审计、可失败分类、可局部重试 | **不存在**。最接近的是 `jobs`（13 列），但它的粒度是**整章/整项目的一次流水线**，且 `type` 只有 `create`/`chapter-video`/`regenerate`/`asset-image`… 没有"单元"概念 | 粒度过粗 | `render_tasks`（14 列，待建） |
| **调度排队机制** | "现在轮到谁跑"。负责任务的等待、租约、退避、去重、计费 | `queue_items`（25 列，**0 行**） | 已实现，**从未启用** | `render_tasks` 的排队载体（不是替代品） |
| **调度执行能力** | "怎么公平地挑下一个"。纯函数 + 循环 | `lib/core/scheduler.js`（`planDispatch`/`fairOrder`/`claim`/`finish`/`fail`/`runInQueue`） | 可用 | 原样复用 |

**`queue_items` 为什么不能等同于 `render_tasks`**——看它的 25 列就够了：

```
id, job_id, project_id, owner_id, pool, kind, status, priority, seq,
attempts, max_attempts, not_before, lease_until, worker_id, remote_task_id,
dedupe_key, payload, last_error, amount, unit_price, currency,
enqueued_at, started_at, finished_at, updated_at
```

这 25 列里**没有一个业务字段**：没有 `unit_id`、没有 `shot_id`、没有 `prompt_package_id`、没有 `track`。它只有"谁、多急、试了几次、租约到几号、多少钱"。`payload` 是唯一能塞业务信息的地方，但它是 JSON 文本（`{ spec, kind }`），不可索引、不可 join、不可做外键。

它还要被**回收**：`status` 只有 `waiting / running / done / cancelled` 四值，`done` 之后就是历史噪声，`fail(retryAt)` 会把它退回 `waiting` 并覆盖 `last_error`。**业务任务需要的是"每次尝试都留一条、失败原因可分类、能回答三个月前这条为什么没过"**——这是审计需求，队列表结构上做不到。

**三者关系（D02 必须按这个方向落地）**：

```
render_tasks（业务单据，永久）
   id, unit_id, prompt_package_id, track, status, error_code, ...
        │ 1 : N
        ▼
render_attempts（每次抽卡，永久）           ← 现有 shot_videos 是它的雏形
   task_id, attempt_no, seed, output_path, selected
        │ 1 : 1（每次尝试入队一条）
        ▼
queue_items（调度记录，可回收）              ← 现有表，原样复用
   job_id / payload.task_id, pool, priority, lease_until, attempts
        ▲
        │ 读写的唯一能力
   scheduler.js（fairOrder → claim → finish/fail）
```

**状态映射（不能混用两套状态机）**：

| 层 | 状态值 | 谁写 |
|---|---|---|
| `render_tasks` | 待定（D01 未冻结此枚举，D02-01 定）：`pending/queued/running/succeeded/failed/cancelled/superseded` | 业务层 |
| `queue_items` | **实测四值**：`waiting / running / done / cancelled` | `scheduler.js`（`Queue.claim` 置 `running`，`finish` 置 `done`，`fail` 退回 `waiting` 或置 `cancelled`） |

→ **`queue_items.status='done'` 不等于 `render_task.status='succeeded'`**。队列 `done` 只说明"这次排队跑完了"，跑完的结果可能是模型返回空视频。**业务成功与否必须由 `render_attempts` 的产物与 QC 判定**，写回 `render_tasks`。这条边界不划清，会出现"队列全绿但成片缺镜"。

**重试与恢复的分工**：

| 问题 | 归谁 | 现状 |
|---|---|---|
| 排队等太久、租约过期、并发穿透 | `scheduler.js` + `queue_items.lease_until` | ✅ 已有（`claim` 带租约、`attempts` 自增、`not_before` 退避） |
| 模型调用失败要不要再试一次 | `queue_items.max_attempts` + `fail(retryAt)` | ✅ 已有（自动退避重排） |
| **这个单元最终失败了，要不要换 seed / 换片段 / 换模型重来** | **`render_tasks`（业务决策）** | ❌ 完全没有。现在只有人工点 `regenerate_shot` |
| 进程崩溃后哪些任务没跑完 | `jobs.status='interrupted'`（粗粒度） | ⚠️ 只能到"整章没跑完"，到不了"哪几个单元" |

**结论**：`queue_items` + `scheduler` 是**已经写好的基础设施，0 成本复用**；`render_tasks` 是**必须新建的业务层**，且它的存在理由不是"功能缺"，而是"现在的 `jobs` 粒度回答不了单元级问题"。

### 4.4 资产内容指纹：D01 的 hash 依赖它，现有完全没有

D01 的 `sourceSpecHash` 要求把"资产内容指纹"纳入 payload（否则换了一张定妆照，hash 不变，同源证明失效）。

【实测】`assets` 表 26 列：`id, project_id, category, name, parent_id, description, voice_desc, voice_desc_used, prompt, prompt_used, prompt_locked, lyrics, max_duration, negative_prompt, voice_ref, image_path, audio_path, video_path, source, consistency_key, versions, params, status, error, created_at, updated_at`。

**没有任何内容指纹列**。`image_path` 是文件路径——**同一路径换文件内容，路径不变**，指纹需求依然不满足。

→ 归入 C 类（新增）。可选实现：① 新增 `content_fp` 列（路径 + size + mtime 派生，弱指纹）；② 对图片/音频文件本身算 sha256（强指纹，但 143 个资产要跑一遍）。**D02-01 定，本轮不实现。**

### 5.2 加载机制【代码】

### 阶段 2：迁移历史（4 步，**按迁移批次**可回滚）

**V1 的回滚方案（`DELETE FROM story_shots` 等）作废**。理由不是"麻烦"，而是它同时违反三条：① 删掉的是**整张表**，包括新业务后来写进去的数据；② 无法回答"这次迁移到底写了哪些行"；③ 一旦新链路已在用这些行，删表会造成外键悬空与前端白屏。

**回滚的最小单位必须是"一次迁移批次写进去的行"，不是"一张表"。**

**2.0 迁移登记结构（新增，属 C13）**——只描述要求，本轮不建表：

| 字段 | 作用 |
|---|---|
| `migration_batch_id` | 一次迁移的批次号（如 `mig-20261127-01`），**所有被写入的行都必须带它** |
| `migration_source` | 来源记录：`shots.id` / `shots.idx` / 源格式（`[镜头N]`\|中文分段\|无分段）/ 解析器版本 |
| `entity_table` + `entity_pk` | 精确到"哪张表的哪一行"，回滚靠它定位 |
| `checksum` | 写入内容的规范化哈希，用于"迁移后内容被改过"检测 |
| `state` | `staged` / `committed` / `rolled_back` |
| `committed_at` / `rolled_back_at` | 时间戳 |

**2.1 五条硬规则**：

| # | 规则 | 违反后果 |
|---|---|---|
| R1 | **回滚只删本批次创建的行**：`WHERE migration_batch_id = ?` | 删到别人/新业务的数据 |
| R2 | **已被新业务引用的行不得删**：删除前检查引用（如 `story_shots` 被 `shot_actions`/`shot_blockings`/`render_unit_shots` 引用，且引用方不是本批次） | 外键悬空 |
| R3 | **迁移幂等**：同一 `(source_table, source_pk, entity_table)` 重复执行只更新不重复插入；重跑同一批次不产生新行 | 重复镜、总数对不上 |
| R4 | **前后数量核对**：迁移前记录源端计数，迁移后比对目标端计数与"预期折算比"，差异必须逐条解释 | 静默丢镜 |
| R5 | **备份先行**：每次写主库前 `cp data/ic.db data/_backup/ic-<ts>.db` + `PRAGMA integrity_check` + 关键表行数比对；恢复演练一次才算验证过 | 无法回退 |

**2.2 四个迁移步（每步一个批次号）**：

| 步 | 内容 | 源端计数（实测） | 预期目标计数 | 回滚方式 |
|---|---|---|---|---|
| 2-1 | `story_shots` 落库（66 段 → N 镜） | 66 段 | 约 200–300 镜（**估计值，需 1-5 干跑确认**） | `DELETE FROM story_shots WHERE migration_batch_id='mig-…-01'` 且该镜未被本批次以外的表引用 |
| 2-2 | `shot_assets` 回填（6 个 JSON 列 + `refs` → N 行） | 66 段 × 6 列 | 约 300–500 行 | 同 2-1，限 `mig-…-02` |
| 2-3 | `shot_blockings` 回填（13 段文本 → 逐人） | 13 段 | 约 30–60 行，坐标全 `NULL` | 限 `mig-…-03` |
| 2-4 | `render_adaptations` 回填（5 个项目 `beats` → 方案） | 5 个项目 | 5 条方案（`adaptation_version=1`） | 限 `mig-…-04`；**同时把 `storyboard-plan.json` 保留原位**，回滚后旧链路仍能读 |

**2.3 已被新业务引用的保护**（R2 的具体判据）：

```
删除候选集 C = SELECT * FROM story_shots WHERE migration_batch_id = 'mig-…-01'
对 c ∈ C：
  if 存在 shot_actions/shot_blockings/shot_states/shot_assets/render_unit_shots 行
     引用 c.id 且该行的来源标记不是同一批次
  → 该行标记 PROTECTED，不删，人工判定
```

如果 `PROTECTED` 非空，回滚**部分成功**，必须报告"哪些行保留了、为什么"，**不得静默跳过**。

**2.4 失败恢复**：迁移脚本必须整体在一个 `tx()` 内，任一步抛错即 `ROLLBACK`；若进程在中途被杀，靠 `migration_batch.state='staged'` 识别残留，下次启动先清扫（`state='staged'` 且超时的批次按 R1 回收）。

## 十三、结论

### 13.1 四个数字

| 项 | 数 |
|---|---:|
| D01 目标表 14 张中，**完全不存在** | **10 张** |
| 有近似物但需改造 | **4 张** |
| 模块复用分类（A 原样 / B 改造 / C 新增） | **8 / 14 / 14** |
| D01 的 49 条回归用例，现有测试覆盖 | **0–2 条** |

> 复用率从 V1 的"14 项 A"收敛到"8 项 A"，不是因为评估变悲观，而是 V1 把"要改读法"的模块也算成了可复用。8 项 A 的共同点是**它们都不认识"镜"这个概念**——镜级重构碰不到它们，这才是真复用。

### 13.2 一句话结论

**现有工程是一个"段级"的生产工具，D01 是一套"镜级"的设计。差距不在功能多少，而在"最小可寻址单位"不同**：

- 现有：最小单位是 `shots` 一行（一个生成段），镜只是这段里的一行文本；
- D01：最小单位是 Shot（有 47 个字段、动作、空间、状态），段是它的**派生**。

所以 D02 的第一步不是"加字段"，而是**建"镜"这一层**（`story_shots` + 解析器），否则后面所有表（`shot_actions`/`shot_blockings`/`shot_states`）都没有挂靠点。

### 13.3 最容易被低估的三个风险

1. **M1（`blocking` 一列缺失）**——它是"现在就能炸"的部署 bug，不是设计问题。修它只要**一列**（V1 误以为三列），但不修，阶段 1 的所有测试都在一个异常库上做；而且 `blocking` 是 D01 站位的唯一历史来源（13/66 有值），缺它连迁移源都没有。
2. **M3（13 条 `blocking` 是画面方位）**——它决定了"越轴检测对历史数据永远不可用"。这不是实现问题，是数据本身缺坐标。
3. **B10（`set_storyboard` 工具已 2,000+ 字）**——D01 的 47 字段不可能塞进一个 function-calling schema。实施时必然要拆成多个工具（写镜、写动作、写空间），这会改变 Agent 的工作方式，不只是加字段。

> 补一个 V2 新增的：**M13（没有迁移批次机制）**。它不"炸"，但它让"回滚"这件事在现有工程里**根本没有实施载体**——`change_logs.batch_id` 只覆盖内容编辑，覆盖不到批量迁移。这是阶段 2 必须先补 C13 的原因。
