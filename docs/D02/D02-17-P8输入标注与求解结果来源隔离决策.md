## 一、结论先行

| 问题 | 结论 |
|---|---|
| 只保留 `rel` 够不够 | **不够**。实测 `src` 与 `conf` 都是真输入：`src` 会改写/传播继承链起点，`conf` 是 `×0.9` 的衰减基数 |
| 冲突的本质 | 不是"字段多少"，而是**同一个 JSON 出现在两个位置时含义不同**：在 `shot_states.meta` 里是求解结果，在 `shots[].meta` 里被当成输入 |
| 采用方案 | **A（字段来源分离）+ C（禁止整体回搬）**；B 仅在"有来源标签"时部分可行，但它无法覆盖 `rel`/`conf`（无标签位），故不作主方案 |
| 落地方式 | 新增 `solver-input.js`（结构校验 + 来源校验），在 `solveContinuity` 的 **Hash 计算之前**执行；并导出给 P8 组装层直接调用 |
| 回归 | P6+P8 专项 **161/161**、P5 **105/105**、CK-2 **69/69**、全量 **834/806/17/11**（失败名单 `diff` 为空） |

## 二、`rel` / `src` / `conf` 的读取点、影响与输出位置

### 2.1 读取点（`lib/core/continuity/solve-continuity.js`，本轮行号）

| 字段 | 读取位置 | 怎么用 | 输出写回位置 |
|---|---|---|---|
| `rel` | `seededRel()` **:232** → `applyField(…, rel, …)` **:406–415** | 决定走哪条分支：①`unknown`→沿用；②比对（仅两侧 `known` 才 FAIL）；③同值不重写；④写入；否则⑤沿用并衰减 | `metaIn['chars.<id>.<f>'].rel` |
| `rel`（继承侧） | `inRelOf()` **:291** | 判断"上镜的可信度"，决定 ④ 还是 ⑤ | 同上（沿用分支写 `inRel`） |
| `src` | `originOf()` **:286** | 只认 `carried:` 与 `prev_shot:` 两种前缀，取其后段作继承起点；不匹配则**回退 `prev.id`** | `carried:<origin>` / `blocking:<id>` / `prev_shot:<id>` / `rule:no_value` / `scene_baseline` |
| `conf` | `inConfOf()` **:292** | 沿用分支的基数：`conf × 0.9`（`CARRY_DECAY`） | 写入分支取 `REL_CONF`（known 0.95 / inferred 0.40）；沿用分支 `×0.9` |

三条都在 **Hash 之前** 就被 `solverInputHash` 读取（`SOLVE_META_FIELDS = ['rel','src','conf']`，`solve-hash.js:52`），所以"Hash 覆盖实际输入"这条本来就成立 —— 问题在**来源**，不在覆盖面。

### 2.2 实测：三者都会改变输出（这就是"不能只留 rel"的证据）

固定三镜 `a(manual, standing) → b(ai, sitting) → c(ai, walking)`，只改 `b` 的一条标注：

| `b` 的标注 | `b.out.posture` | `b.meta` |
|---|---|---|
| 无 | `standing`（沿用） | `{rel:known, src:carried:a, conf:0.855}` |
| `{rel:'known'}` | **`sitting`（被改写）** | `{rel:known, src:blocking:c1, conf:0.95}` |
| `{src:'carried:sh_99'}` | `standing` | `src` **被伪造成 `carried:sh_99`**（一个不存在的镜） |
| `{conf:0.5}` | `standing` | `conf` **0.45**（基数被换：0.855 → 0.5×0.9） |
| 整份状态行回搬 | **`sitting`（被改写）** | 同 `rel:'known'` 行 |

再看跨镜传播：`b` 的 `src` 一旦被写成 `carried:sh_99`，`c` 会跟着记 `carried:sh_99` —— 伪造的起点**沿链传播**。

> 所以"只保留 `rel`"有两种错法：① 从 Hash 里删掉 `src/conf`，但求解器照旧读 → **结果变、Hash 不变**（最坏的一种）；② 连求解器一起删 → 丢掉"人工指定置信度/来源"的能力，且违反 §六"不删除现有 `src/conf` 求解能力"。

## 三、三方案比较

| 判据 | **A 来源分离** | **B 同结构 + 来源识别过滤** | **C 禁止整体回搬** |
|---|---|---|---|
| 阻止"值被改写"（`rel:'known'` 把 carried 变写入） | ✅ 需配合 C | ✅ 靠 `src` 标签识别 | ✅ 直接不搬 |
| 阻止"继承起点被伪造" | ✅ | ✅ `carried:` 前缀可识别 | ✅ |
| 阻止"置信度换基" | ✅ | ⚠️ `conf` **没有标签位**，无法判断它来自人工还是上一轮求解 | ✅ |
| 覆盖 `rel`（裸标注无 `src`） | ✅ 归为"输入标注" | ❌ 无标签 → 无法识别来源 | ✅ 只要来自新数据即可 |
| 需要新增存储 | ❌ 不需要 | ⚠️ 需要"来源"字段（本轮禁止 DDL） | ❌ 不需要 |
| 保留 `src/conf` 能力 | ✅ | ✅ | ✅ |
| 可机检（不是靠自觉） | ✅ `src` 前缀规则 | ✅ | ✅ 与 A 共用同一道闸 |
| 对既有 141 条测试 | 0 影响 | 0 影响 | 0 影响 |

**推荐：A + C。** 理由：

1. **A 解决"含义"**：`shot_states.meta` 定义为**求解结果**（`rel/src/conf/ver` 全部由求解器写出）；`shots[].meta` 定义为**输入标注**，只接受 `src` 以 `manual:` 开头或缺省的条目。同一份 JSON 不再两用。
2. **C 解决"流向"**：P8 **禁止**把 `shot_states.meta` 整体回搬；输入标注只能来自本轮新产生的人工/适配层数据。
3. **B 只解决一半**：`src` 有前缀可认，但 `rel`（裸标注）与 `conf` 没有标签位；要让它成立必须加数据位（本轮禁止 DDL），且会引入"哪一侧优先"的新判定 —— 那是设计新优先级，超出本轮授权。

**为什么不用"只保留 rel"**：见 §2.2 —— `src`/`conf` 是会被读取且会改变输出的真输入，删掉就违反"Hash 必须覆盖求解器实际读取的所有输入"（§四.4）。

## 四、P8 最终接口契约

### 4.1 八条逐条落实

| # | 要求 | 落实方式 | 机检 |
|---|---|---|---|
| 1 | `shot_states.meta` 是正式持久化位置 | 不变（TEXT，`DEFAULT '{}'`；`rel/src/conf/ver/__solver` 全量落库） | `R1-k`（D02-15） |
| 2 | `shots[].meta` 是求解器输入通道，不是数据库字段 | `story_shots` 48 列实测无 `meta` | `R1-k` |
| 3 | 输入标注与求解输出不得隐式覆盖 | `assertAnnotationOnly(shotId, seed)`（`solver-input.js`）：`src` 命中求解产出前缀即抛 `META_IS_RESULT_FEEDBACK` | `P8-C8/C10/C11` |
| 4 | 求解器实际读取的所有输入进 `solverInputHash` | `SOLVE_META_FIELDS = rel/src/conf` **保持不变**（三者在 carried 分支都被读） | `P8-C4~C7` |
| 5 | 继承来源与置信度跨轮保存 | `carried:<起点镜>` + `conf × 0.9` 逐镜衰减；落库由 P9 负责 | `P8-C13/C14` |
| 6 | `global_no` 必须有效，不得静默按 0 排序 | `assertSolverInput`：非有限数或 `<1` → `reason=SHOT_GLOBAL_NO_INVALID` | `P8-C17` |
| 7 | 所有镜头 `scene_key` 必须等于 `sceneKey`，跨场阻断 | 同上 → `reason=SHOT_SCENE_MISMATCH`（带 `shot_ids`） | `P8-C18` |
| 8 | Hash 与求解器使用同一次组装的输入对象 | `solveContinuity` 内部先 `assertSolverInput` → 再算 Hash → 再求解，同一 `shots` 引用 | `P8-C2` |

### 4.2 校验顺序与错误形状

```
solveContinuity({ projectId, sceneKey, shots, sceneState })
  ├ ① shots 必须是数组            → CONTINUITY_SOLVER_FAILED
  ├ ② sceneKey 必须非空            → CONTINUITY_SOLVER_FAILED
  ├ ③ assertSolverInput()          → reason: SHOT_ID_MISSING → SHOT_GLOBAL_NO_INVALID → SHOT_SCENE_MISMATCH
  ├ ④ solverInputHash()            ← 坏输入不会先算出"看起来有效"的指纹
  └ ⑤ 逐镜 assertAnnotationOnly()  → reason: META_IS_RESULT_FEEDBACK / META_SRC_UNKNOWN
```

统一 `code = 'CONTINUITY_SOLVER_FAILED'`，细分原因放 `reason`（`solver-error.js` 提供唯一错误工厂）。
**不拆多个 `code`** 的理由：上游（任务层/测试）已按单个 `code` 识别"求解失败"，拆开会让既有 catch 漏掉新错误。

### 4.3 允许 / 禁止速查

| `shots[].meta` 条目 | 判定 |
|---|---|
| `{rel:'unknown'}` | ✅ 裸标注（人工） |
| `{rel:'known', src:'manual:sh_40', conf:0.9}` | ✅ 带来源的人工标注 |
| `{rel:'known', src:'blocking:c1', conf:0.95, ver:2}` | ❌ `META_IS_RESULT_FEEDBACK`（整份状态行回搬） |
| `{src:'carried:sh_99'}` | ❌ 同上（伪造起点） |
| `{src:'whatever:x'}` | ❌ `META_SRC_UNKNOWN` |
| `{ver:9}` / `{__solver:{…}}` | 忽略（`ver` 会被 `spec_version` 覆写，`__solver` 被剔除） |

### 5.1 多轮关系（关键三行）

```
round 1（无标注）           hash=H1   b.posture=standing  b.src=carried:a  b.conf=0.855
round 2（同输入）           hash=H1   状态逐字段相同
round 3（人工标 rel=known） hash=H2   b.posture=sitting   b.src=blocking:c1 b.conf=0.95
回搬 state.meta             → 抛 META_IS_RESULT_FEEDBACK（不再产生 H3）
```

即：**干净的输入下，Hash 只随"人工标注 + 创作数据"变化；求解结果不再参与输入，于是不会出现 D02-16 观察到的"H1→H3 假失效"。**
