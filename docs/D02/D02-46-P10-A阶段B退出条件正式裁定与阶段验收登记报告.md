## 一、D02-40 §3.0 与 §3.2 的冲突分析

### 1.1 两处原文

**§3.0 阶段总览 · 阶段 B 行**（D02-40 第 250 行，逐字）：

> **B**｜Stage 3 创作写入链（场次、镜、资产引用、站位、动作）｜硬依赖：**A 完成 且 P2/P4 通过**｜退出条件：**五个写入器均有生产调用方**；A1~A5 审计按矩阵生效

**§3.2 工作项（执行与验收面）· 下游调用方列**（D02-40 第 416~421 行，逐字）：

| 工作项 | 下游调用方（原文） | 归属阶段 |
|---|---|---|
| B-01 | 场次列表、投影、求解 | 场次列表属 B 内；投影属 C；求解属 E |
| B-02 | 分镜生成、投影 | 分镜生成属 B 内；投影属 C |
| B-03 | 投影、渲染绑定 | **C** |
| B-04 | 投影、求解 | **C / E** |
| B-05 | 投影、求解 | **C / E** |
| B-06 | C 阶段投影 | **C** |

### 1.2 冲突的准确形态

1. **同一份冻结文件里，退出条件要求的东西由它自己的下游列推到了后续阶段。** §3.0 说阶段 B 退出时五个写入器「均有」生产调用方；§3.2 却把 B-03/B-04/B-05 的下游写明是「投影」「求解」，而投影属阶段 C（§3.3）、求解属阶段 E（§3.0 阶段 E 行）。**要满足退出条件，必须先做 C 或 E；而 C/E 的硬依赖里写着「A、B 完成」。**
2. **这与 D02-37 修掉的 P2/P4 循环依赖结构相同**：把「测一个尚未产出之物」的判据写成前一个阶段的退出条件。D02-37 的结论是「Gate 的位置由它测的东西在冻结时是否已存在决定」，不能反过来。本轮的裁定沿用同一条原则。
3. **冲突不是措辞瑕疵，而是判据缺一层。** 「有生产调用方」把两件事压成一件：① 这个写入器**该由谁用**（归属）；② 它**现在**是否已经在用（时点）。A3/A4/A5 的归属明确（C/E），时点明确在后续阶段——原句没有表达这一层，于是任何实现的阶段 B 都判不过。
4. **实测确认（本轮独立核验，见 §四）**：A1、A2 有真实生产入口链路；A3、A4、A5 零生产调用方，且它们的调用点**在代码里根本不存在**（不是「写了没接」）。按原句判定，阶段 B 永远不可能通过。

### 1.3 为什么不能靠「补几个调用」解决

任务书 §五 已禁止「制造无实际业务意义的空调用」。除此之外还有一条技术理由：**A3/A4/A5 的入参只能从投影或求解上下文里得到**——`writeShotAssets` 要 `input`（三张图的解析结果）、`writeShotBlockings` 要按角色排布的站位矩阵、`writeShotActions` 要时间轴上的动作行。在阶段 B 里没有这些数据源，任何「先接上」的调用都只能是传空数组，那会把「表里有行」变成「表里有空行」，比不接更糟。

### 4.3 两处必须写清的实情

1. **A1 与 A2 的可达条件都是 `structured_spec=1`。** 真实库里 14 个项目**全为 0**（D02-45 §4.2 实测，本轮未重查数据库），也就是说：链路存在、代码可达、**但当前没有任何项目真的走过**。这不影响「接线真实存在」的判定（生产入口就绪，等的只是开关与一次真实运行），但**不能用「已接线」推出「已被验证」**。建议阶段 C 首个结构化项目作为端到端验证（§九）。

### 4.4 判定（原样读）

> **阶段 B 退出条件第 1 条，按本裁定 §2.1 的口径：通过。**
> 理由：五个写入器的**能力交付**全部达成（§六）；**调用方归属已判定并登记** —— A1/A2 有真实生产入口链路，A3/A4/A5 明确归属阶段 C/E 并写明责任（§八）。
> **按 D02-40 原句（未解释）的口径：不通过**（A3/A4/A5 零调用）。两种口径的差异即本裁定的全部内容，不得只引其中一句。
