## 三、R4：`nextShotState` 契约收紧

### 3.1 修复前的漏洞

```js
// lib/core/qc/deps/index.js（修复前）
const stateLike = ['state_in', 'state_out', 'conflicts']
  .some((k) => Object.prototype.hasOwnProperty.call(nextShot, k));
if (!stateLike) throw ...QC_DEPS_NEXT_SHOT_NOT_STATE;
```

而 A-06 只读一项：

```js
// lib/core/validate/action.js:377（P5，不改）
const chars = toObj(toObj(nextState.state_in).chars);
```

于是 `{ state_out: {...} }` 能通过校验，但投影出来的 `nextShotState.state_in` 仍是 `null` —— A-06 的规则级 Hash 恒定、末镜哨兵同时失效。**校验存在，却没有覆盖它要保护的那一项**。

### 3.2 修复后

```js
const hasStateIn = Object.prototype.hasOwnProperty.call(nextShot, 'state_in');
if (!hasStateIn) throw ...QC_DEPS_NEXT_SHOT_NOT_STATE;
```

判据与任务书七条逐条对应：

| 输入 | 期望 | 实际 |
|---|---|---|
| `{state_in: null}` | 通过 | 通过（`state_in` 值可为 null，"状态未知"≠"字段缺失"） |
| `{state_in: {...}}` | 通过 | 通过 |
| `{state_out: {...}}` | 拒绝 | `QC_DEPS_NEXT_SHOT_NOT_STATE` |
| `{conflicts: []}` | 拒绝 | 同上 |
| `{state_out, conflicts}` | 拒绝 | 同上 |
| `null`（末镜） | 通过 | 通过，哨兵 `__last__` 语义不变 |
| A-06 对下镜 `state_in` 敏感 | 必须变 | `nextShot.state_in` 位移 → **只有 A-06** 的 Hash 变（§5.4 矩阵） |

其他保持：`nextShot` 与 `nextShotState` 仍指向同一对象（两者只填一个都能落到同一处）；非对象入参仍报另一个码 `QC_DEPS_NEXT_SHOT_INVALID`，与"形状不对"分开，便于调用方区分"传错了类型"和"传错了行"。

## 四、R1：`shot.meta` 的实际数据类型与调用链

### 4.1 核查结论（逐项回答任务书要求）

| 核查项 | 结论 | 取证方式 |
|---|---|---|
| `story_shots` 有没有 `meta` 列 | **没有**。48 列逐列实测无 `meta` | `:memory:` 建 DDL 后 `PRAGMA table_info(story_shots)`（`R1-k`） |
| `shot_states.meta` 的声明类型 | `TEXT`，`DEFAULT '{}'`，内容为 JSON 对象串 | 同上（`R1-k`） |
| 传入求解器前是否已 `JSON.parse` | **没有**。全仓不存在 `story_shots` / `shot_states` 的行映射器（`db.js` 的 `toShot` 只服务 legacy `shots` 表，不解析 meta） | `grep -rn "FROM story_shots"` 只命中 `global-no.js`（选的列不含 meta）与 `shot-assets.js`（只取存在性） |
| 生产侧调用 `solveContinuity` 的入口 | **0 个**。P6 交付的是纯函数层，P8/P9 才接线 | `grep -rn "solveContinuity(" lib app` 只命中定义处 |
| Hash 与求解器是否拿到同一份 meta | 是。两处都走 `normalizeShotMeta()`，底层同一 `parseShotMeta()` | `solve-hash.js:73`、`solve-hash.js:174`、`solve-continuity.js:213` |

### 4.2 一处必须更正的事实

D02-14 §3.1 写的是「数据库里明明有显式 unknown 标注」。**本轮实测：`story_shots` 没有 `meta` 列**，所以那句话不准确。准确表述是：

- `meta` 只存在于 **`shot_states`**（D01-04 §5.2 的字段级可靠性映射，8 列中的第 4 列），类型 TEXT；
- 求解器的 `shots[].meta` **不是 DB 列**，而是调用方在复合镜头对象上附加的字段（与 `blockings` / `actions` 同一种做法）；
- 因此风险位置不在"读库"，而在**调用方边界**：谁把 DB 里的 TEXT 直接塞进来，谁就会踩到"字符串被当空对象"。

这个更正不改变结论（边界解析仍然必要，且 `shot_states.meta` 走的是同一条路径），但改变了"为什么必要"的说法。`R1-k` 把这条事实写成机器断言：若将来真给 `story_shots` 加 `meta` 列，测试会失败，强制重新决策是否纳入求解输入。

### 4.3 修复：边界单点解析

```js
// lib/core/continuity/solve-hash.js（新增）
export function parseShotMeta(meta) {
  if (meta === null || meta === undefined) return {};
  if (typeof meta === 'object' && !Array.isArray(meta)) return meta;
  if (typeof meta === 'string') {
    const s = meta.trim();
    if (!s) return {};
    let parsed;
    try { parsed = JSON.parse(s); }
    catch { throw metaError('SOLVE_META_INVALID_JSON', ...); }   // 不降级
    if (parsed === null) return {};
    if (typeof parsed !== 'object' || Array.isArray(parsed)) throw metaError('SOLVE_META_NOT_OBJECT', ...);
    return parsed;
  }
  throw metaError('SOLVE_META_NOT_OBJECT', ...);
}
```

`normalizeShotMeta()` 的第一行改为 `const src = parseShotMeta(meta);`，其余归一化（三字段、`__solver` 剔除、空条目剔除）不变。**解析只发生在这一处**：求解器与 Hash 都经由 `normalizeShotMeta`，不存在"两边各自解析、结果不同"的可能。

`qc/deps/index.js` 的 `stripSolver()` 也改用 `parseShotMeta`：`shot_states.meta` 与 `story_shots.meta` 同为 TEXT，而 P5 的 V-22 用 `toObj()` 读它 —— 若 Hash 侧对字符串返回 `{}`，就会出现"规则读到了内容、Hash 认为没有依赖"，报告级 Hash 从此不再覆盖真实输入。

三处取舍：

1. **解析失败抛，不降级**。降级成 `{}` 等于把"数据坏了"伪装成"没有标注"，而这两件事在 Hash 上完全同值 —— 这正是要堵的。
2. **`null` / 空串 / 空白串 / `'{}'` / `'null'` 五者等价于"没有标注"**，不视为缺陷（列默认值就是 `'{}'`）。
3. **`ver` 仍不进 Hash、`__solver` 仍剔除**：边界解析不改变既有口径，`R1-g` 专门断言这一点。

### 4.5 遗留决策点（U-P6-8，C 级）

`shots[].meta` 这条通道**不在 D01-04 §5.5 的输入定义里**（那一步只规定 `meta.src` 由 `scene_baseline` / `prev_shot:<id>` 派生），DB 也没有对应列。本轮的处置是"保留但说清"：

- 保留的理由：它是**可选的调用方通道**，缺失时行为与 P6 之前完全一致（四镜算例、C-1~C-18 一条未变）；且已在 Hash 覆盖内，不会造成"结果变了 Hash 没变"。
- 若审核认为不该存在，移除是 5 行改动（`solve-continuity.js` 的 seed 段 + `solve-hash.js` 的 `meta` 键与 `SOLVE_META_FIELDS`），但会让 D02-14 的 8 条 R1 测试与 D02-15 的 `R1-a~R1-l` 一并失效，需同时决策。**建议在 P8 接线前定案**。

## 附录 B · 两条教训

1. **校验存在 ≠ 校验有效**。R4 的 `some(...)` 看起来在保护 A-06，实际保护的是"这行像状态行"；而 A-06 只读 `state_in`。**校验必须对准"下游真正读的那一项"**，否则它会稳定地放行坏数据，还给人一种"已经管住了"的错觉。
2. **"两边一致"也可能是错的**。R1 修复前，Hash 与求解器都拿到 `{}`，彼此完全一致 —— 一致性让人放心，但它的一致性来自"两边都丢数据"。**判断是否丢数据，只能看"有数据时结果是否不同"**，所以 `R1-c` 那种"必须与无 meta 不同"的断言比"两形态相等"更关键。
