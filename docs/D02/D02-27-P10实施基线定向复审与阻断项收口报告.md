### 3.2 拦截点设计（冻结）

**不能只拦 API，也不能只拦 Agent。** 三条硬事实：

1. 产物写回**也走** `Shots.update`（#12~#16），服务级"一刀切拒绝"会直接把生成链打死。
2. `Shots.update` 是**32 列全量 UPDATE**（`db.js:997`），无法用"调用方传了什么"区分意图，只能看**字段集合**。
3. 有 4 处完全绕过服务（#17、#18、S1~S3）。

因此冻结为**三层**：

| 层 | 位置 | 规则 |
|---|---|---|
| L1 服务门 | `Shots.create/update/remove` 内首行 | 新增 `assertLegacyWriteAllowed(projectId, kind, fields)`：结构化项目下按**字段分组**判定（§4），创作组 → 抛 `STRUCTURED_SPEC_LEGACY_WRITE_BLOCKED`；产物/参数组 → 放行 |
| L2 直写门 | #17、#18 | 两处都必须"按项目分流"：结构化项目改为删/回滚 `story_shots`（+从表），legacy `shots` 只清产物行 |
| L3 读取门 | `Shots.list/get` | **不改**（27 处消费者依赖它）。结构化项目的行是产物单元行，读出来天然可用 |

**为什么不在 API 层拦**：API 只有 8 个入口，Agent 有 6 个，直写 2 个——漏一个就是"两套事实"。服务层是唯一收口点。

## 四、创作字段 / 生成参数 / 产物字段（三组）

### 4.1 现有边界（源码事实，不重造）

`shot-write.js:11~13` 已把"内容白名单"与"产物"分开，注释明确：`status / error / video_path / video_prompt_used / prompt_id` + `seed` 属产物，外部写入拒绝（`:18~20`）。

但 `story_shots` 无 `resolution/aspect_ratio/mode/video_prompt` 列，而生成链会写它们（`tools.js:2564`）——**这组字段没有归属**。因此必须显式定义第三组。

### 4.2 三组归属（冻结）

| 组 | 字段 | 权威落点 | legacy 可写 | Stage 3 可写 |
|---|---|---|---|---|
| **A 创作** | `chapter`/`scene_name`/`camera`/`visual`/`dialogue`/`narration`/`sub_shots`/`blocking`/`idx`/`duration`/`character_ids`/`scene_ids`/`prop_ids`/`costume_ids`/`age_ids`/`audio_ids`/`references` | Stage 3（`story_shots` + 三从表 + `scene_states`） | **否**（结构化项目） | 是 |
| **B 生成参数** | `resolution`/`aspect_ratio`/`mode`/`video_prompt`/`first_frame_path`/`last_frame_path`/`reference_image_path`/`seed` | 产物单元行（Stage 3 无对应列） | 是 | 不适用 |
| **C 产物** | `status`/`error`/`video_path`/`video_prompt_used`/`prompt_id` | 产物单元行 + `shot_videos` | 是 | 不适用 |

**B/C 的判定依据【源码确认】**：`SHOT_STRING_FIELDS`/`SHOT_ARRAY_FIELDS`/`SHOT_NUMBER_FIELDS`（`shot-write.js:11~13`）+ 产物注释（`:18~20`）+ 生成链实际写入集合（#12~#16）。

**一处必须说清的冲突**：`shot-write.js` 把 `resolution/aspect_ratio/mode/video_prompt` 放进**内容白名单**（外部 API 可写），而生成链也写它们。本轮把它们归 B 组（生成参数），理由是 Stage 3 无落点、且它们是"怎么渲染"而不是"拍什么"。这**不改** `shot-write.js` 的白名单（外部 API 行为不变），只改 P10-A 的拦截判据：结构化项目下 B 组放行。

### 4.3 产物单元行（对 D02-26 的实质修订）

```text
story_shots (镜, 权威)  ──切分/聚合──►  产物单元（段）──物化──►  legacy shots 一行
     │                                        │                      │
     │ 创作字段权威                            │ 派生文本（只读）        │ A 组列 = 投影刷新
     └────────────────────────────────────────┴──────────────────────┘
                                              B/C 组列 = 唯一写者（生成链）
```

| 规则 | 内容 |
|---|---|
| 行数 | 一期 **1 段 = 1..n 镜**（段由 `sub_shots` 切分决定，不是 1:1；`story_duration` 2.5–7.5s 而模型最小 4s，1:1 不可生成） |
| A 组列 | **只由投影函数写**（唯一写者），刷新时机 = Stage 3 写入成功后同事务 |
| B/C 组列 | 生成链独占写，投影**不得覆盖**（否则每次刷新都清掉 `video_path`） |
| `sub_shots`/`blocking`/`camera` | 派生文本（D01-05 §六：`projectUnitToShotRow` 渲染），不回流 Stage 3 |
| 一致性检查 | 提供 `checkUnitProjection(projectId)`：A 组列与 Stage 3 投影不一致即报 `UNIT_PROJECTION_DRIFT`（P10-A 验收项） |

**这条修订的代价必须写明**：A 组列在库里存两份（Stage 3 权威 + legacy 物化）。防漂移靠"唯一写者 + 漂移检查"，不靠"两处都能写"。

## 五、存量项目迁移与激活（不猜映射）

### 5.1 迁移契约（冻结）

| # | 条款 |
|---:|---|
| M1 | **不自动推断 1:N**：一条 legacy 行切几镜由 `sub_shots` 解析结果决定，格式 C（无镜信息）**必须人工确认**，不得默认"整行 1 镜"（D01-05 §5.2 置信度 0.2） |
| M2 | 每镜写入 `migration_items`（`target_table='story_shots'`、`source_table='shots'`、`source_pk=<shot id>`），来源可追溯 |
| M3 | 不可映射字段（`camera`、`blocking`）**保留原值在 `legacy_artifacts`**（`artifact_kind='shot_text'`），Stage 3 对应列为空并标 `fill_confidence=0`；**不得静默丢弃** |
| M4 | 激活前置：`unmapped_shot_count = 0` **或**运维显式签收（`migration_items.note` 记录签收人/原因） |
| M5 | 激活 = `structured_spec 0→1`，与"最后一批迁移提交"**同一事务**；失败整体回滚，flag 保持 0 |
| M6 | 回退 = `1→0` + 保留 Stage 3 行（不删），legacy 写入权恢复；再次激活时**复用已有 Stage 3 行**（按 `migration_items` 对应），不重复建 |
| M7 | 激活后 legacy 创作写入由 §3.2 的 L1 门禁拦截；**不存在"激活了但还能写 legacy 创作"**的窗口 |

### 5.2 激活失败的恢复边界

| 失败点 | 结果 | 恢复 |
|---|---|---|
| 迁移中 SQL 抛错 | `tx` 回滚，flag 仍 0 | 原地重跑（幂等：按 `source_pk` upsert） |
| 迁移完成、切 flag 失败 | 同上（同事务） | 同上 |
| 切换后首次求解失败 | flag=1，Stage 3 行在 | 允许，属正常失败（`continuity_runs` 记 failed） |
| 切换后用户要求回退 | `1→0` | Stage 3 行保留；legacy 写入恢复；再次激活复用 |

### 6.2 `scene_states.id` 能否胜任（逐条核实）

| # | 要求 | 结论 | 证据 |

| 1 | 全局 UUID | **是**（RFC 4122 v4） | `utils.js:5` `crypto.randomUUID()` |

## 十一、规范化规则（逐条对齐现有实现）

`canonical-stringify.js:1~12` 已冻结 8 条规则，直接引用，不另立标准：

| 项 | 规则 | 实现 |
|---|---|---|
| 对象键序 | `cmpStr`（UTF-16 code unit）升序，禁 `localeCompare` | `write()` 内 `Object.keys(v).sort(cmpStr)` |
| 整数 | 去小数（`4.0`→`4`） | `numStr()` |
| 浮点 | 保留 6 位去尾零（`0.30000000000004`→`0.3`） | `Math.round(v*1e6)/1e6` |
| `null` vs 缺失 | 统一 `null` 且**保留键** | `write()` 首行 + `canonical()` |
| 字符串 | NFC 归一 + 去首尾空白，内部空白保留 | `normStr()` |
| 有序数组 | `time_slices`/`cam_path`/`position_track` 保原序 | 调用方直传 |
| 无序数组 | `blockings`/`actions`/`assets`/`scenes` 排序后传入 | 见 §10.2 排序键 |
| 时间戳 | **不参与** | 不在任何 payload 里 |
| 记录 id | **参与**（`shots[].id`） | `SOLVE_SHOT_FIELDS` 含 `id` |
| 资产元数据 | 只 `id/name/category/parent_id` | `deps/index.js:126` |
| 算法版本 | `hash_algo_ver` 进 payload；变更即全量失效 | `deps/index.js:305` |

**新增字段必须显式声明归属**（A04-T12 的"未分类即缺陷"），否则 `SOLVE_META_NOT_OBJECT`/`INVALIDATION_FIELD_UNCLASSIFIED` 会抛。`scene_uid` 属于"身份"：进 Hash payload（替换 key），但不进"状态内容"。

## 十二、内容变化检测 vs 并发修改检测（必须区分）

| 类型 | 定义 | 本业务是否需要 | 采用手段 |
|---|---|---|---|
| **内容变化** | 输入内容是否等价 | **是**（幂等、carried、失效） | 双 Hash（内容等价 ⇒ Hash 相同 ⇒ 不写、可继承） |
| **并发修改** | 期间是否有人动过（哪怕改回） | **不需要** | 不用版本号 |

**为什么不需要"期间动过"**：求解是纯函数，结果只取决于当前内容。A 读 → B 改 → B 改回 → A 提交，提交的内容与当前内容等价，**提交无害**。若强行用单调版本号，反而会把"改了又改回"判成冲突，制造无意义的失败。

**已存在的 `state_rev` 为什么不能用**：它在**每次** `upsertSceneStates` 都 `+1`（`scene-state.js:173`），内容完全相同也加。用它做指纹会让"重复提交同一份基线"触发大量假冲突。

> 若将来需要"审计级：谁在期间动过"，应走 `change_logs`（已有），不要塞进并发闸。

## 十三、提交前检查流程（冻结，7 步）

```text
① readSceneSnapshot(projectId, sceneUid)          // 事务外，一次读全（镜+三从表+基线+资产实体）
② fp0 = fingerprint(snapshot)                     // 两组 Hash
③ solved = solveContinuity(snapshot)              // 纯函数，事务外（TX-3）
④ prepared = buildReports(solved, snapshot)       // 纯函数
⑤ txImmediate(() => {                             // 事务开始（写锁）
     fp1 = fingerprint(readSceneSnapshot(...))     // 事务内重读 + 重算
     if (fp1 !== fp0) throw CONTINUITY_INPUT_CHANGED
     persistSceneStates(...)                       // 状态
     saveReport(...) × n                           // 报告（逐镜）
     insertContinuityRun({status:'ok', input_hash: fp0})   // 运行记录（PF-1 批准后）
   })                                              // 提交
⑥ 事务失败 → 整体回滚，不写任何行
⑦ 抛错路径 → 单独短事务写 continuity_runs(status='failed')
```

**成本与优化**：`fp0`/`fp1` 都算两组 Hash。优化：事务内先算 `solver_input`（便宜，一次读），相等再算 `qc_dependency`（要建 69 条规则的依赖上下文）。两次不等即抛，不进入代价高的那段。

**为什么必须"事务内重读"而不是"比对内存版本"**：SQLite deferred `BEGIN` 下，读锁在第一次读就建立，但**写锁在第一次写才升级**；另一个进程可能在我们读完之后提交。只有 `BEGIN IMMEDIATE` + 事务内重读，才能保证"读到的那份 = 提交时的那份"。

## 十四、SQLite 与 PostgreSQL 实现

### 14.1 现有事实（决定实现方式）

| 事实 | 证据 |
|---|---|
| SQLite：`node:sqlite` `DatabaseSync`，WAL，`busy_timeout=5000` | `db-driver.js:63,69` |
| `tx()` = 裸 `BEGIN`（deferred），只收同步函数，嵌套内联 | `db.js:480~496` |
| PG：worker + Atomics 同步门面，SQL 原样转发（只做 `?`→`$n` 与 DDL 类型翻译） | `db-driver.js:11,88,155,195` |
| 已有按方言分支的先例 | `changelog.js:261` `db.dialect === 'postgres'` |

**因此 `BEGIN IMMEDIATE` 绝不能无脑发给 PG**——PG 会直接语法错误。`txImmediate()` 必须按 `db.dialect` 分支。

### 14.2 SQLite 实现

| 项 | 方案 |
|---|---|
| 事务 | `txImmediate(fn)`：`BEGIN IMMEDIATE` → fn → `COMMIT`；异常 `ROLLBACK`；嵌套时沿用 `txDepth` 内联（与 `tx()` 同语义） |
| 适用范围 | 只用于 `runSceneQuality` 的写段（含运行记录）。**不全局替换 `tx()`**（其余写入无此需求，全局替换会放大锁竞争） |
| busy timeout | 保持 5000ms；超时抛 `SQLITE_BUSY` → 外层转 `CONTINUITY_SCENE_BUSY`（**不自动重试**，由调用方决定） |
| WAL | 保持；WAL 下写者仍互斥，`IMMEDIATE` 让竞争提前到事务开始，避免"读到旧值后才失败" |
| 事务内重校验 | §13 第 ⑤ 步 |
| 锁冲突重试 | **不做库内重试**。理由：重试会掩盖"输入已变"的真因，且 `busy_timeout` 已在驱动层自旋 |

### 14.3 PostgreSQL 实现

| 项 | 方案 |
|---|---|
| 隔离级别 | **READ COMMITTED**（默认）。理由：我们用"场次级互斥 + 事务内重读"，不需要 SERIALIZABLE 的代价 |
| 场次互斥 | `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`，键 = `project_id || ':' || scene_uid`；事务结束自动释放，无死锁风险（单锁） |
| 为何不用行锁 | 要锁"一场的全部行"，行锁需先 `SELECT ... FOR UPDATE` 全表扫，锁量大且顺序敏感（易死锁）；advisory lock 是场次级的单一锁 |
| 输入版本检查 | 与 SQLite 相同（事务内重读 + 双 Hash） |
| 序列化失败 | READ COMMITTED 下不产生；若未来升 SERIALIZABLE，需捕获 `40001` 并整场重试 |
| 死锁 | 单锁 + 固定键，不存在交叉等待 |
| 【待确认】 | PG 路径**未在测试环境实跑**（测试进程禁 PG，`db.js` 的 `TEST_REQUIRES_SQLITE`）；`pg_advisory_xact_lock` 需在 P10-D 用真实 PG 验证一次 |

### 14.4 两库差异汇总

| 能力 | SQLite | PG |
|---|---|---|
| 写互斥 | `BEGIN IMMEDIATE` + 文件级写锁 | advisory xact lock |
| 超时 | `busy_timeout 5000` → `SQLITE_BUSY` | `lock_timeout`（需显式 `SET LOCAL`） |
| 重试 | 不重试 | 不重试 |
| 指纹校验 | 同 | 同 |

## 十五、资产变更与求解并发一致性

| 场景 | 风险 | 保护 |
|---|---|---|
| 资产实体修改（`name`/`category`/`parent_id`） | 求解用旧实体、报告用新实体 | 实体进指纹（`assets[*]` 声明字段）；事务内重读 `assets` 后 Hash 变 → 弃写 |

## 十六、阻断项四：`continuity_runs` 生命周期与崩溃恢复

### 16.1 冻结结构（D02-06 §8.2.4，8 列 2 索引，不扩）

| # | 列 | 类型 | 说明 |
|---:|---|---|---|
| 1 | `id` | TEXT PK | `uid()` |
| 2 | `project_id` | TEXT NOT NULL | 归属 |
| 3 | `scene_key` | TEXT NOT NULL | 与 `story_shots.scene_key`/`scene_states.scene_key` 同域 |
| 4 | `run_no` | INTEGER NOT NULL | 项目+场次内递增（1 起），失败与成功共用序列 |
| 5 | `input_hash` | TEXT NOT NULL | 与 `solverInputHash()` **同一个**，`sha256:` 前缀 |
| 6 | `status` | TEXT NOT NULL | **`ok` / `failed`**（冻结值域） |
| 7 | `error_code` | TEXT DEFAULT '' | `ok` 时 `''` |
| 8 | `created_at` | INTEGER | `now()`，同事务与状态写入取同一值 |

索引：`UNIQUE(project_id, scene_key, run_no)`、`INDEX(project_id, scene_key, run_no DESC)`。

### 16.2 状态机（任务书要求的 6 态 → 2 态的映射，不扩枚举）

| 任务书状态 | 是否落库 | 映射 | 理由 |
|---|---|---|---|
| `queued` | **否** | 内存态（请求已收、未开始） | 无持久价值；落库只增加"僵尸 queued" |
| `running` | **否** | 内存态 | **关键**：落 running 就要求"崩溃后有人把它改成 failed"，这正是任务书禁止的依赖 |
| `succeeded` | 是 | `status='ok'` | 冻结值 |
| `failed` | 是 | `status='failed'` + `error_code` | 冻结值 |
| `interrupted` | **否** | **记录缺失** | "没有记录"＝本次没跑完，语义比 `interrupted` 更准（无法区分崩溃/断电/取消，也不该区分） |
| `superseded` | **否** | 由"同场更大 `run_no` 的 ok"隐含 | 最新一条即有效；旧记录自然被覆盖"最新"地位（D02-06 原文） |

**兼容映射表就是这一张。不新增状态值、不新增 `phase` 列。**

### 16.3 写入时机（两条路径，冻结）

| 场景 | 写什么 | 事务 |
|---|---|---|
| 求解成功 | 一行 `ok`、`error_code=''`、`input_hash=fp0`、`run_no = max+1` | **与 `shot_states` + `qc_reports` 同一事务**（`txImmediate`） |
| 求解抛错 | 一行 `failed`、`error_code`、`input_hash=fp0` | **单独短事务立即提交**（事务内只有这一条 INSERT） |
| 同输入重跑成功 | 新一行 `ok`，`run_no+1` → 旧 `failed` 不再是"最新" | 同成功路径 |

`run_no` 分配遵守 RC-1~RC-6：**事务内**取 `MAX(run_no)+1` + `UNIQUE` 冲突重算重试（最多 N=3，常量写进实现）。

### 16.4 崩溃恢复（不依赖崩溃进程）

| 崩溃点 | 库里的状态 | 如何识别 | 恢复动作 |
|---|---|---|---|
| 建记录前崩溃 | 无记录 | "该场从未成功" | 下次正常跑 |
| 求解中崩溃 | 无记录 | 同上 | 重跑（幂等） |
| 求解完、未持久化 | 无记录 | 同上 | 重跑 |
| 状态存成功、报告失败 | **整体回滚**，无记录 | 同事务保证不可能半套 | 重跑 |
| 状态+报告成功、记录失败 | **整体回滚**（同事务） | 同上 | 重跑 |
| 事务提交后响应丢失 | 有 `ok` 记录 | 读最新记录为 `ok` + 报告 Hash 匹配 | 幂等返回，不重跑 |
| 用户重复请求 | 有 `ok` 记录 | 指纹相同 ⇒ 复用报告（P9 已实现） | 幂等 |
| 机器断电 | 事务未提交 ⇒ 无记录 | 同"无记录" | 重跑 |

**结论：不需要启动扫描、不需要 stale 超时、不需要"别人来写 failed"。** 因为**没有 running 态**，就没有"卡在 running"这一整类问题。这是 D02-06 只给 8 列、只给两个状态值的深层原因，不是简化。

**代价（如实写）**：无法从库里区分"从未跑过"与"跑了但崩了"。两者都表现为"无记录"，而业务上它们的处置相同（重跑），所以这个区分没有价值。若将来要审计"崩溃次数"，那是 `jobs` 的职责，不是 `continuity_runs`。

### 16.5 与报告/状态的关联

| 关联 | 方式 | 是否加列 |
|---|---|---|
| 运行 → 报告 | `continuity_runs.input_hash` 与 `qc_reports.hits.__solver_input.qc_input_hash` 相等（同场同轮） | **不加** `report_id` |
| 运行 → 状态 | `shot_states.meta.__solver.hash` 与 `input_hash` 相等 | **不加** `state_hash` |
| 运行 → 场次 | `scene_key`（P10-A 后建议同时存 `scene_uid`，需批准加列） | 待定 |

**为什么不加 `report_id`**：一次运行产出 N 份镜级报告（每镜一份），单列存不下；且加了会产生"记录与报告不一致"的第二真相。用 `input_hash` 关联足够且**不可伪造**。

## 二十三、最终实施基线

**一句话**：P10 的第一步仍然是 B1（零 DDL、可独立验收）；紧接着的 A 不再是"接管镜头写入"，而是"接管**创作字段**、物化**产物单元行**、落地**场次 uuid**"——因为生成链的 27 个读取点和 32 列全量 UPDATE 决定了：**单写权威只能落在字段上，不能只落在表上。**

三件必须先批准的事：

1. **D-27-3**（三组字段 + 产物单元行）——它决定 P10-A 写什么，改起来最贵。
2. **D-27-1 + D-27-2**（18 入口 + `scene_uid`）——两者一起决定"双写会不会漏"。
3. **D-27-4 + D-27-6**（`continuity_runs` 不设 running + 双 Hash 指纹）——它们一起决定崩溃与并发是否可证。

批准后的第一步不是写代码，是 P10-B1 的 14 项测试先红后绿（生产 `shot_assets` 无行，测试必须自建夹具并标明）。
