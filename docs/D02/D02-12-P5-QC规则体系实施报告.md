规则组 = 68 条规则用例 + V-12 + V-10 + S-20/S-21/S-25 联合反向断言。每条规则用例内部断言五件事：

1. 正向：`applicable=true` 且 `level='pass'`（INFO/WARN 类规则的正向同样是 pass，只有"命中"才不 pass）；
2. 负向：`level` 等于该规则声明的档位，且 `code` 不是 `PASS`；
3. `fields[]` 非空、且包含 `field` 本身；
4. `expected` 非空（LLM 能据此改）；
5. 同输入调两次逐字相同。

**这意味着"某条规则没实现"或"实现了但永不命中"都会当场变红** —— 用模块级测试糊过去过不了这一关。

### 6.1 枚举字段映射（P5 必须自己解决的那层）

P4 的 `enums.js` 用扁平键（`speed.profile`、`time_slices.kind`、`contact.impulse`），行对象是嵌套的。`enumSamples()` 做的是**带路径的映射**，每条样本都带 `path`（如 `shot_actions[0].speed_json.profile`），所以：

- 命中时能定位到具体行、具体键（不会只报"某处枚举错了"）；
- 不同对象的同名字段不会混（`blockings[0].posture` 与 `speakers[0].type` 各自独立）；
- `spec_source`（`shot.spec_source`）与 `state_source`（`shot_states.state_source`）都在映射表里 —— 这两个是 P4 复审补齐的字段，P5 直接把它们带进了校验。

**空值不在 V-02 判**（`if (isBlank(value)) continue`）：`power_level` 只在 S2+ 必填，若 V-02 把空值当"必填缺失"，S0/S1 的镜会被误判。缺失由 V-01 按 S 级判，两条规则各管一件事。

## 七、等级与"数据不足"的处理口径

| 情形 | 写什么 | 是否进统计 |
|---|---|---|
| 规则跑过且通过 | `code='PASS'`, `level='pass'`, `applicable=true` | 进（`stats.pass`） |
| 规则命中 | 具体 `code`（如 `COORD_PARTIAL`）+ 档位 | 进（按档位分桶） |
| **数据不足**（真·不可验证） | `level='info'` + §8.5.2 的 U 类码（如 `STATE_UNKNOWN` / `AXIS_UNVERIFIED` / `COORD_SYSTEM_INCOMPLETE`） | 进（`stats.info`） |
| **场次基线写得不全**（S-07 的 `AXIS_LOCK_INCOMPLETE`，§4.8.1） | `level='warn'` + `code='AXIS_LOCK_INCOMPLETE'`；同一条结果的 `detail.items[]` 里保留两条 INFO | 进（`stats.warn`，按 QL-1 取最高档，**不额外多一条记录**） |
| 规则不适用 | `applicable=false`, `level=''`, `code='NOT_APPLICABLE'` | **不进**（`stats.not_applicable`） |
| 阶段 4 未实现（V-12） | 同上（N/A） | 不进 |
| 规则抛异常 | `level='fail'` + `code='QC_RULE_EXEC_FAILED'` + `detail.error` | 进（且报告等级必为 fail） |

报告等级：`applicable=true` 的条目里取最高档（`fail > warn > info > pass`）；**一条适用规则都没有 → `info`**（不伪造 `pass`）。

几个必须写清的取舍：

1. **`visual_content` 为空 → INFO，不是 FAIL**：没写内容不等于写错内容（V-05）。
2. **`lens_mm=0` → INFO，不是 WARN**：没填焦段不等于填错焦段（V-15）。
3. **`time_slices=[]` → INFO**：V-20 与 A-15 都走这条出口，两条都不伪造 PASS。
4. **缺 `active_area` → INFO**：V-21 / S-15 / A-05 / S-04 / V-17 全部把"没有换算基准"报出来，**不猜默认尺寸**（拿 3.2×4.0 去算 6×5 的场次，距离与取景全是错的）。
5. **`cam_pos` 是米制、`norm_*` 是归一化**（D01-02 §4.0 G2）：所有换算只走 `active_area`，两个单位不混。
6. **"轴锁不完整"与"轴线不可验证"是两件事，但共用一条结果**（详见 §十三）：前者是可修的**缺陷**（WARN），后者是**数据不足**（INFO）。缺 `axis_line` 时两者同时成立，按 QL-1 取最高档输出一条 `warn` + `AXIS_LOCK_INCOMPLETE`，两条 INFO 留在 `detail.items[]` 里当证据 —— 既不丢证据，也不破坏 `(target_id, rule_id)` 唯一键。

## 十三、复审修复：补齐 `AXIS_LOCK_INCOMPLETE` 诊断

### 13.1 复审指出的问题（确认属实）

`checkAxisVerifiable()`（S-07）在 `axis_line` 缺失时只产出两条 INFO：

- `AXIS_UNVERIFIED`（侧别算不出来）
- `SCREEN_LR_UNVERIFIED`（画面左右算不出来）

而 D02-06 §4.8.1 的表明确写：`axis_lock` 无 `axis_line` → 允许写 `pair/left/right` 落库，但 **QC 必须报 `AXIS_LOCK_INCOMPLETE`（WARN）**；SC-05 的验收句也要求"落库成功 + `AXIS_LOCK_INCOMPLETE`(warn) + S-05/S-06 输出 `AXIS_UNVERIFIED`(info)"。首轮把"允许落库"实现成了"只报不可验证"，**漏掉了"这是一处可修的缺陷"这个判断** —— 结果是轴锁写不全和轴锁写全但机位没填，在报告里长得一模一样。

附带发现的同类漏洞：`axis_line` **写了但不合法**（只有 1 个点 / 3 个点 / 分量非数字 / 两点重合）时，首轮静默当作"不存在"，同样只报 INFO。这与"格式非法要如实报出来"的原则不符。

### 13.2 实现（`lib/core/validate/continuity.js`）

新增 `axisLockGap(sceneState)`：只判"轴锁能不能用"，返回 `null`（可用）或一段诊断 detail。**"合法轴线"的唯一判据仍是 `common.js` 的 `axisLineOf()`**，没有第二套判断逻辑（新增 57 行里 0 行几何计算）。

四类缺口分开记（`detail.source`），便于分别修：

| `source` | 触发条件 | 含义 |
|---|---|---|
| `scene_state_missing` | 连 `scene_states` 行都没传进来 | P2 已在写入期拦住（`SCENE_STATE_MISSING`），出现在这里即**取数缺陷** |
| `axis_lock_missing` | 有场次行，但 `axis_lock` 缺失或空对象 | 轴锁整块没写 |
| `axis_line_absent` | `axis_lock` 有 `pair/left/right` 等，但没有 `axis_line` | §4.8.1 允许落库的那一半；`pair/left/right` **不能替代轴线** |
| `axis_line_malformed` | `axis_line` 有值但不合法 | 不是两点 / 分量非有限数 / 两点重合（退化） |

命中写 `{level:'warn', code:'AXIS_LOCK_INCOMPLETE', field:'scene_states.axis_lock.axis_line'}`，`expected` 是"给出归一化平面上的两个不同点"，`detail` 带 `source` / `missing[]` / `axis_lock` / `axis_line` 四个键。

### 13.3 与两条 INFO 的聚合关系（QL-1，**本次修复的关键**）

缺 `axis_line` 时三件事同时成立：轴锁不完整 + 侧别不可验证 + 画面左右不可验证。按 D02-06 §8.5.2 QL-1，**同一规则在同一镜只能有一条记录**，所以：

```
S-07 一条结果
├─ level = 'warn'                     ← 各字段命中的最高档（fail > warn > info > pass）
├─ code  = 'AXIS_LOCK_INCOMPLETE'     ← 最高档那条命中
├─ field = 'scene_states.axis_lock.axis_line'
├─ fields[] = 三条命中字段的并集（axis_line / cam_pos / active_area）
└─ detail.items[] = 三条字段级命中
     ├─ {code:'AXIS_LOCK_INCOMPLETE', level:'warn', detail:{source, missing, ...}}
     ├─ {code:'AXIS_UNVERIFIED',      level:'info', detail:{missing:[...]}}
     └─ {code:'SCREEN_LR_UNVERIFIED', level:'info', detail:{missing:[...]}}
```

这是**既有聚合机制**（`toEntry` 的 `worstFinding` + `sortedUnique`）的自然结果，没有为这次修复新增任何聚合分支：**INFO 证据没有被降级成"没报过"，也没有多出第二条 S-07**。测试 `QL-1 · 轴锁不完整时 S-07 仍只产生一条结果` 直接断言 `hits` 里 `S-07` 恰好 1 条、`detail.items.length === 3`、全部 `rule_id` 互不重复。

`RULES` 里 S-07 的**基准档位仍是 `INFO`**（D01-04 §十一 的档位表没改），`ruleCatalog()` 仍返回 69 条、编号集合不变（未新增任何 D01 `rule_id`）。WARN 是 §4.8.1 挂在本条上的加重档，只在轴锁真的不可用时出现。
