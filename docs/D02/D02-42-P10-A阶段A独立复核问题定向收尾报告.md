## 二、D42-01 · A 类审计实体项目归属 fail-closed

### 2.1 原实现与缺陷

`lib/core/changelog.js` 原第 242 行：

```js
const pid = projectIdOf(entity, a || b) || String(projectId || '');
```

`||` 的语义是「解析不到就用备用值」。对 B 类（既有 6 实体）这是历史兼容需要；对 A 类（5 个必需审计实体）
它直接抹掉了 fail-closed：

- `shot_asset` / `shot_blocking` / `shot_action` 三张表**没有 `project_id` 列**，归属只能经 `story_shots` 反查。
- 反查失败（镜不存在、`shot_id` 为空）说明这张子表**已经是孤儿**——这本身就是要被审计记下来的事实。
- 但调用方只要顺手传一个 projectId（`db.js` 的既有写法里就有这个参数），日志就会落在一个**看起来合法**
  的项目名下。事后无法区分「归属是从真实行算出来的」与「归属是调用方嘴报的」。
- 更糟的是它**不会报错**：审计看起来完整，实际每一条都可能指错项目；按项目回滚会撤错项目。

### 2.2 修正后的判据（三个分支，顺序即优先级）

新增 `requiredProjectIdOf(entity, action, before, after, explicit)`（`changelog.js:216`），
`recordChange` 对 A 类只走它（`changelog.js:290`）：

| 分支 | 条件 | 行为 | 错误码 |
|---|---|---|---|
| 0 | `projectIdOf` 解析不到（A 类以外的 B 类） | 保持历史行为，不进入本函数 | — |
| 1 | `before` / `after` **都为空** | 唯一例外：沿用显式 `projectId`；它为空则抛 | `AUDIT_PROJECT_UNRESOLVED`（`side='none'`） |
| 2 | 任一存在的快照解析不到 | 抛，指明是 `side='before'` 还是 `side='after'` | `AUDIT_PROJECT_UNRESOLVED` |
| 3 | 两侧都能解析但归属不同 | 抛（不猜哪一侧），带 `fromBefore` / `fromAfter` | `AUDIT_PROJECT_UNRESOLVED`（`side='both'`） |

三条设计取舍，逐条说明为什么这样而不是别样：

1. **为什么允许分支 1 这个例外**：回滚撤一条「早已被删掉的行」时（漂移 + `force`），
   `applyInverse` 的删除动作两侧快照都是 null，根本没有行可归属；此时不留档会让审计断链、
   `reverted_by` 打不上，之后的全量回滚会把它当「未回滚」再撤一次。例外只到这里，
   而且 `projectId` 本身仍不许为空 —— 否则等于换个方式静默丢弃。
2. **为什么要核 `before` 和 `after` 两侧**：只核 `after`（原实现取 `a || b`）会漏掉
   「行被搬到另一个项目」这种 update；只核 `before` 会漏掉 create。两侧都核 + 不一致即抛，
   才能保证「这一条日志记的项目」与「这一行确实属于这个项目」是同一件事。
3. **为什么错误码不新增**：D02-40 §6.1 的错误码是封闭集。分支 3（归属不一致）在语义上就是
   「解析不出唯一归属」，用 `AUDIT_PROJECT_UNRESOLVED` 并在 `detail.side` 上区分即可，
   不引入 `AUDIT_PROJECT_MISMATCH`。

## 三、D42-02 · 测试锁顺序观察者不进入公共 API

### 3.1 问题成因

```js
// lib/core/index.js
export * from './db.js';
```

`lib/core/index.js` 是 `lib/core` 的公共面，用通配转出把 db.js 的全部 export 都变成了对外 API。
上一版为了 TST-LOCK-07（要求「用注入的 spy 记录真实取锁顺序」，D02-34 §4.1）在 db.js 里加了
`export function setLockOrderSink(fn)`，于是这个**纯测试注入点**自动成了业务代码可调用的接口：
任何人 `import { setLockOrderSink } from '@/lib/core'` 就能把锁顺序改成任意值，
而 TST-LOCK-07 仍然会绿 —— 测试断言的可信度被接口本身泄掉了。

### 3.2 修正方式（两道闸）

**闸一 · 结构**：新增 `lib/core/internal/lock-order.js`（41 行），把观察者整体搬出 db.js。

| 符号 | 作用 | 谁用 |
|---|---|---|
| `emitLockOrder(projectId)` | 取锁时回调一次；无观察者时是空操作 | `lib/core/db.js` 唯一 import 方 |
| `setLockOrderSink(fn)` | 注入 / 注销观察者 | **只允许** `tests/helpers/lock-worker.mjs` |
| `lockOrderObserving()` | 是否已挂上（防止 `order=[]` 被误读成「没取锁」） | 同上 |

`internal/` 不被 `index.js` 转出 ⇒ `lib/core/index.js` 的公共面里没有它；
唯一的引用方式是写显式路径，这种引用一眼可查（由 D42-02-F 的静态扫描守住）。

**闸二 · 运行**：非 `IC_LOCK_TEST=1` 的进程调用 `setLockOrderSink` 直接抛 `LOCK_SINK_TEST_ONLY`。
注销也受同一道闸保护 —— 否则「先注入、再被外部注销」会让测试在没有任何观察者的情况下跑完。

配套改动（都是机械改动，无逻辑变更）：

| 文件 | 改动 |
|---|---|
| `lib/core/db.js` | 删掉 `let _lockOrderSink` 与 `export function setLockOrderSink`；改为 import `emitLockOrder`，取锁循环里直接调用（`db.js:651`、`db.js:656`） |
| `tests/helpers/lock-worker.mjs` | 观察者改从内部路径引用；注入后断言 `lockOrderObserving()`，未生效即 `exit 2`（不静默） |
| `tests/tst-lock-01-13.test.mjs` | 子进程环境补 `IC_LOCK_TEST=1` |
| `scripts/verify/tst-lock-pg.mjs` | 同上（PG 侧子进程） |
