### 5.4 用行号说明的三处真风险

**风险 1 —— `renumberTwoPhase` 拿不到 `projectId`（第 12 行）。**
它只收 `(field, rows, opts)`，项目和章节信息全在 `rows` 之外。要迁到 `txProject(P)` 必须**改签名**（加 `projectId`）或**断言已在 `txProject` 内**。选后者风险更低：`applyTargetOrder`（第 13 行）是唯一生产调用方，它已经在自己的事务里，改造后嵌套同项目自动复用（D-30-13 规则 R6）。**但断言必须落地**，否则将来有人直接调它就会在无锁状态下跑两阶段重编——而两阶段重编中途失败会留下**负值号**（`-(i+1)`），那是必须避免的半完成态。

**风险 2 —— `loadSceneInput` 与 `runSceneQuality` 的写入不在同一事务（第 2 行 vs 第 4 行）。**
今天的顺序是：`loadSceneInput`（自己一个 `tx()`，读完就结束）→ 求解（纯内存）→ `tx()` 写 `shot_states` + `qc_reports`。**两次事务之间有窗口**：别的写者可以在这段里改 `story_shots`/`shot_assets`，于是「算出来的状态」对应的输入已经不存在了。这与 D-30-13 要求「求解方与写入方都参加同一协议」直接冲突。**处置**：`runSceneQuality` 改 `txProject(P)` 时，必须把 `loadSceneInput` 的调用**移进同一个事务内**，不能只把外面那层换成 `txProject`。

**风险 3 —— `writeShotAssets` 的整组替换会与审计差集共用事务（第 17 行）。**
它不是新问题，但迁移时必须一起做：`DELETE FROM shot_assets WHERE shot_id = ?` 之后再 `INSERT`，**物理上是全量替换**；D02-34 §3.3 要求按**逻辑集合**算差集、在**物理写入之前**算。若先迁锁、后补差集，中间那一版就是「锁对了、日志全假」。**处置**：第 17 行的迁移与 A3 差集在同一轮落地（对应 V5-B / TST-AUD-08~15）。

### 5.5 迁移方案（不改代码，只定方案）

**协议（对齐 D-30-13 v3 / D-02-34 §2，不新增机制）**

| 要求 | 本轮方案 |
|---|---|
| `txProjects()` 只能最外层 | 25 处里**没有一处**需要跨项目；本轮不给任何调用点引入 `txProjects` |
| 集合开门前一次定死、取锁后冻结 | 由 A-05 在 `db.js` 实现；本清单只声明「每处只需一个项目」 |
| 同项目嵌套复用 | 三组已知嵌套：`applyTargetOrder`→`renumberTwoPhase`、`runSceneQuality`→`persistSceneStates`、`writeStoryShotWithAssets`→`writeShotAssets`；改造后均走同项目复用，**不重复取锁** |
| 已持锁后调 `txProjects` 必拒 | 本轮无此路径；由 A-05 的错误码兜底 |
| 两库分别实现 | SQLite 靠 `BEGIN IMMEDIATE`（库级锁），`lockedProjects` 只做契约记账；PG 靠 `pg_advisory_xact_lock`（项目级） |
| 不得另造事务管理器 | 全部改动落在既有 `tx()`（`db.js:480`）之上，新增 `txProject`/`txProjects` 两个**包装**，不改 `txDepth` 语义 |

**顺序（阶段 A 内，与 A-05 同期）**

```
A-05 实现 txProject / txProjects
   ↓
① 先迁「写创作权威」的 5 处：19（scene-state）、17/18（shot-assets）、13/14（global-no 上层）
   ↓
② 再迁「触碰生成段」的 6 处：8（insertAt）、10（Chapters.remove）、20（import）、22（chapters PATCH）、23（storyboard PUT）、6（Projects.remove）
   ↓

```

**为什么这个顺序**：①组是 A 类审计与 A3 差集的落点，先动它们能让 V5 与锁一起验；②组会级联删行，锁不对会留下「章节没了、段还在」；③组的读一致性依赖 ① 已锁住写者才成立；④组各自有独立前置（回滚要靠 409、开关要靠运维脚本），不能提前。

| 8 | 独立测试库 / 权限 / 隔离 | 同上 | **无法验证** |

### 7.2 结论与缺失清单

**P7：未通过（阻塞）。** 不是「配置不全」，是**本机没有任何 PostgreSQL 服务端进程**。

| 缺失项 | 具体 | 最短解决路径 |
|---|---|---|
| 服务端软件 | 无 `postgres`/`pg_ctl`/`psql` 可执行文件 | 装 PostgreSQL 16+（Windows 安装包或 `winget install PostgreSQL.PostgreSQL.16`） |
| 容器运行时 | 无 `docker` / `podman` | 若走容器，需先装 Docker Desktop；否则用原生安装包 |
| 测试库 | 无 `infinite_creation_test` 之类独立库 | 建库后设 `db.postgres.database` 或 `DATABASE_URL` 指向**测试库**，禁止指向生产 |
| 权限 | 需 `CREATE`（建表）、事务、`pg_advisory_xact_lock` 执行权 | 用库 owner 或 superuser 跑测试；`hashtextextended` 可用性同时验证（U-32-2） |
| 三件套验证 | TST-LOCK-11~13 需要**两个真实并发连接**交错 | 单进程 `pg.Client` 单连接不够；需两个连接或两个进程（`pg-worker.mjs` 是单连接 + `Atomics.wait`，测试侧要另开连接） |

### 7.3 三条纪律（写死）

| # | 纪律 |
|---:|---|
| 1 | **不得用 SQLite 结果代替 PG 并发验收**。SQLite 的 `BEGIN IMMEDIATE` 是库级锁，PG 的 `pg_advisory_xact_lock` 是项目级；两库粒度不等价，「SQLite 全绿」推不出「PG 无死锁」 |
| 2 | 报告里只能写「未实跑」，不得写「已验证」「等价通过」 |
| 3 | P7 未通过时，**P2 必然无法满足** ⇒ 阶段 A 无法退出 ⇒ 阶段 B 不得开始。这是硬停，不是延期 |

### 7.4 一条容易忽略的连带影响

`pg-worker.mjs` 是**单连接 + `Atomics.wait`** 的同步桥。TST-LOCK-11~13 要验的是「两个事务交错取锁」，**在单连接里做不到真正的交错**——同一连接上的两个事务是串行的。所以 PG 并发测试**不能**复用 `pg-worker`，必须由测试自己开两条 `pg.Client`。这一条要写进 P2 的执行说明，否则实施者会用 `db.tx()` 写测试，得到「全绿但什么也没验」的结论。

**P7 结论：未通过。** 证据 = §7.1 第 5/6 行的实测输出（`ECONNREFUSED`，1 ms 内即失败，说明端口上无监听）。
