### 1.2 三条硬约束（本轮写死）

| # | 约束 |
|---:|---|

## 二、D34-01：多项目锁顺序彻底收口

### 2.1 问题：D02-33 的规则为什么不够

D02-33 §5.3 写「`txProjects` 内的集合必须包含外层已持锁的项目」，§5.5 的状态机则允许在已持锁的事务里继续调用。这两条组合起来会产生真实的顺序反转：

| 时刻 | 事务 T1 | 事务 T2 |
|---|---|---|
| t0 | `txProject(P)` → 拿到 P | — |
| t1 | 内部 `txProjects([P, Q])`；设 **Q 的字典序小于 P**，排序后为 `[Q, P]`，但 P 已在手 ⇒ 实际顺序 **P → Q** | `txProjects([Q, P])`；排序后 `[Q, P]` ⇒ 实际顺序 **Q → P** |
| t2 | 等 Q | 等 P |
| 结果 | **死锁**（PG 报 `40P01` 并杀掉其中一个；`tx()` 是同步的，无法重试整个 `fn`） | 同左 |

同类反例还有：`txProjects([P,Q])` 内部再 `txProjects([P,Q,R])` 追加 R，与另一事务 `txProjects([R,P,Q])`（排序后 `[P,Q,R]`，即先 P 后 R）形成 P 未持有时 R 先被持有 ⇒ 同样反转。

**根因**：排序只能保证「一次调用内部有序」，无法保证「整个事务全局有序」。只要允许追加，全局序就可能是 `P, Q, R`，也可能是 `P, R`，取决于追加时机。

### 2.2 最终契约（8 条，逐条可检查）

| # | 规则 | 违反时 |
|---:|---|---|
| R1 | `txProjects(ids, fn)` **只能作为最外层项目事务入口** | 抛 `TX_NESTED_MULTI_PROJECT` |
| R2 | 项目集合必须在**事务开始前一次性确定**（调用即全量声明） | 无处可「先开事务再定集合」：集合是入参 |
| R3 | 去重去空后按 **`cmpStr` 稳定升序**，再逐项取锁 | 空集合抛 `TX_EMPTY_PROJECT_SET`；超过 8 个抛 `TX_TOO_MANY_PROJECTS` |
| R4 | 事务执行期间**不得增加新的项目锁**（集合冻结） | 结构保证：`lockedProjects` 是 `Object.freeze([...])`，事务内只读 |
| R5 | 已持有项目锁后调用 `txProjects` ⇒ **一律 fail-closed** | 抛 `TX_NESTED_MULTI_PROJECT` |
| R6 | 同项目嵌套事务**复用**已持有的锁，不重复获取 | 命中 `lockedProjects.includes(P)` 即直接执行 `fn` |
| R7 | 多项目操作必须在最外层调用前声明完整集合 | 同上 R2；未声明就想追加 ⇒ 被 R5 拒 |
| R8 | 无法提前确定完整集合的跨项目操作**不得**用嵌套追加实现，必须**拒绝**并要求调用方调整事务边界 | 抛 `TX_NESTED_MULTI_PROJECT`，错误信息提示「把该操作拆成两个独立事务，或改为在最外层声明完整集合」 |

### 2.3 运行时检查位置与错误行为（不能只写文档）

| 检查 | 具体位置 | 时机 | 失败后果 |
|---|---|---|---|
| 拆分「是否最外层」 | `txProject()` / `txProjects()` **函数第一行**，读模块级 `txDepth` | 进入函数时 | 决定走「开门取锁」还是「复用/拒绝」 |
| 是否已持该项目 | 同上，查冻结数组 `lockedProjects` | 进入函数时 | 未持有且非最外层 ⇒ 拒绝 |
| 是否在 `tx()` 内调用 | 同上，看 `txDepth>0` 且 `lockedProjects === null` | 进入函数时 | 抛 `TX_MUST_BE_IMMEDIATE` |
| 锁集合不可扩展 | `lockedProjects` 只在「取锁完成」处赋值一次，且赋 `Object.freeze([...])`；事务结束置 `null` | 结构保证 | 任何 `push` 语义的追加都需要重新赋值，而赋值点唯一 ⇒ 无法绕过 |
| 取锁顺序 | 取锁循环直接遍历 `ids.slice().sort(cmpStr)` 的结果 | 取锁前 | 顺序即排序结果，不可指定 |

**错误码表（封闭集合，新增必须同时改本表）**：

| 错误码 | 触发条件 | 是否 fail-closed |
|---|---|---|
| `TX_MUST_BE_IMMEDIATE` | 在 `tx()`（非项目事务）内调用 `txProject` / `txProjects` | 是（业务写入不发生） |
| `TX_CROSS_PROJECT_NESTED` | 单项目事务内请求另一个项目 | 是 |
| `TX_NESTED_MULTI_PROJECT` | 已持有项目锁后再调 `txProjects`（含集合完全相同的情况） | 是 |
| `TX_TOO_MANY_PROJECTS` | 去重后仍 > 8 | 是 |
| `TX_EMPTY_PROJECT_SET` | 空数组 / 全为空串 | 是 |
| `TX_LOCK_SET_CORRUPT` | 内部一致性断言失败（`lockedProjects` 与声明集合不符） | 是（视为程序 bug，不尝试恢复） |

> 注意 `TX_NESTED_MULTI_PROJECT` 对「集合完全相同」的重入也一律拒绝。理由：允许「相同集合重入」会诱使实现者写出「第一次 [P]、第二次 [P,Q]」的近似调用，而这条路径正是死锁来源。要复用，用 `txProject(P)`（R6）。

### 2.4 两库实现边界（分开写，不得互相套用）

**SQLite**

| 项 | 机制 |
|---|---|
| 互斥来自哪里 | `BEGIN IMMEDIATE`（连接建立时已设 `PRAGMA journal_mode=WAL; busy_timeout=5000`，`db-driver.js:69`）。它取的是**库级 RESERVED 锁** |
| 有没有「项目锁」 | **没有**。`lockedProjects` 在 SQLite 下**只做契约记账**：用于复用判定与拒绝判定，不产生任何互斥效果 |
| 嵌套复用 | `txDepth>0` 时不发 `BEGIN`、不做 SAVEPOINT，直接执行 `fn`（与现有 `tx()` 同语义） |
| 顺序的意义 | 对正确性无影响（库级锁已经全排他），但**必须照排序登记**：否则同一段调用在 SQLite 上能过、在 PG 上死锁，测试会在错误的库上变绿 |
| 释放 | `COMMIT` / `ROLLBACK` 释放库级锁；`lockedProjects` 置 `null` |
| 已知代价 | 不同项目也串行（库级锁），属既有事实，本轮不改变 |

**PostgreSQL**

| 项 | 机制 |
|---|---|
| 互斥来自哪里 | `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`，每个项目一把，**在事务内获取**，随事务结束自动释放 |
| 取锁顺序 | 严格等于 `cmpStr` 排序结果；所有调用方共用同一个函数 ⇒ 全局一致序 |
| 集合能否动态扩展 | **不能**。取锁完成后 `lockedProjects` 冻结；任何新增项目的请求都在进入时被 R5/R8 拒绝，因此不存在「已持 P 再补 Q」的路径 ⇒ 顺序反转被**结构性**排除 |
| 超时 | `SET LOCAL lock_timeout='5s'`（BEGIN 之后、取锁之前）；超时抛 `55P03`，包成 `DB_LOCK_TIMEOUT` |
| 键碰撞 | `hashtextextended` 是 int8；碰撞只会让两个项目共用一把锁（多串行），不会错数据 |
| 连接中断 | 连接断开 ⇒ 服务端回滚事务并释放全部 `xact` 锁，**不残留** |
| 单连接 | 每进程一个 worker 一条连接；进程内事务靠同步门面天然串行，锁只解决跨进程 |

**两库共同的调用契约（必须一致）**：

| 契约 | SQLite | PG |
|---|---|---|
| 最外层唯一入口 | 同 | 同 |
| 集合一次定死 | 同 | 同 |
| 冻结不可扩展 | 同（记账层冻结） | 同（锁层亦冻结） |
| 已持锁后调 `txProjects` ⇒ 拒绝 | 同 | 同 |
| 同项目嵌套复用 | 同 | 同 |
| 错误码 | **完全相同** | **完全相同** |

### 2.5 状态机（实现照此，替换 D02-33 §5.5）

```
// 模块级状态
let txDepth = 0
let lockedProjects = null        // null = 当前没有项目事务；否则是冻结数组

open(ids):                       // 唯一赋值点
    if (dialect === 'sqlite') exec('BEGIN IMMEDIATE')
    else { exec('BEGIN'); exec("SET LOCAL lock_timeout='5s'") }
    for (id of ids) {            // ids 已去重 + cmpStr 升序
        if (dialect === 'postgres')
            query('SELECT pg_advisory_xact_lock(hashtextextended(? ,0))', id)
    }
    lockedProjects = Object.freeze(ids.slice())
    txDepth++

close(ok):
    txDepth--
    if (!ok) exec('ROLLBACK') else exec('COMMIT')
    lockedProjects = null

txProjects(ids, fn):
    if (txDepth > 0) throw TX_NESTED_MULTI_PROJECT      // R1 / R5 —— 无例外
    list = unique(ids).filter(Boolean).sort(cmpStr)
    if (list.length === 0) throw TX_EMPTY_PROJECT_SET
    if (list.length > 8)  throw TX_TOO_MANY_PROJECTS
    open(list)
    try  { r = fn(); close(true);  return r }
    catch (e) { close(false); throw e }                 // 回滚 + 释放 + 清空 lockedProjects

txProject(P, fn):
    if (txDepth === 0) {                                 // 最外层：自己开门
        open([P])
        try  { r = fn(); close(true);  return r }
        catch (e) { close(false); throw e }
    }
    if (lockedProjects === null)     throw TX_MUST_BE_IMMEDIATE     // 在 plain tx() 里
    if (!lockedProjects.includes(P)) throw TX_CROSS_PROJECT_NESTED
    return fn()                                          // R6 复用，不重复取锁
```

**一处必须写死的实现细节**：`open()` 是 `lockedProjects` 的**唯一赋值点**，且赋的是 `Object.freeze` 后的新数组。任何「追加」都需要第二次赋值，而代码里只有一处赋值 ⇒ 追加在结构上不可能，而不是靠纪律。

## 三、D34-02：`shot_assets` 差集审计补齐

### 3.1 问题一：漏了 `order_no`

`shot_assets` 的业务形状是：

```
PRIMARY KEY (shot_id, role, asset_id)
UNIQUE      (shot_id, role, order_no)
业务字段     order_no（排序，即参考图/音色的编号顺序）、variant_of
```

D02-33 的 A3 只写了「`variant_of` 变化 → update」。而 `order_no` 恰恰决定**参考素材的绑定顺序**——它进 `seg-2` 的 `media[]` 序号，改了它就是改了生成输入的编号。漏记 `order_no` 等于「资产顺序被调了，日志里看不出来」。

### 3.2 问题二：物理 SQL ≠ 业务变化

`writeShotAssets` 是**整组替换**（`shot-assets.js:235~237`）：先 `DELETE FROM shot_assets WHERE shot_id=?`，再逐行 `INSERT`。一次「绑定完全没变」的重写，物理上是 N 条 delete + N 条 insert。若按物理操作记日志：

| 现象 | 后果 |
|---|---|
| 一次无变化的重写产出 2N 条日志 | 内容日志被淹掉（与 `VOLATILE` 当初要解决的问题同源） |
| 日志与「业务上改了什么」脱钩 | 审计无法回答「这次改动了哪几个引用」 |
| 条数随资产数量线性膨胀 | 镜引用 7 个资产就 14 条，整章重排能刷出上百条 |

### 3.3 最终差集规则（唯一）

**输入**：同一事务内读到的 `before`（该 `shot_id` 的全部现有行）与 `after`（本次解析出的目标行，已规范化）。
**判定键**：`(role, asset_id)`（`shot_id` 在组内恒定）。

| 变化情况 | 审计动作 | 条数 |
|---|---|---|
| 完全相同（键与 `order_no`、`variant_of` 都一致） | **不记录** | 0 |
| 仅 `order_no` 改变 | update（before/after 全行） | 1 / 行 |
| 仅 `variant_of` 改变 | update | 1 / 行 |
| `order_no` 与 `variant_of` **同时**改变 | **仍只记 1 条 update**（不拆成两条） | 1 / 行 |
| `asset_id` 或 `role` 改变 | 旧键 delete + 新键 create | 2（1 删 1 建） |
| 新增绑定（键在 `after` 不在 `before`） | create | 1 / 行 |
| 删除绑定（键在 `before` 不在 `after`） | delete | 1 / 行 |

**为什么 `asset_id` / `role` 变化是 delete + create 而不是 update**：它们**是主键的一部分**。键变了就是「另一行」，不是「这一行改了值」。把它记成 update 会让回滚与漂移检测都按错误的键去找行。

**条数上界（可断言）**：`日志条数 = |added| + |removed| + |changed|`，且 `≤ |before| + |after|`。这条不等式直接进测试。

### 3.4 判定算法（实现照此）

```
txProject(projectId, () => {
  ① before = SELECT * FROM shot_assets WHERE shot_id = ? ORDER BY role ASC, order_no ASC
  ② after  = resolveShotAssets(...) 产出的规范行（角色/顺序/变体已定）
  ③ b = Map(key(r) → r, before)      key(r) = role + '\u0000' + asset_id
     a = Map(key(r) → r, after)
  ④ added   = [...a.keys()].filter(k => !b.has(k))
     removed = [...b.keys()].filter(k => !a.has(k))
     changed = [...a.keys()].filter(k =>
                 b.has(k) && (b.get(k).order_no !== a.get(k).order_no
                           || b.get(k).variant_of !== a.get(k).variant_of))
  ⑤ 记录：removed → delete（before 全行）
           added   → create（after 全行）
           changed → update（before 全行 / after 全行）
  ⑥ 物理写入：保持现状（DELETE 全组 + INSERT 全组）
  ⑦ deriveVoiceIds → UPDATE story_shots.voice_ids（不记 A2 日志，见 §3.6）
})
```

**顺序关键点**：④ 必须在 ⑥ **之前**计算，且在同一个 `txProject` 内。这样即便 ⑥ 失败，⑤ 的日志也一起回滚（不会出现「日志说改了、数据没改」）。

### 3.5 三个示例（含顺序交换）

**例 1 · 完全相同的重写**

| | 行集合 |
|---|---|
| before | `(char, A, order 1)`、`(char, B, order 2)` |
| after | `(char, A, order 1)`、`(char, B, order 2)` |
| 物理 SQL | DELETE 2 + INSERT 2 |
| **审计** | **0 条** |

**例 2 · 只调顺序（互换）**

| | 行集合 |
|---|---|
| before | `(char, A, order 1)`、`(char, B, order 2)` |
| after | `(char, B, order 1)`、`(char, A, order 2)` |
| 物理 SQL | DELETE 2 + INSERT 2 |
| **审计** | **2 条 update**（A: 1→2；B: 2→1），**0 删除 0 创建** |

例 2 是最能暴露「按物理 SQL 记日志」错误形态的例子：物理 4 条、业务 2 条。

**例 3 · 换人（A → C）**

| | 行集合 |
|---|---|
| before | `(char, A, order 1)` |
| after | `(char, C, order 1)` |
| **审计** | **1 条 delete（A）+ 1 条 create（C）**，不是 update |

### 3.6 五个实现边界

| # | 边界 | 说明 |
|---:|---|---|
| B1 | 审计依据是业务差集，不是 SQL 条数 | 见 §3.3、§3.5 |
| B2 | update 必须保留完整 before/after | 复用 `recordChange` 的整行快照，不裁剪字段 |
| B3 | 日志条数 ≤ 实际变化行数 | 上界断言进测试 |
| B4 | 完全相同的替换**零日志** | 与 `recordChange` 内部的 `contentChanged` 不冲突：差集为空时根本不调用（避免一次无变化重写触发 N 次判定） |
| B5 | 保持 `writeShotAssets` 的事务原子性 | 审计与物理写入同事务；`txProject` 包住整段（现状是 `tx()`，按 D-30-13 v3 升级） |

**关于 `UNIQUE (shot_id, role, order_no)`**：这条唯一索引让「原地逐行改 `order_no`」在 SQL 层不可行（中途会撞约束，除非先写负数或临时值）。本模块是整组替换，物理写入不受影响；而**审计在物理写入前基于逻辑集合计算**，所以顺序交换能被正确记成 update。这是「审计与物理写入解耦」的直接收益，必须写进实现注释，避免后来者把它改回「插入时顺手记日志」。

**关于 `voice_ids`**：`writeShotAssets` 会回填 `story_shots.voice_ids`（`shot-assets.js:241~243`）。`voice_ids` 已列入 A2 的 `VOLATILE`（D02-32 §4.3），因此**不会**产生 A2 的 update 日志，也就不会与 A3 的日志双记。这一点要写明，否则实现者会以为漏记。

### 3.7 八个测试（设计完成，**均未执行**）

| 编号 | 用例 | 断言 |
|---|---|---|
| **TST-AUD-08** | 完全相同的绑定重复写入 | `change_logs` 增量 = 0（且物理 DELETE/INSERT 确实发生过） |
| **TST-AUD-09** | 仅改 `order_no` | 1 条 update；`before.order_no` / `after.order_no` 分别为旧/新值 |
| **TST-AUD-10** | 仅改 `variant_of` | 1 条 update；两个 `order_no` 相同 |
| **TST-AUD-11** | 新增一条绑定 | 1 条 create；无 delete/update |
| **TST-AUD-12** | 删除一条绑定 | 1 条 delete；无 create/update |
| **TST-AUD-13** | 替换资产 ID（A→C） | 1 条 delete（键 A）+ 1 条 create（键 C）；**无 update** |
| **TST-AUD-14** | 混合：新增 1、删除 1、交换顺序 2、改变体 1 | 日志条数 = 5，且 action 分布为 create 1 / delete 1 / update 3 |
| **TST-AUD-15** | 中途失败回滚 | 注入物理写入失败；断言 `shot_assets` 回到 before，`change_logs` 无新增 |

**TST-AUD-14 的 5 条怎么来的**：`|added|=1` + `|removed|=1` + `|changed|=3`（2 条互换 + 1 条变体）= 5。这条用例专门防「把 changed 拆成两条」或「把互换算成 delete+create」。
