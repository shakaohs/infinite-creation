### 1.2 接线后的调用链

```
POST /api/projects/:id/continuity/solve          ← 生产调用点（只读计算）
  └ app/api/projects/[id]/continuity/solve/route.js
      └ solveSceneContinuity({ projectId, sceneKey, annotations })   ← lib/core/continuity/solve-scene.js
          ├ loadSceneInput()                       ← lib/core/continuity/load-scene.js（只读）
          │   ├ SELECT * FROM story_shots          WHERE project_id=? AND scene_key=? ORDER BY global_no,id
          │   ├ SELECT b.* FROM shot_blockings b JOIN story_shots s …（按 s.global_no, b.character_id 排序）
          │   ├ SELECT a.* FROM shot_actions   a JOIN story_shots s …（按 s.global_no, a.t_from, a.id 排序）
          │   ├ SELECT x.* FROM shot_assets    x JOIN story_shots s …（按 s.global_no, x.role, x.order_no 排序）
          │   └ listSceneStates(projectId).find(r => r.scene_key === sceneKey)   ← 复用 P2 读回
          ├ assembleSolverShots({ rows, annotations })   ← 来源隔离 / global_no 规范化 / id·号唯一性
          └ solveContinuity({ projectId, sceneKey, shots, sceneState })
```

`tx()` 包住上面四条 SELECT + 一次场次读回：`BEGIN`…`COMMIT` **只读不写**，作用是让"镜头行 / 站位 / 动作 / 资产"
来自同一个快照，避免读到"镜已建、站位还没写"的中间态。

## 四、输入数据映射说明

| 目标字段 | 来源 | 变换 |
|---|---|---|
| `rows[].id / global_no / scene_key / shot_no / …` | `story_shots` 列 | 原样（`global_no` 由组装层校验为**数字**正整数） |
| `rows[].speakers / time_slices / cam_path / voice_ids` | `story_shots` TEXT(JSON) | `JSON.parse`；**非法 JSON 当场抛 `SCENE_INPUT_INVALID_JSON`**，不降级成 `[]` |
| `rows[].blockings[]` | `shot_blockings` | 按 `shot_id` 分组；`position_track` 解析为数组；`norm_*` 的 `NULL` **保持 NULL**（不补 0） |
| `rows[].actions[]` | `shot_actions` | 按 `shot_id` 分组；9 个 `*_json` 解析为对象、`body_parts` 解析为数组；并给 `result` / `contact` 同名别名（求解器读 `a.result_json ?? a.result`） |
| `rows[].shotAssets[]` | `shot_assets` | 按 `shot_id` 分组，按 `(role, order_no, asset_id)` 排序（AR-2 同口径） |
| `sceneState` | `scene_states` 经 `listSceneStates()` | 已由 P2 解析 `coord_system / fixtures / entries / axis_lock / power_geometry`；缺行 → `sceneState=null` + `baselineMissing=true` |
| `rows[].meta` | **无** | 读取层不产出该键；`assembleSolverShots()` 见到即整批拒（D02-19 R1 的双保险） |
| `annotations` | **请求体**（调用方显式声明 `source`） | 经 `buildShotAnnotations()` 盖 `manual:<source>` |

**为什么不读 `shot_states`**：本轮采用"**整场重算**"——状态链从场次基线起、按 `global_no` 逐镜推出，
不需要把上一轮结果当上下文。一旦读进来，就很容易被"顺手"投影成 `shots[].meta`
（D02-16/17/18/19 反复堵的就是这条路）。所以读取层连读都不读，让"结果回搬"在数据层面不可能发生；
`W4` 用一条带 `carried:` 的 `shot_states` 行证明了这一点。

## 七、数据库读写边界（R6）

| 操作 | 位置 | 读/写 | 是否本轮范围 |
|---|---|---|---|
| `SELECT story_shots / shot_blockings / shot_actions / shot_assets` | `load-scene.js` | **读** | ✅ 本轮 |
| `SELECT scene_states`（经 `listSceneStates`） | `scene-state.js:223` | **读** | ✅ 本轮（复用） |
| `SELECT shot_states` | **无** | — | 刻意不读（见 §四） |
| `INSERT/UPDATE shot_states`（状态持久化） | **无** | — | ❌ P9 |
| QC 报告写入、`carried` 继承、失效集合落库 | **无** | — | ❌ P9 |

- **事务**：读路径用 `tx()` 包裹，只做 `BEGIN`…`COMMIT` 的读快照，不产生写入，因此不存在"半成品状态"。
- **失败语义**：读取阶段抛错（坏 JSON / 字段形状）→ 未产生任何副作用；组装阶段抛错 → 同样无副作用；
  求解是纯函数。**本轮的失败不可能留下半个场次的状态**，因为本轮根本不写。
- **真实库**：本轮所有测试均以 `IC_DATA_DIR=<临时目录>` 隔离运行；项目真实库三文件 SHA 与 `-shm` mtime
  与 D02-16~19 记录**完全一致**（`b2ebdb54…` / `2711665d…` / `22d61103…`，mtime `1795760932`），**0 DDL / 0 DML**。
