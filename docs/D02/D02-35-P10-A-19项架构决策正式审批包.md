## 四、五项重点决策的完整批准内容

> 这五项不能只写一句摘要：它们分别改变**正式规范**、**指纹语义**、**并发正确性**、**审计能力**、**对象身份**。以下为批准时实际生效的文本。

### 4.1 D-30-03 · 你批准的不只是改一个列名

**批准内容**

1. `continuity_runs` 的第 3 列由 `scene_key` 改名为 `scene_uid`，语义 = `scene_states.id`。
2. 两条索引重建：`UNIQUE (project_id, scene_uid, run_no)`、`INDEX (project_id, scene_uid, run_no DESC)`。
3. 读取口径改为 `WHERE project_id=? AND scene_uid=? ORDER BY run_no DESC LIMIT 1`。
4. **修订 `docs/D02/D02-06-阶段3核心创作能力实施任务书.md` §8.2.4 的三处正文**：① 8 列表格中的列名与说明；② 「索引（2 条）」段落；③ 「读取规则」代码块。三处必须同一次提交改完，不允许只改代码和 manifest。
5. 定性不变：该表**不进 `changelog`**、**不参与 QC 统计**、**不进 `version` 类接口**、**不建外键**。

**为什么必须单独批准**：这是本轮唯一一处**正式规范变更**。规范是验收的判据来源，若只改实现，验收时会出现「按 D02-06 查 `scene_key`、按代码查 `scene_uid`」的两套口径，且历史报告（D02-06 §8.2.4 的引文）会与本项冲突。

**批准后的连锁**：D-30-02 才能落地（uid 必须先存在）；E 阶段的求解写入与三态读取全部按 uid；D-31-04 的判空检查按 uid 维度枚举。

**不批准的后果**：`continuity_runs` 继续按可变别名定位，场次改名即断链；且 PF-1（D-30-12）的履约记录会与实现长期不一致。

### 4.2 D-30-09 v4 · 指纹覆盖什么、由谁构造

**批准内容**

1. 算法标识 `SEG_INPUTHASH_ALGO = 'seg-2'`，存储值 `'seg-2:' + hex`，比较用整串相等。
2. 顶层 8 项 + `engine` 子对象 9 项，全部**逐字段构造**（白名单），禁止 `{...exec}`、禁止 `delete` 式黑名单。
3. `engine` 子对象只在 `backend='engine'` 时非 null，含 `id`/`family`/`model`/`baseUrlSha256`/`submitPath`/`outputUrlPath`/`templateSha256`/`extraHeadersSha256`/`syncMode`。
4. `apiKey` 永不进投影、日志、错误信息、`change_logs`；`taskIdPath` 保留在运行时对象但**明确不进**投影。
5. `requestTemplate` / `extraHeaders` 只摘要**模板原文**，不摘要渲染后的请求体（渲染结果含 key）。
6. 三类版本分离且各自可独立升级：`seg-2`（字段集）、`pb-1`（提示词构造）、`specSha256`（工作流源与规格，现算）。
7. 白名单任何变更 ⇒ 必须升 `SEG_INPUTHASH_ALGO`；单测断言键集等于冻结列表。

**不批准的后果**：过期判定退回字符串比较，换模型/换工作流/换资产图/改项目宽高全部漏判；若改为「对执行配置整体 Hash」，则 `apiKey` 入摘要、新增编排字段导致全量假过期。

**一条必须同时接受的语义边界**：`input_hash` 是「渲染时刻的段输入版本」，**不是**「模型输入字节证明」。对外展示、导出说明、错误信息都不得把它描述成「这份视频就是由这些字节生成的」。

### 4.3 D-30-13 v3 · 两库两套锁，一套调用契约

**批准内容**

| 项 | SQLite | PostgreSQL |
|---|---|---|
| 互斥来源 | `BEGIN IMMEDIATE`（库级 RESERVED） | `pg_advisory_xact_lock(hashtextextended(id,0))`（项目级） |
| 超时 | `busy_timeout=5000`（连接建立时已设） | `SET LOCAL lock_timeout='5s'`（BEGIN 后、取锁前） |
| 项目锁的作用 | **仅契约记账**（复用/拒绝判定），不产生互斥 | 真实互斥，随事务提交/回滚释放 |
| 粒度 | 库级（不同项目也串行，属既有事实） | 项目级（不同项目可并行） |
| 中断 | WAL 回滚未提交事务 | 连接断开 ⇒ 服务端回滚并释放全部 xact 锁，不残留 |

**共同契约（必须完全一致）**：`txProject` 唯一入口；`tx()` 内调用 fail-closed；`txProjects` 只能最外层、集合开门前定死、`cmpStr` 升序、取锁后 `Object.freeze`、已持锁后再调一律拒绝、上限 8；错误码封闭集 6 个（`TX_MUST_BE_IMMEDIATE`/`TX_CROSS_PROJECT_NESTED`/`TX_NESTED_MULTI_PROJECT`/`TX_TOO_MANY_PROJECTS`/`TX_EMPTY_PROJECT_SET`/`TX_LOCK_SET_CORRUPT`）。

**为什么「默认禁止跨项目」是必需的**：排序只保证单次调用内部有序。允许追加就会出现「T1 先 P 再 Q、T2 先 Q 再 P」，PG 报 `40P01` 杀一个，而 `tx()` 是同步的、无法重试整个 `fn`。

**不批准的后果**：并发写入撞号失败或丢更新；跨项目场景不可控；P10-A 所有写入链不能开工。

**注意一条**：批准本项**不等于** PG 并发已验证。V4 要求 TST-LOCK-01~13 真实跑通，其中 11~13 **必须在 PG 真库**；当前环境无 PG（`provider=sqlite`、`postgres.url` 空、无 `psql`/`docker`），因此 Gate P2/P7 仍为未满足。

### 4.4 D-30-15 v3 · 审计到哪、回滚到什么程度

**批准内容**

1. **A1~A8 四态矩阵**生效（详见 D02-32 §4.3 + D02-33 §2.2 + D02-34 §3.3）；判定值：应有 / 应无 / 不适用 / 待实现。
2. `ENTITY_META.pk` 允许**字符串或数组**；`rawGet` 支持数组键；`projectIdOf` 对复合表走 `story_shots` 反查；`applyInverse` 对多列主键**一律抛** `ROLLBACK_UNSUPPORTED_ENTITY`。
3. 新增实体条目：**A1~A5 共 5 个**（`scene_state`/`story_shot`/`shot_asset`/`shot_blocking`/`shot_action`），各带 `VOLATILE` 清单（`scene_states.state_rev`、`story_shots.voice_ids` 必须进）。D02-31 §5.2 写的「4 个」是指除 `scene_states` 外的四张 Stage 3 表，但 A1 同样需要登记，故实际为 5 个；按落地进度逐个补，未落地的实体不登记。
4. A3/A4 用**差集审计**：`order_no`/`variant_of` 变记 update（同变 1 条）；`asset_id`/`role` 变记 delete+create；完全相同 0 条；条数 ≤ added+removed+changed。
5. **结构化项目内容回滚长期 409**，UI 文案固定；审计用于取证，不用于自动恢复。
6. 审计失败与业务**同事务回滚**（可注入用例 V5-F）。
7. A6（投影字段）与 A8（派生/执行记录/求解产物）**负向断言**：写入后 `change_logs` 增量必须为 0。

**不批准的后果**：Stage 3 改动**无审计**（`recordChange` 对未登记实体静默返回 null）；复合主键表强行接审计会写错行或 SQL 报错；「用户误操作能否恢复」这个问题将永远答不上来。

### 4.5 D-31-02 v3 · 对象身份是「摘要 + 扩展名」

**批准内容**

1. 身份 `identity = (sha256(bytes), ext)`；对象名 `ic-<64 hex>.<ext>`，**不截断**。
2. `ext` 规范化：魔数嗅探优先 → 路径兜底 → 失败关闭（`UNSUPPORTED_MEDIA_EXT`）；含小写化、`.jpeg→.jpg`、去多重扩展名。
3. 名字**不含** `project_id`/`role`/`asset_id`/时间戳/uid。
4. 无条件写（幂等）；同一身份重复上传不改变字节。
5. 严格模式 `verifyUpload=true` 写后回读校验 —— **未实现**，且回读端点能力未验证（U-32-1），在此之前不得在任何文档或 UI 宣称「已支持完整性校验」。
6. **仅 native ComfyUI**：RunningHub 用平台 `fileName`（`runninghub.js:43`）、外接引擎不传文件（靠冻结 dataUrl）。
7. 外部篡改（有人手工往 `input/ic-<hash>.png` 写不同字节）是**已知边界**，登记 U-32-6，不视为已解决。

**为什么措辞必须是「摘要 + 扩展名」**：同一份字节按 `.png` 与 `.jpg` 两条路径上传会得到两个对象。只要保留原扩展名，「名字只由字节决定」就是错的陈述。代价只是重复存储，不会串台。

**不批准的后果**：跨渲染同名覆盖继续存在（今天就是活的，只是因为还没有 `input_hash` 列所以不可观测）。
