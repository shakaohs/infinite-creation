## 一、缺陷根因

### 1.1 现象

合并 A+B（两镜两段并成一段）时，**若 `shot_videos` 候选只存在于 B（非 base 段）**，D02-49 的守卫全部通过：

1. 计划里只有 A（`decideSegmentId` 判定 A 的归属 `{a}` ⊆ 组 `{a,b}` ⇒ 同一逻辑段，复用 A）；
2. `assertCandidateSafe` 只检查计划段 ⇒ 检查 A，A 没有候选 ⇒ 放行；
3. 写入阶段 A 被 `UPDATE` 成合并后的内容（吸收 B 的画面/台词/时长/资产）；
4. stale 清理阶段，B 已 0 归属：**有候选** ⇒ 进 `blocked` 不删。

结果：**A 的内容已经变了**（内容来自 B），而 B 的候选原样挂在 B 上成为孤儿；一次"成功"的投影把候选与其生成输入永久解耦，且没有任何错误。

### 1.2 为什么 D02-49 没抓到

D02-49 的两道守卫都以「**最终计划段**」为作用域：

| 守卫 | 作用域 | 遗漏 |
|---|---|---|
| `decideSegmentId` 交集判定 | 只对**当前正在裁决的 base id** | B 从未成为任何组的 base，不会被裁决 |
| `assertCandidateSafe` | 只对 `plan[].segmentId` | B 不在 plan 里 |

`blocked` 只是"不删"，**它不阻止合并发生**。也就是说：D02-49 防住了"覆盖有候选的段"，没防住"把有候选的段并掉"。

### 1.3 同类可绕过路径（本轮一并封堵）

| 路径 | 旧行为 |
|---|---|
| 拆分时两组都用**显式新 id** | 原段不在计划里 ⇒ 不被检查 ⇒ 原段失去全部归属，候选成孤儿 |
| 用显式新 id 把某段的**唯一归属镜**迁进新段 | 同上 |
| 三镜合并、候选只在中间的 B/C | 同 1.1 |

### 2.2 关键实现【源码核查】

```
projectSceneUnits(...)
  ├─ ②-b plan：逐组 decideSegmentId（D48-02 / D49-01 原规则不变）
  ├─ ②-c assertCandidateSafe(plan 段)：内容差异 / 归属差异 ⇒ 拒绝      ← D02-49
  ├─ ②-d assertAffectedSegmentsSafe(...)：跨段守卫                       ← 本轮新增
  │      affected = { 范围内所有镜当前指向的段 } ∪ { 计划段 }
  │      for sid of affected:
  │        候选为 0 ⇒ 跳过
  │        投影后归属 = 在计划里 ? 该组全部镜 : 该段在本次范围之外的剩余归属
  │        前 ≠ 后 ⇒ UNIT_SEGMENT_CANDIDATE_CONFLICT（reason=segment_absorbed | ownership_changed）
  └─ ③ 写入 → ④ segment_id 回写 → ⑤ 0 镜段清理
```

三条设计要点：

1. **作用域扩大到"受影响段"**，而不是"最终保留段"：合并被吸收的、拆分被分走的、被迁走的、被清掉的，全在集合里。
2. **不误伤已孤儿段**：投影前 0 归属、投影后仍 0 归属的段（D02-48/49 的 `orphaned_with_candidates` 场景），前后集合相同 ⇒ 放行，继续 `blocked`。
3. **仍不换 id、不删候选、不部分写入**：所有判定都在写入前完成，抛错即整事务回滚。

新增 `reason` 取值：`segment_absorbed`（段被合并/拆分/迁出后失去范围内全部归属）。原有 `ownership_changed` / `content_changed` / `segment_split` / `segment_grew` / `ownership_mixed` 保持不变。

## 三、D50-02：历史归属减少的识别能力与数据模型边界

### 3.1 问题：能否可靠还原被删镜头的历史段归属

| 来源 | 能否回答"镜 b 曾属于段 S" | 说明 |
|---|---|---|
| `story_shots`（live） | **不能** | 行被删除后不留痕迹；`segment_id` 随行消失 |
| `story_shots.segment_id` 的现存归属 | **不能** | 只剩存活镜，历史被裁掉 |
| `change_logs`（A2 delete） | **能** | `action='delete'` 的 `before` 快照含 `segment_id`（`D50-11` 实测） |
| `shot_videos` | **不能** | 只记录候选属于哪个段，不记录段曾由哪些镜组成 |

**结论**：**部分能**。live 模型不能；审计日志能，但日志是"事后取证"而不是"守卫可用输入"（日志可被回滚、批量清理，且按它做守卫会把审计变成业务前提）。

### 3.2 守卫的证据边界（明确写清，不掩盖）

- 守卫只基于「**投影前后仍存活的行**」计算 owners。已被删除的行不可见。
- 因此，本轮**不能**直接断言"某段历史上曾有过更多归属镜"。能断言的是两条可观测事实：
  1. **归属集合（存活行）** 与投影后不同 ⇒ 拒绝（`D50-09`：用内容完全相同的新镜替换旧镜，17 列一字不差，仍被 `ownership_changed=true` 拦下）；
  2. **A 组内容** 与投影后不同 ⇒ 拒绝（`D50-10`：删镜后 `sub_shots` 从按行拼接退化为空串，内容必然变化）。
- **不得把"当前 owners == 新 owners"当成"历史从未变化"**：这句在实现里被拆成两条独立判据（集合比较 + 内容比较），任一不同即拒绝；两者都相同才放行（那正是"完全幂等"的定义）。
- **不得制造虚假历史数据**：本轮没有为测试插入任何伪造的历史行；`D50-11` 只是读 `change_logs` 取证，不参与守卫。

### 3.3 残余风险（明确登记）

当前数据模型下，"归属减少且 A 组 17 列完全不变"**不可构造**：删掉任一镜都会让 `sub_shots` 变化（多镜时按行拼接 → 少一行或退化为空串），`D50-10` 用断言锁住这一点。
**但这条结论依赖"`sub_shots` 在投影字段集内"**。若将来把 `sub_shots` 移出投影字段（或改为按段缓存），"归属减少 + 内容不变"就会变成可达状态，届时必须重新评估——需要"段归属历史"的持久化（软删或独立历史表），那属于 **DDL 决策**，本轮**未做**（D50-02 §5 要求先提交架构影响分析）。
