## 三、注释修正逐条

### 3.1 `normalizeShotMeta` 的入参说明（原表述有误）

```diff
- * 输入**允许是数据库里的原始形态**（P6-R1 收紧）：`story_shots.meta` 与
- * `shot_states.meta` 都是 `TEXT DEFAULT '{}'`，`SELECT *` 读回来是**字符串**。
- * 早期版本对字符串直接返回 `{}` —— 于是"库里明明有显式 unknown 标注"，Hash 与求解器
- * 双双当成"没有标注"，两边还很一致，看起来完全正常。这种一致是假象，不是正确性。
+ * 先明确这条通道到底是什么（P6-R1 / U-P6-8，结论见 D02-16 §三）：
+ *  · **`story_shots` 没有 `meta` 列**（48 列实测），数据库里不存在"镜头的 meta"；
+ *  · **`shot_states.meta`** 才是正式持久化的可靠性标注，类型 `TEXT`、默认 `'{}'`，
+ *    内容是字段级 JSON 对象串（D01-04 §5.2）；
+ *  · 求解器输入里的 **`shots[].meta` 是调用方附加到复合镜头对象上的可选字段**，
+ *    与 `blockings` / `actions` 同一种做法 —— 它没有表、没有列，只能由调用方显式给出。
```

同时保留并强调原有的两条约束：`normalizeShotMeta()` 是统一解析与归一化的唯一入口；求解器与 Hash 必须继续共用同一份归一化结果。

### 3.2 `parseShotMeta` 的定位

```diff
- * `meta` 的边界安全解析（P6-R1）：DB 的 TEXT 列 → 对象。
+ * `meta` 的边界安全解析（P6-R1）：把调用方给的"对象或 JSON 字符串"统一成对象。
+ * 需要它，是因为同一条通道有两种合法来源：调用方直接构造的对象，以及从
+ * `shot_states.meta`（`TEXT DEFAULT '{}'`）取出的 JSON 串。
+ * 注意：**`story_shots` 没有 `meta` 列**，本函数不为它服务。
```

### 3.3 seed 段（求解器侧）

原文写"它不是新字段：与状态行同一种形状"，容易读成"库里有一列"。改为明写：无对应列、P8 回搬属于"同一来源的一次搬运"、不得让两个来源互相覆盖。

## 五、两条通道的冲突：实证与来源

### 5.1 实测：回搬 `shot_states.meta` → 假失效

模拟 P8 的行为：把上一轮求解得到的 `state.meta` 原样填回 `shots[].meta`，创作数据一字未改。

```
round 1  hash sha256:cca133a…  a.src blocking:c1  b.src blocking:c1
round 2  hash sha256:4a9a8fe…  a.src blocking:c1  b.src blocking:c1   ← Hash 变了
round 3  hash sha256:4a9a8fe…  a.src blocking:c1  b.src blocking:c1
round 4  hash sha256:4a9a8fe…  a.src blocking:c1  b.src blocking:c1
```

第二轮的 `state_solver_hash` 与第一轮不同，但**状态内容逐字段相同**（`rel` / `src` / `conf` / 坐标都没变）。按 §9.2.1 的语义，读侧会判定"输入变了，旧状态过期"，于是重算一次 —— 而重算得到的还是同一个状态。**这就是假失效。**

### 5.2 差异定位：只有 `__solver.hash` 变

对两轮 `states` 做深度逐键比对，唯一的差异是：

```
.a.meta.__solver.hash: "sha256:217364d9…" → "sha256:b2e5a277…"
.b.meta.__solver.hash: "sha256:217364d9…" → "sha256:b2e5a277…"
.b.meta_in.__solver.hash: "sha256:217364d9…" → "sha256:b2e5a277…"
```

即使只把 seed 的 `src` 换成另一个字符串（`carried:sh_99`），差异仍然只有这一个键。

### 5.3 来源：`src` / `conf` 是**结果侧**字段，被当成了输入

| 字段 | 在 `shot_states.meta` 里的含义 | 被 `SOLVE_META_FIELDS` 纳入 Hash 后 |
|---|---|---|
| `rel` | 该字段的可靠性判定 | 合理：它是求解的**输入前提**（显式 unknown 一票否决坐标） |
| `src` | **这个值是怎么来的**（`blocking:c1` / `carried:sh_40` / `action:ac_3`） | 它是**上一轮求解的产出**。把它当输入 = 让输入依赖输出 |
| `conf` | **求解算出的置信度**（含 `×0.9` 衰减） | 同上 |

`__solver` 被显式剔除（防自引用），但 `src` / `conf` 没有 —— 它们不是元数据，而是结果的一部分，只是存放在了同一个 JSON 里。

### 5.4 三个候选处置（**本轮不选**，需单独裁决）

| 候选 | 做法 | 影响 |
|---|---|---|
| A | `SOLVE_META_FIELDS` 只保留 `rel`；`src`/`conf` 不再由 `shots[].meta` 提供 | 最小改动、彻底消除假失效；但"人工指定置信度/出处"这条能力消失（当前无调用方，实际影响为 0） |
| B | 允许回搬，但约定 `src` 必须带 `manual:` 等**非求解产出**前缀，求解器产出的一律忽略 | 保留能力，但需要一条"来源过滤"规则，等于设计新的优先级 —— 超出本轮授权 |
| C | 禁止回搬；标注只能来自人工/适配层的新数据，P8 不得把状态行搬回输入 | 零代码改动，纯约定；但 P8 若已按"回搬"设计，需要改 P8 而不是 P6 |

**本轮的处置**：在代码注释里写明"不得让两个来源互相覆盖"，并把候选表登记在此。**未修改 `SOLVE_META_FIELDS`，未加来源过滤，未定优先级。**

### 5.5 另一处调用方责任（顺带记录，不改逻辑）

`solveContinuity` **不按 `scene_key` 过滤**传入的镜头（`solve-continuity.js:144` 只做排序）：

```js
list = shots.filter(...).sort((a, b) => (num(a.global_no) ?? 0) - ...);
```

D01-04 §5.5 要求"前镜只能来自同一 `scene_key`"。若调用方把两个场次的镜头混在一起传，求解器会**静默跨场串链**（不报错，`states` 里两场都有）。这是 P8 组装层的责任，本轮只记录，不新增校验（新增校验会改变运行逻辑）。

## 六、P8 复合镜头对象接口约定

### 6.1 形状

```js
shots[] = {
  // ① story_shots 行（48 列，DB 原样即可；求解器只读下面列出的几列）
  id:             string,     // 必填，缺失抛 CONTINUITY_SOLVER_FAILED
  global_no:      number,     // 必填（排序权威；缺失按 0 处理并排到最前 → 视为调用方缺陷）
  scene_key:      string,     // 必填，且**必须全部等于入参 sceneKey**（求解器不过滤，见 §5.5）
  time_jump:      0 | 1,
  spec_source:    'ai' | 'import' | 'manual' | 'legacy',
  spec_version:   number,
  fill_confidence:number,
  // 其余创作列（shot_size / dialogue / cam_* …）求解器不读，可原样带上

  // ② 子表行（P8 必须组装成对象数组；给 JSON 串也能解析，但那是兜底不是约定）
  blockings:      shot_blockings[],
  actions:        shot_actions[],
  shotAssets?:    shot_assets[],   // 求解只用 role ∈ {character, prop}

  // ③ 可选通道（无表无列）
  meta?:          object | string, // 字段级可靠性标注，键 `chars.<id>.<field>`
}
```

### 6.2 约定条款

| # | 条款 |
|---|---|
| C-1 | `shots` 只含**同一 `sceneKey`** 的镜头；跨场混传不报错但会串链，责任在调用方 |
| C-2 | 顺序由 `global_no` 决定，`shot_no` / `prev_shot_id` / `insertion order` 一律不作为权威 |
| C-3 | `blockings` / `actions` 必须是**对象数组**；DB 里是 TEXT 的 `position_track` / `body_parts` 由调用方或求解器各自的 `arr()` 兜底解析 |
| C-4 | `shots[].meta` 缺失 = 无标注，等价于 `{}`；**不是**"读取失败" |
| C-5 | `shots[].meta` 若给字符串，必须是合法 JSON 对象串；解析失败**抛**（`SOLVE_META_INVALID_JSON` / `SOLVE_META_NOT_OBJECT`），不降级 |
| C-6 | `__solver` 即使出现在 `shots[].meta` 里也会被剔除；`ver` 会被本镜 `spec_version` 覆写，二者都不进 Hash |
| C-7 | 同一镜不得同时从"调用方标注"和"状态行回搬"两个来源取 `meta`；**该口径待 §5.4 裁决** |
| C-8 | 求解器输入与 `solverInputHash` 必须来自**同一次组装**（同一组 `shots` 对象），不得各查一次库 |

### 6.3 输出契约（P8 写库时用）

```js
{ states: { [shotId]: { in, out, meta, meta_in, derived_from, conflicts, diagnostics } },
  sceneConflicts: [ { code, level, character_id, field, detail, scene_key, shot_id } ],
  hash: 'sha256:<64 hex>' }
```

`states` 是**普通对象**（不是 `Map`），可直接 `Object.values()` 落 `shot_states`；`__solver.hash` 即 `state_solver_hash`，与 `qc_input_hash` 同值复用（QH-10）。
