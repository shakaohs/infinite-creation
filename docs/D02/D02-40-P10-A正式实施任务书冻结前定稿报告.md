## 二、PostgreSQL 生命周期约束（定稿）

### 2.1 结论

| 项 | 定稿 |
|---|---|
| 实例形态 | **会话托管进程**（`runas /trustlevel:0x20000` 启动的 `postgres.exe`），**不注册 Windows 服务** |
| 为什么不定为服务 | 注册服务需另建**标准账号**（`LocalSystem` 会被 `postgres.exe` 的管理员令牌检查直接拒绝）；这是环境治理决策，不是 P10-A 的实施内容 |
| 代价 | 会话结束即停 ⇒ **每次 P2 前必须重新拉起并重做自检** |
| 数据 | `D:\pg16\data` 持久化，异常停机后自动恢复，库与数据不丢 |
| 凭据 | 仅 `D:\pg16\pw.txt`（仓库外）；**报告 / 日志 / 提交一律零披露** |

### 2.2 P2 执行前的六项自检（写进 §8.3.3，缺一即 P2 不通过）

| # | 检查 | 判据 |
|---:|---|---|
| 1 | 服务端在跑 | `127.0.0.1:55432` LISTENING |
| 2 | 测试库可连 | 连 `infinite_creation_test` 拿到 backend pid |
| 3 | 版本 16.x | `current_setting('server_version')` 以 `16.` 开头 |
| 4 | advisory lock 可执行 | `pg_advisory_xact_lock` 成功且 `pg_locks` 可见 |
| 5 | **两个独立连接** | 两条 `pg.Client`（或两个 `psql` 会话）；**不是** `pg-worker`、**不是**同一连接上的两个事务 |
| 6 | 连的是测试库 | 库名 = `infinite_creation_test`；否则按**安全事件**立即停止 |

### 2.3 与 P7 的关系（容易被读错的地方）

| 命题 | 是否成立 |
|---|---|
| P7 已通过 ⇒ 环境永远可用 | **不成立**。P7 是 2026-11-28 的**实测事实**，不是永久通行证 |

## 三、锁上下文最终接口契约（定稿）

### 3.1 冻结的四个符号

| 符号 | 签名 | 语义 |
|---|---|---|
| `txProject` | `(projectId: string, fn: () => T) => T` | 单项目事务；最外层自己开门取锁；同项目嵌套直接复用 |
| `txProjects` | `(projectIds: string[], fn: () => T) => T` | 多项目事务；**只能最外层**；集合开门前定死 |
| `lockedProjects` | `() => readonly string[]`（无项目事务时返回 `null`） | 当前锁集合的**只读快照**，冻结数组，写即抛 |
| `assertProjectLocked` | `(projectId: string) => void` | **唯一**锁持有断言入口；通过静默，不通过抛 `TX_PROJECT_NOT_LOCKED` |

### 3.2 六条硬约束（A-05 编码时不得临时决定）

| # | 约束 | 结构性理由 |
|---:|---|---|
| 1 | `_lockedProjects` **全仓只有一处赋值**（开门取锁完成后）与一处清空（`finally`） | 追加锁需要第二次赋值 ⇒ **结构上不可能**，不靠纪律 |
| 2 | `lockedProjects()` 返回 `Object.freeze` 数组，**绝不返回内部可变引用** | 返回引用等于给了追加入口 |
| 3 | `assertProjectLocked` **只有一个参数、无 options、无第三参** | 允许传入锁集合等于允许伪造（P5-1 的核心要求） |
| 4 | 断言**只有一处实现**，写入入口只调用 | P5-1 / P5-3 / P5-4 三个风险都靠它兜底；分散实现必漏一处 |
| 5 | 断言在**业务写入之前**、同一事务内；失败即整事务回滚，不吞不降级不 `warn` | 事务外预检与写入之间可被抢占 |
| 6 | 不新增第二套事务管理器、不新增任何追加接口 | D02-34 §2 已否决；D02-39 LOCK-07 实测 SQL 层不拦追加（先锁 P 再锁 Q 会被放行） |

### 3.3 嵌套四分支（不留解释空间）

```
txProject(P, fn):
  最外层            → open([P])              → try fn()  finally close()
  在普通 tx() 内    → throw TX_MUST_BE_IMMEDIATE
  项目事务内、未持有 → throw TX_CROSS_PROJECT_NESTED
  项目事务内、已持有 → return fn()            // 同项目复用

txProjects(ids, fn):
  已有任何项目事务  → throw TX_NESTED_MULTI_PROJECT     // 无例外，集合相同也拒
  无项目事务        → open(sort(unique(ids))) → try fn()  finally close()
```

### 3.4 错误码：从 6 个改为 7 + 1（这是本轮唯一的口径变化，需说明）

| 码 | 来源 | 说明 |
|---|---|---|
| 6 个项目锁码（`TX_MUST_BE_IMMEDIATE` 等） | **D-30-13** | 原样不动 |
| `TX_PROJECT_NOT_LOCKED` | **P5-1 落实项**（D02-39 §2.1，用户已确认该方案与该码名） | **不是新增决策**，是已确认方案的落地码 |
| `ASYNC_TX` | **既有码**（`db.js:486`） | `txProject` 沿用，不新造 |

⇒ 封闭集 = **8**。**新增第 9 个必须回到 D-30-13 并升版**（已写入 §6.1）。

### 3.5 两库两套实现，一套契约

| 项 | SQLite | PostgreSQL |
|---|---|---|
| 互斥来源 | **库级** `BEGIN IMMEDIATE` | **项目级** `pg_advisory_xact_lock` |
| `lockedProjects` 的作用 | **仅契约记账**（互斥与它无关） | 记账 + 断言依据 |
| 超时 | `busy_timeout=5000` | `SET LOCAL lock_timeout='5s'` |
| 释放 | `COMMIT`/`ROLLBACK` | 随事务自动释放，崩溃不残留（D02-39 LOCK-11 实测） |

**不得合并表述**（「统一升级为 BEGIN IMMEDIATE」这类说法在 D02-32 已被删除）。
