## 四、段 ID 与历史候选关联证明

### 4.1 身份判定规则（写死在 `decideSegmentId`，不靠调用方声明）

复用旧段 id 必须**同时**满足：

1. 段行存在且 `project_id` 等于本次项目；
2. 该段当前归属的 `story_shots` **非空**；
3. 这些归属镜**全部属于本组**（`owners ⊆ group`）。

第 2 条是本次修复的核心：镜被删光后 owners 为空，**空集是任何集合的子集** —— 只做子集判断会把「旧段（还挂着候选）」判成「同一逻辑段」，正是原缺陷。

不满足 ⇒ 一律换身份：`seg_` + `sha256(base + '|alt|' + 组内镜 id 全集排序)`.slice(0,32)。
同一组镜重复投影得到同一 alt id（幂等）；组内换镜得到另一个 alt id（不继承旧候选关联）。

### 4.2 SQLite 侧证明（`C01-14`，实跑通过）

```
旧段 old.id（visual='画面2', duration=4）挂候选 v-d48-c
→ 删除旧镜（段成为 0 归属）
→ 新镜 global_no=3 进入同场次 ⇒ idx=2 ⇒ base id 恰等于 old.id
断言：旧段逐列不变；候选仍在且 shot_id 仍等于 old.id；新镜 segment_id ≠ old.id；
      新段 visual='新画面'、duration=6；conflicts=[{base:old.id, assigned:新 id, reason:'orphaned_with_candidates'}]；
      blocked=[old.id]
```

### 4.3 PostgreSQL 侧证明（`PGPROJ-06`，实跑通过）

```
oldSeg=seg_9ba61d3a732d4646e95e39c380c7108b（候选 pg-cand-d48.shot_id 指向它）
newSeg=seg_d9dafe80ed731fec8efb00aa0a073f03
oldVisual=旧镜画面（未被覆盖） conflicts=["orphaned_with_candidates"] blocked=1
```

### 4.4 身份不翻动（`C01-17`）

候选冲突换名后，再用**显式 units 但不给 `segment_id`** 投影：段序 base 会再次撞上旧段 id。`decideSegmentId` 第 ① 步（组内镜已共同指向 alt 段）优先保持既有身份 ⇒ `created=0`、段 id 不变、旧段仍在、候选未改挂。

### 4.5 四类情形可区分（`conflicts[].reason`）

| reason | 含义 | 处置 |
|---|---|---|
| `owners_outside_group` | 段仍在，但归属别的镜 | 换新身份，不覆盖 |
| `orphaned_with_candidates` | 段已失去全部归属且**仍有候选** | 换新身份，旧段保留、候选保留 |
| `orphaned_without_candidates` | 段已失去归属且无候选 | 换新身份，旧段按 0 镜段规则删除 |
| `candidates_without_segment` | 段行不存在但仍有候选指向该 id | 换新身份，不"复活"该 id |

> **建议**：把 `segment_id` 纳入 `VOLATILE.story_shot`。
> **理由**：它是投影派生的**归属指针**，不是创作内容；逐镜落 A2 update 日志会把内容日志淹掉，直接损害 A6「投影日志增量为 0」的可判定性。

> **替代方案**：保留现状（不审计 + 仅值变化时写），在 D02-40 中以「投影专用写入例外」条款形式登记。
