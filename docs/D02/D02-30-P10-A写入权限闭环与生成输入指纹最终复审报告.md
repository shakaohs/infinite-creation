## 二、任务 1：五个字段的唯一写入路径

### 2.1 矛盾的原样复述

D02-29 同时成立的三句话：

| 出处 | 原话（等价） |
|---|---|
| §2.4 | `structured_spec=1` 时 `creative` **只写 Stage 3 实体**，项目上不因它写 `shots` 创作列 |
| §3.2 表 | `mode`、`first_frame_path`、`last_frame_path`、`reference_image_path`：`story_shots` 无列 ⇒ **暂存 legacy `shots`** |
| §6.4 表 | `video_prompt` 属 **A 组创作**，权威来源写「**无列** ⇒ 暂存此处」 |

⇒ 这五个字段必须被改，却没有任何角色被允许改它们：`creative` 被禁写 `shots`；`render` 只写 C 组；`system` 只碰生命周期；投影只写 A 组 18 列。**这是一个死结，不是措辞问题。**

### 2.2 根因：三条独立错误叠在一起

| # | 错误 | 说明 |
|---:|---|---|
| 1 | **分组判据不一致** | A 组应按「**是否有 Stage 3 落点、是否由 Stage 3 权威**」判定，D02-29 对 `video_prompt` 却用了「谁写的（创作者）」当判据。按落点判，它与 `mode`／三张图同类：**Stage 3 没有列** |
| 2 | **B 组在 writer 表里没有写者** | §2.4 的三行表把 B 组完全漏掉。这不是遗漏一格，而是「参数写入链」整条不存在 |
| 3 | **本轮禁止加列/加表** | 任务书明确不允许扩 `story_shots`、不允许新建配置表 ⇒ 五个字段只能留在 `shots` |

D02-27 §4.2 原本的分类是对的：B 组 = `resolution`／`aspect_ratio`／`mode`／`video_prompt`／三张图／`seed`，并写明「产物单元行（Stage 3 无对应列），legacy 可写：是」。D02-29 把 `video_prompt` 挪进 A 组，才制造了这个死结。**本轮把它挪回去。**

### 2.3 唯一推荐方案：段级参数域 + 独立写入口

**【建议方案】** 三个定义先立住，方案自然唯一：

| 定义 | 内容 | 依据 |
|---|---|---|
| 权威位置 | 五个字段的权威**就是段行 `shots`**，不是「暂存」 | Stage 3 无列；生成链只读段行；本轮禁加列 |
| 语义层级 | 它们是**段级**（一次生成读一行），不是镜级 | `prepareShotForRender(ctx, shotId)` 一次只读一行（`tools.js:2417`） |
| 唯一写者 | `ShotParams.update(unitId, fields, { origin })`，模块 `lib/core/render/unit-params.js`，**5 列白名单 SQL** | 与 `projectRenderUnits()` 同一手法：代码级边界，不靠运行时字符串 |

`ShotParams.update()` 的契约：

| 约束 | 内容 |
|---|---|
| 入参 | `unitId` + 具名键（只认 `video_prompt`／`mode`／`first_frame_path`／`last_frame_path`／`reference_image_path`）+ `origin`（审计串） |
| 白名单 | SQL 字面量只列这 5 列 + `updated_at`。**物理上写不到** A/B 之外的任何列 |
| 前置 | ① 段行必须存在且 `project_id` 可解析；② `isStructuredSpec(projectId) === true`，否则抛 `SHOT_PARAMS_LEGACY_MODE`（旧链路有自己的写者，不许多开一条） |
| 校验 | `mode` ∈ `VIDEO_MODES` 或空串；三张图必须是项目内相对路径（复用 `resolveProjectPath` 的越界防护）；`mode='first_last'` 时首尾帧必须同时非空（与 `tools.js:2437` 的生成期校验对齐，前移到写入期） |
| 记录 | 不写 `change_logs`（结构化项目的内容回滚未定义，见 §3.6）；`updated_at` 正常刷新 |
| 不触发 | **不触发投影**（投影不写 B 组，见 §2.7）；过期判定靠现算指纹，无需标记 |
| 返回 | 更新后的段行（供 HTTP 回包与 UI 就地刷新） |

### 2.6 为什么不让普通 `Shots.update` 兼任（三条硬理由）

1. **会让兼容包装器重新获得权限**：`legacyShotWrite()` 内部就是调 `Shots.update`。一旦 `Shots.update` 能写 B 组，包装器就能写 B 组，任务 2 的验收项「结构化项目不能通过兼容包装器继续写入旧创作字段」当场失守。
2. **`render`／`system` 的字段门禁将无法区分意图**：同一个 `{video_prompt}` 键，来自创作工具是合法，来自渲染回写是缺陷（D-29-B 要禁的正是后者）。字段集判据分不出来，只能靠代码纪律。
3. **独立 SQL 让「投影不写 B 组」变成可静态断言的事实**：`projectRenderUnits()` 的列清单里没有 B 组，`ShotParams.update()` 的列清单里没有 A 组，两条 SQL 互相看不见。这比「两个函数都遵守约定」强。

### 2.7 为什么不在本轮扩 `story_shots` / 新建参数表

| 方案 | 需要 | 结论 |
|---|---|---|
| 给 `story_shots` 加 `mode` + 三张图 + `video_prompt`（4 列） | DDL + manifest + 投影 + 生成链改读 | **本轮禁止**，且语义不对：这四个是段级参数，加在镜表上会立刻产生「同段多镜参数冲突」，还得再造一套冲突仲裁 |
| 新建 `render_params` 表 | 1 表 + 投影 + 同步 | 本轮禁止；且它就是把阶段 4 的 `render_units` 提前建一半，将来必然合并 |
| **段行 + 专用入口（推荐）** | 0 DDL | 与现有生成链零改动兼容，且把「谁能写」用代码边界冻结 |

何时该扩列：当「一个段内的镜需要各自不同的 `mode`」成为真实需求时（当前 UI 只在插入自定义分镜时给 `mode`，段内多镜本就该同模式）。那时作为独立架构决策提出，不在本轮。

### 2.8 创作修改 → 投影 → 视频过期判定（完整时序）

```
① 创作写入（A 组 16 列）
   Stage 3 服务（story_shots / shot_assets / shot_blockings / shot_actions）
   └─ 同一事务内：projectRenderUnits() —— 只写 A 组 17 列 + 建行状态
        └─ 不写 B 组、不写 C 组、不写 E 组、不写 change_logs（§3.6）

② 参数写入（B 组 5 列）
   ShotParams.update() —— 只写 5 列 + updated_at
   └─ 不触发投影（无 A 组变化）

③ 产物写入（C 组 6 列）
   生成链 writer='render'，部分列 UPDATE

④ 过期判定（惰性，不落库）
   expired = selected.input_hash !== segmentInputHash(段当前输入)
   selected.input_hash === ''  → unknown（按过期处理，reason='unknown_provenance'）
   判定点：导出打包、整片合成、应用 BGM 的前置门、整章生成的筛选（§6.2 的四处）

⑤ 段结构变化（镜增删/拆分/合并）
   投影重算 unit id 集合；旧候选的 input_hash 与新段不匹配 ⇒ 过期；
   旧候选**永不改挂**（ShotVideos 无 update 方法，db.js:1018~1041 结构性保证）
```

关键点：**没有任何一步需要「标记过期」的写入**。过期是现算的比较结果，所以不需要新列、不需要状态枚举，也不会出现「标记漏写」的脏状态。

### 3.2 包装器如何获得并检查 `projectId`：**它不该获得**

**【建议方案】** 包装器签名固定为 `legacyShotWrite(source, fn)`，**不接受、不传递、不缓存 projectId**。理由不是洁癖：

- `Shots.remove(id)` 只有行 id，没有 projectId 参数。包装器若「猜」一个 projectId，猜错就等于拿 A 项目的开关去判 B 项目的权限。
- 如果包装器接受 `projectId` 参数，调用方就能传一个 `structured_spec=0` 的项目 id 来解锁——**这就是最直接的绕过路径**。

⇒ projectId 只能由服务方法从**自己手里已有的东西**解析：

| 方法 | projectId 来源 | 时机 |
|---|---|---|
| `Shots.create(projectId, fields)` | 第 1 个实参 | 写库前 |
| `Shots.insertAt(projectId, chapter, idx, shot)` | 第 1 个实参 | 事务开始前 |
| `Shots.update(id, fields, opts)` | `this.get(id).project_id` | 已在方法内读过整行（`db.js:985`），零额外查询 |
| `Shots.remove(id)` | `rawGet('shot', id).project_id` | 方法本来就 `rawGet` 做快照（`db.js:1005`），零额外查询 |

### 3.3 如何识别 `structured_spec=0/1`（三个坑）

| 坑 | 正确做法 | 证据 |
|---|---|---|
| `Projects.get()` 返回的 `structured_spec` 是 **0/1 数字**，不是布尔 | 一律 `isStructuredSpec(projectId)`；**禁止** `=== true` | `db.js:521`（`toProject` 不转换）＋ `project-create.js:14~16` 的显式提醒 |
| `isStructuredSpec()` 对不存在的项目返回 `false`（读路径要稳，故意 fail-open） | 写门禁必须先证明**行存在**、再证明**项目存在**；项目缺失抛 `SHOT_PROJECT_NOT_FOUND`，不当作旧链路 | `structured-spec.js:15~18` |

| 项 | 规则 |

### 4.6 媒体内容指纹怎么算

| 项 | 规则 |
|---|---|
| 算法 | `sha256(file bytes)`，对**本地文件**算，不对「上传后的名字」算 |
| 为什么可信 | 三条上传通道都字节透传：native `readFileSync → Blob`（`comfyui.js:37~40`）；RunningHub 上传同一 `buf`；外接引擎 `dataUrlOf` 读同一文件（`engine-runner.js:66~76`） |
| 缺失文件 | 写 `'missing'` 哨兵。生成期本来就会抛错（`tools.js:2453`），但指纹必须先能表达「文件没了」 |
| 缓存 | 进程内 LRU，键 `(absPath, size, mtimeMs)`；**渲染时强制实算（绕过缓存）**，判定时允许命中缓存 |
| 残余风险 | 文件被替换但 `size` 与 `mtimeMs` 完全相同的极端情况会漏判；导出前可 `forceRehash`，登记为 U-30-5 |
| 大文件 | 逐块 `crypto.createHash('sha256')` 流式读，不整文件进内存 |

### 4.7 时点：必须在渲染开始，禁止结束时回读

**【建议方案】** 在 `prepareShotForRender` 的返回值里增加 `inputSnapshot`（含 §4.4 的完整 payload 与 `hash`），`renderShotCandidate` 只做一件事：把它原样交给 `ShotVideos.create(projectId, shotId, { idx, video_path, seed, input_hash: prepared.inputSnapshot.hash })`。

三条禁令：

1. **禁止**在 `finalizeShot`／下载完成后重新读 `Shots.get` 再算——那时用户可能已经改了台词，会把旧输入生成的视频标成新输入的产物（任务书点名的正是这个错误）。

**为什么把「creative 保持 32 列」也改掉**：`Shots.update` 的合并（`db.js:987`）会把「读取时刻的旧值」一并写回。创作写入与渲染写入并发时（渲染持有 `prepared.shot` 数十秒，`tools.js:2491`），无论谁后写，都会把对方的列覆盖回旧值。只给 `render` 改部分列，等于只修了一半——创作侧仍然会覆盖 `video_path`。统一改部分列是唯一不需要额外锁就能消除这类覆盖的做法，且行为等价（调用方本来就只传要改的列）。

## 九、结论：是否达到编写 P10-A 正式实施任务书的条件

### 9.2 结论：**不予放行**

七条都给了明确判定：1~4 在「口径层」闭合但**未到可执行**，5~6 已满足，7 已保留。放行条件不是口径闭合，而是可实施——以下四项仍使 P10-A 任务书无法写成可执行状态：

1. **决策未获批**：D-30-04／05／06／07／08／09／11／15 八项全部待批；未批就写实施任务书，等于把待批方案当既定事实。
2. **D02-28 的三项硬门槛仍在**：`segment_id`、`scene_uid`、并发实跑。前两项未批 ⇒ DDL 草案无从写；第三项未跑 ⇒ `txLocked` 只能算设计完成。
3. **三个新阻断项会影响任务书的章节结构**：B-30-1（Agent 寻址）、B-30-2（回滚）、B-30-4（无回退开关）——它们不是实现细节，而是「P10-A 交付范围」的一部分，必须先定。
4. **B-30-7（自定义插入的两阶段契约）**未定义 ⇒ 验收标准第 1 条严格说还没到「可执行」。

### 9.3 放行所需的最小动作集（按顺序）

1. 批准 **D-30-04／05／06／07／08／09／11／15**（其余可并行批）。
2. 关闭 **B-30-1／B-30-2／B-30-4**（各给一个唯一选择，不再保留双方案）。
3. 补齐 **D-30-01／02／03** 的 DDL 草案（3 列 + 2 索引 + `continuity_runs` 8 列 2 索引），并在真实 PG 上跑一次 `txLocked` 交错（U-28-4）。
4. 写 **激活路径**（替代「存量迁移细案」）：真实库迁移量为 0，但「新项目如何进入结构化」必须成文，含 `setStructuredSpec` 的受控开关。
5. 在任务书里固定「同一 PR 交付」清单：投影 + 参数入口 + 四处有效性判定 + 3414 筛选 + `input_hash` 写入。任何一项分两次上线，都会出现「投影上线但过期视频仍被导出」或「停写提示词后全量重渲」的窗口。

**最终原则不变：先把权限和数据来源闭环，再实施代码。** 本轮把「闭环的形状」定完了，但闭环还没被批准，也没被真实 PG 与回退开关验证过——所以现在写 P10-A 实施任务书，仍然会把「待批方案」写成「既定事实」。
