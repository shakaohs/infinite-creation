## 一、D45-01：结构化镜号分配安全性

### 1.1 修复前（`3253be7`）

镜号计算整段在 `txProject` **外面**：

```js
const chapterMax = {};
for (…显式 idx…) chapterMax[ch] = Math.max(chapterMax[ch] || 0, n);
for (const ch of chapters) {
  if (chapterMax[ch.title] !== undefined) continue;          // ← 本批有显式 idx 就跳过
  const r = getDb().prepare('SELECT MAX(shot_no) …').get(ch.id);
  chapterMax[ch.title] = Number(r?.m ?? 0) || 0;
}
const idxs = chapterTitles.map((ch, i) => {
  if (raw != null) return idx;
  const n = (chapterMax[ch] || 0) + 1; …
});
txProject(projectId, () => { …写入… });
```

三个独立缺陷：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | `SELECT MAX(shot_no)` 在锁外 | 两个并发追加读到同一个 MAX，算出同一个号。撞 `uq_ss_sn` 只是把"静默错"变成"报错"，**不是正确分配** |
| ② | 本批**有**显式 idx 时**不读库内 MAX** | 「已有 1~3，显式更新 1，同时自动追加一镜」算出 `1+1=2`，**覆盖掉既有的第 2 镜**。显式 idx 表达的是"更新谁"，不是"现在最大到几" |
| ③ | `MAX` 在 `clear` 之前之外的路径上无保护 | `clear` 会改变章内既有镜集合，若 MAX 在 clear 之前读，被清掉的号仍占上限 |

### 1.2 修复后（本轮）

整个计算搬进 `txProject`，顺序固定：**进事务 → `clear` → 锁内读 MAX → 并入本批显式 idx → 再给自动号续号**。

- `lib/agent/tools.js:2340` 事务开始
- `:2352` 锁内逐章读 `COALESCE(MAX(shot_no), 0)`（**在 clear 之后**）
- 随后并入本批全部显式 idx（`Math.max`），最后自动号从合并值 +1 起（`chapterMax` 逐次自增即天然覆盖"本批已分配的自动号"）

这样自动号必然落在「库内既有最大值」与「本批显式最大值」两者的**较大者之后**，不可能覆盖任何未显式指定的既有镜。

### 1.3 证据

| 用例 | 场景 | 断言 |
|---|---|---|
| D45-01-A | 已有 1~3，显式更新 1 + 自动追加 | 新镜得 **4**；第 2/3 镜内容与行 id 都没变（修复前会得 2 并覆盖第 2 镜） |
| D45-01-B | 已有 1~5，混合显式 2 + 两个自动 | 号序列 `[1,2,3,4,5,6,7]`；第 1/3/4/5 镜行 id 与内容逐格不变 |
| D45-01-C | 显式追加到 9 号 + 同批自动 | 自动号得 **10**（不是 4）——证明显式 idx 也并进了上限 |
| D45-01-D | **两个独立进程**并发追加 | 号序列 `[1,2,3,4,5]` 连续唯一；两边 `added=1, updated=0`（不得因为撞号走进 update 去改对方刚建的镜）；既有 3 镜行 id 不变 |
| D45-01-E | `clear` + 自动号 | 清 3 条后自动号得 **1**（MAX 必须在 clear 之后读） |
| D45-01-F | `clear` + 显式 3 + 自动 | `[3, 4]` |
| D45-01-G | 追加后 `global_no` | `[1,2,3,4,5]` 严格递增、无重复（仍在锁内分配） |
| D45-01-H | legacy 项目（`structured_spec=0`） | `shots.idx` 仍为 `[1,2]`，`story_shots` 零行 —— legacy 行为不变 |

并发用例走独立子进程（`tests/helpers/storyboard-worker.mjs`）：SQLite 是同步驱动，同进程两个事务天然串行，做不出"同时读到同一个 MAX"那个瞬间。

## 二、D45-02：站位字段保留与审计一致性

### 2.1 修复前（`3253be7`）

物理写入用的是**只含显式列**的 `normalized`，而物理动作是「整组 DELETE + INSERT」：

```js
const diff = diffShotBlockings(beforeRows, normalized);
db.prepare('DELETE FROM shot_blockings WHERE shot_id = ?').run(shotId);
for (const r of normalized) { …INSERT 只含显式列… }   // ← 未提交的列回落成 DDL 默认值
```

后果：调用方只想改 `facing`，`posture` / `norm_x` / `position_track` / `anchor_object` 全部被清成默认值，**而返回值写着"写入成功"**。审计也看不出来——差集是基于 `normalized` 算的，未提交字段根本不在比较范围内。

### 2.2 修复后（本轮）

物理写入前先做「before 打底 + 显式覆盖」的合并（`lib/core/render/shot-blockings.js:109~115`）：

```js
const beforeByChar = new Map(beforeRows.map((r) => [String(r.character_id), r]));
const merged = normalized.map((r) => {
  const prev = beforeByChar.get(String(r.character_id));
  if (!prev) return r;          // 新角色：只写显式列 ⇒ 仍吃 DDL 默认值
  return { ...prev, ...r };     // 已有角色：before 全列打底 + 显式字段覆盖
});
const diff = diffShotBlockings(beforeRows, merged);   // 差集基于 merged
…DELETE 全组 → INSERT merged…                          // 物理写入也用 merged
```

三条语义同时成立：

| 语义 | 实现 | 用例 |
|---|---|---|
| 本镜未提交的既有角色 = 删除 | 不在 `normalized` 里 ⇒ 不在 `merged` 里 ⇒ `removed` | D45-02-E |
| 已有角色的未提交字段 = 保留 | `{ ...prev, ...r }` | D45-02-A / B |
| 新角色未提交字段 = DDL 默认值 | 新行不合并，只插入显式列 | D45-02-D |

并且因为 `merged` 与 `before` 逐列可比，"完全相同的写入记 0 条"自动成立（D45-02-C）。

### 2.3 证据

| 用例 | 场景 | 断言 |
|---|---|---|
| D45-02-A | 已有 `facing`/`posture`/`norm_x`/`position_abs`/`gaze_target`/`position_track`，只提交 `character_id` | 六个字段**全部保留** |
| D45-02-B | 只提交 `facing` | 只 1 条 update；`posture`/`norm_x`/`position_abs`/`occlusion` 不丢；日志 `after` 快照里的 `posture` 等于库里的值 |
| D45-02-C | 完全相同的输入 | **0 条日志**（合并后与 before 逐列相等） |
| D45-02-D | 新增角色只给 `facing` | `in_frame=1`、`occlusion='none'`、`position_track='[]'`、`posture=''`、`norm_x=null` —— **不得继承上一个角色的值** |
| D45-02-E | 未提交既有角色 | 1 条 delete，`before` 是被删那一行的真实内容 |
| D45-02-F | 一次写入同时改+留+删+加 | 恰好 3 条日志；`update.after.posture` 保留原值；`create` 行吃默认值；被删行真的没了 |

## 三、D45-03：镜头更新与删除快照一致性

### 3.1 修复前（`3253be7`）

| 函数 | 缺陷 |
|---|---|
| `updateStoryShot` | 锁外读 `before` 只为拿 projectId（这点没错），但锁内 `cur` **没有存在性检查**。镜在锁内被删时 `cur = null`，`recordChange` 抛的是 `AUDIT_SNAPSHOT_UNREADABLE`（错误码错位，真实原因是镜没了）；也没有归属变化检查 |
| `deleteStoryShot` | **完全**用锁外读到的行当 before 快照。锁外读之后、取锁之前若有并发事务改了这行，日志记的是一个**从未在库里存在过的状态**，回滚会把这个"幻影"当目标值还原。`DELETE` 也不检查影响行数 |

### 3.2 修复后（本轮）

两个函数统一成同一形态（`lib/core/render/global-no.js:272` / `:320`）：

```
锁外 rawGet  →  只取 projectId，注释里写明"不参与审计"
txProject    →  assertProjectLocked
              →  锁内 rawGet = 真正的 before
              →  null            ⇒ SHOT_NOT_FOUND
              →  project_id 变了  ⇒ SHOT_NOT_IN_PROJECT
              →  UPDATE / DELETE
              →  changes !== 1  ⇒ SHOT_NOT_FOUND（不静默成功）
              →  recordChange(before = 锁内那一行)
```

### 3.3 「锁内快照」怎么被确定性证明

对比"锁外快照 vs 锁内快照"需要一个**两次读之间可以改库**的注入点，而生产代码不该为测试开洞（D42-02 的纪律）。做法是**纯测试侧的读探针**：

拦截 `db.prepare` 拿到的 `SELECT * FROM story_shots WHERE id = ?`，在第一次 `get()`（锁外）返回之后立刻把库改成另一个值，于是第二次 `get()`（锁内）读到新值。若实现用的是锁外快照，审计 `before` 会是旧值。

| 用例 | 断言 |
|---|---|
| D45-03-A | update 的 `before.visual_content` = 毒化后的新值（**若是旧值说明用了锁外快照**） |
| D45-03-B | delete 的 `before.visual_content` = 「删前最后一版」（**若是初始值说明用了锁外快照**） |
| D45-03-C | update 前镜消失（锁内读不到）⇒ `SHOT_NOT_FOUND`，且不留 update 日志 |
| D45-03-D | delete 前镜消失 ⇒ `SHOT_NOT_FOUND`，且不留 delete 日志 |
| D45-03-E | 锁内发现 `project_id` 变了 ⇒ `SHOT_NOT_IN_PROJECT` |
| D45-03-F | 先证前提（SQLite 对 0 行 UPDATE / DELETE 返回 `changes=0`），再证正常路径仍成功 |
| D45-03-G | 审计失败 ⇒ update / delete 都回滚（行还在、内容还是原来的） |
| D45-03-H | **两个独立进程**：一个 update、一个 delete —— delete 的 `before` 必须是 update 之后的内容（若为初始值说明用了过期快照）；update 失败时错误码只能是 `SHOT_NOT_FOUND` |
| D45-03-I | 四锁接口 arity 未变；异常路径也不留锁上下文 |

**一处必须说清的方法学限制**：D45-03-H 在 SQLite 下两个事务是串行的，"锁外读到过期值"的窗口本身很窄，因此该用例是**补充**而非主证。确定性证据是 A/B 两条探针用例——它们直接构造了"锁外读之后被改库"的时序，不依赖调度运气。

### 3.4 为什么回滚用例换了触发方式

`tests/d02-45-d45-03-snapshot.test.mjs` 的 D45-03-G 原本打算沿用 B02-06 的手法（临时删掉 `ENTITY_META.story_shot`）。**行不通**：`rawGet` 也依赖 `ENTITY_META`，删了它连 before 都读不到，会先抛 `SHOT_NOT_FOUND`，测不到"审计抛错后业务写入回滚"这一条。

改为让**归属解析失败**（临时把 `ENTITY_META.story_shot.projectOf` 换成返回空串）⇒ `requiredProjectIdOf` 抛 `AUDIT_PROJECT_UNRESOLVED`，此时行已经 UPDATE/DELETE 过了，正好验证回滚。这是同一类失败（A 类审计抛错），且不依赖"删元数据"这种会连带破坏读路径的手法。

## 五、阶段 B 退出条件冲突分析（**待裁定**）

### 5.1 冲突的原文

**D02-40 §3.0 阶段总览**（第 250 行）：

> **B**｜Stage 3 创作写入链（场次、镜、资产引用、站位、动作）｜硬依赖：A 完成 且 P2/P4 通过｜**退出条件：五个写入器均有生产调用方；A1~A5 审计按矩阵生效**

| B-02 | 分镜生成、投影 |

### 5.2 冲突是什么

1. **循环依赖**：§3.0 要求阶段 B 退出时"五个写入器**均有**生产调用方"；而 §3.2 把 B-04/B-05 的下游调用方定义为「投影、求解」，B-03 定义为「投影、渲染绑定」。**投影属阶段 C**（`§3.3 生成段投影与写权限`），**求解属阶段 E**（`§3.0 E｜连续性与 QC 接管`）。要满足退出条件就得先做 C 或 E，而 C/E 的硬依赖里写着"B 完成"。
2. **同一类错误**：这与 D02-37 修掉的 P2/P4 循环依赖**结构完全一样**——「把一个测未实现产物的 Gate 写成前置条件」。D02-37 的结论是：Gate 的位置由「它测的东西在冻结时是否已存在」决定，不能反过来。
3. **本轮实测**：即便按最宽松口径（把"写入器被另一个写入器内部调用"也算链路），A3/A4/A5 仍是零；按严格口径，A2 也只是"条件可达"（需要 `structured_spec=1` 的项目，而真库全为 0）。

| 方案 | 改哪一句 | 差异大小 | 代价 |
|---|---|---|---|

**我不建议方案 C**：它改的是「下游」这一列的含义，而这一列在 B-01/B-02 上确实表达"本轮之后能服务谁"，改动会让整张表失去一致语义。

**方案 A 的理由**：它保留"必须有人用"这个实质要求（禁止空挂能力），只把"现在就必须有人用"改成"必须说清谁会用、什么时候用"。这也正是本轮报告已经做到的事——§4.2 的表就是那份归属表。
