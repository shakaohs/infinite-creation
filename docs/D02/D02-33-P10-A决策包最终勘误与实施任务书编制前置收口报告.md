## 三、D33-02：执行配置对象与 Hash 投影分离

### 3.1 两个结构，不是同一个

| 结构 | 用途 | 内容 | 生命周期 |
|---|---|---|---|
| **`ExecConfig`** | 运行时真正驱动请求的对象 | 引擎全部 21 个字段 + 后端判别 + 秘密 | 只在内存中，随渲染结束丢弃；**永不落库、永不整体序列化进日志** |
| **`HashProjection`** | 只用来算 `exec` 段的 Hash | 白名单 9 个引擎字段 + 5 个非引擎身份字段 | 随 `input_hash` 一起落 `shot_videos.input_hash`（仅摘要，不含原文） |

**为什么必须分开**：若直接对 `ExecConfig` 整体 Hash，则 ① `apiKey` 会被算进摘要（违反秘密不得入 Hash）；② 新增一个编排字段（如 `pollTimeout`）会**静默**改变所有历史候选的指纹，导致全量假过期；③ 无法审计「到底哪些字段进了指纹」。

### 3.2 `HashProjection` 的构造规则（防整体 Hash 的白名单）

```
hashProjectionOf(exec) → 逐字段显式 new object
```

| 规则 | 内容 | 反例（禁止） |
|---|---|---|
| H1 白名单构造 | 函数体内**逐字段赋值**，字段名与 §3.4 的表一致 | `{...exec}` 、`JSON.parse(JSON.stringify(exec))` |
| H2 禁止删除式 | 不得 `const p = {...exec}; delete p.apiKey` | 删除式是**黑名单**：新增字段默认进 Hash |
| H3 断言键集 | 单测断言 `Object.keys(hashProjectionOf(EXEC))` 等于冻结列表（顺序无关，集合相等） | 只断言「某个键存在」 |
| H4 新增字段默认不进 | `ExecConfig` 加字段不改变投影；要进必须同时改白名单与 `SEG_INPUTHASH_ALGO` 版本号 | 「加了字段自然就进了」 |
| H5 秘密零接触 | 投影构造函数的入参允许含 `apiKey`，但函数体内**不得读取**它；由 H3 的键集断言兜底 | 先取 `exec.apiKey` 再「不放进结果」 |
| H6 版本绑定 | 白名单变更 ⇒ `SEG_INPUTHASH_ALGO` 从 `seg-2` 升到 `seg-3` | 悄悄改白名单 |

### 3.3 21 个配置字段的四态映射（最终）

「执行时消费」= 代码里读它；「保存到 ExecConfig」= 运行时对象里有它；「进 Hash 投影」= 出现在 `hashProjectionOf` 结果里；「变化触发失效」= 已落库候选变过期。

| # | 字段 | 执行时消费 | 保存到 ExecConfig | 进 Hash 投影 | 变化触发失效 | 说明 |
|---:|---|---|---|---|---|---|
| F1 | `id` | 是（产物文件名、日志） | 是 | **是** | **是** | 引擎身份 |
| F2 | `name` | 是（日志、状态回调） | 是 | 否 | 否 | 仅展示 |

### 3.4 `ExecConfig` 与 `HashProjection` 的 Schema

**`ExecConfig`（外接引擎变体）**

```
{
  backend: 'engine',
  family: 'image' | 'video',           // 由 kind 派生
  id, name, kind, enabled, tasks,
  baseUrl, model, apiKey,              // apiKey 只在此层存在
  authHeader, authPrefix,
  submitPath, requestTemplate,
  taskIdPath, pollPath, pollMethod, pollBody, statusPath,
  doneValues, failValues, outputUrlPath,
  extraHeaders, syncMode
}
```

**`ExecConfig`（native / RunningHub 变体）**

```
{
  backend: 'native' | 'runninghub',
  provider,                            // cfg.comfyui.provider
  hardware,                            // hardwareMode(cfg)
  endpoint,                            // cfg.comfyui.baseUrl（native）
  specId, specKind, promptFormat,
  specSourceText                       // 冻结的工作流源文本（仅内存）
}
```

**`HashProjection.exec`（唯一白名单，字段名即断言对象）**

```
{
  backend, provider, hardware, endpoint,
  engine: null | {
    id, family, model,
    baseUrlSha256, submitPath, outputUrlPath,
    templateSha256, extraHeadersSha256, syncMode
  },
  specId, specKind, promptFormat, specSha256
}
```

**精确边界（写进实现注释）**：

| 项 | 位置 |
|---|---|
| `apiKey` | 只在 `ExecConfig`；**不得**出现在 `HashProjection`、日志、错误信息、`change_logs` |
| `taskIdPath` | 在 `ExecConfig`；**明确不进** `HashProjection` |
| `extraHeaders` | 在 `ExecConfig` 保存**模板原文**；投影只放 `extraHeadersSha256(模板原文)`，**不渲染** |
| `requestTemplate` | 同上，投影只放 `templateSha256(原文)` |
| 渲染后的请求体 | 只在内存里发给 HTTP 客户端；**永不落库、永不进日志**（它含 key） |

### 3.5 新增的测试（设计完成，**未执行**）

| 编号 | 用例 | 断言 |
|---|---|---|
| TST-CFG-13 | 键集冻结 | `Object.keys(hashProjectionOf(EXEC))` 集合等于 §3.4 列表 |

### 3.6 语义边界（沿用，不得松口）

`input_hash` 是「渲染时刻的段输入版本」，**不是**模型输入字节证明。`covered` 段是超集（A 组内容只在 fallback 提示词路径下才真正成为模型输入）。对外展示、导出说明、错误信息都不得把 `input_hash` 描述成「这份视频就是由这些字节生成的」。

## 四、D33-03：内容寻址对象身份（修订 D-31-02 v3）

### 4.1 身份定义（把上一轮的措辞错误纠正掉）

D02-32 写的是「名字只由字节决定」。这句话在保留原扩展名时**不成立**：`a.png` 与 `b.png` 字节不同没关系，但同一份字节若一个按 `.png`、一个按 `.jpg` 命名，就会得到两个对象。所以必须改成：

> **对象身份 = (字节的 SHA-256, 规范化扩展名)**
> **对象名 = `ic-<64 hex>.<ext>`**，其中 `<ext>` 是规范化扩展名（含点、小写，如 `.png`）。

**扩展名从哪来（唯一顺序）**：

| 步骤 | 规则 |
|---|---|
| ① 魔数嗅探 | 按内容判定：`PNG`→`.png`、`FFD8FF`→`.jpg`、`GIF8`→`.gif`、`RIFF....WEBP`→`.webp`、`BM`→`.bmp`、`RIFF....WAVE`→`.wav`、`fLaC`→`.flac`、`ID3`/`FFEx`→`.mp3`、ISO BMFF（`ftyp`）→按 brand 判 `.mp4`/`.mov`、`1A45DFA3`（EBML）→`.webm` |
| ② 路径兜底 | 嗅探失败时取源文件路径扩展名，小写化；**必须在受支持集合内** |
| ③ 失败关闭 | ① ② 都得不到受支持扩展名 ⇒ 抛 `UNSUPPORTED_MEDIA_EXT`，中止本次渲染（不猜、不改名） |

**为什么允许 ② 的兜底**：嗅探表只覆盖渲染链真正接受的格式；对没覆盖到的合法格式（或容器变种），用路径扩展名比「拒绝渲染」更安全。代价是同一份字节经两条不同路径上传会得到两个对象——**只是重复存储，不会串台**，符合 I3/I4（不同名不覆盖、同名必同字节）。

**规范化必须做的三件事**：小写化；`.jpeg` → `.jpg`；去掉多重扩展名（`x.tar.png` → `.png`）。

### 4.2 不可变性保证（本系统上传路径）

| 保证 | 内容 | 为什么成立 |
|---|---|---|
| G1 身份函数 | 名字是 `(digest, ext)` 的函数，与调用者、时间、项目无关 | H1 构造规则 |
| G2 写一次 | 对同一身份，本系统只会写**同一份字节**：不同字节 ⇒ 不同 digest ⇒ 不同名字 | 由 G1 直接推出 |
| G3 幂等重写 | 同一身份重复上传是「用相同字节覆盖同名对象」，字节不变 | 上传实现是覆盖写 |
| G4 无跨任务覆盖 | A 任务排队期间，任何其他任务写同一名字必然是同一份字节 | G2 |

**G2 的边界说明**：G2 保证的是「本系统发出的上传请求不会用不同字节覆盖同名对象」。它不保证「远端对象一定还是我们写的字节」——见 §4.3。

### 4.3 第三方绕过本系统的风险边界（如实登记）

| 场景 | 是否可能 | 后果 | 处置 |
|---|---|---|---|
| 有人手工往 ComfyUI `input/ic-<hash>.png` 写入不同字节 | **可能** | 该名字的对象不再等于摘要描述的字节；排队中的任务会消费错字节 | 严格模式（§4.4）可发现；默认模式不可发现。登记为 U-32-6 |
| 另一个使用**不同命名方案**的程序往同一目录写 | 可能 | 同上 | 命名空间上不冲突（我们的前缀是 `ic-`），但同名伪造仍可能 |
| 另一个实例使用**相同**命名方案 | 可能 | 不同字节 ⇒ 不同名字，无冲突 | G2 覆盖 |
| 上传被截断/损坏 | 可能 | 对象存在但字节不完整 | 严格模式可发现；默认模式下客户端与服务端都会因解析失败报错（图裂/音频非法），不会静默出错片 |

**结论**：默认模式的保证是「本系统自身不会制造串台」；「外部篡改」需要严格模式才可发现。这句话必须原样写进文档，不得简化成「不会串台」。

### 4.4 三条通道保持差异（不得强行统一）

| 通道 | 媒体处理 | 命名策略 | 身份是否生效 |

**禁止事项**：不得为了让三通道「看起来一致」而把 RH 的平台名改成内容寻址名（会让云端工作流找不到文件），也不得把引擎通道改成「先上传再引用」。

## 五、D33-04：PostgreSQL 跨项目嵌套锁约束（修订 D-30-13 v3）

### 5.1 唯一入口与默认禁止

| 规则 | 内容 |
|---|---|
| R1 | `txProject(projectId, fn)` 是**项目级写入互斥的唯一入口**；任何源数据写入必须在其内 |
| R2 | **默认禁止**在同一事务内嵌套获取**不同项目**的锁：`txProject(P)` 内调 `txProject(Q)`（Q≠P）抛 `TX_CROSS_PROJECT_NESTED` |
| R3 | `txProject(P)` 内再进 `txProject(P)` **复用**外层锁（不重复取锁、不重复计数） |
| R4 | `tx()` 内调 `txProject(*)` **fail-closed**，抛 `TX_MUST_BE_IMMEDIATE`（SQLite 升级写锁失败会直接 BUSY，`busy_timeout` 不救） |
| R5 | 确有跨项目需求（如全局重编号、跨项目迁移）时，只能走 §5.3 的 `txProjects`；**不允许**用普通嵌套隐式实现 |

### 5.2 为什么必须默认禁止（不是洁癖）

| 风险 | 机制 |
|---|---|
| 死锁 | 事务 A 先锁 P1 再锁 P2，事务 B 先锁 P2 再锁 P1 ⇒ 互相等待，PG 检测到后杀一个（`40P01`）。`tx()` 是同步的，无法重试整个 `fn` |
| 锁泄漏 | 若实现者用会话级 `pg_advisory_lock`，异常路径漏 unlock ⇒ 两项目永久阻塞 |
| 顺序不可审计 | 「先锁谁」写在调用链深处，code review 看不出来；排序接口能让顺序成为显式契约 |
| SQLite 与 PG 语义分叉 | SQLite 只有一个库级锁，跨项目无所谓顺序；PG 有顺序。不禁嵌套，就会写出「SQLite 能过、PG 死锁」的代码 |

### 5.3 跨项目唯一接口：`txProjects(projectIds, fn)`

| 项 | 规定 |
|---|---|
| 入参 | `projectIds: string[]`（去重、去空） |
| 排序 | **按 `cmpStr` 升序**（项目禁用 `localeCompare`，与既有排序纪律一致） |
| SQLite | 单个 `BEGIN IMMEDIATE` 已覆盖全部；仍按排序取锁（只为日志顺序确定），实质无差别 |
| PostgreSQL | 按排序逐个 `SELECT pg_advisory_xact_lock(hashtextextended($i, 0))`，**全局一致顺序** ⇒ 不可能死锁 |
| 嵌套 | `txProjects` 内的集合必须**包含**外层已持锁的项目；否则抛 `TX_LOCK_SET_MISMATCH` |
| 上限 | 一次最多 8 个项目（防止误用成「全库锁」）；超出抛 `TX_TOO_MANY_PROJECTS` |
| 释放 | 全部随事务提交/回滚释放（`xact` 锁），无手工 unlock |

### 5.4 锁获取、执行、提交与中断（最终时序）

| 阶段 | SQLite | PostgreSQL |
|---|---|---|
| ① 开始 | `BEGIN IMMEDIATE` | `BEGIN` |
| ② 超时 | `busy_timeout=5000`（连接建立时已设） | `SET LOCAL lock_timeout='5s'` |
| ③ 取锁 | 由 ① 隐式 | 按排序逐个 `pg_advisory_xact_lock` |
| ④ 执行 | 同步 SQL | 同步 SQL（`Atomics.wait` 门面，单连接） |
| ⑤ 提交 | `COMMIT` → 释放写锁 | `COMMIT` → 释放全部 `xact` 锁 |
| ⑥ 异常 | `ROLLBACK` → 抛原错 → 锁释放 | 同左 |
| ⑦ 进程中断 | WAL 回滚未提交事务；文件句柄释放 | 连接断开 ⇒ 服务端回滚 + 释放 `xact` 锁；**不残留** |
| ⑧ 锁粒度 | **库级**（不同项目也串行） | **项目级**（不同项目并行） |

**再次明确（防止再被写成「统一升级」）**：`BEGIN IMMEDIATE` **只能发给 SQLite**；PG 用 `pg_advisory_xact_lock`。两库**粒度不等价**，文档、验收、性能说明都按此表述。

### 5.5 嵌套状态机（实现必须照此）

```
lockedProjects = Set()        // 当前事务已持有锁的项目
outermost = (txDepth === 0)

txProject(P):
  if outermost:
      openTx(IMMEDIATE | BEGIN) ; lock(P) ; lockedProjects.add(P)
  else if lockedProjects.has(P):  reuse
  else if txStartedByPlainTx():   throw TX_MUST_BE_IMMEDIATE
  else:                           throw TX_CROSS_PROJECT_NESTED   // 引导调用方改 txProjects

finally: if outermost: closeTx() ; lockedProjects.clear()
```
