### 3.2 为什么增量不进 `tables.js` / 不改 D01-05

`tests/stage1-schema.test.mjs` 会把 `tables.js` 的列集合与 **D01-05 冻结 DDL 文本**逐项比对；而 D-30-01/02 的批准书上「是否改正式规范」明确是**否**。所以本轮的三处列变化一律走「既有表补列 + 独立新表」：

```
initSchema = 既有表 DDL → initStage1Schema(21 张) → initStageA(3 列 + 1 表) → 基线批次
```

`initStageA` 放在 21 表之后（`story_shots` 由它建）、基线批次之前（基线记录的含义是「这套结构已就位」）。`SCHEMA_BASELINE_SCRIPT_VER` 由 `stage1-ddl/d02-04.1` 升为 `stage1-ddl/d02-41.1`：基线 DDL 文本没改，但**新库建出来的结构变了**，版本号不升就会被读成「结构相同」。历史库的基线记录不重写（`ensureBaseline` 已有则复用）。

### 3.4 `continuity_runs` 的「改名」在本轮等于「建表」

## 五、第三批：A-05（项目事务锁）+ P2

### 5.1 冻结签名（逐字实现，一个都没改）

```js
txProject(projectId, fn)          // 单项目；最外层自己开门取锁
txProjects(projectIds, fn)        // 多项目；只能最外层，集合开门前定死
lockedProjects()                  // null | Object.freeze(string[])
assertProjectLocked(projectId)    // 一参、无 options、只读上下文
```

`_lockedProjects` **全仓只有两处赋值**：取锁完成后一次（`Object.freeze(list)`），`finally` 清空一次。中途「再锁一个项目」需要第二次赋值 ⇒ 结构上不可能（D02-34 §2.2）。

### 5.2 两库两套实现（不合并表述）

| 步 | SQLite | PostgreSQL |
|---|---|---|
| 开门 | `BEGIN IMMEDIATE` | `BEGIN` |
| 超时 | `busy_timeout=5000`（连接初始化已设） | `SET LOCAL lock_timeout='5s'` |
| 取锁 | 无项目锁；互斥来自库级写锁 | 逐项 `pg_advisory_xact_lock(hashtextextended(concat('project:', id), 0))`，按 `cmpStr` 升序 |
| 记账作用 | 仅契约记账 | 记账 + 断言唯一依据 |
| 释放 | `COMMIT`/`ROLLBACK` | 随事务释放，进程崩溃不残留 |

### 5.3 嵌套四分支（写死，不解释）

```
txProject(P): 最外层 → open([P])；普通 tx() 内 → TX_MUST_BE_IMMEDIATE；
             项目事务内未持有 → TX_CROSS_PROJECT_NESTED；已持有 → 直接 fn()
txProjects(ids): 已有任何项目事务 → TX_NESTED_MULTI_PROJECT；否则 open(sort(unique(ids)))
```

错误码 7 个 + 既有 `ASYNC_TX`，封闭集未扩：`TX_MUST_BE_IMMEDIATE`、`TX_CROSS_PROJECT_NESTED`、`TX_NESTED_MULTI_PROJECT`、`TX_TOO_MANY_PROJECTS`（>8）、`TX_EMPTY_PROJECT_SET`、`TX_LOCK_SET_CORRUPT`、`TX_PROJECT_NOT_LOCKED`。

| LOCK-12 | 外部事务持锁 1 行 → 回滚后另一连接 386ms 取到 |

### 5.6 P2 判据逐条对照（D02-40 §8.3.2）

| 判据 | 结果 |
|---|---|
| TST-LOCK-01~13 全部通过 | 13/13 通过（SQLite 侧 13 条 + PG 侧 13 条同名用例） |
| 11~13 必须在 PG 真库 | 在 PG 真库执行（LOCK-11 双进程相反顺序、LOCK-12 外部事务持锁后释放、LOCK-13 整组重跑 + `pg_locks` 证据） |

| 不得用 SQLite 结果替代 | SQLite 侧结论明确标注「不验隔离性」；`LOCK-03` 的「不同项目不阻塞」只在 PG 成立 |
| 执行前先过 §8.3.3 六项自检 | 全部通过（见 5.5） |

**如实说明两点**：
1. 本机 PG 是**会话托管进程**（非服务）。本轮每次执行前都重做了六项自检；实例在会话结束后会停止，因此 **P2 的证据绑定「本次执行」，不构成长期通行证**（D02-40 §8.3.3）。
2. 首次启动时因残留 `postmaster.pid` 与 `the database system is starting up` 失败两次（`ECONNREFUSED` / 启动中）。清理残留 pid 并改为「等 `SELECT 1` 成功再跑」后通过；**失败的两次没有产生任何写入**，也没有被计入通过。

### 5.7 唯一一处为可测试性新增的导出（需复核方确认）

`setLockOrderSink(fn)`：D02-34 §4.1 的 TST-LOCK-07 写明「用**注入的 spy** 记录取锁顺序」。没有注入点，这条用例只能靠「事后推断顺序」，等于没验。因此新增了这个**只写不读**的观察者：

- 它不提供「追加锁」能力（那是 D02-34 §2.2 明确禁止的），只报告「正在取哪个项目」；

**这算不算「擅自扩大接口」？** 按冻结契约的字面：§3.1.1 只列了四个符号。所以本报告**主动把它列为待复核项**（§十 10.2），而不是当作已获准。
