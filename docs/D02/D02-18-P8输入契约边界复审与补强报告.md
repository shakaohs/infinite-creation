## 二、R1 输入来源隔离

### 2.1 问题复述（为什么求解器那层做不到）

`assertAnnotationOnly()` 能拦住 `src='carried:…'` 这类明显的结果回搬，但拦不住 **`{rel:'known'}`**：
这个对象**形状与人工裸标注完全相同**。求解器看到的是 `shots[].meta`，它无法知道这条 `rel` 是
"人看了画面标的"还是"从 `shot_states.meta` 里抠出来的"。

> 结论：来源隔离**不可能**在求解器层完成，必须在**组装层**——因为只有组装层知道数据从哪来。

### 2.2 落地方案：把"来源"变成必填参数

新增 `lib/core/continuity/assemble-input.js`（230 行），对外三个函数 + 一个 `global_no` 规范化：

| 导出 | 作用 |
|---|---|
| `ANNOTATION_SOURCES` | 白名单 `['manual', 'adaptation']` |
| `RESULT_SIDE_SOURCES` | 结果侧标签黑名单（`shot_states` / `solver` / `carried` / `state_in` / `state_out` / `qc` / `report` … ） |
| `assertAnnotationSource(source)` | 缺省 → `ANNOTATION_SOURCE_MISSING`；黑名单 → `ANNOTATION_SOURCE_IS_RESULT`；不在白名单 → `ANNOTATION_SOURCE_UNKNOWN` |
| `buildShotAnnotations({shotId, source, entries})` | 构造单镜 `meta`，每条盖上 `src='manual:<source>'` |
| `assembleSolverShots({projectId, sceneKey, rows, annotations})` | 整批组装，末尾调 `assertSolverInput` 作为同一道门 |
| `normalizeGlobalNo(v, shotId)` | 见 §三 |

关键设计（每条都对应一个会被犯的错）：

1. **拒收"一坨 meta"**：接口只接受 `{ shotId: { source, entries } }`。想从结果投影，就必须在
   `source` 里填 `shot_states`，而那一栏会被拒 —— **在字段校验之前**拒（R1 第 2 条要求：
   扣掉 `src` 的部分投影也不能过；若先校验字段，`{rel:'known'}` 会因为"形状合法"而通过）。
2. **`conf` / `ver` / `src` 是结果侧字段**：人工标注只描述可靠性。声称来源是 `manual` 却带
   `conf` → `ANNOTATION_CARRIES_RESULT_FIELDS`。这是"谎报来源"的第二道拦网。
3. **每条断言必须有 `rel`**：只给 `conf` 的输入说明它是从结果里抠的 → `ANNOTATION_REL_REQUIRED`。
4. **组装后统一盖 `manual:<source>`**：于是"裸标注"在进求解器前就不存在了；求解器层的
   `assertAnnotationOnly()` 保留为第二道防线（R1 第 6 条），不重复实现来源判断。
5. **标注挂在不存在的镜上直接抛**（`ANNOTATION_SHOT_NOT_FOUND`）：静默丢弃标注会让求解"正常"
   但少了本该生效的可靠性断言 —— 与 R3 的"不得 filter 丢弃"是同一类错误。
6. **不修改入参**：`global_no` 规范化与 `meta` 注入都写进副本（R1-10 断言 `JSON.stringify` 前后一致）。

### 2.3 三种输入的结论对照（R1 补充测试逐条对应）

| 输入 | 组装层结论 | 理由 |
|---|---|---|
| 完整 `shot_states.meta`，`source='shot_states'` | ❌ `ANNOTATION_SOURCE_IS_RESULT` | 结果回搬 |
| 只抠 `rel`（形状与人工裸标注**完全相同**），`source='shot_states'` | ❌ `ANNOTATION_SOURCE_IS_RESULT` | 判据是来源，不是字段 |
| 只抠 `conf`，`source='shot_states'` | ❌ `ANNOTATION_SOURCE_IS_RESULT` | 同上 |
| 只抠 `conf`，谎报 `source='manual'` | ❌ `ANNOTATION_CARRIES_RESULT_FIELDS` | 人工没有置信度可给 |
| 空壳 `{}`，`source='manual'` | ❌ `ANNOTATION_REL_REQUIRED` | 标注必须交代可靠性 |
| 人工裸标注 `{rel:'unknown'}`，`source='manual'` | ✅ 组装为 `{rel:'unknown', src:'manual:manual'}` | 正路 |
| `src='manual:sh_41_panel'` 直投求解器 | ✅ 接受（第二道防线不误伤） | 正路 |

### 2.4 这套隔离的**边界**（必须写清，不许含糊）

它拦得住"从结果投影"（因为投影方必须自报 `shot_states`），拦不住"手抄一份 `rel` 却谎报 `manual`"。
后者无解 —— 除非给 `meta` 加 `origin` 位，那要 DDL（本轮禁止）。记为 **U-P8-3（C）**，与 D02-17 的
同号条目合并，不再单独升级。

## 三、R2 `global_no` 排序契约

### 3.1 规范与 DDL 核对

| 依据 | 内容 | 推论 |
|---|---|---|
| `lib/core/schema/tables.js:94` | `global_no INTEGER NOT NULL` | `INTEGER` → 不接受小数；`NOT NULL` → 不接受空值 |
| `tables.js:385` | `CREATE UNIQUE INDEX uq_ss_gn ON story_shots(project_id, global_no)` | 真实库里**不可能**有重复号；出现重复只说明调用方传的是拼接出来的临时集 |
| D01-04 §5.5 / D02-06 ORD-1 | 权威序 = `global_no` 升序（不是 `shot_no`、不是 `created_at`、不是 `prev_shot_id`） | 排序失真的后果是整条继承链错位 |

### 3.2 最终契约（求解器层）

| 输入 | 结论 | `reason` | 理由 |
|---|---|---|---|
| `1` / `99`（number，正整数） | ✅ | — | 契约形态 |
| `0` / `-3` | ❌ | `SHOT_GLOBAL_NO_INVALID` | 权威序从 1 起；0 正是"缺失"的兜底值 |
| `1.5` | ❌ | `SHOT_GLOBAL_NO_INVALID` | 小数让"第几镜"失去定义，`sort` 退化为浮点比较 |
| `null` / `undefined`（缺失） | ❌ | `SHOT_GLOBAL_NO_INVALID` | 会被 `?? 0` 静默排到最前 |
| `'3'` / `'abc'` / `true` / `{}` | ❌ | `SHOT_GLOBAL_NO_NOT_NUMBER` | 类型契约统一为 `number` |
| 同批次重复 | ❌ | `SHOT_GLOBAL_NO_DUPLICATED` | 重复号的先后由 `cmpStr(id)` 兜底 = 让"第几镜"由 id 决定 |

**数字字符串的归属**：只在组装层接受一次（`normalizeGlobalNo`），且只认 `number` 或无前导零的
十进制串（`'3'` ✅ / `'03'` `' 3'` `'3.0'` ❌）。两边各让一步的后果是"没人说得清哪层负责"。

### 3.3 行为变化（仅限非法输入）

- 之前：`Number(s.global_no)` 宽松转换，`'3'` 能过、`1.5` 能过；
- 现在：严格拒绝，`reason` 分三档；合法正整数输入的行为**完全不变**（R2-3 断言乱序传入
  与升序传入得到同一 `hash` 与同一 `states`，且 `b` 的 `src` 仍是 `carried:a`）。

## 四、R3 `shots` 元素校验

| 元素 | 之前 | 现在 |
|---|---|---|
| `null` | 被 `filter` **静默丢弃**，剩下几镜照样求解成功 | `SHOT_INPUT_INVALID`（带 `index` 与实参类型） |
| `'sh_02'` / `42` / `true` | 同上（`typeof 'x' === 'string'` 被丢） | `SHOT_INPUT_INVALID` |
| `['sh_02']` | **`typeof [] === 'object'` → 被当成镜头行继续跑** | `SHOT_INPUT_INVALID` |
| `{}` | 能进来（无 `id`） | `SHOT_ID_MISSING` |
| 合法对象 | 正常 | 正常（`hash` / `states` 两次求解逐字段相同） |
| `[]`（空数组） | 空结果 | 空结果（`states={}`、`sceneConflicts=[]`、`hash` 合法） |

同时删除了 `solve-continuity.js` 里那句 `.filter((s) => s && typeof s === 'object')`：
校验已经保证每个元素都是普通对象，留着它就是留一条"将来有人绕过校验就悄悄丢元素"的路。
`describeValue()` 让报错能区分 `null` / `array(2)` / `string "sh_02"`（`typeof null === 'object'` 这类坑
不留给读错误信息的人）。

**为什么"静默丢弃"比"整批拒绝"危险**：少一镜时求解器照样跑通、报告照样生成，
只是下游继承链从那一镜起全部错位 —— 而 **Hash 也会跟着变**，读侧会判"未过期"。

## 五、R4 `unknown` 继承语义确认

### 5.1 规范核对结论（D01-04 §5.4 / §5.7）

| 情形 | 规范怎么写的 | 是否有定义 |
|---|---|---|
| 本镜**未给值**（missing / 显式 `null`） | §5.7 Step 2/3：只报 `STATE_UNKNOWN`(INFO)，`state_out` **沿用**且 `rel` **保持 `known`**、`src='carried:<起点>'` | ✅ **已定义**，实现与之一致（R4-1：`b` → `known/carried:a/0.855`，`c` → `known/carried:a/0.77`） |
| 本镜**给了值但显式标 `unknown`** | §5.2.1 矩阵第 10 条："有值也不采信"；§5.7 Step 4 只说"值不予采信"并给 `STATE_UNKNOWN`，**预期输出里没给 `sh_43` 的 `state_out` / `meta`** | ❌ **未定义**（只定义了"本镜不采信"，没定义"这条 unknown 是否随 `state_out` 传给下一镜"） |

### 5.2 现状（本轮锁定，不改语义）

`inheritRows()`（`b`/`c` 都不给坐标，只能继承）实测：

| 情形 | `b.meta['chars.c1.pos']` | `c.meta['chars.c1.pos']` |
|---|---|---|
| 无标注 | `{rel:known, src:carried:a, conf:0.855}` | `{rel:known, src:carried:a, conf:0.77}` |
| `b` 显式 `rel='unknown'` | `{rel:unknown, src:carried:a, conf:0.855}` | `{rel:unknown, src:carried:a, conf:0.77}` |

即：**显式 `unknown` 只否决本镜的"差"，但会作为 `rel` 沿链继续传播**；值仍然沿用（`pos` 不变），
变的是下游的可靠性口径（`c` 从"按 known 计"变成"按 unknown 计"，影响 `verifiable_ratio` 分母）。

两轮求解完全一致 → 这是**语义分歧**，不是抖动，因此不能"顺手修掉"。

### 5.3 处置

- **不改代码**（R4 第 5 条：不得为通过测试而改业务语义；且改这段属"重构求解器"，本轮禁止）；
- 记为 **U-P8-2（B 级，待定案）**，已附两种读法的取舍：① 不传播（`state_out.rel` 回落到 `known`,
  与 missing 情形一致，理由：值来自 `a` 的可信观测，本镜只是"没验"，不是"不可信"）；
  ② 传播（现状，理由：`unknown` 是人对该值的否决，沿链带走这条否决）。**需 D01-04 §5.4/5.7 明确定案。**
- 顺带记录 **U-P8-4（C）**：`manual:` 前缀**不会留在 `state_out.meta`** —— 值被采信时 `src` 被改写为
  `blocking:<id>`，不被采信时改写为 `carried:<起点>`。即"这条 `rel` 是人标的"在求解结果里不可追溯。
  不影响判定，只影响事后审计（R1-6 第 ③ 条已作为事实断言）。

## 九、P8 应该怎么用（交接契约）

```js
import { assembleSolverShots } from './lib/core/continuity/assemble-input.js';
import { solveContinuity } from './lib/core/continuity/solve-continuity.js';

// rows：story_shots 行 + 复合的 blockings / actions / shotAssets
// annotations：只来自**人工/适配层**，不得来自 shot_states.meta
const { shots } = assembleSolverShots({
  projectId, sceneKey,
  rows,
  annotations: {
    sh_41: { source: 'manual', entries: { 'chars.c1.pos': { rel: 'unknown' } } },
  },
});
const { states, sceneConflicts, hash } = solveContinuity({ projectId, sceneKey, shots, sceneState });
```

四条硬约束（P8 接线时的自检项）：

1. `annotations` 的 `source` 只能是 `manual` / `adaptation`；**不得**把 `shot_states.meta` 直接或投影后传入。
2. `rows[].global_no` 可以是数字串（组装层会规范化），但**不得**缺失、不得重复、不得为 0/负数/小数。
3. `rows` 里混入 `null` / 数组 / 字符串会整批失败 —— 不要用 `filter` 包装它（那会退化成本轮修掉的缺陷）。
4. `solveContinuity` 不按 `scene_key` 过滤，必须一场一批；`assembleSolverShots` 会先拦。
