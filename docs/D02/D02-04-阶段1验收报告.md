## 〇·1 V1.1 定向修复（A-01 / B-01 / B-02）

三项都由独立审核提出，全部是"实现与声明不一致"的问题——**文档写了、代码没做到**。本轮只改这三处。

### A-01 回滚脚本没有数据库隔离（严重）

| 项 | V1（问题） | V1.1（修复） |
|---|---|---|
| 打开方式 | `new DatabaseSync(dbPath)` —— **给个路径就能 DROP 21 张表** | 打开前依次执行 `assertEnv()` → `--db` 绝对路径校验 → `assertDbIsolation()`（真实路径逐段 `lstat`/`readlink`）→ 真实路径不得落在 `<repo>/data` |
| 判定方式 | 只看 manifest 有 21 个名字 | 正向白名单：表名集合必须与冻结模块 `STAGE1_TABLES` **完全一致**（少一张 / 多一张 / 换一张 / 分组错位 / 重复 / manifest 结构异常 → 全部拒绝） |
| 干跑 | 可写连接上什么都不做（"靠自觉"） | **只读连接**（`readOnly: true`），SQLite 层面就写不进去 |
| 拒绝对时机 | — | 全部在 `new DatabaseSync()` **之前**；用例 R-03 用"被拒后文件仍不存在"证明没打开过 |

8 条用例（`tests/stage1-rollback.test.mjs`，8/8 绿）：无 `IC_DATA_DIR` / 相对 `IC_DATA_DIR` / 库在隔离外 / 目录链接逃逸 / `--execute` 指向真实库（真实库 SHA 不变）/ manifest 换未知表 / 合法干跑 / 合法真回滚。

### B-01 Task 与 Job 的同项目校验有绕过分支（较严重）

V1 的写法是"`task.project_id` 有值就用它，没有才查 unit"，并且比较时对空值短路：

```js
let projOfTask = String(task.project_id || '');
if (!projOfTask && task.unit_id) { /* 查 unit */ }
if (projOfTask && String(job.project_id || '') && projOfTask !== String(job.project_id)) throw ...
```

两条绕过路径：① `task.project_id` 有值 → **整条 unit 校验被跳过**（unit 指向别的项目、unit 不存在都查不出）；② `job.project_id` 为空 → 比较被短路，跨项目也能写进去。

V1.1 改为**归属唯一来源 = `render_tasks.unit_id → render_units.project_id`**，七项逐项校验、四个错误码：

| # | 校验 | 失败码 |
|---|---|---|
| 1 | Job 存在 | `JOB_OR_TASK_NOT_FOUND` |
| 2 | Task 存在 | `JOB_OR_TASK_NOT_FOUND` |
| 3 | `task.unit_id` 能查到真实 `render_units` 行 | `TASK_UNIT_NOT_FOUND` |
| 4 | `unit.project_id` 非空 | `TASK_PROJECT_MISMATCH` |
| 5 | `job.project_id` 非空 | `JOB_PROJECT_MISMATCH` |
| 6 | `job.project_id === unit.project_id` | `JOB_PROJECT_MISMATCH` |
| 7 | `task.project_id`（若非空）`=== unit.project_id` | `TASK_PROJECT_MISMATCH` |

10 条用例（并入 `tests/stage1-relations.test.mjs`，J-01~J-09 + J-03b）：正常绑定、跨项目、绕过路径 1、绕过路径 2、unit 不存在、unit 项目为空、job 项目为空、幂等重绑、改绑拒绝、双方不存在。**不为了兼容不完整数据而静默放行。**

### B-02 基线批次只有模型、没有接线（中等）

`ensureBaseline()` 早就写好了，但没有任何调用点 —— 全新库初始化后库里**一条批次记录都没有**，`migration_batches` 形同未启用。

V1.1 在 `initSchema()` 末尾（21 表 + 索引之后）调用它：

| 规则 | 实现 |
|---|---|
| 时机 | 结构与索引成功之后；建表失败时抛错，**不写"成功基线"**（B-05 用"第 5 张表建表失败"验证：`migration_batches` 0 行） |
| ID | `mig-YYYYMMDD-00`（当天日期 + `00`） |
| 状态 | `name='schema-init'`、`status='committed'`、`script_ver='stage1-ddl/d02-04.1'` |
| 幂等 | **只要库里已有任何一条 `schema-init` 就复用**（不是按天新建——否则"每天开一次应用多一条基线"）；B-02 用 3 次 `initSchema` + 一次跨日 `ensureBaseline` 验证仍为 1 行 |
| 不覆盖 | 只 `INSERT`；`-00` 被非基线批次占用时抛 `MIG_BASELINE_ID_TAKEN`（B-04） |

6 条用例（并入 `tests/stage1-schema.test.mjs`，B-01~B-05）。**未改动** `blocking` / `structured_spec` 的补列逻辑（它们在同函数更早的位置，且各自有既有测试）。

## 一、实施摘要

本阶段做完六件事，全部围绕"进入阶段 2 之前必须具备的结构能力"：

1. **21 张新表 + 25 个索引**：3 ops + 1 archive + 14 biz + 3 d02_ext，按 D02-03 V3 §11.1 的顺序建，全部 `IF NOT EXISTS`，表齐后统一建索引。

3. **Manifest 生成器 + 校验器**：从冻结 DDL 文本解析（不读数据库反推），支持 `fresh` / `historical` 两个 profile。

5. **迁移登记模型**：三张运维表的状态机与数据访问，四终态无出边、指纹写后不可改、依赖读取 LEFT JOIN。

## 六、Hash 49 条测试结果

**口径说明**：D01-06 §4.6 的表格是 R-01~R-38 + R-40~R-49（48 条），R-39 被明确写成"负向，代码评审项"。本轮把 R-39 也写成可执行断言（payload 里不得出现 `track` / `fragments` / 下划线键），凑足 **49 条**。

| 结果 | 数量 | 说明 |
|---|---:|---|
| 通过 | **43** | R-01~R-35、R-38、R-39~R-44、R-46 |
| 显式 skip | **6** | R-36、R-37、R-45、R-47、R-48、R-49 |
| 合计 | **49** | 另有 2 条额外用例（`canonicalStringify` 十种顺序、`cmpStr` 三语言），共 51 个 test |

**6 条 skip 的共同原因**（不是"没写"，是"本阶段没有被测对象"）：它们验证 `pickLegalCut` / `assertAttribution` / `planAdaptation` / 切点量化边界，属 **阶段 4 适配层**。任务书 §九 明确"不得在阶段 1 提前实现 Seedance/H3 适配算法"。skip 在测试输出里显式可见，不计入通过。

**关键通过项**：
- R-25 同源证明：同一分镜两套 track → `sourceSpecHash` 逐字相同、`adaptationHash` 与 `compiledHash` 均不同
- R-26 五项全序：动作按正序/逆序/随机输入 → source 不变
- R-32/R-33 引用映射：被引用的动作换 id 并同步更新引用 → source 不变；只改引用目标内容 → 变
- R-42 跨 locale：`LANG=en_US / tr_TR / sv_SE` 三种环境起独立进程跑同一 fixture → 逐字相同
- R-44 `posRel` 13 行矩阵逐行核对，含 `not_applicable` 先于缺失检查、显式 `known` 不能翻案、`legacy` 一律 unknown
- R-46 静态检查：`lib/core/hash/` 内 `localeCompare` 零命中、无裸 `stripRef(` 调用（先剥注释再检查，避免把说明文字判成违规）

**一个必须写明的边界**：`canonState` 只做"undefined→null + 递归规范化"，**不补齐 D01-02 的完整字段表**——那需要一张阶段 1 未引入的字段清单。所以"缺字段补 null"只对输入里出现的键生效。这一点登记为 R-12（C 级）。

**四处改造的落点**（对应 V3 §五 S8）：

| # | 改造点 | 改法 |
|---|---|---|
| 1 | `ENTITY_TABLE` → `ENTITY_META` | 从 `{entity: 表名}` 升级为 `{table, pk, projectOf}`；`ENTITY_TABLE` 保留为派生视图，老代码仍可用 |

**新增实体只加一项**：`render_selection`。`migration_batches` / `migration_items` / `migration_edges` / `adaptation_locks` / `render_task_jobs` **均不进** changelog（前者是运维审计、后者不可变或与 task 同生共死）。

**一个改动带来的行为差异（必须记住）**：`recordChange` 对 `render_selection` 在归属解析失败时**抛错**而不是 `return null`。这是故意的——静默丢审计比报错危险得多。
