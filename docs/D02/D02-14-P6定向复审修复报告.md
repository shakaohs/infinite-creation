## 三、P6-R1：求解输入 Hash 覆盖 `shot.meta`

### 3.1 修复前行为（缺口）

`solveContinuity()` 在 Step 1 之后读取 `shot.meta`，把它作为"本镜自带的可靠性标注"合并进 `metaIn`：

```js
const seed = obj(shot.meta);           // ← 影响 posRel / originOf / conf 衰减
for (const k of Object.keys(seed)) metaIn[k] = { ...(metaIn[k] ?? {}), ...seed[k] };
```

而 `solverInputHash()` 只覆盖 `SOLVE_SHOT_FIELDS` + 站位行 + 动作行 + 资产引用，**没有 `meta`**。后果：

| 场景 | 修复前 |
|---|---|
| 同一镜加 `{ 'chars.c1.pos': { rel: 'unknown' } }` | `sh_43` 的 `pos` 从"采信坐标"变"降级沿用"，`state_out` / `meta` 都变 —— **Hash 一字不变** |
| 读侧按 Hash 判"状态是否过期" | 判"没过期"，于是把旧状态当当前结论（正是 §7.8.4 F-2 要防的那件事） |

### 3.2 修复后行为

```js
// solve-hash.js
export const SOLVE_META_FIELDS = Object.freeze(['rel', 'src', 'conf']);
export function normalizeShotMeta(meta) → 键按 cmpStr 排序、每项只留三样、__solver 剔除、全空条目整条剔除
// payload
shots: [{ ...pick(shot, SOLVE_SHOT_FIELDS), meta: normalizeShotMeta(shot.meta), ... }]
```

三处设计决定：

| 决定 | 理由 |
|---|---|
| 只留 `rel` / `src` / `conf` | 求解器只读这三样：`posRel()` 读 `rel`、`originOf()` 读 `src`、继承衰减读 `conf`。多纳一个不参与计算的键 = 假失效 |
| `ver` 不进 Hash | Step 1 会用本镜 `spec_version` 无条件覆写它，它不是输入（且 `spec_version` 已在 Hash 内） |
| 全空条目整条剔除 | `{ 'chars.c1.pos': { ver: 7 } }` 对求解器没有任何信息量；若不剔除，"多挂一个空条目"也会被算成输入变化 |
| `__solver` 剔除 | 它是求解器的**输出**，纳入会自引用（改一次变一次，永远对不上） |

**同源保证**：`solveContinuity` 也改用 `normalizeShotMeta()`（不再用裸 `obj()`）。两处各写一套归一化，迟早分叉，而"Hash 覆盖了什么"就只能靠人眼比对 —— 这正是 R1 的成因。

### 3.3 一个必须同时修的子问题

`normalizeShotMeta` 会把缺省项填成 `null`。若按 `{ ...base, ...seed }` 展开合并，`conf: null` 会把继承来的置信度抹成 0（`Number(null) === 0`，且 `Number.isFinite(0)` 为真），于是**每次继承都丢失置信度**。改为只覆盖非空字段：

```js
for (const k of Object.keys(seed)) {
  const one = { ...(metaIn[k] ?? {}) };
  for (const f of SOLVE_META_FIELDS) if (seed[k][f] !== null && seed[k][f] !== undefined) one[f] = seed[k][f];
  metaIn[k] = one;
}
```

测试 `R1-8` 正向断言：只标 `pos.rel` 时，`posture` 的继承置信度仍是 `0.855`（`0.95 × 0.9`）、`src` 仍是 `carried:a`。

### 3.4 测试（8 条，全过）

| 编号 | 断言 | 结果 |
|---|---|---|
| R1-1 | 相同输入两次 → Hash 相同（`sha256:` + 64 hex） | 通过 |
| R1-2 | 改 `rel` / `src` / `conf` 任一 → Hash 必变 | 通过 |
| R1-3 | 显式 `unknown` 改变求解结果 → **结果不同且 Hash 不同** | 通过 |
| R1-4 | `__solver` 变化 → Hash 不变（两组不同 solver 值） | 通过 |
| R1-5 | 只有 `ver` / 全空条目 → 等于"没有 meta" | 通过 |
| R1-6 | 与求解器共用同一份归一化（`SOLVE_META_FIELDS` = `['rel','src','conf']`，键排序、`__solver` 剔除、非对象入参容错） | 通过 |
| R1-7 | 元数据键序不影响 Hash | 通过 |
| R1-8 | 空字段不抹掉继承来的 `conf` | 通过 |

## 五、P6-R3：资产失效 fail-closed

### 5.1 修复前行为

```js
const refs = toArr(shotAssets).filter((r) => str(r.asset_id) === assetId)...;
```

`shotAssets` 未传 → `toArr(undefined)` → `[]` → `refs` 为空 → 不产生任何 CIS/QIS → 返回 `bothEmpty: true`。

调用方读到的语义是 **"没有东西需要重算"**，真相是 **"我们不知道该重算什么"**。这两件事在返回值上长得完全一样，而后果是实的：`assets.category` 从 `prop` 改成 `costume` 后，`COSTUME_JUMP` / `AS-8` 的结论会变，但没有一个镜被重跑。

### 5.2 修复后行为

```js
if (toArr(ch.assets).length) {
  if (!Array.isArray(shotAssets)) throw err('INVALIDATION_ASSETS_CONTEXT_MISSING', ...);
  const badRefs = shotAssets.filter(r => r.shot_id && !idx.byId.has(str(r.shot_id))).map(r => str(r.shot_id));
  if (badRefs.length) throw err('INVALIDATION_ASSET_REF_UNKNOWN', ..., { shot_ids: [...] });
}
```

两个错误码，两种缺陷：

| 码 | 触发 | 含义 |
|---|---|---|
| `INVALIDATION_ASSETS_CONTEXT_MISSING` | `change.assets` 非空但 `shotAssets` 不是数组（`undefined` / `null` / 字符串 / 对象） | 调用方漏传上下文 |
| `INVALIDATION_ASSET_REF_UNKNOWN` | `shotAssets` 引用了快照里不存在的镜 | 引用关系与镜头快照不一致 |

**为什么不"保守地全项目失效"**：那会让改一个资产的名称导致整个项目重算，比报错更糟 —— 报错至少能被发现，而全量重算会被当成"正常现象"。这里选 fail-closed：让写入口这次失败。

**边界**：fail-closed 只针对"资产变更"。`change.assets` 为空时，不传 `shotAssets` 完全合法（测试 `R3-6` 正向断言不得误抛）。

### 5.3 测试（6 条，全过）

| 编号 | 断言 | 结果 |
|---|---|---|
| R3-1 | 4 种非法 `shotAssets` 各自抛 `INVALIDATION_ASSETS_CONTEXT_MISSING` | 通过 |
| R3-2 | 引用不存在的镜 → 抛 `INVALIDATION_ASSET_REF_UNKNOWN` 且 `e.shot_ids` 含该 id | 通过 |

## 六、P6-R4：`A-06` 邻镜状态 Hash 上下文

### 6.1 修复前行为（两处缺口）

**缺口一：键名不通。** 依赖映射声明 `nextShotState.state_in`，`buildQcDependencyContext()` 却只产出 `ctx.nextShot`，而 P5 的 `checkActionContinuity` 读的是 **`ctx.nextShotState`**：

```js
// lib/core/validate/action.js:375
const nextState = ctx.nextShotState && typeof ctx.nextShotState === 'object' ? ctx.nextShotState : null;
```

于是"规则读的那一行"与"Hash 投影的那一行"根本不是同一个键。只要调用方只填了一个，另一侧恒为 `null` → A-06 的规则级 Hash 恒定不变 → 下镜状态怎么改都能"合法继承"。

**缺口二：没有形状校验。** 调用方手上通常同时有"下一镜的 `story_shots` 行"和"下一镜的 `shot_states` 行"，两者都带 `id`。错传前者时，投影出的 `state_in` 永远是 `null`，且**不报错** —— 与"末镜哨兵"算出同一个值，哨兵随之失去意义。

### 6.2 修复后行为

| 项 | 内容 |
|---|---|
| 契约 | `nextShot` / `nextShotState` 是**同一行状态的两个键名**；接受含 `state_in` / `state_out` / `conflicts` 任一的对象；`null` 表示末镜 |
| 同源 | 构建器把两个键指向**同一个对象**；`readScalar` / `rowsOf` 取 `nextShotState ?? nextShot`（任一填了都可用） |
| 校验 | 非对象 → `QC_DEPS_NEXT_SHOT_INVALID`；对象但三键皆无 → `QC_DEPS_NEXT_SHOT_NOT_STATE`（错误信息带收到的键名） |
| 哨兵 | 末镜写 `__last__`（`LAST_SHOT`），与非末镜必算出不同 Hash |

### 6.3 测试（6 条，全过）

| 编号 | 断言 | 结果 |
|---|---|---|
| R4-1 | 下镜 `state_in` 变 → A-06 Hash 变；下镜 `id` 变 → **不变**（映射只声明 `state_in`） | 通过 |
| R4-2 | 末镜 `__last__` 与非末镜不同；且 `nextShot: { state_in: null }` 与 `nextShot: null` 也不同（哨兵真进了投影） | 通过 |
| R4-3 | 传 `story_shots` 行 → `QC_DEPS_NEXT_SHOT_NOT_STATE`；传字符串/数字/数组 → `QC_DEPS_NEXT_SHOT_INVALID` | 通过 |
| R4-4 | 5 种合法状态行形状（含 `state_in: null`）都接受 | 通过 |
| R4-5 | A-06 Hash 不含下镜的创作列（`shot_size`/`cam_pos` 变 → 不变） | 通过 |
| R4-6 | 两个键指向同一对象；只填其中一个键结果等价 | 通过 |

## 附录 B · 四个缺口的共同教训

| 缺口 | 表面症状 | 真正的判据 |
|---|---|---|
| R1 漏入参 | 测试全绿、Hash 稳定 | **"改一个会影响结果的输入，Hash 必须变"** —— 只能靠构造"结果已知会变"的对照输入才测得出来 |
| R2 投影过宽 | 测试全绿、Hash 稳定 | **"改一个规则不读的字段，Hash 不得变"** —— 只能靠逐字段敏感度矩阵 |
| R3 缺上下文 | 返回值"看起来正常"（空集合） | **"空集合"必须能与"无法计算"区分** |
| R4 键名不通 | 两端各自都对，合起来错 | **"规则读的对象"与"Hash 投影的对象"必须是同一个引用** |

四条的共同点：**都不能靠"有没有报错"发现，只能靠"两种输入是否得到不同结果"发现**。所以本轮 32 条测试里，绝大多数是成对断言（A 变 / B 不变），而不是单点断言。
