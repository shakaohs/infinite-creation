## 一、R2-1 状态快照 Hash 不得回退

### 1.1 缺陷

`lib/core/continuity/run-scene.js` 原第 135 行：

```js
stateSnapshotHash: stateSnapshotHashOf(shotState) || solved.hash,
```

这一行 `||` 有两层危害，而且是叠加的：

| # | 后果 | 为什么严重 |
|---|---|---|
| 1 | 缺快照时不报错，拿 `qc_input_hash`（B）顶替 A | `hashRelationOf()` 里"缺 A 就抛 `QC_REPORT_INVALID`"的保护**永远不会触发**，等于没有 |
| 2 | A 恒等于 B ⇒ `hash_relation` 恒为 `same` | "这行状态不知道是哪版输入算出来的"——最该被看见的缺陷——被伪装成最健康的状态 |

### 1.2 修复（`run-scene.js` 251 行）

新增 `stateSnapshotOf(stateRow, shotId)`（:68），替换全部回退逻辑，调用点在 :190：

```js
// stateSnapshotHash: stateSnapshotOf(shotState, shotId)
function stateSnapshotOf(stateRow, shotId) {
  if (!stateRow) throw qcReportError(... STATE_SNAPSHOT_ROW_MISSING);
  if (typeof stateRow.meta === 'string') {
    try { JSON.parse(stateRow.meta || '{}'); }
    catch (e) { throw qcReportError(... STATE_SNAPSHOT_META_UNPARSEABLE); }
  }
  const h = stateSnapshotHashOf(stateRow);
  if (!h) throw qcReportError(... STATE_SNAPSHOT_HASH_MISSING);
  return h;
}
```

| 要求 | 实现 |
|---|---|
| 删除回退逻辑 | 已删除，`stateSnapshotHashOf(shotState) || solved.hash` 在代码与注释中都不再出现 |
| 必须来自本轮实际读取的 `meta.__solver.hash` | 值只从 `persistSceneStates()` 返回的 `rows`（**库里实际那一行**）取，不是"本来打算写的那一行" |
| 缺失 / 空值 / 无法解析 → `QC_REPORT_INVALID` | 三个分支共用 `qcReportError()`（:51，`code='QC_REPORT_INVALID'`），各带 `reason`：`STATE_SNAPSHOT_ROW_MISSING` / `STATE_SNAPSHOT_META_UNPARSEABLE` / `STATE_SNAPSHOT_HASH_MISSING` |
| 不得以 `qc_input_hash` 补位 | 抛错路径里没有任何 `solved.hash` 引用；同一事务内抛出 ⇒ 状态与报告整体回滚 |
| 不改 `hashRelationOf()` 语义 | `qc/report.js:80` 逐字未动 |
| 不改 `solve-hash.js` / 求解器 Hash 范围 | 未触碰 |

## 二、R2-2 最新报告查询统一遵守正式排序

### 2.1 缺陷

三处查询都写的是 `ORDER BY created_at DESC, rowid DESC`。`rowid` 是**物理插入序**，与"逻辑上的后写"没有任何契约关系：`ON CONFLICT`、迁移、`VACUUM` 都能让两者脱钩。而 §18.11 的正式排序是 `created_at DESC, id DESC`，且明确要求"`id` 用 `cmpStr` 序、不依赖数据库返回顺序"。

### 2.2 修复（`qc/report.js` 413 行）

| 位置 | 改动 |
|---|---|
| `:394` 新增 `const ORDER_LATEST = 'ORDER BY created_at DESC, id DESC'` | 三处共用同一段 SQL 片段，避免"改了一处忘了另一处" |
| `saveReport()` :356~:362 | 排序改为 `ORDER_LATEST`；`SELECT` 多取 `ruleset_ver` |
| `latestReport()` :397~:400 | 同一排序，`LIMIT 1` |
| `reportHistory()` :404~:407 | 同一排序（新 → 旧） |
| `:365~:366` 复用判据 | 增加 `sameRuleset`：`ruleset_ver` 不同 ⇒ 不允许当作"同一份结论的旧输入"复用 |

三条口径：

1. **`id` 与 `cmpStr` 同序**：`id` 是 `uid()`（`crypto.randomUUID()`）生成的小写十六进制 + `-`，纯 ASCII；SQLite 的 BINARY collation 逐字节比较与 `cmpStr` 的逐 code unit 比较在 ASCII 上同序。这一点写进了代码注释，因为它是"用 `id DESC` 就等于 `cmpStr` 序"的前提。
2. **不做 `ruleset_ver` 预过滤、不回退**：候选查询只有 `target_type` + `target_id`（+ `project_id` 作用域），读到候选后由版本校验决定能否继承（`carriedCandidates()` 在 `ruleset_ver` 不一致时返回空 Map ⇒ 全量实跑）。绝不"最新那份过期了，就往前找一份没过的"。
3. **`sameRuleset` 是复用侧的补强**：输入 Hash 与依赖 Hash 都相等、但规则集版本不同，说明这是**另一套规则**算出来的东西，不是"同一份结论的旧输入"。不加这一条，规则升级后第一次运行会直接"复用"旧版本报告，并把 `latestReport()` 停在旧版本上。

### 2.3 新增测试（T1~T4）

| 用例 | 构造 | 断言 |
|---|---|---|
| T1 | 同一 `created_at`、`id` 为 `aaa-decoy` / `zzz-decoy` 两份 | `latestReport().id==='zzz-decoy'`；`reportHistory()` 前三为 `zzz / aaa / 基线` |
| T2 | 同刻两份：`aaa-match`（输入依赖 Hash 与本轮**完全一致**）、`zzz-other`（不一致） | 本轮 `reused=false`、`report_id!=='aaa-match'`、`carried_from==='zzz-other'`——即 `saveReport` 认定的"上一份"与 `latestReport` 是同一行 |
| T3 | 同一 `updatedAt` 连跑两次 | 第二次 `reused=true`、报告 id 相同、库里仍 1 行 |
| T4 | 插入一份 `created_at` 更新、`ruleset_ver='d01-v7/stage3.0'` 的报告（内容与当前一致） | ①`latestReport()` 选中它（不预过滤、不回退到更旧的当前版本）；②带 `plan` 重跑时 `carried` 数为 0；③不复用旧版本报告，新报告 `ruleset_ver` 回到 `d01-v7/stage3.1` |

T2 是这组里最有价值的一条：它同时钉住了"排序一致"与"复用判据"，而 T1 只钉住排序。若哪天有人只改一处 SQL，T2 会红（`carried_from` 立刻变成别的 id）。

另：`tests/stage3-p9-report.test.mjs` 的测试侧取行 SQL 也从 `rowid ASC` 改为 `id ASC`——测试若按物理插入序、实现按 `id DESC`，同一毫秒两份报告时两边会给出两种顺序，红得莫名其妙。
