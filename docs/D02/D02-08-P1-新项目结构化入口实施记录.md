## 二、默认值为什么落在服务层，不落 `Projects.create`

`Projects.create` 是低层原语，`tests/*.test.mjs` 的既有用例、全部测试夹具、阶段 0/1 脚本都直接调它。在那里把默认值翻成 1，会让既有用例整体落到结构化分支，把「17 条旧链路失败」这条回归标尺污染掉——而那是判断"有没有新增回归"的唯一依据。

```js
// lib/core/project-create.js（语义摘要）
export function createUserProject({ structured_spec = true, ...rest } = {}) {
  if (typeof structured_spec !== 'boolean') throw BAD_FLAG_VALUE;   // "1" / 1 / null 一律拒绝
  return Projects.create({ ...rest, structured_spec: structured_spec ? 1 : 0 });
}
```

三层默认值一览：

| 调用方 | 入口 | 默认值 |
|---|---|---|
| 用户建项目（2 个 API） | `createUserProject()` | **1（开）** |
| 测试夹具 / 迁移 / 阶段脚本 | `Projects.create()` | **0（旧链路）** |
| 灰度回退 / 用例造数 | `createUserProject({ structured_spec: false })` | 0（显式） |

**为什么非布尔要抛错**：把 `"1"` / `1` / `"true"` 静默当成"开"，会让本该走旧链路的项目悄悄进新分支，且日志里没有任何痕迹。宁可当场 400。

## 三、读取判断的统一口径

- 判定**只能**走 `isStructuredSpec(projectId)`（`lib/core/structured-spec.js` 是 `projects.structured_spec` 的唯一读写边界）。
- `Projects.get()/list()` 返回的是 `toProject()` 结果，其中 `structured_spec` 是 **0/1 数字**。O-01 里直接钉了这条：`typeof === 'number'`、`=== true` 为 false、`=== 1` 为 true。
- 本轮盘点：改动前 `app/` 内**零处**读写 `structured_spec`；改动后仍为零（默认值不落字面量），静态检查 `P-3` 守住这一点。
