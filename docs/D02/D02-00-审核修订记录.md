## 三、R-03 历史数据回滚方案

### 修订前

```markdown
| 2-1 | `story_shots` 落库（66 段 → N 镜） | `DELETE FROM story_shots` |
| 2-2 | `shot_assets` 回填（6 个 JSON 列 → N 行） | 同上 |
| 2-3 | `shot_blockings` 回填（13 段文本 → 逐人，坐标 NULL） | 同上 |
| 2-4 | `render_adaptations` 回填（5 个项目 `beats` → 方案） | 同上 |
```

### 问题

`DELETE FROM <新表>` 同时违反三条：

1. 删的是**整张表**，包括迁移之后新业务写进去的行；
2. 无法回答"这次迁移到底写了哪些行"，也就无法判断"删得对不对"；
3. 若新链路已在引用这些行，删表造成悬空引用与前端白屏。

根因是**现有工程没有"迁移批次"这个概念**：

| 检查 | 结果 |
|---|---|
| `grep -rn "migration_batch" lib app` | **空** |
| `change_logs.batch_id` | 存在（`db.js:236`、索引 `idx_change_logs_batch`），但语义是**一次内容编辑批次**（`changelog.js:90` 由 `batch()` 生成），**不覆盖批量迁移** |
| `data/backups/` | 不存在 |
| `/api/projects/[id]/backups` | 是**成片导出备份**，与数据库无关 |

→ 所以"回滚"这件事在现有工程里**没有实施载体**，不是改一句 SQL 的问题。

### 修订后

阶段 2 整节重写，四层：

**(1) 迁移登记结构（2.0，属 C13）**——6 个字段：`migration_batch_id` / `migration_source` / `entity_table`+`entity_pk` / `checksum` / `state` / 时间戳。只写要求，本轮不建表。

**(2) 五条硬规则（2.1）**：

| # | 规则 |
|---|---|
| R1 | 回滚只删 `WHERE migration_batch_id = ?` 的行 |
| R2 | 已被新业务引用的行不得删（引用方来源标记不同批次 → `PROTECTED`） |
| R3 | 迁移幂等：同 `(source_table, source_pk, entity_table)` 重复执行只更新 |
| R4 | 前后数量核对：源端计数 → 目标端计数 → 差异逐条解释 |
| R5 | 备份先行：`cp` + `PRAGMA integrity_check` + 行数比对，**恢复演练一次才算验证过** |

**(3) 四步各带批次号（2.2）**：每步给源端计数（实测值）、预期目标计数（**注明是估计**）、回滚语句（带 `migration_batch_id` 且带引用检查）。

**(4) 保护判据与失败恢复（2.3 / 2.4）**：给出 `PROTECTED` 判定伪代码；`tx()` 整体回滚；`state='staged'` 残留清扫。

**同时新增**：C13（迁移批次与精确回滚）、C14（数据库备份与恢复验证）、`M13`、`M14` 四条记录。

### 未决（全部 L3/L4 = 0）

- `migration_batch` 落点：**独立表** 还是 **复用 `change_logs.batch_id`**？倾向独立表（迁移是"数据结构变更"，`change_logs` 是"内容变更"，混用会让回滚语义打架）。**D02-01 定。**
- `checksum` 用哪种规范化：应与 C2 的 `canonicalStringify` 共用，避免两套序列化。
- "预期目标计数 200–300 镜"是**估算**，必须等 1-5 干跑出真实数才能定验收阈值。

## 五、R-05 任务队列与业务任务边界

### 修订前

| 位置 | 原文 |
|---|---|
| §七 A3 | 「渲染公平队列 / `scheduler.js` + `queue_items` / **`render_tasks` 直接入队**」 |
| §3.1 | 「`queue_items` 25 列 / 渲染公平队列（未启用，0 行） / **可复用于 `render_tasks` 排队**」 |

两处都把 `queue_items` 写成"可以当 `render_tasks` 用"或"接上去就行"，没有区分业务任务实体与调度排队机制。

### 证据（L2，已实跑）

**`queue_items` 25 列实测**：

```
id, job_id, project_id, owner_id, pool, kind, status, priority, seq,
attempts, max_attempts, not_before, lease_until, worker_id, remote_task_id,
dedupe_key, payload, last_error, amount, unit_price, currency,
enqueued_at, started_at, finished_at, updated_at
```

**没有一个业务字段**：无 `unit_id`、无 `shot_id`、无 `prompt_package_id`、无 `track`。`payload` 是 JSON 文本（实传 `{ spec, kind }`），不可索引、不可 join。

**状态机实测（`db.js` `Queue` 模型）**：`waiting / running / done / cancelled` 四值。
- `Queue.claim` → `status='running'` + `lease_until` + `attempts+1`
- `Queue.fail(id, err, { retryAt })` → 退回 `waiting` + `not_before`（自动退避）
- `Queue.finish` → `done`

**从未启用**：`queue_items` **0 行**；`queueEnabled()` 仅当 `provider==='runninghub'` 且配置开启才为真（`scheduler.js:57-62`），本地 ComfyUI 永远走"整批串行闸门"。

**`jobs` 粒度**：13 列，`type` 为 `create` / `chapter-video` / `regenerate` / `asset-image` / …，**一次覆盖整章**，没有"单元"概念。

### 修订后

新增 **§4.3 `render_tasks` / `queue_items` / `scheduler` 三层边界**：

| 层 | 是什么 | 现有载体 | 现状 |
|---|---|---|---|
| 业务任务实体 | "为某个单元生成一条视频" | **不存在**（`jobs` 粒度过粗） | 需新建 `render_tasks` |
| 调度排队机制 | "现在轮到谁跑" | `queue_items`（25 列，0 行） | 已实现，未启用 |
| 调度执行能力 | "怎么公平挑下一个" | `scheduler.js`（`fairOrder`/`claim`/`finish`/`fail`） | 原样复用 |

并给出：
- **关系图**：`render_tasks 1:N render_attempts`，每次尝试 1:1 入队；
- **状态映射表**：`queue_items.status='done'` **≠** `render_task.status='succeeded'`（队列 done 只说明排队跑完了，产物可能是空视频）；
- **重试分工表**：租约/退避归队列，**"这个单元最终失败要不要换 seed 重来"归 `render_tasks`**——这一层现在完全没有，只有人工点 `regenerate_shot`。

### 同时修正 §4.2（审核未提，自查发现）

V1 写「断点续跑 ✅ `jobs.checkpoint` + `job-runner.js`」，**是错的**：

| 事实 | 证据 |
|---|---|
| `checkpoint` 存的是**任务参数**，不是进度 | `job-runner.js` 14 处 `Jobs.create` 全是 `checkpoint: { subject, chapter/… }` |
| 运行中从不更新 `checkpoint` / `progress` | 实库 `interrupted` 三条：`cp={"subject":"第1章","chapter":"第1章"}`、`progress={}` |
| 唯一"恢复"是标记中断 | `db.js:381` `UPDATE jobs SET status='interrupted' WHERE status='running'` |
| 重跑是**全量** | `job-runner.js:210` 硬编码 `force: true` → `generate_chapter_videos` 重跑本章全部镜头（含已 done） |
