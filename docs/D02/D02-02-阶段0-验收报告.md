## 三、关键代码变更

### 3.1 `lib/core/db.js`

1. `shots` 的 `CREATE TABLE` 增加 `blocking TEXT DEFAULT ''`（位置在 `sub_shots` 之后）。
   修复前新库是 34 列，而 `Shots.create` 的 INSERT 与 `Shots.update` 都写 `blocking`——
   **新库第一条分镜必然报 `table shots has no column named blocking`**（全量测试里有 46 条用例正是死在这里）。
2. 新增并导出 `ensureColumn(db, table, column, columnDdl)`：

```js
export function ensureColumn(db, table, column, columnDdl) {
  const cols = db.tableColumns(table);              // SQLite: PRAGMA table_info / PG: information_schema
  if (!cols || cols.length === 0) throw new Error(`ensureColumn: 表 ${table} 不存在或不可读`);
  if (cols.includes(column)) return false;          // 已存在 → 不做 ALTER（幂等）
  db.exec(`ALTER TABLE ${table} ADD COLUMN ${columnDdl}`);
  return true;
}
```

3. `initSchema` 末尾调用 `ensureColumn(db, 'shots', 'blocking', "blocking TEXT DEFAULT ''")`。

**与老写法的区别**（老写法 = `try { ALTER ... } catch {}`，全文还有 30 余处，本轮**未动**，只在注释里登记）：
先查列再 ALTER，重复执行零副作用；失败**抛出**而不是当成"已经有了"。老写法会把"表不存在""只读库""语法错"一起吞掉，等于加列失败也报成功。

4. **`getDb()` 在打开数据库之前做隔离断言（A-01）**：

```js
export function getDb() {
  if (!db) {
    const settings = dbSettings();              // 真正会打开的路径（env / config.json / 默认，三级覆盖）
    const isolated = settings.provider !== 'postgres' && !!process.env.IC_DATA_DIR;
    if (isolated) {
      assertEnv({ purpose: '数据库连接' });                    // ① 目录本身合法吗
      assertDbIsolation({ dataDir: process.env.IC_DATA_DIR,    // ② 库文件真的在里面吗（真路径比，悬空链接也解析）
                          dbPath: settings.sqlitePath, purpose: '数据库连接' });
    }
    db = createDb(settings);
    if (isolated) {
      try {                                     // ③ 打开后复核：压缩 ②→打开 的替换窗口（TOCTOU）
        assertDbIsolation({ ..., purpose: '数据库连接（打开后复核）' });
      } catch (e) { try { db.close(); } catch {} db = undefined; throw e; }
    }
    initSchema(db);
  }
  return db;
}
```

生产模式（未设 `IC_DATA_DIR`）**不触发**这两道断言——生产库本来就在 `<repo>/data`，这是职责边界；
一旦设了 `IC_DATA_DIR`，就再没有任何"看一眼环境变量就放行"的余地，因为校验对象变成了 `dbSettings().sqlitePath`。

> 第 ③ 步只是**压缩**窗口，不是消除：SQLite 只接受路径、不暴露文件描述符，无法做 fd 级校验。边界见 §7.6.4。

### 3.2 `lib/core/env-guard.js`（新增）

`assertEnv({ purpose, requireSqlite })` / `assertStage0Env()` / `assertDbIsolation({ dataDir, dbPath })`，拒绝以下情况并给出明确错误码：

| 错误码 | 触发条件 |
|---|---|
| `IC_DATA_DIR_NOT_SET` | 未设或空串 |
| `IC_DATA_DIR_NOT_ABSOLUTE` | 相对路径（解析基准会随 cwd 变） |
| `IC_DATA_DIR_IS_DEFAULT` | 等于 `<repo>/data` |
| `IC_DATA_DIR_INSIDE_PRODUCTION` | 位于 `<repo>/data` 之内 |
| `IC_DATA_DIR_SYMLINK_TO_PRODUCTION` | **真实路径**落在 `<repo>/data` 内（软链 / junction 指过来的） |
| `IC_DATA_DIR_NOT_CREATABLE` / `NOT_WRITABLE` | 建不出 / 写不进（真写一个探针文件再删） |
| `IC_DB_PATH_INSIDE_PRODUCTION` | `IC_DB_SQLITE_PATH` 把库指回生产目录 |
| **`IC_DB_PATH_OUTSIDE_DATA_DIR`** | 最终库文件（含 `config.json` 的 `db.sqlite.path`）**真实路径**不在 `IC_DATA_DIR` 内（含**悬空文件符号链接**） |
| `DB_PATH_EMPTY` | 传入的库路径为空 |
| `PATH_SYMLINK_LOOP` | 路径上的符号链接层数 > 40（疑似循环链接） |
| `STAGE0_REQUIRES_SQLITE` | `requireSqlite` 时检出 PG 配置 |

A-01 的五个突破口分别由谁拦：

| 绕过路径 | 拦截点 |
|---|---|
| `IC_DB_SQLITE_PATH=/elsewhere/ic.db` | `assertDbIsolation`：实际路径不在隔离目录 → `IC_DB_PATH_OUTSIDE_DATA_DIR` |
| `config.json` 的 `db.sqlite.path` 指到别处 | 同上（`dbSettings()` 把三级覆盖解析成同一个 `sqlitePath`） |
| 隔离目录里放一个指向外部目录的软链，库文件写进软链 | `realPathOf()` 取真实路径后再比 → 同样报 `OUTSIDE`（A-01-4） |
| 隔离目录里的 `ic.db` 是**指向外部文件的软链**（目标存在或**悬空**） | 逐段 `lstat` + `readlink` 解析，悬空链接也按目标判 → `OUTSIDE`（A-01-8/9/10，第三轮补） |
| `IC_DATA_DIR` 本身是指向生产目录的软链 | `assertEnv` 的 `SYMLINK_TO_PRODUCTION`，且**在 mkdir / 写探针之前**判，避免探针写进生产目录 |

**路径解析为什么不走 `realpathSync` + `existsSync`**（第三轮的核心修正）：

`fs.existsSync` 会**跟随**链接。链接目标不存在时它返回 `false`，旧实现据此把该路径当成"普通未创建文件"，用**父目录**的真实路径拼回去——于是 `iso/ic.db -> 外部/escaped.db`（目标还没建）在检查时看起来就是 `iso/ic.db`，人畜无害；SQLite 一打开就顺着链接在隔离目录外建库。**这是"检查的对象"和"打开的对象"不是同一个东西**，与 A-01 第一轮的错误同源。

现在的做法是逐段走（`resolveSymlinks()`）：

| 步 | 手段 | 为什么必需 |
|---|---|---|
| 1 | `lstatSync` **不跟随**链接 | 悬空链接也能看出 `isSymbolicLink() === true`；`existsSync` 在这里会撒谎 |
| 2 | `readlinkSync` 取链接目标 | **悬空链接同样能读到目标**；Windows junction / 目录软链 / 文件软链在 `lstat` 下都报 `isSymbolicLink()`，`readlink` 都返回目标，差异只在目标是目录还是文件，对"目标落在哪"的判定没有影响 |
| 3 | 相对目标按链接所在目录拼接 | `../outside/x.db` 这类相对链接必须按 OS 语义解析（A-01-10） |
| 4 | 目标本身还是链接 → 递归（共用 hops 计数，上限 40） | 链接链 / 环；超过上限报 `PATH_SYMLINK_LOOP` 而不是死循环 |
| 5 | 组件不存在 → 剩余部分按物理路径拼回 | 未创建的文件也要能判，不能因为不存在就"假定安全" |
| 6 | 最后对**存在的最长前缀**做一次 `realpath` 规范化 | 修 Windows 大小写 / 8.3 短名 / 卷挂载点；不存在的尾部原样接回 |

另外**不预先词法折叠 `..`**：`path.resolve('iso/link/../ic.db')` 会把 `link` 这一层抹掉，而 OS 解析时 `..` 是在链接目标之后算的。当前所有入口（`dbSettings()` / `assertEnv`）都已先 `path.resolve`，这一层属防御性处理，为将来直接传原始路径的调用方留的。

设计上有三条硬约束：

- **不静默回退**：任何一条不满足都抛错，绝不用默认 `data/` 顶替。
- **断言发生在打开库之前**：`getDb()` 先断言再 `createDb`，失败时不会留下任何库文件（A-01-2/3/4/8/9/10 都断言了"目标位置没有文件 / 原文件一个字节没动"）。
- **打开之后再复核一次**：检查与打开之间路径可能被替换，`createDb` 后立刻用**此刻**的真实路径重判，失败即关连接、抛错，不让后续 `initSchema` 往错的地方建表（边界见 §7.6.4）。
- **本模块故意不 import `config.js`**：`config.js` 在模块加载时就把 `IC_DATA_DIR` 固化成 `DATA_DIR`/`DB_PATH`。如果 `env-guard` 先加载、后设变量，路径已经定死——脚本会"以为"在隔离目录里跑，实际连真库。**这个坑本轮真的踩了**（见 §7.1），现在 `env-guard` 自己算 `REPO_ROOT`，只在函数调用时读 `process.env`。

### 7.6 【已闭环 · 第三轮】悬空文件符号链接曾经可以逃出隔离目录

#### 7.6.1 漏洞成因

`realPathOf()` 原来的实现是"找最接近的**已存在**祖先 → `realpathSync` → 把不存在的尾部按字符串接回"，而"是否已存在"用的是 `fs.existsSync()`。

`existsSync` 会**跟随**链接。于是：

```
iso/ic.db  -->  外部/escaped.db      （escaped.db 尚未创建）
fs.existsSync('iso/ic.db')  ===  false      ← 链接是悬空的，跟随失败
nearestExisting('iso/ic.db') === 'iso'      ← 于是退到父目录
realPathOf('iso/ic.db')      === 'iso/ic.db' ← 看起来干干净净在隔离目录内
```

守卫放行，`createDb()` 把字符串 `iso/ic.db` 交给 SQLite。SQLite 由 OS 解析路径——**OS 会跟随链接**，于是在 `外部/escaped.db` 建库。检查的对象（`iso/ic.db` 的父目录）和打开的对象（链接目标）不是同一个东西。

**实机复现**（修复前，临时脚本 `data/_verify/a01-dangling-repro.mjs`；`data/` 被 `.gitignore` 覆盖，脚本未入库——等价断言已固化为 A-01-9）：

```
linkKind      = file
link exists?  = false (follows link → 悬空即 false)
lstat isLink  = true
realPathOf    = ...\iso\ic.db                       ← 旧实现判成"在隔离目录内"
probe         = PROBE {"ok":true, ...}              ← 守卫放行
escaped.db?   = true ← 漏洞成立：隔离目录外被建库
```

修复后同一条脚本：

```
realPathOf    = ...\outside\escaped.db              ← 按链接目标判
probe         = PROBE {"ok":false,"code":"IC_DB_PATH_OUTSIDE_DATA_DIR", ...}
escaped.db?   = false                               ← 外部未落任何文件
```

#### 7.6.2 修复方式

采用**可靠的符号链接解析**（而不是"一律拒绝链接"），理由：隔离目录内部自建的链接（如快照目录软链）应当是合法的，一律拒绝会把正常用法一起挡掉，反而促使别人去关检查。

`lib/core/env-guard.js`：

| 改动 | 内容 |
|---|---|

| 类型 | `lstat().isSymbolicLink()` | `readlinkSync()` | 本实现 |
|---|---|---|---|

#### 7.6.4 校验与打开之间的竞态：做到了什么、没做到什么

`assertDbIsolation()` 判定的是**路径字符串此刻指向哪里**，`createDb()` 之后才真正打开。这两步之间路径可以被替换（TOCTOU）。本轮采取的措施与边界：

| 措施 | 效果 |
|---|---|
| 断言紧贴 `createDb()` 之前执行 | 窗口缩到最小（中间只剩一次函数调用），但**不是零** |
| `createDb()` 之后**再用此刻的真实路径断言一次**，失败即 `close()` + 抛错 | 若链接是在"断言 → 打开"之间被换上的，后续 `initSchema` 一定不会执行，不会往错的地方建表 |
| 判定对象是 `dbSettings().sqlitePath`（实际被打开的那个字符串），不是环境变量 | 三条覆盖路径共用同一判定，没有"换个配置就绕过"的旁门 |

**没有做到、也不声称做到的**：

1. **不能保证零窗口**。要在打开前把路径钉死，需要拿到文件描述符后交给 SQLite（fd 级打开），而 `node:sqlite` 只接受路径字符串、不暴露 fd，当前架构下做不到。
2. **若竞态真的发生，外部可能留下一个空库文件**。SQLite 打开时就会创建文件；我们在打开后才发现并抛错，只能保证"不建表、不写业务数据"，无法保证"外部不出现空文件"。真要清理，得由操作者按报错路径人工确认——自动删除隔离目录外的文件比留下空文件更危险。
3. **不防"有权限改隔离目录的人"**。能替换 `iso/ic.db` 的人本来就能改隔离目录里的一切；本断言的定位是**防配置错误与误用**（`IC_DB_SQLITE_PATH` 指错、复制来的软链、脚本拼错路径），不是防本机恶意提权。
4. **不处理挂载点 / 重解析点的全部形态**。Windows 的 `\\?\GLOBALROOT` 设备路径、卷挂载目录（volume mount point）由 OS 解析，`canonicalize()` 只能规范化"已存在前缀"，这类路径若绕过字符串前缀比较，属于未覆盖的边界。
5. **`..` 分支只在单元层覆盖**。`splitLoose` 不折叠 `..`，`A-01-12` 直接调 `assertDbIsolation` 验证过；但**当前所有入口都会先 `path.resolve`**，所以这条分支在真实链路上不可触发——它是为将来直接传原始路径的调用方留的，不是当前已存在的攻击面。

#### 7.6.5 与 B-02 的关系

本轮**不改变** §7.1 的结论与证据局限：那次误写的恢复仍只能证明"计数与完整性回到事故前"，不能证明"所有业务数据逐字节恢复"（缺少事故前全库指纹、被删子行主键未落盘、清理未过 `changelog`）。7.6 只修隔离判定的实现缺陷，不给 B-02 增添任何新证据。
