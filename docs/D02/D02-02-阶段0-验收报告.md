## 三、关键代码变更

### 3.1 `lib/core/db.js`

1. `shots` 的 `CREATE TABLE` 增加 `blocking TEXT DEFAULT ''`（位置在 `sub_shots` 之后）。
   修复前新库是 34 列，而 `Shots.create` 的 INSERT 与 `Shots.update` 都写 `blocking`——
   **新库第一条分镜必然报 `table shots has no column named blocking`**（全量测试里有 46 条用例正是死在这里）。
2. 新增并导出 `ensureColumn(db, table, column, columnDdl)`：

```js
export function ensureColumn(db, table, column, columnDdl) {
  const cols = db.tableColumns(table);              // SQLite: PRAGMA table_info / PG: information_schema
  if (!cols || cols.length === 0) throw new Error(`ensureColumn: 表 ${table} 不存在或不可读`);
  if (cols.includes(column)) return false;          // 已存在 → 不做 ALTER（幂等）
  db.exec(`ALTER TABLE ${table} ADD COLUMN ${columnDdl}`);
  return true;
}
```

3. `initSchema` 末尾调用 `ensureColumn(db, 'shots', 'blocking', "blocking TEXT DEFAULT ''")`。

**与老写法的区别**（老写法 = `try { ALTER ... } catch {}`，全文还有 30 余处，本轮**未动**，只在注释里登记）：
先查列再 ALTER，重复执行零副作用；失败**抛出**而不是当成"已经有了"。老写法会把"表不存在""只读库""语法错"一起吞掉，等于加列失败也报成功。

### 3.2 `lib/core/env-guard.js`（新增）

`assertEnv({ purpose, requireSqlite })` / `assertStage0Env()`，拒绝 6 种情况并给出明确错误码：

| 错误码 | 触发条件 |
|---|---|
| `IC_DATA_DIR_NOT_SET` | 未设或空串 |
| `IC_DATA_DIR_NOT_ABSOLUTE` | 相对路径（解析基准会随 cwd 变） |
| `IC_DATA_DIR_IS_DEFAULT` | 等于 `<repo>/data` |
| `IC_DATA_DIR_INSIDE_PRODUCTION` | 位于 `<repo>/data` 之内 |
| `IC_DATA_DIR_NOT_CREATABLE` / `NOT_WRITABLE` | 建不出 / 写不进（真写一个探针文件再删） |
| `IC_DB_PATH_INSIDE_PRODUCTION` | `IC_DB_SQLITE_PATH` 把库指回生产目录（绕过 `IC_DATA_DIR` 检查的那条路） |
| `STAGE0_REQUIRES_SQLITE` | `requireSqlite` 时检出 PG 配置 |

设计上有两条硬约束：

- **不静默回退**：任何一条不满足都抛错，绝不用默认 `data/` 顶替。
- **本模块故意不 import `config.js`**：`config.js` 在模块加载时就把 `IC_DATA_DIR` 固化成 `DATA_DIR`/`DB_PATH`。如果 `env-guard` 先加载、后设变量，路径已经定死——脚本会"以为"在隔离目录里跑，实际连真库。**这个坑本轮真的踩了**（见 §六-1），现在 `env-guard` 自己算 `REPO_ROOT`，只在函数调用时读 `process.env`。

### 3.3 `scripts/stage0/*`

| 脚本 | 做的事 | 关键手法 |
|---|---|---|
| `backup-restore-drill.mjs` | 备份 → SHA → 完整性 → 行数 → 删测试库 → 恢复 → 对账 | 源库**只读连接 + `VACUUM INTO`**：WAL 模式下直接 `copyFile` 可能漏掉 `-wal` 里已提交的页；`VACUUM INTO` 是 SQLite 官方一致性快照手段，且对只读库可用 |
| `init-fresh-db.mjs` | 空库 → initSchema ×3 → 建项目/镜 → 读回 → 幂等断言 | 把 `IC_DATA_DIR` 收窄到 `fresh-<时间戳>/` 子目录，并摘掉 `IC_DB_SQLITE_PATH` 防串库 |
| `baseline-snapshot.mjs` | 副本 + SHA ×2 + 12 表行数 + 全库结构 + `blocking` 非空数 | 每次运行独立目录 `baseline-<时间戳>/`，报告写 `baseline-latest.json` |
| `gen-manifest.mjs` | 空库导出列名 → Manifest | `expect` 写**列名数组**，不写列数 |
| `verify-manifest.mjs` | 比对某库 vs Manifest | `missing = expect - actual`；`extra - tolerate_extra` 必须为空；`tolerated` 只记 INFO |

## 七、发现的问题

### 7.1 【已闭环 · 过程事故】测试一度写入了真实库

- **现象**：第一版 `tests/stage0.test.mjs` 先 `import` 了 `env-guard.js`（当时它 `import { ROOT } from config.js`），`config.js` 在加载瞬间就把 `DATA_DIR` 定成了 `data/`；随后才设 `IC_DATA_DIR`——`config` 已被缓存，改不动了。结果 `getDb()` 连的是真库，T-04 往里写了 **2 个项目 + 4 条分镜 + 2 个章节 + 8 条 change_logs**。
- **怎么发现的**：T-05 断言"新库 35 列"却得到 `37 == 35`——真库是 37 列，一眼看出连错了库。
- **清理**：按项目 id 精确删除（`shots/chapters/change_logs/reference_images/messages/shot_videos/jobs/queue_items` + `projects`），事务内执行；复核 **projects 14 / shots 66 / chapters 15 / assets 143 / blocking 非空 13**，与事故前一致，`integrity_check=ok`。
- **修复**：`env-guard.js` 不再 import `config.js`（自算 `REPO_ROOT`，函数调用时才读 `process.env`）；测试文件在**任何 lib 加载之前**取真库 SHA 作为基线，T-09 结束时比对。
- **代价与价值**：这条事故恰好证明了阶段 0 存在的理由——默认值一旦存在，误写只是时间问题。现在它被两处拦住：`assertEnv` 的目录白名单 + 测试的指纹基线。

### 7.2 【登记 · 阶段 1 前需决策】Manifest 路径与 `.gitignore` 冲突

D02-01 §4.5 写的是 `data/schema-manifest.json`（"随代码入库"），但 `.gitignore` 里有 `data/`。本轮把阶段 0 版放在 `scripts/stage0/`。**阶段 1 必须二选一**：改路径（推荐，如 `lib/core/schema-manifest.json`），或给 `.gitignore` 加白名单。

### 7.3 【登记】`initSchema` 里仍有 30 余处 `try { ALTER } catch {}`

本轮只把 `blocking` 一列改成 `ensureColumn`，其余按"不扩大修改范围"未动。风险：加列失败被当成成功（只读库、表不存在、语法错）。建议阶段 1 建表时统一改用 `ensureColumn`，作为独立小改动做，不和建表混在一起。

### 7.4 【登记 · 影响阶段 2】`data/ic.db` 存在 WAL 残留风险

本次演练用 `VACUUM INTO` 规避了 `-wal` 漏页问题。但**用 `cp` 直接拷库仍是不安全的**——阶段 2 的迁移前备份若照抄 `cp`，会得到"少几个事务"的备份。建议阶段 2 的备份脚本强制走 `VACUUM INTO`。
