## 二、用户决策（本轮依据，不再回溯论证）

用户在阶段 1 通过后作出以下决定，本记录据此成立：

1. **旧项目、旧测试剧本、旧章节、旧分镜、旧提示词、旧人物与场景资产、旧生成记录，均为此前开发测试产生的产物，不作为新系统的业务数据。**

## 六、旧数据：三条界线

必须区分三个动词，它们**不是一回事**：

| 动词 | 含义 | 状态 |
|---|---|---|
| **不使用** | 旧数据不作为新系统的业务输入、测试样本、验收依据 | ✅ 已生效 |
| **不迁移** | 不为旧数据编写解析器、不搬进新表、不做对账 | ✅ 已生效 |
| **不删除** | 旧数据仍然在库里、在磁盘上，一行不少 | ✅ **必须保持** |

**关键判据**：前两条成立，**不推出**第三条的反面。用户在 §二 确认的是"不再使用、不再迁移"，从未授权"物理删除"。

因此以下动作**未经独立授权一律禁止**：

| 禁止动作 | 为什么 |
|---|---|
| 清空真实数据库 | 旧数据是唯一副本，删了就没有了 |
| 删除旧项目及其数据库记录 | 同上；且 `Projects.remove` 会连带删 `change_logs` 与产物 |
| 删除旧测试文件、素材目录、生成视频 | 文件系统里的产物不在数据库事务保护范围内，删了无法回滚 |
| 运行清理脚本 / 批量 DDL / 批量 DML | 清理的判据与迁移不同（D02-01 §12.5.2），需要独立的备份 + 干跑 + 归属校验 |
| 重建真实数据库让它"看起来干净" | 这是最危险的一种：看起来是"重来一次"，实际是不可逆的数据销毁 |

**当前真实库的实际状态（实测，供后续核对）**：33 张表（既有 12 + 阶段 1 的 21，后者全部 0 行）、`projects` 14 行、`shots` 66 行、`chapters` 15 行、`assets` 143 行、`change_logs` 2805 行、`jobs` 44 行、`migration_batches` 0 行、`integrity_check = ok`。这些数字是**保留而非清理**的依据。

## 十、失去"对照数据"之后怎么补

阶段 2 提供的唯一软价值是"迁移结果可以和旧数据对照，验证新模型装得下真实内容"。取消之后，这个对照消失了。补偿方式有三条，**都不依赖旧数据**：

| # | 补偿方式 | 出处 |
|---|---|---|
| 1 | **D01 自带的算例**：`posRel` 13 行矩阵、四镜传播算例、动作时间 4 个算例、切分算例 A~G | D01-04 §5.2.2 / §5.7，D01-03 §5.6，D01-06 |
| 2 | **人工合成的最小剧本**：3 镜 / 2 动作 / 2 站位，覆盖结构化写全链路 | D02-06 §十四 |
| 3 | **真实源文件的首次完整跑通**：用户提供源文件后，一个真实项目写完一章并校验通过（L4） | D02-06 §十六 |

**必须写清的边界**：前两条只能证明"结构装得下、校验有效"，**不能证明"真实创作可用"**。真实可用只有第 3 条能证明，而它需要用户提供源文件并确认。**在这之前不得宣称阶段 3 已完成真实创作验收。**
