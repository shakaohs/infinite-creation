## 二、任务 1：内容寻址命名的碰撞风险（修订 D-31-02）

### 2.1 修订前的契约与它的三个洞

| 项 | D02-31 的写法 | 洞 |
|---|---|---|
| 名字形态 | `ic_<pid8>_<role>_<assetid8>_<sha8>.<ext>` | `sha8` = 8 个十六进制字符 = **32 bit**。生日界约 7.7 万次上传即有 50% 碰撞概率；这不是「概率极低」，是「迟早发生且无法排查」 |
| 唯一性来源 | 依赖 sha8 | 名字里还有 `pid8`/`assetid8`（也是截断），三者都截断 ⇒ 名字不能作为内容标识 |
| 适用通道 | 三条上传通道通吃 | RunningHub 返回平台 `fileName`（`runninghub.js:43~45`），本机名字与平台对象无关；外接引擎**不传文件**（`backend.js:22` 直接返回）⇒ 只有 native ComfyUI 需要内容寻址 |

### 2.2 修订后的唯一契约（D-31-02 v2）

**名字 = `ic-` + 完整 SHA-256（64 个十六进制小写）+ 原扩展名。**

| 不变式 | 内容 | 为什么这样定 |
|---|---|---|
| I1 纯内容 | 名字只由字节决定，不含 `project_id`／`role`／`asset_id`／时间戳／uid | 一旦掺入非内容成分，同名必同内容就不成立，唯一性论证崩塌 |
| I2 全量摘要 | 使用完整 256 bit，不做任何截断 | 32 bit 不满足唯一性；64 hex 的路径长度（约 71 字符）在 Windows/Linux 下都安全 |
| I3 不同内容不同名 | 由 I1+I2 直接得出：不同字节 ⇒ 不同摘要（除密码学碰撞） | 覆盖风险从「命名层」转移到「散列层」，后者是全系统的既有安全前提 |
| I4 同内容同名 | 重复上传落到同一对象，写入的是同一份字节 ⇒ 幂等 | 这是「复用」的正确形态：不是「检测到存在就跳过」，而是「写同一份内容」 |
| I5 不复用判定 | **默认不做存在性检查、不跳过上传**：无条件写 | ComfyUI 没有可靠的「读回 input 对象」契约；跳过上传就必须校验，而校验需要回读，回读在远端不可靠。**无条件写 = 不需要任何判定** |
| I6 严格模式可选 | `verifyUpload=true` 时上传后回读并比 sha256，不一致抛 `UPLOAD_HASH_MISMATCH` 并中止本次渲染 | 满足「已存在必须校验、不一致必须失败」；默认关闭（多一次全文件传输） |

**关于 I5 与任务书「对象已存在时必须验证其字节 Hash」的关系**（必须写清，否则会被读成偷工）：

| 场景 | 是否可能发生 | 处置 |
|---|---|---|
| 同名对象已存在且内容相同 | **唯一可能**（名字是内容的函数） | 重写同字节，幂等，无需校验 |
| 同名对象已存在且内容不同 | 只可能来自：① SHA-256 碰撞（密码学事件）；② 第三方绕过本系统往 `input/` 写了同名文件；③ 上传被截断/损坏 | 默认模式**不检测**（检测需要回读，代价与风险都更高）；`verifyUpload=true` 时**必检必失败**（I6） |
| 名字里不再有 pid/role/assetid，如何排障 | — | 从 `media[]` 指纹段（`ref` + `sha256` + `bytes`）反查；日志里打印 `{ref, sha256, name}` 三元组 |

**明确写下的一句话**：本方案把「串台」的防线从「名字不撞」改成「名字是内容的函数」。这不是概率更小的运气，而是**结构上不再存在第二条写同名不同字节的路径**——除了上表 ② 那种绕过本系统的写入。

### 2.3 四条通道的实际文件消费路径（逐条）

| 通道 | 上传/传递 | 执行时消费什么 | 内容寻址是否有意义 |
|---|---|---|---|
| **native ComfyUI** | `uploadToInput(baseUrl, buf, filename)` → `POST /upload/image` 带 `overwrite='true'`（`comfyui.js:36~45`）；工作流 `LoadImage.image` 写这个名字 | ComfyUI 服务端 `input/<name>` 的字节 | **有**，且是唯一有意义的通道 |
| **RunningHub** | `runninghubUpload(cfg, path)` → `POST /openapi/v2/media/upload/binary`，**平台返回 `fileName`**（`runninghub.js:28~45`），工作流用平台名 | 平台侧对象 | **无意义**（本机名字不进请求）。只需把 `sha256` 记入指纹 |
| **外接引擎** | **不传文件**：`uploadTaskInput` 在引擎模式下直接返回（`backend.js:22`） | 执行期 `dataUrlOf(localPath)` 读本地文件转 base64 内联（`engine-runner.js:67`） | **无意义**（没有对象名）。靠 C2 冻结 dataUrl 解决 |
| **本机工作流文件**（`custom_<slug>.json`） | 不经过上传，`buildWorkflow` 每次重读（`workflow-runner.js:20`） | 重读的 DAG 文本 | 不适用（靠 C3 冻结源文本解决） |

**结论**：D-31-02 的适用范围必须收窄为「native ComfyUI 的参考素材上传」。对另外三条通道，它既不生效也不必要——把这条写进决策定义，避免实现时误把 RH 的平台名改掉（会让云端工作流找不到文件）。

## 三、任务 2：SQLite 与 PostgreSQL 的事务与锁协议（修订 D-30-13）

### 3.1 修订前的矛盾

D02-31 §4.4 写「`tx()` 是 deferred `BEGIN`，由 D-30-13 升级为 `BEGIN IMMEDIATE`」，§8.4 又写「`BEGIN IMMEDIATE` 不能发给 PG（驱动原样转发）」。两句话放在同一份报告里，读者无法判断 PG 该怎么办。

**根因**：把「事务的开始方式」当成了跨库的统一概念。事实上：

| 维度 | SQLite | PostgreSQL |
|---|---|---|
| 写锁粒度 | **整个库**（`BEGIN IMMEDIATE` 取 RESERVED） | 行级 + 表级 + advisory |
| 能否中途升级 | 能，但**升级失败立即 `SQLITE_BUSY`**，`busy_timeout` 不救升级 | 能（行锁随语句获取） |
| 等待方式 | `busy_timeout=5000`（已在 `db-driver.js:69` 设） | `lock_timeout` / 阻塞等待 |
| 进程模型 | 单文件，多进程可能同时打开 | 单进程一条连接（`pg-worker.mjs` 每进程一个 worker） |

### 3.2 修订后的唯一协议

**唯一入口**：`txProject(projectId, fn)`（`lib/core/tx-locked.js`）。`tx(fn)` 保留为「不需要项目级互斥的纯结构事务」（如只改一行自己的字段），两者不可混用。

| 阶段 | SQLite | PostgreSQL |
|---|---|---|
| ① 开始 | `BEGIN IMMEDIATE` | `BEGIN` |
| ② 取锁 | 由 ① 隐式获得（库级写锁） | `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`，`$1 = projectId` |
| ③ 超时 | `busy_timeout=5000` 已在连接建立时设置 | `SET LOCAL lock_timeout = '5s'`（BEGIN 之后、取锁之前） |
| ④ 业务写 | 同步 SQL | 同步 SQL（经 `Atomics.wait` 门面） |
| ⑤ 提交 | `COMMIT`（释放写锁） | `COMMIT`（`xact` 锁随事务释放） |
| ⑥ 失败 | `ROLLBACK` → 抛原错 | `ROLLBACK` → 抛原错 |
| ⑦ 进程中断 | WAL 回滚未提交事务；写锁由文件句柄释放 | 连接断开 ⇒ 服务端回滚 + 释放 `xact` 锁 |
| 锁粒度 | **库级**（不同项目也会串行） | **项目级**（不同项目并行） |

**必须诚实写下的不等价**：SQLite 下 `txProject(A)` 会阻塞 `txProject(B)`。这在单机单进程场景是可接受的（写事务本就毫秒级），但**不能**对外宣称「两库行为一致」。文档与验收都按「SQLite 过度串行、PG 精确到项目」来写。

### 3.3 为什么用 `pg_advisory_xact_lock` 而不是别的

| 候选 | 结论 | 理由 |
|---|---|---|
| `pg_advisory_xact_lock` | **推荐** | 事务结束自动释放，进程崩溃时由服务端随连接释放，**不存在锁泄漏** |
| `pg_advisory_lock`（会话级） | 否决 | 必须在 `finally` 里手工 `unlock`；`tx()` 禁 async，异常路径容易漏掉 ⇒ 泄漏后全项目永久阻塞 |
| `SELECT ... FOR UPDATE` 锁项目行 | 备选 | 语义直观，但要求所有写入方先 `SELECT` 同一行；且 `projects` 行被锁会让无关的项目级读也排队 |
| 提高隔离级别到 `SERIALIZABLE` | 否决 | 需要重试循环（`40001`），而 `tx()` 是同步的，重试会把整段 `fn` 重跑一遍，副作用（LLM 调用、文件写）不可重入 |
| 不加锁，靠唯一索引兜底 | 否决 | 唯一索引只能让第二个写入者**失败**；`global_no` 的 `MAX+1` 竞态（`global-no.js:79`）就会变成用户可见的写入错误 |

**`hashtextextended` 的可用性**：它是 PostgreSQL 内置函数但未在官方文档列出（文档只列 `hashtext`）。若目标版本不可用，退化为**纯文档化**写法：

```sql
SELECT pg_advisory_xact_lock(('x' || substr(md5($1), 1, 16))::bit(64)::bigint)
```

两者都必须**先在目标 PG 版本上实跑确认**（本轮无 PG 环境，见 §3.7）。哈希碰撞的后果说明：两项目撞同一 key 只会**多串行**，不会错数据——因为锁保护的是「同一项目的写者互斥」，多锁一个项目只损失并发度。

### 3.4 嵌套与同步约束

| 情形 | 行为 |
|---|---|
| `txProject(P)` 内再 `txProject(P)` | 复用（`txDepth>0` 且 `lockedProjects.has(P)`），不重复取锁 |
| `txProject(P)` 内 `txProject(Q)` | PG 允许（advisory 可叠加，两个锁都在同一事务内自动释放）；SQLite 本就库级 ⇒ 无差别。记录一条 warn 便于发现设计异常 |
| `tx()` 内调 `txProject(P)` | **抛 `TX_MUST_BE_IMMEDIATE`**（fail-closed）。理由：SQLite 下 deferred 事务已开始，升级写锁失败会直接 `SQLITE_BUSY`，`busy_timeout` 不生效 ⇒ 唯一安全做法是让最外层就用 `IMMEDIATE` |
| `txProject(P)` 内调 `tx()` | 允许（内层只是复用外层） |
| `fn` 返回 Promise | 抛 `ASYNC_TX`（既有行为，`db.js:487`） |

### 3.5 必须参加同一协议的源写入方（逐项）

| 函数 | 改法 |
|---|---|
| `rawGet(entity, key)` | `key` 允许数组；单列时行为不变（向后兼容） |

### 4.4 三个必须一起定的细节

**(a) `shot_assets` 的差集审计，不是整组审计。**
`writeShotAssets` 是 `DELETE FROM shot_assets WHERE shot_id=?` 再逐行 `INSERT`（`shot-assets.js:235~237`）。若按行记日志，**每次重写都会产生 旧组 N 条 delete + 新组 M 条 create**——改一个道具引用就能刷出十几条日志，把内容日志淹掉（这正是 `VOLATILE` 当初要解决的问题）。差集审计把日志量压到「实际变化的行数」（通常 1~3 条）。

**(b) 审计失败必须回滚业务事务。**
`recordChange` 的 INSERT 与业务写在同一个 `txProject` 内，抛错即整体回滚。理由：「改了但查不到」与「没改」在事后不可区分，而审计的全部价值就在于区分这两件事。与既有先例一致：`render_selection` 归属解析失败时 `recordChange` 本就抛错（`changelog.js:120~127`）。

**(c) 补审计不得重新开放整行回滚。**
`applyInverse` 的整行复原（`changelog.js:263`）会绕过 `ShotParams` 白名单、绕过投影、绕过 Stage 3 服务层。补审计后**回滚能力不增加**：结构化项目仍 409（D-30-15 主条不变），多列主键实体一律 `ROLLBACK_UNSUPPORTED_ENTITY`。审计用于取证，不用于自动恢复。

## 七、唯一结论：三问分别判断

### 7.1 可以提交用户批准架构决策吗

**可以。** 19 项决策已具备：唯一定义、依赖的规范条款、DB/接口/兼容影响、推荐与替代方案、是否阻断。本轮修订的 5 项（D-30-08 v2、D-30-09 v3、D-30-13 v2、D-30-15 v2、D-31-02 v2）定义已闭合，可以直接进入批准流程。

批准时请注意两点：① 按 **v2/v3** 批，不按 D02-30/31 的旧定义；② D-30-03 附带 D02-06 §8.2.4 三处正文修订，批的是「改规范」，不只是「改代码」。

### 7.2 可以编写 P10-A 正式实施任务书吗

**可以。** 前置条件已可枚举为 7 条 gate（§6.4），任务书可以把 gate 写成「开工检查表」而不是「待定事项」。同时 V1~V8 已经给出验收口径，任务书不必再讨论「怎么算完成」。

写作时必须内置三条约束：① gate 未全绿不得进入编码章节；② 19 项决策未批时任务书只能是 draft；③ 实施顺序按 D02-31 §6.3 的 S1→S5（先接写链、最后开门禁）。

### 7.3 可以开始 P10-A 编码吗

**不可以。** 三个理由，缺一不可：

| # | 阻断 | 现状 |
|---:|---|---|
| 1 | 13 项阻断决策未批 | 无任何批准记录 |
| 2 | PG 五个交错未实跑 | 无 PG 环境（`provider=sqlite`、`postgres.url` 空、无 psql/docker） |
| 3 | C1~C4 未落地 | 本轮禁改代码；T1~T6、C1~C12 全部「未执行」 |

### 7.4 八个验收问题的直接回答

| # | 问题 | 回答 |
|---:|---|---|
| 1 | 不同渲染任务是否会因文件名相同而串用不同字节 | **今天会**（确定性名字 + `overwrite=true`）。D-31-02 v2（全量 sha256 纯内容命名）落地后**结构上不会** |

| 4 | SQLite 与 PG 是否有各自明确、互不矛盾的锁协议 | **本轮已给出**（§3.2），两库不等价且已明确说明 |
| 5 | 所有 Stage 3 源写入方是否都参加同一协议 | 设计为「是」（S1~S10）；**今天不是**（`upsertSceneStates` 用 `tx()`，`global_no` 用 `MAX+1`） |
