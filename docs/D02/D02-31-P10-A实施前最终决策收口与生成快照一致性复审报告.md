### 1.3 三条本轮新证据（都不是文档问题，是代码事实）

**证据 1（阻断级）· 跨渲染同名覆盖。** 参考图上传名是确定性的 `ic_<pid8>_<role>_<assetid8>.<ext>`（`refs.js:110`），音频同理（`refs.js:169`），上传时带 `overwrite='true'`（`comfyui.js:41`）。同一资产在两次渲染之间被重新生成 ⇒ 后一次上传把同名文件覆盖 ⇒ **先前排队中的任务实际消费新字节，而它落库的 `input_hash` 仍描述旧字节**。这不是时点问题，是命名问题；冻结快照救不了，因为被冻结的是名字。

**证据 2（阻断级）· 外接引擎通道的执行期读取。** `uploadTaskInput` 在引擎模式下**直接返回、不读文件**（`backend.js:22`）；真正的字节读取发生在执行期的 `dataUrlOf`（`engine-runner.js:67`，由 `buildEngineVars` 在 `engine-runner.js:91` 调用）。所以「prepare 阶段读一次字节并冻结」对引擎通道今天不成立。

**证据 3（收口级）· 工作流源文件每次渲染重读。** `buildWorkflow` 调 `cloneSpecSource(spec.sourceFile)`（`workflow-runner.js:78`）→ `loadSpecSource` 的 `fs.readFileSync`（`workflow-runner.js:20`）。自定义工作流按原路径覆盖（`workflows/route.js`），所以「Hash 算完 → 图被换」的窗口真实存在。

### 1.4 结论

七条任务给了七个结论、九条修订、四条新增决策。**没有一条能靠文档措辞解决**——证据 1、2 必须改代码（读一次字节、名字内容寻址），证据 3 必须改 `buildWorkflow` 签名。这三处加上 PG 并发未实跑，构成 P10-A 的四个真阻断。

## 三、生成快照一致性分析（任务一）

### 3.1 真实执行链的六次文件/配置读取

一次视频渲染从 prepare 到提交，共六处「从外部取数据」。这六处就是快照的全部对象：

| # | 读取点 | 时点 | 读什么 | 消费者 | 今天能否被冻结 |
|---:|---|---|---|---|---|
| R1 | `refs.js:107` / `tools.js:2454` 的 `fs.existsSync` | prepare | 存在性 | 决定引用是否入列 | 可（判断本身就是输入） |
| R2 | `comfyui.js:37` `readFileSync` / `runninghub.js:29` `readFileSync` | **prepare**（上传时） | 媒体字节 | 上传到 ComfyUI input 或 RH 平台 | 可，但返回值今天丢弃 |
| R3 | `engine-runner.js:67` `readFileSync` | **执行期** | 媒体字节 → data URL | 引擎请求体 | **不可（今天没有冻结点）** |
| R4 | `workflow-runner.js:20` `readFileSync` | **执行期**（`buildWorkflow` 内） | 工作流 DAG | 提交给 ComfyUI/RH 的图 | **不可（今天每次重读）** |
| R5 | `tools.js:316` `loadConfig()` | job 建立时 | 全部配置 | `ctx.cfg` 贯穿整个 job | 可（job 内不可变） |
| R6 | `workflow-specs.js:524` `Workflows.list()` | prepare（`getSpecForKind`） | 自定义规格行 | `spec.roles` 等 | 可（返回普通对象） |

**关键差别**：R1/R2/R5/R6 都发生在 prepare 内，天然可截；R3/R4 发生在 prepare **之后**、提交**之前**——这正是任务书要求比较的那段窗口。

### 3.2 两个方案的比较

| 维度 | A · 冻结输入快照 | B · 执行前校验 |
|---|---|---|
| 做法 | prepare 读齐字节/配置，渲染只用这份 | prepare 记 Hash，提交前重算比对，不等则中止 |
| 能否覆盖 R2 | 能（本来就已读） | 能（但要多读一次，多一次成本） |
| 能否覆盖 R3 | 能（把 dataUrl 一起冻结） | 能 |
| 能否覆盖 R4 | **不能单独覆盖**：冻结的是「我没有 R4 的读点」，要冻结必须改 `buildWorkflow` 签名 | 能（重读比对，但要改 `runWorkflow` 入口） |
| 能否覆盖「同名覆盖」 | **完全不能**：R2 已冻结名字，ComfyUI 侧字节被换了 | **不能**：比对的是本地文件，本地文件没变 |
| 失败行为 | 不需要失败路径 | 中止 + 重新准备，用户可感知延迟 |
| 残余窗口 | 无（读一次用一次） | 比对到提交之间仍有窗口，只是变窄 |
| 实现成本 | `uploadTaskInput` 与 `buildWorkflow` 各改签名一次 | 再加一次全量 Hash 计算 + 中止分支 + 重试语义 |

**唯一推荐：A′ —— 单次读取即定指纹，B 只保留一项（引擎身份断言）。**

A′ 不是 A 的措辞改写，差别在「先读后算」还是「边读边算」：

| | A（先读后算） | **A′（边读边算）** |
|---|---|---|
| 顺序 | 先 `readFileSync` 拿字节 → 上传 → 另起一次算 Hash | `readFileSync` 的**同一个 buffer** 同时用于上传与 Hash |
| 读取次数 | 2（若实现者图省事就会变成 2） | **1** |
| 窗口 | 「两次读之间」 | **不存在**，因为只有一次读 |

### 3.3 A′ 的四个改动点（最小集）

| 改动 | 位置 | 内容 | 为什么必须改 |
|---|---|---|---|
| C1 | `backend.js:21~26` | `uploadTaskInput` 改为接受**已读好的 buffer**，返回 `{ name, sha256, bytes }` | 让 R2 的字节既上传又入指纹；引擎分支不再「不读就走」 |
| C2 | `engine-runner.js:67~76` | `dataUrlOf` 改为接受 `prepared.media[i].dataUrl`，不再自己 `readFileSync` | 消除 R3 |
| C3 | `workflow-runner.js:77~78` | `buildWorkflow(spec, params, sourceText)`：`sourceText` 由 prepare 读一次并算 Hash 后传入；缺省时才回退到 `loadSpecSource`（保持其它调用方零改动） | 消除 R4 |
| C4 | `refs.js:110` / `refs.js:169` | 上传名加入内容前缀：`ic_<pid8>_<role>_<assetid8>_<sha8>.<ext>` | 消除「同名覆盖」串台（证据 1） |

C4 是唯一一条**改变磁盘上的文件名**的改动，风险点与结论：

| 问题 | 结论 |
|---|---|
| ComfyUI input 目录会不会堆垃圾 | 会，且今天已经在堆（`overwrite=true` 只是覆盖同名，名字本身每次都不同：首帧/尾帧/图生三处已经带 `uid()`）。内容寻址反而**减少**重复上传 |
| 旧任务会不会找不到文件 | 不会：名字在提交时已写进图里，图是冻结的 |
| 会不会影响 RunningHub | 不影响：RH 返回自己的 `fileName`，本机名字只用于本地读取 |
| 会不会让指纹依赖文件名 | 不会：指纹用 `sha256`，名字只是它的函数 |

### 3.4 时点契约（任务书八问逐条）

| 问题 | 唯一答案 | 依据 |
|---|---|---|
| Hash 计算时点 | `prepareShotForRender` 返回前，最终 `inputSnapshot` 组装完那一刻 | `tools.js:2487~2490` 之后 |
| 媒体实际读取时点 | prepare 一次，且**只有这一次**；上传与 Hash 共用同一 buffer | C1 |
| 工作流配置读取时点 | prepare 一次（读源文件文本）；`buildWorkflow` 消费传入文本 | C3 |
| 外接引擎配置读取时点 | job 建立时（`ctx.cfg`），job 内不可变；引擎**身份**在 prepare 用同一 `cfg` 现算 | R5、`tools.js:316` |
| `runWorkflow()` 实际消费的数据来源 | `spec`（内存）+ `params`（prepare 产出）+ `sourceText`（prepare 产出）；引擎分支消费 `cfg` + `spec` + `params`，媒体取 `params.references[].dataUrl` | C2/C3 |

### 3.5 两个反例的证伪路径

**反例 1：Hash 完成后、媒体上传前替换图片文件。**

| 阶段 | 今天（无 C1） | A′（有 C1） |
|---|---|---|
| T0 | prepare 算 Hash（读文件一次） | prepare 读文件一次，得到 `buf` 与 `sha` |
| T1 | 用户覆盖图片 | 用户覆盖图片 |
| T2 | 上传时 `readFileSync` 读到**新字节** | 上传的是 T0 的 `buf`（旧字节） |
| 结果 | 候选 Hash 描述旧字节、模型吃新字节 → **不一致** | 一致；新字节只在下次渲染生效 |

结论：**A′ 下该反例在结构上不可达**（没有第二次读），而不是「被检测到」。这一点比方案 B 强。

**反例 2：Hash 完成后、工作流执行前覆盖同名自定义工作流。**

| 阶段 | 今天（无 C3） | A′（有 C3） |
|---|---|---|
| T0 | prepare 只记 `spec.id` 与源文件名 | prepare 读源文件文本一次，算 `specHash` 并留存 |
| T1 | 用户覆盖 `custom_<slug>.json` | 用户覆盖 `custom_<slug>.json` |
| T2 | `buildWorkflow` 重读 → 构建**新图** | `buildWorkflow` 用 T0 文本 → 构建**旧图** |
| 结果 | 候选 Hash 描述旧图、模型跑新图 → **不一致** | 一致；新图只在下次渲染生效 |

**反例 3（本轮补充，任务书未列但更险）：反例 1 的跨任务版本。**
A 任务已上传旧字节到名字 N 并排队；B 任务在 A 排队期间把同名 N 覆盖成新字节。A 的 `input_hash` 与 A 的 `buf` 一致性无懈可击，但 ComfyUI 侧 N 已不是 A 的字节。**只有 C4 能消灭它**，A′ 单独不够。这是本报告最重要的结论之一。

| C1 后的 `sha256` 来源 | 取自**上传那个 buffer**，不再二次读盘；`bytes` 同步取自 `buf.length` |
| 引擎通道的 `sha256` | 取自 prepare 冻结的 buffer（与 dataUrl 同源），不是执行期读盘 |
| `specHash` | 取 prepare 读到的源文件**文本**的 sha256 + 规范化 `roles/media/fixed/prune`；不含 `sourceFile` 路径（路径改名不应过期） |

### 3.8 关于 `covered` 的「超集」声明（必须写进实现注释）

`covered` 里的 A 组内容**多数情况下并不是模型看到的字节**（模型只看到 `prompt`）。它进指纹的理由只有一条：`video_prompt` 为空时 `fallbackVideoPrompt` 就以这些字段为原料（`tools.js:2467`），且用户预期「改了台词，旧视频就该算旧」。因此：

- **单调性保证**：任何真正喂给模型的东西变了，必然改变该 Hash（`prompt`/`media`/`exec`/`output` 都在）；
- **反向不成立**：Hash 变了不代表模型输入变了（可能只是 `covered` 变了）；
- 该 Hash 的语义是「**渲染时刻的段输入版本**」，不是「模型输入字节指纹」。比较只用于相等判定，不用于声明「这份视频由这些字节生成」——后者由 `media[].sha256` 与 `prompt` 两段子数据承担（排障时按字段展开即可）。

三处禁令（沿用 D02-30 §4.7 并加一条）：① 禁止 `finalizeShot` 回读再算；② 禁止把 `seed` 放进指纹；③ 禁止候选创建失败时补写事后指纹；④ **禁止把 Hash 当「模型输入证明」对外展示**（它会因 `covered` 变化而变，展示会误导「输入变了」）。

### 3.9 B-30-8 的口径（不落地，只定替换关系）

`tools.js:3414` 现用 `(s.video_prompt_used||'') !== (s.video_prompt||'')` 判「需重渲」。D-30-05 停写 `video_prompt` 后：

| 判据 | 现在含义 | 替换后含义 |
|---|---|---|
| `video_prompt_used !== video_prompt` | 提示词改过 ⇒ 重渲 | **保留**，语义收窄为「提示词改了」 |
| `selected.input_hash !== segmentInputHash(段)` | 不存在 | **新增**，语义为「输入版本变了」 |

两者**不可互相替代**：前者便宜（纯字段比较）、能覆盖「提示词改了但还没重渲」；后者贵（要读文件算 Hash）、能覆盖「资产换图/换工作流/改项目宽高」。整章生成的筛选条件必须是**两者或**，且必须先过一个廉价短路（先比字段，相等才去算 Hash），否则一次整章生成会把每个镜的文件都读一遍。

## 四、Agent 单镜更新契约（任务二 · 关闭 B-30-1）

### 4.1 三条现状事实

| 事实 | 依据 | 后果 |
|---|---|---|
| `update_shot` 只认 `shot_id`，直接 `Shots.update(args.shot_id, patch)` | `tools.js:252`（schema）、`tools.js:2357` | 在结构化项目里 `shot_id` 只能是段 id（`Shots.list` 按段返回），A 组字段无处落 |
| `update_shot` 的 patch 白名单**同时**含 A 组与 B 组键 | `tools.js:252` 的 properties | 一次调用可能同时要写两个实体 |
| Agent 拿不到任何 `story_shot_id` | 全仓无读取工具返回 `story_shots` 行 | 即使加了参数，Agent 也无从取值 |

### 4.2 唯一方案：加一个可选参数 + 加一条读侧返回

**不保留「禁用单镜更新」作为并列选项**——它会让结构化项目的 AI 创作能力直接消失，与新项目默认结构化（`project-create.js:19`）冲突。

| 元素 | 定义 |
|---|---|
| `shot_id` | **保持今天含义**：段行 id（`shots.id`）。旧链路、旧 Agent 提示词、旧测试全部零改动 |
| `story_shot_id` | **新增可选参数**：`story_shots.id`。只在 `structured_spec=1` 下被接受 |
| 读侧 | `get_shot` / 分镜列表在结构化项目下返回 `story_shots: [{ id, global_no, idx, ... }]`（只读投影，无 DDL） |

### 4.3 参数与字段的判定矩阵

| 本批字段 | `=0` | `=1` 且无 `story_shot_id` | `=1` 且有 `story_shot_id` |
|---|---|---|---|
| 只含 A 组 | 允许（`Shots.update`） | **拒** `STAGE3_SHOT_ID_REQUIRED` | Stage 3 写入器 |
| 只含 B 组 | 允许 | 允许（`ShotParams.update`，段级，不需要镜） | 允许（同上，`story_shot_id` 忽略但记录） |
| A + B 混合 | 允许 | **拒** `STAGE3_SHOT_ID_REQUIRED` | 同一事务：Stage 3 → 投影 → 参数 |
| 只含 C/E 组 | 拒（既有行为） | 拒 | 拒 |
| 传了 `story_shot_id` 但 `=0` | **拒** `STAGE3_NOT_ENABLED` | — | — |
| `story_shot_id` 不属于该段 | — | — | **拒** `STAGE3_SHOT_NOT_IN_SEGMENT` |

三条纪律：

1. `=0` 下传 `story_shot_id` 必须**报错**，不得静默忽略。静默忽略会让「结构化没生效」这件事被藏起来，排查时只能靠猜。
2. `=1` 下 A 组缺 `story_shot_id` 必须**报错**，不得回退成「整段第一条镜」。回退会静默改错镜。
3. 两处报错都要带**可执行提示**（「先调 get_shot 取 story_shots[].id」），否则模型只会重试同一个错。

### 4.4 事务边界与失败回滚

```
tx(() => {                      // 单个 tx，deferred BEGIN → 由 D-30-13 升级为 BEGIN IMMEDIATE
  ① Stage 3 写入（story_shots 行）
  ② projectRenderUnits(segmentId)   // 整段重投影，只写 A 组
  ③ ShotParams.update(segmentId, 本批 B 组键)
})                              // 任一步抛错 → 整体回滚
```

| 问题 | 答案 |
|---|---|
| 为什么必须同一事务 | ②失败 ⇒ ①的内容成为「Stage 3 有、投影没有」的半截状态，界面上看不到刚改的内容 |
| 为什么 ③ 也在里面 | ③失败（如图路径越界）必须连带撤销 ①，否则用户看到「台词改了但 mode 没改」 |
| `tx()` 能包住吗 | 能：三步全是同步 SQL；`tx()` 禁 async（既有约束），而 Stage 3 写入器与 `ShotParams.update` 都是同步方法 |
| 失败如何回滚前面的 Stage 3 更新 | 不需要手工补偿：单事务原子回滚。这也是为什么不能把 ② 做成异步（投影一旦异步就必须引入补偿事务） |
| 投影失败能不能降级 | 不能。投影是「段行是派生」这一不变式的唯一维护者，允许它失败而不回滚，等于允许派生数据说谎 |

### 4.5 一镜多段 / 一段多镜

| 情形 | 是否可能 | 处置 |
|---|---|---|
| 一个镜属于多个段 | **不可能**：`story_shots.segment_id` 是单值列（D-30-01） | 无需处理 |
| 一个段覆盖多镜，改其中一镜 | 可能 | **整段重投影**：段级字段是聚合（`sub_shots`/`dialogue` 按 global_no 拼接，`duration` 求和，`blocking` 取段首镜），改一镜必然改变聚合结果 |
| 改镜导致该段覆盖镜集合变化（插入/删除） | 可能 | 同上，且段行 `idx` 可能整体位移；旧候选靠 `input_hash` 变旧，不改挂 |

### 4.6 旧链路保证（不得破坏）

| 保证 | 手段 |
|---|---|
| `structured_spec=0` 的既有 Agent 调用零改动 | `shot_id` 语义不变、`story_shot_id` 缺省、字段白名单不变 |
| 既有 17 条失败用例不因本轮增减 | 本轮零代码；实现时以「17 条同名同因」为回归标尺 |
| `update_shot` 对 `video_prompt` 的占位符拦截保留 | `tools.js:2351~2356` 不动 |

### 4.7 被否决的三案

| 方案 | 否决理由 |
|---|---|
| 让 `shot_id` 在结构化下改指 `story_shots.id` | 同名不同义是最坏的兼容方式：旧 Agent 提示词、旧日志、旧测试全部静默改义，且 `Shots.get(shot_id)` 会返回 null 而无从解释 |
| 禁用结构化项目下的单镜更新 | 新项目默认结构化 ⇒ 等于砍掉 AI 单镜改稿能力 |
| 用 `global_no` 或「段内第 N 镜」定位 | 不是主键：重编号（两阶段重编号已在 P0~P6 落地）后编号会变，Agent 手里的旧编号会指错镜 |

## 五、回滚与候选生命周期（任务三 · 关闭 B-30-2 / B-30-3）

### 5.1 结构化项目内容回滚：长期产品边界，不是临时限制

**结论：结构化项目（`structured_spec=1`）不支持内容回滚，回滚路由返回 409。这是长期边界。**

| 理由 | 依据 |
|---|---|
| 回滚实现是**整行复原**，绕过一切服务层门禁 | `changelog.js:263` 的 `INSERT OR REPLACE INTO <table> (全列)` |
| 复原投影派生行会让派生数据说谎 | 段行 A 组是投影产物；单行复原等于用旧快照推翻 Stage 3 现状，且不触发重投影 ⇒ 「段行说 A、镜表说 B」 |
| 复原会绕过 B 组写入口 | `ShotParams.update` 的白名单是唯一合法写者；整行复原能一次写回 `video_prompt`+`mode`+三张图 |
| 「临时限制」需要退出条件，而这里没有退出条件 | 除非重写回滚为「按字段组、按实体、带重投影」的版本恢复系统，否则永远不成立 |

**但审计必须保留**（推翻 D-30-07 第 6 条）：

| 项 | D02-30 | 本轮 |
|---|---|---|
| `ShotParams.update` 是否写 `change_logs` | 不写 | **写** |
| 理由 | 「内容回滚未定义」 | ① B 组 5 列不在 `VOLATILE.shot`（`changelog.js:65`），本来就是内容；② `recordChange` 内部已做内容变化判定（`changelog.js:128`），无变化不落行，体积可控；③ 不写会造成「旧链路改 `video_prompt` 有审计、结构化没有」——权限收紧反而丢了可追溯性 |
| 回滚 | — | 仍 409（D-30-15）。审计用于**取证**，不用于自动恢复 |

### 5.2 六类实体的审计与恢复路径

### 6.1 激活不是开关，是「建项目即生效 + 空态合法」

真实库统计（D02-30 附录 B，副本只读）：14 个项目全部 `structured_spec=0`，Stage 3 各表 0 行。结合代码：

### 6.2 五个激活问题

| # | 问题 | 答案 |

| 1 | 项目何时成为结构化项目 | **创建那一刻**（`createUserProject` 默认 true）。不存在「先旧后转换」的激活步骤 |

### 6.3 上线顺序（必须写进 P10-A 任务书，且不可调换）

```

S3  shot_videos.input_hash 列 + seg-2 计算 + 候选落库

```

### 6.4 回退：仅运维脚本 + Stage 3 必须为空

| 项 | 定义 |

### 6.5 为什么不能「有数据也降级」，也不能只给一个开关

| 做法 | 后果 |
|---|---|
| 有数据仍降级 | ① Stage 3 数据变成无人读的僵尸（关开关不删数据，`structured-spec.js:26` 注释明确）；② 用户在旧链路改了一大轮；③ 重新开启时投影把旧 Stage 3 内容盖回 `shots` ⇒ **静默覆盖用户改动** |
| 只提供 `setStructuredSpec` 开关 | 就是今天的状态：函数齐备、无路由、无前置检查、无 UI ⇒ 谁都能调，谁都不知道调用后会发生什么。任务书明确要求不得以此作为回退方案 |

因此回退方案＝**脚本 + 空表前置 + 审计**，三件缺一不可。重新开启（`=0 → =1`）同样只走脚本，且必须校验 `shots` 自降级后未被改动（用 `change_logs` 时间戳与 `shots.updated_at` 判定），否则拒绝。

### 7.4 `Shots.update` 的三态语义（修正 D02-30 的错误陈述）

**今天的真实行为**（`db.js:987` 的 `{...s, ...fields}` 加 `db.js:995~999` 的 `??` 兜底）：

| 传入 | 结果 | 说明 |
|---|---|---|
| 键**不出现** | **保留旧值** | spread 不会覆盖 |
| `key: undefined` | **落默认值**（TEXT→`''`、`duration`→5、`status`→`'pending'`、`seed`→0） | spread 覆盖成 undefined，`??` 兜底 |
| `key: null` | 同 `undefined` | `??` 对 null 同样兜底 |
| `key: ''` | 写入 `''` | 显式清空 |
| JSON 数组列传 `null` | **保留旧值** | `Array.isArray(null)===false` ⇒ 回退到 `s[k]` |

所以 D02-30 §7.3 末尾「这条与现状不同（现状 `undefined` 会清空）」应改为：**「现状是『键缺失保留、显式 undefined/null 落默认』；新方案要求『键缺失不写、null 视为非法、`''` 才算清空』」**。

**部分列 UPDATE 的最终语义**（必须显式实现，禁止再用 `??`）：

| 值 | 语义 | 备注 |
|---|---|---|
| 键不出现 | 不写该列 | 唯一的「不动」表达 |
| `''` | 清空该文本列 | 与今天一致 |
| `null` | **抛 `BAD_FIELD_VALUE`** | 禁止用 null 表达清空：`null` 与 `undefined` 在 JS 里太容易混，且今天 null 会静默落默认值（`status` 被重置为 `'pending'` 是危险行为） |
| `undefined` | 视同键不出现 | 与「键缺失」对齐，避免 `{...patch}` 里的空键意外清列 |
| 数值列 `0` | 写入 0 | 不得用逻辑或兜底（会把 0 吞成 fallback） |

这一条与 `status` 尤其相关：今天任何带 `status: null` 的 `Shots.update` 都会把状态重置成 `pending`，而 `status` 是流水线状态。改部分列必须顺手堵掉这条。

### 7.5 `POST /shots` 复合入口的三步事务

```
POST /api/projects/:id/shots（含 ?insert_at=）
└─ structured_spec=1：
   tx(() => {
     ① story_shots 插入一条（A 组内容）
     ② projectRenderUnits() 为该段建/更新段行；insert_at 时在该步内完成段内 idx 位移
     ③ ShotParams.update(段 id, { mode, first_frame_path, last_frame_path, reference_image_path })
   })  → 返回段行 id（不是 story_shot id）
└─ structured_spec=0：今天行为不变（Shots.create / Shots.insertAt）
```

| 约束 | 内容 |
|---|---|
| 事务 | 单 `tx()`，三步任一失败整体回滚 |
| `insert_at` | 只影响 `shots.idx` 的段内位移，在 ② 内完成；`story_shots` 侧不参与 |
| 返回 | 段 id（前端后续 PATCH 用段 id + `story_shot_id`） |
| 拒绝 | 结构化下**不允许**只写 `story_shots` 不建段（会出现「镜有、段无」的不可见内容） |
| 与 H-01 的关系 | H-01 的「拒绝裸建」是门禁，本入口是唯一合法替代路径 |
