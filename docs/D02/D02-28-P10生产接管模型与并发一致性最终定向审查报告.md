## 三、问题一：生成段与创作镜头的身份模型

### 3.1 五种身份必须分开

| 身份 | 载体 | 今天谁生成 | 稳定性 |
|---|---|---|---|
| 创作镜头 | `story_shots.id` | `insertStoryShot()`（`global-no.js:220`），**生产 0 调用** | 创作期稳定 |
| 生成段 | `shots.id` | `Shots.create()` → `uid()`（`db.js:950`） | 长期稳定（一旦生成就有产物挂在下面） |
| 生成任务 | `queue_items.id`（+ `jobs.id`） | `Queue.enqueue()`（`db.js:1229`） | 一次性 |
| 视频候选 | `shot_videos.id` | `ShotVideos.create()`（`db.js:1022`） | 长期保留 |
| 最终选片 | `shot_videos.selected=1` + `shots.video_path` 快照 | `setSelected()` + `Shots.update()`（`videos/[vid]/select/route.js:16~17`） | 可变 |

### 3.2 真实 ID 链（源码还原，不是示意图）

      ⋮  (今天不存在任何映射)

【源码确认】`queue_items.payload` **不携带 shot_id**：入队只传 `{...opts.payload, chapter, subject}`（`scheduler.js:399`），镜的定位靠 `dedupeKey` 字符串与 `unitId`（`tools.js:2513` 的 `'shot:'+shot.id+':cand:'+idx`）。
【源码确认】候选视频写 `ShotVideos.create(projectId, shot.id, ...)`（`tools.js:2519`）——**产物永远挂生成段，不挂创作镜头**。

结论：`story_shots.id` 与 `shots.id` 之间**今天没有任何一条数据库关系**。所谓「生成段」当前只是「legacy 的一行 `shots`」，与哪几条创作镜头对应，只在人的脑子里。

### 3.3 四个候选方案

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 复用 `shots.parent_shot_id` | **否决**。① 它是**死列**（零生产者零读者）；② 单指针只能表达 1:1，而 `1 段 = n 镜` 是硬需求；③ 名字语义是「父镜」，与「段↔镜」不同层，复用会让后来者按字面误解 |
| B | 新建 M:N 关联表 `segment_shots(segment_id, story_shot_id, order_no)` | **否决**。关系实际是 1:N（一镜同一时刻只属一段），M:N 表会允许「一镜属两段」这种非法态；且多一张表、多一处写入口 |
| C | **`story_shots.segment_id`（1 列 + 1 索引）** | **推荐**。多的一端放 FK，标准做法；分组查询是一次 `GROUP BY`；段身份仍是 `shots.id`，`shot_videos`/`queue`/`video_path` 全部零改动 |
| D | 强制 1:1（`shots.id = story_shots.id`） | **否决**。`story_duration` 2.5–7.5s vs 模型单段最小 4s，1 镜 1 段必然产出超短段；D02-27 已判不可行 |

### 3.4 唯一推荐：`story_shots.segment_id`

**【建议方案】**
- 新增列：`story_shots.segment_id TEXT DEFAULT ''`，索引 `idx_ss_segment(segment_id)`。
- 段身份 **仍然就是 `shots.id`**，不新造第二套 id；`segment_id` 的值域 = `shots.id` 值域。
- 一镜一段：`segment_id` 非空即表示该镜已进入某个生成段；空串 = 尚未投影（新写入的镜）。
- 段的组成顺序 = 组内 `global_no` 升序，不另存 order 列。

**为什么不新造段 id**：`shot_videos.shot_id`、`queue_items.dedupe_key`、`shots.video_path`、27 处 `Shots.list` 全都以 `shots.id` 为准。新造一套再映射，等于把 5 个消费方全改一遍，收益为零。

**为什么放在 `story_shots` 而不是 `shots`**：`shots` 若放 `covered_shot_ids` 就只能用 JSON 数组（D01 明确警惕），且「一镜属哪段」变成字符串匹配；放多端是唯一规范做法。

### 3.6 「旧视频不得错挂」的证明

三个动作分开看：

1. **改序**：只改 `global_no` 与 `idx`，若段分组不变则 `segment_id` 不变 ⇒ 视频仍挂原段，且段内镜集不变 ⇒ 视频内容对应关系不变。**不错挂。**
2. **某镜移出段 A 进入段 B**：投影只改该镜的 `segment_id`；`shot_videos` 行的 `shot_id` 指向段 A 的 `shots.id`，**没有任何 SQL 会改它**（`ShotVideos` 无 update 路径，只有 create/remove/setSelected）。⇒ 旧视频留在 A，不会跑到 B。**不错挂，但 A 的视频已不覆盖当前镜集 ⇒ 见第 3 条。**
3. **段内容变了**：需要「过期」判定，否则「A 的视频被当成当前镜集的成片」。

**过期判定的唯一推荐【建议方案】**

- **复用现有锚点**：`video_prompt_used ≠ video_prompt` 已是既有的「提示词变了要重出」信号（`tools.js:3414`、`stages.js:184`），且 `video_prompt` 由创作字段生成 ⇒ 台词/构图/景别一变，重跑提示词阶段就会命中。
- **已知缺口**：只改 `blocking`/`*_ids`（资产绑定）而提示词未重写时，无信号。两个选项：
  - 选项 1（0 DDL，推荐先用）：投影在检测到「段内任一镜的 A 组内容变化」时，把该段的 `video_prompt` 置空 → 下一步必然重写提示词 → `video_prompt_used ≠ video_prompt` 成立。代价：丢失旧提示词文本（但 `video_prompt_used` 仍保留上一版，可追溯）。
  - 选项 2（1 列 DDL）：`shots.segment_content_hash`，投影写入 A 组摘要，生成时比对。语义最干净，代价是多一列且要 bump 一次全量（只影响 `shots` 侧比对，不影响求解 Hash）。
- **推荐先选项 1**，把选项 2 登记为 U-28-2。

## 四、问题二：并发协议

### 4.1 三个决定性事实

1. **【源码确认】PG 是「单连接 + 同步门面」**：`PostgresDriver` 只有一个 `pg.Client`（`pg-worker.mjs:43`），主线程通过 `Atomics.wait` 串行等待（`db-driver.js:170` 附近）。⇒ **同进程内不存在真正的并发事务**；并发只来自**多进程/多实例**。
2. **【源码确认】`tx()` 是 deferred `BEGIN`**（`db.js:483`），且**嵌套会被拍平**（`txDepth>0` 直接执行，`:482`），**拒绝 async 回调**（`:487`）。
3. **【源码确认】绝大多数写入方根本不在事务里**：`Shots.update()` 直接 `prepare().run()` 自动提交（`db.js:997`）；`Assets.update()` 同理。⇒ 求解事务读到的快照与它提交时的库状态之间，写入方可自由插队。

**结论**：今天能破坏求解一致性的写入方集中在三处——`assets`（含 Agent 侧 20+ 调用点）、`scene_states`、以及 P10-A 之后的 `story_shots`/`shot_assets`。它们**全都不在事务里、都不知道场次**。

### 4.3 三方案比较

| 方案 | 机制 | 能否闭合 | 评价 |
|---|---|---|---|
| A | **项目级 advisory lock，所有源写入方 + 求解提交方共享** | 能 | **推荐**。单锁键 ⇒ 无死锁排序问题；资产是项目级资源，天然属项目锁；写入是单行短事务，持锁时间毫秒级 |
| B | 场次级锁 + 资产按引用场次集合加锁 | 能，但复杂 | 否决。一个资产可被 N 个场次引用 ⇒ 写入方需锁 N 把锁并规定排序，锁数随规模增长，死锁风险靠纪律维持 |
| C | SERIALIZABLE + 冲突重试 | PG 能，SQLite 无此隔离级 | 否决。两端语义无法统一；且 SSI 只在一方 abort 时才暴露冲突，重试逻辑要覆盖所有写入方（比加锁改动更大） |

### 4.4 唯一推荐：项目级 `txLocked`

**【建议方案】**

```
写入方：txLocked(projectId, fn)
  SQLite : BEGIN IMMEDIATE  → fn() → COMMIT      （单写锁，天然排他）
  PG     : BEGIN; SELECT pg_advisory_xact_lock(hashtext('ic:'||projectId)); → fn() → COMMIT

求解方：runSceneQuality()
  1. 事务外：读快照 A、算 solverInputHash(A) + qcDependencyHash(A)、求解
  2. txLocked：重读全部指纹字段 → 重算两个 Hash
       不等 → throw CONTINUITY_INPUT_CHANGED（回滚，0 写入）
       相等 → 写 shot_states + qc_reports（+ continuity_runs）
  3. COMMIT
```

**为什么第 1 步可以在锁外**：求解是纯计算，不写库；把长计算关在锁里会让所有写入阻塞。正确性由第 2 步的「锁内重算」保证——**锁内看到的快照就是提交依据**。

**为什么锁必须覆盖写入方**：反例正是任务书 §3.1 给的——求解方重读完、未提交，写入方提交了资产改名，求解方随后提交基于旧名的 QC 结论。若写入方也拿同一把锁，这个提交会被挡在求解事务之外（或在求解之后，届时状态已带旧指纹、并由 `hash_relation` 与 P10-D 的触发机制处理）。

**提交后写入的语义（必须写清，不能含糊）**：写入方在求解提交**之后**提交时，`shot_states` 里那份结论**反映的是旧输入**，但它带着 `meta.__solver.hash` 这个旧指纹 ⇒ 任何读者先比指纹再信任结论（`hash_relation='state_older'`）。⇒ 不变量不是「状态永远最新」，而是「**结论永不冒充它没算过的输入**」。

**锁参数**

| 项 | 值 | 理由 |
|---|---|---|
| 锁粒度 | 项目级 | 资产是项目级；单键无死锁 |
| 锁键 | `hashtext('ic:' || project_id)` | `hashtext` 返回 int4，正好是 advisory lock 的参数类型 |
| 等待上限 | PG `SET LOCAL lock_timeout='5s'`；SQLite `busy_timeout=5000`（已是现状，`db-driver.js:69`） | 超时映射 `CONTINUITY_LOCK_TIMEOUT`（可重试），不当作业务失败 |
| 持锁范围 | 只包「重读指纹 + 写状态 + 写报告 + 写运行记录」 | 毫秒级 |
| 释放 | 事务结束自动释放（`_xact_` 版本） | 崩溃即释放，无需清理 |

**必须参与锁的写入方（P10-A/B2 落地清单）**：`Shots.create/update/remove/insertAt`、`Chapters` 改名联动、`Assets.create/update/remove`、`upsertSceneStates`、`insertStoryShot`/`appendStoryShots`、`writeShotAssets`，以及 §6.3 里的 4 处直写 SQL。**`shot_videos` 与 `queue_items` 不需要**（它们不改求解输入）。

**一处必须提前说明的边界【代码推断】**：`Assets.update` 在 Agent 侧被调用 20+ 次，其中多数是长任务（画图/配音）完成后的回写。给它们全部套 `txLocked` 会让每次回写都与该项目上的求解互斥——**语义正确，但把两类长流程耦合了**。缓解：这些回写是单行 UPDATE，持锁只在 UPDATE 那一刻；`txLocked` 内**不得**放 `await`（`tx()` 已强制同步，`:487`）。

### 4.5 SQLite 与 PG 对照

| 维度 | SQLite | PostgreSQL |
|---|---|---|
| 事务开始 | `tx()` = `BEGIN`（deferred）；**求解提交必须用 `BEGIN IMMEDIATE`** | `BEGIN` + advisory lock |
| 写入方是否必须显式拿锁 | **不必**：单写者 + 求解方持写锁 ⇒ 自动排队 | **必须**：否则窗口仍在 |
| 锁冲突表现 | `SQLITE_BUSY`（busy_timeout 5s 后） | `lock_timeout` 触发 `55P03` |
| 嵌套事务 | `txDepth` 拍平，内层不 BEGIN | 同（驱动层无保存点） |
| 异步回调 | 禁止（`ASYNC_TX`） | 禁止（同） |
| 多进程 | WAL 允许并发读，写仍串行 | 真并发，靠 advisory lock |
| 今天是否有外部写入进程 | 【待确认】需核对是否有第二个 Node 进程/脚本直连 `data/ic.db` | 同 |

**`BEGIN IMMEDIATE` 不能发给 PG**【源码确认】：`db-driver.js:139` 的 `call()` 把 SQL 原样转发（仅做 `?`→`$n` 与 DDL 类型翻译），PG 收到 `BEGIN IMMEDIATE` 是语法错误 ⇒ 必须按 `db.dialect` 分支。

### 4.6 资产并发

## 五、问题三：`scene_uid` 的改名语义

### 5.1 D02-27 的矛盾是真的

- 【源码确认】`upsertSceneStates`（`scene-state.js:138`）**只按 `(project_id, scene_key)` 定位**：`SELECT * FROM scene_states WHERE project_id=? AND scene_key=?`；唯一索引 `uq_scene_state(project_id, scene_key)`（`tables.js:382`）。
- ⇒ 若把场次改名（新 key）再 `set_scene_state`，走的是 `!existing` 分支 → `uid()` 新建 → **新身份**。这与「uid 不可变」直接冲突。
- 【源码确认】今天**根本没有改名 API**（`app/api/projects/[id]/` 下无 `scenes` 路由）；场次只能经 Agent `set_scene_state`（`tools.js:629`）。所以「改名 = 换身份」是当前**唯一**行为，且是隐藏行为。

### 5.2 唯一推荐：`scene_uid` 优先、`scene_key` 降为可改属性

**【建议方案】**

1. `upsertSceneStates` 增加可选 `scene_uid`：
   - 给了 uid → 按 `id` 定位；命中即更新（含 `scene_key` 若变）；未命中 → 抛 `SCENE_UID_NOT_FOUND`（**不自动建**）。
   - 没给 uid → 保持今天的 `(project_id, scene_key)` 行为（仅用于新建）。
2. 改 key 的守卫：目标 key 已被**另一个 uid** 占用 → 抛 `SCENE_KEY_TAKEN`（沿用 `SCENE_KEY_DUPLICATED` 的口径，不复用同一个码以免混淆「批内重复」与「跨行占用」）。
3. 优先级：**uid 优先**。同时给 uid 与 key 且 key 与库里不同 ⇒ 视为改名（合法）；同时给且 key 属于另一行 ⇒ `SCENE_KEY_TAKEN`。
4. `scene_key` 仍要求**项目内唯一**（保留 `uq_scene_state`）；改名即改唯一键，同一事务内完成。
5. 旧参数兼容：只给 key 的调用继续工作（今天所有调用都属于这类），但**语义降级为「按 key 匹配或新建」**——即老调用方仍然会在改名时造新身份。兼容办法：Agent/Skill 在 `structured_spec=1` 下必须带 uid（P10-A 改 `set_scene_state` 的入参契约）。
6. 历史可追溯：`shot_states`/`qc_reports` 不存 `scene_key`（`shot_states` 按 `shot_id`，报告按 `target_id`）⇒ 改名不影响它们的关联；**只有 `continuity_runs` 存 `scene_key`**（§7.2）。

### 5.3 生命周期契约（冻结）

| 操作 | `scene_uid` | `scene_key` | 镜头关系 | 历史状态与报告 |
|---|---|---|---|---|
| 创建场次 | 新建 `uid()` | 新建 | 新镜 `scene_uid` 指向它 | 无历史 |
| 改场次名 | **不变** | 更新 | 不变 | 不变（按 `shot_id` 关联，与 key 无关） |
| 改业务键（key） | **不变** | 更新（唯一性重校验） | 不变 | 不变 |
| 场次移动（换章） | **不变** | 不变 | `story_shots.chapter_id` 变 | 需重算（`chapter_id` 不在求解 Hash 内，但章节影响 `chapterShots` 上下文 ⇒ **触发本场重算**） |

| 场次合并 | 保留一方 uid | 统一为保留方的 key | 被并方镜头改指向保留方 | 被并方历史**保留但不再有新结论**（自然失效） |

### 6.3 服务层门禁：现在拿不到「原始字段集合」

【源码确认】`Shots.update(id, fields)`：
- 第一行 `const s = this.get(id)` 读整行，然后 `const m = { ...s, ...fields, updated_at: now() }`（`db.js:987`）——**原始意图在合并瞬间丢失**，后面的 32 列 UPDATE 无法区分「调用方写了」与「沿用旧值」。
- ⇒ 想在 `Shots.update` 内部按字段组拦截，**做不到**。必须改调用方式。

**【建议方案】最小接口改造（P10-A）**

1. `Shots.update(id, fields, { writer })`，`writer ∈ {'creative','render','system'}`，**必填**（不填按 `'creative'` 处理并计数，便于迁移期发现漏改）。
2. 门禁表：`writer='render'` 只允许 C 组 6 列；`writer='creative'` 在 `structured_spec=1` 下**整调用拒绝**（`SHOT_CREATIVE_WRITE_FORBIDDEN`）；`writer='system'` 只允许 `updated_at`/`parent_shot_id`。
3. `insertAt` 内部对既有行做的 `update(..., {idx})` 传 `'creative'`（它确实改创作顺序）。
4. `create` 增加同样参数：`structured_spec=1` 下 `'creative'` 拒绝，只有投影可以 `'system'` 建行。
5. `shot-write.js` 白名单**不冲突**：它是「外部 API 能收什么」，比服务层宽（收了 `video_prompt`/三个 `*_path`）；服务层是「谁能写什么」，更严。二者是两层，不是一套（`pickShotFields` 只用于 HTTP 入口，`tools.js` 有自己的参数校验）。

【源码确认】`shot-write.js` 的注释（第 3~4 行）明确 `status/error/video_path/video_prompt_used/prompt_id` 是「生成流水线产物，外部写入必须拒绝」，且 `seed` 被显式排除（第 20~26 行）。**这份口径可以直接作为 §6.2 分类的独立旁证**：它把 6 个产物字段中的 5 个 + `seed` 全都划成产物。

### 6.4 `audio_ids` 的分流（承接 D02-26 决策三，此处只补事实）

【源码确认】`set_storyboard` 把 `voice/music/sfx` 三类资产**合并**成 `audioMap` 写入 `audio_ids`（`tools.js:2171~2172`、`:2249`）。
⇒ `audio_ids` 里确实混着 music/sfx，而 `shot_assets.role` 值域只有 6 项且 AS-4 禁止 music/sfx 入内。**投影时必须分流**：`category='voice'` → `shot_assets(role='voice')`；`music`/`sfx` → 只保留在 `shots.audio_ids` 与 `story_shots.voice_ids` 之外（`story_shots` 只有 `sfx`/`music_cue` 两个文本列，**不承载资产引用**）。

## 七、问题五：`continuity_runs` 与 PF-1

### 7.1 规范原文关键点【正式规范 D02-06 §8.2.4】

- 8 列：`id` / `project_id` / **`scene_key`** / `run_no` / `input_hash` / `status`（`ok`/`failed`）/ `error_code` / `created_at`。
- 索引 2 条：`UNIQUE(project_id, scene_key, run_no)`、`INDEX(project_id, scene_key, run_no DESC)`。
- 写入时机：成功 → 与 `shot_states` **同事务**；失败 → **单独短事务立即提交**；同输入重跑 → 新行 `run_no+1`。
- RC-1：`run_no` 分配在事务内（SQLite `BEGIN IMMEDIATE`，PG 行锁或 `INSERT..SELECT MAX+1 FOR UPDATE`）。
- RC-6：**不得**扩展成任务调度/重试子系统；没有队列、没有状态机、没有定时补偿。
- PF-1：该表属冻结 DDL 之外的运维表，**须审核方批准**，且「**必须在 P9 之前落定**」。

### 7.2 与 `scene_uid` 的冲突（必须裁决）

【正式规范】冻结列名是 `scene_key`；【建议方案】身份改为 `scene_uid`。
两者不可同时为真：改名后 `scene_key` 变，按 `scene_key` 查运行记录会「查不到历史」。
**处置**：该表**尚未创建**（`tables.js`/`db.js`/manifest 全 0 命中）⇒ 建表时直接用 `scene_uid`（列名与索引一并改），**代价只是修订 §8.2.4 的列名**，不涉及任何数据迁移。此事须批准（D-28-E）。

### 7.3 状态值与「崩溃可见性」

| 情形 | 库里能看到什么 | 是否可审计 |
|---|---|---|
| 未启动 | 无行 | — |
| 求解中（尚未提交） | 无行 | **与「未启动」不可区分** |
| 求解中崩溃 | 无行（进程没机会写） | **不可审计** |
| 成功提交 | `status='ok'` | 是 |
| 正常失败提交 | `status='failed'` + `error_code` | 是 |
| 已提交但响应丢失 | 有行（客户端看不到） | 是（客户端重查可见） |
| 提交后被新运行超越 | 旧行仍在，`run_no` 更小 | 是（「最新」只认 `run_no` 最大） |

**必须如实写明的边界**：D02-27 的「不设 running ⇒ 崩溃=无记录」在**记录语义**上正确，但**不能**由此得出「崩溃已被记录」。§8.2.5 的三态判定（`unknown`/`degraded`/`available`）恰恰是为了让这种「能力缺失」与「数据缺失」可区分——而 `probeContinuityTracking()` **今天不存在**。

### 7.4 PF-1 结论：**尚未满足**

| 判据 | 状态 | 证据 |

**⇒ 按 §8.2.5，当前所有「期望 `qc_validity='current'`」的结论都不可达。** 本轮**不追认** P9 已完成该项能力；也不宣称 `degraded` 是「已实现」（连 `degraded` 的判定代码都不存在）。

### 9.3 一项必须提前说清的依赖

`story_shots.segment_id` 与 `scene_uid` 是**同一份 DDL 申请**（2 列 + 2 索引），但两者语义独立：
- `scene_uid`：身份 → 影响路由与报告关联，**不进求解 Hash**；
- `segment_id`：产物分组 → 影响投影与生成，**不进求解 Hash**。

【源码确认】两者都不会自动进 Hash，因为 `SOLVE_SHOT_FIELDS` 是 7 列**白名单**（`solve-hash.js:154~156`：`id`/`global_no`/`scene_key`/`time_jump`/`spec_source`/`spec_version`/`fill_confidence`）。⇒ **不需要 bump `HASH_ALGO_VER`、不需要全量重算**。这直接推翻 D02-27 §12 的「bump 两版本 + 全量重算」。
