## 二、阶段 3 目标与边界

### 2.1 目标（可判定）

新项目（`structured_spec = true`）能够完成：

1. 读源文件 → 按章建立结构化分镜（`story_shots`）。
2. 为每镜补摄影机 14 字段、构图、光影、时间切片。
3. 为每镜建立结构化人物动作（T1/T2/T3 三档）。
4. 为每镜建立逐人站位与空间关系。
5. 求解镜间连续性状态（`state_in` / `state_out`）。
6. 程序执行确定性校验（不靠 LLM 自述）。
7. 校验结果落 `qc_reports`。
8. 提供结构化读接口 `GET .../shots-structured`。
9. 旧项目（`structured_spec = false`）行为**零变化**。

## 三、★P0 前置门槛：测试环境隔离

**没有通过本节，本节之后的任何"跑测试"动作都禁止执行。** 这不是"顺手改个脚本"，它是阶段 3 能不能安全开工的前提。

### 3.1 要做成什么

| # | 要求 | 实现方式 |
|---|---|---|
| T-1 | 测试入口自动创建临时数据目录并注入 `IC_DATA_DIR` | 新增 `scripts/test/run-tests.mjs`：`fs.mkdtempSync(os.tmpdir()+ic-test-)` → 写入 `process.env.IC_DATA_DIR` → `spawnSync(process.execPath, ['--test','--test-force-exit', ...files], {env, stdio:'inherit'})` |
| T-2 | `IC_DATA_DIR` 必须早于业务模块加载 | 由上：包装器在**子进程**里设 env，子进程内测试文件的 `import` 一律晚于 env 生效；测试文件自身**不再**依赖"我第一行设了 env"这条约定 |
| T-3 | 运行器必须校验实际库路径，拒绝默认真实库 | 包装器内 `assertEnv()` + `assertDbIsolation({dataDir, dbPath})`（复用 `lib/core/env-guard.js`，阶段 0 已验证）；`dbPath` 取 `dbSettings().sqlitePath` 的**真实路径**，不是 env 字符串 |
| T-4 | 不允许清空/初始化/写入真实库 | T-3 通过后 `realpath(dbPath)` 必在临时目录内；包装器再断言"不在 `<repo>/data` 内"（双保险，同 `rollback-stage1.mjs` 的 ④） |
| T-5 | 至少一条负向测试：未设安全目录 → 拒绝启动 | 新增 `tests/stage3-isolation.test.mjs`：① 不设 `IC_DATA_DIR` 直接 spawn 一个会 `getDb()` 的探针 → 断言退出码非 0 且输出含 `IC_DATA_DIR_NOT_SET`；② 设成 `<repo>/data` → 断言 `IC_DATA_DIR_IS_DEFAULT`；③ 设成相对路径 → 断言 `IC_DATA_DIR_NOT_ABSOLUTE` |
| T-6 | `package.json` 的 `test` 指向包装器 | `"test": "node scripts/test/run-tests.mjs"`；保留 `"test:raw"` 指向原始命令，仅供人工排查，**不写进 CI/文档** |

### 3.2 为什么不能只改 `unit.test.mjs`

`unit.test.mjs` 是阶段 0 之前就有的文件（140+ 用例），本轮任务书**不授权改它的内容**（它不是阶段 3 的测试文件）。包装器方案的好处是**一次覆盖全部测试文件**，包括将来新增的；坏处是"绕过包装器直接 `node --test`"仍然会写真库——所以 T-5 的负向测试必须存在，且验收时**必须实际跑一次绕过包装器的场景并证明它被拦住**。

### 4.2 分流规则（唯一的判定点）

```
runTool('set_storyboard', args, ctx)
  ├─ isStructuredSpec(ctx.projectId) === true  → 新路径：写 story_shots 基础字段
  └─ isStructuredSpec(ctx.projectId) === false → 旧路径：原样调用现有实现（一字不改）

**三条硬约束**：

1. 判定**只能**走 `isStructuredSpec()`（`lib/core/structured-spec.js`），不得直接 `SELECT structured_spec`（那会出现第二个读取点，改口径时必漏）。

3. 旧路径**代码零改动**：不是"重构后行为一致"，而是**不动那段代码**。

## 七、工作包 4：写入与 QC 流程

### 7.1 目标链路

```
Agent 工具调用
  → 结构校验（schema，结构类失败即拒绝）
  → 确定性校验（action / blocking / camera）
  → 连续性处理（solveContinuity，写 shot_states）
  → 业务写入（同一事务）
  → QC 记录（qc_reports，同一事务）
```

### 7.2 事务边界（必须逐条实现）

| # | 边界 | 要求 |
|---|---|---|
| TX-1 | 单镜写入（`story_shots` 一行 + 其 `shot_actions` + `shot_blockings` + `shot_assets`） | **一个事务**；任一步失败整体回滚 |
| TX-2 | QC 记录 | 与 TX-1 **同事务**。不允许"业务写成功、QC 丢了" |
| TX-3 | 连续性求解 + `shot_states` 写入 | 独立事务（求解可能跨镜，失败不应回滚已写入的镜），但**求解失败必须返回错误且不静默跳过** |
| TX-4 | 章级批量（`set_storyboard` 多镜） | 一个事务；任一条结构类失败 → **整批拒绝**（与旧 `PUT storyboard` 的"先整体校验再落库"一致） |
| TX-5 | `clear: true` 的删除 | 与写入同事务（先删后插） |

### 7.3 局部性与 hash 联动

| # | 要求 |
|---|---|
| L-1 | 改一镜只写该镜；不得"重写整章"（`set_shot_detail` / `set_shot_actions` / `set_shot_blockings` 都是单镜粒度） |
| L-2 | 改镜后 `sourceSpecHash` 必须随之变化：写入成功后**重算该镜所属章的 `sourceSpecHash` 并在返回值里带回**（阶段 3 **不落库**，只算，因为 `render_adaptations.source_spec_hash` 是阶段 4 的对象） |

### 10.1 接口

### 10.2 归属校验（照抄现有范式）

```
