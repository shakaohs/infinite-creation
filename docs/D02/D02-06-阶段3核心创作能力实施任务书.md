## 三、★P0 前置门槛：测试环境隔离（A-01）

**没有通过本节，本节之后的任何"跑测试"动作都禁止执行。** 阶段 3 新增测试必然写库，这条不闭合，后面每一步都在赌真实库。

### 3.1 根因（必须先承认）

| # | 事实 | 后果 |
|---|---|---|
| 1 | `getDb()` 只在 `!!process.env.IC_DATA_DIR` 时才调 `assertEnv` / `assertDbIsolation`（`db.js:19`） | 没设 env = 零检查 = 生产模式 |
| 2 | 所以"加包装器"只保证**正确路径**安全 | **错误路径（直接 `node --test`）照样写真实库** |
| 3 | `NODE_ENV` 在 `node --test` 下**是 undefined** | 不能用 `NODE_ENV==='test'` 识别测试环境 |
| 4 | `process.execArgv` 在测试子进程里**是空的**（`[]`），`--test` 不在里面 | 不能用 execArgv 兜底识别 |

### 3.2 可靠的识别依据（实测，Node v22.22.2）

```
$ node --test probe.test.mjs        # 在测试体内打印
NODE_TEST_CONTEXT: "child-v8"       # ← node:test 给每个子进程注入
NODE_ENV:          undefined
ARGV:              [node.exe, probe.test.mjs]     # 看不到 --test
EXECARGV:          []                              # 空
```

**结论**：判定函数以 `NODE_TEST_CONTEXT` 为主信号，`execArgv` 的 `--test*` 为兼容兜底（覆盖 `--experimental-test-isolation=none` 这类同进程模式）：

```js
// lib/core/env-guard.js 新增导出
export function isUnderTestRunner() {
  if (String(process.env.NODE_TEST_CONTEXT || '')) return true;
  return process.execArgv.some((a) => a === '--test' || a.startsWith('--test-'));
}
```

**禁止**用 `NODE_ENV` 判定（实测为 undefined，写了也拦不住）。

### 3.3 `getDb()` 的硬闸（A-01 的核心改动）

`lib/core/db.js` 的 `getDb()` 改成三段判定，**顺序不可调换**：

```
underTest = isUnderTestRunner()
hasDir    = !!process.env.IC_DATA_DIR

① underTest && !hasDir   → 抛 TEST_ISOLATION_NOT_SET      （打开库之前）
② underTest || hasDir    → assertEnv() + assertDbIsolation()（真实路径逐段 lstat/readlink）
③ 打开之后                → 再 assertDbIsolation() 复核一次（TOCTOU，沿用阶段 0 现有实现）

生产（!underTest && !hasDir）→ 完全走原路径，一行行为都不变
```

| # | 要求 |
|---|---|
| G-1 | ①的抛出必须发生在 `createDb()` **之前**，错误码 `TEST_ISOLATION_NOT_SET`，消息里给出正确用法（`pnpm test`） |
| G-2 | ②必须复用 `lib/core/env-guard.js` 的 `assertEnv` / `assertDbIsolation`，**不得另写一套路径判断** |
| G-3 | 判定对象是 `dbSettings().sqlitePath` 的**真实路径**，不是 env 字符串 → `IC_DB_SQLITE_PATH`、`config.json` 的 `db.sqlite.path`、符号链接三条绕过路径都拦得住（阶段 0 已验证） |
| G-4 | 生产行为不变：`next dev` / `next start` 未设 `IC_DATA_DIR` 且不在测试运行器里 → 与今天完全一致（W：启动冒烟测试断言） |
| G-5 | `initSchema(db)` 用**外部 adapter** 的调用（阶段 1 的 4 个测试文件就是这种）不受影响 —— 它们不经过 `getDb()` |

### 3.4 测试运行器 `scripts/test/run-tests.mjs`

| T-1 | `package.json`：`"test": "node scripts/test/run-tests.mjs"`，`"test:raw": "node --test --test-force-exit \"tests/*.test.mjs\""`（仅供人工排查，**不写进 CI/文档**） |

> 若审核方不接受 62，**唯一替代方案是把 `set_scene_state` 降级为纯 API + 人工/前端建场**，但那样 L4 真实创作链就断了（Agent 无法自建场次基线）。这是需要审核方拍板的取舍，已登记为 **R-13**。

### 4.2 分流规则（唯一的判定点）

```
runTool('set_storyboard', args, ctx)
  ├─ isStructuredSpec(ctx.projectId) === true  → 新路径：写 story_shots / shot_assets
  └─ isStructuredSpec(ctx.projectId) === false → 旧路径：原样调用现有实现（一字不改）
```

其余 4 个工具**只服务新路径**，入口第一行就判 `isStructuredSpec()`，为 false 直接抛 `STRUCTURED_SPEC_DISABLED`（不静默降级到旧表）。

**四条硬约束**：

| # | 约束 |
|---|---|
| D-1 | 判定**只能**走 `isStructuredSpec()`（`lib/core/structured-spec.js`），不得直接 `SELECT structured_spec`（第二个读取点 = 改口径时必漏） |
| D-2 | `set_storyboard` 的分流点**只能有一个**：`runTool` 内该工具的实现入口。不得在 API 层、Skill 层各判一次 |
| D-3 | 旧路径**代码零改动**：不是"重构后行为一致"，而是**不动那段代码** |
| D-4 | **每一个**新路径写入口都要自己判一次 flag（不能只靠 `set_storyboard` 判过就放行），因为工具是独立调用的（LLM 可以先调 `set_shot_detail`） |
| D-5 | **归属校验是每个写入口的必做项**，不接受"只凭传入 id 就写"：`shot_id` 必须属于本项目（`SHOT_NOT_IN_PROJECT`）、`chapter_id` 属于本项目（`CHAPTER_NOT_IN_PROJECT`）、`asset_id` 属于本项目（`ASSET_NOT_IN_PROJECT`）、`scene_key` 的基线属于本项目（`SCENE_NOT_IN_PROJECT`） |

#### 4.4.1 镜号分配与重排（A-03.1 / **V3-B-01** / **V3-B-06**）

V2 这一节有一处**自相矛盾**（V3-B-06 点名）：第 3 步说"`global_no` 单调递增、按权威序排列"，第 4 步却说"新增镜一律 `MAX+1`"。往 ch1 中间插一镜时，`MAX+1` 会给它一个**大于 ch2 全部镜**的号，于是"按权威序读出来号不递增"。V2 的 N-T1 断言恰好把这个错误盖住了（它只要求"ch2 的号大于 ch1 末镜"，`MAX+1` 天然满足）。

##### 4.4.1.1 两个号的定义（不混用）

| 号 | 语义 | 谁决定 | 用途 |
|---|---|---|---|
| `shot_no` | **章内**序号，`1..n` 连续 | 程序按目标序重编（LLM 传值只作排序输入） | 与 plan 的 `shotRange` 对齐、人工沟通 |
| `global_no` | **项目内**全局序号，唯一且严格递增，**允许不连续** | 程序 | 连续性求解排序、增量重算、结构化 API 排序 |

**权威序（唯一顺序来源，不得按数据库自然返回顺序）**：

```
章序：chapters.seq ASC, chapters.id ASC        （Chapters.list 已是 ORDER BY seq ASC，db.js:1026）
章内：shot_no ASC, story_shots.id ASC
```

> `chapters.seq` 是 `INTEGER DEFAULT 0`，**允许同值**（历史库确实有同值章）。所以章序必须带 `id ASC` 作稳定次序，否则同一 `seq` 下顺序不确定 → 重排结果不可复现。

##### 4.4.1.2 两种写入：纯追加 vs 改变顺序

必须**先判定**，再选算法。判据是"本次写入会不会让任何一镜在权威序中的**排名**变化"。

| 形态 | 判定条件（**全部**满足才算纯追加） | 算法 |
|---|---|---|
| **纯追加** | ① 目标章是权威序的**最后一章**（`seq` 最大，同值取 `id` 最大）；② 新镜 `shot_no` 大于该章现有最大 `shot_no`（该章原无镜则从 1 起） | `global_no = COALESCE(MAX(global_no),0) + 1`，在同一事务内取 MAX；`shot_no` 用章内末位号。**必须断言**：写入后它在权威序里确实是最后一镜 |
| **改变顺序** | 其余一切：非末章插入、章内插入、调换、删除后补空位、镜换章、章序（`seq`）变更 | 先算**目标序**，再算**受影响区间**，再走**两阶段重编**（4.4.1.3） |

**为什么不能统一用 `MAX+1`**：`MAX+1` 只表达"最后来的"，不表达"排在哪"。中间插入用它，会把"物理顺序"和"号大小"解耦，而 `uq_ss_gn` 只保证唯一 —— 于是库里出现 `1, 6, 3, 4, 5` 这种号，求解按 `global_no` 排序就把插入镜排到了全场最后，`state_in` 继承错人。**这类错误不会报错，只会让连续性判断静默失真。**

##### 4.4.1.3 受影响区间与两阶段重编

**区间定义**（保守、可判定、可断言）：

| 字段 | 区间 |
|---|---|
| `shot_no` | **该章全部镜**（章内要求 `1..n` 连续，任何插入/删除都会牵动其后所有镜；整章重编最省事且不会漏） |
| `global_no` | 从"目标序中**排名发生变化的第一镜**"到**项目最后一镜**（含）。不改排名的一律不动 |

**两阶段重编原语**（`renumberTwoPhase`，写进 `lib/core/render/global-no.js`，`shot_no` 与 `global_no` **共用同一份**）：

| 步 | 动作 | 为什么 |
|---|---|---|
| 1 | 对区间内每一行算出**最终值**：`shot_no` = 章内目标序位置（1..n）；`global_no` = 前驱值（区间外最后一镜的号，无前驱取 0）依次 +1 | 保证严格递增且不与区间外冲突 |
| 2 | 先把区间内该列**全部写成负值**（`-(i+1)`，`i` 为区间内序号） | SQLite 的 `uq_ss_sn` / `uq_ss_gn` 是**即时检查**，不做这一步，写第 1 行就会撞上还没腾出来的旧值 |
| 3 | 再写最终正值 | 此时旧值已全部腾空 |
| 4 | 两步**同一事务**；任何异常整体回滚 | 提交后若残留负值，即视为缺陷（`assertGlobalOrder` 兜底） |

**三条实现约束**：

| # | 约束 |
|---|---|
| R-1 | 负值只是**中间态**，绝不允许越过事务边界；不得为了"避开唯一索引"把负值留在库里 |
| R-2 | `shot_no` 与 `global_no` 的重编必须在**同一个事务**内完成（先做完一个字段的两阶段，再做另一个；不同字段的唯一索引互不相交，不会互相撞） |
| R-3 | 重编**不得改变镜的 `id`**：号是位置，镜是身份。调换两镜 = 两个 `id` 的号互换，内容跟着 `id` 走 |

##### 4.4.1.4 部分提交的限制（避免"目标序"不可判定）

`set_storyboard` 允许只提交本章部分镜（V2 §4.4 的"不删未提及的镜"）。但**部分提交无法确定新镜与未提交镜的相对次序**，因此：

| 形态 | 允许？ | 否则报错 |
|---|---|---|
| 本章全部镜一起提交 | ✅ | — |
| 尾部追加（新镜 `shot_no` 大于本章现有最大值） | ✅（走纯追加） | — |
| 就地更新（`shot_no` 已存在，只改字段） | ✅ | — |
| 中间插入 / 调换，但未提交本章全部镜 | ❌ | `CHAPTER_SUBMIT_INCOMPLETE`（结构类：**该章这批镜全部拒写**，其他章不受影响） |

> 这条限制是**故意加的**：不引入"插入锚点"参数，就不用猜。要插中间就整章提交，序号由程序按目标序重排。

##### 4.4.1.5 硬约束

| # | 约束 |
|---|---|
| N-1 | 两个号**都由程序生成**。`shot_no` 允许 LLM 传（只作排序输入），`global_no` **不接受** LLM 传值（传了忽略并记 WARN `GLOBAL_NO_IGNORED`） |
| N-2 | `shot_no` 与 `global_no` 不得混用：`shotRange`、人工沟通用 `shot_no`；求解、增量、API 排序用 `global_no` |
| N-3 | 不得按 `prev_shot_id` 排序（该列是提示，不是权威顺序） |
| N-4 | 同一章内传入重复 `shot_no` → `SHOT_NO_DUPLICATED`（重复值无法确定目标序，属结构类错误） |
| N-5 | `global_no` 允许不连续，但**必须**随权威序严格递增；不要求每次操作都保留旧号（V3-B-06 明确：宁可重编号，不许破坏排序正确性） |
| N-6 | 写入后必须自检 `assertGlobalOrder(projectId)`：**按权威序读回**（`JOIN chapters` 取 `seq`），断言① 章内 `shot_no` 恰为 `1..n` 连续；② `global_no` 严格递增；③ 无负值；④ 无重复。任一不满足即抛 `GLOBAL_ORDER_BROKEN`（系统类，整体回滚） |
| N-7 | `assertGlobalOrder` **不得只检查唯一性**：唯一性由索引保证，它要检查的是"号与真实目标序一致"，这正是 V3-B-06 点出的漏洞 |
| N-8 | 任何一步异常整体回滚，**不得留下负编号或半套编号** |

#### 4.4.2 `shot_assets` 写入契约（A-03.2）

`shot_assets` 是**镜头资产引用的唯一权威**（D01-05 §4.6、D01-02 §6.2）。`story_shots.voice_ids`、`character_ids` 之类一律是**派生兼容列**。

**输入形态**（二选一，同一镜内不得混用）：

| 形态 | 写法 | 适用 |
|---|---|---|
| A（推荐，与旧工具同名，便于 Skill 复用） | `characters: ['罗克珊']`、`scenes: [...]`、`props: [...]`、`costumes: [...]`、`ages: [...]`、`voices: [...]` | 按名称引用 |
| B | `assets: [{ asset_id 或 name, role, variant_of? }]` | 需要精确指定 role/顺序/变体时 |

**解析与校验（逐条实现）**：

| # | 规则 | 错误码 |
|---|---|---|
| AS-1 | 按 `(project_id, name, category)` **精确匹配**（`name` 去首尾空白后全等，不做模糊/包含匹配） | 0 命中 → `ASSET_NOT_FOUND`；≥2 命中 → `ASSET_NAME_AMBIGUOUS`（要求改传 `asset_id`） |
| AS-2 | 传 `asset_id` 时：必须属于本项目 | `ASSET_NOT_IN_PROJECT` |
| AS-3 | 资产的 `category` 必须与 `role` 一致（`role = category`，见下表） | `ASSET_ROLE_MISMATCH` |
| AS-4 | `role` 值域只能是 `character`/`scene`/`prop`/`costume`/`age`/`voice`；`music`/`sfx`/`video`/`other` **不得进 `shot_assets`** | `ASSET_ROLE_INVALID` |
| AS-5 | `order_no`：同 `(shot_id, role)` 内**按传入顺序从 1 起连续编号**，整组替换（不是增量追加） | 跳号 → `ASSET_ORDER_GAP`（V-25） |
| AS-6 | `role='voice'` 最多 3 条 | `VOICE_OVERFLOW`（V-26；DB `CHECK` 兜底） |
| AS-7 | `variant_of`：仅 `role ∈ {costume, age}` 且该资产 `parent_id` 非空时写父 `asset_id`，否则 `''` | 父不在本项目 → `ASSET_VARIANT_ORPHAN` |

### 4.6 `set_shot_actions`（B-07：集合替换与引用维护）

| 项 | 内容 |
|---|---|
| 职责 | 单镜的 1..n 个人物动作（T1/T2/T3） |
| 粒度 | 单镜，`actions[]` 每个元素 = 一个动作 = `shot_actions` 一行 |
| 语义 | **完整集合提交（全量替换）**：本次 `actions[]` 就是该镜动作的**全集**；没提交的旧动作被删除 |
| 必填 | `actor_id`（本项目 `category='character'` 资产）、`action_type`、`tier`、`t_from`、`t_to`、`is_primary` |
| 时间约束 | `0 <= t_from < t_to <= story_duration`，`TQ=0.001` 半开区间；越界 → `ACTION_TIME_OUT_OF_RANGE`（A-11，结构类） |

#### 4.6.1 ID 稳定性（不得裸删后插）

| 情形 | 处理 |
|---|---|
| 已存在的动作**带 `id`**（必须是本镜的动作） | **保留该 id**，走 UPDATE（身份稳定，`trigger.ref` 不会断） |
| 已存在的动作**不带 `id`** | 视为新动作，生成新 `uid()`，INSERT |
| 旧动作**不在本次集合里** | DELETE（属于"全集替换"的自然结果） |
| 带 `id` 但该 id 属于别的镜 / 不存在 | `ACTION_ID_FOREIGN`（结构类，**只拒该镜**） |

> **为什么不能"先全删再全插"**：`trigger_json` 与 `sync_json.parallel_with` 里存的是**动作 id**。全删全插会让每次重写都换一批 id，任何跨动作引用立刻悬空；而 `prompt_packages` 之类的下游若引用了动作 id（阶段 4），历史就断链了。V1 写的"先删后插"必须改成**显式 diff**。

#### 4.6.2 引用完整性（前置校验，结构类）

| # | 规则 | 错误码 |
|---|---|---|
| AR-1 | `trigger_json.kind='action'` 的 `ref` 必须指向**同一镜**里存在（本次提交或保留）的动作 id | `ACTION_REF_DANGLING` |
| AR-2 | `sync_json.parallel_with[]` 里每个 id 必须指向**同一镜**里存在的动作 id，且**不得等于自身** | `PARALLEL_REF_DANGLING` / `PARALLEL_SELF_REF` |
| AR-3 | A-18：**单向声明由程序补齐另一侧**并记 INFO（`PARALLEL_COMPLETED`），**不报错** | — |
| AR-4 | 删除动作后，**不得**留下指向它的 `trigger.ref` / `parallel_with` → 由 AR-1/AR-2 在同一事务内前置拦截 | `ACTION_REF_DANGLING` |
| AR-5 | 全部写操作（UPDATE/INSERT/DELETE + A-18 补齐）在**同一事务** | — |

### 4.7 `set_shot_blockings`（B-05：必填字段与 S 级推导）

| 项 | 内容 |
|---|---|
| 职责 | 单镜逐人站位：坐标、依托物、朝向、姿态、手部、画内外 |
| 粒度 | 单镜，`blockings[]` 每个元素 = 一人 = `shot_blockings` 一行 |
| 落表 | `shot_blockings`（复合主键 `shot_id`+`character_id`，**集合替换**：本次 `blockings[]` 是该镜的全集，未提交的人被删除） |
| 必填（S0） | **`character_id`、`position_abs`、`facing`、`posture`、`in_frame`** —— 四项缺任一 → 结构类拒绝（`BLOCKING_FIELD_MISSING`） |
| `character_id` | 必须是本项目 `category='character'` 资产的真实 id；**不得为空串**（DB 的 `NOT NULL` 拦不住空串） |
| 坐标 | `norm_x/y/z` **三者同有或同空**：部分为空 → `COORD_PARTIAL`（S-24，结构类拒写）；`rel='unknown'` 时不得写 >0 的 `norm_confidence` |
| 可靠性 | `norm_confidence` 必须与 `posRel` 结论自洽（V-24 反向） |

#### 4.7.1 S 级由程序推导（不由 LLM 声明）

按 D01-04 §7，S 级**从数据算**，防止"全标 S0 逃避校验"：

```
level = S0
if (chars_in_frame >= 2)                        level = S1
if (chars_in_frame >= 3 || 有 prop 被 ≥2 人接触)  level = S2
if (有 locomotion 或 position_track.length > 1)   level = S3
if (有 combat 或 chars_total >= 5 或 crowd_switch=A) level = S4
```

| 级别 | 额外必填（在 S0 四项之外） | 缺失时 |
|---|---|---|
| S0 | — | — |
| S1 | `anchor_object`/`behind_object`/`gaze_target`/`hand_state`/`current_task` + 场次 `axis_lock` | `SCHEMA_INVALID`（结构类） |
| S2 | `norm_x/y/z`/`distance_to_camera`/`occlusion`/`power_level` | 结构类 |
| S3 | `position_track` + `state_in/out`（状态由求解器产生） | 结构类（`position_track` 无法推 → 拒写） |
| S4 | 逐动作 `contact` + `crowd_switch` + `instance_anchor` | 结构类 |

**注意**：S 级是**每镜**算的（`chars_in_frame` 取本镜 `in_frame=1` 的人数），所以同一章不同镜可以有不同 S 级。写 `set_shot_blockings` 时**只按本镜数据**判级，不参考同章其他镜。

### 4.8 `set_scene_state`（A-03.3，新增第 5 个工具）

| 项 | 内容 |
|---|---|
| 职责 | 建立/更新**场次实例**的空间基线（`scene_states`），不写镜、不写资产 |
| 归属 | D01-06 §1.1 写权限表：`scene_states` 归**剧本抽取**，分镜创作**严禁**写。**权限怎么落地见 §4.8.4（V3-B-02），不得只写在描述里** |
| 粒度 | 一章一次，`scenes[]` 每个元素 = 一个场次实例 |

| 幂等 | `(project_id, scene_key)` 唯一 → 重写为 UPDATE 且 `state_rev += 1` |

#### 4.8.1 允许"存在但未定义几何"，禁止"编造几何"

这是 A-03.3 的核心判断。**行存在 ≠ 空间已定义**：

| 数据 | 允许的处理 | 禁止 |
|---|---|---|
| `scene_key` 存在 | 建行 —— 这是**确定事实**（这一场戏存在） | — |
| `coord_system` 无 `basis`/`active_area` | 写能确定的部分；缺的部分**不写**（保持 `{}`），QC 记 `COORD_SYSTEM_INCOMPLETE`（INFO） | **不得编造 `active_area` 尺寸**（它是归一化↔米换算的唯一依据，编一个会让 S-15/V-21 全部算错） |
| `axis_lock` 无 `axis_line` | 写 `pair/left/right/camera_side`；缺 `axis_line` → QC `AXIS_LOCK_INCOMPLETE`（WARN）；S-05/S-06 降级为不可验证 | **不得从"画面左右"反推物理左右**（D01-04 §5.4 明令） |
| `fixtures` | 只写用户/源文件能确定的固定物；`zone` 必须 4 个 `0..1` 数字且 `x1<x2`、`y1<y2` | **不得为了过 S-02/A-05 而编造 zone**（`FIXTURE_ZONE_INVALID` 拒写） |
| `scene_id` | 允许为空（**纯虚拟场次**，D01-04 §2.1 明确允许），此时 `fixtures` 必须自包含 | 非空时必须属于本项目且 `category='scene'`，否则 `SCENE_ASSET_NOT_FOUND` |
| `power_geometry` / `crowd_switch` | 允许为空 | 空则 S-16/S-17 输出 INFO，**不判 FAIL** |

#### 4.8.2 镜头写作时的场次基线检查

`set_storyboard` 新路径写入某镜时：`scene_key` 在 `scene_states` 里**必须已有行**，否则抛 `SCENE_STATE_MISSING`（结构类，**只拒该镜**，同批其余镜照常写）。

> **为什么必须拒而不是自动建空行**：自动建行会让"场次存在但空间未知"退化成"场次已定义"，下游（连续性、编译）会误以为有基线可用 —— 正是审核意见点名的"为了满足外键而随意创建一个空场景基线"。

#### 4.8.4 写权限：只在剧本抽取阶段开放（**V3-B-02**）

**问题**：V2 只把"归剧本抽取"写在工具描述与本节"归属"行里。但**描述不拦人** —— 分镜创作阶段的模型看到 `TOOL_DEFINITIONS` 里这个工具，就能调它给任意 `scene_key` 建/改空间基线，而 D01-06 §1.1 明令分镜创作**严禁**写 `scene_states`。

**现有可用的机制（已实测，不必新造）**：

| 机制 | 位置 | 作用 |
|---|---|---|
| 工具池静态过滤 | `openclaude-agent.js:152-156`，`buildMcpTools` 按 `toolSet` 过滤；已有 `OPUSCAR_TOOL_NAMES`（`:141`）、`NOVEL_TOOL_NAMES`（`:147`）两套白名单 | 决定模型**看不看得到**某个工具 |
| 运行时严格参数校验 | `tools.js:4087` `runTool` 的 `ALLOWED_ARG_KEYS`：未在 schema 声明的顶层参数**直接拦截**（`unknown-args`） | 决定模型**能不能夹带**字段 |
| 工具运行时上下文 | `tools.js:310` `createToolRuntime` 产出 `ctx`，`getCtx()` 在同一 job 内复用 | 放可信的权限标记 |

**三层防线（缺一层都不算闭合）**：

| 层 | 机制 | 挡住什么 |
|---|---|---|
| **L1 看不到** | 新增 `SCRIPT_TOOL_NAMES`（含 `set_scene_state`）+ `buildMcpTools` 的 `toolSet === 'script'` 分支；`opuscar` / `novel` / 分镜创作阶段默认池**都不含**该工具 | 分镜创作阶段根本收不到工具定义 |
| **L2 写不进** | `createToolRuntime` 新增形参 `toolSet`（由 `buildMcpTools` 传入，**不从 `args` 读**），`ctx.toolSet` 即为可信标记；`set_scene_state` 处理函数**首行**断言 `ctx.toolSet === 'script'`，否则抛 `SCENE_STATE_WRITE_FORBIDDEN` | 绕过 L1 直达 `runTool` 也拒绝 |
| **L3 夹带无效** | `set_scene_state` 的 Schema **不声明** `stage` 字段；模型传 `stage:'script_extraction'` 会被 `ALLOWED_ARG_KEYS` 以 `unknown-args` 拦截 | LLM 自报阶段**不可能**成为授权依据 |

**四条规定**：

| # | 规定 |
|---|---|
| PS-A | 权限判断的输入**只能**是 `ctx.toolSet`，且它来自服务端构造工具池时传入的参数；不得读取 `args.stage`、不得读取 `ctx.project.*` 里的任何用户可写字段 |
| PS-B | 拒绝时**不写任何行**（`scene_states` 行数、`state_rev`、`updated_at` 全部不变），错误码 `SCENE_STATE_WRITE_FORBIDDEN` |
| PS-C | 现有代码**没有**"剧本抽取"独立阶段，本阶段需补**最小阶段路由**：一个 `toolSet='script'` 的 agent 入口（复用 `jobs.type='agent'`，在 `checkpoint` 里记 `toolSet:'script'` 便于追溯）。**不新增 job 类型、不新增表** |
| PS-D | 该入口承担 D01-06 §1.1 的剧本抽取职责：建章节场次、写 `scene_states`、写 `assets`；它**不写** `story_shots`（越界同属缺陷） |

### 4.9 旧 `blocking` 的降级规则（A-06）

D02-01 §6.2 的意图是：新路径**接受**旧 `blocking` 文本，但**不解析成坐标**。V1 把它落成 `character_id=''`，那是错的 —— `character_id` 必须是真实人物 id（D01-04 §4、复合主键之一）。

#### 4.9.1 正确做法：按人拆分 + 真实 id 解析

| 步骤 | 动作 |
|---|---|
| 1 | 从 `blocking` 文本中找出**明确标注的人物名**（旧 `blocking` 的写法是"每人一段括号"，人名在括号前：`姜知微：（推车左侧，面向右…）`） |
| 2 | 用本项目 `assets(category='character')` 的 `name` 做**精确匹配**；不做包含/模糊匹配，不新造资产 |
| 3 | 唯一命中 → 按人拆成一行：`character_id` = 该真实 id，`position_abs` = 该人的原始括号内文本（**原文照存，不改写**） |
| 4 | `norm_x/y/z` **全部 NULL**（→ `posRel` 走规则③返回 `unknown`）；`norm_confidence = 0.3`；`in_frame = 1`；`facing`/`posture` 从原文**只在能确定时**取枚举值，否则留空并记 WARN |
| 5 | 匹配不到 / 多人同名 → **拒绝写入**，错误码 `BLOCKING_CHAR_UNRESOLVED`，返回未解析名单，要求 LLM 改用逐人站位 |
| 6 | 文本里一个人名都认不出 → 拒绝（`BLOCKING_NO_CHARACTER`），**不得**落成一行无名站位 |

**禁止清单**：

| 禁止 | 原因 |
|---|---|
| 写 `character_id=''` | 主键之一必须真实；空串不是人物 |
| 为降级而 `create_asset` 造人物 | 造出的是"界面里看不见、生成时被静默忽略"的资产 |
| 从"画面左侧"推 `norm_x` | D01-04 §5.4 明令：画面方位不能转物理坐标 |
| 把降级行的 `rel` 写成 `known` | V-24 / S-25：坐标缺失不得当 known |

| BL-02 | 双人物文本 → 2 行，各自 `position_abs` 是各自括号内原文 |

#### 4.10.1 门禁**实际读取**的字段（实测，不是推测）

抽函数前先把"它到底读哪些字段"列清 —— 这是 B-03 能闭合的前提。逐行读 `validateStoryboardPlan` 与 `lintStoryboardShots` 得到：

| 函数 | 读的字段 | 判什么 |
|---|---|---|
| `validateStoryboardPlan(plan, videoModel)` | `plan.mode` / `aspect` / `base` / `assetMode` / `seam`；`plan.anchors.positions`（非空数组）；`plan.beats[]` 的 `durationSec` / `intensity` / `emotion` / `type` / `beatFunction` / `shotRange`（须从 1 起连续覆盖） | 锁档完整性与节拍表连续性。**完全不读 `shots`** |
| `lintStoryboardShots(shots, chapterTitles, planOf, videoModel)` | 每镜的 `idx`、`duration`、`characters[]`、`camera`；`chapterTitles[i]` 决定分章分组；`plan.beats[].shotRange` 判定节拍归属 | ① 时长分档；② 每镜有具名主体；③ 相邻镜 `camera` 归一化后不得完全相同；④ 每镜归属某个节拍 |

**结论**：旧门禁吃的是 `idx` / `duration` / `characters` / `camera` 四个镜级字段。结构化结构里**一个都没有**（对应的是 `shot_no` / `story_duration` / `shot_assets` / 14 个摄影机字段）。所以"直接把新对象传进去"的后果不是报错，而是**四个字段全取到 `undefined`**：时长越界检查被 `Number.isFinite` 跳过、`characters` 判空直接报错或（若写成容错）静默放行、`camera` 两侧都是空串 → 判"完全相同"误报或因为 `a && a === b` 的短路而**永不触发**。这正是 B-03 说的"门禁形同虚设"。

#### 4.10.2 结构化 DTO（`toGateShots()`）

**位置**：`lib/core/storyboard-gate.js` 内的纯函数，与门禁本体同文件（避免又出现"两套映射"）。

**输入**：`{ projectId, chapterIds, shots }`（结构化镜，已落库或已构造好）。**输出**：`{ chapterTitles: string[], shots: GateShot[] }`，形状与旧路径完全一致。

| 门禁字段 | 结构化来源 | 映射规则 |
|---|---|---|
| `idx` | `story_shots.shot_no` | 直接映射（章内 `1..n`，与 `shotRange` 的 1-based 语义一致） |
| `duration` | `story_shots.story_duration` | 直接映射（秒） |
| `characters[]` | `shot_assets` 中 `role='character'` 的 `asset_id` → `assets.name`（限定本项目） | 查询构造；**不得**用 `story_shots.voice_ids`/`character_ids` 之类派生列顶替；解析不出就是 `[]`，让门禁照常报"没有 characters" |
| `camera` | 由摄影机字段**规范化拼串**：`shot_size` / `cam_direction` / `cam_height` / `lens_mm` / `fov_deg` / `cam_distance_m` / `movement` / `movement_amp` / `composition_rule` | 程序按固定顺序拼接（确定性，同输入同串）；**不得**回填 `cam_note`（那是历史整串，与结构化字段不同源） |
| `chapter` 分组 | `chapterTitles[i]` = 该镜所属章标题，**数组与 `shots` 一一对应且同序** | 由 `chapter_id → chapters.title` 查得；顺序取 §4.4.1.1 的权威序 |
| 节拍归属 | 不改：`plan.beats[].shotRange`（1-based）与 `idx` 比对 | 门禁原逻辑 |
| 视觉内容（`visual_content`） | **门禁当前不读**（实测 `lintStoryboardShots` 只取 `duration`/`characters`/`idx`/`camera` 四个镜级字段） | **不映射**。但必须写进 `toGateShots()` 的注释与 GT-01 的基线快照里：**一旦门禁增加"视觉内容"类判定，DTO 必须同步补字段**，否则又是一次"取到空值静默放行" |
| `blocking` | **不映射** | 旧 `blocking` 是段级文本，塞进结构化路径等于把两套模型混起来（B-08 禁止） |

**DTO 的三条硬约束**：

| # | 约束 |
|---|---|
| DTO-1 | 纯函数：只读传入的镜与资产快照，**不写库、不改原始对象**（返回新对象，深拷贝字段） |
| DTO-2 | **不得凭空补齐人物**：`shot_assets` 里没有就是没有，不许从 `blocking` 文本、`characters` 旧列或 `context.bible` 里"捞"人名来凑 |
| DTO-3 | 映射不完整时**不得给假 PASS**（见 §4.10.3） |

#### 4.10.3 映射不完整时怎么办（V3-B-03 第 7 条）

| 情形 | 处理 |
|---|---|
| 某镜摄影机字段**全空**（`shot_size`/`cam_direction`/`cam_height`/`lens_mm`/`movement` 都没值） | DTO 输出 `camera: ''` 并给该镜打标 `unmappable: ['camera']`；相邻镜比较时**跳过**任何一侧带该标的对（不得用"空串等于空串"判成"机位写法完全相同"），同时记 QC `GATE_FIELD_UNMAPPABLE`（INFO，属 QL-3 的"不可验证"集合） |
| `characters[]` 解析为空 | **不补、不放行**：让门禁按原逻辑报"没有 characters"。若产品上确实需要空镜，那是改门禁语义的事，属上游变更，阶段 3 不擅自放开 |
| 章标题查不到（`chapter_id` 指向不存在的章） | 结构类错误 `CHAPTER_NOT_FOUND`，**在进 DTO 之前**就拒绝 |
| 任一门禁字段取值类型非法（如 `story_duration` 为 `null`） | 结构类错误，走 §8.2 的逐镜隔离，不进 DTO |

### 7.5 状态传播（D01-04 §5.5 Step 1–6，逐步实现）

| 步 | 内容 | 关键点 |
|---|---|---|
| **Step 1** | 取前镜 P；有 P → `state_in = P.state_out`（**深拷贝**），`derived_from='prev_shot:<P.id>'`，所有字段 `meta.src` 更新为本镜来源、`ver` = 本镜版本 | 深拷贝，不得共享引用（否则改本镜会污染前镜） |
| **Step 2** | `time_jump=1` → **跳过 Step 3/4 的差异校验**，全部降 `INFO` | 只跳差异判定，不跳状态复制与动作覆盖 |
| **Step 3** | 逐人比对 `shot_blockings` 与 `state_in.chars`（按 §7.6 三值逻辑） | 见下方判定表 |
| **Step 4** | 道具比对（同样受三值逻辑约束） | `PROP_APPEAR`/`PROP_TELEPORT`/`PROP_HANDOVER`/`PROP_REVIVE` |
| **Step 5** | `state_out = state_in`，按 `t_from` 升序应用 `result.char_delta`/`prop_delta`/`env_delta`，再用 `end_state` 覆盖 `pos/posture/facing/hand`；被覆盖字段 `meta.src='action:<act_id>'`、`rel='known'`；未覆盖字段 meta 原样继承、`ver` 不变 | 顺序必须按 `t_from`（`cmpStr` 不参与，数值排序 + `TQ` 量化） |
| **Step 6** | `position_track` 与本镜动作 `path` 交叉校验（PT-1..PT-7） | 见 D01-04 §5.5 与 S-18/S-19 |

**Step 3 判定表（逐条实现，不得简化）**：

| 条件 | 结果 |
|---|---|
| 本镜有该人、`state_in` 无该人 | 新人入画，`state_in` 该人全字段 `rel=unknown` |
| 本镜无该人、`state_in` 有且 `in_frame=1` | `CHAR_POP`（FAIL，仅当前镜 known） |
| `abs(Δpos) ≤ 0.15` | OK |
| `abs(Δpos)` 在 (0.15, 1.5] 且无 locomotion | `POSITION_JUMP`（FAIL，两边 pos 均 known） |
| `abs(Δpos) > 1.5` 且无 locomotion/time_jump | `TELEPORT`（FAIL） |
| `posture` 变 且无 `cog=rise/lower` | `POSTURE_JUMP`（FAIL，两边 known） |
| `facing` 变化 >90° 且无转身动作 | `FACING_FLIP`（WARN） |
| `hand` 变 且无 manipulation | `HAND_JUMP`（FAIL，两边 known） |
| 任一为 `unknown`/`inferred` | `STATE_UNKNOWN`（INFO）/ `INCONSISTENT_INFERRED`（WARN），**不判 FAIL** |
| `gaze` 变化 | 始终允许 |

**执行前提（防"用未知判已知"）**：

```
canCompare(field) = meta(in).rel === 'known' && meta(observed).rel === 'known'
若 !canCompare → 按三值逻辑降级，绝不产出 FAIL
```

### 7.6 三值逻辑（D01-04 §5.4，逐条）

| 场景 | A | B | 结果 |
|---|---|---|---|
| 求差 | known | unknown | **unknown**（不判冲突） |
| 求差 | inferred | unknown | unknown |
| 求差 | unknown | unknown | unknown |
| 求差 | known | known 且超阈值 | FAIL |
| 求差 | inferred | known 且不符 | WARN（`INCONSISTENT_INFERRED`） |
| 动作覆盖 | 动作区间含该字段变化 | unknown 起点 | **unknown**（无法算差异，也无法算无差异） |

四值语义（`known`/`inferred`/`unknown`/`not_applicable`）与"谁能 FAIL"的完整表见 D01-04 §5.3；`inferred` **只能 WARN**，`unknown` **既不 PASS 也不 FAIL**，`not_applicable` 不进统计。

### 7.7 `time_jump`

| 要求 |
|---|
| `time_jump=1` 时按 D01 规则**跳过**位置/姿态/道具/服装的差异判定，全部降为 `INFO`（`TIME_JUMP_SKIPPED`），并在 `meta.src` 里标注 `time_jump` |

### 7.8 增量计算与输入依赖（**V3-A-04** 重写）

#### 7.8.2 失效传播规则

| 变化 | 重算起点 | 重算范围 |
|---|---|---|
| 当前镜的 `blockings` / `actions` / `shot_assets` | 当前镜 | 当前镜 + 同场后续镜 |
| 当前镜的 `time_jump` / `spec_source` / `fill_confidence` | 当前镜 | 当前镜 + 同场后续镜 |
| `scene_states` 任一列（7.8.1 里标"是"的） | 该场 `global_no` 最小镜 | 该场全部镜 |
| 镜头从场次 A 移到场次 B | A、B 各自最早已受影响镜 | A 的后继链 + B 的整条链（两场都算） |
| `global_no` 变化导致场次内镜序变化 | 排名变化的第一镜（**每个受影响场次各一个**） | 该项目内所有排名变化场次的后继链 |
| 删除一镜 | 被删镜在原场的**后继镜** | 原场后继链（若原场无后继则不重算该场） |
| `assets` 的类别/变体/名称变化 | 引用该资产的镜中 `global_no` 最小者 | 引用它的场次中受影响镜及其后继 |
| 只改摄影机/时长/服装/音色（QC 类） | 不重算状态 | 只重生成该镜 QC |

#### 7.8.3 最早受影响镜与受影响场次的判定算法

写进 `lib/core/continuity/invalidate.js`（纯函数，**不写库**）：

```
planInvalidation({ change, shots, states }) → {
  scenes: [sceneKey, ...],                     // 需要重算的场次
  earliestByScene: { [sceneKey]: shotId },     // 每场的最早受影响镜
  qcOnlyShots: [shotId, ...],                  // 只重出 QC、不动 state 的镜
  reasons: [{ sceneKey, shotId, field, rule }]
}
```

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | 把 `change` 映射到 7.8.1 的行 | 未命中任何行 → 返回空（**不触发**） |
| 2 | 求受影响场次集合 | 镜头级变化取该镜 `scene_key`；`scene_key` 变化取原、新两个；`scene_states` / `assets` 变化取该场/引用场 |
| 3 | 求每场最早受影响镜 | 取"受影响镜集合"中 `global_no` **最小**者；场次级变化直接取该场最小 `global_no` 的镜 |
| 4 | 拆 `qcOnlyShots` | 命中行里「派生状态=否、QC=是」的镜，只进 QC 重建 |
| 5 | 返回 | 不含 `shot_states` 自身与 `qc_reports` 自身 |

**执行侧（`applyInvalidation`）**：

| 要求 | 内容 |
|---|---|
| 复用判据 | 只有"位于 earliest 之前且同场"的 `shot_states` 可复用。依据是**输入依赖矩阵里没有任何相关字段变化**，不是"时间戳看着新" |
| 重算方式 | 对该场**整场求解**（`solveContinuity` 的签名就是整场），但**只写** `global_no >= earliest` 的行。更早的行内容必然相同（状态只向前传播），不重写 → `updated_at` 不变（对应 C-3 的断言） |
| 写入口径 | 逐行 upsert；`meta.__solver` 见 §9.2.1 |
| 事务 | 求解在事务**外**（纯函数），写入与 QC 重建在同事务（§8.3） |

#### 7.8.4 过期派生结果绝不允许被读成当前结论

| # | 规则 |
|---|---|
| F-1 | 重算必须**同事务**重建受影响镜的 `qc_reports`（新增报告行，不删历史） |
| F-2 | 读取一律取"当前"= 同 `(target_type, target_id, ruleset_ver)` 下 `created_at` 最大的那条 |
| F-3 | 一致性不变量：**当前 QC 的 `created_at` 必须 ≥ 对应 `shot_states.updated_at`**。小于即 `QC_STALE`（系统级巡检项，可批量查）。**同一事务内两处时间必须取同一个 `now()` 值** —— 分别取两次会因毫秒抖动产生假阳性 |
| F-4 | 结构化 API 返回每镜的 `qc_level` 与 `solver_hash`；两者必须来自同一版输入（同一次重算） |
| F-5 | 不允许"只改数据不重出 QC"，也不允许"重出 QC 但不重算状态"（除非按 7.8.1 明确是 QC-only 变化） |

> F-3 是这一节唯一能被"事后验证"的判据：不需要重跑求解，只要一条 SQL 就能查出"状态比 QC 新"的镜。巡检脚本必须能在阶段验收时跑出 0 行。

#### 7.8.5 禁止循环触发

| # | 禁止 |

| L-1 | `shot_states` 的写入**不得**触发新的求解（它是求解的输出，不是输入） |
| L-2 | `qc_reports` 的写入**不得**触发求解或再次生成 QC |
| L-3 | 求解器内部**不得**读写数据库（D01-06 I3 纯函数）。它只接收 `shots` / `sceneState` 参数 |

## 八、工作包 4：写入、事务与 QC（**V3-A-05** 改写 / B-02 / B-03 / B-06）

### 8.1 唯一执行流程（**V3-A-05**：逐镜原子 + 逐镜隔离）

V2 这条流程的**第 3 步写错了**：它把"结构校验失败"当成"整批拒绝"，于是第 3 镜一个字段写错，第 1、2 镜的正确内容也一起被丢掉。这与冻结的 `D02-01 §6.5`（"该镜拒绝写入…2 轮仍失败 → 落库但 `qc_status='fail'`"）与 `§7.1` 的 E1（"阻断流水线？**否**（该镜 fail，其余继续）"）**直接冲突**。

V3 的流程分两段：**批次级规划**（纯内存，不写库）+ **写入**（按镜原子）。

```
【阶段 0 · 规划，纯内存，不写库】
 ① 读：本章全部镜、目标镜的从表、资产快照、场次基线、同场前序 shot_states
 ② 构造候选结果（新镜行、动作行、站位行、资产行）
 ③ 逐镜结构校验（schema / 枚举 / 引用 / `scene_key` 存在性）
      ├ 合法 → 进入本轮「可写集」
      ├ 非法且 rounds < 2 → 移出可写集，记错误码 + field + expected，rounds += 1（§8.2.1）
      └ 非法且 rounds === 2 → **写最小合法骨架**（§8.2.2，骨架本身是一次合法插入），
                              该镜在本请求内关闭，不再接受重提
 ③b 章级结构校验（章提交完整性 §4.4.1.4、`shot_no` 重复、编号可达性）
      └ 失败 → **该章这批镜全部拒写**（章级问题无法靠单镜修好），其他章继续
 ④ 逐镜确定性校验（action / blocking / camera / asset）→ 只产出 hits，不写库
 ⑤ 逐场连续性求解（solveContinuity 的粒度是**整场**，纯函数、事务外）
      └ 抛错属系统类 → **该场全部镜本轮不写**（不是只丢一镜），错误码进返回；其他场次照常
 ⑥ 算目标编号（§4.4.1）：判定"纯追加"还是"需重排"

【阶段 1 · 写入】
 ⑦ 需重排 → 一个事务内：两阶段重编 + 可写集全部镜的内容 + 受影响 shot_states
              + qc_reports + change_logs；任一步失败 → 整批回滚（见 8.3 TX-4）
    不需重排 → 逐镜事务：每镜一个事务，写它自己的全部行；失败只回滚该镜
 ⑧ 提交后自检 assertGlobalOrder(projectId)
 ⑨ 汇总返回：written / rejected（结构，含 field+expected）/ deferred（依赖，§8.2.3）
              / system_failed（场级，含错误码）；四类必须分开列，不得合并计数
```

**顺序不可调换的三条理由**：

| 约束 | 理由 |
|---|---|
| ⑤ 必须在 ⑦ 之前 | 求解是纯函数（D01-06 I3）。放进事务会持锁做长计算；且求解抛错时事务里已有半套状态 |
| ③ 必须在 ⑦ 之前 | 结构非法的镜**绝不能进任何写入事务** —— 否则要么写进脏数据，要么整批回滚（V2 的做法） |
| ⑦ 内部"业务行 + 状态 + QC + 审计"必须同生同死 | 不允许"业务写成功、审计或 QC 丢了"（V3-A-05 的原始要求不变，只是作用域从"整批"缩到"每镜"） |

### 8.2 三类错误（唯一口径表，**已按 D02-01 §6.5 / §7.1 校正**）

| 类别 | 例子 | 本次发生时的处理 | 该镜落库 | 其他镜 | 错误码 |
|---|---|---|---|---|---|
| **结构类（未耗尽）** | 缺必填、枚举非法、类型错、唯一冲突、资产 id 非法、`scene_key` 无基线、坐标部分为空、`shot_no` 重复、章提交不完整 | **拒绝该镜**（连骨架都不写），返回 `field` + `expected`；修复轮数 +1 | **不写** | **继续** | `SCHEMA_INVALID` / `ASSET_NOT_FOUND` / `SCENE_STATE_MISSING` / `COORD_PARTIAL` / `BLOCKING_CHAR_UNRESOLVED` / `SHOT_NO_DUPLICATED` / `CHAPTER_SUBMIT_INCOMPLETE` … |
| **结构类（两轮耗尽）** | 同上，且该镜已用掉 2 轮修复 | 写**最小合法骨架**（§8.2.2）+ `qc_status='fail'` + QC 记 `STRUCT_REPAIR_EXHAUSTED`（含原始提交） | **写骨架** | **继续** | `STRUCT_REPAIR_EXHAUSTED` |
| **语义类** | 动作塞不下、连续性冲突、站位变化无依据、焦段与景别不符 | **正常写入**（保留创作意图）+ 写 `qc_reports`（fail/warn/info）+ 更新 `qc_status` | 写 | 继续 | `QC_<CODE>`（在 `hits[].code` 里） |
| **系统类** | 数据库写入失败、changelog 写入失败、QC 写入失败、求解器异常、`assertGlobalOrder` 失败 | 回滚**当前事务**（逐镜时=该镜；需重排的批次=整批）+ 抛明确错误 | **不写**（回滚） | 逐镜时：其他镜不受影响；批次事务回滚时：本批全部未写；**求解失败时：该场全部镜本轮不写，其他场次继续** | `TX_FAILED` / `CHANGELOG_WRITE_FAILED` / `QC_WRITE_FAILED` / `CONTINUITY_SOLVER_FAILED` / `GLOBAL_ORDER_BROKEN` |

**五条硬边界**：

| # | 边界 |
|---|---|
| E-1 | 系统类**不得**被当成语义类记录（把"QC 写不进去"降级成一条 `hits` 是掩盖故障） |
| E-2 | 语义类**不得**导致其他镜停止（进待修清单，其他镜继续） |
| **E-3** | **结构类只拒"该镜"，不得因为一镜非法而拒掉同批合法镜**（V2 此处写反了：它要求整批拒绝，与 D02-01 §7.1 E1 相反） |
| **E-4** | 「结构拒写」与「两轮耗尽的骨架」是**两种不同结果**，不得混记：前者 0 行 + 错误码；后者有行 + `qc_status='fail'` + `STRUCT_REPAIR_EXHAUSTED` |
| **E-5** | 与失败镜有连续性依赖的后续镜，**不得伪造 PASS**（§8.2.3） |

> 为什么结构类也必须逐镜隔离：D02-01 §7.1 的核心保证是"**没有任何一类错误会无条件停止整条流水线**"，E1 明确写"该镜 fail，其余继续"。章级批量若整体拒绝，等于让第 3 镜的笔误否决第 1、2 镜的正确创作 —— 用户看到的是"什么都没保存"。

#### 8.2.1 修复轮次：按镜计数，不按批次

| 项 | 做法 |
|---|---|
| 计数位置 | `ctx.repairRoundsByShot[shotId]`（存在 agent 执行上下文的**内存**里，随 `ctx` 走） |
| 键 | **具体 `shotId`**；不是"本章"，也不是一个总数 |
| 首次结构失败 | `rounds` 0→1，返回错误码，允许 LLM 修（第 1 轮） |
| 再次失败 | `rounds` 1→2，返回错误码，允许 LLM 修（第 2 轮） |
| 第三次仍失败（`rounds === 2`） | **不再给机会**：直接写最小合法骨架 + `qc_status='fail'`，该镜在本请求内关闭 |
| 第 1 轮就修好 | 正常写入，**不进入人工待处理**（不得因为"曾经错过一次"就打标） |
| 生命周期 | 单次用户请求内有效；请求结束即丢；**不得**跨请求累计，**不得**写进 `story_shots` |
| 不新增列 | 不为此加任何列（§8.2.2 的"不新增字段"同理） |

> "2 轮"的含义要写死：**2 次修复机会 = 最多 3 次提交**。把"2 轮"理解成"2 次提交"，会让合法镜在第 2 次就被迫落骨架 —— 那会把"模型第一次漏字段、第二次补齐"的正常情况判成失败。

#### 8.2.2 最小合法骨架（`STRUCT_REPAIR_EXHAUSTED`）

骨架的目标只有一个：**让这一镜在库里可定位、可追溯、可人工修，而不是假装它成立。**

| 项 | 要求 |
|---|---|
| 真实标识 | `project_id` / `chapter_id` 必须是**真实存在**的行；`id` 由 `uid()` 新生成（不得冒用别的镜的 id） |
| 编号 | `shot_no` / `global_no` 走 §4.4.1 的正常分配（骨架也是一次合法插入，不特殊对待） |
| `scene_key` | 必须指向已存在的 `scene_states` 行；**若连这一步都做不到 → 不建骨架**，返回 `SKELETON_NOT_CONSTRUCTIBLE`（连骨架都不合法的镜，只能拒） |
| NOT NULL 字段 | 只填真实值（`project_id`/`chapter_id`/`scene_key`/`shot_no`/`global_no`）；其余走 DDL 默认值 |
| 未知内容 | `visual_content=''`、`dialogue=''`、`composition=''`、`lighting=''`、`shot_size=''`、`cam_pos=NULL`、`cam_distance_m=NULL`、`fov_deg=NULL`、`cam_target=''` → **表达"未知"，不填占位值** |
| 置信 | `fill_confidence=0`、`spec_source='ai'`、`qc_status='fail'` |
| **禁止编造** | 不得造人物、资产、坐标、动作、站位、空间基线；`shot_assets` / `shot_actions` / `shot_blockings` **一行都不写**（宁可缺，不造假） |
| 派生状态 | **不写** `shot_states`（没有 `blockings`/`actions`，求解没有输入；硬算只会产出一串假 `unknown` 以外的噪声） |
| QC | 该镜**一条** `qc_reports`：`target_type='shot'`、`level='fail'`，`hits` 含 `{rule_id:'STAGE3-STRUCT', code:'STRUCT_REPAIR_EXHAUSTED', level:'fail', field:'*', expected:'合法结构', detail:<原始提交 JSON>}` |
| 人工识别 | 靠 `qc_status='fail'` + `hits` 里的 `STRUCT_REPAIR_EXHAUSTED` 识别"待人工处理"，**不新增 `status` 字段**（D01 无此列，且 `qc_status` 不是生命周期状态） |
| changelog | 骨架插入要留一条 `story_shot` 的 create 日志（否则"这行哪来的"无从查） |

#### 8.2.3 依赖隔离：后续镜不得伪造 PASS

某镜被结构拒写（或被骨架替代）后，同场后续镜的前序状态就**不可信**了。三种处理里只能选一种，V3 选第三：

| 方案 | 结果 | 采用 |
|---|---|---|
| 让后续镜照常继承"上一镜"（跳过被拒镜） | 状态跳变 → 一串假 `POSITION_JUMP`/`TELEPORT` | ❌ |
| 让后续镜全部 `unknown` + PASS | `unknown` 被当 PASS，等于宣称"没问题" | ❌ |
| **本轮延后同场后续链** | 不写 `shot_states`、不写状态类 QC；QC 记 `CONTINUITY_DEFERRED`(info)；其余场次与独立分支照常 | ✅ |

| # | 规则 |
|---|---|
| DG-1 | 延后范围 = 被拒镜所在 `scene_key` 中 `global_no` **大于**被拒镜的那些镜（同章跨场不受影响） |
| DG-2 | 延后的镜**不写** `shot_states`（不是写一条 unknown，是不写）；已存在的旧 `shot_states` **保留原值**并在读接口标 `stale: true`（由 F-3 不变量可检出） |
| DG-3 | 其余场次、其余章、其余独立分支**继续处理**（这是"局部依赖隔离"，不是"整批停摆"） |
| DG-4 | 被拒镜修复成功后的下一次提交，由 §7.8 的失效规则把整条链重算（不靠"记得回来补"） |
| DG-5 | 延后**不得**被静默：返回结果里必须列出 `deferred: [{shotId, reason}]` |
| DG-6 | **求解器抛错**（系统类）→ 该场**全部**镜本轮不写（含已通过结构校验的），返回 `system_failed`；**不得**"只写内容、不写状态"（那是半成品，且违反 TX-2 同生同死） |

### 8.3 事务边界（TX-1~TX-7，**随逐镜隔离重排**）

| # | 边界 | 要求 |
|---|---|---|
| TX-1 | 单镜内容写入（`story_shots` 全字段 + `shot_actions` + `shot_blockings` + `shot_assets`） | **一个事务**，任一步失败整体回滚该镜 |
| TX-2 | 该镜的 `shot_states`（受影响的那些）+ `qc_reports` + `change_logs` | 与 TX-1 **同事务**（V3-A-05 的核心要求不变，作用域=该镜） |
| TX-3 | 连续性求解的**计算** | 在事务**外**（纯函数、不碰库） |
| **TX-4** | **需要重排的章级批量**（插入/调换/删除/换章） | **一个事务**：两阶段重编 + 可写集全部镜的内容 + 状态 + QC + 审计。理由见下方"为什么这一种要整批" |
| **TX-5** | **不需要重排的章级批量**（纯追加 / 就地更新） | **逐镜事务**：每镜一个 TX-1+TX-2；某镜系统错误只回滚该镜 |
| TX-6 | `clear: true` 的删除 | 单事务（先删从表后删主表），且先过 §8.7 的保护检查 |
| TX-7 | 文件系统操作 | **不在事务内**，提交后再清理（D02-03 V3 的 `Projects.remove` 同一条纪律） |

**为什么"需要重排"这一种要整批、其余逐镜**：

| 事实 | 结论 |
|---|---|
| `uq_ss_sn` / `uq_ss_gn` 是**即时检查**的唯一索引，两阶段重编必须先写负值再写正值 | 负值**不得越过事务边界**（否则库里有负编号，任何读都会炸） |
| 重编涉及多镜的号，无法拆到"每镜一个事务" | 重编 + 该批内容必须同一个事务 |
| 但重编前，结构非法的镜已在**阶段 0** 被剔出可写集（纯内存判定） | 事务里剩下的全是结构合法的镜，此时失败只可能是**系统类** → 整批回滚是**正确**语义 |
| 纯追加不重编（V3-B-06） | 没有跨镜约束，逐镜事务即可，一个镜的系统故障不牵连别的镜 |

> 这条设计同时满足两个看似冲突的要求：B-01/B-06 的"重排必须同一事务、不得留负值"，与 A-05 的"每镜是原子写入单元、单镜失败不牵连其他镜"。**冲突只发生在"既重排又要逐镜"的场景，而那个场景被"阶段 0 预校验剔除非法镜"消掉了。**

**事务失败时的边界（必须写进实现）**：

| 情形 | 结果 |
|---|---|
| 逐镜事务中第 3 镜失败 | 第 3 镜 0 行（业务/状态/QC/审计全回滚）；第 1、2 镜已提交且不受影响；返回里明确"第 3 镜系统失败" |
| 批次事务中任一镜失败 | 本批**全部**未写（含编号重排）；返回里明确"本批回滚，编号未变更" |
| 不得发生 | 业务行已写但 QC/changelog 缺失；动作/站位/资产只写了一半；把 DB/QC/审计/求解器异常记成语义冲突 |

### 8.4 章级批量（`set_storyboard`，**逐镜失败隔离**）

| 步骤 | 要求 |
|---|---|
| 1 | 全部镜先完成**结构预校验**（含资产解析、`scene_key` 存在性、编号可达性、章提交完整性 §4.4.1.4） |
| 2 | 结构非法镜 → **移出可写集**，返回**每一条**错误（不是只报第一个），其余镜照常进入写入 |
| 3 | 语义类错误**不阻断**：正常写入 + 各自 QC |
| 4 | 写入成功后：镜、关联资产、状态、QC、审计五者一致（按 TX-4/TX-5 的边界） |
| 5 | **重试幂等**：`(chapter_id, shot_no)` upsert + 资产组整组替换 → 同一请求重放**不产生重复镜、不产生重复资产行、不重复生成 QC 冲突行** |
| 6 | 单镜修改（`set_shot_detail`/`set_shot_actions`/`set_shot_blockings`）**不得**覆盖同章其他镜（`updated_at` 不变） |
| 7 | 同场后续链因被拒镜而**延后**的，按 §8.2.3 处理并列入 `deferred` |
| 8 | 返回结构必须能区分四类镜：`written` / `rejected`（带错误码与 field）/ `deferred`（带原因）/ `system_failed`（场级，带错误码） |

**为什么不能"整批拒绝"（V2 的写法）**：

| 视角 | 整批拒绝的后果 |
|---|---|
| 用户体验 | 第 3 镜少一个字段，第 1、2 镜写得再好也全丢，界面提示"保存失败"，用户不知道错在哪一镜 |
| 模型行为 | 模型看不到"哪些镜其实成功了"，会**全章重写**，把已经对的镜也改坏 |
| 冻结语义 | `D02-01 §7.1` E1 明写"该镜 fail，其余继续"；`§6.5` 明写"2 轮仍失败 → 落库但 `qc_status='fail'`" |

### 8.5 `qc_reports` 写入契约（V2-B-02 + V2-B-03 / **V3-B-04**）

| 字段 | 取值 | 依据 |
|---|---|---|
| `id` | `uid()` | — |
| `project_id` | 当前项目 | — |
| `target_type` | **`shot`**（阶段 3 只用这一个值；冻结域是 `shot`/`unit`/`package`/`video`） | D01-05:727 |
| `target_id` | `story_shots.id`（镜级报告） | — |
| `ruleset_ver` | 常量，形如 `d01-v7/stage3.1`（实现时定版一次，之后**只增不改**） | — |
| `level` | **`pass` / `warn` / `fail` / `info`** 四值 | D01-05:730 |
| `hits` | JSON 数组，**一条 = 一条规则的执行结果（含 `pass`，不只是异常）**：`{rule_id, code, level, applicable, field, fields[], expected, detail}`；`rule_id` 写 D01 编号（`V-01`/`A-12`/`S-24`…）。口径见 §8.5.2 | — |
| `created_at` | `now()` | — |

#### 8.5.1 报告粒度

**一次工具调用 → 每镜一条 `qc_reports`**（`target_type='shot'`, `target_id=<镜 id>`）。

| 反例 | 为什么不行 |
|---|---|
| 每条规则一条 | 表会被撑爆（69 条规则 × 每镜），且"取最新整体结论"要聚合几十行 |
| 一次调用只写一条（不分镜） | `target_id` 只能填一个镜，其他镜的命中失去归属 |

#### 8.5.2 `hits` 的结构：一条规则一条结果（**V3-B-04**）

V2 写的是 `hits = [] → level = 'pass'`，即**只记异常**。后果是：全通过时 `hits` 为空，**"一共跑了多少条规则、多少条真的过了"这个信息不存在**，于是 `verifiable_ratio` 的分母无从计算 —— 报告里那个比例只能靠人工填一个数。这不是"实现细节"，是口径不可执行。

**改为"逐规则结果"**：

| 字段 | 取值 | 说明 |
|---|---|---|
| `rule_id` | D01 编号（`V-01`/`A-12`/`S-24`） | 与 §六 矩阵一一对应 |
| `code` | 结果码（`PASS` 或具体冲突码） | `pass` 结果的 `code` 统一写 `PASS` |
| `level` | `pass` / `warn` / `fail` / `info` / `''` | `applicable=false` 时写 `''`（无结论） |
| `applicable` | `true` / `false` | 该规则对本镜**是否适用**（D01-04 §5.3 的 `not_applicable` 落到这里） |
| `fields[]` | 命中的**全部**字段路径（长度 ≥1，含 `field` 本身） | 同规则多字段命中**合并进这一条**，不拆成多条 |
| `field` | 主字段（最严重的那一个） | 单字段命中时与 `fields[0]` 相同 |
| `expected` | 期望值/期望形态 | 供 LLM 修 |
| `detail` | 附加信息 | 如 `GLOBAL_NO_IGNORED` 的旧值 |

**四条计数规则**：

| # | 规则 |
|---|---|
| QL-1 | **每条适用规则在每镜内只产生一条记录**：唯一键 `(target_id, rule_id)`。同一规则的多个字段结果写进 `fields[]`，该条 `level` 取各字段的**最高档**（`fail > warn > info > pass`）。写库前断言无重复 `(target_id, rule_id)`，重复即缺陷 |
| QL-2 | **`pass` 必须入 `hits`**：规则跑了且通过，就写一条 `{code:'PASS', level:'pass', applicable:true}`。没有它，`verifiable_ratio` 不可算 |
| QL-3 | **`not_applicable` 写 `applicable:false` + `level:''`**：保留"考虑过但判为不适用"的证据，但**不进任何统计** |
| QL-4 | 报告级 `level` = 在 `applicable:true` 的条目里取最高档（`fail > warn > info > pass`）；**若一条 `applicable:true` 都没有 → `level='info'`**（不是 `pass`，见 8.5.3 的空报告规则） |

**INFO 分成两类（这条是 B-04 的要害）**：

| 类 | code 集合 | 含义 | 统计归属 |
|---|---|---|---|
| **数据不足**（真·不可验证） | `STATE_UNKNOWN`、`AXIS_UNVERIFIED`、`SCREEN_LR_UNVERIFIED`、`CAM_BASIS_DEGENERATE`、`COORD_SYSTEM_INCOMPLETE`、`ROLL_SIGN_UNKNOWN`、`ROLL_UNVERIFIED`、`CROWD_SWITCH_UNKNOWN`、`POWER_GEOMETRY_UNKNOWN`、`GATE_FIELD_UNMAPPABLE` | "没有可信来源，判不了" | 计入 **U**（分母） |
| **有意跳过** | `TIME_JUMP_SKIPPED`、`CONTINUITY_DEFERRED` 等 | "规则主动不执行"或"本轮不执行" | **X，不参与统计** |

> V2 把 `TIME_JUMP_SKIPPED` 也算进"不可验证"，是错的：`time_jump=1` 时跳过差异校验是**规则设计**，不是数据缺失。把它算进分母会系统性地拉低可验证率，让人误以为数据质量差。

#### 8.5.3 `verifiable_ratio` 的可计算口径

**先分类，再算比例**（三桶互斥，覆盖全部条目）：

```
D = |{ e : e.applicable === true  &&  e.level ∈ {pass, warn, fail} }|
U = |{ e : e.applicable === true  &&  e.level === 'info' && e.code ∈ UNVERIFIABLE_CODES }|
X = 其余（applicable=false 的 N/A；applicable=true 但 info 且 code 不在 UNVERIFIABLE 的"有意跳过"）

verifiable_ratio = (D + U === 0) ? null : D / (D + U)
```

| # | 要求 |
|---|---|
| VR-1 | `D + U === 0` 时 `verifiable_ratio = null`，并输出 `ratio_state='no_applicable_rules'`；**不得**写成 `1.0`（"什么都没验"≠"全过"），**不得**写成 `0.0`（"全没验"≠"全错"） |
| VR-2 | `not_applicable`（`applicable:false`）既不进 `D` 也不进 `U`（D01-04 §5.3） |
| VR-3 | 必须能**从库里读回 `hits` 复算出同一个值**：给定同一份 `hits` JSON，任何人用上面三行公式得到同一个比值。禁止"报告里手写一个比例" |
| VR-4 | 报告摘要必须**同时**给 `fail_count` 与 `verifiable_ratio`（只报前者会把"数据缺失"伪装成"质量合格"） |
| VR-5 | 状态侧的可验证率（D01-04 §5.3 原义，按字段 `rel` 算）与 QC 侧的可验证率（本节，按规则算）**是两个数**，报告里分开写，不得混称一个 `verifiable_ratio`。状态侧叫 `state_verifiable_ratio`，QC 侧叫 `rule_verifiable_ratio` |
| VR-6 | 聚合口径：单镜报告算单镜的比值；章级/项目级摘要**先把所有镜的 `hits` 摊平、再按 `(target_id, rule_id)` 去重**，然后套同一公式。不得"先算每镜比值再平均"（那会让规则少的镜占更大权重） |

**状态侧口径（D01-04 §5.3 原义，供对齐）**：

```
state_verifiable_ratio = 已判定字段数 / (已判定字段数 + unknown 字段数)
已判定 = shot_states.meta 里 rel ∈ {known, inferred} 的字段条目（不含 __solver）
unknown = rel === 'unknown'；rel === 'not_applicable' 不计
```

#### 9.2.1 求解器 Hash 的持久化位置（**V3-B-05**）

**问题**：`shot_states` 是冻结的 **8 列**（`shot_id` / `state_in` / `state_out` / `meta` / `derived_from` / `state_source` / `conflicts` / `updated_at`），**没有 `solver_hash` 列**。V2 §9.2 说"用求解器 `hash` 追溯派生状态"，却没说它存在哪 —— 于是"可追溯"只是句口号。

**不能新增列**（D01-05 冻结）。合法落点只有两个：`derived_from`（字符串，语义已被 `prev_shot:<id>` / `scene_baseline` 占满）与 `meta`（JSON，D01-05 注释为"字段级可靠性"）。选 `meta` 的**保留命名空间**：

```json
{
  "chars.as_char_roxanne.pos": { "rel": "known", "src": "prev_shot:sh_10", "conf": 0.92, "ver": 7 },
  "chars.as_char_kaisen.facing": { "rel": "inferred", "src": "rule:facing_from_gaze", "conf": 0.55, "ver": 7 },
  "__solver": {
    "hash": "sha256:…",
    "solver_version": "stage3.1"
  }
}
```

**八条规则**：

| # | 规则 |
|---|---|
| SH-1 | `__solver` 是**求解器元数据**，不是字段可靠性条目：它不是 `chars.<id>.<field>` 形态、不描述任何创作字段、不参与可靠性统计 |
| SH-2 | `posRel(row)` 与一切字段 `meta` 遍历（含 §8.5.3 的 `state_verifiable_ratio`）**必须跳过 `__solver`**，且必须是**显式跳过**（`if (key === '__solver') continue`），不得靠"解析失败就忽略" —— 后者会把真正拼错的键一起吞掉，V-19 就废了 |
| SH-3 | V-19（meta 键必须是可解析字段路径）对 `__solver` **放行**。理由：V-19 的意图是"防拼错 key 导致可靠性标记静默失效"，`__solver` 不是可靠性标记载体。**除此之外不放宽任何键**：非 `__solver` 且不可解析 → 仍 FAIL |
| SH-4 | `hash` = `sha256:` + 对**本次实际参与计算的输入**做 `canonicalStringify`（§5.3）后的摘要。输入至少含：`solver_version`、`scene_key`、`scene_states` 中参与求解的列、本场镜头按 `global_no` 的 `(id, global_no, scene_key, time_jump, spec_source, spec_version, fill_confidence)`、每镜 `shot_blockings` / `shot_actions` / `shot_assets(role ∈ {character, prop})` 的求解相关列。**不得**只绑 `shot_id` 或 `updated_at`（那样输入变了 hash 不变，等于没绑） |
| SH-5 | 纯函数：**不得**读时钟、不得读数据库、不得读 `process.env`、不得依赖调用顺序或对象键插入顺序 |
| SH-6 | 同输入必同 hash：跨进程、跨机器、跨 locale 结果一致（排序用 `cmpStr`，禁用 `localeCompare`） |
| SH-7 | 写入时机：落 `shot_states` 时在**同一条 upsert** 里写 `meta.__solver`。它随派生结果一起生灭，`shot_states` 不进 changelog（§9.2） |
| SH-8 | **语义边界（必须写清，否则会被误判成 bug）**：`__solver.hash` 记录的是"**该行内容最后一次被实际改写时的求解版本**"。若输入变了但派生内容逐字未变，该行按 §7.8.3 **不重写**，hash 保持上一版 —— 这是**预期语义**（内容确实还是那一版算出来的），不是"hash 没更新"。**不得**为了"让 hash 看起来最新"而重写未变化的行（那会让 C-3、C-11 的"前序不动"全线失败） |

#### 9.2.2 必须测试（SH-01~SH-08）

### 9.3 复合主键改造（四处 + 两处配套，缺一处就出错）

| # | 位置 | 现状 | 改成 |
|---|---|---|---|
| 1 | `ENTITY_META[entity].pk` | 字符串 | **`string` 或 `string[]`（数组表示复合主键）** |
| 2 | `rawGet(entity, id)`（`changelog.js:88`） | `WHERE <pk> = ?` | 数组时 `WHERE a = ? AND b = ?`，参数从 `id` 拆开 |
| 3 | `applyInverse` 的 DELETE（`changelog.js:246`） | `DELETE ... WHERE <pk> = ?` | 同上 |
| 4 | PG `ON CONFLICT (<pk>)`（`changelog.js:262`） | `(id)` | `(a, b, c)` |
| 5 | **`entity_id` 的生成**（`changelog.js:132`） | 复合表没有 `id` 列 → 落空串 | 新增 `meta.entityIdOf(row)`；复合表返回 `parts.join('\u001f')` |
| 6 | `projectIdOf`（`changelog.js:93`） | 解析失败 `return null`（**静默丢日志**） | 新实体标 `strictProject: true` → 解析失败**抛错**（同 `render_selection` 的处理） |

**`entity_id` 的分隔符**：用 `'\u001f'`（US 控制符）。理由：`uid()` 是 `crypto.randomUUID()`（`utils.js:5`），只含 `[0-9a-f-]`，永远不会包含 `\u001f`；用 `'|'` 或 `':'` 在未来出现自定义 id 时会有歧义。

**拆回的地方只有一处**：`rawGet`/`applyInverse` 收到 `entity_id` 后按同分隔符 `split('\u001f')` 还原参数数组。要求写一个 `pkArgsOf(meta, entityId)` 辅助函数，**两处共用**，不得各写一份。

### 11.1 接口

### 11.2 归属校验（照抄现有范式）

```
Projects.get(id) 不存在                        → 404 { error: '项目不存在' }
```

## 十四、取证方法（B-10）

### 14.1 两种哈希不能混用

| 类型 | 算法 | 长度 | 命令 | 用途 |
|---|---|---|---|---|
| **Git blob SHA-1** | SHA-1 over `"blob <len>\0" + 内容` | 40 hex | `git hash-object <file>` | 与"文档里给的 SHA"对齐 |
| **文件 SHA-256** | SHA-256 over 文件字节 | 64 hex | `sha256sum <file>`（或 Node `crypto`） | 内容取证、防篡改 |

**判定规则**：40 位十六进制 → 几乎必然是 Git blob SHA-1（或 commit SHA）；64 位 → SHA-256。**不得拿 40 位值去和 64 位值比"是否一致"** —— 那是必然不一致的伪命题（V1 就错在这里）。
