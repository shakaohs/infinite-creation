## 二、QC carried 的真实生产调用链

```
POST /continuity/run
  └ runSceneQuality({ plan })                     ← plan 来自 planInvalidation()（真实调用，不是测试造的）
      ├ ck2Audit()                                ← 映射自检（不合格整体拒绝）
      ├ loadSceneInput() → solveLoaded()          ← 求解（P8 链路不变）
      ├ persistSceneStates()                      ← 落库，返回"库里实际那一行"
      └ tx(每镜)：
          prevReport = latestReport(shotId)       ← 只取最新一份；ruleset_ver 不一致 = 没有历史
          qisRules   = plan.qcInvalidationSet[shotId].rules
          buildShotReport({ prevReport, qisRules, stateSnapshotHash })
            ├ 逐条规则现算 rule_dependency_hash
            ├ 可继承 ⇔ 规则不在 QIS ∧ 历史 applicable ∧ 历史 hash === 现算 hash
            ├ 继承条目 source='carried'、carried_from=<prevReport.id>
            ├ reportLevelRules 单独出口（不得 carried）
            └ assertCarriedIntegrity()（QL-6/7/8，写库前）
          saveReport()                            ← 只与最新一份比，同则复用
      └ gateOf()                                  ← 报告级结论
```

与上一轮的差别：**没有 `plan` 就是全量重建，一条都不继承**（`qis = null`）；有 `plan` 才允许继承。
这条把"什么都没变"与"全都要重算"分开了 —— 否则 carried 会退化成"默认不跑"。

## 三、QIS 与规则级 Hash 的对应验证（`【实跑】`，单镜样本）

| `source='run'`（不适用） | **28** —— `applicable:false`，本来就没有结论可继承，不是"重跑了" |
| `source='report_level'` | **3** —— 三条审计规则各一次 |

36 + 2 + 28 + 3 = 69，一条不多一条不少。关键对照：

- **QIS 内 100% 实跑**（QL-6）：`V-09`/`V-13` 的 `source` 都是 `run`；`C1`/`C2` 逐条断言。
- **carried 只发生在"规则级 Hash 相等"处**（CF-4）：`C10` 逐条比对继承条目的 `rule_dependency_hash`
  与来源报告相同，且 `code/level/field/fields` 原样沿用（继承的是结论，不是"重新算一遍然后说继承"）。
- **不连坐**：`C3` 证明 `qc_dependency_hash` 变了（说明这条 change 确实影响了一部分规则），
  同时 `carried` 仍有 30+ 条 —— 如果按报告级 Hash 判失效，carried 会是 0。
- **不伪造**：`C7`（清空历史 → 全部实跑，carried=0）、`C8`（`ruleset_ver` 不一致 → carried=0）。
- **QR-10**：`C5` 直接喂一条"hash 已变却标 carried"的条目 → 抛 `QC_CARRIED_STALE`；
  结构性错误（QIS 内标 carried / `carried_from` 不对）抛 `QC_CARRIED_INVALID`；
  QIS 规则缺实跑条目抛 `QC_RUN_COVERAGE_MISSING`。生产侧这三条写在 `buildShotReport()` 的写库前检查里，
  正常路径不会产出它们 —— 所以反例只能注入，这是测试手段的边界，不是覆盖缺口。
- **QL-9**：`C4` 用两个数据相同的项目对比"带 plan（有继承）"与"全量重建"，

## 四、`__solver_input` 六字段与 `hash_relation`（`【实跑】` 原样数据）

```json
{
  "qc_input_hash":      "sha256:c381df26c02d902960c4768b0396e88274ad4ee62e40680b35e3d01a8d0b0cdc",
  "state_snapshot_hash":"sha256:c381df26c02d902960c4768b0396e88274ad4ee62e40680b35e3d01a8d0b0cdc",
  "qc_dependency_hash": "sha256:04bf3cea8192806f03f483d5357890ce99ed86c3c014e68220087972681ca4a2",
  "ruleset_ver":        "d01-v7/stage3.1",
  "hash_algo_ver":      "qcdep-2",
  "solver_version":     "stage3.1",
  "hash_relation":      "same"
}
```

| 项 | 来源 | 说明 |
|---|---|---|
| `qc_input_hash` | `solveContinuity()` 返回的 `hash` | SH-10：**不另算第二套**，同一事务内复用同一个值 |
| `state_snapshot_hash` | 库里那一行的 `meta.__solver.hash` | 本轮 QC **实际读到**的快照；内容没变时它就是上一版 |
| `qc_dependency_hash` | `qcDependencyHashDetail(ctx).hash` | 正式字段；上一轮自造的 `rule_dependency_set` **已删除** |
| `ruleset_ver` / `hash_algo_ver` / `solver_version` | 常量 | 与 D02-06 §8.5 / §9.2.1 一致 |
| `hash_relation` | `state_snapshot_hash` vs `qc_input_hash` | `same` / `state_older`；缺任一 Hash 直接抛（不拿 B 顶替 A） |

`state_older` 的真实产出（`C6`）：改 `blockings.power_level`（在求解 Hash 的映射内、但不参与派生），
结果 `state_snapshot_hash ≠ qc_input_hash` 且 `hash_relation='state_older'`，状态行**未被重写**。

> 关于 `qc_missing`：D02-06 §9.2.1 把它定义为"该镜没有 QC 报告"（API 视角）。本报告内调用时 A 一定存在，
> 所以这个值在本层不会产出；缺 A 属于调用方缺陷，直接抛 `QC_REPORT_INVALID`，**不用 B 冒充 A**（F-4）。

## 五、状态内容 Hash 修复前后对照（R1-2）

| 场景 | 修复前 | 修复后 | 证据 |
|---|---|---|---|
| 输入变、派生内容逐字未变（改 `power_level`） | `meta` 进比较 → 判"变了" → **重写状态行**、`updated_at` 刷新、`__solver.hash` 被换成新值 | 判"没变" → **不写**、`updated_at` 不变、`__solver.hash` 保留上一版 | `P13`：`written=0`、`meta` 逐字相同、`hash_relation='state_older'` |

| 业务内容真变（`norm_x`、`state_out`） | 更新 | 更新（不变） | `P5`；`P12` 反例 |

`__solver` **仍原样落库**，只是不参与"内容有没有变"的比较。

## 七、删镜/移场与状态清理（R1-5，`【实跑】`）

**先核对调用链**（`【静态】`）：`shot_states` 只有 `shot_id`，**没有 `project_id` / `scene_key`**；
`lib/` 内没有单镜删除路径（`DELETE FROM story_shots` 零命中），项目级删除走 `db.js` 的级联；
移场只是改 `story_shots.scene_key`，行主键不变。

**结论：自动清理无法安全实现，撤销承诺。**

| 情形 | 旧代码（空转） | 现行为 | 为什么不能删 |
|---|---|---|---|
| 删镜 | 查询"本场仍在 `story_shots` 的镜头"→ 查不到被删的那条 → 永不删除，却对外说"会清理" | **不删**，行成孤儿 | 拿到 `shot_states` 行时已无法证明它属于本项目（无 project_id/scene_key），全表删除会误伤其他项目/场次 |
| 移场 | 同上 | **不删** | 该行仍是这一镜的状态；删掉等于删掉新场次的输入快照 |

`P7` 的真实操作（不是手删 `shot_states` 制造通过）：`DELETE FROM story_shots`（连带从表）→ 重跑本场 →
断言被删镜的状态行**原样保留**、另一场次的状态行**未被触碰**、被移场镜的行仍存在；
返回值里也**不再有** `deleted` 字段（不宣称做不到的事）。

**正确做法（未实现，属后续）**：在**知道 `scene_key` 的写路径**（删除/移场的调用点）显式清理，
或给 `shot_states` 加归属列（DDL，未授权）。记 U-P9-7。
