## 二、问题一：P2/P4 的启动循环依赖

### 2.1 循环是怎么形成的

| 要素 | D02-36 原文 | 事实 |
|---|---|---|
| P2 判据 | 「TST-LOCK-01~13 真实跑通，11~13 必须 PG 真库」 | TST-LOCK 测的是 `txProject`/`txProjects` |
| `txProject`/`txProjects` 在哪实现 | — | **A-05**（阶段 A） |
| P4 判据 | 「`shot_videos` 并入 manifest，重新生成并校验通过」 | 校验对象是 A-04 重新生成的 manifest |
| manifest 修改在哪 | — | **A-04**（阶段 A） |
| 冻结条件 | §12.3「五个动作全部完成后才能开始阶段 A」，其中包含 P2 与 P4 | ⇒ **冻结要求 A-04/A-05 已完成；阶段 A 开始又要求先冻结** |

**一句话**：P2/P4 测的是「还没造出来的东西」，把它们放进冻结前置，等于要求「先做完再开工」。

### 2.2 修复后的唯一顺序链

```
① 用户审批（P1 / P3）
        ↓
② 其余冻结前置（P5 清单 / P6 排期 / P7 PG 可连）
        ↓
③ 任务书冻结（Draft → 已冻结）
        ↓
④ 阶段 A 实施（A-01~A-08）
        ↓   A-04 → 【P4】     A-05 + TST-LOCK-01~13 → 【P2】
⑤ P2 与 P4 通过（阶段 A 退出 Gate）
        ↓
⑥ 阶段 B 实施
```

### 2.3 修复前后对照

| 项 | 修复前（D02-36 原稿） | 修复后（本轮） |
|---|---|---|
| 冻结前置 | P1、P3、P5、P6、**P2**、**P4**、P7（§12.3 五个动作含 P2/P4） | **P1、P3、P5、P6、P7**（五项，全部在冻结前可完成） |
| P2 位置 | 冻结前置（同时又被写在阶段 A 验收里） | **阶段 A 退出 Gate**（A-05 完成后触发） |
| P4 位置 | 冻结前置 | **阶段 A 退出 Gate**（A-04 完成后触发） |
| 未通过 P2/P4 | 语义模糊（既说「保持未满足」，又说「阶段 A 不得宣告完成」） | **不得进入阶段 B**（阶段 A 内部可继续修） |
| 冻结动作 | 五个动作（含 P2/P4） | 五个动作（P1/P3 批准、P5 清单、P6 排期、P7 连接、**冻结签署**） |
| 阶段 A 退出条件 | 「DDL 冻结」一句 | **P2 与 P4 均通过 + DDL 冻结** |

### 2.4 测试要求没有降低（逐条对照）

| 要求 | 修复前 | 修复后 |
|---|---|---|
| TST-LOCK 条数 | 13 条 | **13 条**（不变） |
| 11~13 必须 PG 真库 | 是 | **是**（不变，且写进阶段 A 退出表与 §8.4） |
| 能否用 SQLite 替代 | 不能 | **不能**（新增两处明文：§8.3.2 不降级声明、§8.4 硬纪律） |
| manifest 校验 | 重新生成 + 校验通过 | **不变**，并新增「不得手改 manifest 让它绿，必须由生成脚本产出」 |
| 未通过后果 | 「不得进入阶段 B」（文字散落） | **统一为「停在阶段 A，不得进入 B」**，且写明「宁可停，不可带着未验证的锁协议往下走」 |

### 2.5 代价（如实记录）

P2 未通过时，项目会**停在阶段 A**，而不是「先进阶段 B、回头补锁测试」。这是刻意选择：锁协议如果没在 PG 上真跑过，阶段 B 的五个写入器全部建在未验证的地基上，返工成本远高于停等。**这个代价必须写在排期里，不能等 P2 红了才讨论。**

## 四、问题三：U-36-1 对 Stage 3 必需审计的 fail-closed 边界

### 4.1 原方案为什么不够

| 问题 | 说明 |
|---|---|
| 覆盖面错 | `console.warn` + 计数是**观察手段**，不是**约束手段**：它允许「Stage 3 写成功、审计静默丢失」继续发生 |
| 判定被稀释 | 若把「计数」当过渡期指标，很容易演变成「计数不为 0 也能过」，V5 的判据被悄悄放宽 |
| 与 D-30-15 冲突 | D-30-15 要求「审计失败与业务同事务回滚」，`warn` 恰恰是「不回滚」 |

### 4.2 二分口径（写死）

| 类 | 实体 | 未登记 / 解析失败时 | 能否用 warn + 计数 |
|---|---|---|---|
| **A 类 · 必需审计（5）** | `scene_state`、`story_shot`、`shot_asset`、`shot_blocking`、`shot_action` | **一律 fail-closed：抛错 + 业务事务回滚** | **不能**，零例外 |
| **B 类 · 非必需** | 其余实体（既有 6 实体之外的、且不在 A 类的） | 保留 `console.warn` + 计数 | 可以，但**不得**影响 Stage 3 审计完成判定 |

**B 类的判定边界**：`warn` + 计数**只用于**「将来可能新增、但不属于本轮强制审计范围」的实体；它**不是**通过依据，也不得出现在 V5 的任何断言里。

### 4.3 A 类的六个必失败条件

| # | 条件 | 触发位置 | 错误码 | 事务行为 |
|---:|---|---|---|---|
| 1 | `ENTITY_META` 未登记该实体 | `recordChange` 入口（按 `entity` 查表前） | `AUDIT_ENTITY_META_MISSING` | 抛错 → 整个 `txProject` 回滚 |
| 2 | 项目归属无法解析（反查 `story_shots` 为空 / `project_id` 为空串） | `projectIdOf` | `AUDIT_PROJECT_UNRESOLVED` | 同上 |
| 3 | 复合主键无法准确定位（`rawGet` 命中 0 行或 >1 行） | `rawGet`（数组键路径） | `AUDIT_PK_AMBIGUOUS` | 同上 |
| 4 | `before` / `after` 快照无法读取（行缺失、JSON 解析失败） | `rawGet` + 形状判定 | `AUDIT_SNAPSHOT_UNREADABLE` | 同上 |
| 5 | 审计记录写入失败（`change_logs` INSERT 抛错） | `recordChange` 写入段 | **原错上抛**（不改写成更温和的错误） | 同上 |
| 6 | 回滚请求落在多列主键实体 | `applyInverse` | `ROLLBACK_UNSUPPORTED_ENTITY` | **拒绝回滚**（不是审计失败；D-30-15 既定规则不变） |

### 4.4 五条纪律

1. A 类的审计写入与业务写入**必须在同一个 `txProject` 内**，禁止 after-commit 补记（补记失败时业务已提交，等于永久丢审计）。
2. 禁止 `try/catch` 后吞掉上述任一错误再返回成功；`catch` 只允许「记录上下文后原样上抛」。
3. `console.warn` + 计数**只对 B 类**有效，且不得进入 V5 判定（V5 只看 A 类）。
4. B 类名单必须是代码里的**显式常量**（白名单）；新增实体**默认落入 A 类**，要降级必须改常量并留说明。
5. `applyInverse` 对多列主键的拒绝策略**不因本轮放宽**：本轮只提高审计严格度，不恢复任何回滚能力。

### 4.5 与既有规则的关系（没有重新设计 changelog）

| 既有规则 | 本轮是否改动 |
|---|---|
| `ENTITY_META.pk` 扩数组 | **不改**（A-06 既定） |
| `rawGet` 支持数组键、单列行为不变 | **不改** |
| `projectIdOf` 对复合表反查 `story_shots` | **不改** |
| `applyInverse` 多列主键拒绝 | **不改**（条件 6 只是把它写进 A 类清单） |
| 审计失败回滚业务 | **不改**（本来就是 D-30-15 主条，本轮把它细化成六个可执行条件） |
| B 类 `warn` + 计数 | 保留，但**范围被收窄**到非必需实体 |

**一句话**：本轮**没有**新增 changelog 能力，只是把「哪些实体不许静默」说清楚，并给每个失败点一个错误码。
