## 三、当前生产架构事实（本轮新取证）

### 3.1 场次：三个概念在库里是混在一起的

| 概念 | 当前载体 | 证据 |
|---|---|---|
| 场景**资产**（地点/环境实体） | `assets` 中 `category='scene'` 的行 | `scene-state.js:56~66` `assertSceneAsset()`：非空时必须属于本项目且 `category='scene'` |
| 剧情**场次实例** | `scene_states` 一行；`id` 是 uuid PK，`UNIQUE(project_id, scene_key)` | `tables.js:70`、`:382` |
| 场次**排序** | 无独立字段；顺序由 `story_shots.global_no` 隐式表达 | `story_shots` DDL 无 `scene_no` |

**当前所有 join 都走 `scene_key` 字符串**（`load-scene.js:164/170/174/178`、`persist-state.js:166`、`scene-state.js` 的 upsert、`invalidate.js` 的 `byScene` 索引），而 `scene_states.id` **没有任何代码引用**（除 PK 自身）。

`scene_key` 的生成方式是**字符串**：`S02_病房`（`openclaude-agent.js:276` 给 LLM 的指令原文：「建议形如 S02_病房 / S03_天台」）。**序号 + 名称都嵌在身份里** ⇒ 改名或移动场次必然要改 key。

### 3.2 音频：三套载体、一个 CHECK

| 载体 | 内容 | 证据 |
|---|---|---|
| `shots.audio_ids` | 资产 id 数组，允许 `voice`/`music`/`sfx` 三类 | `db.js:873` `SHOT_REF_FIELD_CATEGORIES.audio_ids = AUDIO_ASSET_CATEGORIES`；`shared/index.js:46` |
| `shot_assets(role='voice')` | 结构化绑定，`CHECK (role <> 'voice' OR order_no BETWEEN 1 AND 3)` | `tables.js:198` |
| `story_shots` 文本列 | `dialogue` / `narration` / `sfx` / `music_cue` / `speakers` | `tables.js` story_shots 段 |
| `story_shots.voice_ids` | **派生列**，由 `writeShotAssets` 按 `role='voice' ORDER BY order_no` 回填 | `shot-assets.js:212` AS-9 |

`role` 的冻结值域是 `character` / `scene` / `prop` / `costume` / `age` / `voice`（`enums.js:170`，源 D01-05 §4.6），**不含 music/sfx**；AS-4 在查库之前就先拦（`shot-assets.js:108` 注释 + `:18` 定义）。

### 3.3 并发：单写者、同步、无场次锁

| 能力 | 现状 | 证据 |
|---|---|---|
| 驱动 | `node:sqlite` 的 `DatabaseSync`（**同步**），PG 走 worker + Atomics 同步门面 | `db-driver.js:11`、`:63` |
| WAL / busy_timeout | `PRAGMA journal_mode = WAL; PRAGMA busy_timeout = 5000` | `db-driver.js:69` |
| 事务 | `tx()` 用裸 `BEGIN`（deferred），**只接受同步函数**（返回 thenable 即抛 `ASYNC_TX`），嵌套时内联 | `db.js:480~496` |
| 场次级互斥 | **不存在** | 全仓无锁表、无 `BEGIN IMMEDIATE` |
| 任务防重 | `jobs`（状态机 + `checkpoint`）、`queue_items`（`lease_until` / `worker_id` / `dedupe_key` / `attempts`）、`scheduler.js` 的租约心跳 | `db.js:215`、`scheduler.js:246/417` |

**为什么现在不出并发事故**：JS 单线程 + 同步驱动 ⇒ 单进程内两次 `runSceneQuality` 天然串行；真正的竞争只来自**多进程**（Next 多实例、CLI 与 Web 同时跑）。WAL 允许一写多读，第二个写者会在 `busy_timeout` 5s 后拿到 `SQLITE_BUSY`。

## 四、决策一：legacy 与 Stage 3 的最终权威关系

### 4.1 三个阶段的唯一写入权威（冻结）

| 阶段 | 唯一写入权威 | 另一侧的角色 | 进入条件 |
|---|---|---|---|
| **A 当前** | legacy（`shots` + `*_ids` + `blocking` + `sub_shots`） | Stage 3 仅模块能力，无生产写入 | 现状 |
| **B 过渡** | **按项目分流**：`structured_spec=0` → legacy；`=1` → Stage 3 | 结构化项目的 legacy 形状由 **Stage 3 现算**（读侧投影，不落库）；legacy 项目的 Stage 3 表为空 | P10-A 完成 |
| **C 接管** | Stage 3（`story_shots` / `shot_assets` / `shot_blockings` / `shot_actions` / `scene_states`） | legacy `shots` **冻结只读**（历史资产与产物指针） | §4.4 八条门槛全过 |

**任何阶段都不允许「同一项目内两套都能写」。** 这条不是本轮新提，是 D01-05 §六原文：「按项目分流：`structured_spec=true` → 新表；否则 → `shots`。**同一项目内不会出现两份都能写**」【正式规范】。

### 4.2 为什么否决「同事务逐镜投影」（B1）

任务书要求比较 B1（同事务）与 B2（可靠待办）。**B1 在技术上可行，在语义上不可行。**

技术可行性【代码推断】：`tx()` 单进程同步、嵌套内联，把 legacy 写入与 stage3 投影放进同一个 `tx()` 没有异步障碍；失败整体回滚，「legacy 成功、stage3 静默失败」不会发生。

语义不可行，三条硬证据：

| # | 事实 | 后果 |
|---|---|---|
| 1 | `shots` 一行 = **生成段**，`story_shots` 一行 = **镜**；1:N | 投影必须先切分。切分依赖 `sub_shots` 解析，**格式 C 无镜信息**，`story_duration` 置信度 0.2（D01-05 §5.2） |
| 2 | `shots.blocking` 是**画面方位文本**（13/66 有值），`shot_blockings` 是 `norm_x/norm_y/norm_z` + 朝向 + 轴线 | 从文本反推归一化坐标＝**编造几何**，违反 `scene-state.js` 第一条铁律与 D01-05 §2.5 |
| 3 | `shots.audio_ids` 含 music/sfx，`shot_assets.role` 无这两个值，AS-4 明令禁止 | 全量映射必被 AS-4 拒绝；只能丢，丢了又没有任何地方记录「丢了什么」 |

**如果强行投影**，产出的 `story_shots` 行会「列齐全但内容是猜的」：`shot_size` 空、`norm_*` 空或编造、`time_slices` 由 0.2 置信度的切分得来。这比没有行更危险 —— 69 条规则会把它当**真实结构化数据**判，`fill_confidence` 只能标在 `story_shots` 上（0.2），而下游 `shot_states`/`qc_reports` 不会继承这个置信度。

### 4.3 为什么也否决 B2（可靠待办 / outbox）

| 问题 | 说明 |
|---|---|
| 需要新表 | outbox 必须有 `pending_projection` 之类的表（DDL），本轮禁止 |
| 引入第三种真相 | legacy 已提交、outbox 待投影、stage3 未写 —— 三者同时存在，任何读方都要判断「该信哪个」 |
| 补偿逻辑是新子系统 | 重试、去重、死信、监控，全部要新建；D02-06 RC-6 对同类诉求的原话是「不得因此扩展成任务调度/重试子系统」 |
| 没有消费方 | 当前 `story_shots` 消费者只有 `loadSceneInput`（求解/QC），而它需要的是**高质量结构化数据**，不是「迟早会有」的数据 |

### 4.4 采用的过渡机制：分流 + 一次性迁移 + 读侧投影（B0）

```text
                ┌──────────────────── structured_spec = 1 ────────────────────┐
用户 / Agent →  │ Stage 3 正式写入入口（P10-A 之后）                          │
                │   story_shots / shot_assets / shot_blockings / shot_actions │
                │   scene_states                                              │
                └───────────────────────────┬─────────────────────────────────┘
                                            │ 读侧现算（不落库）
                                            ▼
                                   legacy 形状投影（listShotsCompat）
                                            │
                                            ▼
                                   旧界面 / 旧 API / 旧投喂链

                ┌──────────────────── structured_spec = 0 ────────────────────┐
用户 / Agent →  │ legacy 写入（shots + *_ids），Stage 3 表保持为空             │
                │ 需要结构化 → 走 M3 一次性迁移（事务内、可回滚、迁移后切 flag）│
                └─────────────────────────────────────────────────────────────┘
```

三条纪律：

1. **投影方向只有一个**：Stage 3 → legacy 形状，纯读、现算、不落库、带 `_projection: true`；任何写回必须先看到该标记就拒绝。
2. **存量项目升级是一次性迁移**，不是持续同步：迁移在一个事务内完成（`tx()`），失败整体回滚、`structured_spec` 保持 0；成功后才切 flag。
3. **迁移可分批、可回滚**：每批记录 `migration_batches`/`migration_items`（阶段 1 已有表），回滚＝删本批新建行 + flag 复位。

> 现状差距：`listShotsCompat()` 在代码里**不存在**【源码确认】。D01-05 §六把它写成了设计（「旧页面/旧 API 过 `listShotsCompat()`，在内存把 `render_units + render_unit_shots + story_shots` 渲染成 `shots` 形状」），属【文档描述】，P10-A 必须补。

### 4.5 字段映射矩阵（legacy → Stage 3，迁移用）

`可逆` 列的含义：迁移后能否无损还原回 legacy 形状。

| legacy `shots` | Stage 3 落点 | 关系 | 可逆 | 处置依据 |
|---|---|---|---|---|
| `id` | 不迁移（新 `story_shots.id`） | — | 否 | 镜是切分产物，与段不同粒度 |
| `idx` | `story_shots.shot_no`（章内） | 1 → 1..n | 否 | 按 `sub_shots` 切分 |
| `chapter`（**标题**） | `chapter_id` | 需 `chapters.title → id` 查表 | 是 | `chapters` 无 `UNIQUE(project_id,title)` ⇒ 重名必须 fail-closed（`LEGACY_CHAPTER_AMBIGUOUS`） |
| `scene_name` | `scene_key`（+ 待批的 `scene_uid`） | 文本 → 场次实例 | 否 | 文本不是身份，映射可能需人工确认 |
| `camera`（文本） | `composition`/`lighting`/`shot_size`/`cam_*` 等 20 列 | **不迁移** | — | D01-05 §五：「无法可靠拆分全部」 |
| `visual` | `visual_content` | 1:1 文本 | 是 | — |
| `dialogue` | `dialogue` | 1:1，**权威仍是它** | 是 | D01-05 §五 |
| `narration` | `narration` | 1:1 | 是 | — |
| `sub_shots` | `time_slices` + `story_duration` | 解析三格式 | 格式 A/B 可，C 否 | D01-05 §2.4 / §5.2 |
| `blocking`（文本） | `shot_blockings`（结构化行） | **不迁移** | — | 文本无法反推坐标；编造即违规 |
| `duration`（**单元**时长） | `story_duration`（镜时长） | 1:N 切分 | 否 | D01-05 §5.2 |
| `character_ids` | `shot_assets(role='character')` | 数组 → 行，`order_no` = 数组下标 + 1 | 是（顺序保住） | `shot-assets.js` 契约 |
| `scene_ids` | `role='scene'` | 同上 | 是 | 且必须满足 AS-8（= `scene_states.scene_id`） |
| `prop_ids` | `role='prop'` | 同上 | 是 | — |
| `costume_ids` | `role='costume'` | 同上，`variant_of` = 对应角色 id | 是 | `variant_of` 语义 |
| `age_ids` | `role='age'` | 同上 | 是 | — |

| `video_prompt` | 不迁移（降级为最近编译结果指针） | — | 否 | D01-05 §五 |

### 4.6 事务边界与 SQLite 行为（阶段 B 的具体要求）

| 场景 | 事务边界 | 依据 |
|---|---|---|
| Stage 3 单镜写入（`story_shots` + 三从表） | **一个 `tx()`**，任一步失败整体回滚 | D02-06 TX-1【正式规范】 |
| 该镜状态 + QC 报告 | 与上一条**同事务** | TX-2；现状 `run-scene.js:161` 已如此 |
| 求解计算 | 事务**外**（纯函数） | TX-3 |
| 需要重排的章级批量 | 一个事务（两阶段重编，负号不得跨事务） | TX-4 |
| 场次求解抛错 | 该场**不开事务**（`continuity_runs` 一行 `failed` 单独短事务） | TX-8 + §8.2.4 |
| 一次性迁移（M3） | 一个事务；失败回滚且 `structured_spec` 不变 | 【建议方案】 |

**SQLite 具体行为（已实测前提）**：WAL 模式下读不阻塞写；写者串行，第二个写者在 `busy_timeout=5000ms` 内自旋等待，超时抛 `SQLITE_BUSY`。`tx()` 用 deferred `BEGIN`，即「第一次写才升级为写锁」——两个进程可能都先读到旧数据再竞争写锁，**这是 RC-1 要求 `BEGIN IMMEDIATE` 的直接原因**（§7.4）。

## 五、决策二：场次实例的稳定身份

### 5.1 三概念必须分开（冻结口径）

| 概念 | 身份载体 | 可变性 | 说明 |
|---|---|---|---|
| 场景**资产** | `assets.id`（`category='scene'`） | 可换（换景） | 一个资产可被多个场次实例引用（同地点不同时间，D01-04 §2.1） |
| 剧情**场次实例** | **`scene_states.id`**（uuid） | **不可变** | 本决策的主角 |
| 场次**排序** | 无（隐式 = 首镜 `global_no`） | 可变 | 排序变化不得影响身份 |

### 5.2 现状证据（决定了方案取舍）

| 事实 | 证据 | 影响 |
|---|---|---|
| `scene_states.id` 是 uuid PK，但**无任何代码引用** | `tables.js:70`；全仓 grep 仅 DDL 命中 | 稳定身份**已存在**，只差被引用 ⇒ 不需新建实体表 |
| 所有 join 走 `scene_key` 字符串 | `load-scene.js:164/170/174/178`、`persist-state.js:166`、`invalidate.js:251` | 改身份必须同时改这些读法 |
| `scene_key` 由「序号 + 名称」拼成 | `openclaude-agent.js:276` 的 LLM 指令原文 | 改名/移动即改身份 ⇒ 违反「名称变化不改变身份」 |
| `story_shots` 无场次 uuid 列 | `tables.js:87` 段 | 需 1 列 |
| `scene_states.scene_id` 是**资产**引用，不是场次身份 | `scene-state.js:56` | 不能拿 `scene_id` 当身份（虚拟场次为空、一个资产多场次） |

### 5.3 三方案比较

| 方案 | 改名稳定 | 移动稳定 | 顺序稳定 | 同名冲突 | 拆分/合并 | 成本 |
|---|---|---|---|---|---|---|
| **A 稳定 UUID**（复用 `scene_states.id`） | ✅ | ✅ | ✅ | ✅ | 可定义 | 1 列 + 1 索引 + 回填 |
| B 复合业务键（`project` + 章 + 序号） | ✅ | ❌（移动即变） | ❌（插入即变） | ✅ | 困难 | 0 DDL，但语义不达标 |
| C 复用 `scene_key` 字符串 | ❌（改名要改 key） | ❌ | ✅ | ✅ | 靠改字符串 | 0 DDL，但违反「不得字符串拼接猜身份」 |

### 5.4 唯一推荐：A（`scene_states.id` 为身份，`scene_key` 降为别名）

**语义变更（需批准）**：

- `scene_key` 从「身份」降为「项目内唯一别名」，**允许改名**（改名不改身份，因此不再触发 `state_rev` 语义上的"新场次"）。
- 所有求解/QC/失效的场次定位改走 `scene_uid`（= `scene_states.id`）。
- `scene_key` 保留 `UNIQUE(project_id, scene_key)` 作为别名唯一性约束。

**最小 DDL（本轮不实施）**：

```sql
ALTER TABLE story_shots ADD COLUMN scene_uid TEXT NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS idx_ss_uid ON story_shots(project_id, scene_uid, global_no);
-- 回填：UPDATE story_shots SET scene_uid = (SELECT id FROM scene_states st
--   WHERE st.project_id = story_shots.project_id AND st.scene_key = story_shots.scene_key)
--   WHERE scene_uid = '';
```

回填后必须校验：`COUNT(*) WHERE scene_uid=''` = 0，否则中断迁移（说明存在无基线的场次，需先建 `scene_states` 行）。

### 5.5 改名 / 移动 / 拆分 / 合并的身份规则（冻结）

| 操作 | 身份处理 | 数据动作 | 禁止 |
|---|---|---|---|
| **改名** | id 不变 | `scene_key` 与展示名可改；`state_rev + 1` 仅表示"基线被编辑" | 不得因改名新建 `scene_states` 行 |
| **移动**（换章 / 换位置） | id 不变 | 改 `story_shots.chapter_id` / `global_no`（两阶段重编） | 不得改 `scene_uid` |
| **拆分** | **新场次 = 新 uuid** | 原场次保留；被拆出的镜显式改 `scene_uid` + `scene_key` | 不得复制 `scene_states` 行后让两行共享同一 id |
| **合并** | **保留其中一个 uuid** | 被并场的镜改指保留方；被并场的 `scene_states` 行**保留不删**（无镜引用即自然失效） | 不得删除被并场的历史行（旧 `shot_states`/`qc_reports` 仍可能引用它） |
| **换景**（同一场次换场景资产） | id 不变 | 改 `scene_states.scene_id`，并按 AS-8 同步 `shot_assets(role='scene')` | 不得因换景新建场次 |

### 5.6 与 `scene_states` / `story_shots` 的一致性要求

1. `story_shots.scene_uid` 非空时，必须存在同项目 `scene_states.id`（应用层校验，不建外键——D01-05 §3.4「无外键」是冻结事实）。
2. `scene_states` 的删除只允许「零镜引用」时进行，且必须检查 `shot_states` / `qc_reports` 的历史引用（§9）。
3. 求解入口的一次调用仍只处理一个场次（ORD-3 不变），只是定位键换成 uid。

## 六、决策三：voice / dialogue / music / sfx 的数据归属

### 6.1 四概念矩阵（冻结）

| 类型 | 含义 | Stage 3 归属 | 是否资产引用 | 是否进 Hash | 权威 |
|---|---|---|---|---|---|
| **Dialogue** | 台词文字 | `story_shots.dialogue` | 否（文本） | 是（`ci_c` 组） | `dialogue` 列，legacy 与 stage3 同名字段 |
| **Voice** | 音色/配音资产 | `shot_assets(role='voice')` ≤3 条；`story_shots.voice_ids` 派生 | 是 | 是（`shotAssets[*]`） | `shot_assets` |
| **Music** | 背景音乐 | `story_shots.music_cue`（**文本线索**）；资产引用**无落点** | 部分 | 文本进 Hash，资产不进 | 文本＝`music_cue`；资产＝legacy `audio_ids`（仅 legacy 项目） |
| **SFX** | 音效 | `story_shots.sfx`（文本线索）；资产引用**无落点** | 部分 | 同上 | 同上 |

`dialogue` 与 `voice` **不得混为一类**：前者是文字（谁说什么），后者是音色资产（用谁的声音说）。`story_shots.speakers` 描述"谁在说话"，与 `voice_ids` 的"用哪个音色"是两件事。

### 6.2 三方案比较

| 方案 | 内容 | 判定 |
|---|---|---|
| A 保留 legacy `audio_ids` | 过渡期不动 | **过渡期采用**，但仅限 `structured_spec=0` 的项目 |
| B 扩展现有正式关系模型 | 把 music/sfx 塞进 `shot_assets` | **否决**：需改 `role` 值域 + CHECK + AS-4，属正式规范变更，且 AS-4 的理由（music/sfx 是整段铺底，不是镜头级参考）成立 |
| C 新增 `shot_audio` 表 | 独立音频关系表 | **P10 不做**：当前没有任何消费方需要它（`refs.js:183` 读 `audio_ids` 组参考包；两条赛道的音频编译属阶段 4）；新增即"为未来可能的需求先建表"，违反「不得凭实现便利新增表」 |

### 6.3 唯一结论（冻结）

1. **P10 不新增任何音频表、不扩 `shot_assets.role`、不改 AS-4。**
2. `audio_ids` → `shot_assets` 的迁移**只取 `voice` 子集**，且 `order_no` 按原数组顺序；voice 超过 3 条必须**显式报错**（`LEGACY_VOICE_OVERFLOW`），不得静默截断。
3. music / sfx 在结构化项目上**只有文本线索**（`music_cue` / `sfx`），**没有资产引用**。这是一条已知能力缺口，必须写进 P10-A 的验收说明，不得当作「已完成迁移」。
4. 何时补：**阶段 4 音频编译**前必须定案（届时才知道 music/sfx 需要时间轴、音量、起止点中的哪些）。本轮登记为 **U-26-3**。

### 6.4 对两条赛道编译输入的影响

| 赛道 | 现在读什么 | 结构化项目下会缺什么 |
|---|---|---|
| Seedance / H3 单镜生成 | `refs.js` 从 `shots.audio_ids` 取音频参考包 | **music/sfx 的音频参考文件**（voice 可由 `shot_assets` 补） |
| 阶段 4 双赛道编译 | 尚未实现 | 音频轨编排需要 music/sfx 的资产与时间位置，属阶段 4 范围 |

### 7.2 十个并发场景的处置（冻结）

| # | 场景 | 当前行为 | P10 要求 | 需要什么 |
|---:|---|---|---|---|
| 1 | 同一场次同时触发两次求解 | 单进程串行；多进程第二个拿 `SQLITE_BUSY` | 第二个**放弃并返回明确码**，不重试覆盖 | `BEGIN IMMEDIATE` + 事务内输入复核 |
| 2 | 求解中用户改镜头 | 计算结果基于旧输入，写入覆盖新状态 | 提交前比对输入指纹，不一致即弃写 | 事务内重读 `story_shots`/三从表/`scene_states.state_rev` 的指纹 |
| 3 | 求解成功、保存报告失败 | 现状同事务，整体回滚 | 保持 | 已具备（`run-scene.js:161`） |
| 4 | 状态保存成功、事务提交失败 | `tx()` 回滚 | 保持 | 已具备 |
| 5 | QC 执行期间资产被改 | 读到旧实体，Hash 按旧值 | 与 #2 同一机制（资产指纹进同一比对） | 同上 |
| 6 | 同一失效计划被重复消费 | `saveReport` 按「最新一份 + 双 Hash」幂等 | 保持 | 已具备 |
| 7 | 任务进程中途退出 | 无记录可查 | 写 `continuity_runs(status='failed')` 或靠 `run_no` 缺号识别 | `continuity_runs` |
| 8 | 用户恢复后重复执行 | 重新全量跑 | 幂等（内容 Hash 不变不刷 `updated_at`） | 已具备 |
| 9 | 两条赛道同时读共同数据 | 只读，无冲突 | 保持；编译**不得**写共同表 | 阶段 4 |
| 10 | 两条赛道各自失败重试 | 阶段 4 | 失败只影响本赛道 | 阶段 4 |

### 7.3 三方案比较

| 方案 | 能否承载 | 结论 |
|---|---|---|
| A SQLite 事务 + 输入 Hash + 幂等写入 | 能覆盖「写一致性」与「重复提交」，**不能**覆盖「上次到底跑成没跑成」 | **必选，但不充分** |
| B 复用 `jobs` / `queue_items` | `queue_items` 有 `lease_until`/`worker_id`/`dedupe_key`/`attempts`，形式像；但**无 `scene_key`、无 `input_hash`**，且 `pool/kind` 语义是渲染任务 | **否决**（D02-06 §8.2.4 已逐条排除；硬塞会把渲染队列与求解记录混成一个状态机） |
| C 新增 `continuity_runs` | 8 列刚好覆盖「哪场、第几轮、什么输入、成没成、为什么」 | **采用（待 PF-1 批准）** |

`continuity_tracking` **不是表**：它是响应里的一个字段，由「部署配置 + 能力探测」现算（`available` / `degraded` / `unknown`），CT-1 明令不得用 `try/catch` 把异常吞成 `degraded`。P10-D 实现时**不要**为它建表。

### 7.4 唯一推荐（冻结）

| 能力 | 结论 | 依赖 |
|---|---|---|
| 持久化运行记录 | **需要**，唯一新表 `continuity_runs`（8 列 2 索引，D02-06 冻结结构） | **PF-1 批准（DDL）** |
| 场次级互斥锁（锁表 / 租约） | **不需要**。用 `BEGIN IMMEDIATE` + 事务内输入指纹复核（乐观并发） | 新增 `txImmediate()`（无 DDL） |
| 过期结果识别 | 事务内比对「读时指纹」与「当前指纹」，不一致抛 `CONTINUITY_INPUT_CHANGED`，**不写任何行** | 同上 |
| 旧求解覆盖新状态 | 同上（同一道闸） | 同上 |
| 重复 QC 报告 | 已解决（`created_at DESC, id DESC` + `qc_input_hash` + `qc_dependency_hash`） | 无 |
| 安全恢复中断任务 | 靠 `continuity_runs` 最新一条 `status`；无记录 = 该场从未求解（**不得**解释为成功） | PF-1 |
| 复用 jobs/queue | **不复用**（渲染队列继续用它自己的） | 无 |

**输入指纹的冻结定义【建议方案】**：`(MAX(story_shots.updated_at), COUNT(*), MAX(shot_blockings 相关), MAX(shot_actions 相关), MAX(shot_assets 相关), scene_states.state_rev, assets.updated_at 最大值)` 的规范化摘要。**不复用** `solverInputHash`（那是求解输入的语义 Hash，不是并发指纹；混用会让"内容相同但指纹不同"误判为冲突）。

### 9.2 冻结设计（P10-B2 实施，本轮不写代码）

### 11.3 顺序可否调整

**B1 可以最后做吗？** 可以但不该：它是唯一「零 DDL、零依赖、能把 3 条规则从"假绿"变成"真判"」的项，先做能立刻缩小不确定性。

**A 与 B2 能并行吗？** 不能。`shot_assets.shot_id` 是指向 `story_shots.id` 的软引用（无外键），并行会写出一批指向不存在镜头的绑定，且没有任何约束会报错。

**D 能提前吗？** 不能。没有 C 的真实站位，`loadSceneInput` 在真实项目上必然 `SCENE_INPUT_EMPTY`，D 的"自动触发"只会自动触发失败。

## 十六、最终唯一推荐

**采用「分流 + 一次性迁移 + 读侧投影」，按 B1 → A → B2 → C → D → E 推进。**

一句话理由：能无损转换的方向只有一个（Stage 3 → legacy 形状），反方向缺 `blocking` 坐标与 `sub_shots` 镜级信息，任何自动投影都会**编造结构化数据**；而「编造的数据比没有数据更危险」是本项目从 P5 到 P9 反复付过学费的一条。

三件必须先批准的事：

1. **D-26-1**（分流方案）—— 它决定 P10-A 写什么，改起来最贵。
2. **D-26-9 + D-26-2**（`scene_uid` 与身份语义）—— 1 列 DDL，但不批就没有稳定的场次身份。
3. **D-26-10**（PF-1）—— 不批则 P10-D 的门禁永远是 `degraded`。

批准后的第一步**不是**写代码，而是 P10-B1 的 12 项测试先红后绿地跑一遍（当前 `shot_assets` 无生产行，测试必须自己造行，且要明确这是**测试夹具**不是生产数据）。
