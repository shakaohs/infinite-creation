## 四、状态持久化（`persist-state.js`）

### 4.1 字段映射（只认 DDL 与 D01-04 §5.1，不按字段名推断）

| `shot_states` 列 | 来源 | 变换 |
|---|---|---|
| `shot_id` | `states[id].id` | 必须存在，缺则抛 `STATE_PERSIST_INVALID`（写错镜头比少写一行严重） |
| `state_in` | `states[id].in` | 必须是对象 → `JSON.stringify` |
| `state_out` | `states[id].out` | 同上 |
| `meta` | `states[id].meta`（**metaOut**） | 同上；`meta_in` **不落库**（表里没有这一列，见 U-P9-2） |
| `derived_from` | `states[id].derived_from` | 原样（`scene_baseline` / `prev_shot:<id>`） |
| `state_source` | 常量 | 本轮只有 `solved`（`manual` 需标注持久化，P8-A 未授权 DDL） |
| `conflicts` | `states[id].conflicts` | 必须是数组 → `JSON.stringify`；`diagnostics` **不落库**（无列） |
| `updated_at` | `Date.now()` 或调用方注入 | 内容没变时不写这一列（见 4.2） |

### 4.2 幂等：比内容，不比主键

`stateContentHash(row)` 对 6 个内容列做规范化序列化后取 sha256（先解析 JSON 再按 `canonicalStringify`
排序键），因此**键序不同不算变化**，`updated_at` 不进 Hash。写库前逐镜比对：

- 相同 → `unchanged`，**不执行 UPDATE**（`updated_at` 不变，事后能看出"这一轮没重算"）；
- 不同 → `updated` / `inserted`，走显式 `ON CONFLICT(shot_id) DO UPDATE`。

为什么不用 `INSERT OR REPLACE`：它是"先删后插"，既无法表达"没变就不写"，也会把将来任何
外键/触发器一起带进坑里。任务书 §三.3 明确禁止"只依赖 `INSERT OR REPLACE` 就宣称幂等"。

### 4.3 carried 继承的可追溯性（`【实跑】` P2 / P3）

| 事实 | 证据 | 说明 |
|---|---|---|
| `src` 指向**起点镜**，不是"上一镜" | `P3`：3 镜只给第 1 镜站位 → `shot2.src === shot3.src === 'prev_shot:<shot1>'` | 与 P8 的 `originOf()` 语义一致；若逐镜改写，继承起点一丢就再也追不回来 |
| `derived_from` 才是"上一镜" | `P3`：`shot3.derived_from === 'prev_shot:<shot2>'` | 两个字段是两件事，混用会写出"看起来对"的错误链 |
| `rel` / `conf` 一起保留 | `P2` / `P3` 逐字段断言 | `conf` 是衰减基数，丢了会让下一轮的置信度无据可依 |
| 显式 `unknown` 的继承仍带起点 | `P2`：`rel='unknown'`，`src='carried:<某镜 id>'`，起点 id 必须是本场镜头 | 与 `U-P8-2` 的现状一致（未改语义） |
| `meta.__solver.hash` 随 `meta` 落库 | `P2` | 报告侧 `qc_input_hash` 与它同值（§五 R4） |

**没有做的事**：`meta_in` 不落库（无列）；`conflicts` 之外的 `diagnostics` 不落库（无列）；
`state_source` 不写 `manual`。三项都是"结构不支持"，不是"漏了"。

### 5.2 关联关系（没有加列的替代方案）

`qc_reports` 只有 8 列，没有 `solve_hash`。可追溯性靠三条既有信息：

1. `target_type='shot'` + `target_id=<镜 id>`（D02-06 §8.5 冻结域）；
2. `hits.__solver_input.detail` 里的 `qc_input_hash` / `rule_dependency_set` / `solver_version`；
3. 同镜多份报告按 `(created_at, rowid)` 倒序 = 历史，最前一条 = 当前有效。

代价如实写：**按 Hash 检索需要解析 JSON**，列级索引做不到（U-P9-1，建议加 `solve_hash` 列，未做）。

| 情形 | 行为 | 证据 |
|---|---|---|
| 相同输入重复执行 | **复用**同一份报告，不插新行（三重判据：`target_id` + `qc_input_hash` + `rule_dependency_set` 全同） | `R7`：第二次 `reused=true`，行数仍为 1 |

| 修复后重试 | 失败一次 + 修复一次 = 2 条报告（历史保留），再跑第三次 `reused=true` 不插行 | `G8` |

## 六、`reportLevelRules` 的真实消费（`【实跑】` R5）

**它不是配置，是 `planInvalidation()` 的返回字段**（`invalidate.js:508`，`['S-20','S-21','S-25']` 或 `[]`）。
所以"消费"只能发生在一个地方：**决定哪几条审计规则在报告级跑**。

实现（`qc/report.js`）：

1. `buildShotReport()` 把 `reportLevelRules` 列为**必填入参**，先过 `assertReportLevelRules()`：
   必须是 `string[]`、按 `cmpStr` 升序、元素必须 `scope==='audit'`、不得重复；否则抛 `QC_REPORT_INVALID`
   （`R6`：非审计级 / 逆序 / 重复 / 非数组 四种都被拒，且**一行报告都没写**）。
2. P5 的 `validateShot()` 本来就会把三条审计规则跑一遍。**直接把它的结果留在报告里，等于"没消费"**；
   追加一遍又是同一 `rule_id` 两条（QL-1 违规）。所以先摘掉 P5 跑的三条，再用**本报告全量 hits**
   （其它规则字段级命中）作 `__audit` 重跑 `reportLevelRules` 里的那几条，标 `source='report_level'`。
3. 可观察差异（`R5`）：

| `reportLevelRules` | 报告里 S-20 / S-21 / S-25 | 规则条目数 |
|---|---|---:|
| 默认（全量重建）`['S-20','S-21','S-25']` | 三条都在，`source='report_level'` | 69 |
| `[]` | **一条都不在** | 66 |
| `['S-20']` | 只有 S-20 | 67 |

这就是"真实消费"：同一个入口、同一批数据，改这个数组，报告内容随之改变，且不是靠断言"配置对象存在"。

**与规范的一处张力**（U-P9-4，需裁）：U-P6-2 #2 写"每次报告重建恰好一次，不得按镜摊开"，
而 D02-06 §8.5.1 规定报告粒度是"每镜一条"。本轮实现的是 **"每份报告内恰好一次"**（一份报告 = 一镜）；
"整场只算一次、落在哪儿"在冻结域里没有落点（`target_type` 只允许 `shot`），没有自行发明。

## 七、自动门禁（`qc/gate.js`，`【实跑】` G1~G9）

| 规则 | 实现 | 证据 |
|---|---|---|
| 默认放行 | `level ∈ {pass, warn, info}` → `decision='pass'` | `G1`（真实链路 2 镜）、`G4` |
