## 二、问题一：writer 权限模型

### 2.1 D02-28 的矛盾（确认成立）

D02-28 同时写了三条互斥的规则：
1. `system` 只能写 `updated_at` 和 `parent_shot_id`；
2. 投影使用 `system` 创建/更新生成段；
3. 投影必须写 18 个创作字段。

⇒ 2 与 3 推出「`system` 写 18 创作列」，与 1 直接冲突。**没有任何一种「角色 + 白名单」的微调能修好它**，因为投影的权限集合与「系统维护」的权限集合本质不同：前者要写**派生创作内容**，后者只碰元数据。

### 2.2 三方案比较

| 方案 | 做法 | 边界是否严格 | 评价 |
|---|---|---|---|
| A | 加第四类 `projection` | 严格（白名单可枚举） | 可行，但 `Shots.update` 会变成「四套语义 + 全量 32 列写」的巨型分支；且投影仍然共享 `Shots.update` 的读-改-写语义（§2.5 的丢失更新问题） |
| B | 保留三类 + 给 `projection` 发 capability（签名/token） | 取决于实现，易退化成「传个布尔值」 | 否决。运行时判据不是调用方身份，而是「谁传了这个参数」，等于没有边界 |
| C | **投影完全从 `Shots` 服务分离**：`projectRenderUnits()` 专用写入口 | **最严格**：白名单在 SQL 里，物理上不可能写到产物列 | **推荐** |

### 2.3 唯一推荐：方案 C

**【建议方案】**

```
projectRenderUnits({ projectId, chapterId, sceneUid, units, writer })
```

| 约束 | 内容 |
|---|---|
| 唯一调用方 | Stage 3 投影模块（`lib/core/render/project-units.js`）。导出面只到 `lib/core/index.js` 的 `projectSceneUnits()`，**不导出内部函数** |
| 可写列（白名单，SQL 字面量） | 18 个创作投影列 + 建行时的 `status='pending'`/`error=''`。**不含** `resolution`/`aspect_ratio`/`mode`/三张图/六个产物列/`parent_shot_id` |
| 禁止 | 不接受任意 `fields` 对象；入参是**结构化 unit 描述**（`unitId` + 18 个具名键），未知键直接抛 `UNIT_FIELD_NOT_ALLOWED` |
| 幂等 | 定位键 `shots.id = unitId`；`INSERT ... ON CONFLICT(id) DO UPDATE SET` 只列白名单列 |
| 事务 | 单事务：段行写入 + `story_shots.segment_id` 回写 + 段内顺序（`idx`）在同一 `txLocked(projectId)` 内（锁属 P10-A 前置，本轮不实现） |
| 失败 | 整批回滚，返回 `UNIT_PROJECTION_FAILED`（带 chapterId + 首个失败 unitId） |
| 不可绕过 | ① 不在 `Shots` 对象上挂任何投影方法；② Agent/HTTP 无对应工具与路由；③ 一条静态测试断言「`projectRenderUnits` 的调用方只有 `project-units.js`」 |

**为什么它比「加第四类 writer」更严格**：`writer` 是**运行时字符串**，任何调用方都能传 `'projection'`；而独立入口是**代码级边界**——`Shots.update` 的 32 列 SQL 里根本没有投影列白名单，传什么都会走「全列写 + 分组门禁」，而投影走的是另一条只有 18 列的 SQL。前者靠判据，后者靠结构。

### 2.4 writer 最终契约（三类，不含 projection）

| writer | 允许行为 | 禁止行为 |
|---|---|---|
| `creative` | `structured_spec=0` 时 legacy 创作写入；`structured_spec=1` 时**只写 Stage 3 实体**（`story_shots`/`shot_assets`/`shot_blockings`/`shot_actions`），项目上不因它写 `shots` 创作列 | 直接改生成段行；写产物列 |
| `render` | 只写 C 组 6 列（`video_path`/`video_prompt_used`/`seed`/`status`/`error`/`prompt_id`） | 写任何 A 组创作列；写 B 组参数列 |
| `system` | 生命周期与受控维护：`updated_at`、`parent_shot_id`（兼容列）、启动修复（`db.js:516` 的 status 复位） | 代替创作链或生成链写内容；充当投影 |

**投影不在这个表里**——它不经过 `Shots` 服务（§2.3）。

### 2.5 必填与迁移（统一口径，不留「默认 creative」）

D02-28 同时写了「必填」与「缺失按 creative」，本轮**取消后者**。

| 项 | 规则 |
|---|---|
| 缺失 `writer` | 抛 `SHOT_WRITER_REQUIRED`（含 `method` + 调用栈首帧），**不写库** |
| 迁移期兼容 | 提供 `legacyShotWrite(source, fn)` 包装器：显式声明来源字符串（如 `'agent:set_storyboard'`），内部以 `writer='creative'` 调用，并 `console.warn` + 计数一次 `LEGACY_WRITER_CALL` |
| 包装器禁止静默默认 | 它必须**要求** `source` 非空；空 source 抛 `LEGACY_WRITER_SOURCE_REQUIRED` |
| 删除条件 | ① 20 个写入点全部显式传 `writer`；② 一条静态测试断言「`lib`/`app` 内除包装器定义外无 `writer` 缺省调用」；③ 包装器调用计数在测试全量跑完后为 0 |

### 2.6 全量 UPDATE 的安全问题（比门禁更严重）

【源码确认】`Shots.update`（`db.js:984~1001`）：
1. 读整行 `s`；
2. `const m = { ...s, ...fields, updated_at: now() }`（`:987`）；
3. `UPDATE shots SET <32 列> ...`（`:997`）；
4. `recordChange`。

**两个必须解决的缺陷：**

**① 门禁必须看原始键集**：白名单判据只能是 `Object.keys(fields)`。若用 `m`，则「渲染只写 `video_path`」会被判成「要写 32 列」，永远过不了门禁；反之若门禁放松，`m` 里的旧创作列就会被写回。

**② 32 列全量写会覆盖并发修改（丢失更新）**：渲染在 `t0` 读到 `s`（含 `dialogue='A'`），用户在 `t1` 把 `dialogue` 改成 `'B'`，渲染在 `t2` 只写 `video_path` —— 但 SQL 会把 `m.dialogue='A'` 一起写回，**用户的修改被静默回滚**。
这不是理论风险：`renderShotCandidate` 全程持有 `prepared.shot`（`tools.js:2491`），一次渲染可能持续数十秒。

**【建议方案】必须拆两条 SQL**

| writer | SQL 形态 | 理由 |
|---|---|---|
| `creative` | 保持 32 列全量（现状） | 创作是整行语义，且调用方本来就给全字段 |
| `render` / `system` | **部分列 UPDATE**：`UPDATE shots SET <仅 keys(fields)>, updated_at=? WHERE id=?` | 物理上不可能覆盖没传的列 |

这条改动同时解决「未授权字段借由合并旧值覆盖数据库新值」——因为渲染路径**根本不读整行**。

## 三、问题二：六个生成参数的真实写入链

### 3.1 它们不是一类（这是 D02-28 的根因）

【源码确认】生成时的取值：

```js
// tools.js:2478
const mode = (shot.mode && VIDEO_MODES.includes(shot.mode)) ? shot.mode : inferVideoMode(references);
// tools.js:2484~2485
const reso  = ctx.project.video_resolution   || shot.resolution   || '480P';
const ratio = ctx.project.video_aspect_ratio || shot.aspect_ratio || '16:9';
```

⇒ **`shots.resolution` / `shots.aspect_ratio` 是「项目设置的回写副本」，不是镜级创作意图**。三处证据：

1. 生成时**项目值优先**，`shot.*` 只是兜底；
2. `Projects.update` 在改 `video_resolution` 时**主动同步全部分镜**（`db.js:644~647`，注释明写「应用内没有单镜分辨率入口，项目设置就是唯一开关」）；
3. 生成链每渲染一次就回写这两个字段（`tools.js:2564`、`:3484`）。

`mode` 有**派生兜底**（空/非法 → `inferVideoMode(references)`），是真正的镜级选择。
三张图（`first_frame_path`/`last_frame_path`/`reference_image_path`）只在 `mode` 为 `first_last`/`image` 时被读（`tools.js:2426~2452`），且是**用户上传**（「插入自定义分镜」）。

### 3.2 逐字段表

| 字段 | 正式权威 | Stage 3 保存位置 | 生成段读取位置 | 修改入口 | 投影规则 | Hash/版本影响 |
|---|---|---|---|---|---|---|
| `resolution` | **`projects.video_resolution`** | 不单独存（Stage 3 无此概念） | `ctx.project.video_resolution \|\| shot.resolution` | 项目设置（`PATCH /projects/:id`）+ 自动同步循环 | 投影写「项目当前值」（保持副本一致） | **不进**视频指纹（值由项目决定，项目一变全项目都变） |
| `aspect_ratio` | **`projects.video_aspect_ratio`** | 同上 | `ctx.project.video_aspect_ratio \|\| shot.aspect_ratio` | 同上 | 同上 | 同上 |
| `mode` | 镜级（创作侧） | **`story_shots` 无此列**（48 列无 `mode`）⇒ 暂存 legacy `shots.mode` | `shot.mode`，非法/空走 `inferVideoMode` | 分镜编辑 / Agent `update_shot` / `set_storyboard` | 段取首镜；组内不一致则**投影失败** | **进**指纹（决定工作流 kind） |
| `first_frame_path` | 镜级（用户上传） | 无列 ⇒ 暂存 `shots.first_frame_path` | `mode==='first_last'` 时读 | 「插入自定义分镜」上传 | 段取首镜；组内不一致则投影失败 | **进**指纹（内容+文件） |
| `last_frame_path` | 同上 | 同上 | 同上 | 同上 | 同上 | **进**指纹 |
| `reference_image_path` | 镜级（用户上传） | 无列 ⇒ 暂存 `shots.reference_image_path` | `mode==='image'` 时读 | 同上 | 同上 | **进**指纹 |

**一处留白必须点明**：`story_shots` 48 列里**既没有 `mode`，也没有三张图的路径**。所以「参数进入 Stage 3 创作数据」在当前 Schema 下**没有落点**——这是方案 B 被否的硬理由。

### 3.3 三方案比较

| 方案 | 做法 | 需要 DDL | 评价 |
|---|---|---|---|
| A | 参数仍存 `shots`，Stage 3 通过受控写入口（`render` 以外的授权路径）更新 | 0 | **推荐**。与现有生成链零改动兼容；把「谁能写」用 §2 的 writer 冻结 |
| B | 参数进 Stage 3（`story_shots` 加 4 列）+ 生成段只读投影 | 4 列 | 否决（本轮）。语义最干净，但会把「项目级副本」这个既有事实强行建模成镜级意图，且生成链要改 4 处读取 |
| C | 独立编译/生成配置实体 | 1 表 | 否决。阶段4 的 `render_units` 才是它的位置；现在建表等于提前做阶段4 |

**推荐 A，并冻结「分三段权威」**：

| 段 | 字段 | 权威 | 写入口 |
|---|---|---|---|
| 项目级 | `resolution`、`aspect_ratio` | `projects` | 项目设置（+ 同步循环），**不是** Stage 3 |
| 镜级模式 | `mode` | 创作侧 | 分镜编辑（`creative`） |
| 镜级图 | 三张 `*_path` | 创作侧 | 上传（`creative`） |

⇒ **D02-28 的「六个参数权威在创作侧」必须改为「2 个在项目、4 个在创作侧」**。

### 3.4 默认值与继承（逐项冻结）

| 项 | 规则 |
|---|---|
| 项目默认值 | `projects.video_resolution`（空 → `'480P'`）、`video_aspect_ratio`（空 → `'16:9'`） |
| 镜头级覆盖 | `resolution`/`aspect_ratio` **无镜级覆盖**（生成时项目优先）；`mode` 与三张图有 |
| 段内多镜参数冲突 | `mode`/三张图**不一致即投影失败** `SEGMENT_PARAM_CONFLICT`（fail-closed；静默取首镜会让其余镜的意图丢失） |
| 首尾帧归属 | 归段（生成读段行）；段内只允许一个镜声明，多镜声明视为冲突 |
| 「空」与「缺省」 | `mode=''` = 缺省（走 `inferVideoMode`），与「显式 `mode='text'`」不同；`*_path=''` = 无图，与「有图但文件缺失」不同（后者生成时抛错，`tools.js:2453`） |
| 参数改动后旧视频 | `mode`/三张图变化 ⇒ **过期**；`resolution`/`aspect_ratio` 变化 ⇒ **过期**（整项目级变化，见 §5.4） |
| 新段如何继承 | 从首镜的镜级值取；项目级值**不写进段**（永远现读项目） |
| 已有段是否自动更新 | 项目级两列：由 `Projects.update` 同步循环更新（现状），投影**不介入**；镜级四项：只有该镜创作字段变化时投影才写 |

## 四、问题三：三个指纹（必须完全分离）

### 4.1 三个指纹的分工

| 指纹 | 已有/新建 | 覆盖 | 用途 | 谁算 |
|---|---|---|---|---|
| `solverInputHash` | **已有**（`solve-hash.js`，7 列白名单） | 连续性求解输入 | 状态与求解结论的版本 | `runSceneQuality` |
| `qcDependencyHash` | **已有**（`qc/deps`，`qcdep-2`） | QC 规则依赖字段 | 报告复用与 carried | `buildShotReport` |
| **`segmentInputHash`** | **新建（只在生成侧）** | 一次渲染真正读到的全部输入 | 判断「这条视频是不是当前内容的产物」 | 生成前算一次、判定时现算 |

**三者不得互相替代**：`solverInputHash` 不含 `video_prompt`/`mode`/三张图/`duration` 之外的渲染参数；`qcDependencyHash` 不含 `seed`/文件路径；`segmentInputHash` **不含** `scene_states` 几何。混用会让「改了个备注」也判视频过期，或「改了台词」判不出来。

### 4.2 `segmentInputHash` 的字段集（按真实生成链枚举）

依据 `prepareShotForRender`（`tools.js:2417~2491`）与 `renderShotCandidate`（`:2494~2510`）实际送进工作流的参数：

```
sha256( canonicalJson({
  unit: {
    id,                  // 段身份（拆/合会变 → 必含）
    duration,            // seconds
    mode,                // 生效后的 mode（含 inferVideoMode 结果）
  },
  prompt,                // 实际送模型的完整提示词（= video_prompt 或 fallback 结果）
  frames: {              // 只含生效的那一组
    first, last,         // mode==='first_last'
    reference,           // mode==='image'
  },
  references: [          // assembleShotReferences 的产物，按 type+role+order 排序
    { type, role, assetId, variantOf, order }
  ],
  output: { resolution, aspect_ratio, width, height, scale },
  covered: [             // 段覆盖的创作镜头，按 global_no 升序
    { id, globalNo, dialogue, narration, visual, camera, composition, blocking, duration,
      characterIds, sceneIds, propIds, costumeIds, ageIds, voiceIds }
  ],
  algo: 'seg-1'
}) )
```

**逐条规则**

| 项 | 规则 |
|---|---|
| 键序 | 全部对象键按 `cmpStr` 升序（复用 `canonicalStringify` 的冻结规则，不新造） |
| 数组序 | `covered` 按 `global_no` 升序；`references` 按 `(type, role, order_no, assetId)` 升序；`*_ids` 按数组原序（顺序即参考图编号，`__MINIMAX_H3_REF_N__` 依赖它） |
| 缺失 vs null | 缺失键**不出现**；显式空串按 `''` 写入。二者不同（`''` 表示「显式清空」，缺失表示「没这个概念」） |
| 数值 | `duration` 保留 1 位小数；`resolution` 用档位字符串而非像素，`custom` 时补 `width`/`height` |
| 字符串编码 | UTF-8，不做 NFC 归一化（与既有 Hash 一致） |
| 时间戳 / `updated_at` | **不含**（否则每次保存都过期） |
| `seed` | **不含**。每次渲染随机取（`randomSeed()`，`tools.js:2497`），含它等于「生成完立刻过期」 |
| `status`/`error`/`video_path`/`prompt_id` | **不含**（产物自身） |
| 资产元数据 | 只含 `assetId` + `variantOf`（身份），**不含** `name`/`category`（改名不该让视频过期——那由 QC 管） |
| 算法版本 | `algo:'seg-1'` 进指纹；换算法即显式改前缀 |

### 4.3 三个指纹如何组合

- **求解与 QC**：只用前两个（不变）。
- **视频有效性**：只用 `segmentInputHash`。
- **门禁**：`qc` 结论 + `video` 有效性**各自独立**判；一份报告不因视频过期而改 level（视频过期不是 QC 规则），但**编译/导出**必须先过视频有效性。
- 交叉引用只做「记录」不做「计算」：报告里可写 `state_snapshot_hash`，视频行里写 `input_hash`，两者不互相推导。

### 4.4 存储：只加 1 列

| 侧 | 存哪 | 为什么 |
|---|---|---|
| 当前内容 | **现算**（每次判定时从 `shots` + 覆盖镜 + 资产引用算出） | 不需要列；多一列就多一处要维护的冗余 |
| 这条视频的输入 | **`shot_videos.input_hash TEXT DEFAULT ''`**（待批 DDL） | 只有它必须持久化——视频一旦生成，输入快照就没了 |

⇒ **否决 D02-28 的 `shots.segment_content_hash`**（不需要）。总 DDL 从 2 列降为 **1 列**。

**旧行兼容**：`input_hash=''` = **未知**（历史候选）。判定必须返回 `unknown`，**不得**当成「未过期」（fail-closed 的方向是「不当作有效」）。

## 五、视频过期判定与产物状态

### 5.1 过期判定矩阵

判定式：`expired = (selectedCandidate.input_hash !== segmentInputHash(now))`，`input_hash=''` → `unknown`（按过期处理，附 `reason='unknown_provenance'`）。

| 变化 | 当前视频是否过期 | 是否需重新生成 | 原视频是否保留 |
|---|---|---|---|
| 台词变化 | **过期** | 是 | 保留（候选变历史） |
| 镜头顺序变化（段内） | **过期** | 是 | 保留 |
| 角色绑定变化 | **过期** | 是 | 保留 |
| 场景资产变化（`scene_ids`） | **过期** | 是 | 保留 |
| 道具变化 | **过期** | 是 | 保留 |
| 服装/年龄变体变化 | **过期** | 是 | 保留 |
| `voice` 引用变化 | **过期** | 是 | 保留 |
| 生成分辨率变化（项目级） | **过期**（全项目） | 是 | 保留 |
| 首帧/尾帧/参考图变化 | **过期** | 是 | 保留 |
| `mode` 变化 | **过期** | 是 | 保留 |
| 提示词变化（`video_prompt`） | **过期** | 是 | 保留 |
| 时长变化 | **过期** | 是 | 保留 |
| 仅修改备注（`narration` 之外的备注类文本，不参与生成） | **不过期** | 否 | 保留 |
| 仅改 `idx`（段内顺序不变、`global_no` 不变） | **不过期** | 否 | 保留 |
| 仅改 `chapter`（换章、不换段） | **不过期**（`chapter` 不进指纹） | 否 | 保留 |
| 仅改 `status`/`error` | **不过期** | 否 | 保留 |
| 资产**改名/改分类**（id 不变） | **不过期** | 否 | 保留 |
| 资产**被删除**（引用变悬空） | **过期**（引用集变） | 是 | 保留 |

**「仅修改备注」需要定义清楚**：`shots` 里没有独立备注列；`narration` 参与提示词生成 ⇒ 改它**必须过期**。真正的「备注」只有未参与生成的字段（如未来的 `note`），当前不存在。⇒ 这一行应读作「**当前不存在不参与生成的文本字段**；将来若加，必须显式排除在指纹之外」。

### 5.2 五种视频状态的表达（不加枚举）

| 状态 | 判据（全部用现有字段 + `input_hash`） | 是否可导出 |
|---|---|---|
| 历史候选 | `shot_videos.selected = 0` | 否 |
| 当前有效 | `selected = 1` 且 `input_hash === 现算指纹` | **是** |
| 已过期 | `selected = 1` 且 `input_hash !== 现算指纹` | **否** |
| 未知来源 | `selected = 1` 且 `input_hash = ''` | **否**（fail-closed） |
| 待重新生成 | 段 `status ∈ {pending, failed}`，或无候选 | 否 |
| 已被替代 | `selected = 0` 且 存在 `created_at` 更新的候选 | 否 |

**导出过滤必须升级**（3 处，P10-A 前置）：
`status==='done' && video_path` → `selected candidate 存在 && 未过期 && 文件存在`。

位置：`shots/zip/route.js:15`、`hAssembleVideo`（`tools.js:3766~3769` 的 `every(status==='done' && video_path)`）、`progress` 统计。

**【源码确认】它们现在只看 `status==='done'` 与 `video_path`**，而 `video_path` 是「当前选中候选的路径快照」（`select/route.js:17`）——所以「过期的 selected」目前**会被当成有效成片导出**。这不是新风险，是现状；加 `input_hash` 后才第一次可判。

### 5.3 分组变化

| 变化 | 段 | 旧视频 | 旧候选 |
|---|---|---|---|
| 段内增加镜头 | 同一段 id；覆盖集变大 | **过期**（`covered` 变） | 保留 |
| 段内删除镜头 | 同一段 id；覆盖集变小 | **过期** | 保留 |
| 镜头移出段（A→B） | A 覆盖集变小；B 变大 | A 的**过期**；B 的（若有）**过期** | 各自保留，**永不改挂** |
| 镜头移入段 | 同上 | 同上 | 同上 |
| 镜头拆分 | 原段覆盖集变；拆出部分归入邻近段 | **过期** | 保留 |
| 镜头合并 | 目标段覆盖集变大 | **过期** | 保留 |
| 段被腾空（覆盖集为空） | **删除段行**（见 §5.4） | 保留在 `shot_videos`（悬空指向旧段 id） | 保留 |
| 段重新排序（段间顺序变） | 段 id 不变 | **不过期**（指纹不含章内 idx） | 保留 |

**「旧视频绝不改挂」的结构保证【源码确认】**：`ShotVideos` 只有 `create` / `remove` / `deleteByShot` / `deleteByProject` / `setSelected`，**没有任何 update 方法**（`db.js:1020~1041`）。⇒ 没有任何代码路径能改 `shot_videos.shot_id`。这是结构性的，不靠纪律。

### 5.4 孤儿段：否决 `orphaned`，改「删段行、保候选」

**为什么否决（三条硬证据）**

1. 【源码确认】`chapterStats`（`db.js:858~869`）判章完成用 `done === rows.length`。多一条 `status='orphaned'` ⇒ 该章永远不 `done`，界面卡在「待生成」。
2. 【源码确认】整片合成要求 `every(s.status==='done' && s.video_path)`（`tools.js:3766~3769`）⇒ 有孤儿段的章**永远无法合成**。
3. 【源码确认】`SHOT_STATUS`（`lib/shared/index.js:122~127`）是与 UI 标签表共用的枚举，新增值需要同步改前端徽章，属跨端改动，不该由投影顺带引入。

**推荐做法**

| 情形 | 处理 |
|---|---|
| 段被腾空且无产物 | 删除 `shots` 行 |
| 段被腾空**有产物** | **删除 `shots` 行**；`shot_videos` 行与磁盘文件保留（`shot_id` 仍存旧段 id 字符串，作为**身份痕迹**）；`changelog` 的 shot-delete 快照保留原行内容 |
| 段覆盖集部分缩小 | 段保留，按 §5.3 判过期 |

**代价（如实登记）**：① 这些候选成了「无主候选」，只有 `shot_videos` 直查可见（后续可做只读「孤儿产物」视图，非阻塞）；② `Chapters.remove` 清理候选时用 `shot_id IN (SELECT ... FROM shots ...)`（`db.js:1128`），段行已删的候选不会被级联清 ⇒ 文件与行会留到项目删除。两条都登记为 U-29-3。

### 5.5 旧视频处理的边界

- **不得**为了「让成片看起来干净」删除旧候选——`deleteByShot` 只在 `Shots.remove` 与显式删候选时调用，投影**不得**调用。
- **不得**用 `status='pending'` 来表达「视频过期」：`pending` 会让界面显示「待生成」，掩盖「已有过期视频」这个事实。过期是**候选级**属性（`input_hash` 比对结果），不是段状态。

### 6.2 唯一推荐：生成侧禁写 `video_prompt`

1. `prepared.prompt = shot.video_prompt || fallbackVideoPrompt(...)`（`tools.js:2467`）——**生成侧写的值与已有值相同**（有值时）或**是兜底生成物**（无值时）。前一种是无意义重写，后一种把「机器兜底」冒充「创作者写的提示词」。

### 7.2 `scene_uid` 变更的性质

1. **这是正式规范修改**，不是实现选择：冻结文本写的是 `scene_key`，改成 `scene_uid` 必须改 D02-06 §8.2.4 的两处列名与两条索引定义。

3. **当前状态**：未建表、未实现、未批准（`tables.js`/`db.js`/`manifest` 0 命中；`probeContinuityTracking` 0 命中）。
4. **需用户明确批准**：是否接受这处历史偏离，以及是否批准修订 §8.2.4 的列名。
5. **同步修订范围**：D02-06 §8.2.4 + `schema-manifest.json` 新增条目 + `tables.js` 建表。三者必须一次改齐，否则 manifest 校验会出现「DDL 有、manifest 无」。
