## 二、R1：禁止 `row.meta` 绕过来源校验

### 2.1 缺陷成因

```js
const next = { ...row, global_no: normalizeGlobalNo(row.global_no, id) };
if (a) next.meta = buildShotAnnotations(...);   // ← 只有"有标注的镜"才被覆盖
```

`{...row}` 会把调用方塞进来的 `row.meta` 一并复制。**当该镜没有 `annotations` 时，没有任何代码
去覆盖它** —— 于是 `rows[].meta` 直接进求解器，`buildShotAnnotations()` 的来源声明与
`manual:` 盖章被完全跳过。来源隔离在"有标注"的那条路上有效，在"没标注"的这条路上等于不存在。

### 2.2 A/B 实证（用 `git show 36b7207:…` 取出修复前版本运行，跑完即删）

| 输入（`rows[1].meta`） | 修复前 | 修复后 |
|---|---|---|
| 完整状态行 `{rel:'inferred', src:'carried:a', conf:0.855, ver:3}` | 拒绝 `META_IS_RESULT_FEEDBACK`（**第二道防线拦住**） | 拒绝 `ROWS_META_NOT_ALLOWED` |
| 只给裸 `{rel:'known'}` | **放行**，`b.pos.rel='known'` 直达求解器 | 拒绝 `ROWS_META_NOT_ALLOWED` |
| `{}` | **放行**，静默进入 | 拒绝 `ROWS_META_NOT_ALLOWED` |
| 不带 `meta` | 正常 | 正常 |

> 关键发现：完整状态行在修复前**已经**被 `assertAnnotationOnly()` 拦住（因为 `src` 带结果前缀）。
> 真正漏掉的是**扣掉 `src` 的裸 `rel`** —— 它形状合法、无处可查来源，正是 D02-18 R1 想堵的那个洞，
> 只是当时从 `annotations` 那条路堵住了，`rows` 这条路还开着。

### 2.3 拒绝策略：带 `meta` 就整批拒，不按内容放行

| 策略 | 问题 |
|---|---|
| 非空拒绝、`{}` 放行 | 规则变成"看里面有什么"；而"空对象"与"投影结果为空"无法区分 —— 等于留一条"看起来没事"的旁路 |
| 静默剥掉 | 调用方以为标注生效了，实际被丢弃 —— 与 D02-18 R3 的 `filter` 丢弃同类 |
| **带 `meta`（`!== undefined`）即拒** | 唯一合法路径收敛为 `annotations → buildShotAnnotations()`；`undefined` 视为"没有这个字段"（JSON 往返也不会产出它） |

错误信息直接指出"rows 只承载镜头基础数据与求解所需的 blockings/actions/shotAssets，不是输入标注通道"，
并带 `index` 与 `shot_id`，便于调用方定位。

**纵深防御**：构造副本时显式剥键 —— `const { meta: _ignored, ...base } = row;`。即使将来有人放宽上面
那条检查，"进求解器的 `meta` 只由组装层生成"这条不变量仍然成立（`D19-R1-5` 用 `deepEqual` 精确断言
`shots[1].meta` 只含组装层写入的那一项；`D19-R1-6` 断言入参未被改写）。

**第二道防线保留**：求解器侧 `assertAnnotationOnly()` 未改。它现在仍然拦得住"直调 `solveContinuity`
并塞 `src='carried:…'`"这条路径（`R1-7` 已在 D02-18 锁定）。

## 三、R2：镜头 ID 唯一性

### 3.1 缺陷成因

`assembleSolverShots` 用 `new Set(rows.map(r => String(r.id ?? '')))` 只做"标注是否挂在已知镜上"的判断，
重复 id 会被**折叠**；求解器侧也没有任何检查。而输出 `states` 是 `{ [shotId]: state }`：

- 3 行输入（`a` / `b` / `b`）→ 最多只有 2 个键，**后一镜覆盖前一镜**，少一镜却无报错；
- `annotations[id]` 按 id 查找，重复时同一份标注会同时作用在两行上（张冠李戴）。

### 3.2 A/B 实证（修复前 `assemble-input.js` + `solver-input.js` 同时取出运行）

| 调用 | 修复前 | 修复后 |
|---|---|---|
| 旧 `assertSolverInput({shots:[a,b,b]})` | **放行（无检查）** | 拒绝 `SHOT_ID_DUPLICATED` |
| 旧 `assembleSolverShots({rows:[a,b,b]})` | **放行**，产出 3 行（`new Set` 只有 2 个 id → 必有一行被覆盖） | 拒绝 `SHOT_ID_DUPLICATED` |
| 3 个不同 id | 正常 | 正常（反向断言） |

### 3.3 落地：一份判据、两个入口

新增 `export function assertUniqueShotIds(rows)` 于 `solver-input.js`（共用输入校验模块）：

- `assertSolverInput()` 在 `id` 存在性检查之后调用它 → **直调求解器也拦**；
- `assembleSolverShots()` 在按 id 查 `annotations` **之前**显式调用它 → 防止张冠李戴。

不靠 `Map` / 对象键覆盖：先计数、再对 `> 1` 的 id 抛错，`reason='SHOT_ID_DUPLICATED'`，带 `shot_ids`。
