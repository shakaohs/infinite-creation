## 三、连续性求解器实现说明

签名逐字遵循 D01-06 §2.1：`solveContinuity({ projectId, sceneKey, shots, sceneState })` → `{ states, sceneConflicts, hash }`。

| 环节 | 实现口径 | 依据 |
|---|---|---|
| 排序 | `global_no ASC`，同号退化 `cmpStr(id)`；**不用** `shot_no` / `prev_shot_id` / `created_at` | ORD-1 / C-2 |
| 前镜 | 只来自**同一 `sceneKey`** 的批次内；跨场不串 | ORD-3 / C-1 |
| 首镜基线 | `scene_states.axis_lock` + 首镜 `shot_blockings`；三者皆缺 → `unknown`，**不编造** | §7.4 / C-6 |
| `time_jump` | **只跳过差异校验**，状态复制与动作覆盖照常；单独记 `TIME_JUMP_SKIPPED`(info) | §7.7 / C-5 |
| 三值逻辑 | `known` / `inferred` / `unknown` / `not_applicable`；**FAIL 只在两侧都 `known` 时产生** | D01-04 §5.4 / §7.6 |
| 冲突码 | `CHAR_POP` / `POSITION_JUMP` / `TELEPORT` / `POSTURE_JUMP` / `HAND_JUMP` / `PROP_APPEAR` / `PROP_REVIVE` 进 `conflicts`；`FACING_FLIP` / `INCONSISTENT_INFERRED` / `TRACK_ENDS_MISMATCH` / `STATE_UNKNOWN` / `TIME_JUMP_SKIPPED` / `COORD_SYSTEM_INCOMPLETE` 进 `diagnostics` | §3.5 |
| 动作覆盖 | `state_out = state_in`，按 `t_from` 升序应用 `result_json.char_delta` / `prop_delta` / `env_delta` / `end_state` | Step 5 |
| 轨迹校验 | `position_track` 末点 vs `state_out.pos`，差 > `TRACK_TOL`(0.02) → `TRACK_ENDS_MISMATCH`(warn) | Step 6 |
| 异常 | 非数组 / 缺 `sceneKey` / 缺 `id` → 抛 `CONTINUITY_SOLVER_FAILED`，**绝不返回空 `states`** | §7.9 |

### 3.1 三处必须说明的实现决定

**① 跳变阈值是米制，不是归一化。** D01-04 §5.5 给的是 `0.15`（自然微调）与 `1.5`（瞬移）**米**，而 `norm_*` 是 0~1 归一化——归一化差值最大只有 1.0，用归一化去比 `TELEPORT_MIN=1.5` 会**永远不触发**。本轮实现改为经 `scene_states.coord_system.active_area` 换算成米再比；`active_area` 缺失时报 `COORD_SYSTEM_INCOMPLETE`(info) 并**不判跳变**，不猜场景尺寸。首轮实现正是踩了这个坑，测试 `TELEPORT` 用例当场变红才暴露。

**② 新增 `carried` 传播语义。** D01-04 §5.7 规定：本镜没给值（missing / `null` / 显式 `rel='unknown'`）时，值沿用上镜、`src='carried:<起点镜>'`、`conf × 0.9`。首轮实现把"缺值"与"给了个不可信的观测值"都当成"有值"，于是 `state_out` 里出现了本该 `unknown` 的坐标——下一镜拿去比对，就会凭空造出一个跳变。修正后四镜算例四条断言全过（第 ④ 条 `meta.src` 与 D01 预期逐字一致：`carried:sh_40` / `prev_shot:sh_40` / `conf 0.855`）。

**③ 显式 `unknown` 通过 `shot.meta` 传入。** D01-04 §5.7 的 `sh_43` 场景是"坐标齐备但 `meta.rel='unknown'`"，而 `shot_blockings` 没有 `meta` 列、`meta` 在 `shot_states` 里。求解器因此接受一个可选入参 `shot.meta`（**与状态行 `meta` 同一种形状**，不是新字段），用于把写入期的显式标注带进来。未传时行为不变。

## 四、动作时间分析实现说明

**唯一实现在 `lib/core/validate/action.js`（P5）**，P6 通过 `lib/core/continuity/action-time.js` 转出，不复制第二份——复制一份的后果是"同一条时间口径两处实现"，改一处忘一处必然分叉（P4 的 `posRel` 就是这么处理的）。

| 口径 | 值 | 为什么 |
|---|---|---|
| `spanRequired` | 所有动作 `t_to` 的最大值 | 回答"镜头**至少要多久**" |
| `unionMax` | 按 `actor_id` 分组、组内区间并集后的**最大长度** | 回答"谁**最忙**"；跨人**不相加** |
| `gaps` | 合并后区间之间的空隙 | §5.6.2 的 `[[1.0,4.0]]` |
| 冲突 | 同人 + 区间重叠 + 部位组相交 + 未声明 `parallel_with` | 左右手可并行，同部位才冲突 |
| 量化 | 入口 `round(x*1000)/1000`，严格比较，**不设 EPS** | EPS 会让边界算例两边都对 |

四个算例逐项通过（`tests/stage3-p6-action-time.test.mjs`，8 条）：§5.6.1 三种顺序逐字相同且冲突是 `ac_1↔ac_3`（不是 `ac_1↔ac_2`）；§5.6.2 `spanRequired=5.0` 而 `unionLen=2.0`；§5.6.3 左手+右手不报、同部位报；§5.6.4 三人并行 `spanRequired` 仍为最大 `t_to`。

> 部位在输出里是**分组名**（`arm_r`），不是原字段名（`right_arm`）——D01-03 §5.6.1 的预期输出写的是 `arm_r`，按分组比对。

## 五、CIS/QIS 双层失效实现说明

`planInvalidation({ change, shots, sceneStates, shotAssets })` → `{ continuityInvalidationSet, qcInvalidationSet, reportLevelRules, bothEmpty, reasons }`（§7.8.3 的签名 + 一个报告级出口，见 §5.3）。

`change` 的入口形状（`L-4`：只能由写入用例**显式**构造，不得由触发器/轮询产生）：

```js
{
  shots:         [{ shot_id, fields: ['shot_size', ...] }],
  scene_states:  [{ scene_key, fields: ['axis_lock', ...] }],
  tables:        [{ shot_id, table: 'shot_blockings'|'shot_actions'|'shot_assets', fields?, role? }],
  assets:        [{ asset_id, fields: ['category', ...] }],
  shots_added / shots_deleted / shots_moved
}
```

### 5.1 字段分类（48 列 + 14 列，逐列对 DDL）

| 表 | CIS+QIS | 仅 QIS | 无失效 | 合计 |
|---|---|---:|---:|---:|
| `story_shots` | 6（`scene_key`/`global_no`/`time_jump`/`spec_source`/`spec_version`/`fill_confidence`） | 22 | 20 | **48** |
| `scene_states` | 7（`coord_system`/`fixtures`/`entries`/`axis_lock`/`power_geometry`/`crowd_switch`/`time_of_day`） | 1（`scene_id`） | 5 + `scene_key`（换场语义） | **14** |

`shot_blockings` / `shot_actions` 全部内容列 → CIS+QIS（保守）；`shot_assets` 按 `role` 分（`character`/`prop` 进 CIS，其余只进 QIS）；`assets` 只 `name`/`category`/`parent_id` 三列进 CIS+QIS。

**未分类字段一律抛 `INVALIDATION_FIELD_UNCLASSIFIED`**（系统类），不静默按"不触发"处理（§7.8.3 步①，A04-T12）。

### 5.2 一处规范与代码的实质冲突（`U-P6-1`）

§7.8.1.2 把 `purpose`、`dialogue_function`、`is_insert` 归入「无失效」，但 P5 的规则**确实在读**它们：

| 列 | 读取它的规则 | 后果（照表执行） |
|---|---|---|
| `purpose` | `V-02`（枚举）、`S-17`（权力几何）、`A-01`（纯空镜） | 改 `purpose` 不重跑 → 留着上一轮 A-01 结论 |
| `is_insert` | `A-01`、`V-13`（空镜不得开口） | 同上 |
| `dialogue_function` | `V-02`（枚举） | 同上 |

本轮**没有擅自改 D01/D02**，做法是：声明口径仍按 6+22+20=48 保留（用于与 DDL 核对），另加一张显式偏差表 `READ_OVERRIDES`，把这三列**升**为「仅 QIS」，并在 `auditColumnClassification()` 的 `deviations[]` 里单独输出。测试 `A04-T9 反例` 正向断言这三列必须触发 QC。**定案需要独立审核方确认**（`U-P6-1`，B 级）。

### 5.3 审计级三条不进 QIS（`U-P6-2`）

`S-20` / `S-21` / `S-25` 读的是 `__audit`（其它规则的产出），作用域是**整份报告**。把它们塞进"按镜 × 规则"的 `qcInvalidationSet` 有两处失真：语义上某个镜并不"拥有"一条报告级规则；成本上 1000 镜的项目会凭空多跑 3000 次。因此改为并列出口 `reportLevelRules: ['S-20','S-21','S-25']`（QIS 非空时才有值），`reasons[]` 里给一条 `scope:'report'` 的记录。这是对 §7.8.3 返回结构的**增补**（不改变 `qcInvalidationSet` 的形状），需审核确认（`U-P6-2`，C 级）。

### 5.4 R-1~R-4 的四条关系

| 关系 | 实现 | 测试 |
|---|---|---|
| R-1 CIS 非空 → QIS 必非空，且 CIS 内每镜含镜级 + 状态级**全部**规则 | 步②统一补 | `A04-T1` |
| R-1 补充：`A-06` 追加**同场下一镜**（本镜 `state_out` 变了，下镜的比对对象就变了） | 步② | `A04-T4` |
| R-2 QIS 非空**不蕴含** CIS 非空 | 两集合独立生成 | `A04-T6/T7/T8` |
| R-3 同镜同时在两集合 → 先求解后 QC（执行顺序属 P9） | 只算集合 | `A04-T10` |
| R-4 双空 → 不求解、不重出、不写入 | `bothEmpty` | `A04-T9` |

`checkInvalidationRelations(plan, allShotIds)` 把这四条做成可机检的自检函数（测试与 P9 都能直接调）。

## 六、求解输入 Hash 实现说明

`solverInputHash({ projectId, sceneKey, shots, sceneState })` → `sha256:<64 hex>`。

| 纳入 | 不纳入 |
|---|---|
| `solver_version`、`scene_key`、`project_id` | `created_at` / `updated_at` / `qc_status` |
| 场次七列（`coord_system`…`time_of_day`） | `state_rev`（版本戳，不是几何） |
| 每镜 `(id, global_no, scene_key, time_jump, spec_source, spec_version, fill_confidence)` | 景别 / 台词 / 运镜 / 幅度 / 画面内容 / 时长 / 时片（QC-only） |
| 每镜站位行、动作行、`role ∈ {character, prop}` 的资产引用 | 其余 `role`（`costume`/`age`/`voice`/`scene`） |

排序键全用 `cmpStr`（禁 `localeCompare`）；站位行按 `character_id`、动作行按 `id`、资产引用按 `(role, asset_id)` 排序，**行序不影响结果**。

`SOLVER_VERSION = 'stage3.1'` 进 Hash：换实现即换 Hash（SH-4）。同一个函数同时供给 `shot_states.meta.__solver.hash`（A）与 `qc_input_hash`（B）——写两份的后果是 A 与 B 永远对不上，`hash_relation` 直接失效（SH-10）。

## 七、报告级 QC Hash 实现说明

`buildQcDependencyContext(p)` → ctx（一份快照，两个入口共用）；`qcDependencyHash(ctx)` / `qcDependencyHashDetail(ctx)`。

**两步算法（C.1，QH-14）**：① `expectedRuleSet()` 得 69 条 → ② 逐条 `qcRuleDependencyHash` → 按 `rule_id` 用 `cmpStr` 排序 → 与 `ruleset_ver`、`hash_algo_ver` 一起做 `canonicalStringify` 后摘要。

| 规则 | 实现 |
|---|---|
| RH-1 每条适用规则只出现一次 | 显式断言，重复即抛 `QC_DEPS_DUPLICATE_RULE` |
| RH-2 集合 = `expectedRuleSet` | `expectedRuleSet()` 与 `RULE_IDS` 同源 |
| RH-3 集合增减 → Hash 变 | 规则集合本身进 payload |
| RH-4 任一规则 Hash 变 → 报告级变 | 摘要即逐规则集合 |
| RH-5 跨进程/机器/locale 稳定 | `canonicalStringify` + `cmpStr` |
| RH-6 `source`（`run`/`carried`）不进 Hash | ctx 不含该字段；测试用带噪声的 ctx 验证同值 |
| RH-7 `carried_from` / 时间戳 / 报告 id 不进 Hash | 同上 |

`hash_algo_ver = 'qcdep-2'`（V6 的 `qcdep-1` 报告因此一律不匹配，这是**预期失效**，不为兼容旧报告放宽）。

## 八、规则级 QC Hash 实现说明

`qcRuleDependencyHash(ruleId, ctx)`：payload = `{ hash_algo_ver, ruleset_ver, rule_id, scope, deps }`，`deps` 是**该规则声明的字段**在 ctx 上的投影（`X[*].a` 按行取 `a` 后按内容排序；`X` 整块取；`nextShotState` 缺下镜写哨兵 `__last__`）。

四条实现约束（漏一条就退化成"全局清单"）：

1. **只读映射里写了的字段**（LR-3），不读"该镜全部字段"，也不从 `change` 推测（QH-8）。
2. **未登记的 `rule_id` 抛 `QC_RULE_DEPS_UNKNOWN`**，不回退到全景清单。
3. **适用性输入也在依赖内**（LR-4）：如 `V-05` 的 `shot_size`/`visual_content`、`V-11` 的 `movement`/`movement_amp`。
4. **`scope` 进 payload**：章级规则的输入集与镜级不同，换作用域必须换 Hash。

验证过的三条敏感度断言：

- 改 `cam_roll_deg` → `S-22` 变；受影响规则 < 10 条（若接近 69，说明退化成全局清单）；`V-11`/`A-01`/`S-24` **不变**。
- 改 `shot_size` → `V-05` 变、`V-11` **不变**（X-1：报告级变了不等于所有规则都失效）。
- 改 `chapterShots` 里任一镜的 `shot_size` → 全章 `V-07`/`V-08` 变（QH-2）；镜级规则不变。
