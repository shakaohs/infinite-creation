## 一、V1 的越轴算法为什么站不住（评审 P0-3）

V1 写了一个"叉积判侧"的算法，但没回答一个前置问题：**机位坐标从哪来？**

实测（`data/ic.db`，见 `D01-05 §2`）：66 条分镜的 `camera` 全是文本（「中景 · 50mm · 侧45度 · 固定」），**没有任何坐标数据**。而 V1 的 `story_shots` 里也没有 `cam_pos` 字段。

结果：V1 的越轴算法**在真实数据上永远无法执行**，却会输出 PASS——这正是评审说的"虚假宣称自动检测成功"。

**V2 的修正**：

1. 在 `D01-02 §D` 增加 `cam_pos` / `cam_target` / `cam_distance_m` / `cam_roll_deg` / `cam_path`（摄影机空间模型）；
2. 定义**摄影机数据完整度四级**（P-A ~ P-D）；
3. 越轴只在 P-A / P-B 可算；P-C / P-D **输出 `AXIS_UNVERIFIED`，绝不输出 PASS**；
4. 历史 66 条一律 P-C/P-D → **全部"无法验证"**，写入 `qc_reports` 时明确标注。

## 二、三层空间模型

```
Scene 层  scene_states      场基线：坐标系 / 固定物 / 入口 / 轴线 / 权力几何
Shot 层   shot_blockings    逐人：位置 / 朝向 / 视线 / 姿态 / 距离 / 遮挡 / 手位 / 多段轨迹
Transition shot_states      首尾状态差异集
```

### 2.1 场景资产 vs 场次实例（修订 P1-6）

V1 把 `scene_key` 和 `scene_id` 混在一起讲，导致"同一间病房用于 5 场戏"时不知道该复制什么。V2 明确区分：

| 概念 | 载体 | 数量关系 | 例子 |
|---|---|---|---|
| **场景资产**（可复用） | `assets(category=scene)` | 一个场景可被多场次复用 | 「私立医院 VIP 病房」资产图，用于 EP1/EP3/EP7 |
| **场次实例**（具体故事单位） | `scene_states(scene_key)` | 一场 = 一个实例，归属一个 `scene_id` | `S02_病房`（EP1 第 2 场）、`S09_病房`（EP3 第 9 场） |

| 字段 | 归属 | 说明 |
|---|---|---|
| `scene_states.scene_id` | 场次实例 → 资产 | **N:1**：多个 `scene_key` 可指向同一 `scene_id` |
| `scene_states.coord_system` | 场次实例 | 每个场次可建立自己的坐标系（同一间病房，机位可换朝向） |
| `scene_states.axis_lock` | 场次实例 | 轴线是**这一场戏**的，不是场景资产的 |
| `assets.params` / `versions` | 场景资产 | 出图风格、参考图版本 |

**为什么要分开**：同一病房在 EP1 是"罗克珊的病房"（东西向布置、机位在南），在 EP3 变成"哈罗德的病房"（重新布置、机位在北）。若把坐标和轴线挂在资产上，两场会互相覆盖。

**校验**：`scene_states.scene_id` 为空时允许（纯虚拟场次），但 `fixtures` 必须自包含；非空时 `assets.category` 必须为 `scene`。

### 3.1 `coord_system`

```json
{
  "basis": { "north": "正对主窗", "south": "回望入口", "east": "病床侧", "west": "走廊侧" },
  "levels": [ { "name": "floor", "offset_m": 0 }, { "name": "bed_level", "offset_m": 0.6 } ],
  "grid": { "x": "east→west", "y": "south→north", "z": "floor→ceiling" },
  "active_area": { "width_m": 3.2, "height_m": 4.0, "label": "病床与床头柜之间" }
}
```

**`active_area` 必须给实际尺寸**——归一化坐标 ↔ 米的换算全靠它（`D01-03 §3.3` 的 `distance_m`、遮挡判定、取景半径校验都依赖）。

来源：`blocking-direction.md` §1.2。

### 3.2 `fixtures`

```json
[
  { "id": "fx_bed",    "name": "病床",   "asset_id": "as_prop_bed",
    "zone": [0.05,0.30,0.55,0.95], "movable": false, "can_lean": true,  "height_m": 0.6 },
  { "id": "fx_table",  "name": "床头柜", "asset_id": "as_prop_nightstand",
    "zone": [0.30,0.35,0.50,0.55], "movable": false, "can_place": true },
  { "id": "fx_window", "name": "百叶窗", "asset_id": null,
    "zone": [0.70,0.00,1.00,0.40], "movable": false, "light_source": true }
]
```

- `zone`：`[x1,y1,x2,y2]` 归一化占位矩形 → 位移穿模、遮挡、可达性判定；
- `can_lean` / `can_place`：可作为依托/置物面（对应"每步有依托"与"落点"）；
- `height_m`：用于机位高度与遮挡的物理合理性（如"大俯角需真实高点"）。

### 3.3 `axis_lock`

```json
{
  "pair": ["as_char_harold", "as_char_roxanne"],
  "left": "as_char_roxanne",
  "right": "as_char_harold",
  "camera_side": "left",
  "axis_line": [[0.15,0.60],[0.30,0.70]],
  "cross_allowed": [
    { "after_shot": "sh_01HQ2K7V", "type": "neutral_insert", "reason": "空镜过渡", "approved_by": "director" }
  ]
}
```

| 字段 | 用途 |
|---|---|
| `left`/`right` | 物理左右归属（**不是画面左右**） |
| `camera_side` | 机位必须待的侧别（越轴基准） |
| `axis_line` | 两人视线连线（归一化两点），供叉积计算 |
| `cross_allowed` | 合法跨轴白名单：必须给 `type` + `reason`，禁止"无记录跨轴" |

`cross_allowed.type` 枚举：`neutral_insert`（中性空镜）/`character_cross`（人物走到对面）/`pov_switch`（主观视角切换）/`scene_turn`（换场）/`deliberate`（刻意越轴，需导演确认）。

### 4.1 `position_track`（修订 P1-5：单镜内多次位移）

问题：一镜 6 秒内人物可能"起身→走到窗边→回头"，V1 只有首尾两个位置，中间过程丢失。

```json
[
  { "t": 0.0, "x": 0.15, "y": 0.60, "z": 0.6, "posture": "sitting_supported" },
  { "t": 2.2, "x": 0.15, "y": 0.60, "z": 0,   "posture": "standing" },
  { "t": 4.0, "x": 0.62, "y": 0.85, "z": 0,   "posture": "standing" },
  { "t": 6.0, "x": 0.62, "y": 0.85, "z": 0,   "posture": "standing", "facing": "S" }
]
```

| 规则 | 内容 | 级别 |
|---|---|---|
| PT-1 | `track[0]` 必须等于 `state_in.chars[id].pos`（±0.02） | FAIL |
| PT-2 | `track[last]` 必须等于 `state_out.chars[id].pos`（±0.02） | FAIL |
| PT-3 | `track` 的点必须与 `shot_actions.path` 的 `from/to` 端点一致（有 locomotion 时） | FAIL |
| PT-4 | `t` 必须严格递增 | FAIL |
| PT-5 | 相邻两点距离 >0.15 且中间无 locomotion 动作 → `POSITION_JUMP` | FAIL |
| PT-6 | 空数组时，视为"本镜无位移"，用 `norm_x/y/z` 作为唯一位置 | — |
| PT-7 | `position_track` 与 `norm_x/y/z` 冲突时，**以 track 为准**（更细），`norm_*` 取 `track[0]` | WARN |

**与 `norm_*` 的关系**：`norm_*` = 本镜**起始**位置（= `track[0]`），是索引列（供 SQL 查询）；`position_track` 是完整轨迹（JSON，供动画与继承）。二者冗余但用途不同。

## 五、ShotState 与继承算法

### 5.1 表结构（7 列）

| 字段 | 类型 | 说明 |
|---|---|---|
| `shot_id` | TEXT PK | — |
| `state_in` | JSON | 首状态 |
| `state_out` | JSON | 尾状态 |
| `derived_from` | TEXT | `prev_shot:<id>` / `scene_baseline` / `manual` |
| `state_source` | ENUM | `solved`/`none`/`manual` |
| `conflicts` | JSON | 求解冲突（**归属见 §8**） |
| `updated_at` | INT | — |

### 5.2 状态结构（四顶层键固定）

```json
{
  "chars":    { "<char_id>": { "pos":[x,y,z], "posture":"", "facing":"", "hand":{}, "gaze":"" } },
  "props":    { "<prop_id>": { "state":"held|placed|dropped|consumed|broken|fixed", "owner":"", "hand":"", "surface":"", "condition":"" } },
  "costumes": { "<char_id>": "<costume_asset_id>" },
  "env":      { "light":"", "time":"", "door":"" }
}
```

四键固定是为了**按 id 求差集**，而不是文本比对。

### 5.3 求解算法（输入 / 输出 / 依据）

```
solveContinuity({ projectId, sceneKey, shots, sceneState })
  → { states: Map<shotId, {in,out,derived_from,conflicts}>, sceneConflicts:[], hash }
```

```
Step 1  取同场前序镜 P（global_no 最大且 < 本镜）
        ├ 无 P → state_in = scene_baseline（由 axis_lock + 首镜 blocking 生成）
        │          derived_from = 'scene_baseline'
        └ 有 P → state_in = P.state_out（深拷贝），derived_from = 'prev_shot:<P.id>'

Step 2  本镜 time_jump=1 → 跳过 Step 3/4 的差异校验（全部降 INFO）

Step 3  逐人比对 shot_blockings 与 state_in.chars：
        ├ |Δpos| ≤0.15                     → OK
        ├ |Δpos| ∈ (0.15,1.5] 且无 locomotion → POSITION_JUMP (FAIL)
        ├ |Δpos| >1.5 且无 locomotion/time_jump → TELEPORT (FAIL)
        ├ posture 变 且无 cog=rise/lower   → POSTURE_JUMP (FAIL)
        ├ facing 变化 >90° 且无转身动作    → FACING_FLIP (WARN)
        └ hand 变 且无 manipulation        → HAND_JUMP (FAIL)
        （gaze 变化始终允许）

Step 4  道具比对：
        ├ 本镜 shot_assets(role=prop) 有 X，state_in 无 X → PROP_APPEAR (FAIL)
        ├ X: held→placed 但无 manipulation    → PROP_TELEPORT (FAIL)
        ├ X: owner 变更但无交接动作           → PROP_HANDOVER (FAIL)
        └ X: consumed/broken 后复活           → PROP_REVIVE (FAIL)

Step 5  state_out = state_in
        按 t_from 升序应用每个动作的 result.char_delta / prop_delta / env_delta
        再以 end_state 覆盖对应角色的 pos/posture/facing/hand

Step 6  position_track 与本镜动作的 path 交叉校验（PT-1..PT-7）
```

**输出示例**：

```json
{
  "states": {
    "sh_11": {
      "in":  { "chars": { "as_char_harold": { "pos": [0.30,0.70], "posture": "standing" } }, "props": { "as_prop_notice": { "state": "held", "owner": "as_char_harold" } } },
      "out": { "chars": { "as_char_harold": { "pos": [0.26,0.66], "posture": "standing" } }, "props": { "as_prop_notice": { "state": "placed", "surface": "fx_table" } } },
      "derived_from": "prev_shot:sh_10",
      "conflicts": []
    }
  },
  "sceneConflicts": [],
  "hash": "sha256:…"
}
```

### 5.4 为什么 `state_in` 由程序算

模型无记忆。让模型每镜"写" `state_in`，它只能根据提示词上下文猜"看起来连贯"的状态——这正是漂移的来源。

程序算的 `state_in` 有明确依据：**上一镜的 `state_out` + 本镜动作的 `result`**。不一致的地方（模型填的 `shot_blockings` 与算出来的状态不符）就是冲突点，逐条报出来。

## 六、越轴检测（修订 P0-3：带降级）

### 6.1 前置：摄影机数据完整度判定

```
has_pos      = shot.cam_pos != null
has_target   = shot.cam_target != ''
has_distance = shot.cam_distance_m != null
has_axis     = sceneState.axis_lock.axis_line 存在

if (has_pos && has_target && has_distance && has_axis) → P-A
else if (has_pos && has_axis)                          → P-B
else if (shot.cam_direction)                           → P-C
else                                                   → P-D
```

### 6.2 算法（仅 P-A / P-B 执行）

```
输入：shot（含 cam_pos）、prev（前一镜）、axis_lock

Step 1  轴线向量 axis = axis_line[1] - axis_line[0]

Step 2  机位相对轴线的侧别
        v = cam_pos(x,y) - axis_line[0]
        cross = axis.x * v.y - axis.y * v.x
        side = cross > 0 ? 'left' : (cross < 0 ? 'right' : 'on_axis')

Step 3  与前一镜比较（前一镜也必须是 P-A/P-B，否则本镜无法比较）
        ├ side == prev.side                          → OK
        ├ 本镜在 cross_allowed 白名单（after_shot 匹配） → INFO「合法跨轴」
        ├ 本镜 movement=arc/dolly_zoom 等连续运动      → INFO「运动中跨轴」
        └ 否则                                        → AXIS_CROSS (FAIL)

Step 4  左右一致性（画面左右 vs 物理左右）
        a_left = cross(axis, pos_a - cam_pos) > 0
        若 a_left != (axis_lock.left == a.id) → LEFT_RIGHT_FLIP (FAIL)

Step 5  P-B 级（无 target）只输出 WARN，不输出 FAIL
```

### 6.3 降级规则（必须诚实）

| 完整度 | 输出 | 说明 |
|---|---|---|
| P-A | 可出 FAIL / WARN / PASS | 四项数据齐全 |
| P-B | **最高 WARN**，不出 FAIL | 缺 `cam_target`，侧别可能有歧义 |
| P-C | `AXIS_UNVERIFIED`（INFO 级） | 只有枚举，**不判** |
| P-D | `AXIS_UNVERIFIED` | 无数据 |
| 前一镜为 P-C/P-D | `AXIS_UNVERIFIED` | 无法比较 |

**`AXIS_UNVERIFIED` 的语义是"我们没有足够数据判断"，不是"通过"。** 写入 `qc_reports` 时 `level='info'`，UI 必须显示"本镜未验证"，不得显示绿灯。

### 6.4 历史数据的必然结果

实测 66 条分镜全部无 `cam_pos` → **全部 P-C/P-D → 全部 `AXIS_UNVERIFIED`**。

这不是算法失败，而是诚实：V1 声称"越轴可机检"，在真实数据上是假的。V2 明确"历史数据不可验证，需人工补机位坐标后才能启用"，并把"补机位坐标"列为实施阶段的独立任务。

**弱推断为什么不做**：有人会想"从 `cam_direction=over_shoulder` 推机位在某侧"。但过肩镜的机位在两个人物连线的任一侧都可能，`three_quarter` 也不固定。**推断出来的侧别会被当成事实用于 FAIL 判定，比不判更危险。**

## 七、S0–S4 分级（由数据推导）

```
level = S0
if (chars_in_frame >= 2)                             level = S1
if (chars_in_frame >= 3 || 有 prop 被 ≥2 人接触)      level = S2
if (有 locomotion 或 position_track.length>1)         level = S3
if (有 combat 或 chars_total >= 5 或 crowd_switch=A)  level = S4
```

| 级别 | 额外必填 |
|---|---|
| S0 | `position_abs`/`facing`/`posture`/`in_frame` |
| S1 | + `anchor_object`/`behind_object`/`gaze_target`/`hand_state`/`current_task` + `axis_lock` |
| S2 | + `norm_x/y/z`/`distance_to_camera`/`occlusion`/`power_level` |
| S3 | + `position_track` + `state_in/out` |
| S4 | + 逐动作 `contact` + `crowd_switch` + `instance_anchor` |

**级别由数据推导，不由模型声明**——防止"全标 S0 逃避校验"。

## 八、冲突归属（修订 P1-11）

V1 把冲突全塞在 `shot_states.conflicts` 里，但有些冲突不属于"状态"（越轴属于机位，服装跳变属于资产）。

**V2 归属规则**：

| 冲突类型 | 归属 | 落点 | 理由 |
|---|---|---|---|
| `POSITION_JUMP` / `TELEPORT` / `POSTURE_JUMP` / `HAND_JUMP` / `PROP_*` | 状态 | `shot_states.conflicts` | 状态继承问题 |
| `AXIS_CROSS` / `LEFT_RIGHT_FLIP` / `AXIS_UNVERIFIED` | 机位 | `qc_reports(target_type='shot')` | 摄影机问题 |
| `COSTUME_JUMP` / `AGE_JUMP` | 资产 | `qc_reports(target_type='shot')` | 资产引用问题 |
| `FACING_FLIP` | 状态 | `shot_states.conflicts`（WARN） | 人物朝向 |
| `SCENE_MISMATCH`（同段跨场） | 单元 | `qc_reports(target_type='unit')` | 切分问题 |
| `CHAR_POP` | 状态 | `shot_states.conflicts` | 在场连续性 |

**每条冲突必须带**：`code` / `level` / `shot_id` / `field` / `character_id`（可选）/ `msg` / `suggest`。

`suggest` 是给修复模块的建议，不是自动执行。

## 十、道具状态机

```
absent ──(取用)──► held(owner,hand) ──(放下)──► placed(surface)
                        │  ▲
                 (递交) │  │ (拿起)
                        ▼  │
                   held(owner2)   placed
                        │
                   (掉落) ▼
                     dropped(pos) ──(拾起)──► held
                        
  held/placed ──(消耗/损毁)──► consumed / broken   （不可逆，除非 time_jump）
```

| 迁移 | 必需动作 | 校验 |
|---|---|---|
| absent→held | manipulation + contact(prop) | 无 → `PROP_APPEAR` |
| held→placed | manipulation + `result.prop_delta` | 无 → `PROP_TELEPORT` |
| held→held(2) | 两人同在画内 + 交接动作 | 无 → `PROP_HANDOVER` |
| held→dropped | 打击/失手 | — |
| →consumed/broken | env 事件 | 反向恢复 → `PROP_REVIVE` |

**四必写**（`blocking-direction.md` §五）：持有者 / 手位 / 落点 / 状态。

## 十二、`blocking` 文本的生成（派生，非事实源）

`shots.blocking` 保留，但性质改变：

| 项 | V1 之前 | D01 之后 |
|---|---|---|
| 性质 | 唯一事实来源 | **派生产物** |
| 写法 | 每段重写 | 由 `shot_blockings` + `scene_states` 渲染 |
| 用途 | 直接进提示词 | 进提示词前可润色，但不参与机检判断 |
| 机检 | 只核"有没有" | 核"与结构化数据是否一致" |

渲染模板（对齐实测的既有写法，保证提示词风格不突变）：

```
【段首站位声明】
@哈罗德（画面右 · 病床右侧床头柜旁 0.6m · 背靠百叶窗 · 侧身45°朝左 · 立 · 右手垂 · 施压等待）
@罗克珊（画面左 · 病床上床头抬高 30° · 半坐 · 仰视 · 右手撑床指尖收紧 · 抵抗）
轴线锁定：罗克珊在左、哈罗德在右，机位恒定在罗克珊一侧，全段禁越轴；位移仅限：哈罗德 1.2m → 0.6m
```

> 实测 13 条 `blocking` 就是这种写法（「@斯洛恩（画面左 · 背靠西侧金属护栏 · 正面朝右前方赛道 · 双手扶护栏 · 手头事务：注视赛场）；轴线锁定：…」）。渲染模板按它对齐，是为了**不改变现有提示词观感**。
