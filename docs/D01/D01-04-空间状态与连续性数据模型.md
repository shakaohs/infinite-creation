## 一、V1 的越轴算法为什么站不住（评审 P0-3）

V1 写了一个"叉积判侧"的算法，但没回答一个前置问题：**机位坐标从哪来？**

实测（`data/ic.db`，见 `D01-05 §2`）：66 条分镜的 `camera` 全是文本（「中景 · 50mm · 侧45度 · 固定」），**没有任何坐标数据**。而 V1 的 `story_shots` 里也没有 `cam_pos` 字段。

结果：V1 的越轴算法**在真实数据上永远无法执行**，却会输出 PASS——这正是评审说的"虚假宣称自动检测成功"。

**V2 的修正**：

1. 在 `D01-02 §D` 增加 `cam_pos` / `cam_target` / `cam_distance_m` / `cam_roll_deg` / `cam_path`（摄影机空间模型）；
2. 定义**摄影机数据完整度四级**（P-A ~ P-D）；
3. 越轴只在 P-A / P-B 可算；P-C / P-D **输出 `AXIS_UNVERIFIED`，绝不输出 PASS**；
4. 历史 66 条一律 P-C/P-D → **全部"无法验证"**，写入 `qc_reports` 时明确标注。

## 二、三层空间模型

```
Scene 层  scene_states      场基线：坐标系 / 固定物 / 入口 / 轴线 / 权力几何
Shot 层   shot_blockings    逐人：位置 / 朝向 / 视线 / 姿态 / 距离 / 遮挡 / 手位 / 多段轨迹
Transition shot_states      首尾状态差异集
```

### 2.1 场景资产 vs 场次实例（修订 P1-6）

V1 把 `scene_key` 和 `scene_id` 混在一起讲，导致"同一间病房用于 5 场戏"时不知道该复制什么。V2 明确区分：

| 概念 | 载体 | 数量关系 | 例子 |
|---|---|---|---|
| **场景资产**（可复用） | `assets(category=scene)` | 一个场景可被多场次复用 | 「私立医院 VIP 病房」资产图，用于 EP1/EP3/EP7 |
| **场次实例**（具体故事单位） | `scene_states(scene_key)` | 一场 = 一个实例，归属一个 `scene_id` | `S02_病房`（EP1 第 2 场）、`S09_病房`（EP3 第 9 场） |

| 字段 | 归属 | 说明 |
|---|---|---|
| `scene_states.scene_id` | 场次实例 → 资产 | **N:1**：多个 `scene_key` 可指向同一 `scene_id` |
| `scene_states.coord_system` | 场次实例 | 每个场次可建立自己的坐标系（同一间病房，机位可换朝向） |
| `scene_states.axis_lock` | 场次实例 | 轴线是**这一场戏**的，不是场景资产的 |
| `assets.params` / `versions` | 场景资产 | 出图风格、参考图版本 |

**为什么要分开**：同一病房在 EP1 是"罗克珊的病房"（东西向布置、机位在南），在 EP3 变成"哈罗德的病房"（重新布置、机位在北）。若把坐标和轴线挂在资产上，两场会互相覆盖。

**校验**：`scene_states.scene_id` 为空时允许（纯虚拟场次），但 `fixtures` 必须自包含；非空时 `assets.category` 必须为 `scene`。

### 3.2 `fixtures`

```json
[
  { "id": "fx_bed",    "name": "病床",   "asset_id": "as_prop_bed",

  { "id": "fx_table",  "name": "床头柜", "asset_id": "as_prop_nightstand",
```

```json

  "left": "as_char_roxanne",
  "right": "as_char_harold",
  "camera_side": "left",
  "axis_line": [[0.15,0.60],[0.30,0.70]],
```

|---|---|
| `left`/`right` | 物理左右归属（**不是画面左右**） |

### 4.1 `position_track`（修订 P1-5：单镜内多次位移）

问题：一镜 6 秒内人物可能"起身→走到窗边→回头"，V1 只有首尾两个位置，中间过程丢失。

```json
[
  { "t": 0.0, "x": 0.15, "y": 0.60, "z": 0.6, "posture": "sitting_supported" },
  { "t": 2.2, "x": 0.15, "y": 0.60, "z": 0,   "posture": "standing" },
  { "t": 4.0, "x": 0.62, "y": 0.85, "z": 0,   "posture": "standing" },
  { "t": 6.0, "x": 0.62, "y": 0.85, "z": 0,   "posture": "standing", "facing": "S" }
]
```

| 规则 | 内容 | 级别 |
|---|---|---|
| PT-1 | `track[0]` 必须等于 `state_in.chars[id].pos`（±0.02） | FAIL |
| PT-2 | `track[last]` 必须等于 `state_out.chars[id].pos`（±0.02） | FAIL |
| PT-3 | `track` 的点必须与 `shot_actions.path` 的 `from/to` 端点一致（有 locomotion 时） | FAIL |
| PT-4 | `t` 必须严格递增 | FAIL |
| PT-5 | 相邻两点距离 >0.15 且中间无 locomotion 动作 → `POSITION_JUMP` | FAIL |
| PT-6 | 空数组时，视为"本镜无位移"，用 `norm_x/y/z` 作为唯一位置 | — |
| PT-7 | `position_track` 与 `norm_x/y/z` 冲突时，**以 track 为准**（更细），`norm_*` 取 `track[0]` | WARN |

**与 `norm_*` 的关系**：`norm_*` = 本镜**起始**位置（= `track[0]`），是索引列（供 SQL 查询）；`position_track` 是完整轨迹（JSON，供动画与继承）。二者冗余但用途不同。

### 5.2 状态结构（四顶层键固定 + 平行 `meta`）

```json
{
  "chars":    { "<char_id>": { "pos":[x,y,z], "posture":"", "facing":"", "hand":{}, "gaze":"" } },
  "props":    { "<prop_id>": { "state":"held|placed|dropped|consumed|broken|fixed", "owner":"", "hand":"", "surface":"", "condition":"" } },
  "costumes": { "<char_id>": "<costume_asset_id>" },
  "env":      { "light":"", "time":"", "door":"" }
}
```

四键固定是为了**按 id 求差集**，而不是文本比对。

**V3 新增平行可靠性映射**（不改上面的值形状，向后兼容）：

```json
{
  "meta": {
    "chars.as_char_harold.pos":          { "rel":"known",    "src":"manual",            "conf":0.95, "ver":12 },
    "chars.as_char_roxanne.posture":     { "rel":"known",    "src":"prev_shot:sh_10",   "conf":0.90, "ver":12 },
    "chars.as_char_kaisen.pos":          { "rel":"inferred", "src":"rule:from_door",    "conf":0.50, "ver":12 },
    "props.as_prop_notice.condition":    { "rel":"unknown",  "src":"no_source",         "conf":0,    "ver":12 },
    "env.light":                         { "rel":"not_applicable", "src":"scene_default", "conf":1,  "ver":12 }
  }
}
```

**为什么用扁平键路径而不是给每个值套 `{v,rel,...}`**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 每个值套 `{v,rel,src,conf}` | 强绑定，不会漏 | 值形状全变，`pos:[x,y,z]` 变成 `pos:{v:[...]}`，所有下游解析器要改；JSON 体积翻倍；人读困难 | ❌ |
| B. 平行 `meta` 扁平映射 | 值形状零变化，旧代码可直接读；只在需要时查 meta；缺省即 known | 可能漏标（缺省被当 known） | ✅ 推荐 |
| C. 单独 `shot_states.meta` 列 | 与 B 等价但更整齐 | 查询要两次 | ✅ 采纳（B 的落库形态） |

**写入权约束**：`meta` 只能由 Continuity Engine 与人工写，**LLM 不得写 `meta`**——否则模型会把自己猜的东西标成 `known`，这比不标更坏。

`meta` 的 key 是 `"<topKey>.<id>.<field>"`，`env` 与 `costumes` 同理。

### 5.2.1 `meta` 缺省怎么判（P1-07 修正）

V3 写的是"缺省 = `known`，因为绝大多数字段确实确定"。**这句话对文本成立，对几何与状态字段不成立。**

反例：历史 66 条分镜**没有一条**有 `norm_xyz`。若"缺 `meta` 就是 known"，程序会认为"人物的位置是确定的（只是没填）"，进而在求差时把 `undefined` 与"某个默认位置"比，产出一个假的 PASS。**缺失被当成确定，是这个模型最危险的失效模式。**

**先归一化输入，再谈可信度**。五个形态，两种字段类：

| 输入形态 | 类 A（描述/带默认的枚举） | 类 B（几何/姿态/持物/道具状态） |
|---|---|---|
| 键不存在 / `undefined` | `known`（语义 = 无内容） | **`unknown`** |
| `null` | `known`（= 无内容） | **`unknown`** |
| `''` / `[]` / `{}` | `known`（= 无内容） | **`unknown`** |
| 有值，`meta.src` 存在 | 按其 `rel` | 按其 `rel` |
| 有值，无 `meta` | `known` | 见下方"来源判定" |
| 显式 `meta.rel='unknown'` | **`unknown`**（最高优先，即使有值） | 同 |

**类 A：缺失即"没有"，可以默认 `known`**

`purpose`（默认 `advance`）、`visual_content`、`composition`、`lighting`、`dialogue`、`narration`、`sfx`、`music_cue`、`cam_note`、`is_cut_point`（默认 1）、`time_jump`（默认 0）、`speed_ramp`（默认 `none`）、`movement`（默认 `static`）、`shot_size`、`cam_direction`、`cam_height`。

理由：这些字段"没写"就是"没有这个信息"，不存在"其实有但我们不知道"。空台词不会让谁演错。

**类 B：缺失必须 `unknown`，不得补默认值**

`cam_pos`、`cam_target`、`cam_distance_m`、`fov_deg`、`norm_xyz`、`position_abs`、`posture`、`facing`、`hand_state`、`gaze_target`、`distance_to_camera`、`occlusion`、`in_frame`、`position_track`，以及道具的 `state` / `owner` / `condition`。

理由：这些字段的"缺失"与"某个具体默认值"在物理上是两件事。给人 `facing='N'` 的默认值，程序就会判下一镜"他转身了"——**用一个编出来的值去判创作者错了**。

**有值但无 `meta` 时的来源判定（类 B）**

```
if (该行 spec_source === 'manual')          → known（人工填的）
else if (值来自 scene_baseline 场级默认)      → inferred（conf 0.5）
else                                         → inferred（conf 0.4）   // AI 生成或历史导入
```

**为什么 AI 生成的有值也只给 `inferred`**：模型写 `pos:[0.5,0.5]` 可能只是占位。给它 `known` 就等于用占位值做 FAIL 判定。给 `inferred` 则最高只出 WARN，把判断交回人。

**统一入口**（写库前、hash 前、求解前都必须过这个函数）：

```js
const CLASS_A = new Set([
  'purpose','visual_content','composition','lighting','dialogue','narration',
  'sfx','music_cue','cam_note','is_cut_point','time_jump','speed_ramp',
  'movement','shot_size','cam_direction','cam_height'
]);

function normalizeRel({ field, value, metaEntry, specSource, fromBaseline }) {
  if (metaEntry?.rel) return metaEntry.rel;               // 显式标记最高优先
  if (CLASS_A.has(field)) return 'known';                 // 类 A：缺失=无内容
  const missing = value === undefined || value === null || value === ''
               || (Array.isArray(value) && value.length === 0)
               || (typeof value === 'object' && value !== null && Object.keys(value).length === 0);
  if (missing) return 'unknown';                          // ★ 类 B 缺失 → 不知道
  if (specSource === 'manual') return 'known';
  return 'inferred';                                      // AI/历史，有值但来源不可靠
}
```

**三条硬规则**：

1. **`unknown` 只在两种情况下变 `known`**：人工显式确认，或动作 `result` 算出（`src='action:<id>'`）。程序不得因为"缺一个值不好看"就补齐；
2. **`inferred` 不得升 `known`**，除非人工确认（UI 上是"采纳推断"按钮，写 `meta.src='manual_accepted'`）；
3. **类 B 字段只要 `rel='unknown'`，所有依赖它的判定全部降级**：`POSITION_JUMP` / `POSTURE_JUMP` / 越轴 `SCREEN_LR` / 距离相关 WARN 一律不判，输出 `STATE_UNKNOWN`（INFO）。

**与"缺省即 known"的差别，用一句话说清**：

> V3：没标 `meta` → 当作确定。
> V4：**类 A 没标 → 确定；类 B 没标 → 看值。有值还要看来源（人工才确定，AI 只算推断），没值一律 unknown。**

### 5.2.2 三维坐标必须整体判定（V5 · P1-04）

`pos` 是 `[x, y, z]` 三元组，但库里是三个独立列（`norm_x` / `norm_y` / `norm_z`）。列默认值的存在让"缺失"和"某个具体值"变得难以区分——**这是 `norm_z DEFAULT 0` 必须改掉的根本原因**。

**判定函数（唯一入口，hash / QC / 求解前都必须过）**：

```js
/** 三个分量都拿到非 null 数值才算有坐标；缺一个就是 unknown，不做任何补齐 */
function posRel({ x, y, z, metaEntry, specSource }) {
  if (metaEntry?.rel === 'unknown') return 'unknown';         // 显式标记最高优先
  if (x == null || y == null || z == null) return 'unknown';  // ★ 任一缺失 → 整体 unknown
  if (Number.isNaN(x) || Number.isNaN(y) || Number.isNaN(z)) return 'unknown';
  if (metaEntry?.rel) return metaEntry.rel;
  return specSource === 'manual' ? 'known' : 'inferred';
}
```

| 输入 | `rel` | 说明 |
|---|---|---|
| `x=1.2, y=3.4, z=0` | 按来源（`manual`→`known`） | **z=0 是确定值**（站在地面），合法 |
| `x=1.2, y=3.4, z=NULL` | **`unknown`** | 缺分量，位置不可计算 |
| `x=1.2, y=NULL, z=0` | **`unknown`** | 同上，不得因为"z 有值"就认为部分可信 |
| 三者皆 NULL | **`unknown`** | 无坐标 |
| 三者皆 NULL，但 `meta.rel='not_applicable'` | `not_applicable` | 该字段对本镜无意义（如画外人物） |

**五个必测输入（`D01-06 §4.6 R-38`）**

| # | 输入 | 期望 `rel` | 期望 sourceSpecHash |
|---|---|---|---|
| 1 | x/y/z 全有值（manual） | `known` | 基线 |
| 2 | x/y 有值、z 缺失 | `unknown` | **与 1 不同** |
| 3 | x/y/z 全缺失 | `unknown` | **与 1、2 均不同**（1 与 2 的 `pos` 值不同，2 与 3 的 `pos` 不同） |
| 4 | z 明确 = 0 | `known` | **与 2 不同**（0 ≠ NULL） |
| 5 | 历史行（默认值补出来的 z=0，`spec_source='legacy'`） | `unknown` | 与 4 不同——**必须能区分"真 0"与"补出来的 0"** |

**第 5 条的落地**：历史行无法从值本身分辨"原本就是 0"与"被默认值补成 0"。因此迁移时**不读 `norm_z`** 来判定历史坐标——历史行的 `pos` 一律 `unknown`（`src='legacy:no_coord'`），除非人工在站位面板里重新拖过。这与 `D01-05 §一`"历史 66 条全部无坐标"的实测结论一致。

**hash 必须保留"值"与"可靠性"两个维度**：

```
payload.blockings[i].xyz = [x, y, z]        // 值：null 与 0 在 canonical 里不同
payload.blockings[i].rel = <posRel 的结果>   // 可靠性：unknown / known / inferred
```

只放值不放 `rel` → "把 unknown 悄悄改成 known 但值不变"不改变 hash（同源证明失效）；只放 `rel` 不放值 → 改坐标不改 hash（更严重）。**两者必须都在。**

### 5.3 状态可靠性模型（P1-02 新增）

每个状态值有且只有四种可靠性：

| `rel` | 含义 | 允许来源 | 可否参与判定 | UI |
|---|---|---|---|---|
| `known` | 有确定依据（人工填、上镜继承、动作算出） | `manual` / `prev_shot:<id>` / `action:<id>` | ✅ 可 PASS / 可 FAIL | 正常 |
| `inferred` | 程序按规则推断，未经确认 | `rule:<name>`（如 `rule:from_door`） | ⚠️ 只可 WARN，**不可 FAIL** | 黄色「推断」 |
| `unknown` | 没有来源，无法确定 | `no_source` | ❌ **既不 PASS 也不 FAIL** | 灰色「未验证」 |
| `not_applicable` | 该字段对本镜无意义（如空镜的 `hand`） | `na_rule:<name>` | ❌ 不参与统计 | 灰色「不适用」 |

**`inferred` 为什么不能 FAIL**：推断是程序的猜测，拿猜测去判创作者"错了"，等于让程序替导演定罪。`inferred` 与 `observed` 不符时只报 `INCONSISTENT_INFERRED`（WARN），把决定权交回人。

**`unknown` 为什么不能 PASS**：这是 V2 的最大漏洞——历史 66 条分镜没有 `cam_pos`、没有物理坐标，如果"没数据=通过"，那 QC 全是绿的，等于没有 QC。V3 规定 `unknown` 单独计入**可验证率**：

```
verifiable_ratio = 已判定条数 / (已判定 + unknown条数)
```

一个项目的 QC 报告必须同时给出 `fail_count` 与 `verifiable_ratio`。只报前者，会把"数据缺失"伪装成"质量合格"。

### 5.4 未知传播规则（三值逻辑）

求解时遇到 `unknown`，按 Kleene 三值逻辑传播：

| 场景 | A | B | 结果 |
|---|---|---|---|
| 求差 | known | unknown | **unknown**（不判冲突） |
| 求差 | inferred | unknown | unknown |
| 求差 | unknown | unknown | unknown |
| 求差 | known | known 且超阈值 | FAIL |
| 求差 | inferred | known 且不符 | WARN |
| 动作覆盖 | 动作区间含该字段变化 | unknown 起点 | **unknown**（无法算差异，也无法算无差异） |

**"未知不能被程序擅自补成确定"的落地**（原则 6）：

| 情形 | 错误做法 | 正确做法 |
|---|---|---|
| 上一镜没写 `facing` | 默认 `facing='N'`，然后判本镜转身 | `facing.rel='unknown'`，本镜的 facing 直接取本镜 `shot_blockings` 值，标 `known(manual)`；不判转身，不报 FACING_FLIP |
| 道具 `condition` 未记录 | 默认"完好" | `unknown`，`PROP_CONDITION_CHANGED` 不判 |
| `pos` 缺坐标 | 从"画面左侧"推 `x=0.2` | `unknown`。**画面方位不能转物理坐标**（§6.7） |
| 角色是否在场不明 | 视为在场 | `not_applicable` 或 `unknown`，`CHAR_POP` 不判 |

**哪些状态可以自动继承**（无需本镜重写）：

| 字段 | 可继承 | 条件 |
|---|---|---|
| `chars.*.pos` / `posture` / `facing` / `hand` | ✅ | 前镜 `rel ∈ {known,inferred}` 且本镜无动作覆盖 |
| `props.*.state` / `owner` | ✅ | 前镜 `known`，且本镜 `shot_assets` 未新增该道具 |
| `costumes.*` | ✅ | 除非有 `COSTUME_CHANGE` 声明 |
| `env.light` / `time` | ✅ | 同场且无 `time_jump` |
| `props.*.condition` | ⚠️ 仅继承 `known` | 前镜 `unknown` 则继续 `unknown` |

**需要动作依据的**：位置变化 >0.15、姿态切换、手持物变化、道具状态迁移——这些**不是继承，是变更**，必须有 `shot_actions.result` 覆盖。

**需要人工确认的**：`inferred` → `known` 的升级；`unknown` 的任何赋值。

**不能计算的**：没有坐标的物理关系（距离、遮挡、轴线侧别）、没有 `cam_target` 的画面左右（§6）。

### 5.5 求解算法（输入 / 输出 / 依据）

```js
solveContinuity({ projectId, sceneKey, shots, sceneState })
  → { states: Map<shotId, {in, out, meta, derived_from, conflicts}>, sceneConflicts:[], hash }
```

```
Step 1  取同场前序镜 P（global_no 最大且 < 本镜）
        ├ 无 P → state_in = scene_baseline（由 axis_lock + 首镜 blocking 生成）
        │          derived_from = 'scene_baseline'
        │          所有字段 meta.src = 'scene_baseline'
        └ 有 P → state_in = P.state_out（深拷贝），derived_from = 'prev_shot:<P.id>'
                 所有字段 meta.src = 'prev_shot:<P.id>'，ver = 本镜版本号

Step 2  本镜 time_jump=1 → 跳过 Step 3/4 的差异校验（全部降 INFO）

Step 3  逐人比对 shot_blockings 与 state_in.chars（按 §5.4 三值逻辑）：
        ├ 本镜 blockings 有该人、state_in 无该人 → 新人入画，state_in 该人全字段 rel=unknown
        ├ 本镜 blockings 无该人、state_in 有该人且 in_frame=1 → CHAR_POP (FAIL, 仅当前镜 known)
        ├ |Δpos| ≤0.15                     → OK
        ├ |Δpos| ∈ (0.15,1.5] 且无 locomotion → POSITION_JUMP (FAIL，前提两边 pos 均 known)
        ├ |Δpos| >1.5 且无 locomotion/time_jump → TELEPORT (FAIL，同上)
        ├ posture 变 且无 cog=rise/lower   → POSTURE_JUMP (FAIL，两边 known)
        ├ facing 变化 >90° 且无转身动作    → FACING_FLIP (WARN)
        ├ hand 变 且无 manipulation        → HAND_JUMP (FAIL，两边 known)
        └ 任一为 unknown/inferred           → STATE_UNKNOWN / INCONSISTENT_INFERRED（不判 FAIL）
        （gaze 变化始终允许）

Step 4  道具比对（同样受三值逻辑约束）：
        ├ 本镜 shot_assets(role=prop) 有 X，state_in 无 X 且先前也未出现 → PROP_APPEAR (FAIL)
        ├ X: held→placed 但无 manipulation    → PROP_TELEPORT (FAIL)
        ├ X: owner 变更但无交接动作           → PROP_HANDOVER (FAIL)
        ├ X: consumed/broken 后复活           → PROP_REVIVE (FAIL)
        └ state_in 中 X 的 state 为 unknown   → PROP_STATE_UNKNOWN (INFO，不判)

Step 5  state_out = state_in
        按 t_from 升序应用每个动作的 result.char_delta / prop_delta / env_delta
        再以 end_state 覆盖对应角色的 pos/posture/facing/hand
        被覆盖字段 meta.src = 'action:<act_id>'，rel = 'known'（动作是确定依据）
        未被覆盖字段 meta 原样继承，ver 不变

Step 6  position_track 与本镜动作的 path 交叉校验（PT-1..PT-7）
```

**Step 3 的执行前提**（V3 新增，防止"用未知判已知"）：

```
canCompare(field) = meta(in).rel === 'known' && meta(observed).rel === 'known'
若 !canCompare → 按 §5.4 表格降级，绝不产出 FAIL
```

### 5.6 为什么 `state_in` 由程序算

模型无记忆。让模型每镜"写" `state_in`，它只能根据提示词上下文猜"看起来连贯"的状态——这正是漂移的来源。

程序算的 `state_in` 有明确依据：**上一镜的 `state_out` + 本镜动作的 `result`**。不一致的地方（模型填的 `shot_blockings` 与算出来的状态不符）就是冲突点，逐条报出来。

四镜连续，只跟踪哈罗德的 `pos` 与 `posture`。

**输入**

## 六、越轴检测（P1-03 重写：两个检测器）

### 6.1 V2 的算法把两件事混成了一件

V2 §6.2 的 Step 4 写：

```
a_left = cross(axis, pos_a - cam_pos) > 0
若 a_left != (axis_lock.left == a.id) → LEFT_RIGHT_FLIP (FAIL)
```

这个式子是**错的**，而且错得很隐蔽：

| 问题 | 说明 |
|---|---|
| **公式语义错** | `cross(axis, pos_a - cam_pos)` 算的是「人物 A 相对**轴线**的哪一侧」，其中还混进了机位位置。它与「A 在**画面**的左边还是右边」没有必然关系 |
| **画面左右取决于摄影机朝向** | A 在画面左还是右，取决于 `A - cam_pos` 在摄影机**右向量**上的投影符号。摄影机转过身，同一个物理位置的人在画面里就换边了 |
| **`side='left'/'right'` 命名撞车** | V2 用 `left/right` 描述「机位在轴线哪侧」，又用 `left/right` 描述「人在画面哪侧」。两个 left 不是同一个 left，代码里必然串 |
| **单镜自比** | Step 4 拿本镜的 `a_left` 与 `axis_lock.left` 比——`axis_lock.left` 是**场级**约定，与"这一镜画面里谁在左"不是同一层 |

结论：**「机位换侧」和「观众看错方向」是两件事，必须两个检测器分别算，再组合判断。**

| 检测器 | 回答 | 输入 | 输出 |
|---|---|---|---|
| **AXIS_SIDE** | 摄影机在轴线哪一侧 | `axis_line` + `cam_pos` | `side ∈ {A, B, on_axis}` + 是否换侧 |
| **SCREEN_LR** | 人物在画面左还是右 | `cam_pos` + `cam_target` + `cam_roll_deg` + 人物坐标 | 每个人的 `screen_x` 符号 + 相对左右是否翻转 |

`AXIS_SIDE` 换侧**不一定**错（人物也可能走位）。`SCREEN_LR` 翻转才是观众真的会看错方向。只有两者组合才能定性。

### 6.2 摄影机坐标系（几何定义）

**世界坐标系约定**（必须写死，否则所有数值无法验算）：

```
右手系；+Z 向上（世界 up）；地面为 XY 平面；单位米
cam_pos      = [x, y, z]      摄影机光学中心
cam_target   = [x, y, z] 或 <char_id> / <fixture_id>   观察目标点
cam_roll_deg = 绕 forward 轴的滚转角（正值 = 画面顺时针倾斜，地平线左端上抬）
```

`norm_xyz ∈ [0,1]³` 需先换算成米：`P_m = P_norm * coord_system.active_area`（`active_area = [width_m, depth_m, height_m]`）。

**基向量**：

```js
function cameraBasis(camPos, camTarget, rollDeg) {
  const forward = normalize(sub(camTarget, camPos));            // 视线方向
  const worldUp = [0, 0, 1];
  let right = cross(forward, worldUp);

  // 退化：正俯拍/正仰拍时 forward ∥ worldUp，cross 为零向量
  if (len(right) < 1e-6) return { ok: false, code: 'CAM_BASIS_DEGENERATE' };
  right = normalize(right);
  let up = cross(right, forward);                                // 已是单位向量

  // 滚转：绕 forward 旋转
  const t = rollDeg * Math.PI / 180;
  const rightR = add(scale(right, Math.cos(t)), scale(up, Math.sin(t)));
  const upR    = add(scale(right, -Math.sin(t)), scale(up, Math.cos(t)));

  return { ok: true, forward, right: rightR, up: upR };
}
```

**滚转符号必须实测校定**：不同渲染器对"dutch 正负"的约定不一致。实施第一步要用一张带水平线的测试图（`cam_roll_deg = +10`）确认渲染结果与公式同向，把结论写进 `target_profiles`。**在未校定前，`cam_roll_deg ≠ 0` 的镜头只算不滚转的近似并标 `ROLL_UNVERIFIED`。**

### 6.3 检测器 A：轴线侧别（AXIS_SIDE）

```js
function axisSide({ camPos, axisLine }) {
  const p0 = axisLine[0], p1 = axisLine[1];
  const ax = p1[0] - p0[0], ay = p1[1] - p0[1];      // 轴线水平投影
  const vx = camPos[0] - p0[0], vy = camPos[1] - p0[1];
  const crossZ = ax * vy - ay * vx;
  const side = Math.abs(crossZ) < 1e-6 ? 'on_axis' : (crossZ > 0 ? 'A' : 'B');
  return { side, crossZ };
}
```

**命名用 `A`/`B` 而非 `left`/`right`**：轴线两端谁是 A 谁是 B 由 `axis_line` 的点序决定，与画面左右无关。这样代码里再也不会把两个"左"混用。

`axis_lock` 里应记录 `a_side_ref: {A: <char_id 或 fixture_id>, B: <...>}`，把抽象的 A/B 锚到具体人/物上，便于人读与校验。

### 6.4 检测器 B：画面左右（SCREEN_LR）

```js
function screenX({ point, camPos, camTarget, rollDeg }) {
  const basis = cameraBasis(camPos, camTarget, rollDeg);
  if (!basis.ok) return { ok: false, code: 'SCREEN_LR_UNVERIFIED', reason: basis.code };
  const d = sub(point, camPos);
  const x = dot(d, basis.right);      // >0 画面右，<0 画面左
  const y = dot(d, basis.up);
  return { ok: true, screenX: x, screenY: y, side: x > 0 ? 'R' : (x < 0 ? 'L' : 'C') };
}
```

**这就是"人物在画面哪边"的唯一正确算法**：投影到摄影机右向量。

### 6.5 组合判定

```
相邻两镜 S_prev、S_cur，同一对人物 (P, Q)：

sidePrev = axisSide(S_prev)     sideCur = axisSide(S_cur)
lrPrev   = sign(screenX(P) - screenX(Q))   在 S_prev 中
lrCur    = sign(screenX(P) - screenX(Q))   在 S_cur 中

├ sideCur === sidePrev && lrCur === lrPrev
│     → OK（同侧、左右关系保持）
│
├ sideCur !== sidePrev && lrCur === lrPrev
│     → AXIS_CROSS_SOFT (INFO)
│       机位换侧，但画面左右关系未变（人物走位或构图补偿）
│       这是合法技巧，记录但不告警
│
├ sideCur !== sidePrev && lrCur !== lrPrev
│     ├ 白名单 cross_allowed 命中（明确要跨轴，如主观视角重建）
│     │     → AXIS_CROSS_INTENDED (INFO)
│     └ 否则
│           → LEFT_RIGHT_FLIP (FAIL)   ← 观众会看错谁在左谁在右
│
├ sideCur === sidePrev && lrCur !== lrPrev
│     → LR_FLIP_SAME_SIDE (WARN)
│       机位没换侧，但人物在画面里换边了（通常是人物穿越了对方的视线/机位之间）
│       也可能是人物大幅走位导致，需人工看一眼
│
└ 任一为 P-C/P-D 或基向量退化
      → AXIS_UNVERIFIED / SCREEN_LR_UNVERIFIED (INFO)
```

**为什么 `LEFT_RIGHT_FLIP` 才是 FAIL**：越轴本身不是错误，**造成观众方向感混乱**才是。机位换侧而画面左右未变，观众不会混乱；机位没换侧而人物在画面里换边，观众会瞬间迷惑。用两条线交叉判断，比"只看机位侧别"准确得多。

### 6.6 数值算例（可手工验算）

场景：病房，`active_area = [6, 5, 3]` 米。

| 对象 | 归一化 | 米坐标 |
|---|---|---|
| 哈罗德 P | (0.30, 0.70) | (1.80, 3.50, 0) |
| 罗克珊 Q | (0.15, 0.60) | (0.90, 3.00, 0) |

`axis_line` = [Q, P] = [(0.90,3.00), (1.80,3.50)]，`a_side_ref = { A: "roxanne", B: "harold" }`。

**镜 1**：`cam_pos=(1.35, 1.00, 1.20)`，`cam_target=harold`，`roll=0`

```
axisSide: ax = 0.90, ay = 0.50
          v  = (1.35-0.90, 1.00-3.00) = (0.45, -2.00)
          crossZ = 0.90*(-2.00) - 0.50*(0.45) = -2.025  → side = 'B'

basis:    forward = normalize((0.45, 2.50, -1.20)) = (0.1602, 0.8899, -0.4271)
          right   = normalize(cross(forward, [0,0,1])) = (0.9842, -0.1772, 0)

screenX(P) = dot((0.45, 2.50, -1.20), right) = 0.4429 - 0.4430 ≈ 0     → 画面中心
screenX(Q) = dot((-0.45, 2.00, -1.20), right) = -0.4429 - 0.3544 = -0.797 → 画面左
```

**镜 2**：`cam_pos=(1.35, 5.50, 1.20)`（绕到病床另一侧），`cam_target=harold`

```
axisSide: v = (0.45, 2.50)
          crossZ = 0.90*2.50 - 0.50*0.45 = +2.025  → side = 'A'   ← 换侧了

basis:    forward = normalize((0.45, -2.00, -1.20)) = (0.1894, -0.8420, -0.5052)
          right   = normalize(cross(forward, [0,0,1])) = (-0.9753, -0.2194, 0)

screenX(P) ≈ 0                                                          → 画面中心
screenX(Q) = dot((-0.45, -2.50, -1.20), right) = 0.4389 + 0.5485 = +0.987 → 画面右
```

**判定**：

```
side:  B → A        换侧
lr:    Q 在左 → Q 在右   翻转
→ 两条件同时成立，且无 cross_allowed 声明
→ LEFT_RIGHT_FLIP (FAIL)
```

这就是真实的越轴后果：观众上一秒看到"罗克珊在左、哈罗德在右"，下一秒变成"罗克珊在右"，方向感被打断。**而这个结论是用坐标算出来的，不是从"机位换侧"猜的。**

**反例（为什么不能只看侧别）**：若镜 2 里罗克珊也走到 (2.10, 5.20)，则 `screenX(Q)` 会变成负值（仍在画面左），此时 `side` 换侧但 `lr` 未翻转 → `AXIS_CROSS_SOFT`（INFO），**不该 FAIL**。V2 的算法在这里会误报，因为它只看 `side`。

### 6.7 数据完整度与降级

```
has_pos    = cam_pos 是三元素数值数组
has_target = cam_target 可解析为坐标或可查到实体坐标
has_axis   = sceneState.axis_lock.axis_line 有两个点
has_meters = coord_system.active_area 存在

AXIS_SIDE 可用 = has_pos && has_axis && has_meters
SCREEN_LR 可用 = has_pos && has_target && has_meters && basis 非退化
```

| 完整度 | AXIS_SIDE | SCREEN_LR | 最高级别 |
|---|---|---|---|
| P-A 全齐 | ✅ | ✅（roll 已校定） | FAIL |
| P-B 缺 roll 校定 | ✅ | ⚠️ 不滚转近似 | WARN |
| P-C 只有 `cam_direction` 枚举 | `AXIS_UNVERIFIED` | `SCREEN_LR_UNVERIFIED` | INFO |
| P-D 无数据 | `AXIS_UNVERIFIED` | `SCREEN_LR_UNVERIFIED` | INFO |
| 正俯拍（forward∥up） | ✅ | `CAM_BASIS_DEGENERATE` | INFO |

**`AXIS_UNVERIFIED` / `SCREEN_LR_UNVERIFIED` 的语义是"我们没有足够数据判断"，不是"通过"。** 写入 `qc_reports` 时 `level='info'`；UI 必须显示"本镜未验证"，不得显示绿灯；`verifiable_ratio` 单独统计（§5.3）。

### 6.8 历史数据的必然结果

实测 66 条分镜全部无 `cam_pos`、无 `axis_line` 的物理坐标 → **全部 P-C/P-D → 全部 `AXIS_UNVERIFIED` + `SCREEN_LR_UNVERIFIED`**。

这不是算法失败，而是诚实：V1 声称"越轴可机检"，在真实数据上是假的。V3 明确了三件事：

1. 没有坐标就没有几何，任何"越轴判定"都是文本匹配的伪判定；
2. 画面左/右**不能**从「画面左侧/画面右侧」这类文本反推物理坐标——那是把描述当测量；
3. 要启用越轴检测，唯一路径是补 `cam_pos` / `cam_target`（建议在站位面板里拖拽机位，由 UI 反算坐标），而不是让模型多写几个字。

**弱推断为什么不做**：有人会想"从 `cam_direction=over_shoulder` 推机位在某侧"。但过肩镜的机位在两个人物连线的任一侧都可能，`three_quarter` 也不固定。**推断出来的侧别会被当成事实用于 FAIL 判定，比不判更危险。**

```
level = S0
```

## 八、冲突归属（修订 P1-11）

V1 把冲突全塞在 `shot_states.conflicts` 里，但有些冲突不属于"状态"（越轴属于机位，服装跳变属于资产）。

**V3 归属规则**（新增 `STATE_UNKNOWN` 与几何相关码）：

| 冲突类型 | 归属 | 落点 | 理由 |
|---|---|---|---|
| `POSITION_JUMP` / `TELEPORT` / `POSTURE_JUMP` / `HAND_JUMP` / `PROP_*` | 状态 | `shot_states.conflicts` | 状态继承问题 |
| `AXIS_CROSS` / `AXIS_CROSS_SOFT` / `AXIS_CROSS_INTENDED` / `LEFT_RIGHT_FLIP` / `LR_FLIP_SAME_SIDE` | 机位 | `qc_reports(target_type='shot')` | 摄影机几何 |
| `AXIS_UNVERIFIED` / `SCREEN_LR_UNVERIFIED` / `CAM_BASIS_DEGENERATE` / `ROLL_UNVERIFIED` | 机位（不可验证） | `qc_reports(target_type='shot')`，`level='info'` | **数据不足，不是通过** |
| **`STATE_UNKNOWN`** | 状态 | `shot_states.conflicts`，`level='info'` | 缺来源，不判定 |
| **`INCONSISTENT_INFERRED`** | 状态 | `shot_states.conflicts`，`level='warn'` | 推断与观测不符，交人判断 |
| `COSTUME_JUMP` / `AGE_JUMP` | 资产 | `qc_reports(target_type='shot')` | 资产引用问题 |
| `FACING_FLIP` | 状态 | `shot_states.conflicts`（WARN） | 人物朝向 |
| `SCENE_MISMATCH`（同单元跨场） | 适配 | `qc_reports(target_type='unit')` | 切分问题 |
| `ADAPT_*` / `FRAG_*` | 适配 | `qc_reports(target_type='adaptation')` | `D01-06 §3.4` |
| `CHAR_POP` | 状态 | `shot_states.conflicts` | 在场连续性 |

**每条冲突必须带**：`code` / `level` / `shot_id` / `field` / `character_id`（可选）/ `msg` / `suggest` / **`evidence`**（V3 新增：判定依据的原始值，便于人复核"程序为什么会这么判"）。

`suggest` 是给修复模块的建议，不是自动执行。

**`info` 级不等于 PASS**：`qc_reports` 统计里 PASS 只计 `level='pass'`。`AXIS_UNVERIFIED` 与 `STATE_UNKNOWN` 计入 `unverified`，单独算 `verifiable_ratio`（§5.3）。

## 十、道具状态机

```
absent ──(取用)──► held(owner,hand) ──(放下)──► placed(surface)
                        │  ▲
                 (递交) │  │ (拿起)
                        ▼  │
                   held(owner2)   placed
                        │
                   (掉落) ▼
                     dropped(pos) ──(拾起)──► held
                        
  held/placed ──(消耗/损毁)──► consumed / broken   （不可逆，除非 time_jump）
```

| 迁移 | 必需动作 | 校验 |
|---|---|---|
| absent→held | manipulation + contact(prop) | 无 → `PROP_APPEAR` |
| held→placed | manipulation + `result.prop_delta` | 无 → `PROP_TELEPORT` |
| held→held(2) | 两人同在画内 + 交接动作 | 无 → `PROP_HANDOVER` |
| held→dropped | 打击/失手 | — |
| →consumed/broken | env 事件 | 反向恢复 → `PROP_REVIVE` |

**四必写**（`blocking-direction.md` §五）：持有者 / 手位 / 落点 / 状态。

## 十一、校验规则（S-01 ～ S-25）

| 编号 | 规则 | 级别 |
|---|---|---|
| S-01 | 场次基线存在 | FAIL |
| S-02 | 依托物存在（`fixtures` 或 `prop`） | FAIL |
| S-03 | `position_abs` 方位词与 `norm_xyz` 一致（**仅当两者均 `known`**） | FAIL |

| **S-06** | `AXIS_SIDE` 换侧但 `SCREEN_LR` 未翻转 | INFO `AXIS_CROSS_SOFT` |
| **S-07** | 缺 `cam_pos` / `cam_target` / `axis_line` → 两个检测器均不可用 | INFO `AXIS_UNVERIFIED` + `SCREEN_LR_UNVERIFIED` |
| S-08 | 位置跳变 | FAIL |
| S-09 | 姿态跳变 | FAIL |
| S-10 | 手位跳变 | FAIL |
| S-11 | 道具凭空出现 | FAIL |
| S-12 | 道具复活 | FAIL |
| S-13 | 服装跳变 | FAIL |
| S-14 | 画内/画外矛盾 | FAIL |
| S-15 | 取景半径不足（`distance_to_camera` vs `lens_mm`） | WARN |
| S-16 | 群像开关未裁 | WARN |
| S-17 | 权力几何未变且未声明过场 | WARN |
| S-18 | `position_track` 首尾与状态不符 | FAIL |
| S-19 | `track` 相邻点跳变无动作 | FAIL |
| **S-20** | **对任何 `unknown` 字段产出 FAIL** | **禁止（QC 自身错误）** |
| **S-21** | **对任何 `inferred` 字段产出 FAIL**（只可 WARN `INCONSISTENT_INFERRED`） | **禁止（QC 自身错误）** |
| **S-22** | `cam_roll_deg ≠ 0` 且 `target_profiles.roll_sign_verified=false` | WARN `ROLL_UNVERIFIED` |
| **S-23** | `forward ∥ worldUp`（正俯拍/正仰拍） | INFO `CAM_BASIS_DEGENERATE`，`SCREEN_LR` 不判 |
| **S-24** | `norm_x`/`norm_y`/`norm_z` 部分为 NULL（有非空也有空） | FAIL `COORD_PARTIAL`（写入侧错误，不是创作错误；见 §5.2.2） |
| **S-25** | 三维坐标任一缺失，却被当作 `known` 参与位置判定 | **禁止（QC 自身错误）**，同 S-20 |

**S-20/S-21 是"规则的规则"**：它们约束 QC 自身，不约束创作。任何按 `unknown` 判 FAIL 的实现都属于 bug——这会让"数据缺失"变成"创作者有罪"，也会逼人把未知填成猜测值来"消红灯"。

**S-05 与 V2 S-05/S-06 的差别**：V2 的 S-05 是「越轴 FAIL」、S-06 是「左右反转 FAIL」，两条都只看机位侧别。V3 把它们合并成一条**双条件**判定（侧别换 + 画面左右翻转），并新增 S-06 覆盖"换侧但未翻转"的合法情形。
