## 二、P0-01 · `D01-02 §10.1` 的旧版 EPS 公式

### 2.1 修订前

`D01-02-ShotSpec完整字段规范.md §10.1` 在"合法切点集合（唯一权威定义在 `D01-06 §3.3.1`）"这句之后，给出的却是 **V5 的公式**：

```
candidateCuts(shot) = { 0, story_duration } ∪ { a.t_from } ∪ { a.t_to }
crosses(a, t)  ⟺  (a.t_from + EPS < t) && (t < a.t_to - EPS)
legalCuts(shot) = { t ∈ candidateCuts | ¬∃ a : crosses(a, t) }
```

### 2.2 为什么这是 P0

这句话自己说"唯一权威在 `D01-06`"，紧接着给了一份**与 `D01-06` 不同**的可执行伪代码。三种读者会得到三种实现：

| 读者 | 读到什么 | 实现出什么 |
|---|---|---|
| 只读字段字典 | `crosses` 带 `±EPS` | V5 的丢动作 bug |
| 只读接口规范 | `q()` + 严格比较 | 正确 |
| 两份都读 | 发现矛盾，自己选一个 | 取决于他先读哪份 |

而 `D01-02` 是**字段字典的唯一出处**（它自己在第 6 行这么写）。字段字典里放算法，本身就是越权；放了旧算法，则是**用最权威的那份文档传播最错误的实现**。

### 2.3 修订后

删除该伪代码块，改为：

1. **五步执行顺序表**（入口量化 → 量化留痕 → 退化/越界 → 候选与跨越 → 归属与后置校验），每步标注"用什么口径"；
2. **三个容差名字表**（`TQ` / `SNAP_TOL` / `PAD_TOL`），各写唯一作用域；
3. 明确"容量、最小片段、尾单元、片段首尾覆盖与重叠**一律严格比较**"；
4. 末尾加一条**全局约束**：`EPS` 只允许出现在描述 V5 缺陷的语境，不得作为现行算法参数。

**保留**七条语义规则表（起点可切 / 终点可切 / 区间内禁切 / 必须全量检查 / 半开区间 / 唯一归属 / 局部时间）——这些是**语义**，属于字段字典的职责；被删掉的只有**算法**。

## 三、P1-01 · `stripRef` 的定义与调用不一致

### 3.1 修订前

| 位置 | 内容 |
|---|---|
| `D01-06 §4.2.1` `bodyOf()` | `trigger: stripRef(a.trigger_json)`、`sync: stripRef(a.sync_json)` |
| `D01-06 §4.2.3` 正式定义 | `function stripRefTrigger(json)`、`function stripRefSync(json)` |

`stripRef` 出现 2 次调用、0 次定义；`stripRefTrigger`/`stripRefSync` 各 1 次定义、0 次调用。

### 3.2 为什么这是 P1 而不是"笔误"

它决定 `bodyOf()` 里 `trigger` 与 `sync` 两个字段的具体内容，**也就是 `sourceSpecHash` 的一半输入**。名字对不上，等于这段语义没有实现：

- 有人按 §4.2.1 实现 → `ReferenceError`（好结果，至少会炸）；
- 有人"顺手"补一个 `function stripRef(j) { const {ref, ...r} = j; return r; }` → `sync` 的 `parallel_with` **不会被剥掉**，`triggerRef`/`parallelWith` 的回填就变成"引用进了两次 hash"，R-32/R-33（改 id 命名 hash 不变）**当场失败**；
- 更坏的是这个补法"看起来对"，因为 `trigger_json` 确实只需要剥 `ref`。

**一个名字错了，可以引出三种不同的错误实现，其中两种能跑通。**

### 3.3 修订后

`bodyOf()` 改为调用已定义的两个函数，并新增一张**依赖表**，把 `bodyOf()` 用到的 6 个外部函数逐个标注定义位置：

| 函数 | 定义位置 | 调用位置 |
|---|---|---|
| `stripRefTrigger(json)` | §4.2.3 | `bodyOf()` 的 `trigger` |
| `stripRefSync(json)` | §4.2.3 | `bodyOf()` 的 `sync` |
| `arr()` | §4.2.1 附注 | `parts` |
| `num()` | §4.2.1 附注 | `tFrom`/`tTo` |
| `canonicalStringify()` | §4.5 | `contentHashOfBody()` |
| `cmpStr()` | §4.5.0 | `canonicalActions()` 排序 |

并写明：**`stripRef` 这个名字在本设计中不再存在**。`D01-11 §六` 的示例加了 V7 历史注记（保留原写法，声明不作规范）。

### 3.4 边界行为（未改，V6 已定义，此处复核）

| 输入 | `stripRefTrigger` | `stripRefSync` |
|---|---|---|
| `null` / `undefined` | `{}` | `{}` |

## 四、P1-02 · `assertAttribution` 真正接入

### 4.1 修订前

`assertAttribution` 定义在 `§3.3.2` 末尾，注释写"落库前的强制后置校验"，但：

- `planAdaptation` 内部**没有调用**；
- 返回值里没有它；
- 只有 `§3.3.1.8` 的散文说"落库前必须跑"。

**"必须跑"写在文档里，但代码里没有那一行。** 这种缺陷最危险的地方在于：所有单元测试都会通过（因为没人调用它，也就没人能触发它失败），而真实产出会带着 V5 的丢动作 bug 一路进成片。

### 4.2 修订后

`planAdaptation` 的镜内切分点插入调用，**在 `put()` 之前**：

```js
// ⑤ 镜内切分：先校归属，再落片段（P1-02：这是唯一必须调用的位置）
const att = assertAttribution(s, cut);
if (!att.ok)
  return { ok: false, code: att.code, shotId: s.id, warnings,
           detail: { at: cut, bad: att.detail } };

put(s, consumed, cut);
```

**为什么在 `put()` 之前**：`put()` 会写 `cur.items` 并累加 `cur.dur`。先落片段再校验，失败时要么回滚（`cur` 是内存对象，回滚容易出错），要么带着脏数据返回。**先校验后写入，失败时 `units` 一次都没被污染**。

### 4.3 调用位置的三分（写进 §3.3.1.8）

| 位置 | 调用 | 理由 |
|---|---|---|
| 镜内切分点 | **必须** | 唯一可能把同一镜动作分到两段的点 |
| 镜与镜之间 | **不调用** | 不存在该问题；判出来恒为 `n=1`，是平凡结果 |
| `verifyAdaptation` | **不调用本函数**，改用"片段包含"判定 F-5 | 判据不同，见下 |

### 4.4 两层校验的职责（这是本轮最需要说清的一点）

| | `assertAttribution(s,t)` | F-5 片段包含 |
|---|---|---|
| 时机 | 生成时，落库前 | 读取时，对已落库数据 |
| 输入 | 单镜 + 一个切点 | 单镜 + 全部片段 |
| 判据 | 左右计数之和 `n === 1` | 恰有一个 `[tFrom,tTo]` 包含动作区间 |
| 抓 | 比较符写错、绕过 `q()` | 片段整体错位、plan 版本升级后旧方案失效、直接 INSERT 绕过 plan |
| 抓不到 | 片段区间本身错（只看单点） | — |
| 失败 | `ok:false`，不落库 | 拒绝出片，方案标 `failed` |

**plan 侧防"我算错了"，verify 侧防"有人绕过了我"。** 只留一个，另一条路就没人守。

### 4.5 三个算例（L2，详见 `§3.3.2.2`）

| 例 | 输入 | `n` | 结果 |
|---|---|---|---|
| **I-1 正常** | `A(1,3)`、`B(5,7)`，`t=7` | A=1、B=1 | `ok:true` |
| **I-2 丢失** | `C(3,6)`，`t=5` | `6<=5` 假、`3>=5` 假 → **0** | `ADAPT_ACTION_LOST` |
| **I-3 重复** | `G(4,4)`（退化），`t=4` | `4<=4` 真、`4>=4` 真 → **2** | `ADAPT_ACTION_DUPLICATED` |
| **I-4 镜边界** | `sh_40` 末动作 `(8,10)`、`D=10` | **1** | 不误判（但仍不调用） |

I-2 的关键：**这个切点正常路径到不了**（`pickLegalCut` 只从 `legalCuts` 取，`crosses(C,5)` 为真会排除 5）。所以 I-2 触发，等于"有人绕过了 `legalCuts`"。**兜底校验不检查"算法有没有按设计走"，它检查"结果对不对"。**

I-3 说明 **③（退化拒绝）必须先于 ⑤**：`q(t_from) == q(t_to)` 时左右同时成立，动作会播两遍。

## 五、P1-03 · TOL 的职责重新梳理

### 5.1 修订前：声明与用法不一致

V6 的声明是"全篇唯一容差 `TOL`，只用于吸附"，但 `§3.3.2` + `§3.4` 里 `TOL` 出现在 **11 处**：

| # | 位置 | V6 写法 |
|---|---|---|
| 1 | 容量判断 | `remain <= room + TOL` |
| 2 | 最小片段 | `room < minSlice - TOL` |
| 3 | 循环条件 | `while (consumed < D - TOL)` |
| 4 | 尾单元合并 | `last.dur < shortFloor - TOL && prev.dur + last.dur <= max + TOL` |
| 5 | 尾单元警告 | `tail.dur < shortFloor - TOL` |
| 6 | 候选过滤 | `c >= -TOL && c <= q(D) + TOL` |
| 7 | 镜边界判定 | `t <= TOL \|\| t >= q(D) - TOL` |
| 8 | 切点窗口 | `t >= lo - TOL && t <= hi + TOL` |
| 9 | 单元超限（verify） | `u.unitDuration > u.profileMax + TOL` |
| 10 | 片段首尾/重叠（verify） | `frags[0].tFrom > TOL`、`d > TOL`、`d < -TOL` |
| 11 | 片段越界（verify） | `f.tFrom < -TOL \|\| f.tTo > D + TOL` |

### 5.2 诊断：这些容差在 plan 内部是冗余的，在 verify 里是有害的

**plan 内部（#1~#8）**：两侧都是 `q()` 出来的网格值。任意两个**不同**网格值的间距 ≥ `TQ = 1 ms`，而 `2 × SNAP_TOL = 1 ms`。因此 `a <= b + SNAP_TOL ⟺ a <= b`——**容差从不改变结论**。

但它不改变结论不等于没问题：

- 它让"唯一容差只用于吸附"这句声明变成假话，实施者读到哪一句都觉得自己理解对了；
- 它掩盖了"有人没做入口量化"这件事。如果 `consumed` 是原始浮点而非网格值，容差会让代码"看起来还能跑"，真问题被推迟到出片才暴露。

**verify 里（#9~#11）是真的有害**：`verifyAdaptation` 直接读库，历史数据可能未量化。`unitDuration = 15.0004`、`profileMax = 15.000`：

```
V6：15.0004 > 15.000 + 0.0005 = 15.0005?  假  → 判不超限 → 超限单元落库 → 出片被截断，QC 全绿 ✗
V7：q(15.0004)=15.000 > q(15.000)=15.000?  假  → 判不超限 ✓（它在 1 ms 时间码下确实是 15 s）
```

两条路径结论相同，但 V6 是**碰巧对**（靠容差），V7 是**对得有理由**（量化后再判）。差别在于：若 `unitDuration = 15.0008`，V6 会判超限（`15.0008 > 15.0005`），V7 归一成 `15.001` 也判超限——两者都对；但若 `unitDuration = 15.0004` 而 `PAD_TOL` 被误写成 `0.0001`，V6 就漏判了。**靠容差兜住的判断，容差一改就崩。**

### 5.3 修订后：三个名字 + 归一 + 严格比较

| 名称 | 值 | 唯一作用域 | 保留理由 |
|---|---|---|---|
| `TQ` | `0.001` | 时间量子（网格步长） | 不是容差。H3 时间码精度决定 |
| `SNAP_TOL` | `TQ/2 = 0.0005` | **仅 `snap()`** | 外部请求切点可能非网格值，允许半个刻度内吸附 |
| `PAD_TOL` | `0.01` | **仅 `UNIT_PADDING_EXCESS`** | `tailHoldMax` 是配置值（`1.0`），非网格值 |

`TOL` 这个名字**从设计中删除**。11 处比较改为：

| # | V6 | V7 | 语义 |
|---|---|---|---|
| 1 | `remain <= room + TOL` | `remain <= room` | 装得下吗 |
| 2 | `room < minSlice - TOL` | `room < minSlice` | 空间够不够一个最小片段 |
| 3 | `while (consumed < D - TOL)` | `while (consumed < D)` | 本镜还有没分配的时间 |
| 4 | `last.dur < shortFloor - TOL && ... <= max + TOL` | `last.dur < shortFloor && q(prev.dur + last.dur) <= max` | 尾单元过短 / 合并后是否超限 |
| 5 | `tail.dur < shortFloor - TOL` | `tail.dur < shortFloor` | 尾单元过短 |
| 6 | `c >= -TOL && c <= q(D) + TOL` | `c >= 0 && c <= D` | 候选点在本镜内 |
| 7 | `t <= TOL \|\| t >= q(D) - TOL` | `t <= 0 \|\| t >= D` | 是否镜边界 |
| 8 | `t >= lo - TOL && t <= hi + TOL` | `t >= lo && t <= hi` | 切点窗口 |
| 9 | `unitDuration > profileMax + TOL` | `q(unitDuration) > q(profileMax)` | 单元超限 |
| 10 | `frags[0].tFrom > TOL` 等 | `q(...)` 后 `> 0` / `d > 0` / `d < 0` | 缺口 / 重叠 |
| 11 | `f.tFrom < -TOL \|\| f.tTo > D + TOL` | `f.tFrom < 0 \|\| f.tTo > D` | 片段越界 |

### 5.4 边界算例（L2，详见 `§3.3.2.1`）

| 例 | 输入 | 期望 | 关键 |
|---|---|---|---|
| **H-1** | `cur.dur=13.000`、`D=4.000`、`max=15` | 切出 2.000 片段，`dur=15.000`，不超限 | `hi = q(consumed+room)`，片段长度在构造上 ≤ `room` |
| **H-2** | `D=7.000`，`A(1,3)`、`B(4,6)`，`consumed=0` | 切点 3.000，两段 `[0,3]`、`[3,7]` | 若归属写成 `<` 而非 `<=` → `ADAPT_ACTION_LOST` |
| **H-3** | `consumed=4.000`、切点 8.000 | `[4,8]`、`[8,10]`，`d=0` | 重叠由"用起点而非终点做 `consumed`"造成，`assertAttribution` 抓不到，靠 F-2 |
| **H-4** | 库里 `unitDuration=15.0004` | 归一后不报超限 | 见 §5.2 |

H-1 有个纯写法陷阱：若 `pickLegalCut` 的上界写成 `hi + TOL`，就能切出 `room + 0.5 ms` 的片段，`cur.dur = 15.0005 > 15`，把"构造上不可能超限"变成"可能超限"——**而 `UNIT_OVERFLOW` 在 verify 里，verify 那时又带容差，于是两边都不报。**

## 六、P1-04 · `ACTION_EDGE_SNAPPED` 真正落地

### 6.1 修订前

三处提到它，全在散文里：

- `§3.3.1` 的文字："若 `|a.t_from - q(a.t_from)| > 0` … → 记 `ACTION_EDGE_SNAPPED`（INFO）"
- 算例 G-1/G-2 的"留痕：… → ACTION_EDGE_SNAPPED（INFO）"
- `D01-07` 的风险 R-14："触发率未知"

而 `planAdaptation` 里**没有 `warnings` 数组**（它在 `return` 处才临时 `const warnings = []`，只 push `SHORT_UNIT`）。入口量化那段只做了丢值，没做比较。

**结果：这个 INFO 从设计以来从未产生过一次。** 所有"会留痕"的说法都是承诺，不是行为。

### 6.2 修订后

`warnings` 提到函数开头，与入口量化同层：

```js
const warnings = [];                       // 全程累积，成功与失败都返回

for (const a of s.actions || []) {
  const f = q(a.t_from), t = q(a.t_to);

  if (f !== a.t_from || t !== a.t_to)      // 只在真偏移时产生
    warnings.push({ code: 'ACTION_EDGE_SNAPPED', level: 'INFO',
                    shotId: s.id, actionId: a.id,
                    rawFrom: a.t_from, rawTo: a.t_to, qFrom: f, qTo: t,
                    dFrom: a.t_from - f, dTo: a.t_to - t });
  ...
}
```

四条硬要求（写进 `§3.3.1.6`）：

1. **只在真偏移时产生**：`q(3.0) === 3.0` 不产生。精确命中是常态，不该刷屏；
2. **偏移量用原始浮点差，不再 `q()`**：`q(0.0004) === 0`，量化就把要记录的那件事抹掉了；
3. **`level` 恒为 `INFO`**，不进 `errors`、不阻断切分。写成 `WARN` 会让每镜都亮黄灯，最后没人看；
4. **成功与失败都带 `warnings`**：`ADAPT_NO_LEGAL_CUT` 时最需要知道"哪些边界被挪过"——切不出来往往就因为某个候选点被挪了 0.4 ms 而消失。

### 6.3 四形态 + 一个补充算例（L2）

| 形态 | 输入 | 产生条数 | 备注 |
|---|---|---|---|
| 精确命中 | `t_from=3.000`、`t_to=8.000` | **0** | 必须测"不产生"，只测"产生"会漏掉刷屏风险 |
| 起点偏移 | `t_from=3.0004` | 1 | `dFrom=+0.0004` |
| 终点偏移 | `t_to=5.0004` | 1 | `dTo=-0.0004` |
| 两端同时偏移 | `t_from=3.0004`、`t_to=8.0006` | **1（不是 2）** | 见 G-7 |

**G-7 还顺带暴露一件事**：`8.0006` 量化成 `8.001`，于是 `8.000` **不再是合法切点**（A1 跨越：`3.000 < 8.000 < 8.001`）。原以为"两端偏移"只是留两条记录，实际它会让一个原本可切的点变得不可切。

**为什么是一条不是两条**：偏移是"一个动作在一次量化里"发生的一件事，`rawFrom/qFrom/dFrom/rawTo/qTo/dTo` 是同一事件的六个字段。拆成两条会让 R-14 的触发率统计翻倍。

## 十、结论

**本轮不宣布 D01 通过。**

四项修的都是"规则与执行断开"：权威文档里的旧算法、未定义函数名、未被调用的校验、从未 push 过的 INFO。它们不需要新的架构判断，只需要把已经写下的东西接上——**但这恰恰是评审最容易放过的一类缺陷**，因为每一份文档单独读都自洽。

按任务书要求，本轮止于文档，等待独立架构复审。复审通过后才进入 D-01 实施（建表 + 字段落地 + 49 条用例实现）。
