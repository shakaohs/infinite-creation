## 一、这份设计要解决的真问题

### 1.1 现状一句话

**分镜写得出来，但存不下来。**

依据 `docs/rebuild-v2/03-分镜设计能力审计.md` 与 `08-数据库与数据结构审计.md` 的实测数据（66 条分镜）：

| 能力 | 现状 | 数据证据 |
|---|---|---|
| 镜头语言 | `camera` 一列自由文本承载景别+焦段+机位+角度+构图+运镜 | 19 个目标字段域中 6 个完全缺失、8 个半结构化 |
| 空间站位 | `blocking` 一段话，80% 为空（53/66） | 无继承、无校验、无覆盖率门禁 |
| 动作表达 | 无字段，全混在 `visual` 叙述里 | 打戏"僵硬/缓慢"的工程根因 |
| 连续性 | 无 State In/Out，无状态表 | `seam` 字段 0/66 被写入，无消费方 |
| 提示词 | 与分镜同表（`shots.video_prompt`） | 无版本、无格式标记、无法回溯"这条片子是哪版提示词产的" |

### 1.2 必须先纠正的一个语义错位（本次设计的切入点）

**现有 `shots` 表的一行，不是一个"镜头"，而是一个"生成段"。**

证据链（代码级）：

1. `set_storyboard` 工具描述原文：「**一个生成段（一个分镜）只写一次 `blocking`**」「25-30s 段写 4-13 行都合规」——即一条记录覆盖 4~13 个镜。
2. `lib/core/storyboard-import.js:770 buildSegment()`：把 N 个 sub-shot 合成**一行**，段时长 = Σ 子镜时长，子镜逐条压进 `sub_shots` 文本，格式 `00:00-00:02 [镜头1] 中景 · 50mm · 平视 · 固定。画面主体：…；声音：…`。
3. `shot-write.js` 的时长上限按模型分档：h3 / seedance20 = 15s、seedance25 = 30s —— 这是**模型单次生成的物理上限**，不是镜头时长。
4. `duration` 字段的校验区间 `[1, 15/30]`，与"一镜 2.5–7.5 秒"的密度规则并存 —— 两个量纲被塞进同一列。

**结论**：现有模型把「导演镜头」与「模型生成单元」压缩成了一层，镜只能以文本形式寄生在 `sub_shots` 里。这直接导致三件事做不到：

- 无法逐镜做摄影/动作/空间结构化（没有镜级的行）；
- 无法在换模型时保持导演设计不变（时长列同时是创作时长和生成时长）；
- 无法做镜级连续性与镜级质检（状态只能挂在段上）。

因此 D01 的第一个动作不是加字段，而是**把这三层拆开**。

### 1.3 三条设计铁律

| # | 铁律 | 含义 | 反例（现存的违规） |
|---|---|---|---|
| **L1** | **分镜唯一**：ShotSpec 是唯一导演产物，模型无关 | Seedance 与 H3 只能"编译"，不能"另写一套分镜" | 现状：`DURATION_PROFILES` 让模型反向决定镜头能多长 |
| **L2** | **单向派生**：创作态 → 适配态 → 编译态 → 执行态，禁止回流 | 编译层发现"时长装不下"只能报错或提出建议，不能改 Shot | 现状：`regenerate_shot(feedback)` 允许提示词阶段反向改分镜结构 |
| **L3** | **程序不创作、模型不自证**：模型产出规格，程序验规格 | 合格与否由确定性规则判定，不由产出方宣布 | 现状：机检只核"有没有写 blocking"，不判"左右是否矛盾" |

## 二、实体层级

### 2.1 六个实体与职责

```
Project（项目）
  └─ Episode（集/章）          叙事容器，1 集 = 现有 chapters 一行
       └─ Scene（场）          空间容器，持有唯一空间基线（坐标系/固定物/轴线）
            └─ Shot（镜头）     导演创作最小单位，1–12s，一条 ShotSpec
                 └─ RenderUnit（渲染单元）  模型单次生成单位，聚合 1–N 个 Shot
                      └─ RenderTask（渲染任务） 一次真实提交（含参数/种子/产物/成本）
```

| 实体 | 回答什么问题 | 生命周期 | 数据归属 | 权威字段 |
|---|---|---|---|---|
| **Project** | 这部片子是什么 | 长期 | 风格/画幅/默认模型/段缝策略 | `style`、`aspect_ratio`、`video_model`、`seam` |
| **Episode** | 这是第几集 | 与剧本同寿 | 剧本/大纲/音乐 | `title`、`script`、`seq` |
| **Scene** | 这场戏在哪个空间里发生 | 跨镜、跨段、跨集可复用 | **空间基线**（坐标系/固定物/入口/轴线） | `coord_system`、`fixtures`、`axis_lock` |
| **Shot** | 导演要观众看到什么 | 创作期反复改，出片后冻结 | **ShotSpec 全量**（摄影/表演/动作/声音/时长） | `shot_size`、`camera_*`、`performance`、`story_duration` |
| **RenderUnit** | 模型这一次能生成多少 | 随目标模型变化 | 聚合关系 + 单元级约束 | `unit_duration`、`target_profile`、`shot_ids[]` |
| **RenderTask** | 这一次提交实际发生了什么 | 每次抽卡新增一条，只追加 | 参数/种子/耗时/成本/产物 | `engine`、`params`、`seed`、`video_path`、`status` |

### 2.2 三者不可混淆的判据（需求书重点）

用户明确要求区分「导演创作镜头 / 模型单次生成单元 / 实际视频生成任务」。判据如下：

| 维度 | Shot（导演镜头） | RenderUnit（生成单元） | RenderTask（生成任务） |
|---|---|---|---|
| 谁决定 | 导演/编剧逻辑 | 编译层按 Target Profile 切分 | 调度层按队列发起 |
| 数量关系 | N 个 | 1 个单元含 1–N 个 Shot | 1 个单元可有 M 次任务（抽卡） |
| 时长量纲 | `story_duration`（创作，可 2.3s） | `unit_duration`（≤ 模型上限） | 实际产出时长（可能 ≠ 请求值） |
| 换模型时 | **不变** | 重新切分 | 重新排队 |
| 可否人工改 | 可（导演权） | 可（切分权），但不得改 Shot 内部 | 否（只读记录） |
| 失败重试 | 不涉及 | 不变 | 新增一条，不改旧记录 |

**一句话记忆**：Shot 是"戏"，RenderUnit 是"一刀能拍多长"，RenderTask 是"这一刀拍了第几次"。

### 2.3 "段"（Segment）的归属裁决

老李流程里的「段」是投喂单位（≤15s，段首写站位声明，段间配段缝）。它与 RenderUnit 高度重合但不完全相等：

- 换 30s 的 Seedance 2.5 时，两个 15s 的段会被合并成一个 RenderUnit；
- 换 4–15s 的 H3 时，一个 30s 的导演段会被拆成两个 RenderUnit。

**裁决：不建独立 Segment 表。** 「段」以 `RenderUnit` 为载体，另在 Shot 上保留 `beat_key`（节拍分组标签）供叙事层使用。

理由：段的三项实质内容（切分边界、站位权威、段缝）分别由 RenderUnit（边界）、Scene（站位）、RenderUnit（接缝）承载，独立建表会与 RenderUnit 产生 1:1 冗余，且换模型时两者必然不同步。

### 2.4 一处重要修正：站位权威从「段」上移到「场」

现有实现把「段首站位声明」当作全段唯一方位权威（`prompts.js:2811` 注入「本段唯一方位权威 · 必须原样沿用」）。这个设计在单模型下有效，但在 D01 目标下有一个硬伤：

> 段是模型相关的（15s 一刀 / 30s 一刀），而**空间关系是模型无关的**。让段承载方位权威，等于让模型切分方式决定人物站位——违反 L1。

**修正设计**：

- **Scene 持有空间基线**（坐标系、固定物、入口、主轴线）—— 与模型、与段数完全无关；
- **Shot 持有空间增量**（本镜每个人在哪、朝哪、看哪、距离多少）—— 逐镜可机检；
- **RenderUnit 只是"把这些 Shot 打包投喂"的容器**，投喂时由编译器**从 Shot 事实生成**段首站位声明，而不是反过来把段的声明当作事实来源。

这样：换模型 → 段变了 → 生成的站位声明变了，但底层 Shot 事实一字不动，画面不会跳。

## 三、四层数据模型（L2 单向派生的落地）

| 层 | 名称 | 存什么 | 谁写 | 谁读 | 变更频率 |
|---|---|---|---|---|---|
| **L0** | 创作态 Creative | ShotSpec / SceneState / Blocking / Action / StateIn-Out | 大模型 + 人工 | 人、编译器 | 高（创作期反复改） |
| **L1** | 适配态 Adaptation | RenderUnit 划分、TargetProfile 约束 | 编译层（程序） | 编译器、调度 | 中（换模型/改时长时） |
| **L2** | 编译态 Compiled | PromptPackage（每模型每格式一份） | 编译器（纯函数） | 投喂、质检、复现 | 每次编译新增版本 |
| **L3** | 执行态 Execution | RenderTask / Attempt / 产物 / 成本 | 调度器与渲染通道 | 成片、复盘 | 只追加 |

**铁律落地**：

- L0 的任何字段**不得**由 L1/L2/L3 回写。编译发现 "3 个 Shot 塞不进 15s" 时，正确行为是**报 `UNIT_OVERFLOW` 并给出可选切分方案**，由人在 L0 决定拆镜还是延时长。
- L2 的产物**不覆盖**上一版，`prompt_packages` 每次编译新增一行（带 `hash` 与 `compiler_ver`），旧版只读。
- L3 的 `render_tasks` 只追加，`shots.video_path` 这类"最新产物指针"作为 L0 上的便捷索引保留（兼容旧读法）。

## 四、ShotSpec 的字段分区（详表见 D01-02）

需求书列了 26 个设计项。**不放在同一层**，按"是否随镜变化"和"是否需要被机检"分区：

| 分区 | 载体 | 字段数 | 说明 |
|---|---|---|---|
| **A. 标识与归属** | `story_shots` 行 | 8 | 集/场/镜序/节拍/前后镜指针 |
| **B. 剧作意图** | `story_shots` 行 | 4 | `purpose`（叙事功能）、`beat_key`、`dramatic_value`、`info_delta` |
| **C. 画面内容** | `story_shots` 行 | 3 | `visual_content`（谁在做什么）、`composition`（构图）、`lighting` |
| **D. 摄影（六要素）** | `story_shots` 行 | 8 | 景别/方向/高度/焦段/运镜/运镜幅度/构图法/机位描述（原生） |
| **E. 表演与动作** | `shot_actions` 从表 | 15/动作 | 主体/起止态/路径/发力/速度/力度/重心/协调/接触点/结果/余势/收势/后态/与台词关系/节奏 |
| **F. 声音** | `story_shots` 行 | 6 | 台词/说话人/旁白/音效/配乐/音色引用 |
| **G. 空间（逐人）** | `shot_blockings` 从表 | 12/人 | 位置/依托物/朝向/视线/姿态/距离/遮挡/手位/手头事务/在画/单实例锚/权力位阶 |
| **H. 状态（首尾）** | `shot_states` 1:1 | 2 组 | State In / State Out（结构化差异集） |
| **I. 资产引用** | `story_shots` 行 + `shot_assets` | 7 类 | 角色/场景/道具/服装/年龄/音频/参考图 |
| **J. 时间** | `story_shots` 行 | 4 | 创作时长/镜内时间轴/变速/是否切点 |

**分区原则**：能被规则判定的一律进标量列或小从表（可索引、可 JOIN、可 SQL 校验）；只有"高度不定长且不需逐项检索"的（如构图法备注、光影描述）才用 JSON。

### 4.1 为什么不做成一个大 JSON

**备选方案比较**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 整条 ShotSpec 存一个 JSON 列 | 改动最小、Schema 演进自由 | 无法 JOIN、无法索引、SQL 层零校验、查询"哪些镜越轴"要全表扫 | ❌ 否决 |
| B. 全字段拆标量列（60+ 列） | 可查询、可约束 | 单表过宽、逐人/逐动作无法表达（1:N） | ❌ 否决 |
| C. **主体标量 + 热点从表 + 少量 JSON** | 可查询、可约束、可表达 1:N、演进成本可控 | 表数量增加（+6），JOIN 成本 | ✅ **推荐** |

拆表数量的取舍：只把真正 1:N 的三种关系拆表（逐人空间、逐动作、逐资产引用）；1:1 的状态直接放 `shot_states`（不塞进主表是因为它是"派生结果"，会被连续性引擎重算，与导演手填字段的生命周期不同）。

## 五、实体关系（文字 ER 图）

```
projects ─1:N─ chapters(Episode)
   │                 │
   │                 └─1:N─ story_shots（Shot，含 chapter_id 真外键）
   │                            │
   ├─1:N─ scene_states（Scene 空间基线，按 scene_key 唯一）
   │                            │
   ├─1:N─ render_units ◄────────┘（N:M，经 render_unit_shots 关联）
   │         │
   │         └─1:N─ prompt_packages（编译产物，按 unit+track+format 版本化）
   │         └─1:N─ render_tasks（执行记录，只追加）
   │                    └─1:N─ render_attempts（同一任务的多次抽卡）
   │                    └─1:N─ shot_videos（兼容保留：候选视频）
   │
   └─1:N─ assets ◄── story_shots（character/scene/prop/costume/age/audio）
                      └─ shot_blockings（逐人空间，ref character_id）
                      └─ shot_actions（动作，ref actor character_id）
                      └─ shot_states（State In/Out）
```

物理映射的关键决定（详 D01-05）：

> **现有 `shots` 物理表 = RenderUnit 的存储**，不迁不改列；另建 `render_units` **视图**提供新语义读取。真正的镜落在新表 `story_shots`，通过 `render_unit_id → shots.id` 关联。

这样历史 66 条分镜无需迁移即可被新代码读取（每条旧行视为"含 1~N 镜的渲染单元"，镜从 `sub_shots` 解析回填）。

## 六、全链路数据流

```
剧本 chapters.script
   │  ① 抽取（程序，幂等）
   ├──► 资产 assets（人物/场景/道具/服装/年龄/音色）
   └──► 场景基线 scene_states（坐标系/固定物/入口/轴线）
          │
          │  ② 导演创作（大模型 + Skill 规则 → ShotSpec）
          ▼
    story_shots（ShotSpec）
    ├─ shot_blockings（逐人空间）
    ├─ shot_actions（动作链）
    └─ shot_states（State In/Out）
          │
          │  ③ 连续性求解（程序，非模型）
          ▼
    shot_states 重算 + 冲突报告（state_conflicts）
          │
          │  ④ 适配（程序，按 TargetProfile 切分）
          ▼
    render_units + render_unit_shots（N:M）
          │
          ├─⑤a Seedance Compiler ──► prompt_packages(track=seedance)
          └─⑤b H3 Compiler ────────► prompt_packages(track=h3)
          │
          │  ⑥ 质检（规则引擎 + 可选视觉质检）
          ▼
    qc_reports（按 shot / unit / package 三级）
          │
          │  ⑦ 调度（DAG，未来）
          ▼
    render_tasks → render_attempts → 视频产物
          │
          │  ⑧ 成片
          ▼
    timeline（Σ 采用片段）= timeline_duration
```

**关键约束**：③④⑤ 三步都是**纯函数式**——给定相同输入必然产出相同结果（④⑤ 落 `hash`），因此可以离线重放、可以 A/B 对比"换模型后画面是否漂移"。

## 七、时间体系（三轨，互不污染）

| 量 | 作用域 | 语义 | 上限来源 | 落库位置 |
|---|---|---|---|---|
| `story_duration` | Shot | 导演为这一镜设计的银幕时长 | **无**（创作自由，建议 1.5–12s） | `story_shots.story_duration` |
| `unit_duration` | RenderUnit | 模型单次生成的请求时长 | TargetProfile.max（H3=15 / SD2.0=15 / SD2.5=30） | `render_units.unit_duration` |
| `timeline_duration` | 成片 | 实际剪进片子的时长 | 无（= Σ 实际片段，含变速/裁切） | `timeline`（未来表）/ 导出时计算 |

**三条硬规则**：

1. `unit_duration ≥ Σ story_duration`，差额由编译器用「镜头间呼吸/定格延长」吸收，不得反向压缩 `story_duration`；
2. 超出时必须报 `UNIT_OVERFLOW`，给出 3 种处置建议（拆单元 / 拆镜 / 换模型），**由人决定**；
3. H3 的 15 秒只出现在 TargetProfile 中，**不得出现在 Shot 的任何约束里**——现有 `SHOT_DURATION_MAX = 15` 作为 Shot 级上限的用法，在新模型中降级为"RenderUnit 级约束"。

> 现状问题实证：`shot-write.js` 把 `duration` 同时当"镜头时长"和"生成段时长"，导致 seedance25 项目要写 25–30s 的"一镜"，视觉上必然变成多镜长镜头，密度机检又要求"每镜 2.5–7.5 秒"——两条规则在同一列上互相打架。三轨拆分后，这个矛盾从根上消失。

## 八、AI 与程序的职责边界（需求书第 7 项）

| 职责 | 大模型（LLM） | 程序（确定性代码） |
|---|---|---|
| 剧作意图 | ✅ 判断"这一镜为什么存在" | ❌ 不判断 |
| 镜头语言选择 | ✅ 选景别/角度/运镜（在受控词表内） | 校验"是否在词表内""是否连续三镜同景别" |
| 站位设计 | ✅ 决定谁在哪（绝对方位） | 校验"依托物是否存在""距离是否与景别匹配""是否越轴" |
| 动作拆解 | ✅ 设计动作链与节奏 | 校验"位移是否有路径""接触点是否有对象""时长是否够" |
| 状态传递 | ❌ **不负责**（模型无记忆） | ✅ 从前序 Shot 求解 State In，比对 State Out |
| 合格判定 | ❌ **禁止自证** | ✅ 规则引擎出 PASS/WARN/FAIL，写入 `qc_reports` |
| 修复 | ✅ 依据 FAIL 报告改（受约束的局部重写） | ✅ 校验修复后是否引入新冲突（回归） |

**反模式（必须禁止）**：同一轮对话里模型先写分镜、再自己宣布"已通过机检"。现有 `set_storyboard` 的硬门禁（必读 reference + 结构机检）是正确做法，D01 将其扩展为「规格校验器」：

- **Schema 校验**：字段类型、枚举值、必填项（按 S0–S4 分级，见 D01-04）；
- **引用校验**：所有 `*_id` 必须存在且 category 正确（现状已有，扩到镜级）；
- **跨镜校验**：景别重复、轴线跨越、状态断裂、道具凭空出现；
- **预算校验**：台词语速（3.5 字/秒、3.8 词/秒）、动作时长、单元容量。

**校验器与创作器必须物理分离**：校验逻辑只读数据库 + 只写 `qc_reports`，**不得修改 Shot**。这样"模型改完即合格"在架构上不可能发生。

## 九、方案比较：实体粒度的三种选择

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **S1 保持现状** | 一行 = 一段，镜只在 `sub_shots` 文本 | 零改动 | 镜级结构化不可能；换模型必漂；连续性子表无处挂 | ❌ |
| **S2 一行 = 一镜** | 现有 `shots` 改语义为镜，段按需聚合 | 语义干净 | 破坏 66 条历史数据语义（`duration` 从段变镜，值全部错）；`video_prompt` 段级产物无处挂；导入器全面返工 | ❌ 破坏性 |
| **S3 双层并存（推荐）** | 现有 `shots` 保持"段/单元"语义不动；新增 `story_shots` 存镜，N:1 挂到单元 | 零迁移、历史可读、逐镜可结构化、换模型只改单元层 | 多一层 JOIN；短期存在"旧行无子镜"的兼容态 | ✅ **推荐** |

**S3 的兼容态处理**（详 D01-05）：

- 旧行（无子镜）：读取时视为"1 个推断镜"，从 `sub_shots` 解析出 N 个镜行 → 生成 `story_shots` 影子行（惰性、只读期不回写）；UI 标注「旧版分镜（未结构化）」。
- 新行：写入即产生 N 条 `story_shots`，`shots.sub_shots` 改为**由子镜渲染生成**（保持旧读法与投喂兼容）。
