## 一、这份设计要解决的真问题

### 1.1 现状一句话

**分镜写得出来，但存不下来。**

实测依据（`data/ic.db`，7.63MB，mtime 2026-11-25T03:01:02Z，12 表）：

| 能力 | 现状 | 数据证据（查询见 `D01-05 §2`） |
|---|---|---|
| 镜头语言 | `camera` 一列自由文本承载景别+焦段+机位+角度+运镜 | `camera` 非空 66/66，但无一个结构化子字段 |
| 空间站位 | `blocking` 一段话，覆盖率 20% | 非空 13/66，且 13 条全在同一项目，写法是「画面左/右」 |
| 动作表达 | 无字段，全混在 `visual` 叙述 | `shots` 37 列中零个动作列 |
| 连续性 | 无 State In/Out | `shot_states` 概念不存在 |
| 提示词 | 与分镜同表 | `video_prompt` 非空 55/66，`video_prompt_used` 仅 2 |

### 1.2 必须先纠正的语义错位（本次设计的切入点）

**现有 `shots` 表的一行，不是一个"镜头"，而是一个"生成段"。**

代码级证据（三条独立）：

1. `set_storyboard` 工具描述原文：「**一个生成段（一个分镜）只写一次 `blocking`**」「25-30s 段写 4-13 行都合规」——一行覆盖 4~13 个镜。
2. `lib/core/storyboard-import.js:770 buildSegment()`：把 N 个 sub-shot 合成**一行**，`duration = Σ 子镜时长`，子镜压进 `sub_shots` 文本。
3. 实测 `duration` 分布：项目 `a053dabd` 的 13 条为 14–30s（seedance25 段），其余 4–15s（H3/SD2.0 段）——这是**模型单次生成上限**，不是镜头时长。

**后果**：镜只能以文本寄生在 `sub_shots` 里，于是镜级摄影/动作/空间/状态全部无处安放，换模型时导演设计跟着变。

### 1.3 三条设计铁律

| # | 铁律 | 反例（现状违规） |
|---|---|---|
| **L1** | **分镜唯一**：ShotSpec 是唯一导演产物，模型无关 | `DURATION_PROFILES` 让模型反向决定镜头能多长 |
| **L2** | **单向派生**：创作态 → 适配态 → 编译态 → 执行态，禁止回流 | `regenerate_shot(feedback)` 允许提示词阶段反向改分镜结构 |
| **L3** | **模型不自证**：模型产出规格，程序验规格 | 机检只核"有没有写 blocking"，不判左右矛盾 |

## 二、七个实体

```
Project ──1:N── Episode ──1:N── Scene ──1:N── Shot
                                                 │
                                     N:M（经 render_unit_shots，带 t_from/t_to 片段范围）
                                                 │
                                            RenderUnit ──N:1── RenderAdaptation
                                                 │              （track/profile/version）
                                                 │
                                            RenderTask ──1:N── Attempt
```

| 实体 | 回答什么 | 权威字段 |
|---|---|---|
| **Project** | 这部片子是什么 | 风格 / 画幅 / 默认模型 / 段缝策略 |
| **Episode** | 第几集 | 剧本 / 大纲 / 音乐（= 现有 `chapters`） |
| **Scene** | 这场戏在哪个空间发生 | 空间基线：坐标系 / 固定物 / 入口 / 轴线 |
| **Shot** | 导演要观众看到什么 | ShotSpec 41 业务字段（`D01-02`） |
| **RenderAdaptation** | 这一次是按什么规则切的 | `track` / `profile_ver` / `adaptation_version` / profile 参数快照 |
| **RenderUnit** | 模型这一次能生成多少 | `unit_duration` / `unit_no`（方案内） |
| **RenderTask** | 这一次提交实际发生了什么 | 参数 / 种子 / 产物 / 成本（只追加） |

### 2.1 四者不可混淆的判据

| 维度 | Shot | RenderAdaptation | RenderUnit | RenderTask |
|---|---|---|---|---|
| 谁决定 | 导演/编剧 | 适配层按 Target Profile 切 | 同一方案内的装箱结果 | 调度层按队列发起 |
| 数量 | N 个 | 每章每轨道每 profile 多版 | 每方案 M 个 | 每单元可多次抽卡 |
| 时长量纲 | `story_duration`（可 2.3s） | 无（它是规则，不是时长） | `unit_duration`（≤ 模型上限） | 实际产出（可能 ≠ 请求） |
| 换模型时 | **不变** | 新建一版方案 | 随方案重建 | 重新排队 |
| 可否人工改 | 可（导演权） | 只可"重切"，不可手改片段 | 否 | 否 |
| 删除影响 | 已编译则禁删 | 被编译引用则禁删 | 有产物则禁删 | 只追加，不删 |

**为什么 Adaptation 单列一行**：它不是"某个单元的属性"，而是"一次切分的整体决定"。把 `track` / `profile_ver` 挂在 Unit 上，等于让每个单元各自声明"我属于哪版切分"——一旦某个单元漏写或写错，整版切分就自相矛盾。方案级信息必须方案级存储。

## 三、Shot 与 RenderUnit 的关系（修订 P0-1，本文最重要的一节）

### 3.1 结论：N : M，且必须带片段范围

上一版 D01-01 的 ER 图写了 `render_unit_shots`（N:M），但 D01-05 只给了 `story_shots.render_unit_id`（1:N），两份文档自相矛盾。**V2 统一为 N:M，1:N 的方案废止。**

`story_shots.render_unit_id` 这一列**取消**。

### 3.1.1 三层：Shot → Adaptation → Unit（V3 新增）

V2 只有 Shot ↔ Unit 两层，缺了"这一次切分"这个对象。后果是：同一模型换 profile、或同 profile 重切时，**新旧单元无法区分归属**，唯一索引直接冲突（`D01-05 §4.7`）。

V3 补一层：

```
Shot ──(N:M, 带 t_from/t_to)──► RenderUnit ──(N:1)──► RenderAdaptation
                                                        ├ track
                                                        ├ profile_ver
                                                        ├ adaptation_version
                                                        └ profile_* 快照
```

| 实体 | 是什么 | 生命周期 | 谁创建 |
|---|---|---|---|
| **Shot** | 导演的一个镜头 | 随剧本，人工修改 | 创作层 |
| **Adaptation** | 对某章某轨道的一次完整切分方案 | 可有多版并存，旧版 `superseded` | 适配层（程序） |
| **RenderUnit** | 某方案下的一个生成单元（≤ profile.max） | 随方案，方案作废即失效 | 适配层（程序） |
| **RenderTask** | 对某单元的一次实际生成请求 | 只追加，不修改 | 调度器 |

**为什么不能让 Unit 直接挂 track/profile**：那样"换一版切分"只能改现有单元的行，旧切分就消失了。而实际需求是：**旧版要能重新编译、重新出片、能被对比**（`D01-06 §8` 适配视图要能并排看两版片段范围）。版本必须是一等对象，不能是单元上的几个列。

**Adaptation 与 Unit 的基数**：1:N。一个方案包含全部单元；一个单元只属于一个方案。**不存在"单元跨方案共享"**——因为单元编号、时长、片段范围都是方案内定义的。

**Shot 与 Adaptation 的基数**：N:M（通过 `render_unit_shots` 间接）。同一镜可出现在多个方案、多个单元（跨轨道、跨 profile、被劈开）。

### 3.1.2 四个"不能混"的对象

| 对象 | 单位 | 时长字段 | 受模型约束 | 谁改 |
|---|---|---|---|---|
| Shot | 一个导演镜头 | `story_duration` | ❌ 无上限 | 导演 |
| Adaptation | 一次切分 | — | ✅ 用 profile 参数 | 程序 |
| RenderUnit | 一次生成 | `unit_duration` | ✅ ≤ `profile.max` | 程序 |
| RenderTask | 一次请求 | `params.duration` | ✅ 由 profile 决定 | 调度 |

这四层的区分是本设计的地基。**任何"因为 H3 只有 15 秒，所以把镜头改成 15 秒"的做法，都是把 Unit 的约束写进了 Shot**，直接违反"专业分镜是唯一创作源"。

### 3.2 六个场景逐一验证

| 场景 | 是否发生 | N:M 下的表现 |
|---|---|---|
| **① 一镜被 Seedance 与 H3 同时使用** | 必然（双轨） | 同一 `shot_id` 在 `render_unit_shots` 出现 2 行，分别属于 track=seedance 与 track=h3 的单元 |
| **② 两模型单元组合方式不同** | 必然（15s vs 30s） | 各自单元不同，关联行各自独立；片段范围可不同 |
| **③ 同模型换 Target Profile 后单元变化** | 会发生（SD2.0↔SD2.5） | 新单元的 `profile_ver` 不同，旧单元保留（不删，标记 `superseded`） |
| **④ 长镜头超过单次生成上限** | 会发生（一镜 20s vs H3 15s） | 同一 `shot_id` 在同一单元集合里出现 2 行：`(0,15)` 与 `(15,20)`，`split_reason='oversize'` |
| **⑤ 一镜是否允许被多个单元引用** | **允许** | 跨轨道 + 跨片段，均合法，必须记录 |
| **⑥ 一逻辑镜是否允许多个模型适配片段** | **允许** | 每个片段是 `render_unit_shots` 的一行，`t_from/t_to` 定义截取范围 |

### 3.3 关联表就是"片段映射结构"

```sql
CREATE TABLE render_unit_shots (
  id          TEXT PRIMARY KEY,
  unit_id     TEXT NOT NULL,      -- → render_units.id
  shot_id     TEXT NOT NULL,      -- → story_shots.id
  order_no    INTEGER NOT NULL,   -- 单元内顺序
  t_from      REAL NOT NULL,      -- 从该镜的第几秒开始截取
  t_to        REAL NOT NULL,      -- 截取到第几秒（正常镜 = 0 ~ story_duration）
  split_reason TEXT DEFAULT '',   -- ''/oversize
  UNIQUE (unit_id, shot_id),       -- 同一单元内一镜只能一行（V4）
  UNIQUE (unit_id, order_no)
);
```

**统一规则**：**每一镜进单元都写一行，即使是完整镜**（`t_from=0, t_to=story_duration`）。不设"完整镜不写关联"的例外——两套逻辑会让所有查询分叉。

**片段合法性**：
- `0 ≤ t_from < t_to ≤ story_duration`；
- 同一 `shot_id` 在所有片段上的并集必须覆盖 `[0, story_duration]`，交集为空（不得漏、不得重叠）；
- 片段边界必须落在**动作的 `t_from` 或 `t_to`**，或镜边界（`D01-02 §10.1` / `D01-06 §3.3.1`），**且必须通过本镜全部动作的跨越检查**——某个动作结束，不代表其他人物也演完了；
- 片段内的动作时间一律重基：`t_local = t_abs - t_from`（存储与 QC 用 `t_abs`，投喂与编译用 `t_local`）。
- **每个动作必须恰好归属一个片段**（V6）：时间统一量化到 1 ms 网格后，按 `q(a.t_to) <= t → 左`、`q(a.t_from) >= t → 右` 判定，二者恰有一个成立；落库前必须跑归属后置校验，`n != 1` 报 `ADAPT_ACTION_LOST` / `ADAPT_ACTION_DUPLICATED` 并拒绝该方案（算法与证明见 `D01-06 §3.3.1.4`，**调用位置见 `§3.3.1.8`**）。

### 3.4 为什么不用"每轨道复制一份 ShotSpec"

**备选方案比较**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 每轨道各存一份 ShotSpec（`track` 列进主表） | 查询简单 | **分镜分裂成两套**，直接违反 L1；改一处漏一处 | ❌ |
| B. `story_shots.render_unit_id` 单外键（1:N） | 简单 | 无法表达双轨、无法表达超长镜拆分 | ❌ 上一版的错 |
| C. **N:M 关联表 + 片段范围** | 一份 ShotSpec，多单元引用；超长镜天然支持 | 多一张表、查询需 JOIN | ✅ **推荐** |

### 3.5 物理存储：`shots` 冻结为 legacy 单元

上一版说"`shots` = RenderUnit，用视图 `render_units` 读"。V2 修正：**视图无法承载 `track` / `profile_ver` / 单元状态，且一项目多轨道需要多行，现有 `shots` 一行只有一个 `mode` 列**。

**决议**：

| 对象 | 角色 | 状态 |
|---|---|---|
| `shots`（现有表） | **legacy 单元**，66 行历史数据 | **冻结**：不再新增行，只读；`Shots.create` 对新项目改走 `render_units` |
| **`render_adaptations`（新表）** | **一次切分方案**（track + profile + version） | 新数据方案级唯一入口 |
| `render_units`（新表） | 方案下的渲染单元 | 新数据唯一写入口 |
| `render_unit_shots`（新表） | 单元↔镜 N:M + 片段范围 | — |

**"冻结"的准确含义（V3 补齐，消除 P1-04 矛盾）**：

| 动作 | 对 `shots` | 对新表 |
|---|---|---|
| 历史项目读写 | ✅ 原样 | 不写（新表空） |
| 新项目写入 | ❌ **完全不写**（不建行、不渲染回） | ✅ 唯一写入口 |
| 新项目读取（旧页面/旧 API） | ❌ 不读 | ✅ 过 `listShotsCompat()` 投影成 `shots` 形状 |

**V2 曾同时写"冻结不新增"与"渲染回 `shots.sub_shots`"，两者不可能同时成立**（见 `D01-05 §7 M2`）。V3 定案为**不双写**，理由与六个问题的逐条回答在 `D01-05 §6.4`，此处不重复。

**兼容读**：`listUnits(projectId)` = `render_units`（join `render_adaptations` 取 active） UNION `shots`（映射为 track=`legacy`、profile_ver=`pre-d01`）。历史项目无需迁移即可读。

> 这个决定牺牲了一点"表数最少"的洁癖，换来三件事：一项目可并行双轨、切分可版本化、`shots` 的历史包袱（`seam`/`storyboard_sheet` 两列代码根本不可写，见 `D01-05 §3.3`）不再扩散。

### 3.6 站位权威从「段」上移到「场」

上一版已提出，V2 保留并强化：段（RenderUnit）是**模型相关**的（15s 一刀 / 30s 一刀），而空间关系是**模型无关**的。让段承载方位权威，等于让模型切分方式决定人物站位。

- **Scene 持有空间基线**（坐标系、固定物、入口、轴线）；
- **Shot 持有空间增量**（本镜每人位置/朝向/视线/距离）；
- **RenderUnit 只是打包容器**，投喂时的段首站位声明由编译器**从 Shot 事实生成**，而不是把段的声明当事实。

## 四、四层数据模型（L2 的落地）

| 层 | 名称 | 存什么 | 谁写 | 变更频率 |
|---|---|---|---|---|
| **L0** | 创作态 | ShotSpec / SceneState / Blocking / Action / State | 大模型 + 人工 | 高 |
| **L1** | 适配态 | RenderAdaptation + RenderUnit + 片段划分 | 适配层（程序） | 中（换模型/换 profile/重切） |
| **L2** | 编译态 | PromptPackage（每轨道每格式一份） | Compiler（纯函数） | 每次编译新增版本 |
| **L3** | 执行态 | RenderTask / Attempt / 产物 | 调度器 | 只追加 |

**铁律落地**：
- L0 字段不得由 L1/L2/L3 回写。编译发现"3 镜塞不进 15s"时正确行为是报 `UNIT_OVERFLOW` 并给三种处置建议，由人决定；
- L2 产物不覆盖上一版（`compiled_hash` 唯一键）；
- L3 只追加，`shots.video_path` 作为"最新产物指针"保留。

## 六、全链路数据流

```
剧本 chapters.script
  │ ①抽取（程序，幂等）
  ├─► assets（人物/场景/道具/服装/年龄/音色）
  └─► scene_states（坐标系/固定物/入口/轴线）
        │
        │ ②导演创作（LLM + Skill 规则）
        ▼
  story_shots + shot_blockings + shot_actions + shot_assets
        │
        │ ③连续性求解（程序）
        ▼
  shot_states（含 conflicts）
        │
        │ ④适配（程序，按 TargetProfile）
        ▼
  render_units + render_unit_shots（N:M + 片段范围）
        │
        ├─⑤a Seedance Compiler ──► prompt_packages(track=seedance)
        └─⑤b H3 Compiler ────────► prompt_packages(track=h3)
        │
        │ ⑥质检
        ▼
  qc_reports（shot / unit / package 三级）
        │
        │ ⑦调度
        ▼
  render_tasks → render_attempts → 视频
        │
        │ ⑧成片
        ▼
  timeline（Σ 采用片段）
```

③④⑤ 均为纯函数：同输入必得同输出（落 `hash`），可离线重放、可 A/B 对比。

## 七、时间体系（三轨）

| 量 | 作用域 | 语义 | 上限来源 | 落库位置 |
|---|---|---|---|---|
| `story_duration` | Shot | 导演设计的银幕时长 | **无** | `story_shots.story_duration` |
| `unit_duration` | RenderUnit | 模型单次生成的请求时长 | TargetProfile.max | `render_units.unit_duration` |
| `timeline_duration` | 成片 | 实际剪进片子的时长 | 无 | **`timelines` 表**（P1-12，见 `D01-06 §10`） |

**三条硬规则**：
1. `unit_duration ≥ Σ 片段截取时长`；差额**只允许**是尾镜定格（`tailHold`，默认 0，上限 `tailHoldMax`）。`tailHoldMax` 的权威只存在于 TargetProfile 并快照进 `render_adaptations.profile_tail_hold_max`，**校验代码不得兜底默认值**（见 `D01-05 §4.14.1`）。不得用"拉长单元"来消化差额，更不得压缩 `story_duration`；
2. 超出 `profile.max` 报 `UNIT_OVERFLOW`，给三种处置（拆单元/拆镜/换模型），由人决定；整镜超限且无合法动作断点报 `ADAPT_NO_LEGAL_CUT`，**不得硬切**；
3. H3 的 15 秒只出现在 TargetProfile，**不得出现在 Shot 的任何约束里**。

**Adaptation 不产生第四种时长**：它是规则（`max` / `shortFloor` / `minSlice` / `seamPolicy`），不是被计时的对象。`unit_duration` 仍归 Unit。

> 现状问题：`shot-write.js` 把 `duration` 同时当镜头时长与段时长，导致 seedance25 项目要写 25–30s 的"一镜"，视觉上必然变成多镜长镜头；而密度机检又要求"每镜 2.5–7.5 秒"——两条规则在同一列上互斥。三轨拆分后矛盾消失。

## 八、AI 与程序的职责边界

| 职责 | LLM | 程序 |
|---|---|---|
| 剧作意图 | ✅ 判断"这镜为什么存在" | ❌ |
| 镜头语言 | ✅ 在受控词表内选择 | ✅ 校验枚举与配额 |
| 站位设计 | ✅ 决定谁在哪 | ✅ 校验依托物/距离/轴线/坐标 |
| 动作拆解 | ✅ 设计动作链 | ✅ 校验路径/接触/时长/位置可计算性 |
| 状态传递 | ❌ **不负责** | ✅ 从前镜求解 State In |
| 合格判定 | ❌ **禁止自证** | ✅ 规则引擎写 `qc_reports` |
| 修复 | ✅ 依 FAIL 报告改 | ✅ 校验修复是否引入新冲突 |

**物理分离**：校验器只读库 + 只写 `qc_reports`，不得修改 Shot。这样"模型改完即合格"在架构上不可能。

## 十、方案比较汇总

| # | 决策 | 推荐 | 否决 | 理由 |
|---|---|---|---|---|
| 1 | 镜与段的关系 | 双层并存 | ①镜寄生文本 ②`shots` 改语义为镜 | ①无法结构化 ②破坏 66 条历史 `duration` 语义 |
| 2 | Shot:Unit 基数 | **N:M + 片段范围** | 1:N 单外键 | 双轨/超长镜/多 profile 三种场景都必然出现多引用 |
| 3 | 单元物理存储 | 新表 + `shots` 冻结 | 视图 | 视图无法承载 track/多行 |
| 4 | 字段存储 | 主表标量 + 从表 | 大 JSON / 宽表 | 无法约束/无法 1:N |
| 5 | 站位权威 | 场 + 镜增量 | 段 | 段随模型变 |
| 6 | 状态继承 | 程序求解 | 模型每镜写 | 模型无记忆，写的是猜的连贯 |
| 7 | 越轴判定 | 坐标 + 机位推算，缺数据则"无法验证" | 文本匹配 / 默认 PASS | 历史数据无坐标，文本左右是渲染结果 |
| 8 | 动作粒度 | T1/T2/T3 三档 | 全 11 环 / 全简述 | 前者失真，后者丢打击感 |
| 9 | 时长 | 三轨 | 单列 + 分档 | 现状已证互相打架 |
| 10 | 资产引用 | 关联表 | 6 个 JSON 列 | 无法查询/无外键/无顺序 |
| 11 | 历史兼容 | 惰性影子读 + 可选回填 | 批量迁移 | 一次失败全库不可用 |
| 12 | 片段划分 | 适配产物（`render_unit_shots`） | 镜属性 | 不同模型切分不同，镜属性存放会互相覆盖 |
