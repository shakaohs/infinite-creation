# D01-03 人物动作结构化模型

> 依赖：`D01-02`（ShotSpec 主表）
> 本文回答：**一个动作由哪些数据组成；动作与运镜如何分开；动作如何被机检。**
> 素材来源：`blocking-direction.md` §三（节拍闭环五段）、`storyboard-sheet-template.md` §三（action_phase 七态）、`kinetic-chain-11.md`（11 环动力链）、`shot-economy-and-acting.md`（表演幅度与镜长）

---

## 一、为什么动作不能是自然语言

现状：动作全部混在 `shots.visual` 的叙述里，例如「哈罗德猛地把纸摔在柜上，罗克珊一惊」。

这一句话里同时包含 7 件事：主体、起势、路径、接触对象、接触点、结果、反应。**全是形容词和动词，没有一个可判定的字段**。后果：

| 目标 | 自然语言下能否实现 | 原因 |
|---|---|---|
| 判断"这一镜 4.5 秒装不装得下这个动作" | ❌ | 无法知道动作有几段、每段多长 |
| 判断"他抬手时另一只手在干什么" | ❌ | 没记录 |
| 判断"他有没有真的走到床边" | ❌ | 位移混在动词里 |
| 判断"道具是否在动作后离手" | ❌ | 没有持有状态 |
| 跨镜继承"他右手还拿着纸" | ❌ | 状态不落库 |
| 换模型后动作是否被压缩变形 | ❌ | 无基线可比 |

这正是打戏"僵硬/缓慢"的工程根因：**模型拿到一段文学描写，只能平均分配时间做"整体平移"**，无法知道哪里该快、哪里该停、哪里是接触瞬间。

## 二、三档粒度（关键设计：不能一律 11 环）

需求书列了 15 个动作要素。如果每一镜都强制写全，文戏的成本会爆炸，且模型输出质量反而下降（`kinetic-chain-11.md` 明确写"过度细节同样有害——模型会忽略或失真"）。

**因此动作模型分三档**，档位由「动作类型 + 是否关键重击」推导：

| 档 | 名称 | 必填字段 | 适用 | 依据 |
|---|---|---|---|---|
| **T1** | `brief` 简式 | actor / type / init / trigger / result / end_state / duration（7 项） | 日常小动作：坐下、点头、递物、转身 | `blocking-direction.md`「连接招/过渡招只需写清起点、受力点与状态继承，不强制逐环展开」 |
| **T2** | `standard` 标准式 | T1 + path / speed / cog / contact / sync（12 项） | 有位移或有接触的动作：走近、夺物、推门、抬手打人 | 五段闭环（起势→路径→接触→落点→反应） |
| **T3** | `full` 完整式 | 全 18 项 + 发力链逐环 | **关键重击**：终结技、决定性一击、情绪爆点的爆发动作 | 11 环动力链（关键重击必须完整推导） |

**自动判档规则**（程序判定，不由模型自选）：

```
if (action.type == 'combat' && action.is_key_blow)        → T3
else if (action.path || action.contact.target)            → T2
else                                                      → T1
```

模型若给 T1 但实际写了位移（`path` 非空）→ 自动升档并 WARN「档位与内容不符」；模型若给 T3 但动作是"点头"→ WARN「过度设计」。

## 三、ActionSpec 字段表（18 字段，对应需求书 15 项）

载体：`shot_actions` 表，一镜 N 行（`is_primary=1` 恰一行）。

| # | 字段 | 类型 | 需求书对应 | 说明 | 必填档 |
|---|---|---|---|---|---|
| 1 | `id` | TEXT PK | — | `ac_<ulid>` | T1 |
| 2 | `shot_id` | TEXT FK | — | 所属镜 | T1 |
| 3 | `actor_id` | TEXT | **动作主体** | 执行者资产 id；`env` 表示环境动作（风吹、门自动关） | T1 |
| 4 | `action_type` | ENUM | — | `locomotion` 位移 / `manipulation` 操作物件 / `combat` 打斗 / `expression` 表情 / `reaction` 反应 / `environment` 环境 | T1 |
| 5 | `is_primary` | BOOL | — | 本镜主动作（一镜恰一个） | T1 |
| 6 | `init_state` | JSON | **动作起始状态** | `{posture, hand, cog, gaze}` 动作开始前的稳定态 | T1 |
| 7 | `trigger` | TEXT | **动作启动** | 是什么引发了动作：`台词结束` / `对方逼近` / `听到声响` / `自主` | T1 |
| 8 | `path` | JSON | **动作路径** | `{from, to, via[], blocked_by, move_type}`；`via` 是必经点，`blocked_by` 是障碍物 | T2 |
| 9 | `force` | JSON | **发力过程** | `{source, chain[], type}`；`chain` 为 11 环中被采用的环节（T3 要求 ≥8 环） | T2 |
| 10 | `speed` | JSON | **动作速度** | `{profile, peak_at, avg}`；`profile` ∈ `constant`/`accelerate`/`decelerate`/`sudden`/`hold` | T2 |
| 11 | `power` | INT | **动作力度** | 0–10，与 `speed` 独立（可以又快又轻：抽纸；也可以又慢又重：压门） | T2 |
| 12 | `cog` | ENUM | **重心变化** | `stable` / `forward` 前压 / `backward` 后撤 / `lower` 下沉 / `rise` 起身 / `shift_left` / `shift_right` | T2 |
| 13 | `body_parts` | JSON | **身体协调** | `[{part:'右手', act:'抬起至胸高'}, {part:'左肩', act:'随之后撤'}]` | T2 |
| 14 | `contact` | JSON | **动作接触点** | `{target_type: char/prop/env, target_id, point, surface, duration_ms}`；`point` 精确到部位（下颌骨/柜面/纸沿） | T2（有接触时必填） |
| 15 | `result` | JSON | **动作结果** | `{target_delta, prop_delta, self_delta}` 三方的变化 | T1 |
| 16 | `follow_through` | TEXT | **动作余势** | 惯性带来的附加反应：衣摆、发丝、纸角、脚步换位 | T2 |
| 17 | `recovery` | TEXT | **动作收势** | 如何稳住：踏步稳住 / 手撑桌面 / 直接进下一动作（`chained`） | T2 |
| 18 | `end_state` | JSON | **动作后的身体状态** | 与 `init_state` 同结构，动作结束时的稳定态 | T1 |
| 19 | `sync` | JSON | **与台词、情绪关系** | `{with_dialogue:'before'/'during'/'after'/'none', dialogue_span:[from,to], emotion, relation:'reinforce'/'contrast'/'conceal'}` | T2 |
| 20 | `t_from` / `t_to` | REAL | — | 动作在镜内的起止秒（用于时间片对齐） | T1 |

> 表中 20 行是因为 `t_from`/`t_to` 合并计一行；需求书 15 项全部覆盖，另加 5 个工程字段（id/actor归属/类型/主次/时间）。

## 四、动作相位与节拍闭环（两套框架的对接）

Skill 里有两套并行框架，必须让它们指向同一份数据：

**框架 A：节拍闭环五段**（`blocking-direction.md` §三，叙事侧）
起势 → 路径 → 接触/阻挡 → 落点 → 接收者反应

**框架 B：action_phase 七态**（`storyboard-sheet-template.md` §三，出图侧）
起始 → 过程 → 接触 → 顶点 → 结果 → 反应 → 出口

**对接映射**（这是 D01 的裁决，避免两套框架各自解释）：

| 框架 A | 框架 B | ActionSpec 字段 | 落库位置 |
|---|---|---|---|
| ① 起势 | `起始` START | `init_state` + `trigger` | 本动作行 |
| ② 路径 | `过程` PROCESS | `path` + `speed` + `cog` | 本动作行 |
| ③ 接触/阻挡 | `接触` CONTACT / `顶点` APEX | `contact` + `force` | 本动作行 |
| ④ 落点 | `结果` RESULT | `result` + `end_state` | 本动作行 |
| ⑤ 接收者反应 | `反应` REACTION | **另一个 ActionSpec 行**（`actor_id` = 被影响者，`action_type=reaction`，`trigger` = 上一个动作 id） | 独立行 |
| — | `出口` EXIT | = 本镜 `state_out` | `shot_states.state_out` |

**关键裁决**：⑤「接收者反应」不是描述字段，而是**独立的一条动作记录**。理由：反应有自己的主体、自己的时长、自己的状态变化，混在主动作里就无法判断"反应是否被拍到"（这正是"动作没有戏剧价值"的常见成因）。

**校验**：`contact.target_type='char'` 时，若没有对应的 `reaction` 动作行 → WARN「有接触无反应」（打戏必然要，文戏可豁免 `purpose=insert`）。

## 五、动作节奏曲线（需求书"先慢后快、突然发力、短暂停顿"）

`speed.profile` 五值不够表达"节奏"，因此引入 `time_slices`（在 ShotSpec 主表 J 区）与 `speed.peak_at` 配合：

| 节奏型 | 写法 | 适用 | 数据表达 |
|---|---|---|---|
| 匀速 | 全程同速 | 走路、常规操作 | `profile=constant` |
| 先慢后快 | 起手慢、接触瞬间加速 | 抬手打人、拔剑 | `profile=accelerate`, `peak_at=接触前 0.1s` |
| 先快后慢 | 快速启动后稳住 | 转身、坐下 | `profile=decelerate` |
| **突然发力** | 静止 → 瞬间爆发 | 拍桌、暴起、砸 | `profile=sudden`, 前面必有一个 `hold` 时间片 |
| **短暂停顿** | 动作中定住（不是结束） | 抬手后停一拍再落下 | `time_slices` 中出现 `what='定格'` 的片段 |
| 收势回稳 | 动作末尾减速 | 打完收手 | `profile=decelerate` + `recovery` |

**校验规则**：
- `profile=sudden` 但 `time_slices` 无前置 `hold` → WARN（"突然"没有对比就不突然）；
- `time_slices` 总时长 ≠ `story_duration`（容差 ±0.1s）→ FAIL；
- 任一动作的 `[t_from, t_to]` 超出 `[0, story_duration]` → FAIL；
- **动作总时长 > `story_duration`** → FAIL（这是"动作塞不下"的确定判据，替代现在靠感觉判断）。

## 六、人物动作 vs 摄影机运动（严格区分）

需求书明确要求区分。二者常被混写（"镜头跟随他起身"），导致模型把"人物动"演成"镜头动"或反之。

### 6.1 归属判定表

| 现象 | 归属 | 数据位置 |
|---|---|---|
| 人物从坐变站 | **人物动作** | `shot_actions(actor=A, cog=rise)` |
| 人物从 A 点走到 B 点 | **人物动作** | `shot_actions(path)` |
| 人物抬手、转头、握拳 | **人物动作** | `shot_actions(body_parts)` |
| 画面整体向左平移 | **摄影机运动** | `story_shots.movement=truck_left` |
| 画面推近、拉远 | **摄影机运动** | `movement=dolly_in/out` |
| 人物大小不变但背景压缩 | **摄影机运动**（光学变焦） | `movement=zoom_in` |
| 人物大小变化且背景同时变化 | **人物靠近 + 摄影机不动**（除非 `dolly_zoom`） | 需在 `cam_note` 说明 |
| 画面倾斜 | **摄影机运动** | `cam_height=dutch` |
| 人物入画/出画 | **人物动作**（走位）+ 可能伴随摇镜 | `path` + `movement=pan` |

### 6.2 三条硬规则

1. **同一件事不得两处都写**。写 `movement=tracking` 就不许在 `visual_content` 里写"镜头跟着他走"；反之写人物位移就不许用 `movement=crane` 假装。
2. **跟随类运镜必须有人物位移作为理由**。`movement ∈ {tracking, pan_left, pan_right}` 且本镜无 `locomotion` 动作 → WARN「无位移目标却跟拍」。
3. **人物位移必须有落点**。`path` 缺 `to` → FAIL「瞬移」；`path.to` 与下一镜该角色 `position_abs` 不一致超过 1m → FAIL「位移不连续」。

### 6.3 常见错误对照（来自实测）

| 错误写法 | 问题 | 正确拆法 |
|---|---|---|
| "镜头推近，他后退一步" | 两件事互相抵消，画面会糊 | `movement=dolly_in` + `action(path: 后退0.5m)`，二选一为主 |
| "他把纸摔在桌上，镜头一震" | "镜头一震"是效果不是运镜 | `contact(result)` + `sfx`，不写运镜 |
| "镜头环绕他转，他站着不动" | 环绕是无位移主体的运镜，合法但需 `arc` | `movement=arc` + 无 locomotion（合法） |

## 八、校验规则（供 D01-06 实现）

| 编号 | 规则 | 级别 | 判据 |
|---|---|---|---|
| A-01 | 主动作唯一 | FAIL | 一镜内 `is_primary=1` 的行数必须 = 1（`purpose=insert` 可为 0） |
| A-02 | 位移必有路径 | FAIL | `action_type=locomotion` 或 `path.to` 存在 → `path.from/to` 必填 |
| A-03 | 位移不穿模 | FAIL | `path` 线段与 `scene_states.fixtures` 的占位区域相交 → 冲突（需 `via` 绕行） |
| A-04 | 位移连续 | FAIL | 本镜 `path.to` 与下一镜同角色 `position_abs` 距离 > 1m |
| A-05 | 接触有对象 | FAIL | `contact` 存在 → `target_id` 必须存在且 category 匹配 |
| A-06 | 有接触有反应 | WARN | `contact.target_type=char` 且无 `reaction` 行 |
| A-07 | 发力链完整 | FAIL(T3) / WARN(T2) | T3 要求 `force.chain.length ≥ 8`；T2 ≥ 3 |
| A-08 | 档位与内容相符 | WARN | 见 §2 自动判档 |
| A-09 | 动作塞得下 | FAIL | `Σ(t_to - t_from)` > `story_duration` |
| A-10 | 时间片对齐 | FAIL | `time_slices` 总长 ≠ `story_duration`（±0.1s） |
| A-11 | 节奏有依据 | WARN | `speed.profile=sudden` 且无前置 `hold` 片段 |
| A-12 | 无位移不跟拍 | WARN | `movement ∈ {tracking,pan}` 且无 locomotion |
| A-13 | 手持道具状态闭环 | FAIL | `hand_state` 引用的道具不在 `prop_ids`，或动作 `result.prop_delta` 后与下一镜 `state_in` 矛盾 |
| A-14 | 表情与情绪一致 | WARN | `sync.emotion` 与 `shot_actions(expression).result` 情绪极性相反（如 emotion=rage 但表情=smile） |

## 九、与时长预算的联动（解决"动作塞不下"）

现状完全没有这一层：动作写多少字都行，时长按段给，出片后才发现动作被压缩成"平移"。

新模型的预算公式：

```
动作可用时长 = story_duration
              - 台词占用时长（中文 字/3.5，英文 词/3.8）
              - 起势静默（默认 0.3s，T3 打戏 0.5s）
              - 收势静默（默认 0.2s）

要求：Σ 各动作 (t_to - t_from) ≤ 动作可用时长
```

**同时**给出"动作复杂度上限"（超出即建议拆镜）：

| 动作类型 | 单个动作建议时长 | 一镜内建议个数 |
|---|---|---|
| `expression` 表情 | 0.3–1.0s | ≤3（并行） |
| `manipulation` 操作物件 | 0.8–2.0s | ≤2 |
| `locomotion` 位移 | 0.6–2.5s | ≤2 |
| `combat` 单次攻击 | 0.4–1.2s | ≤3（连招可更多，需 T3） |
| `reaction` 反应 | 0.4–1.5s | ≤2 |

这条规则把「密度机检」（每镜 2.5–7.5 秒）从"文本长度推断"升级为"动作数量 × 动作时长推断"，两者互为校验：密度合规但动作塞不下 → 说明这一镜的动作设计有问题（不是时长问题）。

## 十、不做的设计（避免过度工程）

| 不做 | 理由 |
|---|---|
| 不建"动作库/招式库"表 | 招式组合是打戏引擎的职责（`sd-combat-engine`），分镜层只需要"这一镜发生了什么" |
| 不做骨骼/物理仿真 | 视频模型本身做物理，分镜层只需给出物理**意图**（力度/接触点/重心） |
| 不做表情微动作的 FACS 全量编码 | FACS 留给提示词层（`facs-*.md`），分镜层只到"情绪 + 强度 + 可见表情描述" |
| 不强制每镜填 `body_parts` | 只对 T2/T3 要求，T1 只写 `init/end_state` 即可 |
