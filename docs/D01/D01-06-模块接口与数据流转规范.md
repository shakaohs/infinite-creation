## 三、适配层：切分与片段完整性

### 3.1 职责与产物

按 TargetProfile 把 Shot 序列切成单元，产出**一个可版本化的适配方案**（`render_adaptations`）及其单元与片段。

**不属于任何编译器**——否则两编译器会切出不同单元，导演分镜就没有唯一适配记录了。

### 3.2 适配方案（P0-02 新增）

一个 `adaptation` = 一次完整的切分结果，身份是四元组：

```
(project_id, chapter_id, track, profile_ver, adaptation_version)
```

| 触发新版本的场景 | 处理 |
|---|---|
| 第一次给某章某轨道做适配 | `adaptation_version = 1`，`status='active'` |
| 同一 `track` 换 `profile_ver`（SD2.5 → SD2.0） | 新 adaptation，`version = 1`（profile 不同，是另一条序列） |
| 同一 `track` 同一 `profile` 重新切分（改了 `seamPolicy`、改了最短单元） | `adaptation_version +1`；旧方案 `status='superseded'`、`superseded_by=<新id>`，**行不删** |
| 分镜被修改后重切 | 同样 +1 版本；旧方案保留，并在 `source_spec_hash` 上留痕，便于回答"这版切分是对哪版分镜做的" |

**关键**：旧方案保留，意味着同一个 Shot 在同一 `track/profile` 下会同时存在**多套片段划分**。因此：

> **片段完整性校验的作用域是「单个 adaptation」，不是「单个 shot」。**
> 跨 adaptation 的片段重叠是**合法的**（它们是不同版本的方案），不能拿来判 `FRAG_OVERLAP`。

V2 的唯一索引 `uq_ru_no (project_id, track, unit_no)` 无法容纳多版本（新版本会产生相同 `unit_no` → 唯一冲突），V3 改为 `(adaptation_id, unit_no)`。详见 `D01-05 §4.8`。

`Profile` 四个数值的含义与来源（全部快照进 `render_adaptations`，见 `D01-05 §4.14`）：

| 字段 | 含义 | 取值来源 | 例（h3.v1） | 缺失时 |
|---|---|---|---|---|
| `max` | 单次生成时长上限 | TargetProfile（模型能力） | 15 | 不可为空 |
| `shortFloor` | 单元最短可接受时长 | TargetProfile（太短则画面无信息） | 5 | 不可为空 |
| `minSlice` | 镜内切出的最小片段 | TargetProfile（<2s 的片段模型接不住） | 2.0 | 不可为空 |
| `tailHoldMax` | 单元尾镜允许的定格延长上限 | TargetProfile（`tail_hold_max`） | 1.0 | 报 `ADAPT_PROFILE_SNAPSHOT_MISSING`，**不猜** |

**切点：候选 + 跨越检查（P0-01 修正）**

V3 的 `cuts = {a.t_to}` 只保证"切在**某个**动作结束时"，**没有检查其他动作是否正在执行**。

反例：A(0–3.0)、B(1.5–5.0)。3.0 是 A 的 `t_to`，V3 认为它合法；但 B 跨越 3.0（`1.5 < 3.0 < 5.0`），切在这里把 B 劈成两半。

```
candidateCuts(shot) = { 0, story_duration } ∪ { a.t_from } ∪ { a.t_to }

crosses(a, t)  ⟺  (a.t_from + EPS < t) && (t < a.t_to - EPS)

isLegalCut(shot, t)  ⟺  t ∈ candidateCuts(shot)
                    &&  ¬∃ a ∈ shot.actions : crosses(a, t)

legalCuts(shot) = { t ∈ candidateCuts(shot) | isLegalCut(shot, t) }
```

**为什么把 `t_from` 也放进候选**：切在动作**起点**是安全的——动作还没开始，完整留在右片段。V3 把它排除是过度保守，会让"两个动作首尾相接"的镜无点可切（例如 B 从 3.0 开始，而 3.0 恰好是 A 的结束点，V3 只在 `t_to` 里找，能切到，但如果 A 结束于 3.2、B 开始于 3.2，V3 也能切——真正的差别在于**只有 `t_from` 没有 `t_to` 的场景**，如镜首动作从 2.0 开始，V3 无法在 2.0 处切）。

**边界语义（必须写死，否则实现者各按各的理解）**

| 切点位置 | 语义 | 动作归属 |
|---|---|---|
| `t == a.t_from` | 动作在右片段**起点**开始 | 右片段 |
| `t == a.t_to` | 动作在左片段**终点**结束 | 左片段 |
| `a.t_from < t < a.t_to` | **禁止**（动作被劈） | — |
| `t` 不落在任何动作区间内 | 安全（静默段），可直接切 | — |

动作区间采用**半开区间** `[t_from, t_to)`：

```
a 属于左片段  ⟺  a.t_to <= t
a 属于右片段  ⟺  a.t_from >= t
```

两端点不重复计入，因此"切点处的动作"永远只有一个归属。

**片段内时间重基（V3 遗漏，必须补）**

片段 `[f.t_from, f.t_to]` 进入单元后从 0 开始计时，因此片段内所有动作的时间必须相对化：

```
t_local = t_abs - f.t_from
```

| 用途 | 用哪个 |
|---|---|
| `render_unit_shots.t_from / t_to`（存储） | **`t_abs`** |
| 编译器时间轴、投喂提示词的 `At 00:SS.mmm` | **`t_local`** |
| QC 的动作区间校验 | `t_abs`（相对于 `story_duration`） |

两者混用会让第二片段的动作时间整体偏移——例如从 3.0s 处切开的片段，动作时间会被误报成 3.0 而非 0，提示词里就会出现"镜长 4 秒但动作从 3 秒开始"的荒谬描述。

**无合法切点时的行为**

- 若某镜 `story_duration > max`，且 `legalCuts(shot)` 内部只有 `{0, D}`（无任何安全切点）→ 返回 `ADAPT_NO_LEGAL_CUT`；
- **不得**为了满足 `max` 而硬切正在执行的动作；
- 三条处置由人决定（不自动选）：① 在动作设计上补一个自然收势 → ② 拆镜 → ③ 换 profile。

#### 3.3.2 算法

```js
const EPS = 1e-6;

function planAdaptation({ shots, profile, seamPolicy }) {
  const { max, shortFloor, minSlice } = profile;
  const units = [];
  let cur = null;

  const open  = () => { cur = { unitNo: units.length + 1, items: [], dur: 0 }; units.push(cur); };
  const close = () => { cur = null; };
  const put   = (s, a, b) => {
    cur.items.push({ shotId: s.id, tFrom: a, tTo: b, splitReason: (a > EPS || b < s.story_duration - EPS) ? 'oversize' : '' });
    cur.dur += (b - a);
  };

  for (const s of shots) {
    const D = s.story_duration;
    let consumed = 0;

    while (consumed < D - EPS) {
      if (!cur) open();
      const remain = D - consumed;
      const room   = max - cur.dur;

      // ① 整段剩余装得下 → 放入，本镜结束
      if (remain <= room + EPS) { put(s, consumed, D); consumed = D; break; }

      // ② 剩余空间不足一个片段 → 关单元，下轮在新单元里放
      if (room < minSlice + EPS) { close(); continue; }

      // ③ 在 [consumed+minSlice, consumed+room] 内找最大的合法切点
      const cut = pickLegalCut(s, consumed + minSlice, consumed + room);

      if (cut === null) {
        // 本单元内切不了。
        if (cur.items.length === 0) {
          // 空单元都放不下 → 该镜本身超限且无合法断点 → 适配失败，不硬切
          return { ok: false, code: 'ADAPT_NO_LEGAL_CUT', shotId: s.id,
                   detail: { storyDuration: D, max, minSlice,
                             candidates: explainNoCut(s, consumed + minSlice, consumed + room) } };
        }
        close(); continue;      // 关掉当前单元，换个新单元再试（新单元 room 更大）
      }

      put(s, consumed, cut);
      consumed = cut;
      close();                  // 切完即接近满，关单元；剩余部分进下一单元
    }
  }

  // 尾单元处理
  if (units.length >= 2) {
    const last = units[units.length - 1], prev = units[units.length - 2];
    if (last.dur < shortFloor - EPS && prev.dur + last.dur <= max + EPS) {
      prev.items.push(...last.items);
      prev.dur += last.dur;
      units.pop();
    }
  }

  const warnings = [];
  const tail = units[units.length - 1];
  if (tail && tail.dur < shortFloor - EPS) {
    warnings.push({ code: 'SHORT_UNIT', unitNo: tail.unitNo, dur: tail.dur,
                    msg: `尾单元 ${tail.dur}s 低于最短 ${shortFloor}s，且无法并入前一单元`,
                    suggest: '缩短上一镜或延长尾镜，或接受该单元（出片后可能信息量不足）' });
  }

  // 单元号重排（尾合并后可能缺号）
  units.forEach((u, i) => { u.unitNo = i + 1; });
  return { ok: true, units, warnings };
}

/** 候选切点：镜边界 + 所有动作的起点与终点 */
function candidateCuts(s) {
  const set = new Set([0, r6(s.story_duration)]);
  for (const a of s.actions || []) { set.add(r6(a.t_from)); set.add(r6(a.t_to)); }
  return [...set].filter(c => c >= -EPS && c <= s.story_duration + EPS).sort((x, y) => x - y);
}

/** 该切点是否会把任何动作劈成两半 */
function crossingActions(s, t) {
  return (s.actions || []).filter(a => (a.t_from + EPS < t) && (t < a.t_to - EPS));
}

function isLegalCut(s, t) {
  if (t <= EPS || t >= s.story_duration - EPS) return true;   // 镜边界恒合法
  return crossingActions(s, t).length === 0;                  // 必须不被任何动作跨越
}

function legalCuts(s) {
  return candidateCuts(s).filter(t => isLegalCut(s, t));
}

function pickLegalCut(s, lo, hi) {
  const cands = legalCuts(s).filter(t => t >= lo - EPS && t <= hi + EPS && t > EPS && t < s.story_duration - EPS);
  return cands.length ? cands[cands.length - 1] : null;   // 取最大 → 尽量装满
}

/** 失败时给出"为什么没有切点"，供人而不是程序做决定 */
function explainNoCut(s, lo, hi) {
  return candidateCuts(s)
    .filter(t => t > EPS && t < s.story_duration - EPS)
    .map(t => ({ at: t, inWindow: t >= lo - EPS && t <= hi + EPS,
                 blockedBy: crossingActions(s, t).map(a => ({ id: a.id, from: a.t_from, to: a.t_to })) }))
    .filter(x => x.blockedBy.length || x.inWindow);
}
```

**为什么取最大切点**：单元越满，单元数越少，出片次数越少（成本与漂移风险都更低）。取最小切点会切出大量短单元。

**为什么不用 bin-packing 求全局最优**：切点受动作约束，可行解空间是每镜若干离散偏移，贪心在"每镜切点独立"的前提下已经是局部最优；全局最优需要跨镜重新分配（把 sh_03 的尾巴挪到下一单元换取 sh_06 完整），但这会**增加一次切镜**，从而多一个接缝，代价高于收益。这是权衡，不是最优解，已在 `D01-10 §六` 记录。

| 镜 | 时长 | 动作 `t_to` |
|---|---|---|
| sh_01 | 6.0 | 2.0, 4.5 |
| sh_02 | 5.5 | 3.0 |
| sh_03 | 7.0 | 3.5, 6.0 |

| sh_05 | 5.0 | 2.5 |

| sh_07 | 5.5 | 3.0 |
| sh_08 | 4.5 | — |

逐步：

| 步骤 | 单元 | 动作 | acc |
|---|---|---|---|
| 1 | U1 | sh_01 整段 (0,6.0) | 6.0 |
| 2 | U1 | sh_02 整段 (0,5.5) | 11.5 |
| 3 | U1 | sh_03 整段 (0,7.0) | 18.5 |
| 4 | U1 | sh_04 整段 (0,4.0) | 22.5 |
| 5 | U1 | sh_05 整段 (0,5.0) | 27.5 |
| 6 | U1 | sh_06 剩 6.0 > room 2.5；`pickLegalCut(1.5, 2.5)` → **2.0** | 29.5，关 U1 |
| 7 | U2 | sh_06 剩 (2.0,6.0)=4.0 | 4.0 |
| 8 | U2 | sh_07 (0,5.5) | 9.5 |
| 9 | U2 | sh_08 (0,4.5) | 14.0 |

结果：**U1 = 29.5 / U2 = 14.0**，两单元。

校验：

```
Σfragment(U1) = 6.0+5.5+7.0+4.0+5.0+2.0 = 29.5 ≤ unit_duration(29.5) ≤ max(30)   ✓
Σfragment(U2) = 4.0+5.5+4.5 = 14.0 ≤ max(30)                                       ✓
sh_06 片段 (0,2.0)+(2.0,6.0) 覆盖 [0,6.0]，不重叠，切点 2.0 ∈ 动作 t_to          ✓
```

注意第 6 步：若 `room` 是 1.0（< `minSlice` 1.5），算法走分支②关单元，sh_06 完整进 U2，结果会变成 U1=27.5 / U2=16.0——**不会**切出 1.0s 的碎片。

#### 3.3.4 算例 B：H3 15s 上限下的超长镜头（修正 V2 的算术错误）

`profile = h3.v1`（`max=15, shortFloor=5, minSlice=2.0`）

| 镜 | 时长 | 动作 `t_to` |
|---|---|---|
| sh_18 | 4.0 | 1.5 |
| sh_19 | 6.0 | 3.0 |
| **sh_20** | **20.0** | 3.0, 7.0, 11.5, 16.0 |
| sh_21 | 5.0 | 2.5 |

逐步：

| 步骤 | 单元 | 动作 | acc |
|---|---|---|---|
| 1 | U1 | sh_18 (0,4.0) | 4.0 |
| 2 | U1 | sh_19 (0,6.0) | 10.0 |
| 3 | U1 | sh_20 剩 20.0 > room 5.0；`pickLegalCut(2.0, 5.0)` → 候选 {3.0} → **3.0** | 13.0，关 U1 |
| 4 | U2 | sh_20 剩 17.0 > room 15.0；`pickLegalCut(5.0, 18.0)` → 候选 {7.0, 11.5, 16.0} → **16.0** | 13.0，关 U2 |

结果：**U1 = 13.0 / U2 = 13.0 / U3 = 9.0**。

```
片段：sh_20 (0,3.0) + (3.0,16.0) + (16.0,20.0) = 3.0+13.0+4.0 = 20.0 = story_duration   ✓
无重叠、无缺口、切点全部 ∈ {3.0,7.0,11.5,16.0}                                          ✓
U1 13.0 ≤ 15  U2 13.0 ≤ 15  U3 9.0 ≤ 15                                                 ✓
尾单元 9.0 ≥ shortFloor 5                                                               ✓
```

**V2 的错误必须记下来**（这是本轮 P0-03 的直接证据）：

> V2 `D01-06 §3.5` 给的是 `sh_20 (0,9.0)` + `(9.0,20.0)`，然后 U3 = `sh_19 6.0 + sh_20 9.0`、U4 = `sh_20 11.0 + sh_21 5.0`。
> 其中 **U4 = 11.0 + 5.0 = 16.0 > 15**，超限 1 秒；且 `9.0` 这个切点不在 sh_20 的任何动作 `t_to` 上（动作断点是 3/7/11.5/16），**切在了动作中段** —— 同时违反了"单元不得超 max"和"不得劈开动作"两条自定规则。
> 根因：V2 的伪代码写的是 `acc += 截取长度`，但没定义"截取长度怎么算"，示例是手写数字而非算法产出。**伪代码与示例不对应，示例就没人验算。**

#### 3.3.6 算例 D：一个动作结束、另一个仍在执行 → 必须失败

这是 P0-01 的核心反例。**V3 的算法会在这里切错**。

**输入**

| 项 | 值 |
|---|---|
| 镜 | `sh_30`，`story_duration = 20.0` |
| profile | `h3.v1`（`max=15`、`shortFloor=5`、`minSlice=2.0`） |
| 动作 A1（哈罗德） | `0.0 – 10.0` 走向床边 |
| 动作 A2（罗克珊） | `2.0 – 16.0` 缓慢坐起并转头 |

**处理过程**

```
候选切点（V4，含 t_from）：{0, 2, 10, 16, 20}
可用窗口：consumed=0，room=15 → 需在 [2, 15] 内切

逐点检查跨越：
  t=2    A1 跨越（0 < 2 < 10）      → 非法
  t=10   A2 跨越（2 < 10 < 16）     → 非法
  t=16   超出窗口上限 15             → 不在考虑范围
  t=0,20 是镜边界，但都在窗口外       → 不可用

legalCuts 中落在 [2,15] 的 = ∅
```

**V3 会怎么做**：V3 的候选只有 `{a.t_to} = {10, 16}`，窗口内只有 **10**，于是切在 10 —— 此时 A2 已执行到 8 秒（从 2 秒起），硬切等于**把罗克珊"正在坐起"的动作从中间截断**，第二段只能从"半坐"继续，模型必然重演或跳变。

**预期输出**

```json
{
  "ok": false,
  "code": "ADAPT_NO_LEGAL_CUT",
  "shotId": "sh_30",
  "detail": {
    "storyDuration": 20.0, "max": 15, "minSlice": 2.0,
    "candidates": [
      { "at": 2,  "inWindow": true,  "blockedBy": [{ "id": "ac_A1", "from": 0, "to": 10 }] },
      { "at": 10, "inWindow": true,  "blockedBy": [{ "id": "ac_A2", "from": 2, "to": 16 }] }
    ]
  }
}
```

**触发的错误码**：`ADAPT_NO_LEGAL_CUT`（**不是** `FRAG_CUT_MID_ACTION`——后者是落库前的二次校验，前者是切分阶段就该拒绝）。

**数据库约束**：此镜不产生任何 `render_unit_shots` 行；`render_adaptations` 记一条 `status='failed'`，`status_reason='ADAPT_NO_LEGAL_CUT'`，`unit_count=0`。

**处置**（由人决定，不自动选）：A1 与 A2 交叠覆盖了整个 2–15 窗口，唯一的出路是 ① 让 A2 的坐起在 10 秒前有个自然停顿（改动作）→ ② 把这一镜拆成两镜 → ③ 换更长上限的 profile。

#### 3.3.7 算例 E：多人物动作重叠但仍可合法切分

同样是三人并行、结束时间各不相同，但动作之间有安全空隙。

**输入**

| 项 | 值 |
|---|---|
| 镜 | `sh_31`，`story_duration = 22.0` |
| profile | `h3.v1`（`max=15`、`shortFloor=5`、`minSlice=2.0`） |
| A1（哈罗德） | `0.0 – 5.0` |
| A2（罗克珊） | `3.0 – 13.0`（跨 A1 的结束点 5.0） |
| A3（凯森） | `15.0 – 19.0` |

**处理过程**

```
候选切点：{0, 3, 5, 13, 15, 19, 22}
窗口 [2, 15]

  t=3    A1 跨越（0<3<5）        → 非法
  t=5    A2 跨越（3<5<13）       → 非法
  t=13   A2 终点，A3 未开始      → 合法 ✓
  t=15   A3 起点                 → 合法 ✓

legalCuts ∩ [2,15] = {13, 15}，取最大 → 15
```

**预期输出**

| 单元 | 片段 | 时长 |
|---|---|---|
| U1 | `sh_31 (0, 15.0)` | 15.0 |
| U2 | `sh_31 (15.0, 22.0)` | 7.0 |

```
A1 (0–5)   完整落在 U1 ✓
A2 (3–13)  完整落在 U1 ✓（跨 A1 结束点，但不跨切点 15）
A3 (15–19) 完整落在 U2，局部时间 0–4 ✓
Σfrag = 15.0 + 7.0 = 22.0 = story_duration ✓
U1 = 15.0 ≤ max 15 ✓   U2 = 7.0 ≥ shortFloor 5 ✓
```

**V3 会怎么做**：候选 `{0, 5, 13, 19, 22}`，窗口内 `{5, 13}`，取最大 **13** → U1=13.0 / U2=9.0。这个结果**也是合法的**（13 是 A2 终点），只是没装满。

**两个算例合起来说明**：V3 的错误不是"总是切错"，而是**在某些动作交叠形态下会切错（算例 D），在另一些形态下只是切得不够满（算例 E）**。前者是硬伤，后者是优化空间。只测后者会以为算法没问题。

**触发的错误码**：无。

**数据库约束**：`sh_31` 在 `render_unit_shots` 出现 2 行，分属不同 `unit_id`，`t_from` 分别为 0 与 15.0；`UNIQUE(unit_id, shot_id)` 不冲突（两个 unit 不同）。

#### 3.3.8 算例 F：动作恰好从切点开始 / 恰好到切点结束（边界测试）

算例 E 的 15 是 A3 起点，但那只是"顺手取到"。本算例专门把切点压在边界上，验证三件事：**起点可切、终点可切、且动作不重复播放**。

**输入**

| 项 | 值 |
|---|---|
| 镜 | `sh_32`，`story_duration = 18.0` |
| profile | `h3.v1`（`max=15`、`shortFloor=5`、`minSlice=2.0`） |
| A1（哈罗德） | `0.0 – 12.0` 走到床尾站定 |
| A2（罗克珊） | `12.0 – 16.0` 接话同时抬眼（`t_from` 恰等于 A1 的 `t_to`） |
| A3（凯森） | `16.0 – 18.0` 合上病历夹（`t_to` 恰等于镜尾） |

**处理过程**

```
candidateCuts = {0, 12, 16, 18}
窗口 [2, 15]

  t=12  A1: crosses? 0+ε < 12 && 12 < 12-0 ?  → 12 < 12 为假 → 不跨越 ✓
        A2: crosses? 12+ε < 12 为假          → 不跨越 ✓
        A3: 不涉及                            → 不跨越 ✓
        → 合法（A1 终点 + A2 起点，同一点既是终点又是起点）
  t=16  超窗口上限 15                       → 不在候选范围

legalCuts ∩ [2,15] = {12}  → 取 12
```

**预期输出**

| 单元 | 片段 | 时长 | 片段内动作（`t_local`） |
|---|---|---|---|
| U1 | `sh_32 (0, 12.0)` | 12.0 | A1 `0.0–12.0` |
| U2 | `sh_32 (12.0, 18.0)` | 6.0 | A2 `0.0–4.0`、A3 `4.0–6.0` |

```
A1 完整落在 U1，t_local 0–12           ✓ 不在 U2 重播
A2 t_from = 12.0 = 切点 → 归属 U2      ✓ 只属于 U2（半开区间 [12,16)）
A3 t_to = 18.0 = 镜尾 → 归属 U2        ✓
Σfrag = 12.0 + 6.0 = 18.0 = story_duration ✓
U1 = 12.0 ≤ 15 ✓    U2 = 6.0 ≥ shortFloor 5 ✓   两片段均 ≥ minSlice 2.0 ✓
```

**归属唯一性验算**（这是本算例的重点）：

```
左片段判据：a.t_to <= t   → A1: 12.0 <= 12.0 真 → 属 U1
右片段判据：a.t_from >= t → A2: 12.0 >= 12.0 真 → 属 U2
若实现按 a.t_from <= t 判左、a.t_to >= t 判右，则 A1 同时满足两侧（12<=12 且 12>=0），
A1 会被播两遍。半开区间必须写成 t_to <= t（左）与 t_from >= t（右），不能写成 < / >。
```

**应触发**：无错误。
**不应触发**：`FRAG_CUT_MID_ACTION`（12.0 不是任何动作的内部点）、`FRAG_FRACTION_MISMATCH`（`t_local` 已重基）。

**数据库约束**：`sh_32` 在 `render_unit_shots` 2 行，`(0, 12.0)` 与 `(12.0, 18.0)`——**两行首尾相接不重叠**，`UNIQUE(unit_id, shot_id)` 各自成立。

**V4 会怎么做**：这条路 V4 也能走对（它的 `candidateCuts` 已含 `t_from`），但 V4 没有任何算例验证"`t_from` 与 `t_to` 重合于一点"的归属，实现者极可能在这里把 A1 播两遍。本算例把该点固定成回归项（`D01-06 §4.6 R-36`）。

### 3.4 片段完整性校验（按 adaptation 执行）

```js
/**
 * 作用域：单个 adaptation
 * @returns {{ ok: boolean, errors: [], warnings: [] }}
 */
export function verifyAdaptation({ adaptationId }) {
  const errors   = [];
  const warnings = [];
  const units  = selectUnits(adaptationId);              // status ∈ active|superseded
  const shots  = uniqueShotsOf(units);

  for (const u of units) {
    // U-1 单元不超上限
    if (u.unitDuration > u.profileMax + EPS)
      errors.push({ code: 'UNIT_OVERFLOW', unitId: u.id, dur: u.unitDuration, max: u.profileMax });

    // U-2 单元时长 ≥ 片段之和；差额只允许是尾镜定格，且不得过大
    const sum = u.items.reduce((n, f) => n + (f.tTo - f.tFrom), 0);
    if (u.unitDuration < sum - 0.01)
      errors.push({ code: 'UNIT_DURATION_MISMATCH', unitId: u.id, sum, declared: u.unitDuration,
                    msg: '声明时长小于片段之和，片段装不进去' });

    const pad = u.unitDuration - sum;

    // ★ tailHoldMax 只从 adaptation 快照读，不兜底默认（D01-05 §4.14.1）
    const tailHoldMax = u.profileTailHoldMax;
    if (tailHoldMax == null) {
      warnings.push({ code: 'ADAPT_PROFILE_SNAPSHOT_MISSING', unitId: u.id,
                      field: 'profile_tail_hold_max',
                      msg: '方案缺 tailHoldMax 快照，无法校验单元留白；不猜默认值' });
    } else if (pad > tailHoldMax + 0.01) {
      errors.push({ code: 'UNIT_PADDING_EXCESS', unitId: u.id, pad, allowed: tailHoldMax,
                    msg: '片段之和远小于单元时长，多出的时长没有内容依据' });
    }

    // U-3 单元内顺序连续
    const ord = u.items.map(f => f.orderNo);
    for (let i = 0; i < ord.length; i++)
      if (ord[i] !== i + 1) errors.push({ code: 'UNIT_ORDER_BROKEN', unitId: u.id });
  }

  for (const s of shots) {
    const frags = fragsOf(adaptationId, s.id).sort((a, b) => a.tFrom - b.tFrom);

    // F-1 覆盖起点与终点
    if (!frags.length) { errors.push({ code: 'FRAG_MISSING_SHOT', shotId: s.id }); continue; }
    if (frags[0].tFrom > EPS) errors.push({ code: 'FRAG_GAP_HEAD', shotId: s.id, at: frags[0].tFrom });
    if (frags.at(-1).tTo < s.storyDuration - EPS)
      errors.push({ code: 'FRAG_GAP_TAIL', shotId: s.id, at: frags.at(-1).tTo, want: s.storyDuration });

    // F-2 相邻片段首尾相接（不重叠、不遗漏）
    for (let i = 1; i < frags.length; i++) {
      const d = frags[i].tFrom - frags[i - 1].tTo;
      if (d > EPS)  errors.push({ code: 'FRAG_GAP', shotId: s.id, from: frags[i-1].tTo, to: frags[i].tFrom });
      if (d < -EPS) errors.push({ code: 'FRAG_OVERLAP', shotId: s.id, at: frags[i].tFrom });
    }

    // F-3 不越出原生时长
    for (const f of frags) {
      if (f.tFrom < -EPS || f.tTo > s.storyDuration + EPS || f.tTo <= f.tFrom)
        errors.push({ code: 'FRAG_OUT_OF_RANGE', shotId: s.id, tFrom: f.tFrom, tTo: f.tTo, dur: s.storyDuration });
      // F-4 切点必须落在合法切点集合
      if (!isLegalCut(s, f.tTo) && f.tTo < s.storyDuration - EPS)
        errors.push({ code: 'FRAG_CUT_MID_ACTION', shotId: s.id, at: f.tTo });
    }
  }

  // F-5 单元跨场景（只警告，不失败）
  units.filter(u => crossesScene(u)).forEach(u =>
    warnings.push({ code: 'UNIT_CROSS_SCENE', unitId: u.id }));

  return { ok: errors.length === 0, errors, warnings };
}
```

**必须强调的执行范围**：

| 检查 | 作用域 | 跨 adaptation 时 |
|---|---|---|
| F-1 ~ F-4（片段补集） | 单 adaptation 内的**该 shot 全部片段** | **允许重叠**，不得报错 |
| U-1 ~ U-3（单元约束） | 单 unit | — |
| 跨 adaptation 一致性 | 不做 | 它们是不同版本，本就不同 |

错误码一览：

| code | 含义 | 处置 |
|---|---|---|
| `ADAPT_NO_LEGAL_CUT` | 整镜超 max 且无合法动作断点 | **适配失败**，返回给创作者：拆镜或延长/缩短，不得硬切 |
| `UNIT_OVERFLOW` | 单元超 profile.max | 算法 bug，拒绝落库 |
| `UNIT_DURATION_MISMATCH` | 声明时长 < 片段之和 | 拒绝落库 |
| `UNIT_PADDING_EXCESS` | 声明时长 ≫ 片段之和（差额超过 `tailHoldMax`） | 拒绝落库 |
| `FRAG_GAP` / `FRAG_GAP_HEAD` / `FRAG_GAP_TAIL` | 片段有缺口 | 拒绝落库 |
| `FRAG_OVERLAP` | 同 adaptation 内重叠 | 拒绝落库 |
| `FRAG_OUT_OF_RANGE` | 越出 `[0, story_duration]` | 拒绝落库 |
| `FRAG_CUT_MID_ACTION` | 切点劈开动作 | 拒绝落库 |
| `SHORT_UNIT` | 尾单元低于 shortFloor | 警告，可落库 |
| `UNIT_CROSS_SCENE` | 单元跨 2 场景 | 警告（`D01-01 §3.7` 允许但标风险） |

### 3.5 不可切时怎么办（明确拒绝）

`ADAPT_NO_LEGAL_CUT` 是**正常返回**，不是异常。典型场景：一个 20s 长镜头全程一个连续长动作（无 `t_to` 断点），H3 上限 15s。

返回给创作者的三条处置建议（不自动选）：

1. 在动作设计上**补一个可断点**（自然的动作收势），这属于改创作态，必须人工决定；
2. **拆镜**（把 20s 拆成两个导演镜，各自有独立构图），这是导演决策；
3. **换 profile**（该轨道不可用 → 用支持更长时长的模型）。

**禁止**：截断到 15s 丢掉 5s 内容、拉伸动作、加速播放。这三种都会破坏导演设计，而 `D01` 的核心原则是"适配不改变创作"。

## 四、三种哈希（P0-01 重写）

### 4.1 为什么必须是三种

V2 只有一个 `sourceSpecHash`，而它的 payload 里包含 `unit.track` / `profile_ver` / `unit_duration` / `fragments`。后果：

- 同一份分镜在 Seedance 和 H3 下 `track` 必然不同 → **两个 hash 必然不同**；
- V2 却把 `H-21「双编译器同输入两 sourceSpecHash 逐字相同」` 写成 CI 断言 → **这条断言在 V2 的设计下永远失败**；
- V2 的 `H-19「改 track → hash 变」`、`H-20「改 fragments → hash 变」` 进一步把这个错误固化成"预期行为"。

也就是说：**V2 声称"能证明同源"，但它定义的函数在结构上就不可能输出同源结果。** 这是本轮最重的一处定义冲突。

正确做法是把三件事分开：**导演做了什么 / 怎么切成片 / 用什么程序编译**。

```
┌─────────────────────────┐      ┌──────────────────────────┐
│  L0 创作态                │      │  L1 适配态                 │
│  ShotSpec + 动作 + 空间    │      │  track / profile / 片段    │
└───────────┬─────────────┘      └────────────┬─────────────┘
            │                                  │
     sourceSpecHash                     adaptationHash
            │                                  │
            └──────────────┬───────────────────┘
                           ▼
                   compiledHash
              （+ compilerVer + 编译参数）
```

三个 hash **相互正交**：任一维度变化只影响自己及其下游。

| 维度 | hash | 回答的问题 |
|---|---|---|
| 创作 | `sourceSpecHash` | 这两条片子拍的是不是同一份分镜？ |
| 适配 | `adaptationHash` | 切分方案有没有变？ |
| 编译 | `compiledHash` | 产物是不是同一版程序在同参数下的结果？ |

### 4.2 `sourceSpecHash` · 只覆盖导演语义

**明确排除**（这些字段变了，`sourceSpecHash` 必须不变）：

| 排除项 | 理由 |
|---|---|
| `track`、`profile_ver`、`unit_duration`、`unit_no`、`seam` | 属于适配决策，不进创作语义 |
| `render_unit_shots.t_from/t_to`、`split_reason` | 切分结果，不是导演意图 |
| `shot.id`、`action.id`、`created_at`、`updated_at`、`qc_status`、`fill_confidence`、`spec_source` | 非语义；`action.id` 排除后由 `contentHash` 承担引用映射 |
| 任何以 `_` 开头的键（V4 的 `_id`/`_ref`/`_par`） | 实现细节，不是语义；V5 改为白名单 `bodyOf()` 后这类键**不可能**进入 payload（P1-02） |
| `voice_ids` | 派生兼容字段，权威是 `shot_assets(role=voice)` |
| `prompt_packages.*`、`render_attempts.*` | 下游产物 |

**注意 `seam` 的归属判断**：`seam`（段缝策略）影响"这一镜是不是单元收尾、要不要加定格句"。哪一镜成为单元收尾是**切分决定的**，不是导演决定的——同一镜在 30s 切法里是段中，在 15s 切法里可能是段尾。所以 `seam` 归 `adaptationHash`。V2 把它放进 `unit` 再进 source，是错的。

**`state_in_meta` / `state_out_meta` 必须进 hash**：否则"把 unknown 悄悄改成 known 的猜测值"不会改变 hash，同源证明就形同虚设。

**音色（P1-05）：`shot_assets(role='voice')` 是唯一权威，`voice_ids` 不进 hash**

| 问题 | 答案 |
|---|---|
| 音色是否统一走 `shot_assets` | **是**。`role='voice'`，`category ∈ {voice, narration}`，每镜 ≤3 |
| `voice_ids` 保留吗 | **保留，但降级为只读派生字段**：由 `shot_assets(role='voice')` 按 `order_no` 渲染出一维数组，只供旧页面/旧 API 读 |
| 两个字段能否都是权威 | **不能**。写入时只写 `shot_assets`，`voice_ids` 由程序在读出时现算；任何代码不得以 `voice_ids` 为准 |
| hash 用哪个 | **`shot_assets` 的 voice 条目 + 内容指纹**，即 payload 里的 `assets` 数组（`role='voice'`） |
| 音色变了 hash 会变吗 | **会**。`assets[].fp` 是该资产的内容指纹，换音色 = 换 `asset_id` 或换 `fp` → hash 变 |

**为什么必须这样**：若 `voice_ids` 和 `shot_assets` 都是权威，改一处漏一处时 hash 会漏掉变化——"同源证明"会证明一个已经不存在的事实。派生字段的唯一职责是兼容旧读者，不是记录事实。

#### 4.2.1 动作的规范序与引用映射（P1-06）

V3 的排序键是 `(tFrom, actor)`。这**不是全序**：

- 同一镜里多个动作 `tFrom` 都等于 0（很常见），且同一 actor 在同一时刻有多个动作时，顺序取决于输入数组；
- 数据库返回顺序一变，`sourceSpecHash` 就变——**同源证明失效**。

**V4 规则**：

```
① 动作按 (tFrom, actor, tTo, type, contentHash) 排序 —— 五项全序，与输入顺序无关
② 动作的 `id` 不进 hash（否则"复制一个动作换个 id"会改变 hash）
③ trigger.ref / sync.parallel_with 中的动作 id → 映射为该动作的 contentHash
   （目标不在本镜内时保留原字符串，如 "sfx:monitor"）
④ contentHash = sha256(canonicalStringify(动作语义体))
```

**V5 修正（P1-02）：`contentHash` 的输入必须是纯语义体**

V4 的实现是 `contentHashOf(a) { const { _id, ...rest } = a; ... }`——**只排除了 `_id`**，而 `_ref` / `_par` 这两个临时映射字段仍在对象里，于是：

```
A2.trigger.ref = "ac_1"（A1 的 id）
→ A2 的 contentHash 里含字符串 "ac_1"
→ 把 A1 改名成 "ac_9" 并同步更新引用，A2 的内容一字未改，contentHash 却变了
→ sourceSpecHash 变 → "同源"证明被 id 命名污染
```

更糟的是它在排序里自引用：排序键用 `contentHash`，`contentHash` 里含**别人**的 id，而别人的 id 又不进 hash——**排序键与被排序对象之间出现了不该有的耦合**，重命名可能改变动作顺序，进而改变 payload 顺序。

**V5 规则（取代 V4 的 ④）**：

```
④ contentHash = sha256(canonicalStringify(body(a)))
   body(a)  = 动作的语义字段全集（见下方 `bodyOf()`，20 个业务字段），
              结构性排除 _id / _ref / _par / 任何以 _ 开头的临时键
⑤ 先算全部 body 与 contentHash（此时不读任何 id），再建 id→contentHash 映射，最后回填引用
⑥ 引用映射的结果（triggerRef / parallelWith）是 payload 的字段，但它取值为 contentHash，
   因此"改引用目标的引用关系"会变 hash，"改引用目标的 id 命名"不会变
```

```js
// 只挑语义字段；白名单而非黑名单——新加的临时字段不会意外漏进 hash
function bodyOf(a) {
  return {
    actor: a.actor_id, type: a.action_type, primary: !!a.is_primary, tier: a.tier,
    init: a.init_state,
    trigger: stripRef(a.trigger_json),        // 去掉 ref，留空占位
    path: a.path_json, force: a.force_json, speed: a.speed_json,
    power: a.power, cog: a.cog, parts: arr(a.body_parts),
    contact: a.contact_json, result: a.result_json, follow: a.follow_through,
    recovery: a.recovery, end: a.end_state,
    sync: stripRef(a.sync_json),              // 去掉 parallel_with
    tFrom: num(a.t_from), tTo: num(a.t_to)
  };
}

function contentHashOfBody(body) {
  return sha256(canonicalStringify(body));    // 纯语义体，无任何 id
}

function canonicalActions(s) {
  const raw = (s.actions || []).map(a => ({
    id: a.id,                                  // 仅用于建映射，绝不进 hash
    ref: a.trigger_json?.ref || '',
    par: arr(a.sync_json?.parallel_with, []),
    body: bodyOf(a),
    ch: null                                   // contentHash，下面填
  }));

  // ① 先算 contentHash（此时不读任何 id）
  for (const r of raw) r.ch = contentHashOfBody(r.body);

  // ② 全序排序（五项，末项用 contentHash）
  raw.sort((x, y) =>
    (x.body.tFrom - y.body.tFrom) ||
    String(x.body.actor).localeCompare(String(y.body.actor)) ||
    (x.body.tTo - y.body.tTo) ||
    String(x.body.type).localeCompare(String(y.body.type)) ||
    x.ch.localeCompare(y.ch));

  // ③ id → contentHash（同镜内）
  const refMap = new Map(raw.map(r => [r.id, r.ch]));

  // ④ 回填引用：引用目标是 contentHash，不是 id
  return raw.map(r => ({
    ...r.body,
    triggerRef: r.ref ? (refMap.get(r.ref) ?? `ext:${r.ref}`) : null,
    parallelWith: r.par.map(t => refMap.get(t) ?? `ext:${t}`).sort()
  }));
}
```

**为什么用白名单 `bodyOf` 而不是 `{ const { _id, _ref, _par, ...rest } = a }`**：黑名单要求"每加一个临时字段都记得加一行排除"，漏一次 hash 就被污染且**没有任何报错**。白名单要求"每加一个语义字段都记得加一行包含"，漏了会在 `R-01`（改任一字段 hash 必须变）当场暴露。**两种遗漏的可见性完全不同，选白名单。**

**外部引用（`ext:` 前缀）**：`trigger.ref` 指向本镜之外的对象（如 `sfx:monitor`、`prev_shot:sh_10`）时，映射不到本镜动作，保留 `ext:<原字符串>`。这是稳定表示——它不依赖任何数据库 id，只依赖那个外部标识本身。

**已知的可接受歧义**：若同一镜内存在两个**内容完全相同**的动作（body 全字段相等），它们的 `contentHash` 相同，`triggerRef` 指向二者之一无法区分。这在语义上无差别（两个动作一模一样），因此不视为缺陷——但**必须显式记录**，不得靠"数据库返回顺序决定指向谁"来隐式处理（§4.2.2）。

#### 4.2.2 引用映射的确定性边界

| 情形 | 是否确定 | 处理 |
|---|---|---|
| 引用一个 body 唯一的动作 | ✅ | `contentHash` 唯一，映射无歧义 |
| 引用两个 body 全等的动作之一 | ⚠️ 有歧义 | 二者语义无差别，hash 相同即视为同一目标；在 `qc_reports` 记 `REF_AMBIGUOUS_CONTENT`（INFO） |
| 引用目标不在本镜 | ✅ | `ext:<原字符串>` |
| `parallel_with` 乱序 | ✅ | `.sort()` 后写入 |
| 同一对动作双向都声明 `parallel_with` | ✅ | 两边各自映射，值相同 |

**"不得偷偷依赖数据库顺序"的落地**：若实现按 `raw` 的输入顺序去 `refMap.get()` 并在重复 contentHash 时取第一个，结果会随 `SELECT` 顺序变化。V5 规定：重复 `contentHash` 时，`triggerRef` 取该 contentHash 即可（**不取实例**），因为 contentHash 相同的两个动作在被引用这件事上完全等价。

**排序确定性的验证**（§4.6 R-26）：把同一组动作按正序、逆序、随机三种顺序传入 `sourceSpecHash`，hash 必须逐字相同。

### 4.3 `adaptationHash` · 只覆盖切分方案

```js
function adaptationHash({ adaptation, units, fragments }) {
  const payload = {
    hashKind: 'd01.adaptation',
    adaptationVersion: adaptation.adaptation_version,
    track: adaptation.track,
    profileVer: adaptation.profile_ver,
    profileParams: {                       // profile 的四个能力参数（快照值），换任一数值即换适配
      max: num(adaptation.profile_max),
      shortFloor: num(adaptation.profile_short_floor),
      minSlice: num(adaptation.profile_min_slice),
      tailHoldMax: num(adaptation.profile_tail_hold_max)   // 缺失 → null，不补默认值
    },
    seamPolicy: adaptation.seam_policy_json,   // 段缝策略（含 tailHold）
    units: units
      .slice().sort((a, b) => a.unit_no - b.unit_no)
      .map(u => ({
        unitNo: u.unit_no,
        unitDuration: num(u.unit_duration),
        shots: fragments
          .filter(f => f.unit_id === u.id)
          .sort((a, b) => a.order_no - b.order_no)
          .map(f => ({ shotId: f.shot_id, orderNo: f.order_no,
                       tFrom: num(f.t_from), tTo: num(f.t_to), reason: f.split_reason }))
      }))
  };

```

**不包含 `sourceSpecHash`**：这是刻意的。若把源 hash 混进来，"切分方案本身有没有变"就无法单独回答。组合关系由 `compiledHash` 承担。

### 4.4 `compiledHash` · 组合

```js
function compiledHash({ sourceHash, adaptationHash, compilerVer, compilerParams }) {
  const payload = {
    hashKind: 'd01.compiled',
    sourceSpecHash: sourceHash,
    adaptationHash,
    compilerVer,
    compilerParams: canonical(compilerParams, [
      'format',          // 'ref2va' | 't2va'
      'language',        // 'en' | 'zh'
      'aspectRatio',
      'fps',
      'refPackPolicy',   // 'ordered' | 'by-role'
      'seamInjection'    // true | false
    ])
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

用途：
- 产物幂等（同 hash 不重复插 `prompt_packages`）；
- 回答"这条片子是哪套分镜 + 哪套切分 + 哪个编译器版本产的"。

**三者关系（可判定的推论）**：

| 操作 | source | adaptation | compiled |
|---|---|---|---|
| 改一句台词 | **变** | 不变（若切点未受影响） | **变** |
| 改切分（同 profile 重切） | 不变 | **变** | **变** |
| 换 track（sd → h3） | **不变** | **变**（不同 adaptation） | **变** |
| 换 profile（sd25 → sd20） | **不变** | **变** | **变** |
| 升编译器版本 | 不变 | 不变 | **变** |
| 改 `seam` | 不变 | **变** | **变** |

**同源验证示例**（P0-01 强制要求）：

```
分镜 F1，8 镜，总长 38.0s

Seedance 适配：
  adaptation ad_sd_1 (track=seedance, profile=seedance25.v1, ver=1)
  units: 29.5 / 8.5                     → adaptationHash = sha256:7c1e…
  compile(compilerVer=1.0.0, format=ref2va)
  → sourceSpecHash  = sha256:3f9a…   ← 同一个
  → compiledHash    = sha256:b84d…

H3 适配：
  adaptation ad_h3_1 (track=h3, profile=h3.v1, ver=1)
  units: 14.5 / 13.0 / 10.5             → adaptationHash = sha256:e0a2…
  compile(compilerVer=1.0.0, format=ref2va)
  → sourceSpecHash  = sha256:3f9a…   ← **逐字相同，这就是同源证明**
  → compiledHash    = sha256:1d77…

断言：
  sd.sourceSpecHash === h3.sourceSpecHash        ✓ 同源
  sd.adaptationHash !== h3.adaptationHash        ✓ 适配不同
  sd.compiledHash   !== h3.compiledHash          ✓ 产物不同
```

### 4.5 规范化序列化（三者共用）

| 规则 | 实现 | 原因 |
|---|---|---|
| 键排序 | 所有对象键按 UTF-16 字典序输出 | DB 返回键序不稳定 |
| 整数 | 去小数（`4.0` → `4`） | `4` 与 `4.0` 必须同 hash |
| 浮点 | 保留 6 位并去尾零（`4.500000` → `4.5`，`0.30000000000004` → `0.3`） | 浮点误差不得影响 hash |
| `null` / `undefined` | 统一 `null`，**保留键** | 省略与 null 语义不同 |
| 空集合 | `[]` / `{}` 保留 | 同上 |
| 字符串 | NFC 归一化 + 去首尾空白 + **不去内部空白** | 内部空格是语义（台词停顿） |
| 有序数组 | `time_slices`、`cam_path`、`position_track` 保原序 | 顺序即语义 |
| 无序数组 | `blockings`（按 char）、`actions`（**五项全序** tFrom→actor→tTo→type→contentHash）、`assets`（按 role+id）、`scenes`（按 scene_key） | 插入顺序不应影响 |
| 派生字段 | `voice_ids` **不进 hash**（由 `shot_assets(role=voice)` 派生，见 §4.2） | 两个权威会让变化漏检 |
| 缺失字段 | 视为 `null`（不视为"不存在"） | 加字段不改变旧数据 hash |

`canonState` / `canonMeta`：按 `chars.<id>.<field>` 的字典序展开成一维键值对，保证嵌套对象的键序无关。

| R-21 | **`profile_ver` sd25 → sd20** | source **不变**；adaptation 变 | P0-01 核心 |
| R-22 | **同 profile 重切（片段 t_to 变）** | source **不变**；adaptation 变 | P0-01 核心 |
| R-23 | 改 `seam` 策略 | source **不变**；adaptation 变 | 归属判定 |
| R-24 | 只升 `compilerVer` | source、adaptation 均不变；compiled 变 | 分层 |
| R-25 | 双编译器（同分镜、不同 track） | **source 逐字相同**；adaptation 与 compiled 均不同 | **同源证明（CI 断言）** |
| **R-26** | **仅打乱动作的数据库返回顺序**（正序 / 逆序 / 随机） | source **不变** | **P1-06 核心**：五项全序 |
| **R-27** | 复制一个动作、只换新 `id`（内容全等） | source **不变** | `action.id` 不进 hash |
| **R-28** | 换音色资产（`shot_assets(role=voice)` 的 `asset_id` 变） | source **变** | **P1-05 核心**：音色走资产 |
| **R-29** | 同一音色资产换版本（`fp` 变，`asset_id` 不变） | source **变** | 内容指纹参与 |
| **R-30** | 把某人的 `blockings.rel` 从 known 改成 unknown（值不变） | source **变** | 可靠性是语义 |
| **R-31** | **无引用动作换 `id`**（谁都不引用它） | source **不变** | **P1-02 核心**：`_ref`/`_par` 不进 contentHash |
| **R-32** | **被 `trigger.ref` 引用的动作换 `id`，并同步更新引用** | source **不变** | **P1-02 核心**：引用映射到 contentHash 而非 id |
| **R-33** | **被 `parallel_with` 引用的动作换 `id`，并同步更新引用** | source **不变** | **P1-02 核心** |
| **R-34** | 只改引用目标的**实际动作内容**（如把"抬手"改成"转身"） | source **变** | 内容变必须反映 |
| **R-35** | 打乱动作输入顺序（含引用关系不变） | source **不变** | 与 R-26 共同覆盖 |
| **R-36** | 动作 `t_from` 恰好等于切点 / `t_to` 恰好等于镜尾（算例 F） | 切分结果确定；动作只归属一个片段 | **P0-01 边界** |
| **R-37** | 动作 A 的 `t_to` 与动作 B 的 `t_from` 重合，切在该点 | 两者分属左右片段，**各播一次** | 半开区间归属 |
| **R-38** | `norm_xyz`：(x,y,z 全有) / (x,y 有 z 缺) / (全缺) / (z 明确 = 0) | 前三种中仅第一种可 `known`；`z=0` 与 `z 缺` 的 source 不同 | **P1-04 核心** |
| **R-40** | 交换同一镜两条 voice 资产的 `order_no`（1↔2） | source **变** | **P1-03 核心**：`order_no` 进 payload，`Audio 1/2` 对调必须反映 |
| **R-41** | 同一 `(shot, role)` 两条资产写同一个 `order_no` | 应在写入时被 `UNIQUE` 拒绝，**不入 hash** | 顺序冲突在库层拦截，不是 hash 的责任 |

**实施要求**：
- R-01 ~ R-30、R-32 ~ R-38、R-40 为纯函数单测，输入用固定 fixture（不依赖数据库）；
- R-41 是数据库约束测试，需真实建表（属 D 类，见 `D01-07 §三`）；
- **R-25 必须做成 CI 断言**：`compileSeedance(...).sourceSpecHash === compileH3(...).sourceSpecHash`，不等即构建失败；
- **R-39（负向，代码评审项）**：把 `fragments`、`track`、或任何 `_` 开头的临时键混入 source payload / contentHash 的实现必须被拒绝——这在 V2 是设计，在 V3/V4 是反例。
- **R-31 ~ R-35 是一组**：单测必须用"同一 fixture、只改 id 命名"的方式跑，而不是手写两个不同的期望值——否则测不出污染。

### 4.7 `sourceSpecHash` 的作用域

一个 hash 对应**一章的全部分镜**（按 `global_no` 排序）。跨章的镜不参与同一 hash。

若只修改了第 30 镜，第 1–29 镜的 `state_out` 会被增量复用，但 **hash 必须整体重算**（因为 payload 包含全体 shots）。重算是毫秒级，不做"分块 hash 拼接"——分块拼接会让"插入一镜"无法被检测到。

## 十、接口稳定性

| 变更 | 破坏性 | 处理 |
|---|---|---|
| 加可选字段 | 否 | 直接加，`spec_version` 不变 |
| 加必填字段 | 是 | `spec_version` +1，旧数据按 S 级降级 |
| 加枚举值 | 否（读者）/ 是（switch） | 编译器与 QC 必须"未知值 → WARN 不崩" |
| 删枚举值 | 是 | 禁止，只标 deprecated |
| 表结构变更 | 视情况 | 只加列/加表 |
| 编译器逻辑变更 | 是 | `compiler_ver` +1（只影响 `compiledHash`） |
| **切分算法变更** | 是 | 新 `adaptation_version`，旧方案保留（不影响 `sourceSpecHash`） |
| **hash payload 变更** | 是 | `specVersion` +1；旧产物的 hash 无法复算，必须保留原值不重算 |

**`spec_version` 管数据形状，`compiler_ver` 管编译逻辑，`adaptation_version` 管切分方案**——三者必须分开，否则无法判断"产物不同是数据变了、切法变了，还是程序变了"。

## 十一、本轮的明确不做

| 项 | 原因 |
|---|---|
| 实现 Compiler | 任务书禁止；且 hash 契约需先评审 |
| 实现连续性引擎 | 同上 |
| 全局最优切分（bin-packing） | 收益低于多一次切镜的接缝代价，且会引入跨镜重排，违反"镜序不变" |
| 分块 hash 拼接 | 无法检测镜的插入/删除 |
| 自动补 `cam_pos` | 从文本方位推坐标 = 伪造确定状态（`D01-04 §6.4`） |
| 把 unknown 当合法 | 会让"没数据"变成"全绿" |
