## 三、适配层：切分与片段完整性

### 3.1 职责与产物

按 TargetProfile 把 Shot 序列切成单元，产出**一个可版本化的适配方案**（`render_adaptations`）及其单元与片段。

**不属于任何编译器**——否则两编译器会切出不同单元，导演分镜就没有唯一适配记录了。

### 3.2 适配方案（P0-02 新增）

一个 `adaptation` = 一次完整的切分结果，身份是四元组：

```
(project_id, chapter_id, track, profile_ver, adaptation_version)
```

| 触发新版本的场景 | 处理 |
|---|---|
| 第一次给某章某轨道做适配 | `adaptation_version = 1`，`status='active'` |
| 同一 `track` 换 `profile_ver`（SD2.5 → SD2.0） | 新 adaptation，`version = 1`（profile 不同，是另一条序列） |
| 同一 `track` 同一 `profile` 重新切分（改了 `seamPolicy`、改了最短单元） | `adaptation_version +1`；旧方案 `status='superseded'`、`superseded_by=<新id>`，**行不删** |
| 分镜被修改后重切 | 同样 +1 版本；旧方案保留，并在 `source_spec_hash` 上留痕，便于回答"这版切分是对哪版分镜做的" |

**关键**：旧方案保留，意味着同一个 Shot 在同一 `track/profile` 下会同时存在**多套片段划分**。因此：

> **片段完整性校验的作用域是「单个 adaptation」，不是「单个 shot」。**
> 跨 adaptation 的片段重叠是**合法的**（它们是不同版本的方案），不能拿来判 `FRAG_OVERLAP`。

V2 的唯一索引 `uq_ru_no (project_id, track, unit_no)` 无法容纳多版本（新版本会产生相同 `unit_no` → 唯一冲突），V3 改为 `(adaptation_id, unit_no)`。详见 `D01-05 §4.8`。

`Profile` 四个数值的含义与来源（全部快照进 `render_adaptations`，见 `D01-05 §4.14`）：

| 字段 | 含义 | 取值来源 | 例（h3.v1） | 缺失时 |
|---|---|---|---|---|
| `max` | 单次生成时长上限 | TargetProfile（模型能力） | 15 | 不可为空 |
| `shortFloor` | 单元最短可接受时长 | TargetProfile（太短则画面无信息） | 5 | 不可为空 |

| `tailHoldMax` | 单元尾镜允许的定格延长上限 | TargetProfile（`tail_hold_max`） | 1.0 | 报 `ADAPT_PROFILE_SNAPSHOT_MISSING`，**不猜** |

**切点：时间量子 + 跨越检查（V6 重写，P0-01）**

V5 的 `crosses()` 用 `±EPS` 容差，而归属规则 `a.t_to <= t` / `a.t_from >= t` **没有任何容差**。两者的缝隙就是"动作凭空消失"的地方：

```
动作 A(0, 5.0004)，切点 t = 5.000（另一个动作恰好在这里起）
  crosses:  0+ε < 5.000 && 5.000 < 5.0004-ε = 4.9994  →  后半为假  → 不算跨越（判为合法切点）
  归属左:   5.0004 <= 5.000                            →  假
  归属右:   0 >= 5.000                                 →  假
  →  A 既不属于左片段，也不属于右片段：**整条动作在成片里消失，且不报任何错**
```

**V6 的解法：先把时间量化，再用严格比较。容差只在"吸附"这一处，且必须分名。**

##### 3.3.1.1 容差分类（V7 · P1-03：五个用途，两个名字，三处不用）

V6 说"全篇唯一的容差是 `TOL`，且只用于吸附"，但 `§3.3.2` 里 `TOL` 实际出现在 **11 个位置**（完整清单见 `D01-13 §5.1`）：循环条件、容量、最小片段、尾单元合并、尾单元警告、候选过滤、镜边界、切点窗口、单元超限、片段首尾与重叠、片段越界。**声明与用法不一致，比没有声明更坏**——实施者照"只用于吸附"去理解，读到容量比较处会怀疑自己记错了文档。

V7 按**用途**分五行，其中只有两行需要容差：

| 用途 | 用什么 | 值 | 单位 | 说明 |
|---|---|---|---|---|
| ① 时间量化精度 | `TQ` | `0.001` | 秒 | 网格步长。**它不是容差**，是把连续时间映射到离散网格的步长（H3 时间码 `00:SS.mmm` 只有毫秒精度） |
| ② 切点吸附容差 | `SNAP_TOL` | `TQ/2 = 0.0005` | 秒 | **只有 `snap()`**。外部请求切点可能不是网格点，允许落在某边界半个刻度内即视为该边界；超出即 `null`（拒绝，**不四舍五入到最近的动作**） |
| ③ 单元容量比较 | **无容差，严格** | — | — | `remain <= room`、`room < minSlice`、`consumed < D`。两侧都是网格值，容差恒等价 → 删掉 |
| ④ 片段完整性校验 | **无容差，严格**（入口先 `q()` 归一） | — | — | 缺口与重叠是**状态**不是"接近"：要么齐平（`d === 0`），要么差一个网格 |
| ⑤ 尾镜留白容差 | `PAD_TOL` | `0.01` | 秒 | **只有 `UNIT_PADDING_EXCESS`**。`tailHoldMax` 是配置值（如 `1.0`），不是网格值；10 ms 是书写余量，避免 `1.0000001 > 1.0` 误报 |

**五行的判定规则**：**只要比较的两侧都是网格值（③④），就不该有容差；只要一侧不是网格值（②⑤），就必须有容差，且必须说清"它不是网格值"。** 这条规则比"记住哪几个地方用容差"更可靠——它把判断依据放在**量的来源**上，而不是放在**函数名**上。

**为什么只要两侧是网格值，容差就恒等价**：任意两个**不同**网格值的间距 ≥ `TQ = 1 ms = 2 × SNAP_TOL`，所以 `a <= b + SNAP_TOL ⟺ a <= b`。容差在这里不改变任何结论，只是让读者以为"这里有个容差在起作用"。

**冗余不等于无害：两个实际代价**

1. **声明的可信度**：V6 写"全篇唯一容差只用于吸附"，代码里却有 11 处用它。实施者读到哪一句都会觉得自己理解对了，实际两处矛盾；
2. **输入一旦不是网格值就真出错**：`verifyAdaptation` 直接读库，历史数据可能有 `unitDuration = 15.0004`。带容差时 `15.0004 > 15 + 0.0005` 为假 → **判为不超限** → 落库 → 出片被模型截断，而 QC 全绿。严格比较则会报 `UNIT_OVERFLOW`。

所以修法是**两件事一起做**：删掉冗余名（`TOL` 这个通用名不再存在），并且 `verifyAdaptation` 读到的所有时间值**先 `q()` 归一，再严格比较**。归一之后，`15.0004` 变成 `15.000`，既不误报也不漏报——这才是 `TQ` 作为"时间码精度"的正确用法：**入口处归一，之后不再有"接近"这种状态**。

```js
const TQ       = 0.001;      // 时间量子（网格步长，不是容差）
const SNAP_TOL = TQ / 2;     // 吸附容差，仅 snap() 使用
const PAD_TOL  = 0.01;       // 单元留白容差，仅 UNIT_PADDING_EXCESS 使用
const q = (x) => Math.round(x * 1000) / 1000;   // 量化到 1 ms 网格
```

`q()` 是**幂等**的：`q(q(x)) === q(x)`。因此纯函数（`candidateCuts` / `crosses` / `isLegalCut`）内部可以重复量化而不改变结果；但 `planAdaptation` 的主循环里**只用已量化值**，唯一的 `q()` 出现在"入口量化"和"网格加法"（`q(cur.dur + len)`）两处。

##### 3.3.1.2 执行顺序（固定五步，不得调换）

| 步 | 做什么 | 失败返回 |
|---|---|---|
| ① **入口量化** | 每镜 `story_duration`、每动作 `t_from`/`t_to` 全部 `q()` 一次 | — |
| ② **量化留痕** | 原始值 ≠ 网格值 → `ACTION_EDGE_SNAPPED`（INFO），进 `warnings` | 不失败 |
| ③ **退化 / 越界** | `q(t_to) - q(t_from) < TQ` → 退化；`q(t_from) < 0` 或 `q(t_to) > D` → 越界 | `ADAPT_DEGENERATE_ACTION` / `ADAPT_ACTION_OUT_OF_RANGE` |
| ④ **候选 + 跨越** | 候选 = 边界 ∪ 全部量化后的 `t_from`/`t_to`；跨越判定用严格比较 | — |
| ⑤ **归属 + 后置校验** | 切点处逐动作数左右归属，必须恰为 1 | `ADAPT_ACTION_LOST` / `ADAPT_ACTION_DUPLICATED` |

**为什么必须"入口量化"而不是"每次比较前量化"**：后者会让同一个量在不同比较点算出不同结果（漏一次 `q()` 就回到 V5 的缝隙）。入口量化之后，主循环里出现的每个时间值都已经是网格值，"有没有漏"变成可检查的事：`§3.3.2` 代码里 `q(` 只应出现在入口段、`q(cur.dur + len)` 与 `q(max - cur.dur)` 三处。

##### 3.3.1.3 候选、吸附、跨越

```
candidateCuts(shot) = { 0, D } ∪ { q(a.t_from) } ∪ { q(a.t_to) }      // D 已量化

snap(t) = 唯一 b ∈ candidateCuts(shot) 使 |t - b| <= SNAP_TOL
        = null   （不在任何边界半个刻度内 → 不是切点，拒绝，不四舍五入到最近的动作）

crosses(a, t)  ⟺  q(a.t_from) < t && t < q(a.t_to)                   // 严格比较，零容差

legalCuts(shot) = { b ∈ candidateCuts | ¬∃ a : crosses(a, b) }
```

**跨越判定为什么能不带容差**：两侧都已量化，`t` 也是网格点。把三个数同乘 1000 后就是整数比较，`q(t_from) < t < q(t_to)` 在整数上没有"接近"这回事。V5 的 `±EPS` 是"把边界往里缩一个极小量"，缩完之后 `t` 落在 `(t_to - EPS, t_to)` 里既不算跨越、也不归左——**缝隙就在这里**。

##### 3.3.1.4 证明：每个动作恰归一个片段

`q(t_to) > q(t_from)`（③ 已保证）时，对任意网格点 `t` 只有三种情形，互斥且穷尽：

| 情形 | 左 `q(a.t_to) <= t` | 右 `q(a.t_from) >= t` | 是否合法切点 |
|---|---|---|---|
| `t <= q(a.t_from)` | 假（因 `q(t_from) < q(t_to)` 且 `t <= q(t_from)`） | **真** | 合法，动作全在右 |
| `q(a.t_from) < t < q(a.t_to)` | 假 | 假 | **非法**（`crosses` 为真，被 ④ 排除） |
| `t >= q(a.t_to)` | **真** | 假（因 `t >= q(t_to) > q(t_from)`） | 合法，动作全在左 |

第三、四列合起来：**候选切点必然落在第 1 行或第 3 行，而这两行里"左/右"恰有一个为真。** 这不是"实现应该这样"，是由 `q(t_to) > q(t_from)` 直接推出的。

##### 3.3.1.5 退化动作必须拒绝

若 `q(t_to) - q(t_from) < TQ`（动作短于 1 ms），则 `q(t_from) === q(t_to)`，上表第 1 行与第 3 行**同时成立**，动作被左右各算一次——成片里播两遍，且不报错。

```
q(a.t_to) - q(a.t_from) < TQ          →  ADAPT_DEGENERATE_ACTION（拒绝适配，不猜怎么处理）
q(a.t_from) < 0 || q(a.t_to) > D      →  ADAPT_ACTION_OUT_OF_RANGE（拒绝）
```

越界判定用**量化后**的值：`t_from = -0.0004` 量化成 `0`，算合法（并留痕 `ACTION_EDGE_SNAPPED`，偏移 0.4 ms）；`t_from = -0.0006` 量化成 `-0.001`，拒绝。

##### 3.3.1.6 亚毫秒偏移必须留痕（`ACTION_EDGE_SNAPPED`，V7 · P1-04 真正落地）

量化会把 `2.9996` 变成 `3.000`，语义上是"动作起点后移了 0.4 ms"。在 1 ms 时间码下不可见，但**必须留痕**：否则"设计者写 2.9996、程序按 3.000 算"这件事没有任何人知道，等出片后发现动作起手差了半帧，也无从追溯。

```
对每个动作 a（在 ① 之后、③ 之前）：
  qFrom = q(a.t_from)
  qTo   = q(a.t_to)
  若 qFrom !== a.t_from  或  qTo !== a.t_to
    → warnings.push({
        code: 'ACTION_EDGE_SNAPPED', level: 'INFO',
        shotId: s.id, actionId: a.id,
        rawFrom: a.t_from, rawTo: a.t_to,     // 原始值（设计者写的）
        qFrom, qTo,                            // 量化值（程序算的）
        dFrom: a.t_from - qFrom,               // 偏移量，**不再 q()**
        dTo:   a.t_to   - qTo
      })
```

四条硬要求：

1. **只在真偏移时产生**：`q(3.0) === 3.0`，精确命中网格**不产生**（精确命中是常态，不该刷屏）；
2. **偏移量用原始浮点差，不得再量化**：`q(0.0004) === 0`，量化就把要记录的那件事抹掉了。展示时可 `toFixed(4)`，但计算值保留原始差；
3. **`level` 恒为 `INFO`**：不参与 `ok` 判定、不阻断切分。它是"设计精度不足"的提示，不是错误。写成 `WARN` 会让每一镜都亮黄灯，最后没人看；
4. **`warnings` 在入口阶段创建、全程累积、随结果返回**。V6 只在文字里写"记 INFO"，`planAdaptation` 里既没有这个数组、也没有 `push`——规则没接入执行，等于不存在（这就是本轮 P1-04 要修的东西）。

**成功与失败都要带 `warnings`**：`ADAPT_NO_LEGAL_CUT` 时，正是最需要知道"哪些动作边界被量化挪过"的时候——切不出来往往就是因为某个边界被挪了 0.4 ms 导致候选点消失。

##### 3.3.1.7 归属（对已吸附的切点 `t`，全部用网格值）

```
a 属于左片段  ⟺  q(a.t_to)   <= t
a 属于右片段  ⟺  q(a.t_from) >= t
```

两式都用 `<=` / `>=`，**不能写成 `<` / `>`**，否则 `t` 恰好等于边界时两侧都不成立。

##### 3.3.1.8 后置校验 `assertAttribution`（V7 · P1-02 真正接入调用链）

```
for each a in shot.actions:
    n = (q(a.t_to) <= t ? 1 : 0) + (q(a.t_from) >= t ? 1 : 0)
    n != 1  →  ADAPT_ACTION_LOST (n==0) / ADAPT_ACTION_DUPLICATED (n==2)
```

它不是"再检查一遍"，而是**唯一的兜底**：只要实现写错比较符、或有人绕过 `q()` 直接用原始浮点，这条校验就会把"动作丢失/重复"变成硬错误，而不是让它悄悄进成片。

**调用位置（V6 只定义、从未调用，等于没有）**

| 位置 | 是否调用 | 理由 |
|---|---|---|
| `planAdaptation` 的**镜内切分**点（`put(s, consumed, cut)` 之前） | **必须** | 这里是唯一可能把同一镜的动作分到两个片段的地方 |
| 镜与镜之间的边界 | **不调用** | 不存在"同一镜动作被分到两段"；且上镜动作全在左、下镜动作全在右，判出来的 `n` 恒为 1，是平凡结果，白跑一遍 |
| `verifyAdaptation` | **不调用本函数**，改用独立的"片段包含"判定 | 见 `§3.4` 的两层职责表：plan 侧防"算错"，verify 侧防"绕过" |

失败时**不得继续生成、不得落库当前 adaptation**：返回 `{ ok:false, code, warnings }`，调用方不得把 `units` 写进 `render_units` / `render_unit_shots`。

**片段内时间重基（V3 遗漏，必须补）**

片段 `[f.t_from, f.t_to]` 进入单元后从 0 开始计时，因此片段内所有动作的时间必须相对化：

```
t_local = t_abs - f.t_from
```

| 用途 | 用哪个 |
|---|---|
| `render_unit_shots.t_from / t_to`（存储） | **`t_abs`** |
| 编译器时间轴、投喂提示词的 `At 00:SS.mmm` | **`t_local`** |
| QC 的动作区间校验 | `t_abs`（相对于 `story_duration`） |

两者混用会让第二片段的动作时间整体偏移——例如从 3.0s 处切开的片段，动作时间会被误报成 3.0 而非 0，提示词里就会出现"镜长 4 秒但动作从 3 秒开始"的荒谬描述。

**无合法切点时的行为**

- 若某镜 `story_duration > max`，且 `legalCuts(shot)` 内部只有 `{0, D}`（无任何安全切点）→ 返回 `ADAPT_NO_LEGAL_CUT`；
- **不得**为了满足 `max` 而硬切正在执行的动作；
- 三条处置由人决定（不自动选）：① 在动作设计上补一个自然收势 → ② 拆镜 → ③ 换 profile。

#### 3.3.2 算法

```js
const TQ       = 0.001;      // 时间量子（网格步长）
const SNAP_TOL = TQ / 2;     // 吸附容差，仅 snap()
const PAD_TOL  = 0.01;       // 单元留白容差，仅 verify 的 UNIT_PADDING_EXCESS
const q = (x) => Math.round(x * 1000) / 1000;

function planAdaptation({ shots, profile, seamPolicy }) {
  const { max, shortFloor, minSlice } = profile;
  const warnings = [];                       // ② 全程累积，成功与失败都返回（P1-04）
  const units = [];
  let cur = null;

  // ① 入口量化 + ② 留痕 + ③ 退化/越界：一次做完，之后全程网格值
  const prepared = [];
  for (const s of shots) {
    const D    = q(s.story_duration);
    const acts = [];
    for (const a of s.actions || []) {
      const f = q(a.t_from), t = q(a.t_to);

      if (f !== a.t_from || t !== a.t_to)     // ② 只在真偏移时产生 INFO
        warnings.push({ code: 'ACTION_EDGE_SNAPPED', level: 'INFO',
                        shotId: s.id, actionId: a.id,
                        rawFrom: a.t_from, rawTo: a.t_to, qFrom: f, qTo: t,
                        dFrom: a.t_from - f, dTo: a.t_to - t });

      if (t - f < TQ)                          // ③ 退化：量化后时长不足 1 ms
        return { ok: false, code: 'ADAPT_DEGENERATE_ACTION', shotId: s.id, warnings,
                 detail: { actionId: a.id, tFrom: a.t_from, tTo: a.t_to, quantum: TQ } };
      if (f < 0 || t > D)                      // ③ 越界（量化后判）
        return { ok: false, code: 'ADAPT_ACTION_OUT_OF_RANGE', shotId: s.id, warnings,
                 detail: { actionId: a.id, tFrom: a.t_from, tTo: a.t_to, storyDuration: D } };

      acts.push({ ...a, t_from: f, t_to: t });  // 之后只用这一份
    }
    prepared.push({ ...s, D, actions: acts });
  }

  const open  = () => { cur = { unitNo: units.length + 1, items: [], dur: 0 }; units.push(cur); };
  const close = () => { cur = null; };
  const put   = (s, a, b) => {
    cur.items.push({ shotId: s.id, tFrom: a, tTo: b,
                     splitReason: (a > 0 || b < s.D) ? 'oversize' : '' });
    cur.dur = q(cur.dur + (b - a));        // 网格加法：每步重新量化，误差不累积
  };

  for (const s of prepared) {
    const D = s.D;
    let consumed = 0;

    while (consumed < D) {                   // 严格：两者都是网格值
      if (!cur) open();
      const remain = D - consumed;           // 网格差（网格 − 网格 ∈ 网格）
      const room   = q(max - cur.dur);       // max 是配置值，减完量化一次

      // 装得下 → 并入当前单元。含"尾巴 < minSlice"的情形：另一条路（另开单元）
      // 同样会产出 < minSlice 的片段，还多一次接缝，所以尾巴优先并入
      if (remain <= room) { put(s, consumed, D); consumed = D; break; }

      // 剩余空间不足一个最小片段 → 关单元，下轮在新单元里放
      if (room < minSlice) { close(); continue; }

      // 在 [consumed+minSlice, consumed+room] 内找最大的合法切点
      const cut = pickLegalCut(s, q(consumed + minSlice), q(consumed + room));

      if (cut === null) {
        if (cur.items.length === 0)          // 空单元都放不下 → 真切不出来
          return { ok: false, code: 'ADAPT_NO_LEGAL_CUT', shotId: s.id, warnings,
                   detail: { storyDuration: D, max, minSlice,
                             candidates: explainNoCut(s, q(consumed + minSlice), q(consumed + room)) } };
        close(); continue;                   // 换个更大的空单元再试
      }

      // ⑤ 镜内切分：先校归属，再落片段（P1-02：这是唯一必须调用的位置）
      const att = assertAttribution(s, cut);
      if (!att.ok)
        return { ok: false, code: att.code, shotId: s.id, warnings,
                 detail: { at: cut, bad: att.detail } };

      put(s, consumed, cut);
      consumed = cut;
      close();                               // 切完即接近满，关单元；剩余进下一个
    }
  }

  // 尾单元合并（严格：dur 都在网格上）
  if (units.length >= 2) {
    const last = units[units.length - 1], prev = units[units.length - 2];
    if (last.dur < shortFloor && q(prev.dur + last.dur) <= max) {
      prev.items.push(...last.items);
      prev.dur = q(prev.dur + last.dur);
      units.pop();
    }
  }

  const tail = units[units.length - 1];
  if (tail && tail.dur < shortFloor)
    warnings.push({ code: 'SHORT_UNIT', level: 'WARN', unitNo: tail.unitNo, dur: tail.dur,
                    msg: `尾单元 ${tail.dur}s 低于最短 ${shortFloor}s，且无法并入前一单元`,
                    suggest: '缩短上一镜或延长尾镜，或接受该单元（出片后可能信息量不足）' });

  units.forEach((u, i) => { u.unitNo = i + 1; });   // 尾合并后可能缺号
  return { ok: true, units, warnings };
}

/** 候选切点：镜边界 + 全部动作起点/终点，已全部落在网格上 */
function candidateCuts(s) {
  const D   = s.D ?? q(s.story_duration);
  const set = new Set([0, D]);
  for (const a of s.actions || []) { set.add(q(a.t_from)); set.add(q(a.t_to)); }
  return [...set].filter(c => c >= 0 && c <= D).sort((x, y) => x - y);
}

/** 吸附：把外部请求切点对齐到边界；不在半个刻度内 → null（拒绝，不就近取整） */
function snap(s, t) {
  let hit = null;
  for (const b of candidateCuts(s)) {
    if (Math.abs(t - b) <= SNAP_TOL) { if (hit !== null && b !== hit) return null; hit = b; }
  }
  return hit;
}

/** 该切点是否会把任何动作劈成两半（严格比较——容差已在 q() 里用掉） */
function crossingActions(s, t) {
  return (s.actions || []).filter(a => q(a.t_from) < t && t < q(a.t_to));
}

function isLegalCut(s, t) {
  const D = s.D ?? q(s.story_duration);
  if (t <= 0 || t >= D) return true;         // 镜边界恒合法
  return crossingActions(s, t).length === 0;
}

function legalCuts(s) {
  return candidateCuts(s).filter(t => isLegalCut(s, t));
}

function pickLegalCut(s, lo, hi) {
  const D     = s.D ?? q(s.story_duration);
  const cands = legalCuts(s).filter(t => t >= lo && t <= hi && t > 0 && t < D);
  return cands.length ? cands[cands.length - 1] : null;   // 取最大 → 尽量装满
}

/** 失败时给出"为什么没有切点"，供人而不是程序做决定 */
function explainNoCut(s, lo, hi) {
  const D = s.D ?? q(s.story_duration);
  return candidateCuts(s)
    .filter(t => t > 0 && t < D)
    .map(t => ({ at: t, inWindow: t >= lo && t <= hi,
                 blockedBy: crossingActions(s, t)
                   .map(a => ({ id: a.id, from: q(a.t_from), to: q(a.t_to) })) }))
    .filter(x => x.blockedBy.length || x.inWindow);
}

/** 后置校验：每个动作必须恰好归属一个片段（P1-02：必须被 planAdaptation 调用） */
function assertAttribution(s, t) {
  const bad = [];
  for (const a of s.actions || []) {
    const n = (q(a.t_to) <= t ? 1 : 0) + (q(a.t_from) >= t ? 1 : 0);
    if (n !== 1) bad.push({ actionId: a.id, assigns: n,
                            code: n === 0 ? 'ADAPT_ACTION_LOST' : 'ADAPT_ACTION_DUPLICATED' });
  }
  return bad.length ? { ok: false, code: bad[0].code, detail: bad } : { ok: true };
}
```

**六个比较位置的业务语义（V7 · P1-03，逐项说明为什么这样比）**

| 位置 | 原（V6） | 现（V7） | 语义 | 为什么不能带容差 |
|---|---|---|---|---|
| `while (consumed < D - TOL)` | 带 `TOL` | `consumed < D` | "本镜还有没分配的时间吗" | 两者都是网格值。`consumed = D` 时循环必须停；带容差会让 `consumed = D - 0.0004` 也停（但它不可能是网格值，所以这里的容差只会掩盖"有人没量化"） |
| `remain <= room + TOL` | 带 `TOL` | `remain <= room` | "剩余装得下吗" | 这是**能不能塞**的判定。容差方向是"放宽"，会让装不下的剩余被塞进去 → `cur.dur > max` |
| `room < minSlice - TOL` | 带 `TOL` | `room < minSlice` | "空间不够一个最小片段吗" | 容差方向是"缩小 minSlice"，会切出短于 `minSlice` 的片段。`minSlice` 的物理含义是"再短模型接不住"，这个界限不该被 0.5 ms 松动 |
| `last.dur < shortFloor - TOL` | 带 `TOL` | `last.dur < shortFloor` | "尾单元是否过短" | 只影响 WARN 与合并判断，但同样应两值同网格。带容差会让 `shortFloor = 5, dur = 4.9996` 判为"不过短" |
| `u.unitDuration > u.profileMax + TOL` | 带 `TOL` | `q(unitDuration) > q(profileMax)` | "单元超限了吗" | **这是唯一会漏判 FAIL 的位置**：`15.0004 > 15.0005` 为假 → 超限单元落库 → 出片被截断而 QC 全绿（下方算例 H-4） |
| `d = frags[i].tFrom - frags[i-1].tTo` 的 `±TOL` | 带 `TOL` | `q(...)` 后 `d > 0` / `d < 0` | "有缺口 / 有重叠" | 缺口与重叠是**状态**，不是"接近"：要么齐平（`d === 0`），要么有一个网格的差。带容差会把 0.4 ms 的重叠报成"齐平" |

**唯一保留 `SNAP_TOL` 的地方是 `snap()`**，因为它的输入是外部请求（可能来自用户拖拽、可能来自上游浮点计算），本来就不在网格上；**唯一保留 `PAD_TOL` 的地方是 `UNIT_PADDING_EXCESS`**，因为 `tailHoldMax` 是配置值（`1.0`），与网格无关。

#### 3.3.2.1 容差改动的四个边界算例（V7 · P1-03 第 8 条）

统一设定：`h3.v1`（`max = 15`、`shortFloor = 5`、`minSlice = 2.0`），`TQ = 0.001`。

**H-1 不得产生单元超限**

`cur.dur = 13.000`，`D = 4.000`，`consumed = 0`。`remain = 4.000`、`room = q(15 - 13) = 2.000`。

```
remain(4.000) <= room(2.000)?  假  → 走切分
room(2.000) < minSlice(2.000)? 假  → 有空间
pickLegalCut(s, 2.000, 2.000) → 切点只能是 2.000（若合法）
put(0, 2.000) → cur.dur = q(13 + 2) = 15.000
```

`15.000 > 15` 为假 → **不超限**。

关键在 `pickLegalCut` 的过滤条件 `t <= hi`：`hi` 就是 `q(consumed + room)`，所以切出的片段长度 `cut - consumed <= room` **在构造上就成立**，`cur.dur` 不可能超过 `max`。V6 若把上界写成 `hi + TOL`，就能切出 `room + 0.5 ms` 的片段，`cur.dur = 15.0005 > 15`，把"不可能超限"变成"可能超限"——一个纯写法问题，却不报错（因为 `UNIT_OVERFLOW` 在 verify 里，而 verify 那时又带容差）。

**H-2 不得产生片段遗漏**

`D = 7.000`，动作 `A(1.000, 3.000)`、`B(4.000, 6.000)`，`consumed = 0`，`room = 3.000`（单元还空 3 s）。

```
candidates = {0, 7.000, 1.000, 3.000, 4.000, 6.000}
pickLegalCut(s, 0+2.000, 3.000) → 候选在 [2.000, 3.000] 内且合法的：
  3.000（A 的 t_to，无动作跨越）  → 取最大 3.000
put(0, 3.000) → consumed = 3.000
下一轮：remain = 4.000，新单元 room = 15.000 → remain <= room → put(3.000, 7.000)
```

两段 `[0,3]`、`[3,7]` 首尾相接，`d = 0`，无缺口。**若归属判定写成 `q(t_to) < t`（严格小于）**：3.000 处 A 判"不归左"、`q(t_from)=1.000 >= 3.000` 也假 → `n = 0` → `ADAPT_ACTION_LOST`，被后置校验拦住。

**H-3 不得产生片段重叠**

`D = 10.000`，`consumed = 4.000`，切点 `8.000`。

```
put(4.000, 8.000) → [4,8]
consumed = 8.000，下一轮 remain = 2.000
若 remain <= room → put(8.000, 10.000) → [8,10]
验证：d = q(8.000 - 8.000) = 0  → 不重叠
```

重叠只会由"切点用了上一段的起点而不是终点"造成（例如误写 `consumed = cut - len`）。`assertAttribution` 抓不到这种错（它只看单点归属），所以 `verifyAdaptation` 的 F-2 是**必需的互补检查**，不是重复。

**H-4 不得错误拒绝（历史数据归一）**

库里读出 `unitDuration = 15.0004`、`profileMax = 15.000`（写入侧未量化）。

```
V6：15.0004 > 15.000 + 0.0005 = 15.0005?  假 → 判不超限 → 超限单元落库 ✗
V7：q(15.0004) = 15.000 > q(15.000) = 15.000?  假 → 判不超限 ✓（归一后它确实是 15 s）
```

同一份数据两条路径结论相同，且都不误报。**归一不是"抹掉证据"**：`15.0004` 与 `15.000` 在 1 ms 时间码下是同一个时刻，真正的 0.4 ms 偏移应该在写入侧被 `ACTION_EDGE_SNAPPED` 记录，而不是让 QC 因为浮点尾数报一个没人能修的 `UNIT_OVERFLOW`。

**为什么取最大切点**：单元越满，单元数越少，出片次数越少（成本与漂移风险都更低）。取最小切点会切出大量短单元。

**为什么不用 bin-packing 求全局最优**：切点受动作约束，可行解空间是每镜若干离散偏移，贪心在"每镜切点独立"的前提下已经是局部最优；全局最优需要跨镜重新分配（把 sh_03 的尾巴挪到下一单元换取 sh_06 完整），但这会**增加一次切镜**，从而多一个接缝，代价高于收益。这是权衡，不是最优解，已在 `D01-10 §六` 记录。

#### 3.3.2.2 `assertAttribution` 的三个算例（V7 · P1-02 第 8 条）

统一设定：`D = 10.0`，`h3.v1`。`assertAttribution(s, t)` 只判**一个**切点 `t` 处的归属，逐动作数 `n`。

**I-1 正常归属（不报错）**

动作 `A(1.000, 3.000)`、`B(5.000, 7.000)`，切点 `t = 7.000`。

| 动作 | 左 `q(t_to) <= 7.000` | 右 `q(t_from) >= 7.000` | `n` | 结论 |
|---|---|---|---|---|
| A | `3.000 <= 7.000` 真 | `1.000 >= 7.000` 假 | 1 | ✓ 归左 |
| B | `7.000 <= 7.000` 真 | `5.000 >= 7.000` 假 | 1 | ✓ 归左（终点在切点上） |

返回 `{ ok: true }`，`put(0, 7.000)`。**这是唯一允许继续落片段的情形。**

**I-2 动作丢失 → `ADAPT_ACTION_LOST`**

动作 `C(3.000, 6.000)`，切点 `t = 5.000`（C 正在执行中）。

| 动作 | 左 `6.000 <= 5.000` | 右 `3.000 >= 5.000` | `n` | 结论 |
|---|---|---|---|---|
| C | 假 | 假 | **0** | ✗ `ADAPT_ACTION_LOST` |

返回 `{ ok: false, code: 'ADAPT_ACTION_LOST', detail: [{ actionId:'C', assigns:0 }] }`。

**这个切点正常路径下到不了这里**：`pickLegalCut` 只从 `legalCuts` 取点，而 `crosses(C, 5.000)` 为真会把 5.000 排除。所以 I-2 出现，等于"有人绕过了 `legalCuts`"——比如把 `pickLegalCut` 改成"在窗口内直接取 `consumed + room`"。**这正是后置校验存在的理由**：它不检查"算法有没有按设计走"，它检查"结果对不对"。

**I-3 动作重复 → `ADAPT_ACTION_DUPLICATED`**

动作 `G(4.000, 4.000)`（退化，量化后时长 0），切点 `t = 4.000`。

| 动作 | 左 `4.000 <= 4.000` | 右 `4.000 >= 4.000` | `n` | 结论 |
|---|---|---|---|---|
| G | **真** | **真** | **2** | ✗ `ADAPT_ACTION_DUPLICATED` |

这就是 **③ 必须先于 ⑤** 的原因：退化动作会让"左"和"右"同时成立，动作在左右两个片段各演一遍。`③` 在入口就把它拒掉（`ADAPT_DEGENERATE_ACTION`），`⑤` 只是第二道门。

**I-4 镜与镜之间的边界（不调用，且调用了也不会误判）**

镜 `sh_40` 的最后动作 `(8.000, 10.000)`，`D = 10.000`；下一个镜 `sh_41` 的第一个动作 `(0, 2.000)`。

`assertAttribution(sh_40, 10.000)` 只遍历 `sh_40.actions`：`10.000 <= 10.000` 真 → `n = 1` ✓。`sh_41` 的动作**不在 `sh_40.actions` 里**，不参与判定。

所以镜边界处调用也不会报错——但**仍然不调用**：那里不存在"同一镜动作被分到两段"的可能，跑了只会得到一行平凡结果，让后来的人以为"镜边界也需要校验"，进而把 `t` 传成 `D` 去做切分。**不调用本身就是一种说明：镜内切分才是需要防的地方。**

#### 3.3.6 算例 D：一个动作结束、另一个仍在执行 → 必须失败

这是 P0-01 的核心反例。**V3 的算法会在这里切错**。

**输入**

| 项 | 值 |
|---|---|
| 镜 | `sh_30`，`story_duration = 20.0` |
| profile | `h3.v1`（`max=15`、`shortFloor=5`、`minSlice=2.0`） |
| 动作 A1（哈罗德） | `0.0 – 10.0` 走向床边 |
| 动作 A2（罗克珊） | `2.0 – 16.0` 缓慢坐起并转头 |

**处理过程**

```
候选切点（V4，含 t_from）：{0, 2, 10, 16, 20}
可用窗口：consumed=0，room=15 → 需在 [2, 15] 内切

逐点检查跨越：
  t=2    A1 跨越（0 < 2 < 10）      → 非法
  t=10   A2 跨越（2 < 10 < 16）     → 非法
  t=16   超出窗口上限 15             → 不在考虑范围
  t=0,20 是镜边界，但都在窗口外       → 不可用

legalCuts 中落在 [2,15] 的 = ∅
```

**V3 会怎么做**：V3 的候选只有 `{a.t_to} = {10, 16}`，窗口内只有 **10**，于是切在 10 —— 此时 A2 已执行到 8 秒（从 2 秒起），硬切等于**把罗克珊"正在坐起"的动作从中间截断**，第二段只能从"半坐"继续，模型必然重演或跳变。

**预期输出**

```json
{
  "ok": false,
  "code": "ADAPT_NO_LEGAL_CUT",
  "shotId": "sh_30",
  "detail": {
    "storyDuration": 20.0, "max": 15, "minSlice": 2.0,
    "candidates": [
      { "at": 2,  "inWindow": true,  "blockedBy": [{ "id": "ac_A1", "from": 0, "to": 10 }] },
      { "at": 10, "inWindow": true,  "blockedBy": [{ "id": "ac_A2", "from": 2, "to": 16 }] }
    ]
  }
}
```

**触发的错误码**：`ADAPT_NO_LEGAL_CUT`（**不是** `FRAG_CUT_MID_ACTION`——后者是落库前的二次校验，前者是切分阶段就该拒绝）。

**数据库约束**：此镜不产生任何 `render_unit_shots` 行；`render_adaptations` 记一条 `status='failed'`，`status_reason='ADAPT_NO_LEGAL_CUT'`，`unit_count=0`。

**处置**（由人决定，不自动选）：A1 与 A2 交叠覆盖了整个 2–15 窗口，唯一的出路是 ① 让 A2 的坐起在 10 秒前有个自然停顿（改动作）→ ② 把这一镜拆成两镜 → ③ 换更长上限的 profile。

#### 3.3.7 算例 E：多人物动作重叠但仍可合法切分

| 单元 | 片段 | 时长 |
|---|---|---|

#### 3.3.8 算例 F：动作恰好从切点开始 / 恰好到切点结束（边界测试）

算例 E 的 15 是 A3 起点，但那只是"顺手取到"。本算例专门把切点压在边界上，验证三件事：**起点可切、终点可切、且动作不重复播放**。

**输入**

| 项 | 值 |
|---|---|
| 镜 | `sh_32`，`story_duration = 18.0` |
| profile | `h3.v1`（`max=15`、`shortFloor=5`、`minSlice=2.0`） |
| A1（哈罗德） | `0.0 – 12.0` 走到床尾站定 |
| A2（罗克珊） | `12.0 – 16.0` 接话同时抬眼（`t_from` 恰等于 A1 的 `t_to`） |
| A3（凯森） | `16.0 – 18.0` 合上病历夹（`t_to` 恰等于镜尾） |

**处理过程**

```
candidateCuts = {0, 12, 16, 18}
窗口 [2, 15]

  t=12  A1: crosses? 0+ε < 12 && 12 < 12-0 ?  → 12 < 12 为假 → 不跨越 ✓
        A2: crosses? 12+ε < 12 为假          → 不跨越 ✓
        A3: 不涉及                            → 不跨越 ✓
        → 合法（A1 终点 + A2 起点，同一点既是终点又是起点）
  t=16  超窗口上限 15                       → 不在候选范围

legalCuts ∩ [2,15] = {12}  → 取 12
```

**预期输出**

| 单元 | 片段 | 时长 | 片段内动作（`t_local`） |
|---|---|---|---|
| U1 | `sh_32 (0, 12.0)` | 12.0 | A1 `0.0–12.0` |
| U2 | `sh_32 (12.0, 18.0)` | 6.0 | A2 `0.0–4.0`、A3 `4.0–6.0` |

```
A1 完整落在 U1，t_local 0–12           ✓ 不在 U2 重播
A2 t_from = 12.0 = 切点 → 归属 U2      ✓ 只属于 U2（半开区间 [12,16)）
A3 t_to = 18.0 = 镜尾 → 归属 U2        ✓
Σfrag = 12.0 + 6.0 = 18.0 = story_duration ✓
U1 = 12.0 ≤ 15 ✓    U2 = 6.0 ≥ shortFloor 5 ✓   两片段均 ≥ minSlice 2.0 ✓
```

**归属唯一性验算**（这是本算例的重点）：

```
左片段判据：a.t_to <= t   → A1: 12.0 <= 12.0 真 → 属 U1
右片段判据：a.t_from >= t → A2: 12.0 >= 12.0 真 → 属 U2
若实现按 a.t_from <= t 判左、a.t_to >= t 判右，则 A1 同时满足两侧（12<=12 且 12>=0），
A1 会被播两遍。半开区间必须写成 t_to <= t（左）与 t_from >= t（右），不能写成 < / >。
```

**应触发**：无错误。
**不应触发**：`FRAG_CUT_MID_ACTION`（12.0 不是任何动作的内部点）、`FRAG_FRACTION_MISMATCH`（`t_local` 已重基）。

**数据库约束**：`sh_32` 在 `render_unit_shots` 2 行，`(0, 12.0)` 与 `(12.0, 18.0)`——**两行首尾相接不重叠**，`UNIQUE(unit_id, shot_id)` 各自成立。

**V4 会怎么做**：这条路 V4 也能走对（它的 `candidateCuts` 已含 `t_from`），但 V4 没有任何算例验证"`t_from` 与 `t_to` 重合于一点"的归属，实现者极可能在这里把 A1 播两遍。本算例把该点固定成回归项（`D01-06 §4.6 R-36`）。

#### 3.3.9 算例 G：时间量子边界（P0-01 的四个必测形态）

统一设定：`sh_33`，`D = 12.0`，`h3.v1`（max 15）——**本镜不超限，只测切点判定，不测切分结果**。`TQ = 0.001`、`SNAP_TOL = 0.0005`、`PAD_TOL = 0.01`。

**G-1 切点距动作起点不足一个刻度**

| 项 | 值 |
|---|---|
| A1 | `t_from = 3.0004`、`t_to = 8.0` |
| 请求切点 | `t = 3.000` |

```
q(A1.t_from) = 3.000 → 切点 3.000 命中边界
crosses: 3.000 < 3.000 为假 → 不跨越
归属：左 8.0 <= 3.000 假；右 3.000 >= 3.000 真 → **右片段** ✓
留痕：|3.0004 - 3.000| = 0.0004 > 0 → ACTION_EDGE_SNAPPED（INFO）
```

**V5 行为**：`crosses` 判不跨越（合法），归属右（`3.0004 >= 3.000` 真）——结果**正确但理由偶然**：它把动作起点前 0.4 ms 的那一小段判给了左片段却毫无记录。V6 是"显式吸附 + 留痕"。

**G-2 切点距动作终点不足一个刻度（V5 在这里丢动作）**

| 项 | 值 |
|---|---|
| A1 | `t_from = 0`、`t_to = 5.0004` |
| 请求切点 | `t = 5.000`（另一个动作恰好在此起） |

```
q(A1.t_to) = 5.000
crosses: 5.000 < 5.000 为假 → 不跨越
归属：左 5.000 <= 5.000 真 → **左片段** ✓
留痕：|5.0004 - 5.000| = 0.0004 → ACTION_EDGE_SNAPPED（INFO）
```

**V5 的行为（这是本轮要修的核心）**：

```
crosses:  0+ε < 5.000 && 5.000 < 5.0004-ε = 4.9994  → 后半假 → 不跨越（判为合法切点）
归属左:   5.0004 <= 5.000  → 假
归属右:   0 >= 5.000       → 假
→ A1 既不在左也不在右：动作丢失，无报错
```

**G-3 多个动作边界接近（亚毫秒相邻）**

| 项 | 值 |
|---|---|
| A1 | `t_to = 3.0004` |
| A2 | `t_from = 3.0006` |
| 请求切点 | `t = 3.000` |

```
candidateCuts 量化后：{0, 3.000, ..., 12.0}   ← 3.0004 与 3.0006 都是 3.000，合并成一个
crosses(A1): 3.000 < 3.000 假（A1 已结束）  → 不跨越
crosses(A2): 3.000 < 3.000 假（A2 未开始）  → 不跨越
归属：A1 左（3.000<=3.000）、A2 右（3.000>=3.000）  → 各一次 ✓
```

**V5 的行为**：候选里同时存在 `3.0004` 与 `3.0006` 两个切点，相距 0.0002 s。若算法在窗口内取到 `3.0004`，会切出一个**时长 0.0002 s 的片段**——短于 `minSlice`，但 `pickLegalCut` 的窗口只约束"切点到 consumed 的距离"，不约束"切点到下一个边界"，因此能通过。V6 用 1 ms 网格把两者合并，这种片段在结构上不可能产生。

**G-4 正常精确边界（对照）**

| 项 | 值 |
|---|---|
| A1 | `0 – 12.0` |
| A2 | `12.0 – 16.0` |

即算例 F 的形态。`snap(12.0) = 12.0`（精确命中，不产生 `ACTION_EDGE_SNAPPED`），A1 归左、A2 归右，各一次。

**G-5 退化动作（必须拒绝）**

| 项 | 值 |
|---|---|
| A1 | `t_from = 4.0000`、`t_to = 4.0004`（时长 0.4 ms） |

```
q(t_from) = 4.000, q(t_to) = 4.000 → q(t_to) - q(t_from) = 0 < TQ
→ ADAPT_DEGENERATE_ACTION
```

**为什么必须拒绝而不是"归给某一侧"**：`q(t_from) == q(t_to)` 时，G-1 与 G-2 的两条归属规则在 `t = 4.000` 处**同时成立**，动作会被左右各播一次。这类动作本身是数据错误（0.4 ms 的动作在 1 ms 时间码下不存在），拒绝比猜更诚实。

**G-6 切点不在任何边界半个刻度内（必须拒绝，不得就近取整）**

| 项 | 值 |
|---|---|
| 动作边界 | `{5.0, 9.0}` |
| 请求切点 | `t = 7.0` |

```
snap(7.0) = null   → 不是候选切点
```

**"不允许四舍五入到最近的动作"的理由**：若允许就近取整，手填的 `7.0` 会被吸到 `9.0`（距离 2 s 也吸？）或吸到某个更远的边界，切出来的片段与用户看到的数字对不上，而错误在成片里才暴露。**V6 只吸附"本来就在边界上"的值（半个刻度内），其余一律拒绝并提示合法切点列表。**

**G-7 两个边界同时偏移（必须产生**一条** INFO，不是两条）**

| 项 | 值 |
|---|---|
| A1 | `t_from = 3.0004`、`t_to = 8.0006` |
| 请求切点 | `t = 8.000` |

```
qFrom = 3.000（dFrom = +0.0004）
qTo   = 8.001（dTo   = -0.0006）   ← round(8.0006*1000)=8001，不是 8000
归属：左 8.001 <= 8.000 假；右 3.000 >= 8.000 假 → n = 0
```

**这个例子暴露的是另一件事**：`t_to = 8.0006` 量化成 `8.001`，于是切点 `8.000` **不再是 A1 的合法切点**（A1 跨越 8.000：`3.000 < 8.000 < 8.001`）。`crosses` 会把它排除，`pickLegalCut` 不会返回 8.000。

所以 G-7 的正确期望不是"归左 + INFO"，而是：

| 结果 | 值 |
|---|---|
| `warnings` | **一条** `ACTION_EDGE_SNAPPED`，同时带 `dFrom=+0.0004`、`dTo=-0.0006` |
| 8.000 是否合法切点 | **否**（被 A1 跨越），`explainNoCut` 里 `blockedBy=[A1]` |

**为什么"一条"而不是"两条"**：偏移是**一个动作在一次量化里**发生的事，`rawFrom`/`qFrom`/`dFrom`/`rawTo`/`qTo`/`dTo` 是同一事件的六个字段。拆成两条 INFO 会让"这个动作被挪过"这件事看起来像两件事，统计触发率时会翻倍（R-14 的风险评估会因此偏高一倍）。

**七例汇总**

| 例 | 输入 | 期望输出 | 错误码 |
|---|---|---|---|
| G-1 | 起点偏差 0.4 ms | 归右 + INFO 留痕 | — |
| G-2 | 终点偏差 0.4 ms | 归左 + INFO 留痕 | —（V5 会丢动作） |
| G-3 | 两边界相距 0.2 ms | 合并为一个候选，各归一次 | —（V5 会产生 0.0002 s 片段） |
| G-4 | 精确边界 | 各归一次，**无留痕** | — |
| G-5 | 动作时长 0.4 ms | 拒绝适配 | `ADAPT_DEGENERATE_ACTION` |
| G-6 | 切点离边界 2 s | 拒绝该切点 | 不是候选（`snap` 返回 null） |
| G-7 | 两端同时偏移 | 一条 INFO（六个字段） + 该切点因跨越被排除 | — |

### 3.4 片段完整性校验（按 adaptation 执行）

```js
/**
 * 作用域：单个 adaptation
 * 与 planAdaptation 的关系：plan 防"算错"（fail-fast，不落库）；
 * verify 防"绕过"（对已落库数据独立复算，含历史数据与 plan 版本升级前的方案）
 * @returns {{ ok: boolean, errors: [], warnings: [] }}
 */
export function verifyAdaptation({ adaptationId }) {
  const errors   = [];
  const warnings = [];

  const units = selectUnits(adaptationId);          // status ∈ active|superseded
  const shots = uniqueShotsOf(units);

  // 读库后一律先归一到 1 ms 网格，之后全部严格比较（V7 · P1-03）
  const TQ = 0.001;
  const PAD_TOL = 0.01;                              // 仅用于与非网格的 tailHoldMax 比较

  for (const u of units) {
    const declared = q(u.unitDuration);
    const max      = q(u.profileMax);

    // U-1 单元不超上限
    if (declared > max)
      errors.push({ code: 'UNIT_OVERFLOW', unitId: u.id, dur: declared, max });

    // U-2 单元时长 ≥ 片段之和（网格累加，与 plan 的 put() 同口径）
    let sum = 0;
    for (const f of u.items) sum = q(sum + (q(f.tTo) - q(f.tFrom)));

    if (declared < sum)
      errors.push({ code: 'UNIT_DURATION_MISMATCH', unitId: u.id, sum, declared,
                    msg: '声明时长小于片段之和，片段装不进去' });

    const pad = q(declared - sum);

    // ★ tailHoldMax 只从 adaptation 快照读，不兜底默认（D01-05 §4.14.1）
    const tailHoldMax = u.profileTailHoldMax;
    if (tailHoldMax == null) {
      warnings.push({ code: 'ADAPT_PROFILE_SNAPSHOT_MISSING', unitId: u.id,
                      field: 'profile_tail_hold_max',
                      msg: '方案缺 tailHoldMax 快照，无法校验单元留白；不猜默认值' });
    } else if (pad > tailHoldMax + PAD_TOL) {
      errors.push({ code: 'UNIT_PADDING_EXCESS', unitId: u.id, pad, allowed: tailHoldMax,
                    msg: '片段之和远小于单元时长，多出的时长没有内容依据' });
    }

    // U-3 单元内顺序连续
    const ord = u.items.map(f => f.orderNo);
    for (let i = 0; i < ord.length; i++)
      if (ord[i] !== i + 1) errors.push({ code: 'UNIT_ORDER_BROKEN', unitId: u.id });
  }

  for (const s of shots) {
    const D = q(s.storyDuration);
    const frags = fragsOf(adaptationId, s.id)
      .map(f => ({ ...f, tFrom: q(f.tFrom), tTo: q(f.tTo) }))
      .sort((a, b) => a.tFrom - b.tFrom);

    if (!frags.length) { errors.push({ code: 'FRAG_MISSING_SHOT', shotId: s.id }); continue; }

    // F-1 覆盖起点与终点
    if (frags[0].tFrom > 0)
      errors.push({ code: 'FRAG_GAP_HEAD', shotId: s.id, at: frags[0].tFrom });
    if (frags.at(-1).tTo < D)
      errors.push({ code: 'FRAG_GAP_TAIL', shotId: s.id, at: frags.at(-1).tTo, want: D });

    // F-2 相邻片段首尾相接（不重叠、不遗漏）
    for (let i = 1; i < frags.length; i++) {
      const d = q(frags[i].tFrom - frags[i - 1].tTo);
      if (d > 0) errors.push({ code: 'FRAG_GAP',     shotId: s.id, from: frags[i-1].tTo, to: frags[i].tFrom });
      if (d < 0) errors.push({ code: 'FRAG_OVERLAP', shotId: s.id, at: frags[i].tFrom });
    }

    // F-3 / F-4 不越界、切点合法
    for (const f of frags) {
      if (f.tFrom < 0 || f.tTo > D || f.tTo - f.tFrom < TQ)
        errors.push({ code: 'FRAG_OUT_OF_RANGE', shotId: s.id, tFrom: f.tFrom, tTo: f.tTo, dur: D });
      if (f.tTo < D && !isLegalCut(s, f.tTo))
        errors.push({ code: 'FRAG_CUT_MID_ACTION', shotId: s.id, at: f.tTo });
    }

    // F-5 动作归属完整性（独立于 plan 的兜底，判据不同：这里用"片段包含"）
    for (const a of s.actions || []) {
      const af = q(a.t_from), at = q(a.t_to);
      const owners = frags.filter(f => f.tFrom <= af && at <= f.tTo);
      if (owners.length !== 1)
        errors.push({
          code: owners.length === 0 ? 'FRAG_ACTION_LOST' : 'FRAG_ACTION_DUPLICATED',
          shotId: s.id, actionId: a.id, span: [af, at],
          owners: owners.map(f => [f.tFrom, f.tTo]),
          msg: owners.length === 0 ? '动作不落在任何片段内（成片会整条消失）'
                                   : '动作跨越多个片段（会被播两遍）'
        });
    }
  }

  // F-6 单元跨场景（只警告，不失败）
  units.filter(u => crossesScene(u)).forEach(u =>
    warnings.push({ code: 'UNIT_CROSS_SCENE', unitId: u.id }));

  return { ok: errors.length === 0, errors, warnings };
}
```

**两层归属校验的职责划分（V7 · P1-02 第 9 条）**

`planAdaptation` 里的 `assertAttribution` 和 `verifyAdaptation` 里的 F-5 都在查"动作有没有丢"，但**判据不同、时机不同、防的东西不同**，不是重复：

| | `assertAttribution(s, t)` | F-5 片段包含 |
|---|---|---|
| 时机 | 生成时，**落库前** | 读取时，**对已落库数据** |
| 输入 | 单镜 + 一个切点 `t` | 该镜在一个 adaptation 内的**全部片段** |
| 判据 | 左右两侧计数之和 `n` 必须为 1 | 恰好有一个片段 `[tFrom, tTo]` 包含该动作区间 |
| 能抓到 | 比较符写错、绕过 `q()` 用原始浮点 | **片段本身错位**（整段偏移、`tFrom` 写成别的值）、plan 版本升级后旧方案失效、有人直接 INSERT 绕过 plan |
| 抓不到 | 片段区间本身错了（它只看切点） | 单点归属符写错但区间恰好正确（此时 F-1~F-4 会报缺口/重叠） |
| 失败处置 | `ok:false`，**不落库** | 拒绝出片 / 标记方案 `status='failed'` |

一句话：**plan 侧防"我算错了"，verify 侧防"有人绕过了我"。** 只留一个，另一条路就没人守。

**`planAdaptation` 与 `verifyAdaptation` 的比较口径对照（V7 · P1-03 第 5 条）**

这两处是"算"与"验"的关系，如果口径不同，就会出现"plan 产出的东西 verify 判它不合格"的死循环。逐项对照：

| 量 | plan 侧 | verify 侧 | 同口径 |
|---|---|---|---|
| 单元时长累加 | `cur.dur = q(cur.dur + (b - a))` | `sum = q(sum + (q(tTo) - q(tFrom)))` | ✅ 都是"每加一项就重新量化" |
| 上限比较 | `remain <= room`（两侧网格值） | `q(unitDuration) > q(profileMax)` | ✅ 都严格，都先归一 |
| 单片段下限 | `put()` 只在 `b > a` 时落片段 | `tTo - tFrom < TQ` → `FRAG_OUT_OF_RANGE` | ✅ 都以 `TQ` 为物理下限（`minSlice` 是业务下限，只约束切点窗口，不约束镜尾） |
| 留白 | 不判（plan 只产出，不校验自己） | `pad > tailHoldMax + PAD_TOL` | 单向：只有 verify 判，因为 `tailHoldMax` 是配置值不是 plan 的输入约束 |
| 缺口 / 重叠 | 由 `consumed = cut` 的赋值方式保证 | `d = q(tFrom - prev.tTo)`，`d>0`/`d<0` | ✅ 前者是构造，后者是事后判；两者都必须有（见 H-3） |

**"单片段下限"这条最容易被误读**：`minSlice` 只约束**切点窗口**（`pickLegalCut(s, consumed+minSlice, consumed+room)`），它**不约束镜尾**。一个 `D = 2.0, minSlice = 2.0` 的镜放进空单元，走的是"整段装得下"分支，产出 2.0 s 片段——正好等于 `minSlice`，合法。而一个 `D = 0.002` 的镜也会被整体放入（0.002 s 片段），因为拒绝它没有意义（它就是一镜，不是切出来的）。所以 verify 的下限是 `TQ`，不是 `minSlice`。

**必须强调的执行范围**：

| 检查 | 作用域 | 跨 adaptation 时 |
|---|---|---|
| F-1 ~ F-5（片段补集 + 归属） | 单 adaptation 内的**该 shot 全部片段** | **允许重叠**，不得报错 |
| U-1 ~ U-3（单元约束） | 单 unit | — |
| 跨 adaptation 一致性 | 不做 | 它们是不同版本，本就不同 |

错误码一览：

| code | 层 | 含义 | 处置 |
|---|---|---|---|
| `ADAPT_NO_LEGAL_CUT` | plan | 整镜超 max 且无合法动作断点 | **适配失败**，返回给创作者：拆镜或延长/缩短，不得硬切 |
| `ADAPT_DEGENERATE_ACTION` | plan | 动作量化后时长 `< TQ`（不足 1 ms），区间退化 | 适配失败，要求修正动作时间 |
| `ADAPT_ACTION_OUT_OF_RANGE` | plan | 动作量化后越出 `[0, story_duration]` | 适配失败 |
| `ADAPT_ACTION_LOST` | plan | 切点处某动作左右归属之和为 0 | **算法 bug**（比较符写错），拒绝落库 |
| `ADAPT_ACTION_DUPLICATED` | plan | 切点处某动作左右归属之和为 2 | **算法 bug**（绕过 `q()` 用原始浮点），拒绝落库 |
| `UNIT_OVERFLOW` | verify | 单元超 profile.max | 算法 bug，拒绝落库 |
| `UNIT_DURATION_MISMATCH` | verify | 声明时长 < 片段之和 | 拒绝落库 |
| `UNIT_PADDING_EXCESS` | verify | 声明时长 ≫ 片段之和（差额超过 `tailHoldMax`） | 拒绝落库 |
| `FRAG_GAP` / `FRAG_GAP_HEAD` / `FRAG_GAP_TAIL` | verify | 片段有缺口 | 拒绝落库 |
| `FRAG_OVERLAP` | verify | 同 adaptation 内重叠 | 拒绝落库 |
| `FRAG_OUT_OF_RANGE` | verify | 越出 `[0, story_duration]` 或片段 `< TQ` | 拒绝落库 |
| `FRAG_CUT_MID_ACTION` | verify | 切点劈开动作 | 拒绝落库 |
| `FRAG_ACTION_LOST` | verify | 某动作不被任何片段包含（**独立于 plan 的兜底**） | 拒绝出片，方案标 `failed` |
| `FRAG_ACTION_DUPLICATED` | verify | 某动作被多个片段包含（会播两遍） | 拒绝出片，方案标 `failed` |
| `SHORT_UNIT` | plan | 尾单元低于 shortFloor | 警告（`WARN`），可落库 |
| `UNIT_CROSS_SCENE` | verify | 单元跨 2 场景 | 警告（`WARN`），`D01-01 §3.7` 允许但标风险 |
| `ACTION_EDGE_SNAPPED` | plan | 动作边界被量化挪动（亚毫秒） | **`INFO`，不在 `errors` 里**，不阻断切分 |
| `ADAPT_PROFILE_SNAPSHOT_MISSING` | verify | 方案缺 `profile_tail_hold_max` 快照 | 警告，不猜默认值 |

### 3.5 不可切时怎么办（明确拒绝）

`ADAPT_NO_LEGAL_CUT` 是**正常返回**，不是异常。典型场景：一个 20s 长镜头全程一个连续长动作（无 `t_to` 断点），H3 上限 15s。

返回给创作者的三条处置建议（不自动选）：

1. 在动作设计上**补一个可断点**（自然的动作收势），这属于改创作态，必须人工决定；
2. **拆镜**（把 20s 拆成两个导演镜，各自有独立构图），这是导演决策；
3. **换 profile**（该轨道不可用 → 用支持更长时长的模型）。

**禁止**：截断到 15s 丢掉 5s 内容、拉伸动作、加速播放。这三种都会破坏导演设计，而 `D01` 的核心原则是"适配不改变创作"。

## 四、三种哈希（P0-01 重写）

### 4.1 为什么必须是三种

V2 只有一个 `sourceSpecHash`，而它的 payload 里包含 `unit.track` / `profile_ver` / `unit_duration` / `fragments`。后果：

- 同一份分镜在 Seedance 和 H3 下 `track` 必然不同 → **两个 hash 必然不同**；
- V2 却把 `H-21「双编译器同输入两 sourceSpecHash 逐字相同」` 写成 CI 断言 → **这条断言在 V2 的设计下永远失败**；
- V2 的 `H-19「改 track → hash 变」`、`H-20「改 fragments → hash 变」` 进一步把这个错误固化成"预期行为"。

也就是说：**V2 声称"能证明同源"，但它定义的函数在结构上就不可能输出同源结果。** 这是本轮最重的一处定义冲突。

正确做法是把三件事分开：**导演做了什么 / 怎么切成片 / 用什么程序编译**。

```
┌─────────────────────────┐      ┌──────────────────────────┐
│  L0 创作态                │      │  L1 适配态                 │
│  ShotSpec + 动作 + 空间    │      │  track / profile / 片段    │
└───────────┬─────────────┘      └────────────┬─────────────┘
            │                                  │
     sourceSpecHash                     adaptationHash
            │                                  │
            └──────────────┬───────────────────┘
                           ▼
                   compiledHash
              （+ compilerVer + 编译参数）
```

三个 hash **相互正交**：任一维度变化只影响自己及其下游。

| 维度 | hash | 回答的问题 |
|---|---|---|
| 创作 | `sourceSpecHash` | 这两条片子拍的是不是同一份分镜？ |
| 适配 | `adaptationHash` | 切分方案有没有变？ |
| 编译 | `compiledHash` | 产物是不是同一版程序在同参数下的结果？ |

### 4.2 `sourceSpecHash` · 只覆盖导演语义

```js
function sourceSpecHash({ scenes, shots, assets }) {
  const payload = {
    hashKind: 'd01.source',
    specVersion: 3,

    // —— 场景依赖（坐标基线、固定物、轴线、光线）——
    scenes: scenes
      .map(sc => canonical(sc, [
        'scene_id','scene_key','coord_system','fixtures','entries',
        'axis_lock','power_geometry','crowd_switch','time_of_day','lighting_base'
      ]))
      .sort((a, b) => cmpStr(a.scene_key, b.scene_key)),

    // —— 镜头（按 global_no 升序）——
    shots: shots
      .slice()
      .sort((a, b) => a.global_no - b.global_no)
      .map(s => ({
        // A 标识：只保留影响剪辑位置的编号，不含 id
        no: s.global_no, shotNo: s.shot_no, sceneKey: s.scene_key,
        prevShotNo: s.prev_shot_no ?? null,

        // B 剧作意图
        purpose: s.purpose, dramaticValue: s.dramatic_value, infoDelta: s.info_delta,
        dialogueFunction: s.dialogue_function, isInsert: !!s.is_insert,

        // C 画面
        visual: s.visual_content, composition: s.composition, lighting: s.lighting,

        // D 摄影（14 字段全部）
        size: s.shot_size, dir: s.cam_direction, height: s.cam_height,
        roll: num(s.cam_roll_deg), camPos: vec(s.cam_pos), camTarget: s.cam_target,
        camDist: num(s.cam_distance_m), lens: num(s.lens_mm), fov: num(s.fov_deg),
        movement: s.movement, amp: s.movement_amp, camPath: arr(s.cam_path),
        compRule: s.composition_rule, camNote: s.cam_note,

        // F 声音（5 字段 + 音色走资产）
        // ★ 音色唯一权威 = shot_assets(role='voice')，见下方 assets；
        //   voice_ids 是派生兼容字段，**不进 hash**（P1-05）
        dialogue: s.dialogue, speakers: arr(s.speakers), narration: s.narration,
        sfx: s.sfx, musicCue: s.music_cue,

        // J 时间（5 字段；duration 是导演时长，不是单元时长）
        duration: num(s.story_duration), slices: arr(s.time_slices),
        ramp: s.speed_ramp, cut: !!s.is_cut_point, timeJump: !!s.time_jump,

        // G 空间（逐人，按 character_id 排序后归一化可靠性）
        blockings: (s.blockings || [])
          .map(b => ({ char: b.character_id, pos: b.position_abs, xy: vec(b.norm_xyz),
                       posTrack: arr(b.position_track), anchor: b.anchor_object, behind: b.behind_object,
                       facing: b.facing, gaze: b.gaze_target, posture: b.posture,
                       dist: num(b.distance_to_camera), occ: b.occlusion,
                       hand: b.hand_state, task: b.current_task,
                       inFrame: !!b.in_frame, power: b.power_level, anchorObj: b.instance_anchor,
                       // 可靠性必须进 hash，且必须由 posRel() 求（§4.2 末、D01-04 §5.2.2）：
                       // 直接读 b.rel 会把 not_applicable 吞成 unknown，也会漏掉三分量整体性判定
                       rel: posRel({ x: b.norm_x, y: b.norm_y, z: b.norm_z,
                                     metaEntry: b.meta, specSource: s.spec_source }) }))
          .sort((a, b) => cmpStr(a.char, b.char)),

        // E 动作（20 业务字段）—— 全序规范化，见 canonicalActions()
        actions: canonicalActions(s),

        // H 首尾状态 + 可靠性（unknown 与 known 必须区分，否则"补一个猜测值"不改变 hash）
        stateIn: canonState(s.state_in), stateInMeta: canonMeta(s.state_in_meta),
        stateOut: canonState(s.state_out), stateOutMeta: canonMeta(s.state_out_meta),

        // I 资产引用 + 内容指纹
        assets: (s.assets || [])
          .map(x => ({ id: x.asset_id, role: x.role, order: x.order_no,
                       variant: x.variant_of, fp: assets[x.asset_id]?.fingerprint || '',
                       fpLevel: assets[x.asset_id]?.fpLevel || 'meta' }))
          .sort((a, b) => cmpStr(a.role, b.role) || cmpStr(a.id, b.id))
      }))
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

**明确排除**（这些字段变了，`sourceSpecHash` 必须不变）：

| 排除项 | 理由 |
|---|---|
| `track`、`profile_ver`、`unit_duration`、`unit_no`、`seam` | 属于适配决策，不进创作语义 |
| `render_unit_shots.t_from/t_to`、`split_reason` | 切分结果，不是导演意图 |
| `shot.id`、`action.id`、`created_at`、`updated_at`、`qc_status`、`fill_confidence`、`spec_source` | 非语义；`action.id` 排除后由 `contentHash` 承担引用映射 |
| 任何以 `_` 开头的键（V4 的 `_id`/`_ref`/`_par`） | 实现细节，不是语义；V5 改为白名单 `bodyOf()` 后这类键**不可能**进入 payload（P1-02） |
| `voice_ids` | 派生兼容字段，权威是 `shot_assets(role=voice)` |
| `prompt_packages.*`、`render_attempts.*` | 下游产物 |

**注意 `seam` 的归属判断**：`seam`（段缝策略）影响"这一镜是不是单元收尾、要不要加定格句"。哪一镜成为单元收尾是**切分决定的**，不是导演决定的——同一镜在 30s 切法里是段中，在 15s 切法里可能是段尾。所以 `seam` 归 `adaptationHash`。V2 把它放进 `unit` 再进 source，是错的。

**`state_in_meta` / `state_out_meta` 必须进 hash**：否则"把 unknown 悄悄改成 known 的猜测值"不会改变 hash，同源证明就形同虚设。

**音色（P1-05）：`shot_assets(role='voice')` 是唯一权威，`voice_ids` 不进 hash**

| 问题 | 答案 |
|---|---|
| 音色是否统一走 `shot_assets` | **是**。`role='voice'`，`category ∈ {voice, narration}`，每镜 ≤3 |
| `voice_ids` 保留吗 | **保留，但降级为只读派生字段**：由 `shot_assets(role='voice')` 按 `order_no` 渲染出一维数组，只供旧页面/旧 API 读 |
| 两个字段能否都是权威 | **不能**。写入时只写 `shot_assets`，`voice_ids` 由程序在读出时现算；任何代码不得以 `voice_ids` 为准 |
| hash 用哪个 | **`shot_assets` 的 voice 条目 + 内容指纹**，即 payload 里的 `assets` 数组（`role='voice'`） |
| 音色变了 hash 会变吗 | **会**。`assets[].fp` 是该资产的内容指纹，换音色 = 换 `asset_id` 或换 `fp` → hash 变 |

**为什么必须这样**：若 `voice_ids` 和 `shot_assets` 都是权威，改一处漏一处时 hash 会漏掉变化——"同源证明"会证明一个已经不存在的事实。派生字段的唯一职责是兼容旧读者，不是记录事实。

#### 4.2.1 动作的规范序与引用映射（P1-06）

V3 的排序键是 `(tFrom, actor)`。这**不是全序**：

- 同一镜里多个动作 `tFrom` 都等于 0（很常见），且同一 actor 在同一时刻有多个动作时，顺序取决于输入数组；
- 数据库返回顺序一变，`sourceSpecHash` 就变——**同源证明失效**。

**V4 规则**：

```
① 动作按 (tFrom, actor, tTo, type, contentHash) 排序 —— 五项全序，与输入顺序无关
② 动作的 `id` 不进 hash（否则"复制一个动作换个 id"会改变 hash）
③ trigger.ref / sync.parallel_with 中的动作 id → 映射为该动作的 contentHash
   （目标不在本镜内时保留原字符串，如 "sfx:monitor"）
④ contentHash = sha256(canonicalStringify(动作语义体))
```

**V5 修正（P1-02）：`contentHash` 的输入必须是纯语义体**

V4 的实现是 `contentHashOf(a) { const { _id, ...rest } = a; ... }`——**只排除了 `_id`**，而 `_ref` / `_par` 这两个临时映射字段仍在对象里，于是：

```
A2.trigger.ref = "ac_1"（A1 的 id）
→ A2 的 contentHash 里含字符串 "ac_1"
→ 把 A1 改名成 "ac_9" 并同步更新引用，A2 的内容一字未改，contentHash 却变了
→ sourceSpecHash 变 → "同源"证明被 id 命名污染
```

更糟的是它在排序里自引用：排序键用 `contentHash`，`contentHash` 里含**别人**的 id，而别人的 id 又不进 hash——**排序键与被排序对象之间出现了不该有的耦合**，重命名可能改变动作顺序，进而改变 payload 顺序。

**V5 规则（取代 V4 的 ④）**：

```
④ contentHash = sha256(canonicalStringify(body(a)))
   body(a)  = 动作的语义字段全集（见下方 `bodyOf()`，20 个业务字段），
              结构性排除 _id / _ref / _par / 任何以 _ 开头的临时键
⑤ 先算全部 body 与 contentHash（此时不读任何 id），再建 id→contentHash 映射，最后回填引用
⑥ 引用映射的结果（triggerRef / parallelWith）是 payload 的字段，但它取值为 contentHash，
   因此"改引用目标的引用关系"会变 hash，"改引用目标的 id 命名"不会变
```

```js
// 只挑语义字段；白名单而非黑名单——新加的临时字段不会意外漏进 hash
function bodyOf(a) {
  return {
    actor: a.actor_id, type: a.action_type, primary: !!a.is_primary, tier: a.tier,
    init: a.init_state,
    trigger: stripRefTrigger(a.trigger_json),  // 剥 ref，保留 kind/text/未知新字段
    path: a.path_json, force: a.force_json, speed: a.speed_json,
    power: a.power, cog: a.cog, parts: arr(a.body_parts),
    contact: a.contact_json, result: a.result_json, follow: a.follow_through,
    recovery: a.recovery, end: a.end_state,
    sync: stripRefSync(a.sync_json),           // 剥 parallel_with，保留其余与未知新字段
    tFrom: num(a.t_from), tTo: num(a.t_to)
  };
}

function contentHashOfBody(body) {
  return sha256(canonicalStringify(body));    // 纯语义体，无任何 id
}

function canonicalActions(s) {
  const raw = (s.actions || []).map(a => ({
    id: a.id,                                  // 仅用于建映射，绝不进 hash
    ref: a.trigger_json?.ref || '',
    par: arr(a.sync_json?.parallel_with, []),
    body: bodyOf(a),
    ch: null                                   // contentHash，下面填
  }));

  // ① 先算 contentHash（此时不读任何 id）
  for (const r of raw) r.ch = contentHashOfBody(r.body);

  // ② 全序排序（五项，末项用 contentHash）
  raw.sort((x, y) =>
    (x.body.tFrom - y.body.tFrom) ||
    cmpStr(x.body.actor, y.body.actor) ||
    (x.body.tTo - y.body.tTo) ||
    cmpStr(x.body.type, y.body.type) ||
    cmpStr(x.ch, y.ch));

  // ③ id → contentHash（同镜内）
  const refMap = new Map(raw.map(r => [r.id, r.ch]));

  // ④ 回填引用：引用目标是 contentHash，不是 id
  return raw.map(r => ({
    ...r.body,
    triggerRef: r.ref ? (refMap.get(r.ref) ?? `ext:${r.ref}`) : null,
    parallelWith: r.par.map(t => refMap.get(t) ?? `ext:${t}`).sort()
  }));
}
```

**`bodyOf()` 的依赖必须都是已定义函数（V7 · P1-01）**

V6 的 `bodyOf()` 里写的是 `stripRef(a.trigger_json)` / `stripRef(a.sync_json)`，而 §4.2.3 正式定义的是 `stripRefTrigger()` / `stripRefSync()`——**一个从未定义的名字被调用了两次，两个正式定义从未被调用**。这种"定义与调用各写一套"在评审时看不出来（两段都在文档里，读哪段都像成立），只有把两段拼起来才会发现 `ReferenceError: stripRef is not defined`。

| 函数 | 定义位置 | 调用位置 | 作用 |
|---|---|---|---|
| `stripRefTrigger(json)` | §4.2.3 | `bodyOf()` 的 `trigger` | 剥 `ref`，保留 `kind`/`text`/未知字段 |
| `stripRefSync(json)` | §4.2.3 | `bodyOf()` 的 `sync` | 剥 `parallel_with`，保留其余全部 |
| `arr()` | §4.2.1 附注 | `bodyOf()` 的 `parts` | `null`/非数组 → `[]` |
| `num()` | §4.2.1 附注 | `bodyOf()` 的 `tFrom`/`tTo` | `null` → `0`；`'3.0'` → `3` |
| `canonicalStringify()` | §4.5 | `contentHashOfBody()` | 键排序 + 数值归一 |
| `cmpStr()` | §4.5.0 | `canonicalActions()` 排序 | UTF-16 code unit 比较，不依赖 locale |

> **`stripRef` 这个名字在本设计中不再存在。** 任何文档、伪代码、实施代码里出现裸 `stripRef(...)` 调用，都视为 V6 遗留的未定义调用。`D01-11 §六` 里的同名示例属历史记录，不作规范。

**为什么用白名单 `bodyOf` 而不是 `{ const { _id, _ref, _par, ...rest } = a }`**：黑名单要求"每加一个临时字段都记得加一行排除"，漏一次 hash 就被污染且**没有任何报错**。白名单要求"每加一个语义字段都记得加一行包含"，漏了会在 `R-01`（改任一字段 hash 必须变）当场暴露。**两种遗漏的可见性完全不同，选白名单。**

**外部引用（`ext:` 前缀）**：`trigger.ref` 指向本镜之外的对象（如 `sfx:monitor`、`prev_shot:sh_10`）时，映射不到本镜动作，保留 `ext:<原字符串>`。这是稳定表示——它不依赖任何数据库 id，只依赖那个外部标识本身。

**已知的可接受歧义**：若同一镜内存在两个**内容完全相同**的动作（body 全字段相等），它们的 `contentHash` 相同，`triggerRef` 指向二者之一无法区分。这在语义上无差别（两个动作一模一样），因此不视为缺陷——但**必须显式记录**，不得靠"数据库返回顺序决定指向谁"来隐式处理（§4.2.2）。

#### 4.2.2 引用映射的确定性边界

| 情形 | 是否确定 | 处理 |
|---|---|---|
| 引用一个 body 唯一的动作 | ✅ | `contentHash` 唯一，映射无歧义 |
| 引用两个 body 全等的动作之一 | ⚠️ 有歧义 | 二者语义无差别，hash 相同即视为同一目标；在 `qc_reports` 记 `REF_AMBIGUOUS_CONTENT`（INFO） |
| 引用目标不在本镜 | ✅ | `ext:<原字符串>` |
| `parallel_with` 乱序 | ✅ | `.sort()` 后写入 |
| 同一对动作双向都声明 `parallel_with` | ✅ | 两边各自映射，值相同 |

**"不得偷偷依赖数据库顺序"的落地**：若实现按 `raw` 的输入顺序去 `refMap.get()` 并在重复 contentHash 时取第一个，结果会随 `SELECT` 顺序变化。V5 规定：重复 `contentHash` 时，`triggerRef` 取该 contentHash 即可（**不取实例**），因为 contentHash 相同的两个动作在被引用这件事上完全等价。

#### 4.2.3 引用剥离函数的正式定义（V6 首定义，V7 修正命名 · P1-01）

"剥引用"这件事在 V4/V5 里被提到 4 次、在伪代码里被调用 2 次，**却从未定义**。它决定 `bodyOf()` 里 `trigger` 与 `sync` 两个字段的具体内容，也就是 hash 的一半输入——不定义它，`sourceSpecHash` 的实现就是自由的。

V6 补了定义，但**定义的名字（`stripRefTrigger` / `stripRefSync`）与调用的名字（`stripRef`）不一致**，等于仍然没有可运行的实现。V7 只做一件事：把 `bodyOf()` 的调用改成这两个名字（见 §4.2.1 的依赖表）。**函数体本身不变**——V6 的剥离语义是对的，错的只是名字。

**两个字段的结构（`D01-03 §3.2`、`§3.10`）**

| 字段 | 结构 | 谁是引用 |
|---|---|---|
| `trigger_json` | `{ kind, ref, text }` | **只有 `ref`** |
| `sync_json` | `{ with_dialogue, dialogue_span, emotion, relation, parallel_with, focus_rank }` | **只有 `parallel_with`** |

**规则：只剥引用字段，其余一律原样保留**

```js
/** trigger：去掉 ref，保留 kind / text 及其后新增的一切字段 */
function stripRefTrigger(json) {
  const { ref, ...rest } = json || {};
  return rest;                       // 空对象时返回 {}，不是 null
}

/** sync：去掉 parallel_with，保留 with_dialogue / dialogue_span / emotion / relation / focus_rank 等 */
function stripRefSync(json) {
  const { parallel_with, ...rest } = json || {};
  return rest;
}
```

**输入 / 输出算例**

| # | 输入 | 输出 | 说明 |
|---|---|---|---|
| 1 | `{kind:'action', ref:'ac_1', text:'纸被摔在柜上'}` | `{kind:'action', text:'纸被摔在柜上'}` | 剥 `ref`，保留 `kind`/`text` |
| 2 | `{kind:'self', ref:'', text:'自主'}` | `{kind:'self', text:'自主'}` | 空 `ref` 也剥（不能因为"是空串"就留下键） |
| 3 | `{kind:'ambient', ref:'sfx:monitor', text:'监护仪报警'}` | `{kind:'ambient', text:'监护仪报警'}` | 外部引用同样剥——它在 `triggerRef` 里以 `ext:` 形式回来 |
| 4 | `null` / `undefined` | `{}` | 统一空对象，不产生 `null` 分支 |
| 5 | `{kind:'action', ref:'ac_1', text:'…', strength:0.8}` | `{kind:'action', text:'…', strength:0.8}` | **未知新字段必须保留**——它是语义（见下） |
| 6 | sync `{with_dialogue:'after', dialogue_span:[1.6,4.5], emotion:'cold_pressure', relation:'reinforce', parallel_with:['ac_2'], focus_rank:1}` | 同上去掉 `parallel_with` 的 5 个字段 | 一个都不许少 |
| 7 | sync `{with_dialogue:'before', parallel_with:[]}` | `{with_dialogue:'before'}` | 空数组也剥 |
| 8 | sync `{..., parallel_with:['ac_2'], tempo:'staccato'}`（新字段） | 保留 `tempo` | 同 #5 |

**为什么这里用"黑名单式只剥一个键"，而 `bodyOf()` 用白名单**

这两个地方看着矛盾，其实是两个不同的对象：

| | `bodyOf()` | `stripRefTrigger` / `stripRefSync` |
|---|---|---|
| 操作对象 | **我们自己拼的映射对象**（`a.trigger_json` → `trigger` 等） | **数据库里的领域 JSON 列**（`trigger_json` / `sync_json`） |
| 未知键从哪来 | 来自我们自己的临时变量（`_id`/`_ref`/`_par`）——它们**一定不是语义** | 来自未来的 schema 演进（新增 `strength`/`tempo`）——它们**一定是语义** |
| 漏掉一个的后果 | 临时 id 进 hash → 同源证明被污染 | 新语义字段进不了 hash → 改了提示词 hash 不变 |
| 该用 | **白名单**（默认排除） | **黑名单**（默认保留） |

一句话：**"我们自己的临时字段"默认不信，"用户数据里的未知字段"默认相信。**

**引用关系仍然回填**：`stripRefTrigger` / `stripRefSync` 只是把引用从"内容"里拿出来，不让它参与内容 hash；引用本身在 `canonicalActions` 的第 ④ 步以 `triggerRef` / `parallelWith` 写回 payload，取值是该目标的 `contentHash`（而非 id）。因此：

- 改引用的**目标内容** → 目标的 `contentHash` 变 → `triggerRef` 变 → `sourceSpecHash` 变（正确）；
- 改引用的**目标 id 命名**（同步更新引用）→ `contentHash` 不变 → `triggerRef` 不变 → `sourceSpecHash` 不变（正确，R-32/R-33）。



**排序确定性的验证**（§4.6 R-26）：把同一组动作按正序、逆序、随机三种顺序传入 `sourceSpecHash`，hash 必须逐字相同。

### 4.3 `adaptationHash` · 只覆盖切分方案

```js
function adaptationHash({ adaptation, units, fragments }) {
  const payload = {
    hashKind: 'd01.adaptation',
    adaptationVersion: adaptation.adaptation_version,
    track: adaptation.track,
    profileVer: adaptation.profile_ver,
    profileParams: {                       // profile 的四个能力参数（快照值），换任一数值即换适配
      max: num(adaptation.profile_max),
      shortFloor: num(adaptation.profile_short_floor),
      minSlice: num(adaptation.profile_min_slice),
      tailHoldMax: num(adaptation.profile_tail_hold_max)   // 缺失 → null，不补默认值
    },
    seamPolicy: adaptation.seam_policy_json,   // 段缝策略（含 tailHold）
    units: units
      .slice().sort((a, b) => a.unit_no - b.unit_no)
      .map(u => ({
        unitNo: u.unit_no,
        unitDuration: num(u.unit_duration),
        shots: fragments
          .filter(f => f.unit_id === u.id)
          .sort((a, b) => a.order_no - b.order_no)
          .map(f => ({ shotId: f.shot_id, orderNo: f.order_no,
                       tFrom: num(f.t_from), tTo: num(f.t_to), reason: f.split_reason }))
      }))
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

**不包含 `sourceSpecHash`**：这是刻意的。若把源 hash 混进来，"切分方案本身有没有变"就无法单独回答。组合关系由 `compiledHash` 承担。

### 4.4 `compiledHash` · 组合

```js
function compiledHash({ sourceHash, adaptationHash, compilerVer, compilerParams }) {
  const payload = {
    hashKind: 'd01.compiled',
    sourceSpecHash: sourceHash,
    adaptationHash,
    compilerVer,
    compilerParams: canonical(compilerParams, [
      'format',          // 'ref2va' | 't2va'
      'language',        // 'en' | 'zh'
      'aspectRatio',
      'fps',
      'refPackPolicy',   // 'ordered' | 'by-role'
      'seamInjection'    // true | false
    ])
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

用途：
- 产物幂等（同 hash 不重复插 `prompt_packages`）；
- 回答"这条片子是哪套分镜 + 哪套切分 + 哪个编译器版本产的"。

**三者关系（可判定的推论）**：

| 操作 | source | adaptation | compiled |
|---|---|---|---|
| 改一句台词 | **变** | 不变（若切点未受影响） | **变** |
| 改切分（同 profile 重切） | 不变 | **变** | **变** |

### 4.5 规范化序列化（三者共用）

#### 4.5.0 字符串比较必须与区域设置无关（V6 · P1-03）

V5 的排序全部用 `String(a).localeCompare(String(b))`。**`localeCompare` 在不传 locale 时用的是宿主默认区域**，同一份数据在两台机器上可能排出两种顺序：

| 环境 | `"i"` vs `"I"` | `"ä"` vs `"z"` | `"ı"` vs `"i"` |
|---|---|---|---|
| `en-US` | `I < i` | `ä < z` | `ı < i` |
| `tr-TR` | `I < i` | 同 | **`ı` 与 `i` 不同组，且 `I` 与 `ı` 也不等同** |
| `sv-SE` | `I < i` | **`z < ä`**（ä 是第 27 个字母） | 同 |
| `de-DE`（phonebook） | `I < i` | **`ä ≈ ae`**，与 `a` 同组 | 同 |

动作 id、角色 id 目前都是 ASCII 小写，看似安全；但 `scene_key` 可能含中文（`S02_病房`）、`type` 可能含下划线、资产 id 可能含大写——**只要有一个非 ASCII 字符，两台机器就可能排出不同 hash**，而 `sourceSpecHash` 的全部意义就是"在任何机器上算出同一个值"。

**V6 规定：hash 路径上一律用 `cmpStr()`，禁止 `localeCompare()`。**

```js
// 按 UTF-16 code unit 逐位比较。ECMA-262 的字符串关系比较（< >）
// 定义为 code unit 序列的字典序，与宿主机 locale / ICU 版本无关。
function cmpStr(a, b) {
  const x = String(a ?? ''), y = String(b ?? '');
  return x < y ? -1 : x > y ? 1 : 0;
}
```

| 项 | `localeCompare` | `cmpStr` |
|---|---|---|
| 依赖 | 宿主默认 locale + ICU 版本 | 仅 ECMA-262 规范 |
| 换机器 | **可能变** | 恒定 |
| `null` / `undefined` | 抛错或按 `"null"` 比（实现相关） | 统一空串 |
| 大小写 | 可配置为忽略大小写 | 严格区分（`A` < `a`） |
| 中文 | 按拼音/笔画（随 locale） | 按 code unit（恒 `U+4E00` 起） |

**同一规则适用于 `canonicalStringify` 的对象键排序**：键排序也必须用 `cmpStr`，不是 `Object.keys().sort()` 的默认行为（虽然默认恰好也是 code unit 序，但必须写死，不能依赖"默认恰好一致"）。

**回归要求（`R-42`）**：同一 fixture 在 `LANG=en_US.UTF-8`、`LANG=tr_TR.UTF-8`、`LANG=sv_SE.UTF-8` 三种环境下跑 `sourceSpecHash`，**必须逐字相同**。CI 至少跑前两种——Node 的 `localeCompare` 受 ICU 与 `LANG` 双重影响，容器里改 `LANG` 即可复现差异。

| 规则 | 实现 | 原因 |
|---|---|---|
| 键排序 | 所有对象键按 UTF-16 code unit 序输出，比较函数固定为 `cmpStr`（§4.5.0），**禁止 `localeCompare`** | DB 返回键序不稳定 + 不能依赖宿主 locale |
| 整数 | 去小数（`4.0` → `4`） | `4` 与 `4.0` 必须同 hash |
| 浮点 | 保留 6 位并去尾零（`4.500000` → `4.5`，`0.30000000000004` → `0.3`） | 浮点误差不得影响 hash |
| `null` / `undefined` | 统一 `null`，**保留键** | 省略与 null 语义不同 |
| 空集合 | `[]` / `{}` 保留 | 同上 |
| 字符串 | NFC 归一化 + 去首尾空白 + **不去内部空白** | 内部空格是语义（台词停顿） |
| 有序数组 | `time_slices`、`cam_path`、`position_track` 保原序 | 顺序即语义 |
| 无序数组 | `blockings`（按 char）、`actions`（**五项全序** tFrom→actor→tTo→type→contentHash）、`assets`（按 role+id）、`scenes`（按 scene_key） | 插入顺序不应影响 |
| 派生字段 | `voice_ids` **不进 hash**（由 `shot_assets(role=voice)` 派生，见 §4.2） | 两个权威会让变化漏检 |
| 缺失字段 | 视为 `null`（不视为"不存在"） | 加字段不改变旧数据 hash |

`canonState` / `canonMeta`：按 `chars.<id>.<field>` 的字典序展开成一维键值对，保证嵌套对象的键序无关。

### 4.7 `sourceSpecHash` 的作用域

一个 hash 对应**一章的全部分镜**（按 `global_no` 排序）。跨章的镜不参与同一 hash。

若只修改了第 30 镜，第 1–29 镜的 `state_out` 会被增量复用，但 **hash 必须整体重算**（因为 payload 包含全体 shots）。重算是毫秒级，不做"分块 hash 拼接"——分块拼接会让"插入一镜"无法被检测到。

| 加必填字段 | 是 | `spec_version` +1，旧数据按 S 级降级 |
| 加枚举值 | 否（读者）/ 是（switch） | 编译器与 QC 必须"未知值 → WARN 不崩" |
| 删枚举值 | 是 | 禁止，只标 deprecated |
| 表结构变更 | 视情况 | 只加列/加表 |
| 编译器逻辑变更 | 是 | `compiler_ver` +1（只影响 `compiledHash`） |
| **切分算法变更** | 是 | 新 `adaptation_version`，旧方案保留（不影响 `sourceSpecHash`） |
| **hash payload 变更** | 是 | `specVersion` +1；旧产物的 hash 无法复算，必须保留原值不重算 |

**`spec_version` 管数据形状，`compiler_ver` 管编译逻辑，`adaptation_version` 管切分方案**——三者必须分开，否则无法判断"产物不同是数据变了、切法变了，还是程序变了"。

## 十一、本轮的明确不做

| 项 | 原因 |
|---|---|
| 实现 Compiler | 任务书禁止；且 hash 契约需先评审 |
| 实现连续性引擎 | 同上 |
| 全局最优切分（bin-packing） | 收益低于多一次切镜的接缝代价，且会引入跨镜重排，违反"镜序不变" |
| 分块 hash 拼接 | 无法检测镜的插入/删除 |
| 自动补 `cam_pos` | 从文本方位推坐标 = 伪造确定状态（`D01-04 §6.4`） |
| 把 unknown 当合法 | 会让"没数据"变成"全绿" |
