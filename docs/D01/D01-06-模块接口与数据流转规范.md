### 2.3 约束

- **只写 `shot_states`**，冲突不写回 `story_shots`；
- 确定性：同输入必得同状态（`hash` 可校验）；

## 三、适配层：切分与片段完整性

### 3.1 职责与产物

按 TargetProfile 把 Shot 序列切成单元，产出**一个可版本化的适配方案**（`render_adaptations`）及其单元与片段。

**不属于任何编译器**——否则两编译器会切出不同单元，导演分镜就没有唯一适配记录了。

### 3.2 适配方案（P0-02 新增）

一个 `adaptation` = 一次完整的切分结果，身份是四元组：

```
(project_id, chapter_id, track, profile_ver, adaptation_version)
```

| 触发新版本的场景 | 处理 |
|---|---|
| 第一次给某章某轨道做适配 | `adaptation_version = 1`，`status='active'` |
| 同一 `track` 换 `profile_ver`（SD2.5 → SD2.0） | 新 adaptation，`version = 1`（profile 不同，是另一条序列） |
| 同一 `track` 同一 `profile` 重新切分（改了 `seamPolicy`、改了最短单元） | `adaptation_version +1`；旧方案 `status='superseded'`、`superseded_by=<新id>`，**行不删** |
| 分镜被修改后重切 | 同样 +1 版本；旧方案保留，并在 `source_spec_hash` 上留痕，便于回答"这版切分是对哪版分镜做的" |

**关键**：旧方案保留，意味着同一个 Shot 在同一 `track/profile` 下会同时存在**多套片段划分**。因此：

> **片段完整性校验的作用域是「单个 adaptation」，不是「单个 shot」。**
> 跨 adaptation 的片段重叠是**合法的**（它们是不同版本的方案），不能拿来判 `FRAG_OVERLAP`。

V2 的唯一索引 `uq_ru_no (project_id, track, unit_no)` 无法容纳多版本（新版本会产生相同 `unit_no` → 唯一冲突），V3 改为 `(adaptation_id, unit_no)`。详见 `D01-05 §4.8`。

### 3.3 切分算法（P0-03 重写，可执行）

#### 3.3.1 输入契约

```js
/**
 * @param {Shot[]} shots       按 global_no 升序，含 story_duration / is_cut_point / actions[]
 * @param {Profile} profile    { max, shortFloor, minSlice, maxUnits? }
 * @param {object} seamPolicy  { mode, tailHold }   // 只影响单元级拼接策略，不参与切点计算
 * @returns {{ ok: true, units: Unit[], warnings: Warning[] }
 *          | { ok: false, code: string, shotId: string, detail: object }}
 */
export function planAdaptation({ shots, profile, seamPolicy }) {}
```

`Profile` 三个数值的含义与来源：

| 字段 | 含义 | 取值来源 | 例（h3.v1） |
|---|---|---|---|
| `max` | 单次生成时长上限 | TargetProfile（模型能力） | 15 |
| `shortFloor` | 单元最短可接受时长 | TargetProfile（太短则画面无信息） | 5 |
| `minSlice` | 镜内切出的最小片段 | TargetProfile（<2s 的片段模型接不住） | 2.0 |

**切点集合**（唯一来源，不得临时发明）：

```
cuts(shot) = { 0, shot.story_duration } ∪ { a.t_to | a ∈ shot.actions }
```

- 只取 `t_to`（动作**结束**点）。`t_from` 是动作**起手**，切在这里等于把动作劈成两半；
- `is_cut_point` 只作用于**镜与镜之间**的边界，不产生镜内切点；
- 切点必须精确匹配动作的 `t_to`（容差 `EPS=1e-6`），不允许"四舍五入到最近的动作"。

#### 3.3.2 算法

```js
const EPS = 1e-6;

function planAdaptation({ shots, profile, seamPolicy }) {
  const { max, shortFloor, minSlice } = profile;
  const units = [];
  let cur = null;

  const open  = () => { cur = { unitNo: units.length + 1, items: [], dur: 0 }; units.push(cur); };
  const close = () => { cur = null; };
  const put   = (s, a, b) => {
    cur.items.push({ shotId: s.id, tFrom: a, tTo: b, splitReason: (a > EPS || b < s.story_duration - EPS) ? 'oversize' : '' });
    cur.dur += (b - a);
  };

  for (const s of shots) {
    const D = s.story_duration;
    let consumed = 0;

    while (consumed < D - EPS) {
      if (!cur) open();
      const remain = D - consumed;
      const room   = max - cur.dur;

      // ① 整段剩余装得下 → 放入，本镜结束
      if (remain <= room + EPS) { put(s, consumed, D); consumed = D; break; }

      // ② 剩余空间不足一个片段 → 关单元，下轮在新单元里放
      if (room < minSlice + EPS) { close(); continue; }

      // ③ 在 [consumed+minSlice, consumed+room] 内找最大的合法切点
      const cut = pickLegalCut(s, consumed + minSlice, consumed + room);

      if (cut === null) {
        // 本单元内切不了。
        if (cur.items.length === 0) {
          // 空单元都放不下 → 该镜本身超限且无合法断点 → 适配失败，不硬切
          return { ok: false, code: 'ADAPT_NO_LEGAL_CUT', shotId: s.id,
                   detail: { storyDuration: D, max, minSlice, legalCuts: legalCuts(s) } };
        }
        close(); continue;      // 关掉当前单元，换个新单元再试（新单元 room 更大）
      }

      put(s, consumed, cut);
      consumed = cut;
      close();                  // 切完即接近满，关单元；剩余部分进下一单元
    }
  }

  // 尾单元处理
  if (units.length >= 2) {
    const last = units[units.length - 1], prev = units[units.length - 2];
    if (last.dur < shortFloor - EPS && prev.dur + last.dur <= max + EPS) {
      prev.items.push(...last.items);
      prev.dur += last.dur;
      units.pop();
    }
  }

  const warnings = [];
  const tail = units[units.length - 1];
  if (tail && tail.dur < shortFloor - EPS) {
    warnings.push({ code: 'SHORT_UNIT', unitNo: tail.unitNo, dur: tail.dur,
                    msg: `尾单元 ${tail.dur}s 低于最短 ${shortFloor}s，且无法并入前一单元`,
                    suggest: '缩短上一镜或延长尾镜，或接受该单元（出片后可能信息量不足）' });
  }

  // 单元号重排（尾合并后可能缺号）
  units.forEach((u, i) => { u.unitNo = i + 1; });
  return { ok: true, units, warnings };
}

function legalCuts(s) {
  const set = new Set([0, s.story_duration]);
  for (const a of s.actions || []) set.add(round6(a.t_to));
  return [...set].filter(c => c >= -EPS && c <= s.story_duration + EPS).sort((x, y) => x - y);
}

function pickLegalCut(s, lo, hi) {
  const cands = legalCuts(s).filter(c => c >= lo - EPS && c <= hi + EPS && c > EPS && c < s.story_duration - EPS);
  return cands.length ? cands[cands.length - 1] : null;   // 取最大 → 尽量装满
}
```

**为什么取最大切点**：单元越满，单元数越少，出片次数越少（成本与漂移风险都更低）。取最小切点会切出大量短单元。

**为什么不用 bin-packing 求全局最优**：切点受动作约束，可行解空间是每镜若干离散偏移，贪心在"每镜切点独立"的前提下已经是局部最优；全局最优需要跨镜重新分配（把 sh_03 的尾巴挪到下一单元换取 sh_06 完整），但这会**增加一次切镜**，从而多一个接缝，代价高于收益。这是权衡，不是最优解，已在 `D01-09 §未决` 记录。

|---|---|---|

| sh_02 | 5.5 | 3.0 |
| sh_03 | 7.0 | 3.5, 6.0 |
| sh_04 | 4.0 | — |

逐步：

| 步骤 | 单元 | 动作 | acc |
|---|---|---|---|
| 1 | U1 | sh_01 整段 (0,6.0) | 6.0 |
| 2 | U1 | sh_02 整段 (0,5.5) | 11.5 |
| 3 | U1 | sh_03 整段 (0,7.0) | 18.5 |
| 4 | U1 | sh_04 整段 (0,4.0) | 22.5 |

校验：

```
Σfragment(U1) = 6.0+5.5+7.0+4.0+5.0+2.0 = 29.5 ≤ unit_duration(29.5) ≤ max(30)   ✓
Σfragment(U2) = 4.0+5.5+4.5 = 14.0 ≤ max(30)                                       ✓
sh_06 片段 (0,2.0)+(2.0,6.0) 覆盖 [0,6.0]，不重叠，切点 2.0 ∈ 动作 t_to          ✓
```

注意第 6 步：若 `room` 是 1.0（< `minSlice` 1.5），算法走分支②关单元，sh_06 完整进 U2，结果会变成 U1=27.5 / U2=16.0——**不会**切出 1.0s 的碎片。

#### 3.3.4 算例 B：H3 15s 上限下的超长镜头（修正 V2 的算术错误）

`profile = h3.v1`（`max=15, shortFloor=5, minSlice=2.0`）

| 镜 | 时长 | 动作 `t_to` |
|---|---|---|
| sh_18 | 4.0 | 1.5 |
| sh_19 | 6.0 | 3.0 |
| **sh_20** | **20.0** | 3.0, 7.0, 11.5, 16.0 |
| sh_21 | 5.0 | 2.5 |

逐步：

| 步骤 | 单元 | 动作 | acc |
|---|---|---|---|
| 1 | U1 | sh_18 (0,4.0) | 4.0 |
| 2 | U1 | sh_19 (0,6.0) | 10.0 |
| 3 | U1 | sh_20 剩 20.0 > room 5.0；`pickLegalCut(2.0, 5.0)` → 候选 {3.0} → **3.0** | 13.0，关 U1 |
| 4 | U2 | sh_20 剩 17.0 > room 15.0；`pickLegalCut(5.0, 18.0)` → 候选 {7.0, 11.5, 16.0} → **16.0** | 13.0，关 U2 |
| 5 | U3 | sh_20 剩 (16.0,20.0)=4.0 | 4.0 |
| 6 | U3 | sh_21 (0,5.0) | 9.0 |

结果：**U1 = 13.0 / U2 = 13.0 / U3 = 9.0**。

```
片段：sh_20 (0,3.0) + (3.0,16.0) + (16.0,20.0) = 3.0+13.0+4.0 = 20.0 = story_duration   ✓
无重叠、无缺口、切点全部 ∈ {3.0,7.0,11.5,16.0}                                          ✓
U1 13.0 ≤ 15  U2 13.0 ≤ 15  U3 9.0 ≤ 15                                                 ✓
尾单元 9.0 ≥ shortFloor 5                                                               ✓
```

**V2 的错误必须记下来**（这是本轮 P0-03 的直接证据）：

> V2 `D01-06 §3.5` 给的是 `sh_20 (0,9.0)` + `(9.0,20.0)`，然后 U3 = `sh_19 6.0 + sh_20 9.0`、U4 = `sh_20 11.0 + sh_21 5.0`。
> 其中 **U4 = 11.0 + 5.0 = 16.0 > 15**，超限 1 秒；且 `9.0` 这个切点不在 sh_20 的任何动作 `t_to` 上（动作断点是 3/7/11.5/16），**切在了动作中段** —— 同时违反了"单元不得超 max"和"不得劈开动作"两条自定规则。
> 根因：V2 的伪代码写的是 `acc += 截取长度`，但没定义"截取长度怎么算"，示例是手写数字而非算法产出。**伪代码与示例不对应，示例就没人验算。**

### 3.4 片段完整性校验（按 adaptation 执行）

```js
/**
 * 作用域：单个 adaptation
 * @returns {{ ok: boolean, errors: [], warnings: [] }}
 */
export function verifyAdaptation({ adaptationId }) {
  const errors = [];
  const units  = selectUnits(adaptationId);              // status ∈ active|superseded
  const shots  = uniqueShotsOf(units);

  for (const u of units) {
    // U-1 单元不超上限
    if (u.unitDuration > u.profileMax + EPS)
      errors.push({ code: 'UNIT_OVERFLOW', unitId: u.id, dur: u.unitDuration, max: u.profileMax });

    // U-2 单元时长 ≥ 片段之和；差额只允许是尾镜定格，且不得过大
    const sum = u.items.reduce((n, f) => n + (f.tTo - f.tFrom), 0);
    if (u.unitDuration < sum - 0.01)
      errors.push({ code: 'UNIT_DURATION_MISMATCH', unitId: u.id, sum, declared: u.unitDuration,
                    msg: '声明时长小于片段之和，片段装不进去' });
    const pad = u.unitDuration - sum;
    if (pad > (u.tailHoldMax ?? 1.0) + 0.01)
      errors.push({ code: 'UNIT_PADDING_EXCESS', unitId: u.id, pad, allowed: u.tailHoldMax ?? 1.0,
                    msg: '片段之和远小于单元时长，多出的时长没有内容依据' });

    // U-3 单元内顺序连续
    const ord = u.items.map(f => f.orderNo);
    for (let i = 0; i < ord.length; i++)
      if (ord[i] !== i + 1) errors.push({ code: 'UNIT_ORDER_BROKEN', unitId: u.id });
  }

  for (const s of shots) {
    const frags = fragsOf(adaptationId, s.id).sort((a, b) => a.tFrom - b.tFrom);

    // F-1 覆盖起点与终点
    if (!frags.length) { errors.push({ code: 'FRAG_MISSING_SHOT', shotId: s.id }); continue; }
    if (frags[0].tFrom > EPS) errors.push({ code: 'FRAG_GAP_HEAD', shotId: s.id, at: frags[0].tFrom });
    if (frags.at(-1).tTo < s.storyDuration - EPS)
      errors.push({ code: 'FRAG_GAP_TAIL', shotId: s.id, at: frags.at(-1).tTo, want: s.storyDuration });

    // F-2 相邻片段首尾相接（不重叠、不遗漏）
    for (let i = 1; i < frags.length; i++) {
      const d = frags[i].tFrom - frags[i - 1].tTo;
      if (d > EPS)  errors.push({ code: 'FRAG_GAP', shotId: s.id, from: frags[i-1].tTo, to: frags[i].tFrom });
      if (d < -EPS) errors.push({ code: 'FRAG_OVERLAP', shotId: s.id, at: frags[i].tFrom });
    }

    // F-3 不越出原生时长
    for (const f of frags) {
      if (f.tFrom < -EPS || f.tTo > s.storyDuration + EPS || f.tTo <= f.tFrom)
        errors.push({ code: 'FRAG_OUT_OF_RANGE', shotId: s.id, tFrom: f.tFrom, tTo: f.tTo, dur: s.storyDuration });
      // F-4 切点必须落在合法切点集合
      if (!isLegalCut(s, f.tTo) && f.tTo < s.storyDuration - EPS)
        errors.push({ code: 'FRAG_CUT_MID_ACTION', shotId: s.id, at: f.tTo });
    }
  }

  // F-5 单元跨场景（只警告，不失败）
  const warnings = units.filter(u => crossesScene(u)).map(u => ({ code: 'UNIT_CROSS_SCENE', unitId: u.id }));

  return { ok: errors.length === 0, errors, warnings };
}
```

**必须强调的执行范围**：

| 检查 | 作用域 | 跨 adaptation 时 |
|---|---|---|
| F-1 ~ F-4（片段补集） | 单 adaptation 内的**该 shot 全部片段** | **允许重叠**，不得报错 |
| U-1 ~ U-3（单元约束） | 单 unit | — |
| 跨 adaptation 一致性 | 不做 | 它们是不同版本，本就不同 |

错误码一览（`D01-09` 编号索引）：

| code | 含义 | 处置 |
|---|---|---|
| `ADAPT_NO_LEGAL_CUT` | 整镜超 max 且无合法动作断点 | **适配失败**，返回给创作者：拆镜或延长/缩短，不得硬切 |
| `UNIT_OVERFLOW` | 单元超 profile.max | 算法 bug，拒绝落库 |
| `UNIT_DURATION_MISMATCH` | 声明时长 < 片段之和 | 拒绝落库 |
| `UNIT_PADDING_EXCESS` | 声明时长 ≫ 片段之和（差额超过 `tailHoldMax`） | 拒绝落库 |
| `FRAG_GAP` / `FRAG_GAP_HEAD` / `FRAG_GAP_TAIL` | 片段有缺口 | 拒绝落库 |
| `FRAG_OVERLAP` | 同 adaptation 内重叠 | 拒绝落库 |
| `FRAG_OUT_OF_RANGE` | 越出 `[0, story_duration]` | 拒绝落库 |
| `FRAG_CUT_MID_ACTION` | 切点劈开动作 | 拒绝落库 |
| `SHORT_UNIT` | 尾单元低于 shortFloor | 警告，可落库 |
| `UNIT_CROSS_SCENE` | 单元跨 2 场景 | 警告（`D01-01 §3.7` 允许但标风险） |

### 3.5 不可切时怎么办（明确拒绝）

`ADAPT_NO_LEGAL_CUT` 是**正常返回**，不是异常。典型场景：一个 20s 长镜头全程一个连续长动作（无 `t_to` 断点），H3 上限 15s。

返回给创作者的三条处置建议（不自动选）：

1. 在动作设计上**补一个可断点**（自然的动作收势），这属于改创作态，必须人工决定；
2. **拆镜**（把 20s 拆成两个导演镜，各自有独立构图），这是导演决策；
3. **换 profile**（该轨道不可用 → 用支持更长时长的模型）。

**禁止**：截断到 15s 丢掉 5s 内容、拉伸动作、加速播放。这三种都会破坏导演设计，而 `D01` 的核心原则是"适配不改变创作"。

## 四、三种哈希（P0-01 重写）

### 4.1 为什么必须是三种

V2 只有一个 `sourceSpecHash`，而它的 payload 里包含 `unit.track` / `profile_ver` / `unit_duration` / `fragments`。后果：

- 同一份分镜在 Seedance 和 H3 下 `track` 必然不同 → **两个 hash 必然不同**；
- V2 却把 `H-21「双编译器同输入两 sourceSpecHash 逐字相同」` 写成 CI 断言 → **这条断言在 V2 的设计下永远失败**；
- V2 的 `H-19「改 track → hash 变」`、`H-20「改 fragments → hash 变」` 进一步把这个错误固化成"预期行为"。

也就是说：**V2 声称"能证明同源"，但它定义的函数在结构上就不可能输出同源结果。** 这是本轮最重的一处定义冲突。

正确做法是把三件事分开：**导演做了什么 / 怎么切成片 / 用什么程序编译**。

```
┌─────────────────────────┐      ┌──────────────────────────┐
│  L0 创作态                │      │  L1 适配态                 │
│  ShotSpec + 动作 + 空间    │      │  track / profile / 片段    │
└───────────┬─────────────┘      └────────────┬─────────────┘
            │                                  │
     sourceSpecHash                     adaptationHash
            │                                  │
            └──────────────┬───────────────────┘
                           ▼
                   compiledHash
              （+ compilerVer + 编译参数）
```

三个 hash **相互正交**：任一维度变化只影响自己及其下游。

| 维度 | hash | 回答的问题 |
|---|---|---|
| 创作 | `sourceSpecHash` | 这两条片子拍的是不是同一份分镜？ |
| 适配 | `adaptationHash` | 切分方案有没有变？ |
| 编译 | `compiledHash` | 产物是不是同一版程序在同参数下的结果？ |

### 4.2 `sourceSpecHash` · 只覆盖导演语义

```js
function sourceSpecHash({ scenes, shots, assets }) {
  const payload = {
    hashKind: 'd01.source',
    specVersion: 3,

    // —— 场景依赖（坐标基线、固定物、轴线、光线）——
    scenes: scenes
      .map(sc => canonical(sc, [
        'scene_id','scene_key','coord_system','fixtures','entries',
        'axis_lock','power_geometry','crowd_switch','time_of_day','lighting_base'
      ]))
      .sort((a, b) => String(a.scene_key).localeCompare(String(b.scene_key))),

    // —— 镜头（按 global_no 升序）——
    shots: shots
      .slice()
      .sort((a, b) => a.global_no - b.global_no)
      .map(s => ({
        // A 标识：只保留影响剪辑位置的编号，不含 id
        no: s.global_no, shotNo: s.shot_no, sceneKey: s.scene_key,
        prevShotNo: s.prev_shot_no ?? null,

        // B 剧作意图
        purpose: s.purpose, dramaticValue: s.dramatic_value, infoDelta: s.info_delta,
        dialogueFunction: s.dialogue_function, isInsert: !!s.is_insert,

        // C 画面
        visual: s.visual_content, composition: s.composition, lighting: s.lighting,

        // D 摄影（14 字段全部）
        size: s.shot_size, dir: s.cam_direction, height: s.cam_height,
        roll: num(s.cam_roll_deg), camPos: vec(s.cam_pos), camTarget: s.cam_target,
        camDist: num(s.cam_distance_m), lens: num(s.lens_mm), fov: num(s.fov_deg),
        movement: s.movement, amp: s.movement_amp, camPath: arr(s.cam_path),
        compRule: s.composition_rule, camNote: s.cam_note,

        // F 声音（6 字段）
        dialogue: s.dialogue, speakers: arr(s.speakers), narration: s.narration,
        sfx: s.sfx, musicCue: s.music_cue, voiceIds: sorted(s.voice_ids),

        // J 时间（5 字段；duration 是导演时长，不是单元时长）
        duration: num(s.story_duration), slices: arr(s.time_slices),
        ramp: s.speed_ramp, cut: !!s.is_cut_point, timeJump: !!s.time_jump,

        // G 空间（逐人，按 character_id 排序）
        blockings: (s.blockings || [])
          .map(b => ({ char: b.character_id, pos: b.position_abs, xy: vec(b.norm_xyz),
                       posTrack: arr(b.position_track), anchor: b.anchor_object, behind: b.behind_object,
                       facing: b.facing, gaze: b.gaze_target, posture: b.posture,
                       dist: num(b.distance_to_camera), occ: b.occlusion,
                       hand: b.hand_state, task: b.current_task,
                       inFrame: !!b.in_frame, power: b.power_level, anchorObj: b.instance_anchor }))
          .sort((a, b) => String(a.char).localeCompare(String(b.char))),

        // E 动作（20 业务字段，按 t_from + actor 排序）
        actions: (s.actions || [])
          .map(a => ({ actor: a.actor_id, type: a.action_type, primary: !!a.is_primary, tier: a.tier,
                       init: a.init_state, trigger: a.trigger_json, path: a.path_json, force: a.force_json,
                       speed: a.speed_json, power: a.power, cog: a.cog, parts: arr(a.body_parts),
                       contact: a.contact_json, result: a.result_json, follow: a.follow_through,
                       recovery: a.recovery, end: a.end_state, sync: a.sync_json,
                       tFrom: num(a.t_from), tTo: num(a.t_to) }))
          .sort((a, b) => (a.tFrom - b.tFrom) || String(a.actor).localeCompare(String(b.actor))),

        // H 首尾状态 + 可靠性（unknown 与 known 必须区分，否则"补一个猜测值"不改变 hash）
        stateIn: canonState(s.state_in), stateInMeta: canonMeta(s.state_in_meta),
        stateOut: canonState(s.state_out), stateOutMeta: canonMeta(s.state_out_meta),

        // I 资产引用 + 内容指纹
        assets: (s.assets || [])
          .map(x => ({ id: x.asset_id, role: x.role, order: x.order_no,
                       variant: x.variant_of, fp: assets[x.asset_id]?.fingerprint || '',
                       fpLevel: assets[x.asset_id]?.fpLevel || 'meta' }))
          .sort((a, b) => String(a.role).localeCompare(String(b.role)) || String(a.id).localeCompare(String(b.id)))
      }))
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

**明确排除**（这些字段变了，`sourceSpecHash` 必须不变）：

| 排除项 | 理由 |
|---|---|
| `track`、`profile_ver`、`unit_duration`、`unit_no`、`seam` | 属于适配决策，不进创作语义 |
| `render_unit_shots.t_from/t_to`、`split_reason` | 切分结果，不是导演意图 |
| `shot.id`、`created_at`、`updated_at`、`qc_status`、`fill_confidence`、`spec_source` | 非语义 |
| `prompt_packages.*`、`render_attempts.*` | 下游产物 |

**注意 `seam` 的归属判断**：`seam`（段缝策略）影响"这一镜是不是单元收尾、要不要加定格句"。哪一镜成为单元收尾是**切分决定的**，不是导演决定的——同一镜在 30s 切法里是段中，在 15s 切法里可能是段尾。所以 `seam` 归 `adaptationHash`。V2 把它放进 `unit` 再进 source，是错的。

**`state_in_meta` / `state_out_meta` 必须进 hash**：否则"把 unknown 悄悄改成 known 的猜测值"不会改变 hash，同源证明就形同虚设。

### 4.3 `adaptationHash` · 只覆盖切分方案

```js
function adaptationHash({ adaptation, units, fragments }) {
  const payload = {
    hashKind: 'd01.adaptation',
    adaptationVersion: adaptation.adaptation_version,
    track: adaptation.track,
    profileVer: adaptation.profile_ver,
    profileParams: {                       // profile 的关键能力参数，换数值即换适配
      max: num(adaptation.profile_max),
      shortFloor: num(adaptation.profile_short_floor),
      minSlice: num(adaptation.profile_min_slice)
    },
    seamPolicy: adaptation.seam_policy_json,   // 段缝策略（含 tailHold）
    units: units
      .slice().sort((a, b) => a.unit_no - b.unit_no)
      .map(u => ({
        unitNo: u.unit_no,
        unitDuration: num(u.unit_duration),
        shots: fragments
          .filter(f => f.unit_id === u.id)
          .sort((a, b) => a.order_no - b.order_no)
          .map(f => ({ shotId: f.shot_id, orderNo: f.order_no,
                       tFrom: num(f.t_from), tTo: num(f.t_to), reason: f.split_reason }))
      }))
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

**不包含 `sourceSpecHash`**：这是刻意的。若把源 hash 混进来，"切分方案本身有没有变"就无法单独回答。组合关系由 `compiledHash` 承担。

### 4.4 `compiledHash` · 组合

```js
function compiledHash({ sourceHash, adaptationHash, compilerVer, compilerParams }) {
  const payload = {
    hashKind: 'd01.compiled',
    sourceSpecHash: sourceHash,
    adaptationHash,
    compilerVer,
    compilerParams: canonical(compilerParams, [
      'format',          // 'ref2va' | 't2va'
      'language',        // 'en' | 'zh'
      'aspectRatio',
      'fps',
      'refPackPolicy',   // 'ordered' | 'by-role'
      'seamInjection'    // true | false
    ])
  };
  return 'sha256:' + sha256(canonicalStringify(payload));
}
```

用途：
- 产物幂等（同 hash 不重复插 `prompt_packages`）；
- 回答"这条片子是哪套分镜 + 哪套切分 + 哪个编译器版本产的"。

**三者关系（可判定的推论）**：

| 操作 | source | adaptation | compiled |
|---|---|---|---|
| 改一句台词 | **变** | 不变（若切点未受影响） | **变** |
| 改切分（同 profile 重切） | 不变 | **变** | **变** |
| 换 track（sd → h3） | **不变** | **变**（不同 adaptation） | **变** |
| 换 profile（sd25 → sd20） | **不变** | **变** | **变** |
| 升编译器版本 | 不变 | 不变 | **变** |
| 改 `seam` | 不变 | **变** | **变** |

**同源验证示例**（P0-01 强制要求）：

```
分镜 F1，8 镜，总长 38.0s

Seedance 适配：
  adaptation ad_sd_1 (track=seedance, profile=seedance25.v1, ver=1)
  units: 29.5 / 8.5                     → adaptationHash = sha256:7c1e…
  compile(compilerVer=1.0.0, format=ref2va)
  → sourceSpecHash  = sha256:3f9a…   ← 同一个
  → compiledHash    = sha256:b84d…

H3 适配：
  adaptation ad_h3_1 (track=h3, profile=h3.v1, ver=1)
  units: 14.5 / 13.0 / 10.5             → adaptationHash = sha256:e0a2…
  compile(compilerVer=1.0.0, format=ref2va)
  → sourceSpecHash  = sha256:3f9a…   ← **逐字相同，这就是同源证明**
  → compiledHash    = sha256:1d77…

断言：
  sd.sourceSpecHash === h3.sourceSpecHash        ✓ 同源
  sd.adaptationHash !== h3.adaptationHash        ✓ 适配不同
  sd.compiledHash   !== h3.compiledHash          ✓ 产物不同
```

### 4.5 规范化序列化（三者共用）

| 规则 | 实现 | 原因 |
|---|---|---|
| 键排序 | 所有对象键按 UTF-16 字典序输出 | DB 返回键序不稳定 |
| 整数 | 去小数（`4.0` → `4`） | `4` 与 `4.0` 必须同 hash |
| 浮点 | 保留 6 位并去尾零（`4.500000` → `4.5`，`0.30000000000004` → `0.3`） | 浮点误差不得影响 hash |
| `null` / `undefined` | 统一 `null`，**保留键** | 省略与 null 语义不同 |
| 空集合 | `[]` / `{}` 保留 | 同上 |
| 字符串 | NFC 归一化 + 去首尾空白 + **不去内部空白** | 内部空格是语义（台词停顿） |
| 有序数组 | `time_slices`、`cam_path`、`position_track` 保原序 | 顺序即语义 |
| 无序数组 | `blockings`（按 char）、`actions`（按 tFrom+actor）、`assets`（按 role+id）、`voice_ids`（字典序）、`scenes`（按 scene_key） | 插入顺序不应影响 |
| 缺失字段 | 视为 `null`（不视为"不存在"） | 加字段不改变旧数据 hash |

`canonState` / `canonMeta`：按 `chars.<id>.<field>` 的字典序展开成一维键值对，保证嵌套对象的键序无关。

- R-01 ~ R-24 为纯函数单测，输入用固定 fixture（不依赖数据库）；

- 另加 R-26（负向）：把 `fragments` 混入 source payload 的实现必须被 code review 拒绝——这在 V2 是设计，在 V3 是反例。

### 4.7 `sourceSpecHash` 的作用域

一个 hash 对应**一章的全部分镜**（按 `global_no` 排序）。跨章的镜不参与同一 hash。

若只修改了第 30 镜，第 1–29 镜的 `state_out` 会被增量复用，但 **hash 必须整体重算**（因为 payload 包含全体 shots）。重算是毫秒级，不做"分块 hash 拼接"——分块拼接会让"插入一镜"无法被检测到。

## 五、QC（质检）

### 5.1 接口

## 七、DAG 调度

| 节点 | 输入 | 输出 | 幂等键 |
|---|---|---|---|
| `plan_adaptation` | shots + profile + seamPolicy | adaptation + units + fragments | `(chapterId, track, profileVer, sourceSpecHash, adaptationVersion)` |
| `compile` | adaptation + unit + track | package | `(unitId, track, compiledHash)` |

## 十、接口稳定性

| 变更 | 破坏性 | 处理 |
|---|---|---|
| 加可选字段 | 否 | 直接加，`spec_version` 不变 |
| 加必填字段 | 是 | `spec_version` +1，旧数据按 S 级降级 |
| 加枚举值 | 否（读者）/ 是（switch） | 编译器与 QC 必须"未知值 → WARN 不崩" |
| 删枚举值 | 是 | 禁止，只标 deprecated |
| 表结构变更 | 视情况 | 只加列/加表 |
| 编译器逻辑变更 | 是 | `compiler_ver` +1（只影响 `compiledHash`） |
| **切分算法变更** | 是 | 新 `adaptation_version`，旧方案保留（不影响 `sourceSpecHash`） |
| **hash payload 变更** | 是 | `specVersion` +1；旧产物的 hash 无法复算，必须保留原值不重算 |

**`spec_version` 管数据形状，`compiler_ver` 管编译逻辑，`adaptation_version` 管切分方案**——三者必须分开，否则无法判断"产物不同是数据变了、切法变了，还是程序变了"。

## 十一、本轮的明确不做

| 项 | 原因 |
|---|---|
| 实现 Compiler | 任务书禁止；且 hash 契约需先评审 |
| 实现连续性引擎 | 同上 |
| 全局最优切分（bin-packing） | 收益低于多一次切镜的接缝代价，且会引入跨镜重排，违反"镜序不变" |
| 分块 hash 拼接 | 无法检测镜的插入/删除 |
| 自动补 `cam_pos` | 从文本方位推坐标 = 伪造确定状态（`D01-04 §6.4`） |
| 把 unknown 当合法 | 会让"没数据"变成"全绿" |
