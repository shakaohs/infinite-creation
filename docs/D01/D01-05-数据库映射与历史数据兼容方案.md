# D01-05 数据库映射与历史数据兼容方案

> 依赖：`D01-02/03/04`（字段定义）
> 约束（任务书）：**不允许修改数据库、不允许删除或重命名现有文件、不能破坏性迁移**。本文只出 DDL 与迁移步骤草案。
> 现状数据：`data/ic.db`，12 张表、66 条分镜、143 条资产、2,805 条变更日志（审计 08 实测）。

---

## 一、兼容总原则

| # | 原则 | 具体做法 |
|---|---|---|
| C1 | **只加不改** | 现有列一律不动（不改名、不改类型、不改语义），新增一律用新表/新列 |
| C2 | **物理名不变，逻辑名可换** | `shots` 表名不动，但语义上它存的是 **RenderUnit**；给新代码一个只读视图 `render_units` |
| C3 | **旧读法必须仍然有效** | 任何旧查询（`SELECT * FROM shots WHERE chapter=?`）结果不变，66 条历史分镜照常显示 |
| C4 | **新数据双写，旧数据惰性补** | 新写入同时落 `story_shots` 与 `shots.sub_shots`；旧行不批量迁移，读取时按需生成影子数据 |
| C5 | **任何一步可回滚** | 迁移按阶段提交，每阶段都有 `--rollback` 路径；删表前必须完成数据对账 |
| C6 | **不猜** | 无法解析的历史字段留空（`confidence=0`），不生成"看起来合理"的假数据 |

## 二、新增表（9 张，全部 `CREATE TABLE IF NOT EXISTS`）

### 2.1 `story_shots`（Shot + ShotSpec 主体）

```sql
CREATE TABLE IF NOT EXISTS story_shots (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL,
  chapter_id      TEXT NOT NULL,              -- 章节真 id（不用标题字符串）
  render_unit_id  TEXT DEFAULT '',            -- → shots.id（旧表=渲染单元）
  scene_key       TEXT NOT NULL,
  scene_id        TEXT DEFAULT '',
  shot_no         INTEGER NOT NULL,           -- 场内镜号
  global_no       INTEGER NOT NULL,           -- 全集镜号
  beat_key        TEXT DEFAULT '',
  prev_shot_id    TEXT DEFAULT '',

  -- B 剧作意图
  purpose         TEXT DEFAULT '',            -- establish/advance/react/reveal/turn/close/insert
  dramatic_value  INTEGER DEFAULT 0,          -- -10..10
  info_delta      TEXT DEFAULT '',
  dialogue_function TEXT DEFAULT '',

  -- C 画面
  visual_content  TEXT DEFAULT '',
  composition     TEXT DEFAULT '',
  lighting        TEXT DEFAULT '',

  -- D 摄影六要素
  shot_size       TEXT DEFAULT '',            -- 9 档枚举
  cam_direction   TEXT DEFAULT '',            -- front/three_quarter/profile/over_shoulder/pov
  cam_height      TEXT DEFAULT '',            -- eye/slight_low/low/high/extreme_low/extreme_high/bird_eye/dutch
  lens_mm         INTEGER DEFAULT 0,
  movement        TEXT DEFAULT 'static',      -- 21 值枚举
  movement_amp    TEXT DEFAULT 'none',
  composition_rule TEXT DEFAULT '',
  cam_note        TEXT DEFAULT '',

  -- F 声音
  dialogue        TEXT DEFAULT '',
  speaker_ids     TEXT DEFAULT '[]',
  narration       TEXT DEFAULT '',
  sfx             TEXT DEFAULT '',
  music_cue       TEXT DEFAULT '',
  voice_ids       TEXT DEFAULT '[]',

  -- I 资产
  character_ids   TEXT DEFAULT '[]',
  scene_ids       TEXT DEFAULT '[]',
  prop_ids        TEXT DEFAULT '[]',
  costume_ids     TEXT DEFAULT '[]',
  age_ids         TEXT DEFAULT '[]',
  audio_ids       TEXT DEFAULT '[]',

  -- J 时间
  story_duration  REAL DEFAULT 0,
  time_slices     TEXT DEFAULT '[]',
  speed_ramp      TEXT DEFAULT 'none',
  is_cut_point    INTEGER DEFAULT 1,

  -- 元数据
  spec_version    INTEGER DEFAULT 1,
  spec_source     TEXT DEFAULT 'ai',          -- ai / import / manual / legacy
  fill_confidence REAL DEFAULT 0,             -- 回填完整度 0..1
  qc_status       TEXT DEFAULT '',            -- ''/pass/warn/fail
  created_at      INTEGER,
  updated_at      INTEGER
);
CREATE INDEX IF NOT EXISTS idx_ss_unit   ON story_shots(project_id, render_unit_id);
CREATE INDEX IF NOT EXISTS idx_ss_scene  ON story_shots(project_id, scene_key, global_no);
CREATE INDEX IF NOT EXISTS idx_ss_chap   ON story_shots(chapter_id, shot_no);
```

**不建 `shot_specs` 独立表**：ShotSpec 与 Shot 是 1:1，拆表只会增加 JOIN 且无独立生命周期。字段多了就宽，这是可接受的代价（对比：拆表后每次读镜都要 JOIN 两次）。

### 2.6 `render_units`（视图，不加表）

```sql
CREATE VIEW IF NOT EXISTS render_units AS
SELECT
  id            AS id,
  project_id    AS project_id,
  chapter       AS chapter_title,
  scene_name    AS scene_label,
  duration      AS unit_duration,
  blocking      AS blocking_legacy,
  mode          AS mode,
  status        AS status,
  video_prompt  AS prompt_legacy,
  seam          AS seam,
  created_at, updated_at
FROM shots;
```

**为什么用视图而不是新表**：`shots` 一行就是一个渲染单元（D01-01 §1.2 已论证）。新建 `render_units` 表会导致双写双读、数据分裂。视图让新代码用新语义名读取，写入仍走 `shots`，零迁移风险。

**视图的写限制**：SQLite 视图默认不可写。写单元仍走 `Shots.create/update`，在文档层声明"= 写 render unit"即可。

CREATE TABLE IF NOT EXISTS prompt_packages (

### 3.1 处置统计

| 处置 | 列数 | 占比 |
|---|---|---|
| 原样保留 | 30 | 81% |
| 保留 + 语义重定义（值不变） | 5（`duration`/`sub_shots`/`blocking`/`video_prompt`/`seam`） | 14% |
| 标记待废弃（不删） | 1（`storyboard_sheet`） | 3% |
| 删除 / 重命名 | **0** | 0% |

**结论：零破坏。** 唯一的"语义变化"是解释层的（`duration` 从"镜头时长"解释为"单元时长"），物理值不动。

### 3.2 为什么 `shots.duration` 不能直接当 `story_duration`

一条 `shots` 行的 `duration` = 该单元总时长（如 28s），内含 5 个镜。若直接当镜时长，会得到"一个 28 秒的镜头"，与"每镜 2.5–7.5 秒"的密度规则冲突。

**必须按 `sub_shots` 时间轴切分**：

```
输入：sub_shots = "00:00-00:05 [镜头1] 中景…  00:05-00:11 [镜头2] …"
解析：正则 /(\d{2}:\d{2})-(\d{2}:\d{2})\s*\[镜头(\d+)\]/
输出：每镜 story_duration = to - from
校验：Σ story_duration ≈ shots.duration（容差 0.5s），不等则 WARN 并记录
```

`storyboard-import.js` 里已有类似解析（`parseSubShotEndSeconds`），复用它即可。

## 四、历史数据兼容：三层读取

### 4.1 读取优先级

```
getShots(unitId):
  1. SELECT * FROM story_shots WHERE render_unit_id = unitId ORDER BY shot_no
     ├ 有结果 → 用结构化数据（新路径）
     └ 无结果 → 2
  2. 解析 shots.sub_shots 生成「影子镜」（内存对象，spec_source='legacy'）
     ├ 解析成功 → 返回影子镜，UI 标「旧版分镜（未结构化）」
     └ 解析失败 → 3
  3. 返回 `[{single_shot: true, story_duration: shots.duration, ...}]`（整行视为 1 镜）
```

**影子镜不落库**（除非用户显式点"结构化为 ShotSpec"），避免一次读操作产生写副作用。

### 4.2 UI 呈现

| 数据状态 | 标记 | 可编辑 | 可用功能 |
|---|---|---|---|
| 全结构化 | 无标记 | ✅ 全字段 | 全部（越轴检测、状态继承、双轨编译） |
| 影子镜（legacy） | 🟡「旧版」 | 仅文本字段 | 提示词生成、导出 |
| 无法解析 | 🔴「无镜信息」 | 仅文本字段 | 提示词生成 |

**不假装**：旧数据不会被标成"已结构化"，也不会被强行填入猜测的枚举值。

### 4.3 回填策略（可选、分批、可中断）

回填只在用户主动触发时执行（`POST /api/projects/:id/backfill-spec`），三档：

| 档 | 动作 | 风险 | 复审要求 |
|---|---|---|---|
| **B1 只读推断** | 计算 `fill_confidence`，不写库 | 无 | 无 |
| **B2 写低置信字段** | `camera` 正则拆六要素、`blocking` 解析逐人、`speaker_ids` 从台词解析；写 `spec_source='legacy'`、`confidence<0.7` | 中（可能拆错） | 抽检 10% |
| **B3 人工确认** | UI 逐条确认后转 `manual` | 低 | 全量 |

**明确不做**：不自动生成 `shot_actions`（从叙述拆动作必然臆造）、不自动生成 `state_in/out`（由连续性引擎首次编译时求解，且标 `state_source='solved'`）。

### 4.4 `camera` 拆分规则（B2）

```
输入："中近景 · 50mm · 侧45度 · 俯拍15° · 固定"
1. 按 " · " 切分
2. 逐段匹配词表：
   中近景/近景/特写…      → shot_size
   50mm/35mm/85mm        → lens_mm
   侧45度/正面/侧面/过肩   → cam_direction
   平视/俯拍/仰拍/大仰角   → cam_height
   固定/推镜/横移/跟拍…    → movement
3. 未匹配段 → 拼进 cam_note
4. 匹配率 < 50% → confidence=0.3，标低置信
```

**先验证再批量**：抽样 50 条统计匹配率（审计 03 V-10 遗留问题），匹配率 < 80% 则放弃自动拆分，只做 B1。

## 五、迁移步骤（4 阶段，每阶段可停可回滚）

### 阶段 M0：准备（不动数据）

1. 备份：`cp data/ic.db data/ic.db.bak-<date>`（项目已有 `.bak` 惯例）；
2. 记录基线：行数、每表 md5（`SELECT count(*)` + 关键字段聚合）；
3. 建表：执行 §2 的 `CREATE TABLE/VIEW IF NOT EXISTS`（纯新增，无风险）；
4. 验证：`SELECT name FROM sqlite_master WHERE type IN ('table','view')` 应多出 10 个对象。

**回滚**：`DROP TABLE`/`DROP VIEW` 新增对象即可，旧表未动。

### 阶段 M1：影子读（只读，不写）

1. 实现 `getShots` 三层读取（§4.1），`story_shots` 为空时全走 legacy；
2. 打开 UI 标记，验证 66 条历史分镜都能正常显示；
3. 对账：`legacy 解析出的镜数` 与 `sub_shots 里的 [镜头N] 行数` 必须一致（抽样 20 条）。

**回滚**：关掉 feature flag，读路径退回旧实现。

### 阶段 M2：新写（双写）

1. `set_storyboard` 与 `importStoryboard` 改为：写 `story_shots` + 渲染 `shots.sub_shots/blocking/camera`；
2. 双写一致性校验：写完立即 `SELECT` 回读，比对渲染结果与写入值；
3. **只对新建项目启用**（`feature_flags.structured_spec = true`），历史项目保持 legacy。

**回滚**：关 flag，新数据仍可读（因为 `shots` 旧列也写了）。

### 阶段 M3：回填（可选，用户触发）

1. 按项目逐个执行 B1 → B2；
2. 每批留 `fill_confidence` 与 `qc_reports`；
3. 人工抽检通过后才允许升级为 `manual`。

**回滚**：`DELETE FROM story_shots WHERE spec_source='legacy' AND fill_confidence < 0.7 AND reviewer IS NULL` —— 只删回填产生的行，不动用户确认过的。

## 六、不丢数据的验证方法（验收必须做）

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| **行数守恒** | 迁移前后 `count(*)` 全表对比 | 旧表行数 100% 不变 |
| **字段指纹** | 对 `shots` 全部列做 `md5(group_concat(...))` | 前后一致 |
| **可读性** | 随机 10 条分镜，人工比对 UI 显示 | 文本内容逐字一致 |
| **提示词可复现** | 取 5 条有 `video_prompt` 的旧镜，重新走编译 | 生成的提示词与原文差异仅限格式 |
| **镜数对账** | `Σ 影子镜数` vs `Σ sub_shots 的 [镜头N]` | 相等（容差 0） |
| **资产引用** | `Σ *_ids 元素数` 前后对比 | 相等 |
| **回滚演练** | 演练一次 M1 回滚 | 30 分钟内可回到迁移前状态 |

## 七、旧视频提示词如何保留

现状：`shots.video_prompt`（55/66 有值）+ `video_prompt_used`。

**保留方案**：

1. **原地不动**：两列都不删、不改，历史内容可读；
2. **首次编译时归档**：某镜第一次走新编译器时，把旧 `video_prompt` 复制到 `prompt_packages`，`track='legacy'`、`format='flat'`、`compiler_ver='pre-d01'`、`compiled_hash=md5(原文)`；
3. **差异可见**：UI 提供"旧版提示词 / 新版提示词"对照，不静默替换；
4. **旧版仍可投喂**：`track='legacy'` 的 package 可以直接投喂（保持向下兼容），但会被标记「非编译产物，无溯源」。

**为什么归档而不是覆盖**：`video_prompt` 是甲方交付过的资产（真实出过片），覆盖等于销毁证据。归档后"这条片子是哪版提示词产的"才可回答。

## 八、双库兼容（SQLite / PostgreSQL）

项目现有机制：`db.js initSchema` 一份 SQL 跑两库，PG 通过 `pg-worker.mjs` 同步门面（审计 08 §5）。

新增表注意事项：

| 项 | SQLite | PostgreSQL | 处理 |
|---|---|---|---|
| `INTEGER PRIMARY KEY` | 自增 | 不自增 | 本项目主键均为 TEXT，无影响 |
| `TEXT DEFAULT '[]'` | OK | OK | — |
| `CREATE VIEW IF NOT EXISTS` | 支持 | 支持（9.6+） | — |
| `BOOLEAN` | 用 INTEGER | 用 BOOLEAN | 统一用 INTEGER 0/1 |
| `REAL` | OK | 用 DOUBLE PRECISION | 沿用现有 `db-driver` 的类型映射 |
| 部分索引 | 支持 | 支持 | — |
| `ON CONFLICT` | 3.24+ | 支持 | 沿用现有 upsert 写法 |

**建议**：DDL 走现有的 `initSchema` 追加，不引入迁移框架（避免与现有 60+ 条 `try ALTER` 机制冲突）。但必须**在文件头加 schema 版本常量**（`SCHEMA_VERSION = 2`），解决审计 08 §5 指出的"无版本号"问题。

## 九、风险与缓解

| 风险 | 触发 | 缓解 |
|---|---|---|
| 表变宽导致写入慢 | `story_shots` 40+ 列 | 单项目镜数通常 <2000，SQLite 无压力；批量写用事务 |
| 双写不一致 | 写 `story_shots` 成功、渲染 `sub_shots` 失败 | 同事务写入；失败整体回滚；回读校验 |
| 影子镜解析不准 | `sub_shots` 写法不标准 | 解析失败降级为 1 镜，标 `legacy`，不猜 |
| 回填污染数据 | B2 拆错枚举 | 只写 `confidence<0.7` 且 `spec_source='legacy'`，UI 明显标记，可一键清除 |
| 视图与表语义混淆 | 新人以为 `render_units` 可写 | 文档与代码注释双标注；写入统一走 `Shots` 模型 |
| `chapter` 标题脱章 | 用户改章节名 | 新表用 `chapter_id`；旧表提供"修复归属"工具（按 id 反查标题） |
| JSON 列无法查询 | `shots.sub_shots` 等 | 热点查询字段已拆成独立列（`norm_x/y`、`t_from/t_to`） |
