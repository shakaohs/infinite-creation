### 2.4 `sub_shots` 的真实格式（**上一版判断错误**）

上一版假设 `sub_shots` 统一为 `00:00-00:05 [镜头1] …`。实测有三种：

| 格式 | 条数 | 样例 |
|---|---|---|
| A. `[镜头N]` + `00:00` 时间码 | **13** | `00:00-00:02 [镜头1] 中景 · 50mm · 平视 · 固定。画面主体：…` |
| B. 中文分段 `0-3s：` | **37** | `0-3s：大远景，栏杆在左、游船在右后，姜知微在画面左下推车…；3-7s：镜头缓推至中景…` |
| C. 无时间分段（整段叙述） | **16** | 纯连续描述，无 `0-3s` 也无 `[镜头]` |

查询：
```sql
SELECT count(*) FROM shots WHERE sub_shots LIKE '%[镜头%';                    -- 13
SELECT count(*) FROM shots WHERE sub_shots GLOB '*[0-9]-[0-9]*s：*';         -- 37
SELECT count(*) FROM shots WHERE sub_shots NOT LIKE '%[镜头%'
  AND sub_shots NOT GLOB '*[0-9]-[0-9]*s：*'
  AND sub_shots NOT GLOB '*[0-9][0-9]:[0-9][0-9]-*';                         -- 16
```

**影响**：回填 `story_duration` 必须支持三种格式，且 C 类 16 条**无法切分**（只能整行当 1 镜，`fill_confidence=0.2`）。

### 2.5 `blocking` 的真实写法（**上一版判断错误**）

实测 13 条全部在项目 `a053dabd`（4 个项目之一），长度 119–332 字。真实格式：

```
@斯洛恩（画面左 · 背靠西侧金属护栏 · 正面朝右前方赛道 · 双手扶护栏 · 手头事务：注视赛场）；
@怀亚特（画面右 · 东侧庆祝区台阶前 · 正面对镜头 · 右手持毛巾 · 手头事务：擦汗）；
轴线锁定：斯洛恩在左、怀亚特在右，机位恒在两人连线南侧，全段禁越轴；位移仅限：无，全员原位。
```

结构 = `@角色（画面方位 · 依托/背靠 · 朝向 · 手部 · 手头事务）` 五段式 + `轴线锁定：` 句 + `位移仅限：` 句。

**两个关键事实**：

1. **用的是「画面左/右」，不是绝对方位** —— 与 `blocking-direction.md` 的"绝对方位优先"要求相反。原因：这是甲方交付稿，按拍摄习惯写；
2. **画面左右无法转物理坐标** —— 画面左右是渲染结果，同一物理位置在不同机位下会变成画面左或右。所以回填 `norm_x/y` **必须为空**（`confidence=0`），越轴检测对这些数据一律 `AXIS_UNVERIFIED`。

### 3.2 章节改标题有事务同步（**上一版说"会脱章"，已过时**）

`app/api/projects/[id]/chapters/[cid]/route.js:26-35`：

```js
// 改标题要连带迁移该章分镜的 chapter 字段（shots 按标题归属）：包一个事务，
// 避免「标题改了、部分分镜还挂在旧标题下」这种半迁移状态。
const c = tx(() => {
  const updated = Chapters.update(cid, patch);
  if (!updated) return null;
  if (patch.title !== undefined && before.title !== updated.title) {
    for (const s of Shots.list(id)) if (s.chapter === before.title) Shots.update(s.id, { chapter: updated.title });
  }
  return updated;
});
```

另外 agent 的章节更新工具（`lib/agent/tools.js:4008-4020`）**只改 novel / volume / outline，不改 title**；`lib/core/changelog.js:187` 的注释也确认这个同步逻辑存在。

**修正结论**：在基线代码下，通过 UI 或 agent 改章节标题**不会脱章**。残留风险只有"绕过 API 直接 UPDATE `chapters.title`"（如手工 SQL 或 `scripts/db-migrate.mjs` 的字段映射错误），属于运维风险而非设计缺陷。

`D01-01` 的"新表用 `chapter_id` 消除耦合"依然成立，但理由从"会脱章"改为"减少字符串依赖，避免标题唯一性等间接约束"。

### 3.3 三个"幽灵列"（**本轮最重要的代码发现**）

| 列 | 在 `initSchema` 建表语句 | 有 `ALTER TABLE ... ADD COLUMN` | 在 `Shots.create` INSERT | 在 `Shots.update` SET | 代码引用 |
|---|---|---|---|---|---|
| `blocking` | ❌ 无 | ❌ **无** | ✅ **有** | ✅ **有** | ✅ 多处 |
| `seam` | ❌ 无 | ❌ **无** | ❌ 无 | ❌ 无 | ❌ 仅 `projects.seam` 有 |
| `storyboard_sheet` | ❌ 无 | ❌ **无** | ❌ 无 | ❌ 无 | ❌ **全项目零引用** |

证据：
- `sed -n '/CREATE TABLE IF NOT EXISTS shots/,/);/p' lib/core/db.js | grep -c blocking` → **0**
- `grep -rn "ADD COLUMN blocking\|ADD COLUMN seam\|ADD COLUMN storyboard_sheet" lib app scripts` → **无匹配**（只有 `ALTER TABLE projects ADD COLUMN seam`）
- `grep -rn "storyboard_sheet" lib app studio/src` → **零匹配**

**结论与风险**：

1. **`blocking` 是代码依赖但建表缺失的列** —— `Shots.create` 的 INSERT 语句明确包含 `blocking`，若在一个由 `initSchema` **全新创建**的库上运行，INSERT 会抛 `table shots has no column named blocking`。现有 `data/ic.db` 是历史演进出来的（列由早期脚本或手工 SQL 加上），所以没暴露。
2. **`seam` / `storyboard_sheet` 是纯 DB 遗留** —— 代码既不读也不写。上一版说"`seam` 写入了锁档"是错的（那只在 `storyboard_plan.json` 与 `projects.seam`），`shots.seam` 从未被写。
3. **这是部署级隐患**，D01 不修（不改代码），但必须记录，并在实施阶段作为独立任务处理（见 §9 风险 R-1）。

### 3.4 无外键约束

`lib/core/db-driver.js:69` 只设 `journal_mode` 与 `busy_timeout`，**未执行 `PRAGMA foreign_keys = ON`**（SQLite 默认 OFF）。

因此现有"关联"全是**软关联**：`shots.character_ids` 里存了不存在的资产 id 也不会报错，只能靠应用层 `normalizeShotRefs` 清理。

**对 D01 的影响**：新表若要外键生效，必须显式 `PRAGMA foreign_keys = ON`——但这会改变现有软关联行为（历史脏数据可能突然报错）。所以 **V2 决定：新表不加 DB 级外键，改用应用层事务 + 校验**（§8.1）。

### 3.5 事务边界

`lib/core/db.js:352 tx(fn)`：
- 只接受**同步函数**（异步会抛 `ASYNC_TX`）；
- 可嵌套（`txDepth > 0` 时直接执行）；
- `BEGIN` / `COMMIT` / 异常 `ROLLBACK`。

**对 D01 的要求（V4 修正）**：新项目的一次分镜提交必须在**同一个 `tx()` 内**完成：

```
story_shots + shot_blockings + shot_actions + shot_assets
+ render_adaptations + render_units + render_unit_shots
```

**不写 `shots`**。V3 在这里留着"渲染 `shots.sub_shots`"的旧句，与本轮 §6.4 的单向投影原则冲突，已删除。原因见 §6.4：`sub_shots` 是有损文本格式，回写等于把结构化的镜级信息降级一次。

历史项目的写入路径**不变**：仍走 `Shots.create/update`，单表事务，不碰新表。两条路径按 `structured_spec` 分流，互不交叉。

### 3.6 删除策略（现状）

`Shots.remove(id)` 手动级联删 `shot_videos`，再删 `shots`，最后记 changelog。**没有 DB 级 `ON DELETE CASCADE`**。

**对 D01 的要求**：新表删除必须沿用"应用层级联 + 变更日志"，见 §8.2。

**唯一键定为 `(unit_id, shot_id)` + `(unit_id, order_no)`（V3 收紧，V4 确认为唯一版本）**：

#### 4.14.1 `tailHoldMax` 的权威归属（P1-08）

`tailHoldMax` 是"单元尾镜允许的定格延长上限"（秒）。它出现在校验里（`D01-06 §3.4` 的 `UNIT_PADDING_EXCESS`），因此必须有唯一权威来源，不能在校验代码里写 `?? 1.0` 这种隐式默认。

| 问题 | 答案 |
|---|---|
| 权威配置归属 | **TargetProfile**：`target_profiles.tail_hold_max`（全局 `config.json` 的 profile 定义） |
| 是否属于 TargetProfile | **是**。它是模型能力参数（某些模型接不住长时间定格），与 `max`/`shortFloor`/`minSlice` 同级 |
| 是否进 RenderAdaptation 快照 | **是**：`profile_tail_hold_max`。理由同其他三个参数——profile 被改后，旧方案必须仍能按当时的参数复算 |
| 是否进 `adaptationHash` | **是**：进 `profileParams`（`D01-06 §4.3`）。否则改 `tailHoldMax` 后重算 hash 不变，等于"参数变了但方案指纹没变" |
| 旧方案在 Profile 参数变化后能否独立复算 | **能**。四个参数都在方案行上快照，`adaptationHash` 只读快照，不读当前 profile |

**禁止清单**：

- 校验函数里不得出现 `u.tailHoldMax ?? 1.0` 这类兜底；
- 若方案行缺 `profile_tail_hold_max`（历史数据），按 `NULL` 处理并报 `ADAPT_PROFILE_SNAPSHOT_MISSING`（WARN），**不猜默认值**；
- `tail_hold_max` 的默认值只在**创建 profile** 时给一次（`config.json` 里写死，例如 `1.0`），之后以 profile 为准，不在代码里另设默认。

**为什么单独强调**：`UNIT_PADDING_EXCESS` 是个 FAIL 级校验。如果它的阈值来自一个"代码里随手写的 1.0"，那么同一个方案在不同版本的程序里会得到不同结论——而 `compiledHash` 却认为产物相同。**校验阈值必须是数据，不是代码常量。**

**为什么必须独立成表，而不是在 `render_units` 上加几个列**：

| 信息 | 粒度 | 放 `render_units` 的问题 |
|---|---|---|
| `adaptation_version` | 方案级 | 每个单元都要重复存，且要保证同方案内一致 → 冗余即不一致的温床 |
| `profile_*` 四个参数 | 方案级 | 同上；且改 profile 参数时无法判断"哪些单元属于旧参数" |
| `source_spec_hash` | 方案级 | 单元级存则无法回答"这套切分是对哪版分镜做的" |
| `status='superseded'` | 方案级 | 单元级会出现"部分单元被取代"这种无意义状态 |

**`profile_*` 四个参数为什么要快照**：TargetProfile 是可编辑的配置。若只存 `profile_ver='h3.v1'` 而 `h3.v1` 的 `max` 后来从 15 调成 20，旧方案的可复算性就没了——`adaptationHash` 会变，但切分结果不会变，二者不再对应。**快照四个数值（含 `tailHoldMax`），`adaptationHash` 才能复算。**

**`shot_scope_hash` 的用途**：一章可能只对部分镜做适配（用户先做前 20 镜）。片段完整性校验只对该集合执行，否则会报"其余镜缺片段"。hash 用于快速判断两个方案是否覆盖同一范围。

**`source_spec_hash` 不参与 `adaptationHash`**（见 `D01-06 §4.3`），这里存它是为了运维判断：

```
若 render_adaptations.source_spec_hash ≠ 当前分镜的 sourceSpecHash
  → 方案已过期（分镜改了但没重切）
  → 编译前必须提示，不得静默用旧切分
```

**方案状态机**：

```
        创建          重切            确认可用
  ──────────► active ──────► superseded
                 │
                 └─► failed（切分失败，如 ADAPT_NO_LEGAL_CUT）

同一时刻，同一 (chapter, track) 下**至多一个 active**（应用层保证，DB 无法用部分唯一索引表达；
SQLite 支持 `CREATE UNIQUE INDEX ... WHERE status='active'`，但为避免与历史库兼容问题，采用应用层 + 定时巡检）
```

### 5.2 为什么 `duration` 不能直接当 `story_duration`

`a053dabd` 项目的 13 条 `duration` 是 14–30s，若直接当镜时长，会得到"一镜 30 秒"，与"每镜 2.5–7.5 秒"的密度规则冲突。

**切分规则（按 §2.4 三格式）**：

| 格式 | 正则/方法 | 可得 `story_duration` | 置信度 |
|---|---|---|---|
| A `[镜头N]` | `/(\d{2}:\d{2})-(\d{2}:\d{2})\s*\[镜头(\d+)\]/` | 逐镜精确 | 0.9 |
| B 中文分段 | `/(\d+(?:\.\d+)?)-(\d+(?:\.\d+)?)s：/` | 逐段精确 | 0.8 |
| C 无分段 | 无法切 → 整行 1 镜 | `= duration` | 0.2 |

**校验**：Σ 切出的片段 ≈ `shots.duration`（容差 0.5s）；不等 → 记 `DURATION_MISMATCH`，该行 `fill_confidence` 降 0.2。

|---|---|---|---|
| 全结构化 | 无 | 全字段 | 越轴（P-A/P-B）、状态继承、双轨编译 |
| 影子镜 A/B | 🟡「旧版」 | 文本字段 | 编译（单轨）、导出 |
| 影子镜 C | 🔴「无镜信息」 | 文本字段 | 编译（单轨）、导出 |

**不假装**：旧数据不标"已结构化"，也不填猜测的枚举值。

### 6.4 `shots` 兼容策略：单向投影，不落库

> 本节回答 P1-04 的六个问题。它与 `D01-01 §3.5`（`shots` 冻结）和 §7 M2（不双写）是同一套决定的三个面。

**最终权威**：

| 对象 | 权威 | 说明 |
|---|---|---|
| 新项目（`structured_spec=true`） | `story_shots` + 从表 + `render_*` | `shots` 表**没有该项目的行** |
| 历史项目（无 flag） | `shots` | 新表为空，走影子镜读取（§6.1） |
| 旧字段（`video_prompt` / `video_path` / `seed`） | 历史项目读 `shots`；新项目读 `prompt_packages` + `render_attempts` | 各自独立，不互相覆盖 |

**读适配器**（内存渲染，不落库）：

V3 的 `selectActiveUnits(projectId, chapterId)` **没有指定 track**。当 Seedance 与 H3 同时 active 时，它会把两套单元一起返回——旧列表里同一镜出现两次、`unit_no` 各自从 1 开始交错、总时长变成两轨之和。这是 P0-04 的原始缺陷。

```js
/**
 * 旧接口兼容投影。**单轨语义**：旧 shots 一行只有一个 `mode` 列，
 * 结构上无法同时表达 Seedance 与 H3 两套单元。
 *
 * @param {object} p
 * @param {'auto'|'seedance'|'h3'} [p.track]  显式选择；auto = 走选择链
 * @returns {{ track: string, rows: object[], reason?: string }}
 */
function listShotsCompat({ projectId, chapterId, track = 'auto' }) {
  const structured = selectStoryShots(projectId, chapterId);

  // ① 历史项目：新表为空 → 走旧读法
  if (!structured.length) {
    return { track: 'legacy', rows: selectLegacyShots(projectId, chapterId) };
  }

  // ② 新项目：先定轨，再只取该轨的那一个 active 方案
  const resolved = track === 'auto'
    ? resolveDefaultTrack({ projectId, chapterId })
    : track;

  const ad = selectActiveAdaptation({ projectId, chapterId, track: resolved });
  if (!ad) return { track: resolved, rows: [], reason: 'NO_ACTIVE_ADAPTATION' };

  const units = selectUnitsByAdaptation(ad.id);          // 只来自这一个 adaptation
  return {
    track: resolved,
    rows: units.map(u => projectUnitToShotRow(u, ad)),
  };
}
```

#### 6.4.1 旧接口的 track 选择链（P0-04）

旧接口**只能表示单轨**，所以必须有确定性规则：

```
resolveDefaultTrack({ projectId, chapterId }):

  1. project.default_track ∈ {seedance, h3}            → 用它
  2. 该章存在唯一 active adaptation 的 track            → 用它
  3. 该章有多个 active adaptation                       → 取 updated_at 最新者的 track，
                                                          同时报 ADAPT_MULTI_ACTIVE (WARN)
  4. 都没有 active adaptation                           → 'legacy'（返回空列表 + NO_ACTIVE_ADAPTATION）
```

**三个概念的关系**（任务书要求明确）：

| 概念 | 存在哪 | 作用 | 优先级 |
|---|---|---|---|
| 项目默认模型 | `projects.default_track` | 新建适配时的默认轨道、旧接口默认显示哪轨 | 中 |
| 用户选择模型 | UI 参数 / `listShotsCompat({track})` 显式传参 | 当次调用的轨道 | **最高** |
| 兼容接口 | `listShotsCompat()` | 投影成旧形状，轨道由前两者决定 | — |

**多 Profile 并存时的选择**：

同一 `(chapter, track)` 下 `status='active'` 应唯一（应用层保证 + §4.14 巡检）。若脏数据出现两个 active：

```
selectActiveAdaptation:
  ORDER BY adaptation_version DESC LIMIT 1
  并在返回时附带 warning: ADAPT_MULTI_ACTIVE
```

**为什么不按 profile 再分一层**：旧接口的消费者（旧页面、旧 API）根本不认识 profile 概念，给它一个 `profile_ver` 参数没有意义。`profile` 的选择发生在**适配层的重切动作**里（新方案 = 新 version），不在读取时。

**为什么不能把两轨合并返回**：

| 后果 | 具体表现 |
|---|---|
| 重复显示 | 同一镜在 sd 与 h3 各一份，列表出现两次，用户以为分镜被复制了 |
| 时长错乱 | sd 单元 29.5s + h3 单元 14.5s 混在一列，"总时长"变成 44s |
| 顺序交错 | 两轨 `unit_no` 都从 1 开始，按 `idx` 排序后交替出现 |
| 编译错配 | 用户点第 3 行"生成"，拿到的可能是另一轨的单元 |
| 编辑错位 | 旧 UI 的"改这一行"会写到投影上——而投影不可写（`_projection:true`），操作静默失败 |

**算例：Seedance 与 H3 同时 active**（P0-04 要求 6、7）

**输入**

| 对象 | 值 |
|---|---|
| 项目 | `p_9f3a`，`default_track='h3'` |
| `ad_sd_1` | `track=seedance`，`profile=seedance25.v1`，`ver=1`，`status=active`，**6 个单元**（29.5/28/…） |
| `ad_h3_1` | `track=h3`，`profile=h3.v1`，`ver=1`，`status=active`，**9 个单元**（14.5/13/…） |

**调用与结果**

| 调用 | 返回 `track` | `rows.length` | 内容 |
|---|---|---|---|
| `listShotsCompat({projectId, chapterId})` | `h3` | **9** | 只含 `ad_h3_1` 的单元 |
| `listShotsCompat({..., track:'h3'})` | `h3` | 9 | 同上（显式与默认一致） |
| `listShotsCompat({..., track:'seedance'})` | `seedance` | **6** | 只含 `ad_sd_1` 的单元 |
| 把 `default_track` 改成 `seedance` 后再调默认 | `seedance` | 6 | 选择链第 1 步生效 |

**证明不重复、不混合、不覆盖**：

```
① 不重复：rows.length === units.length（1:1 映射，不做笛卡尔积）
   9 === 9 ✓

② 顺序唯一：new Set(rows.map(r => r.idx)).size === rows.length
   {1..9} 大小 9 === 9 ✓

③ 不混合：rows.every(r => r._track === resolved)
   全部 'h3' ✓

④ 不覆盖：投影 id 带 adaptation 前缀
   h3 行    → 'proj_ad_h3_1_u03'
   seedance → 'proj_ad_sd_1_u03'
   两者不同，即使同一章同一单元号也不会相互覆盖 ✓

⑤ 切轨不残留：两次调用互不影响（无缓存写回，纯读） ✓
```

**V3 会怎么错**：`selectActiveUnits` 不带 track，返回 6+9=**15 行**，其中 sh_03 出现两次（sd 里完整、h3 里被切成两片 → 甚至三次）。用户看到的"分镜列表"有 15 行，总时长 44 秒，而实际片长 38 秒。**这不是显示问题，是数据语义被合并破坏了。**

**`projectUnitToShotRow(u, ad)` 渲染哪些列**（投影 = 派生，全部现算，不存库）：

| `shots` 列 | 投影来源 | 是否可写 |
|---|---|---|
| `id` | `'proj_' + ad.id + '_' + u.id` | ❌ 只读 |
| `project_id` / `chapter` | 参数 + `chapters.title` | ❌ |
| `idx` | `u.unit_no`（**该 adaptation 内**） | ❌ |
| `scene_name` | 单元内首个镜的 `scene_key` → 场景名 | ❌ |
| `camera` | 单元内各镜 `D` 区字段拼成的文本 | ❌ 派生 |
| `visual` | 各镜 `visual_content` 拼接 | ❌ 派生 |
| `sub_shots` | `render_unit_shots` + `story_shots` 渲染的时间轴文本（**`t_local`，不是 `t_abs`**） | ❌ 派生 |
| `blocking` | `shot_blockings` 渲染的画面方位文字（段首声明） | ❌ 派生 |
| `duration` | `u.unit_duration` | ❌ |
| `dialogue` | 单元内各镜台词按 `order_no` 拼接 | ❌ 派生 |
| `character_ids` | `shot_assets(role='character')` 去重 | ❌ 派生 |
| `video_prompt` | `''`（新项目放 `prompt_packages`） | ❌ |
| `status` | `u.status` | ❌ |
| **`_projection`** | `true` | — |
| **`_track`** | `ad.track` | — |
| **`_adaptation`** | `ad.id` | — |

**`_projection` / `_track` / `_adaptation` 三个下划线字段是给 UI 与调试用的**：任何写回操作必须先看到 `_projection=true` 就拒绝，并提示"这是投影，请改 `shot_blockings`"。

**回滚**：关 flag。已写的新项目仍可读（走 `listShotsCompat`）；`shots` 从未被写，无残留。

**P1-04 的六个问题逐条回答**：

| 问题 | 回答 |
|---|---|
| 新项目是否创建旧 `shots` 行？ | **不创建** |
| 旧页面 / 旧 API 如何读？ | 过 `listShotsCompat()`，在内存把 `render_units + render_unit_shots + story_shots` 渲染成 `shots` 形状。**M2 的前置条件是把读取入口切过来** |
| 若创建，如何定义 legacy compatibility record？ | 不创建，因此不需要。（若将来必须，只能是"派生只读投影"，且必须带 `_projection:true`） |
| 一个旧记录如何映射多个 RenderUnit？ | 旧记录（`shots` 一行）本身就是一个 legacy 单元，1:1。**"一镜多单元"是新模型的概念**；旧记录没有镜级信息，无从映射。历史项目要多单元，只能走 M3 结构化升级 |
| 删除/修改新数据时，旧数据如何同步？ | **不需要同步**，因为不双写。历史项目改 `shots` 只影响自己，新项目改新表只影响自己，两者不共享行 |
| 哪份数据具有最终权威？ | 按项目分流：`structured_spec=true` → 新表；否则 → `shots`。**同一项目内不会出现两份都能写** |

**一个必须承认的取舍**：新项目的"段首站位声明"（投喂时那段文字）不再从 `shots.blocking` 读，而是编译时从 `shot_blockings` **现算**。好处是它必然与结构化数据一致（不会出现"文字说在左、坐标在右"）；坏处是"用户手改那段文字"这条路径在新项目上消失了——要改就改 `shot_blockings`，让编译器重新生成。这是有意的：**文字是投影，数据是源**。

**`sub_shots` 为什么不能回写**：历史 `sub_shots` 有三种格式（`D01-05 §2.4`），其中格式 C 无镜信息。把它当作新数据的"渲染目标"，等于用一个有损格式表达结构化的镜级信息（动作区间、坐标、状态），**渲染一次就丢一次**。所以不是"能写但不写"，而是"写了就是降级"。

**V3 决议：不双写。**

```sql
-- 唯一写入口（新项目）
BEGIN;
  INSERT INTO story_shots ...;
  INSERT INTO shot_blockings ...;
  INSERT INTO shot_actions ...;
  INSERT INTO shot_assets ...;
  INSERT INTO render_adaptations ...;   -- 触发切分后落一个方案
  INSERT INTO render_units ...;
  INSERT INTO render_unit_shots ...;
COMMIT;
-- 注意：没有任何一条语句写 shots
```

**为什么最终选"不双写"**（方案比较）：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 双写（新表 + 回写 `shots.sub_shots/blocking/camera`） | 旧页面零改动 | **两份权威**：改一处漏一处；`sub_shots` 是**有损渲染**（三种格式无法表达动作/坐标/状态），回写即丢失；写放大 2×；回滚时无法判断哪份是准的 | ❌ |
| B. 不双写 + 旧接口换源（读适配器） | 单一权威；无同步问题；旧页面代码不动，只换数据源 | 需要改 3 个读取入口（`D01-05 §3.7`）；`shots` 空时旧页面必须先过适配器，否则白屏 | ✅ **推荐** |
| C. 冻结 + 新项目也建一条 `shots` 占位行 | 旧页面直接能读到 | 占位行的 `sub_shots` 必须渲染，等于 A 的缺点 + 一条无意义记录 | ❌ |

**选 B 的代价必须写清楚**：`shots` 表对**新项目是空的**。任何直接 `SELECT * FROM shots WHERE project_id=?` 的旧代码都会拿到空数组。因此 **M2 的前置条件是先把 3 个读取入口切到 `listUnits()`**，否则新项目在旧页面看不到东西。这不是"顺手改一下"，是硬前置。

**读适配器、投影规则与六个问题的回答见 §6.4。**

V2 回滚规则：

```sql
-- 只删「从未被确认、从未被引用」的回填行
DELETE FROM story_shots
WHERE spec_source='legacy'
  AND fill_confidence < 0.7
  AND id NOT IN (SELECT shot_id FROM render_unit_shots)
```

**原则：回滚不是"回到从前"，而是"撤销未生效的改动"。已经进入有效业务链的数据，只能降级标记，不能删除。**

## 八、约束、事务与删除策略（修订 P1-8）

### 8.1 外键：不启用 DB 级，改用应用层

**决策**：新表**不写 `REFERENCES`**，理由：

1. 现有库未开 `PRAGMA foreign_keys`，一旦开启，历史软关联脏数据会让旧代码的删除/更新突然失败；
2. `tx()` 只支持同步，应用层事务已能保证一致性；
3. 校验由 `spec-validator`（`D01-06 §6`）承担，产出明确的 FAIL 而不是一个 SQL 错误码。

**替代手段**：

| 手段 | 实现 |
|---|---|
| 引用存在性 | 写前查 `assets`/`story_shots` 存在性 |
| 级联删除 | 应用层按 §8.2 顺序删 |
| 孤立检测 | 定时任务扫 `story_shots` 无 `scene_states`、`shot_assets` 无 `assets` |

### 8.2 删除策略（顺序敏感）

| 操作 | 顺序 | 说明 |
|---|---|---|
| 删一镜 | `shot_assets` → `shot_blockings` → `shot_actions` → `shot_states` → `render_unit_shots` → `story_shots` | 先删从表，再删主表 |
| 删一单元 | `render_unit_shots` → `prompt_packages` → `render_units` | 任务不删（历史） |
| 删一项目 | 上述全部 + legacy `shots` 及其 `shot_videos` | 沿用现有 `Shots.remove` 模式 |
| 已编译过的镜 | **禁止物理删除**，改 `status='void'` | 保留 `prompt_packages` 溯源 |

**为什么"已编译禁止物理删除"**：`prompt_packages` 里存着 `source_spec_hash`，若镜被删，该 hash 无从复算，"这条片子是哪版分镜产的"永久失效。

### 8.3 唯一约束清单

| 表 | 唯一键 | 目的 |
|---|---|---|
| `scene_states` | `(project_id, scene_key)` | 一场一基线 |
| `story_shots` | `(project_id, global_no)` | 集内镜号唯一 |
| `story_shots` | `(chapter_id, shot_no)` | 章内镜号唯一 |
| `shot_assets` | `(shot_id, role, asset_id)` | 防重复引用 |
| **`render_adaptations`** | `(chapter_id, track, profile_ver, adaptation_version)` | **同一轨道同一 profile 的版本号唯一**；不同 profile 各自从 1 起 |
| **`render_units`** | `(adaptation_id, unit_no)` | **适配方案内**单元号唯一（V2 的 `(project_id,track,unit_no)` 无法容纳多版本，已废） |
| **`render_unit_shots`** | `(unit_id, shot_id)` | 同一单元内一镜只能出现一次（切分不变量） |
| **`render_unit_shots`** | `(unit_id, order_no)` | 单元内顺序不重复 |
| `prompt_packages` | `(unit_id, track, compiled_hash)` | 编译幂等 |
| `timelines` | `(project_id, chapter_id, name)` | 一项目一章一主时间线 |

**`render_units.adaptation_id` 必须有索引**（`idx_ru_ad (adaptation_id, unit_no)`），因为"取某方案全部单元"是最热查询。

**SQLite 部分唯一索引的取舍**：理论上可以用

```sql
CREATE UNIQUE INDEX uq_ra_active ON render_adaptations(chapter_id, track)
  WHERE status = 'active';
```

来保证"同一章同一轨道至多一个 active 方案"。V3 **不用**它，理由：现有 `db.js` 的迁移是 `CREATE TABLE IF NOT EXISTS` + `ALTER` 的简单叠加，引入部分索引后，若历史库已有不一致数据（两个 active），建索引会直接失败，导致启动崩。改为**应用层唯一 + 定时巡检**：

```sql
-- 巡检：找出多 active 的 (chapter, track)
SELECT chapter_id, track, COUNT(*) c
FROM render_adaptations WHERE status='active'
GROUP BY chapter_id, track HAVING c > 1;
```

命中则把 `updated_at` 最新的保留为 active，其余转 `superseded` 并记录日志。**先修数据、后收紧约束**是这套库一贯的迁移顺序。

### 8.4 事务边界

| 操作 | 必须在同一 `tx()` 内 | 备注 |
|---|---|---|
| 写入一镜（新项目） | `story_shots` + 3 从表 + `shot_assets` | **不含 `shots`** |
| 提交一次完整分镜（新项目） | 上述全部 + `render_adaptations` + `render_units` + `render_unit_shots` | 切分在同事务内完成，失败则整体回滚（含 `status='failed'` 的方案行**不**回滚——它记录失败事实） |
| 写入一镜（历史项目） | 仅 `shots` | 不动新表 |
| 重切（换 profile / 改 seamPolicy） | 插新 `render_adaptations` + 新单元 + 新关联；旧方案 `status='superseded'` | 旧方案行与旧关联**保留** |
| 编译 | 插 `prompt_packages` + 更新 `render_units.status` | — |
| 成片 | 插 `timelines` + 更新 `render_units.status` | — |

## 九、不丢数据的验证（验收必做）

| 验证项 | 方法 | 通过标准 |

## 十、风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | `blocking` 列不在 `initSchema`，新环境建库后 `Shots.create` 会失败 | 部署级 | 实施阶段补一条 `ALTER TABLE shots ADD COLUMN blocking`（或把列并入建表语句）；本阶段只记录 |
| R-2 | 历史 `blocking` 用画面方位，无法转坐标 | 越轴对历史数据不可用 | 明确 `AXIS_UNVERIFIED`，需人工补 `cam_pos` |
| R-3 | 16 条 `sub_shots` 无分段 | 无法切镜 | 整行 1 镜 + `confidence=0.2`，人工复核 |
| R-4 | 无外键，靠应用层 | 脏数据可能写入 | 校验器前置 + 孤立检测任务 |
| **R-5** | **不双写后，旧读入口未切会导致新项目在旧页面白屏** | **用户可见** | M2 的**硬前置**：先把 3 个读取入口切到 `listShotsCompat()`，再开 `structured_spec` flag；灰度按项目 |
| R-6 | 表增至 26 张 | 查询复杂度上升 | 列表页只查主表，从表懒加载 |
| R-7 | `shots` 冻结后旧代码仍在写它 | 历史项目正常，新项目会产生"孤儿行" | 写入口按 flag 分流；巡检：`shots` 行所属项目 `structured_spec=1` → 告警 |
| **R-8** | **适配方案多版本并存，若不清理会产生大量 `superseded` 行** | 存储与查询 | 保留策略：每 `(chapter,track,profile)` 保留最近 3 版 + 所有被 `prompt_packages` 引用的版本，其余转 `archived`（新增状态）后定期归档 |
| **R-9** | **`profile_*` 参数快照后，若 TargetProfile 配置改动，新旧方案混用** | 切分不可比 | `adaptationHash` 含快照参数；`plan_adaptation` 幂等键含 `profileVer` + 参数，改参数即新方案 |
| **R-10** | **`data/_verify/*.mjs` 核查脚本被 `.gitignore` 的 `data/` 排除，不在仓库内** | **公开仓库无法独立复核数据库结论** | 见 §1.1：结论标注为"本地实测，脚本未入库"；若需外部复核，须把脚本移到 `docs/D01/evidence/` 一并提交（本轮未做，属未关闭项）|

**R-5 是最容易被低估的一条**：它不影响数据正确性，但会让"新建项目后旧页面一片空白"，看起来像 bug。实施时必须先切读路径再开写路径，顺序不能反。
