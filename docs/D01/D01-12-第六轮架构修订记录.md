## 二、P0-01 · 容差与归属的缝隙

### 2.1 原设计（V5）

```
crosses(a, t)  ⟺  (a.t_from + EPS < t) && (t < a.t_to - EPS)     ← 带 ±EPS
a 属于左片段  ⟺  a.t_to <= t                                      ← 不带
a 属于右片段  ⟺  a.t_from >= t                                    ← 不带
```

两处用的"尺子"不同量纲：一边把边界往里缩了一个 `EPS`，一边没有。

### 2.2 反例（不是理论推演，是能直接算出来的）

```
A = (0, 5.0004)，切点 t = 5.000（另一动作恰好在此起）
   crosses:  0+ε < 5.000  ✓   5.000 < 5.0004-ε = 4.9994  ✗   → 不跨越（判为合法切点）
   左:       5.0004 <= 5.000        ✗
   右:       0 >= 5.000             ✗
   → A 既不在左也不在右。整条动作在成片里消失，无任何报错。
```

**同一族的第二个形态**：`A = (3.0004, 8)`，`t = 3.000`。此时归属判右（`3.0004 >= 3.000` 为真），结果"看起来对"——但它把 A 起点前 0.4 ms 判给了左片段却毫无记录。**同一个 bug，一处丢动作，一处静默改语义。**

### 2.3 改法：先把时间放到同一个网格上

```js
const TQ  = 0.001;                    // 1 ms，与 H3 时间码 00:SS.mmm 同精度
const TOL = TQ / 2;                   // 唯一容差，只用于吸附
const q   = (x) => Math.round(x * 1000) / 1000;
```

| 步骤 | 规则 |
|---|---|
| ① 量化 | 所有 `t_from` / `t_to` / `story_duration` 入口即 `q()` |
| ② 候选 | `candidateCuts = {q(0), q(D)} ∪ {q(t_from)} ∪ {q(t_to)}` |
| ③ 吸附 | `snap(t)`：唯一 `b` 使 `\|t-b\| <= TOL`；否则 `null`（**拒绝，不就近取整**） |
| ④ 跨越 | `crosses(a,t) ⟺ q(t_from) < t && t < q(t_to)`（严格，无容差） |
| ⑤ 归属 | 左 `⟺ q(t_to) <= t`；右 `⟺ q(t_from) >= t` |
| ⑥ 后置校验 | 每个动作 `n = 左 + 右` 必须 `== 1`，否则 `ADAPT_ACTION_LOST` / `ADAPT_ACTION_DUPLICATED` |

### 2.4 为什么这样就消掉了缝（证明，不是断言）

`q(t_from) < q(t_to)` 时，对任意网格点 `t` 只有三种情形：

| 情形 | 左 `q(t_to) <= t` | 右 `q(t_from) >= t` | 合法切点 |
|---|---|---|---|
| `t <= q(t_from)` | 假（因 `q(t_to) > q(t_from) >= t`） | **真** | 是 |
| `q(t_from) < t < q(t_to)` | 假 | 假 | **否**（`crosses` 真） |
| `t >= q(t_to)` | **真** | 假（因 `q(t_from) < q(t_to) <= t`） | 是 |

**每行恰有一个为真**，且三行互斥穷尽 → 对合法切点，每个动作恰属一个片段。

### 2.5 前置条件：退化动作必须拒绝

证明依赖 `q(t_to) > q(t_from)`。若动作时长 < 1 ms，则 `q(t_from) == q(t_to)`，第一行与第三行**同时成立**，动作会被左右各播一次。因此：

```
q(t_to) - q(t_from) < TQ   →  ADAPT_DEGENERATE_ACTION
t_from < -TOL || t_to > D+TOL  →  ADAPT_ACTION_OUT_OF_RANGE
```

### 2.6 算例 G（`D01-06 §3.3.9`，四个必测形态 + 两个补充）

| 例 | 输入 | 期望 | V5 的行为 |
|---|---|---|---|
| G-1 | 起点偏差 0.4 ms（`3.0004` vs 切点 `3.000`） | 归右 + `ACTION_EDGE_SNAPPED`(INFO) | 归右但对 0.4 ms 偏移无记录 |
| G-2 | **终点**偏差 0.4 ms（`5.0004` vs 切点 `5.000`） | 归左 + INFO | **动作丢失** |
| G-3 | 两边界相距 0.2 ms（`3.0004` / `3.0006`） | 量化合并为一个候选，各归一次 | 候选含两个点 → 可能切出 0.0002 s 片段 |
| G-4 | 精确边界（`12.000`） | 各归一次，无 INFO | 一致 |
| G-5 | 动作时长 0.4 ms | 拒绝 | 静默：同一时刻左右双算 |
| G-6 | 切点离边界 2 s | 拒绝（`snap` 返回 null） | 不是候选（一致，但 V5 未写"拒绝"语义） |

**G-3 的隐藏危害**：V5 的 `pickLegalCut` 只约束"切点到 `consumed` 的距离 ≥ `minSlice`"，**不约束"切点到下一个边界的距离"**。所以两个相距 0.2 ms 的合法切点能造出一个 0.2 ms 的片段，而它通过了所有现有校验。

### 2.7 落库前的归属后置校验

```js
function assertAttribution(s, t) {
  const bad = [];
  for (const a of s.actions || []) {
    const n = (q(a.t_to) <= t ? 1 : 0) + (q(a.t_from) >= t ? 1 : 0);
    if (n !== 1) bad.push({ actionId: a.id, assigns: n,
                            code: n === 0 ? 'ADAPT_ACTION_LOST' : 'ADAPT_ACTION_DUPLICATED' });
  }
  return bad.length ? { ok: false, code: bad[0].code, detail: bad } : { ok: true };
}
```

它不是"再检查一遍"，是**本轮唯一的兜底**：只要实现写错比较符、或有人绕过 `q()` 直接用原始浮点，这条就会把"动作丢失/重复"变成硬错误。

### 2.8 同步修改

| 位置 | 改动 |
|---|---|
| `D01-06 §3.3.2` | 算法全文改用 `q()` / `TOL`；入口先量化并做退化/越界检查；`cur.dur` 用网格加法 |
| `D01-06 §3.4` | `verifyAdaptation` 里的 `EPS` 全部换成 `TOL`（另设 `PAD_TOL=0.01` 专用于尾镜留白） |
| `D01-01 §3.3` | 片段合法性补"恰好归属一个片段 + 后置校验"一条 |
| `D01-02 §10.1` | 补"容差只有一处，且只用于吸附" |

## 三、P1-01 · `posRel()` 的优先级

### 3.1 原设计（V5）的两处错

```js
if (metaEntry?.rel === 'unknown') return 'unknown';
if (x == null || y == null || z == null) return 'unknown';
...
```

| # | 错 | 后果 |
|---|---|---|
| 1 | **没有 `not_applicable` 分支** | 画外人物本就没有坐标，必落进缺失检查 → 返回 `unknown`。而同一节表格写着 `not_applicable`。**表格与代码矛盾** |
| 2 | 第 ⑤ 分支 `specSource === 'manual' ? 'known' : 'inferred'` | `legacy` 来源（历史行）会得到 `inferred`，但同一节又规定"历史行一律 `unknown`" |

第 1 条的后果不是学术问题：`unknown` 计入 `verifiable_ratio` 分母并触发 `STATE_UNKNOWN`，`not_applicable` 完全不计。把画外人物算成"未验证"，会让**真正缺数据的镜头被泛滥的 unknown 淹没**。

### 3.2 改法：五级优先级，顺序固定

```js
function posRel({ x, y, z, metaEntry, specSource }) {
  const explicit = metaEntry?.rel;

  if (explicit === 'not_applicable') return 'not_applicable';   // ① 先于缺失检查
  if (explicit === 'unknown')        return 'unknown';          // ②
  if (x == null || y == null || z == null) return 'unknown';    // ③ 任一缺失 → 整体 unknown
  if (![x, y, z].every(Number.isFinite)) return 'unknown';
  if (explicit === 'known' || explicit === 'inferred') return explicit;  // ④
  if (specSource === 'manual') return 'known';                  // ⑤
  if (specSource === 'legacy') return 'unknown';                //    历史行不可信
  return 'inferred';
}
```

| 优先级 | 判据 | 结果 | 谁能否决谁 |
|---|---|---|---|
| ① | 显式 `not_applicable` | `not_applicable` | **最高**，坐标有无都不改变 |
| ② | 显式 `unknown` | `unknown` | 否决 ④ 的 known/inferred |
| ③ | 任一分量缺失/非有限数 | `unknown` | **否决 ④**：标了 known 但坐标不全，仍判 unknown |
| ④ | 显式 `known` / `inferred` | 原值 | 须通过 ③ 才生效 |
| ⑤ | 无 meta | manual→known / legacy→unknown / 其他→inferred | 最低 |

### 3.3 13 行矩阵（`D01-04 §5.2.2`，与代码逐行对应）

| # | `meta.rel` | x | y | z | `spec_source` | 返回 | 分支 |
|---|---|---|---|---|---|---|---|
| 1 | — | 1.2 | 3.4 | 0 | manual | `known` | ⑤ |
| 2 | — | 1.2 | 3.4 | 0 | ai | `inferred` | ⑤ |
| 3 | — | 1.2 | 3.4 | NULL | manual | **`unknown`** | ③ |
| 4 | — | 1.2 | NULL | 0 | manual | **`unknown`** | ③ |
| 5 | — | NULL | NULL | NULL | manual | **`unknown`** | ③ |
| 6 | — | 1.2 | 3.4 | NaN | manual | **`unknown`** | ③ |
| 7 | `known` | 1.2 | 3.4 | 0 | ai | `known` | ④ |
| 8 | `known` | 1.2 | 3.4 | NULL | manual | **`unknown`** | ③ 否决 ④ |
| 9 | `inferred` | 1.2 | 3.4 | 0 | manual | `inferred` | ④ |
| 10 | `unknown` | 1.2 | 3.4 | 0 | manual | **`unknown`** | ② |
| 11 | `not_applicable` | NULL | NULL | NULL | ai | **`not_applicable`** | ① |
| 12 | `not_applicable` | 1.2 | 3.4 | 0 | manual | **`not_applicable`** + WARN | ①（记 `COORD_NA_WITH_VALUE`） |
| 13 | — | 1.2 | 3.4 | 0 | **legacy** | **`unknown`** | ⑤ |

**第 8 条**（显式 known 但坐标不全）为什么要否决：这不是"确定"，是**标记与数据不一致**。判 `unknown` 并记 `META_VALUE_MISMATCH`(WARN)，让人去补坐标或改标记，而不是带着半个坐标进场。

**第 12 条**为什么仍返回 `not_applicable`：标记是人的意图，程序不擅自推翻，只提示。

### 3.4 四值与统计的关系（本轮补）

| `rel` | 计入 `verifiable_ratio` 分母 | 可 FAIL | 可 PASS |
|---|---|---|---|
| `known` | ✅ | ✅ | ✅ |
| `inferred` | ✅ | ❌ | ⚠️ 不算 PASS |
| `unknown` | ✅（记为未验证） | ❌ | ❌ |
| `not_applicable` | ❌ **完全不计** | ❌ | ❌ |

`not_applicable` 与 `unknown` 在统计上必须分开：前者是"这题不考"，后者是"这题没答"。

## 四、P1-02 · `order_no` 的库级约束

### 4.1 原设计（V5）

```sql
order_no INTEGER NOT NULL,
UNIQUE (shot_id, role, order_no),
CHECK (role <> 'voice' OR order_no BETWEEN 1 AND 3)
```

**缺口**：`order_no = 0` 对 `role='character'` 完全合法。于是角色参考图顺序可以写成 0,1,2，而 `@图片N` 从 1 起编号，编译时必须做 `+1` 偏移——偏移写错就整体串位，而库里看不出任何异常。

### 4.2 改法

```sql
CHECK (order_no >= 1),                                  -- 全部 role
UNIQUE (shot_id, role, order_no),
CHECK (role <> 'voice' OR order_no BETWEEN 1 AND 3)
```

### 4.3 数据库约束与应用层校验的分工（本轮新增）

| 约束 | 谁负责 | 拦得住 | 拦不住 |
|---|---|---|---|
| `order_no >= 1` | DB `CHECK` | 0、负数 | — |
| 同 `(shot,role)` 重号 | DB `UNIQUE` | 两行都是 1 | — |
| `voice` 第 4 条 | DB `CHECK` + `VOICE_OVERFLOW` | `order_no=4` 越界 | 1,2,3,1 → 由 `UNIQUE` 拦 |
| **连续不跳号（1,3）** | **只能应用层**（`ASSET_ORDER_GAP`，V-25） | — | **SQL 无法表达"集合 = {1..n}"** |
| `order_no` 与 `voice_ids` 一致 | 应用层（V-23） | — | 跨表，DB 不可能 |

**为什么不引入触发器**：仓库现有迁移是 `CREATE TABLE IF NOT EXISTS` + `ALTER` 的叠加（`D01-05 §8.3` 同理由），加触发器会改变启动路径的失败模式。取舍是：DB 只保证三条硬边界（不 0、不重、voice ≤3），连续性交给校验器 —— **最坏情况是"Audio 编号跳一个"，而不是"两条资产抢同一个槽"**。

### 4.4 引用错误修正

`D01-05 §4.6` 原文把 `ASSET_ORDER_GAP` 指到 `D01-02 V-24`。V-24 实际是"类 B 字段 AI 自称 known"；`ASSET_ORDER_GAP` 是 **V-25**。已改，并给第 4 条补上 **V-26**。

## 五、P1-03 · hash 排序的区域设置依赖

### 5.1 原设计（V5）

动作排序、blockings 排序、assets 排序、scenes 排序全部用：

```js
String(a).localeCompare(String(b))
```

`localeCompare` 不传 locale 时用**宿主默认区域 + 宿主 ICU 版本**。

### 5.2 同一份数据可能排出两种顺序

| 环境 | `"ä"` vs `"z"` | `"ı"` vs `"i"` |
|---|---|---|
| `en-US` | `ä < z` | `ı < i` |
| `sv-SE` | **`z < ä`** | 同 |
| `tr-TR` | 同 | **`ı` 与 `i` 不同组** |

动作 id 目前是 ASCII，看似安全；但 `scene_key` 含中文（`S02_病房`）、资产 id 可能含大写、`type` 含下划线——**只要有一个非 ASCII 字符，两台机器就可能算出不同 hash**，而 `sourceSpecHash` 的全部意义就是"任何机器算出同一个值"。

### 5.3 改法

```js
// 按 UTF-16 code unit 逐位比较；ECMA-262 规定字符串 < > 为 code unit 字典序，
// 与宿主 locale / ICU 版本无关
function cmpStr(a, b) {
  const x = String(a ?? ''), y = String(b ?? '');
  return x < y ? -1 : x > y ? 1 : 0;
}
```

替换点（5 处）：

| 位置 | 原 | 现 |
|---|---|---|
| `sourceSpecHash` 的 scenes 排序 | `localeCompare` | `cmpStr` |
| blockings 排序 | `localeCompare` | `cmpStr` |
| assets 排序（role / id） | `localeCompare` | `cmpStr` |
| actions 排序（actor / type / contentHash） | `localeCompare` | `cmpStr` |
| `D01-03 §5.2` QC 冲突列表排序 | `localeCompare` | `cmpStr`（不是 hash，但同属"输出必须可复现"） |

`canonicalStringify` 的对象键排序也**必须**用 `cmpStr`：虽然 `Object.keys().sort()` 默认恰好也是 code unit 序，但必须写死，不能依赖"默认恰好一致"。

### 5.4 回归要求（R-42）

同一 fixture 在 `LANG=en_US.UTF-8` / `tr_TR.UTF-8` / `sv_SE.UTF-8` 下跑 `sourceSpecHash`，**必须逐字相同**。CI 至少跑前两种；容器里改 `LANG` 即可复现差异，不需要真的换机器。

**单机跑一次不算通过**——这正是本项的关键。

## 六、P1-04 · `stripRef()` 的定义

### 6.1 原设计：不存在

`stripRef()` 在 V4/V5 里出现 4 次、被调用 2 次，**从未定义**。它决定 `bodyOf()` 中 `trigger` / `sync` 的内容，也就是 hash 的一半输入——不定义它，`sourceSpecHash` 的实现就是自由的。

### 6.2 两个字段的结构

| 字段 | 结构 | 谁是引用 |
|---|---|---|
| `trigger_json` | `{ kind, ref, text }` | **只有 `ref`** |
| `sync_json` | `{ with_dialogue, dialogue_span, emotion, relation, parallel_with, focus_rank }` | **只有 `parallel_with`** |

### 6.3 定义

```js
function stripRefTrigger(json) {
  const { ref, ...rest } = json || {};            // trigger 只剥 ref
  return rest;                                    // 空对象时返回 {}，不是 null
}
function stripRefSync(json) {
  const { parallel_with, ...rest } = json || {};  // sync 只剥 parallel_with
  return rest;
}
```

### 6.4 八个算例

| # | 输入 | 输出 |
|---|---|---|
| 1 | `{kind:'action', ref:'ac_1', text:'纸被摔在柜上'}` | `{kind:'action', text:'纸被摔在柜上'}` |
| 2 | `{kind:'self', ref:'', text:'自主'}` | `{kind:'self', text:'自主'}`（空串也剥键） |
| 3 | `{kind:'ambient', ref:'sfx:monitor', text:'监护仪报警'}` | `{kind:'ambient', text:'监护仪报警'}` |
| 4 | `null` / `undefined` | `{}` |
| 5 | `{kind:'action', ref:'ac_1', text:'…', strength:0.8}` | 保留 `strength` |
| 6 | sync 六字段 | 除 `parallel_with` 外 5 个全留 |
| 7 | sync `{with_dialogue:'before', parallel_with:[]}` | `{with_dialogue:'before'}` |
| 8 | sync `{…, parallel_with:['ac_2'], tempo:'staccato'}` | 保留 `tempo` |

### 6.5 为什么这里用黑名单，而 `bodyOf()` 用白名单

看着矛盾，其实是两个对象：

| | `bodyOf()` | `stripRef()` |
|---|---|---|
| 对象 | 我们自己的映射对象 | 数据库里的领域 JSON 列 |
| 未知键来源 | 我们的临时变量（`_id`/`_ref`/`_par`）——**一定不是语义** | 未来 schema 演进（`strength`/`tempo`）——**一定是语义** |
| 漏掉的后果 | 临时 id 进 hash，同源证明被污染 | 新语义字段进不了 hash，改了提示词 hash 不变 |
| 该用 | **白名单** | **黑名单** |

一句话：**"我们自己的临时字段"默认不信，"用户数据里的未知字段"默认相信。**

### 6.6 引用关系仍要回填

`stripRef` 只是把引用从"内容"里拿出来，不让它参与内容 hash；引用本身在 `canonicalActions` 第 ④ 步以 `triggerRef` / `parallelWith` 写回 payload，取值是目标的 `contentHash`。因此：

- 改引用**目标的内容** → 目标 `contentHash` 变 → `triggerRef` 变 → `sourceSpecHash` 变（正确，R-34）；
- 改引用**目标的 id 命名**（同步更新引用）→ `contentHash` 不变 → `sourceSpecHash` 不变（正确，R-32/R-33）。
