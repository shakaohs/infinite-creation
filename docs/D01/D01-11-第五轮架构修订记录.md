**后果**：实施者读 `D01-02`（字段规范，最像"字典"的那份）会实现成"只能切 `t_to`"，然后遇到 V3 的算例 E 场景（A1 结束于 5.0、A2 从 3.0 到 13.0）时，切点 5 被 A2 跨越——他会判定"无合法切点"而 `D01-06` 认为 13 合法。**同一份分镜，两份文档给出两种切分结果，都自称合规。**

### 2.2 修订后（V5，唯一权威）

`D01-06 §3.3.1` 保留为唯一算法权威；`D01-02 §10.1` 改为引用它并列出七条规则；`D01-01 §3.3` 只保留"片段合法性"结论。

七条规则（三处逐字同义）：

| # | 规则 |
|---|---|
| 1 | `t == a.t_from` **可以**作为合法切点 |
| 2 | `t == a.t_to` **可以**作为合法切点 |
| 3 | `a.t_from < t < a.t_to` **禁止**（动作执行区间内部） |
| 4 | 候选点必须通过**本镜全部**动作的跨越检查，不是只过"产生该候选的那一个动作" |
| 5 | 动作占半开区间 `[t_from, t_to)` |
| 6 | 切点处的动作**只归属一个片段**（`a.t_to <= t` → 左；`a.t_from >= t` → 右） |
| 7 | 片段内动作时间 `t_local = t_abs - fragment.t_from` |

### 2.3 新增算例 F（`D01-06 §3.3.8`）

**输入**：`sh_32`，`D=18`，A1(0–12)、A2(12–16)、A3(16–18)，`h3.v1`（max 15）。

**关键点**：切点 12 同时是 A1 的 `t_to` 与 A2 的 `t_from`。这是"起点可切/终点可切"两条规则**同时生效于同一点**的唯一形态，V4 没有任何算例覆盖它。

**验算**：

```
crosses(A1, 12): 0+ε < 12 && 12 < 12-ε  → 后者为假 → 不跨越
crosses(A2, 12): 12+ε < 12             → 为假     → 不跨越
→ 12 合法

U1 = sh_32(0,12)  → A1 t_local 0–12
U2 = sh_32(12,18) → A2 t_local 0–4、A3 t_local 4–6
Σfrag = 18 = D ✓   U1 12 ≤ 15 ✓   U2 6 ≥ shortFloor 5 ✓
```

**归属唯一性陷阱（本算例真正要防的）**：

```
正确：左 = (a.t_to <= t)；右 = (a.t_from >= t)
错误：左 = (a.t_from <= t)；右 = (a.t_to >= t)
      → A1 同时满足两侧（12<=12 且 12>=0）→ A1 被播两遍
```

这个错误**不会报错、不会抛异常**，只会让成片里"走到床尾"的动作演两次。半开区间的比较符必须写成 `<=` / `>=`，不能写成 `<` / `>`，也不能写成 `<=` / `>`。

## 四、P1-02 · `contentHash` 的 id 泄漏

### 4.1 原设计（V4）

```js
function contentHashOf(a) {
  const { _id, ...rest } = a;      // 只排除了 _id
  return sha256(canonicalStringify(rest));
}
```

`a` 里还有 `_ref`（`trigger_json.ref` 的原文）与 `_par`（`sync_json.parallel_with` 的原文），**它们是别的动作的 id**。

### 4.2 三个具体后果

| # | 后果 | 说明 |
|---|---|---|
| 1 | 改 id 命名会改 hash | A2 的 `_ref='ac_1'` 进了 A2 的 contentHash；把 A1 改名成 `ac_9` 并同步更新引用，A2 内容一字未改，**hash 却变了** |
| 2 | 排序键与被排序对象互相污染 | 排序键含 `contentHash`，`contentHash` 含别人的 id，而别人的 id 又不进 hash → **重命名可能改变动作顺序** → payload 数组顺序变 → hash 变 |
| 3 | 引用映射实际仍依赖 id | 若实现把 `_ref` 直接放进 body，就等于"用 id 做同源证明"，与 `action.id` 不进 hash 的设计意图直接矛盾 |

第 2 条最隐蔽：它不是"算错"，是"排序不稳定"，只在特定重命名下触发。**R-26（打乱顺序 hash 不变）测不出它**，因为打乱输入顺序不会改 id；只有 R-32（改 id 并同步引用）才暴露。

### 4.3 修订后（V5）

```js
// 白名单：只挑语义字段
function bodyOf(a) {
  return { actor, type, primary, tier, init, trigger: stripRef(trigger_json),
           path, force, speed, power, cog, parts, contact, result, follow,
           recovery, end, sync: stripRef(sync_json), tFrom, tTo };
}
function contentHashOfBody(body) { return sha256(canonicalStringify(body)); }

function canonicalActions(s) {
  const raw = s.actions.map(a => ({ id: a.id, ref: ..., par: ..., body: bodyOf(a) }));
  for (const r of raw) r.ch = contentHashOfBody(r.body);     // ① 先算 hash（不读 id）
  raw.sort(五项全序，末项用 r.ch);                            // ② 排序
  const refMap = new Map(raw.map(r => [r.id, r.ch]));          // ③ id → contentHash
  return raw.map(r => ({ ...r.body, triggerRef: r.ref ? refMap.get(r.ref) ?? `ext:${r.ref}` : null,
                         parallelWith: r.par.map(t => refMap.get(t) ?? `ext:${t}`).sort() }));
}
```

**顺序不可换**：先算 hash（不读 id）→ 再排序（用 hash）→ 再建 id 映射 → 最后回填引用。任何一步提前都会引入 id 依赖。

**为什么用白名单不用黑名单**：

| 方案 | 漏一个字段的后果 | 可见性 |
|---|---|---|
| 黑名单 `{const {_id,_ref,_par,...rest}}` | 新加的临时字段静默进 hash | **不可见**——hash 变了但只有比对才发现 |
| 白名单 `bodyOf()` | 新加语义字段没进 hash | **可见**——R-01（改任一字段 hash 必变）当场失败 |

两种遗漏都会出错，但一种会自己喊，一种不会。选会喊的。

### 4.4 引用映射的确定性边界（新增 `§4.2.2`）

| 情形 | 确定性 | 处理 |
|---|---|---|
| 引用 body 唯一的动作 | ✅ | contentHash 唯一 |
| 两个 body 全等的动作，引用其一 | ⚠️ | 二者 contentHash 相同 → 视为同一目标；记 `REF_AMBIGUOUS_CONTENT`（INFO） |
| 引用目标不在本镜 | ✅ | `ext:<原字符串>` |
| `parallel_with` 乱序 | ✅ | `.sort()` |
| 重复 contentHash 时取"第一个" | ❌ **禁止** | 取 contentHash 本身，不取实例——否则 `SELECT` 顺序决定结果 |

### 4.5 新增回归用例（`D01-06 §4.6`）

| # | 输入 | 期望 |
|---|---|---|
| R-31 | 无引用动作换 `id` | source **不变** |
| R-32 | 被 `trigger.ref` 引用的动作换 `id`，同步更新引用 | source **不变** |
| R-33 | 被 `parallel_with` 引用的动作换 `id`，同步更新引用 | source **不变** |
| R-34 | 只改引用目标的**实际内容** | source **变** |
| R-35 | 打乱动作输入顺序 | source **不变** |
| R-39 | （负向·评审项）把 `_` 开头的键放进 payload / contentHash 的实现 | 必须被拒 |

**这组必须用"同一 fixture、只改 id 命名"跑**。手写两个不同期望值的测法测不出污染——因为两个 fixture 本来就不一样。

## 五、P1-03 · `shot_assets` 顺序约束

### 5.1 原设计（V4）

```sql
order_no INTEGER DEFAULT 0,
PRIMARY KEY (shot_id, role, asset_id)
```

### 5.2 三个缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 主键含 `asset_id`，**不含 `order_no`** | 两个不同音色资产都能写 `order_no=1`（主键不冲突），编译时"谁当 `Audio 1`"取决于 `SELECT` 顺序 |
| 2 | `DEFAULT 0` 让"不写顺序"合法 | 一批资产全是 0，顺序信息实际不存在 |
| 3 | 无 `role` 级顺序约束 | 换音色资产后新旧两行都写 `order_no=1`，两条并存 |

**后果的严重性**：同一份分镜两次编译可能产出两个不同音色的提示词，而 `sourceSpecHash` **一模一样**——"同源"证明会把它们当成同一份产物。这不是"顺序错了"，是"同源证明失效"。

### 5.3 修订后（V5）

```sql
order_no INTEGER NOT NULL,                              -- 1 起，无默认
PRIMARY KEY (shot_id, role, asset_id),
UNIQUE (shot_id, role, order_no),                       -- 同镜同角色顺序唯一
CHECK (role <> 'voice' OR order_no BETWEEN 1 AND 3)     -- 音色槽只有 3 个
```

| 规则 | 落点 |
|---|---|
| 起始值 1（不是 0） | DDL `NOT NULL`，全文统一 |
| 同 `(shot,role)` 连续 `1..n`，跳号 → `ASSET_ORDER_GAP` | 校验 V-25 |
| 重号 → 数据库 `UNIQUE` 拒绝 | DDL |
| `role='voice'` ≤ 3 → 第 4 条 `CHECK` 失败 / `VOICE_OVERFLOW` | DDL + 校验 V-26 |
| 编号映射：`ORDER BY order_no ASC` → `Audio 1/2/3` | `D01-02 §6.2` |

**为什么上限是 3 而不是 4**：不是"暂时不支持"，是**输出格式没有第 4 个槽**——H3 提示词的音色定义是 `Audio 1` / `Audio 2` / `Audio 3`，且每段只定义实际使用者。

### 5.4 三个算例（`D01-05 §4.6`）

| 算例 | 输入 | 期望 |
|---|---|---|
| 一 | 两条 voice 都写 `order_no=1` | **第二条被 `UNIQUE` 拒绝**（V4 会安静存下两行） |
| 二 | 三条 voice，`order_no` 1/2/3 | 全部成功；映射 `Audio 1/2/3` |
| 三 | 两条 voice，`order_no` 1/3 | DDL 放行，校验 `ASSET_ORDER_GAP`（FAIL） |

## 六、P1-04 · `norm_z` 默认值

### 6.1 原设计（V4）

```sql
norm_x REAL DEFAULT NULL,
norm_y REAL DEFAULT NULL,
norm_z REAL DEFAULT 0,        -- ← 问题
```

### 6.2 为什么这是最危险的一处

它不是"某个字段错了"，是**制造了一个无法区分的状态**：

| 库里读到的值 | 真实含义 | 程序会认为 |
|---|---|---|
| `norm_z = 0`（本次写入的确定值） | 人物在地面层 | `known`，位置确定 ✅ |
| `norm_z = 0`（建表默认值补出来的） | **根本不知道 z** | `known`，位置确定 ❌ |

两者在库里**完全一样**。一旦这个值存在，任何下游代码（`posRel`、求差、越轴、hash）都无法分辨，`unknown` 纪律在这里被绕过，而且**不报任何错**。

`D01-04 §5.3` 说"`unknown` 不能被程序补成确定"——`DEFAULT 0` 就是数据库层在替程序补。

### 6.3 修订后（V5）

| 改动 | 内容 |
|---|---|
| DDL | `norm_z REAL DEFAULT NULL`，列注释写明"0 是合法确定值，NULL 才是没有" |
| 整体性 | 三列**同写同空**；`posRel()` 要求三个分量都非 null 才可能 `known` |
| 校验 | `COORD_PARTIAL`（S-24，FAIL）拦"部分有值部分空"；S-25 禁止把缺坐标当 `known` |
| 迁移 | **禁止** `UPDATE ... SET norm_z=0 WHERE norm_z IS NULL` |
| 历史行 | 一律 `unknown`（`src='legacy:no_coord'`），除非人工重拖 |

### 6.4 五个必测算例（`D01-04 §5.2.2` + R-38）

| # | 输入 | `rel` | source hash 关系 |
|---|---|---|---|
| 1 | x/y/z 全有（manual） | `known` | 基线 |
| 2 | x/y 有、z 缺 | `unknown` | ≠ 1 |
| 3 | 全缺 | `unknown` | ≠ 1、≠ 2 |
| 4 | z 明确 = 0 | `known` | ≠ 2（0 ≠ NULL） |
| 5 | 历史行（默认值补的 0） | `unknown` | ≠ 4 |

第 4 与第 5 是同一列、同一个值 `0`，**唯一区别是来源**。这正好说明：光靠值判不出来，必须靠 `meta`/`spec_source`——所以 hash 必须同时含值与可靠性（`D01-04 §5.2.2` 末段）。

### 6.5 一个实施期会复发的坑（R-11）

SQLite 不支持 `ALTER COLUMN`。改列默认值必须重建表。而现有 `db.js` 的迁移风格是 `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN`。

**若实施时照这个风格写 `ALTER TABLE shot_blockings ADD COLUMN norm_z REAL DEFAULT 0`，本轮的修复会原样失效，且不报错。** 已列为开工必检（`D01-07 §四 R-11`）。
