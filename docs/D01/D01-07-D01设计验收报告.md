## 三、每个 A 类里隐含的 B/C/D（诚实拆解）

| 编号 | 设计已满足的部分 | 仍隐含的缺口 | 类别 |
|---|---|---|---|
| P0-01 | 切点判定规则、边界语义、两个算例 | 跨越检查 O(候选×动作)，大动作量未优化；真实 62 镜未跑 | B / D |
| P0-02 | 排序与两个量的定义 | `coverage>0.9` 阈值估的；`spanRequired` 未与真实稿校准 | B |
| P0-03 | 五处文字统一 | 3 个旧读入口未切，M2 前新项目在旧页面会白屏 | **D（硬前置）** |
| P0-04 | 选择链四级、五项不重复证明 | `default_track` 为空时按 `updated_at` 取最新，用户可能未察觉轨道变化 | B |
| P1-01/02/03 | 列数与 DDL 对齐 | 未 `PRAGMA` 实测 | **D** |
| P1-04 | 唯一键唯一版本 | 未建表，无法验证插入行为 | **D** |
| P1-05 | 权威划分 + V-23 | 历史项目 `voice_ids` 与关联表可能本就不一致 → V-23 会集体 FAIL | B |
| P1-06 | 五项全序 + R-26/R-27 | `contentHash` 依赖规范化规则，规则变动即契约变动 | B |
| P1-07 | 五形态 × 两类别 + 算例 | **模型是否肯写 unknown 完全未知**（这是整个机制的前提） | **C** |

**P1-07 的 C 类最要命**：整套可靠性模型建立在"模型会老实标 unknown"上。若 LLM 一律填值并把 `spec_source` 写成 `manual`，`normalizeRel` 会把它们当 `known`，前面所有防线失效。**规则能约束程序，约束不了模型。**

## 五、结论

| 问题 | 回答 |
|---|---|
| V3 的定义冲突是否消除 | **是**。12 项 P0/P1 的冲突点均在文档层面消解，且每项附算例 |
| 是否新增了设计内容 | **很少**。只补了"片段内时间重基""状态置信度衰减""投影字段映射"三个实现必需但 V3 漏掉的点 |
| 是否可以开始写代码 | **不能全量开工**。三件前置：R-2（`blocking` 列）、R-7（读入口）、R-6（建表后 PRAGMA 复核） |
| 是否已验证 | **没有**。0 行代码、0 次 DDL、0 次真实出片 |

> **D01 V4 是一份"冲突已清除、但完全未验证"的架构契约。**
> 它的价值在于：实施人员不需要猜设计者的意图——每个歧义点都写了"取哪个值、为什么、算例是什么"。
> 它的局限在于：所有算例都是手算的，没有一行代码跑过。**是否进入实施，由独立复审决定。**
