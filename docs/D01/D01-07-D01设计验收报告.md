### 3. 动作结构可以被程序处理，而非仅换 JSON 皮

| V1 缺陷 | V2 修正 | 可验证点 |
|---|---|---|
| `path.from/to` 是字符串 | **坐标** `{x,y,z}` + `label` 人读 | 可算距离、可判穿模（A-05） |
| `result` 是描述 | `char_delta` / `prop_delta` / `env_delta`，`prop_delta` 带 `from→to` | 可直接推 `state_out.props`（`D01-03 §7.3` Step 1） |

**完整算例**：`D01-03 §7` 给出 state_in + 3 个动作 → 逐步 apply → state_out（含两人坐标 + 道具 placed/fx_table）→ 与下镜比对。每一步都可手工复核。

### 4. 状态继承算法有完整的输入、输出和可计算依据

`D01-04 §5.3` 给出六步算法：

- **输入**：`projectId` / `sceneKey` / `shots[]`（含 blockings/actions）/ `sceneState`；
- **输出**：`states{ in, out, derived_from, conflicts }` + `sceneConflicts` + `hash`；
- **依据**：前镜 `state_out` 复制 → 与本镜 `shot_blockings` 求差 → 差异须有动作覆盖 → `state_out` 由 `result` 逐条 apply；
- **依据的可计算性**：位置差用归一化距离（阈值 0.15 / 1.5）、姿态用枚举差、持物用 `hand` 字符串差 + `manipulation` 存在性、道具用状态机迁移。

**边界情形已定义**：无前镜 → `scene_baseline`；`time_jump=1` → 差异降 INFO；`state_source='none'` → 标未结构化不求解。

## 三、本轮最需要被看到的三件事

### 3.1 上一版有一处"看起来对但根本执行不了"的设计

越轴算法。V1 写了叉积判侧，却没给机位坐标字段，也没检查历史数据是否有坐标。结果是一个**在任何真实数据上都跑不起来的检测器**，而且会输出 PASS。

V2 的修法不是"改算法"，而是：**先补数据字段（cam_pos 等），再定义数据不足时必须承认算不了。**

### 3.2 发现一个部署级隐患（不在 D01 范围内，但必须记录）

`shots.blocking` 列被 `Shots.create` 的 INSERT 语句依赖，但**不在 `initSchema` 的建表语句里，也没有任何 `ALTER` 语句添加它**。现有 `data/ic.db` 是历史演进出来的，所以没暴露；在一个全新初始化的库上，第一次写分镜就会抛 `no such column: blocking`。

D01 不改代码，但这条必须在实施阶段处理（`D01-05 §10 R-1`）。

### 3.3 关于"字段数量"的口径

V1 说"47 字段"，把主表和从表混在一起数，评审据此无法核对。V2 明确分三类：**41 业务字段 / 48 持久化列 / 从表 20-22 列**，并且每一处在文档里都标了口径。
