## 一、任务书 9 个必答问题 · 逐条回答

### Q1 一份专业分镜究竟由哪些数据组成？

**答**：47 个字段，分 10 个分区（`D01-02` §1）：

- **主表 34 字段**：标识归属（9）/ 剧作意图（4）/ 画面（3）/ 摄影六要素（8）/ 声音（6）/ 时间（4）
- **从表 3 类 1:N**：逐人空间（17 字段 × N 人）/ 动作（20 字段 × N 个）/ 首尾状态（1 组）
- **资产引用 7 类**：角色/场景/道具/服装/年龄/音频/参考包

关键判断：分镜**不是一张表**，而是「1 个主表 + 3 个从表 + 1 个场景基线」的最小集合。任何试图塞进单表或单个 JSON 的方案都会在"逐人 / 逐动作"的 1:N 关系上崩掉（`D01-01` §4.1 已做三方案比较）。

---

### Q2 一个镜头如何准确表达导演意图？

**答**：三层表达（`D01-02` §3–5）：

| 层 | 字段 | 作用 |
|---|---|---|
| 为什么拍 | `purpose`（7 枚举）+ `dramatic_value` + `info_delta` | 把"废镜"变成可判定项：没有 purpose 的镜无法解释存在理由 |
| 让观众看什么 | `shot_size`（9 档）+ `cam_direction`（5）+ `cam_height`（8）+ `lens_mm` + `movement`（21）+ `movement_amp` | 受控词表，全部来自 Skill，可机检配额（荷兰角 ≤1/集、侧面 ≤15%） |
| 怎么构图取景 | `composition_rule`（7）+ `composition` + `cam_note` | 枚举保证可算，`cam_note` 保留物理可行性描述（过肩需退 1.5–2m） |

**关键**：六要素拆开后，"连续三镜同景别""大仰角超 3 次""特写比例 <25%"这类规则才第一次变得可机检——现状只能靠字符串匹配（审计 03 §3）。

---

### Q3 如何保存人物站位、朝向和动作？

**答**：三层空间 + 三档动作（`D01-04` §2/§4，`D01-03` §2）。

**站位**（`shot_blockings`，每人一行，17 字段）：

- 人读层：`position_abs`（"病床右侧·床头柜旁 0.6m"）、`anchor_object`（依托物）、`behind_object`
- 机器层：`norm_x/y/z`（归一化坐标）+ `norm_confidence` → 越轴、距离、遮挡、位移连续性**全部可算**
- 关系层：`facing` / `gaze_target` / `distance_to_camera` / `occlusion` / `power_level`
- 状态层：`posture` / `hand_state` / `current_task` / `in_frame` / `instance_anchor`

**为什么必须"两套坐标"**：文字方位模型能渲染但程序算不了，数值坐标程序能算但模型读不懂。二者互为校验（文字说东、坐标在西 → FAIL）。

**动作**（`shot_actions`，20 字段）：按 T1/T2/T3 三档粒度，文戏 7 项、标准 12 项、关键重击全 18 项 + 11 环发力链。**不强制所有镜写满 11 环**——Skill 原文即写"过度细节同样有害"。

### Q4 如何让后续镜头继承前面的状态？

**答**：`state_in` 由程序求解，不由模型填写（`D01-04` §5.2）。

```
state_in = 上一镜 state_out（全量沿用）
         → 与本镜 shot_blockings 逐人求差
         → 差异无动作依据 = 冲突（POSITION_JUMP / POSTURE_JUMP / HAND_JUMP …）
state_out = state_in + 本镜各动作 result/end_state 逐条 apply
```

**这解决了什么**：现状 `blocking` 每段重写，写的人只能凭记忆；新模型里"上一镜他在床右侧 0.6m"是数据库里的一行，本镜写"床左侧"立刻报冲突。

**关键设计**：`derived_from` 记录求解来源（`prev_shot:<id>` / `scene_baseline`），使继承链可追溯、可重放。

---

### Q5 如何判断连续性问题？

**答**：一张判定矩阵 + 17 条规则（`D01-04` §6/§11）。

矩阵核心逻辑：**变化本身不违规，"无依据的变化"才违规**。

| 变化 | 有动作依据 | 无依据 |
|---|---|---|
| 位置 ≤0.15 | 放行 | 放行（自然微调） |
| 位置 0.15–1.5 | 放行（locomotion） | `POSITION_JUMP` FAIL |
| 姿态坐→站 | 放行（cog=rise） | `POSTURE_JUMP` FAIL |
| 持物→空手 | 放行（manipulation） | `HAND_JUMP` FAIL |
| 道具 held→placed | 放行（contact） | `PROP_TELEPORT` FAIL |
| 视线任意变 | 放行（视线自由） | — |

新增能力：**越轴第一次可真判**（`D01-04` §8）——用坐标 + 机位推算侧别，白名单式跨轴，无法判定时输出 `AXIS_UNVERIFIED` 而不是假 PASS。

### Q6 如何区分人物动作与摄影机运动？

**答**：两张独立字段表 + 归属判定表（`D01-03` §6）。

- 人物动作 → `shot_actions`（actor / path / cog / contact / result）
- 摄影机运动 → `story_shots.movement`（21 枚举）+ `movement_amp`
- **三条硬规则**：同一件事不得两处都写；跟随类运镜必须有人物位移作理由；人物位移必须有落点
- 判定表覆盖 9 种常见现象（"镜头跟随他起身"这类混写被明确拆开）

**可机检**：`movement ∈ {tracking, pan}` 且本镜无 `locomotion` → WARN「无位移目标却跟拍」。

---

### Q7 如何兼容历史数据？

**答**：S3 双层并存 + 三层读取 + 四阶段迁移（`D01-01` §9，`D01-05` 全文）。

| 项 | 结论 |
|---|---|
| 现有 37 列 | **零删除、零重命名**；30 列原样保留，5 列保留但语义重定义（值不变），1 列标记 deprecated |
| 历史 66 条分镜 | 不批量迁移；读取时从 `sub_shots` 解析"影子镜"（内存态，`spec_source='legacy'`） |
| 历史 55 条提示词 | 原地不动；首次新编译时归档为 `track='legacy'` 的 package，可对照不可静默覆盖 |
| 旧 `duration`（段时长） | 语义明确为 `unit_duration`；镜时长按 `sub_shots` 时间轴切分，**不直接复用** |
| 迁移风险 | 四阶段（M0 建表 → M1 只读 → M2 双写 → M3 回填），每阶段可停可回滚 |
| 数据不丢验证 | 7 项对账（行数守恒 / 字段指纹 / 可读性 / 提示词复现 / 镜数对账 / 资产引用 / 回滚演练） |

**关键决策**：不新建 `render_units` 表，而是给现有 `shots` 建只读视图——因为 `shots` 一行本就等于一个渲染单元（有代码级证据，`D01-01` §1.2）。新建表会导致双写双读、数据分裂。

---

### Q8 如何让 Seedance 和 H3 使用同一份分镜？

**答**：三轨时长 + 单一适配层 + `sourceSpecHash`（`D01-01` §7，`D01-06` §3/§4）。

| 机制 | 作用 |
|---|---|
| `story_duration`（镜，无模型上限） / `unit_duration`（单元，受 profile 约束） / `timeline_duration`（成片） | H3 的 15s **只作用于单元切分**，不回写镜头 |
| 适配层 `splitIntoUnits` 独立于两个编译器 | 避免"两个编译器各切一套单元" |
| 两个 Compiler 输入同一 `ShotSpec`，输出各自的 `prompt_packages` | 分叉只发生在编译态 |
| `sourceSpecHash` 必须逐字相同 | **这是"同一份分镜"的机器可读证据**，可直接做成回归断言 |
| 双向污染检测 | Seedance body 含 H3 段名 / 反之 → 0 命中 |

**反向验证**：若某天有人给 Seedance 单独加了一个"分镜字段"，`sourceSpecHash` 立刻会不一致，CI 直接失败——从机制上防止"两套分镜"。

---

### Q9 如何为后续提示词编译和自动质检提供可靠输入？

**答**：四层模型 + 写权限表 + 分离原则（`D01-01` §3/§8，`D01-06` §1）。

| 机制 | 内容 |
|---|---|
| 四层数据 | 创作态 → 适配态 → 编译态 → 执行态，**单向**，编译发现装不下只能报错不能改创作 |
| 写权限表 | 9 个模块各自可写表明确；Continuity 只能写 `shot_states`，QC 只读，Repair 只能出 patch |
| 职责分离 | 模型产出规格，程序验规格；**校验器与创作器物理分离**，`qc_reports` 由独立模块写 |
| 规则来源可溯 | 每条规则注明来自哪个 Skill 文件哪一节（如景别 9 档来自 `short-drama-camera-system.md` §一） |
| 版本戳 | `spec_version`（数据）与 `compiler_ver`（程序）分开，`prompt_packages` 带双版本 + 双 hash |

| # | 决策 | 推荐方案 | 否决方案 | 否决理由 |
