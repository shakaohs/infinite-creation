## 二、P0 逐条

### P0-01 · 三种哈希必须分开

**原设计（V2）**

`D01-06 §4.2`：

```js
const payload = {
  scene: ...,
  unit: canonical(unit, ['track','profile_ver','unit_duration','seam']),   // ← 含 track
  shots: [...],
  fragments: (unit.fragments||[]).map(...)                                  // ← 含切分
};
```

回归用例：H-19「改 `track` → hash 变」、H-20「改 `fragments` → hash 变」、H-21「双编译器同输入两 `sourceSpecHash` 逐字相同」。

**发现的问题**

三个用例**互相否决**：

- `track` 在 payload 里 → Seedance 传 `track='seedance'`、H3 传 `track='h3'`；
- 两者 payload 必然不同 → hash 必然不同；
- 所以 H-21「逐字相同」**在数学上永远不成立**。

也就是说，V2 声称"能证明同源"，但它定义的函数在结构上就输出不了同源结果。而 H-19/H-20 把这个错误固化成了"预期行为"。

**修订后的设计**

拆三个正交哈希（`D01-06 §4`）：

| hash | 覆盖 | 排除 |
|---|---|---|
| `sourceSpecHash` | 场景依赖 + 完整 ShotSpec（41 业务字段）+ 逐人空间 + 动作 20 字段 + 首尾状态 + 状态 `meta` + 资产引用与指纹 | `track` / `profile_ver` / `unit_duration` / `unit_no` / `seam` / 片段范围 / `id` / 时间戳 |
| `adaptationHash` | `track` + `profile_ver` + **profile 三参数快照** + `seamPolicy` + 单元划分 + 片段映射 + `adaptation_version` | `sourceSpecHash`（刻意不混，否则无法单独回答"切法变了没"） |
| `compiledHash` | `sourceSpecHash` + `adaptationHash` + `compilerVer` + 编译参数 | — |

关系：`source ⊥ adaptation → compiled`。给出 6 种操作的 hash 变化表（§4.4）与 25 条回归用例（§4.6），其中 R-20/R-21/R-22 是"改 track / 改 profile / 重切 → **source 不变**"，R-25 是 CI 断言。

**修改理由**

"导演做了什么""怎么切成片""用什么程序编译"是三件事，一个 hash 装不下。混装的后果不是"hash 不准"，而是**同源证明这件事本身失效**——因为不同轨道的 hash 永远不同，也就永远无法用 hash 说"这是同一份分镜"。

**文档位置**：`D01-06 §4.1~§4.7`；`D01-07 §一.6`；`D01-05 §4.14`（`source_spec_hash` 列的用途）

**验证方式**：R-01~R-24 单测（纯函数、固定 fixture）+ R-25 CI 断言。**本轮未实现，只定义。**

**未决**：hash 值本身无法在文档里验算。§4.4 的同源示例里 `sha256:3f9a…` 是占位，不是真实计算结果。

### P0-02 · 适配方案必须是一等实体

**原设计（V2）**

`D01-05 §4.7`：

```sql
CREATE TABLE render_units (
  ...
  track TEXT NOT NULL,
  profile_ver TEXT DEFAULT '',
  unit_no INTEGER NOT NULL,
  status TEXT DEFAULT 'draft',   -- 含 superseded
  superseded_by TEXT DEFAULT '',
  ...
);
CREATE UNIQUE INDEX uq_ru_no ON render_units(project_id, track, unit_no);
```

**发现的问题**

| 场景 | V2 会发生什么 |
|---|---|
| 同模型换 profile（sd25 → sd20）重新切 | 新单元同样是 `(项目, seedance, 1..6)` → **唯一冲突** |
| 同 profile 重切（改了 seamPolicy） | 同上，**唯一冲突** |
| 想保留旧方案 | 只能先删旧行或改 `unit_no`（改了就丢原编号） |

`superseded` 挂在单元上还有个语义问题：**"部分单元被取代"没有意义**——被取代的是整套切分。

**修订后的设计**

新增 `render_adaptations`（当时计 14 列；**该计数有误，V4 重数为 17 列**，见 `D01-10 §三 P1-02`）：

```
(chapter_id, track, profile_ver, adaptation_version)  唯一
profile_max / profile_short_floor / profile_min_slice  ← 参数快照
seam_policy / source_spec_hash / shot_scope_hash
status ∈ active | superseded | failed
```

`render_units` 改为 12 列，加 `adaptation_id`，去掉 `superseded_by`，唯一键改 `(adaptation_id, unit_no)`。

`render_unit_shots` 唯一键从 `(unit_id, shot_id, t_from)` **收紧**为 `(unit_id, shot_id)`，并补 `(unit_id, order_no)`。

**修改理由**

1. 版本是一等概念，不能是单元上的几个列——否则"哪些单元属于旧参数"无法回答；
2. **profile 参数必须快照**：`h3.v1` 的 `max` 若从 15 改成 20，旧方案的 `adaptationHash` 会变但切分结果不变，两者不再对应。快照三个数值才能复算 hash；
3. 片段完整性**作用域必须是 adaptation**：跨 adaptation 的片段重叠是合法的（不同版本方案），拿它判 `FRAG_OVERLAP` 是误报；
4. `(unit_id, shot_id)` 收紧的依据是切分算法的不变量：一镜被劈开是因为当前单元装不下，劈完立即 `close()`，所以**同一单元内不可能出现同一镜的两行**。V2 的 `(unit_id, shot_id, t_from)` 留了一个永远不该被用到的口子。

**文档位置**：`D01-05 §4.7/§4.8/§4.14/§8.3`；`D01-06 §3.2/§3.4`；`D01-01 §3.1.1/§3.5/§2.1`

**验证方式**：DDL 语法可执行（未执行）；索引冲突场景用 4 行数据手推（见 `D01-05 §4.7` 对照表）。

**未决**：`uq_ra_active`（同章同轨道至多一个 active）**故意不用部分唯一索引**，改应用层 + 巡检。理由是历史库若已有两个 active，建索引会让启动崩。这是妥协，不是最优解。

### P0-03 · 切分算法必须能跑

**原设计（V2）**

`D01-06 §3.3`：

```
acc = 0
for shot in shots:
   if acc + shot.story_duration > profile.max:
      在当前单元结束前，找最后一个 is_cut_point=1 的镜作为断点
      若无可用剪辑点 → 在最近的「动作 t_to」处劈开当前镜（split_reason='oversize'）
   acc += 截取长度
if 尾单元 < profile.shortFloor:
  并入前单元（若合并 ≤ max）或标 SHORT_UNIT
```

示例（`§3.5`）：

```json
{ "unitNo": 3, "track": "h3", "shots": [
    { "shotId": "sh_19", "tFrom": 0, "tTo": 6.0 },
    { "shotId": "sh_20", "tFrom": 0, "tTo": 9.0, "splitReason": "oversize" } ] },
{ "unitNo": 4, "track": "h3", "shots": [
    { "shotId": "sh_20", "tFrom": 9.0, "tTo": 20.0, "splitReason": "oversize" },
    { "shotId": "sh_21", "tFrom": 0, "tTo": 5.0 } ] }
```

**发现的问题**

| # | 问题 |
|---|---|
| 1 | **`acc += 截取长度` 里的"截取长度"从未定义**——伪代码是空转的，示例是手写的 |
| 2 | **U4 = 11.0 + 5.0 = 16.0 > 15**（H3 上限），超限 1 秒 |
| 3 | **切点 9.0 不在 sh_20 的任何动作 `t_to` 上**（动作断点是 3/7/11.5/16），落在动作中段 |
| 4 | "找最后一个 `is_cut_point=1` 的镜作为断点"——`is_cut_point` 是**镜后**的边界，不是镜本身，措辞模糊 |
| 5 | 没有"剩余空间不足 `minSlice`"的分支 → 会切出 0.5s 的碎片 |
| 6 | 尾单元合并只写了"若合并 ≤ max"，没说合并以什么为界、合并后 `unit_no` 如何重排 |

**修订后的设计**

`D01-06 §3.3.2` 给出可执行伪代码：三分支（①整段装下 ②剩余空间 < `minSlice` 则关单元 ③在 `[consumed+minSlice, consumed+room]` 内取**最大**合法切点）+ 尾单元合并 + `unit_no` 重排。`legalCuts()` / `pickLegalCut()` 单独定义。

关键决策：
- 切点集合 = `{0, story_duration} ∪ {a.t_to}`，**只取 `t_to`**；
- 无合法切点时：空单元 → 返回 `ADAPT_NO_LEGAL_CUT`（**适配失败，不硬切**）；非空单元 → 关单元重试；
- 取最大切点（装得更满，出片次数更少）。

三个算例（§3.3.3 / §3.3.4 / §3.3.5）每个都写 `Σfragment ≤ unit_duration ≤ max` 的逐项校验。

**修改理由**

伪代码与示例不对应，示例就没人验算——V2 的 16 > 15 存在了一整轮无人发现，就是因为"示例看起来挺像"。

**文档位置**：`D01-06 §3.2~§3.5`；`D01-02 §10.1`（合法切点集合）；`D01-05 §4.14`（profile 参数快照）

**验证方式**：三个算例可手工逐行复核。**未在真实 62 镜上跑过。**

**未决**：贪心不是全局最优（见 `D01-06 §3.3.2` 的权衡说明）。全局最优能减少单元数，但要多切一次镜、多一个接缝，且会打乱镜序。是否值得，需要真实数据对比。

## 三、P1 逐条

### P1-01 · 动作时间：从"加法"改成"区间"

**原设计（V2）**

`D01-03 §5.2`：

```
1. 并查集分组
2. 每组占用 = max(组内时长)
3. 总占用 = Σ over groups
4. 可用 = story_duration - 台词占用 - 起势 - 收势
5. 总占用 > 可用 → FAIL
```

**发现的问题**

| 错误 | 说明 |
|---|---|
| **E1 跨人相加** | A1(哈罗德 1.6s) + A3(凯森 1.0s) = 2.6 → 这是「人工时」，不是「镜头时长需求」。三人同时动作，镜头仍只占 1.6s |
| **E2 扣台词** | 把台词时长从动作可用时长里减掉 = 强制台词与动作串行。但 V2 自己在 §6 T-6 写着"边说边做允许"——**两处规则互斥** |
| **E3 算例算术** | 同一句台词既算"中文 48 字符"又算"英文 12 词"；`48/3.5 = 13.7s > 4.5s` 却称合规；`dialogue_span=[1.6,4.5]`（2.9s）与"占满 4.5s"不一致 |

E3 的后果：V2 用这个算例得出「2.6 > 0.8 → FAIL」，把完全正常的三人病房戏判死。

**修订后的设计**

`D01-03 §5.2`：

```js
requiredMin = max over actors ( unionLen(actor) )   // 不跨人相加
perActor[actor].coverage = unionLen / story_duration
同 actor 区间重叠 + 共享 body_parts 独占组 + 未声明 parallel_with → FAIL
台词：不扣减；只算语速（按 dialogue_span）+ 口型冲突（说话人同时有 head/face 且 power≥8）
```

`body_parts` 分五个独占组（头面/躯干/右臂/左臂/下肢），左右臂独立（左手操作 + 右手握手合法）。

**§5.4 用同一组数据重算**：`requiredMin = 1.6 ≤ 4.5`，`coverage` 最高 0.36，无部位冲突，台词 8 词 / 2.75s = 2.91 词/秒 → **合规**。并附 V2 算例的逐项核对表。

**修改理由**

"动作要塞多久"和"这个人有没有在做两件互斥的事"是两个问题。V2 用一个加法同时回答，两个都答错。区间并集是正确的度量：镜头时长要能容纳**最忙的那个人**，而不是所有人的总和。

**文档位置**：`D01-03 §5`（全节重写）、`§6 T-1`（并行动作无法被互不重叠的时间片覆盖）、`§7.5`（算例时间账）、`§8 A-11/A-12/A-13`；`D01-02 §13 V-09/V-10`

**验证方式**：§5.4 算例可手工复核；§7.5 与 §7 的位置算例对照。

**未决**：`coverage > 0.9` 判"无呼吸"的阈值是估的，未用真实分镜统计校准（`D01-07 R-6`）。

### P1-02 · 未知状态：加第四维

**原设计（V2）**

状态是裸值：`{"pos":[0.30,0.70], "posture":"standing"}`。`D01-04 §5.3` 直接按阈值判 `POSITION_JUMP` / `POSTURE_JUMP`。

**发现的问题**

- 没有"这个值不确定"的表达方式 → 缺值只能二选一：要么不写（当作没有），要么编一个（当作有）；
- 历史 66 条分镜**没有一条有物理坐标**。若"缺数据"走"不判"分支，QC 全绿；若走"判"，则创作者被判死；
- 更坏的情况：模型为了"看起来完整"，把 `pos` 填成 `[0.5,0.5]` 这种占位值，程序当作事实使用，**假的精确比明显的缺失更危险**。

**修订后的设计**

`D01-04 §5.3` 四值 + `§5.2` 平行 `meta`：

| rel | 可否 PASS | 可否 FAIL | 来源 |
|---|---|---|---|
| `known` | ✅ | ✅ | manual / prev_shot / action |
| `inferred` | ⚠️ 只 WARN | ❌ | `rule:<name>` |
| `unknown` | ❌ | ❌ | `no_source` |
| `not_applicable` | ❌ | ❌ | `na_rule:<name>` |

- `meta` 用**扁平键路径**（`"chars.<id>.<field>"`）而非给每个值套壳：值形状零变化，旧解析器不受影响；
- 缺省 = `known`（有意默认，因为绝大多数字段确实确定）；
- **`meta` 只能由 Continuity Engine 与人工写，LLM 不得写**——否则模型会把自己的猜测标成 known；
- §5.4 给 Kleene 三值传播表 + "可以继承 / 需动作依据 / 需人工确认 / 不能计算"四张清单；
- §11 新增 S-20/S-21 **"规则的规则"**：任何对 unknown/inferred 判 FAIL 的实现都算 QC 自身 bug；
- `verifiable_ratio` 单独统计，避免"因为没数据所以全绿"。

**修改理由**

原则 6 说"未知不得被程序擅自补成确定状态"。V2 里这条无法落地，因为**状态没有"未知"这个值**——没有表达方式，规则就是口号。

**文档位置**：`D01-04 §5.1~§5.6`、`§8`、`§11 S-20/S-21`；`D01-02 §〇`（`shot_states` 8 列）、`§13 V-19/V-22`；`D01-06 §2.2/§2.4`（下游如何处理 unknown）；`D01-05 §4.5`（`meta` 列）

**验证方式**：三值逻辑表可逐格手推；`D01-03 §7` 的算例可对照（但该算例全程 known，未演示 unknown 分支）。

**未决（重要）**：**规则能约束程序，不能约束模型。** LLM 是否肯写 `unknown` 而不是编一个数，只能实测。已列为 `D01-07 R-3`，并给了判据：20 镜试跑，主动写 `unknown` 比例 < 50% 则该机制形同虚设。

### P1-03 · 摄影机几何：一个公式拆成两个

**原设计（V2）**

`D01-04 §6.2` Step 4：

```
a_left = cross(axis, pos_a - cam_pos) > 0
若 a_left != (axis_lock.left == a.id) → LEFT_RIGHT_FLIP (FAIL)
```

**发现的问题**

1. `cross(axis, pos_a - cam_pos)` 算的是"A 相对**轴线**的哪侧"，其中还混进了机位位置；它与"A 在**画面**的左右"没有必然关系；
2. 画面左右取决于**摄影机朝向**：`screen_x = dot(A - cam_pos, right)`，`right` 由 `forward × worldUp` 得到。摄影机转个身，同一物理位置的人在画面里就换边；
3. V2 用 `side='left'/'right'` 描述机位侧别，又用 `left/right` 描述画面左右——**两个 left 不是同一个 left**，代码必然串；
4. Step 4 拿本镜 `a_left` 与**场级** `axis_lock.left` 比，层级错位；
5. `D01-02 §4.6` 的 P-A 条件引用了 `cam_axis_side` 字段——**D 区 14 字段里根本没有这个字段**。

**修订后的设计**

`D01-04 §6` 全节重写：

| 检测器 | 回答 | 输入 | 输出 |
|---|---|---|---|
| `AXIS_SIDE` | 机位在轴线哪侧 | `axis_line` + `cam_pos` | `side ∈ {A, B, on_axis}` |
| `SCREEN_LR` | 人在画面哪边 | `cam_pos` + `cam_target` + `cam_roll_deg` + 人物坐标 | `screen_x` 符号 |

- 给出基向量构造（`forward` / `right` / `up` + 滚转旋转）、退化检测（正俯拍 `forward ∥ up`）；
- 命令用 `A`/`B` 而非 `left`/`right`，彻底断开与画面左右的命名纠缠；
- **组合判定**：换侧 + 左右翻转 → `LEFT_RIGHT_FLIP`(FAIL)；换侧但未翻转 → `AXIS_CROSS_SOFT`(INFO)；未换侧但左右翻转 → `LR_FLIP_SAME_SIDE`(WARN)；
- **数值算例**（§6.6）：两次完整投影，Q 从画面左 → 画面右，附反例说明"只看侧别会误报"；
- `cam_pos` 统一为**米制世界坐标**（`D01-02 §4.0` G1~G4），归一化只在 `norm_xyz` 保留并提供唯一换算点。

**修改理由**

越轴本身不是错误，**造成观众方向感混乱**才是。而"混乱"只能由画面左右关系翻转来判定，不能由机位侧别推定。

**文档位置**：`D01-04 §6.1~§6.8`、`§11 S-05~S-07/S-22/S-23`；`D01-02 §4.0/§4.6/D4~D6`；`D01-06 §4.2`（`cam_pos` 进 hash）

**验证方式**：§6.6 两镜算例可手工重算（叉积、归一化、点积都有中间值）。

**未决**：`cam_roll_deg` 的正负号在不同渲染器上可能相反，**必须用测试图实机校定**（`D01-07 R-5`）。未校定前所有含滚转的镜头只算不滚转近似并标 `ROLL_UNVERIFIED`。

### P1-04 · `shots` 策略：定案不双写

**原设计（V2）**

**修订后的设计**

| 方案 | 否决理由 |

### P1-05 · 验收：不再自宣

**原设计（V2）**

`D01-07` 由设计编写者出具，结论「18 项 P0/P1 全部关闭」「D01 V2 可作为工程实施依据」。`D01-08 §一` 也写"6/6、12/12、4/4 全部关闭"。

**发现的问题**

1. 自己宣布自己合格，不构成验收；
2. "设计已满足"与"能在真实环境跑通"混为一谈；

**修订后的设计**

- `D01-07` 重写，结论改四分类（A 设计已满足 / B 部分满足 / C 需真实环境 / D 需实施验证），**明令"关闭"一词不得单独出现**；

- `D01-08 §〇` 追加第三轮补正，把"全部关闭"降级为"当时声称关闭"。

**修改理由**

一个说"全部通过"的验收报告，比没有验收报告更糟——它让人停止检查。

**文档位置**：`D01-07`（全文重写）、`D01-08 §〇/§一`、`D01-05 §1.1.1`

**验证方式**：本节的 `git ls-files` / `git check-ignore` 输出可在仓库内任意复现。

**未决**：把脚本移到 `docs/D01/evidence/` 并提交这件事，**本轮没做**（属新增文件，且需脱敏检查）。列在 §四。

## 七、一句话总结

第三轮修的不是"字段不够"，而是**六处"看起来对、实际算不出"的伪精确**：同源 hash 永假、切分算例超限、台词计时串行、越轴拿侧别当左右、冻结与双写并存、唯一键装不下版本。改法统一是：**把"应该相等"换成"能算出来的关系"**，算不出来的一律输出 `UNVERIFIED`，而不是输出一个好看的结论。
