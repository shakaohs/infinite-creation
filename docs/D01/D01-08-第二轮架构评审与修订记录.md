## 二、P0 逐条记录

### P0-1 · Shot 与 RenderUnit 的关系

**原设计（V1）**

- `D01-01` 的 ER 图写了 `render_unit_shots`（N:M）；
- `D01-05` 的 DDL 只给 `story_shots.render_unit_id`（1:N）；
- `D01-06` 的适配层输出单单元。

**问题**

三份文档三种说法。评审要求的六个场景（双轨同用、组合不同、换 profile、超长镜、多单元引用、多适配片段）中，有四个在 1:N 下无法表达。

**新设计（V2）**

1. **统一为 N:M**，删除 `story_shots.render_unit_id`；
2. 关联表 `render_unit_shots(id, unit_id, shot_id, order_no, t_from, t_to, split_reason)`，**本身就是片段映射结构**——`t_from/t_to` 定义"该镜在本单元里截取哪一段"；
3. 每一镜进每个单元都写一行，**即使完整镜**也写（`0 ~ story_duration`），不设例外；
4. `render_units` 改为**新表**（V1 的视图方案废止），因为视图无法承载 `track` / `profile_ver` / `superseded_by`，且一项目双轨需多行；
5. `shots` 表**冻结为 legacy 单元**，不再新增行。

**六场景验证结果**

| 场景 | N:M 下的表现 |
|---|---|
| 一镜被 SD/H3 同用 | 同 `shot_id` 两行，属不同 track 单元 |
| 单元组合不同 | 各自单元独立 |
| 换 profile | 新单元 `profile_ver` 不同，旧单元 `superseded_by` 指向新单元 |
| 超长镜 | 同 `shot_id` 两行，`(0,15)` 与 `(15,20)`，`split_reason='oversize'` |
| 多单元引用 | 允许 |
| 多适配片段 | 允许，每片段一行 |

**理由**

双轨和超长镜是必然发生的事，不是边界情况。1:N 单外键在第一个双轨项目上就会崩。

**位置**：`D01-01 §3`、`D01-05 §4.7/§4.8`、`D01-06 §3.2/§3.5`（含双轨与超长镜两段 JSON）。

### P0-2 · 动作数据结构可执行化

**原设计（V1）**

`path: {from:"床右侧 1.2m", to:"床右侧 0.6m"}`、`result: {target_delta:"纸滑落一半"}`、`end_state` 无位置、动作时长直接相加。

**问题**

评审原话："仅仅把自然语言换成 JSON"。六个子问题全部成立：

1. `path.from/to` 无法计算；
2. 无坐标 → 无法判穿模、无法与下镜比对；
3. `end_state` 无位置 → 不能作为状态继承的可计算来源；
4. `result` 是描述 → 推不出道具最终状态；
5. 道具无状态迁移结构；
6. 反应动作无法关联触发它的动作；
7. 并行动作时长错误相加；
8. 动作时间线与镜头时间线关系未定义。

**新设计（V2）**

| 子问题 | 修法 |
|---|---|
| 1/2 | `path.from/to/via` 全为 `{x,y,z}` 归一化坐标；`label` 保留人读文字；`distance_m` 由程序算 |
| 3 | `end_state` 必含 `pos`；A-04 校验 `end_state.pos = path.to`（容差 0.02） |
| 4/5 | `result` 拆 `char_delta` / `prop_delta` / `env_delta`；`prop_delta` 带 `from → to` 状态迁移，`from` 必须等于当前状态（A-10） |
| 6 | `trigger: {kind:'action', ref:'<act_id>'}`，A-09 校验存在性与时序 |
| 7 | 并查集分组 + 组内 max + 组间相加（`D01-03 §5`），并扣除台词占用与起势/收势静默 |
| 8 | 镜头时间线（`time_slices`）与动作时间线（`t_from/t_to`）分存，T-1~T-6 六条交叉校验 |

**完整算例**：`D01-03 §7` 给 state_in + 3 动作 → 四步 apply → state_out（两人坐标 + 道具 `placed/fx_table`）→ 与下镜四项比对。

**理由**

"可计算"的最低标准是：给定输入，程序能不借助自然语言理解算出输出。V2 的每个关键字段都过了这条线：坐标可算距离、`prop_delta` 可算状态、`trigger.ref` 可查因果、并行组可算时长。

**位置**：`D01-03` 全文（§3 字段表、§5 时长算法、§7 算例）。

### P0-3 · 摄影机空间模型

**原设计（V1）**

摄影只有 8 字段（景别/方向/高度/焦段/运镜/幅度/构图/备注），其中 `dutch` 被放在高度轴枚举里。越轴算法用叉积，但没有机位坐标字段。

**问题（三处）**

1. **`dutch` 归错类**：荷兰角是绕光轴**滚转**（roll），不改变机位高度，也不改变机位位置。放进高度轴会导致"选了 dutch 就没有高度"的语义冲突；
2. **越轴没有数据支撑**：算法需要机位坐标，但模型里没有这个字段；
3. **虚假成功**：即使没有坐标，V1 的检测也会输出 PASS。

**新设计（V2）**

1. `cam_height` 移除 `dutch`，**定为 8 值**；新增 `cam_roll_deg ∈ [-20,20]`，配额改为统计 `cam_roll_deg ≠ 0` 的镜数（≤1/集）；
2. D 区扩为 **14 字段**，新增 `cam_pos`（归一化坐标）、`cam_target`（观察目标）、`cam_distance_m`、`cam_path`（轨迹采样点）；
3. 定义**四级完整度** P-A（完整）/ P-B（半完整）/ P-C（仅枚举）/ P-D（缺失）；
4. 越轴**只在 P-A/P-B 执行**，P-B 最高只出 WARN，P-C/P-D 输出 `AXIS_UNVERIFIED`（INFO 级），**不输出 PASS**；
5. 明确"不做弱推断"：不从 `over_shoulder` 猜机位侧别——猜出来的侧别会被当真用于 FAIL 判定，比不判更危险。

**数据现实**：实测 66 条分镜 `camera` 全为文本，无坐标 → **全部 P-C/P-D → 全部 `AXIS_UNVERIFIED`**。写进 `D01-04 §6.4`。

**理由**

评审要求"没有完整坐标时必须降级为无法验证，不能虚假宣称自动检测成功"。这条要求本质是**诚实性要求**，所以修法不只是加字段，还要加"什么情况下必须承认算不了"的规则。

**位置**：`D01-02 §4.3/§4.6`、`D01-04 §6`（全程）、`D01-04 §1`（V1 为什么站不住）。

### P0-5 · sourceSpecHash 覆盖完整

**原设计（V1）**

```js
const payload = shots.map(s => ({
  no, size, dir, h, mv, amp, dur, vc, dlg, spk, block, act
}));
return sha256(JSON.stringify({ scene: sceneState.coord_system, shots: payload }));
```

**问题**

1. **漏掉 8 类语义字段**：`sfx` / `music_cue` / `purpose` / `dramatic_value` / `is_insert` / `time_slices` / `speed_ramp` / `cam_pos` / `cam_roll_deg` / `lens_mm` / `composition_rule` / `lighting` / `state_in/out` / 资产内容；
2. **没有规范化**：`JSON.stringify` 依赖键序，数据库返回键序不稳；`4` 与 `4.0` 会算出不同 hash；
3. **数组顺序敏感**：`blockings` 插入顺序不同 → hash 不同，但语义相同；
4. **没有回归测试**，无法证明"改任一语义字段 hash 必变"。

**新设计（V2）**

1. **覆盖 10 类**：剧作意图 / 画面 / 摄影 14 字段 / 声音 6 字段 / 时间 5 字段 / 空间逐人 16 字段 / 动作 20 字段 / 首尾状态 / 资产引用+内容指纹 / 单元上下文（track/profile_ver/fragments）；
2. **规范化序列化**：键排序、数字规整（`4.0→4`、浮点 6 位）、`null` 保留键、字符串 NFC、**无序数组排序**（blockings 按 char、actions 按 t_from+actor、assets 按 role+id、voice_ids 字符串序）；
3. **排除非语义字段**：`id` / `created_at` / `updated_at` / `qc_status` / `fill_confidence` / `spec_source` / `unit.id`；
4. **22 条回归用例**（H-01~H-22），含"改任一语义字段必变"（H-04~H-20）与"同输入/键序/数字格式必同"（H-01~H-03）；
5. **H-21 做成 CI 断言**：两编译器同输入的 `sourceSpecHash` 必须逐字相同，不等即失败。

**限制标注**：现有 `assets` 表无内容哈希列，素材指纹可能只到 `versions+params` 的元数据级，届时标 `fp_level:'meta'`，不假装内容已锁定。

**理由**

"同源"要有可执行的证明。部分字段哈希只能证明"部分相同"，无法排除"两个编译器用了不同的服装/机位/音效"。

**位置**：`D01-06 §4.2`（完整实现伪码）、§4.3（规范化规则）、§4.4（素材指纹）、§4.5（22 用例）。
