## 二、P0 逐条

### P0-01 · 切点必须通过所有动作的跨越检查

**原文位置**：`D01-06 §3.3.1`（切点集合）、`§3.3.2`（算法）

**原文**

```
cuts(shot) = { 0, shot.story_duration } ∪ { a.t_to | a ∈ shot.actions }
```

**问题**

`t` 是某个动作的 `t_to`，**不代表其他动作也结束了**。

反例（真实形态）：A(0–10.0) 与 B(2.0–16.0)。`10.0` 是 A 的终点，V3 认为它合法；但 B 已从 2 秒起执行，切在 10 等于**把 B 从第 8 秒处截断**。

V3 的三条说明没有一条能拦住这个错误：

- "只取 `t_to`" —— 只保证"切点是某个动作的结束"，不保证"没有别的动作正在进行"；
- "`t_from` 是起手，切在这里等于劈成两半" —— 这句话本身是错的：切在 `t_from` 时动作**尚未开始**，完整留在右片段；
- "精确匹配 `t_to`" —— 匹配的是单个动作，不是全体。

**修改内容**（`D01-06 §3.3.1`）

```
candidateCuts(shot) = { 0, story_duration } ∪ { a.t_from } ∪ { a.t_to }

crosses(a, t)  ⟺  (a.t_from + EPS < t) && (t < a.t_to - EPS)

isLegalCut(shot, t)  ⟺  t ∈ candidateCuts(shot) && ¬∃a : crosses(a, t)
```

同时补齐三件事：

| 补充 | 内容 |
|---|---|
| 边界语义 | 半开区间 `[t_from, t_to)`；`t==t_from` → 动作归右片段；`t==t_to` → 归左片段；`t_from<t<t_to` → 禁止 |
| **片段内时间重基** | `t_local = t_abs - f.t_from`。存储用 `t_abs`，编译器/提示词用 `t_local`。**V3 完全没提这一条**，实现时会算出"镜长 4 秒、动作从第 3 秒开始"这种荒谬结果 |
| 无切点时 | 返回 `ADAPT_NO_LEGAL_CUT`，附 `explainNoCut()` 说明每个候选被谁挡住 |

**修改理由**

切分的目的是"找一个不伤害任何表演的位置"，而不是"找一个动作结束的位置"。前者是集合判定，后者是单点判定。

**验证算例**：`D01-06 §3.3.6`（算例 D，必须失败）、`§3.3.7`（算例 E，合法切分）

- 算例 D：A1(0–10)、A2(2–16)、`D=20`、`max=15` → 窗口 `[2,15]` 内无安全点 → `ADAPT_NO_LEGAL_CUT`。**V3 会切在 10，劈断 A2**。
- 算例 E：A1(0–5)、A2(3–13)、A3(15–19)、`D=22` → 合法点 `{13, 15}`，取最大 15 → U1=15/U2=7。V3 切 13，合法但没装满。

**未决风险**：跨越检查是 O(n²)（每候选 × 每动作）。一镜通常 ≤10 个动作、≤20 个候选，可忽略。若将来单镜动作超 50 个需加索引，暂不做。

### P0-02 · 动作检测的排序错配与 `requiredMin` 语义

**原文位置**：`D01-03 §5.2`

**原文**

```js
const iv = list.map(a => [a.t_from, a.t_to]).sort((x, y) => x[0] - y[0]);
// ...
const A = list[i], B = list[j];      // ← list 未排序
```

**问题一：E4 排序错配**

`iv` 排了序、`list` 没排。`iv[j]` 是第 j 早的动作区间，`list[i]` 是输入数组第 i 个元素——**两个下标指向不同的动作**。

后果：
- 报出的冲突角色对张冠李戴（A1 与 A3 冲突，报成 A1 与 A2）；
- `iv[j][0] >= iv[i][1]` 判"不重叠"用的是排序后区间，而 `A`/`B` 是原始对象，二者可能根本不相交；
- 若原始顺序恰好与时间顺序相反，几乎所有冲突都会漏报。

**问题二：E5 `requiredMin` 语义错**

`requiredMin = max(unionLen(actor))` 被当成"镜头最短时间需求"。

同一人 A(0–1.0)、B(4.0–5.0)：
- `unionLen = 2.0`（他"动了 2 秒"）
- 但动作最晚结束在 **5.0**，镜长 3 秒就放不下

用并集当需求会**低估 3 秒**。V3 在 `§5.4` 的算例里还自我印证了一遍："`requiredMin = 1.6 ≤ 4.5`，装得下"——1.6 是哈罗德的并集，而凯森的动作到 3.0 才结束。

**修改内容**（`D01-03 §5.2`）

| 改动 | 内容 |
|---|---|
| 排序对象 | 直接对**动作对象**排序：`(t_from, t_to, id)`，区间从对象读，不再维护平行数组 |
| 冲突检测 | 用 `list[i]` / `list[j]`，此时 `list` 与区间同源，下标必然对应 |
| 量改名 | `requiredMin` → **`spanRequired = max(a.t_to)`**（时间轴需求） |
| 新增量 | `unionMax = max(unionLen)`（最忙那个人的占用时长），仅用于报告 |
| 语义表 | `spanRequired` 判"装不装得下"；`coverage = unionLen/D` 判"够不够满"；两者不可互替 |

**修改理由**

"动作要塞多久"与"这个人动了多久"是两个量，V3 用后者回答前者。而排序错配是纯粹的实现错误——文档里写了一段跑不通的代码，且跑了整整一轮没人发现，因为示例数据恰好是顺序的。

**验证算例**：`D01-03 §5.6`

- §5.6.1 三种输入顺序 → 结果必须逐字相同（含 `ac_1`↔`ac_3` 冲突，不能报成 `ac_1`↔`ac_2`）
- §5.6.2 同人 A(0–1)+B(4–5) → `spanRequired=5.0`、`unionLen=2.0`
- §5.6.3 左手/右手独立合法、同部位冲突、说话+摇头
- §5.6.4 三人并行总时长 8.0 > 镜长 4.0，但 `spanRequired=4.0`，无冲突

**未决风险**：`coverage > 0.9` 判"无呼吸"仍是估值（`D01-07 R-6`）。本轮未校准。

### P0-04 · 旧接口投影必须选定单轨

**原文位置**：`D01-05 §6.4` 的 `listShotsCompat()`

**原文**

```js
const units = selectActiveUnits(projectId, chapterId);   // 不带 track
return units.map(u => ({ id: `proj_${u.id}`, ... }));
```

**问题**

`selectActiveUnits` 只按 `(projectId, chapterId)` 过滤。当 Seedance 与 H3 同时 active 时，返回两套单元：

| 后果 | 具体 |
|---|---|
| 行数翻倍 | 6 + 9 = 15 行，而实际单元只有 9 个（H3） |
| 同一镜重复 | `sh_03` 在 sd 完整、在 h3 被切成两片 → 出现 3 次 |
| 顺序交错 | 两轨 `unit_no` 都从 1 开始，按 `idx` 排序后交替 |
| 总时长错 | 29.5 + 14.5 + … 混成一列，"总时长"变成 44s，实际片长 38s |
| 编译错配 | 用户点第 3 行"生成"，可能拿到另一轨的单元 |

根因：旧 `shots` 表一行只有一个 `mode` 列，**结构上就是单轨的**；投影却按多轨返回。

**修改内容**（`D01-05 §6.4` / `§6.4.1`）

```js
function listShotsCompat({ projectId, chapterId, track = 'auto' }) {
  ...
  const resolved = track === 'auto' ? resolveDefaultTrack({projectId, chapterId}) : track;
  const ad = selectActiveAdaptation({ projectId, chapterId, track: resolved });
  if (!ad) return { track: resolved, rows: [], reason: 'NO_ACTIVE_ADAPTATION' };
  return { track: resolved, rows: selectUnitsByAdaptation(ad.id).map(u => projectUnitToShotRow(u, ad)) };
}
```

**track 选择链**（四级，确定性）：

```
1. project.default_track ∈ {seedance, h3}
2. 该章唯一 active adaptation 的 track
3. 多个 active → 取 updated_at 最新者，报 ADAPT_MULTI_ACTIVE (WARN)
4. 无 active → 'legacy' + NO_ACTIVE_ADAPTATION
```

**多 profile**：同 `(chapter, track)` 下 active 应唯一（应用层 + 巡检）。脏数据取 `adaptation_version` 最大者。旧接口**不暴露 profile 参数**——它的消费者不认识 profile，profile 的选择发生在"重切"动作里。

**返回结构变化**：从"数组"改为 `{ track, rows }`，并给每行加 `_track` / `_adaptation` / `_projection` 三个下划线字段。

**修改理由**

不能把两轨合并成一个"无法区分的旧分镜列表"——那不是兼容层，是数据污染。单轨 + 明确 `track` 返回值，让 UI 能显示"当前：H3 版（9 单元）"。

**验证算例**：`D01-05 §6.4.1`（sd 6 单元 + h3 9 单元同时 active）

五项证明：① `rows.length === units.length`（1:1）② `unit_no` 唯一 ③ 全行同 `_track` ④ 投影 id 带 adaptation 前缀不覆盖 ⑤ 切轨无残留。

**未决风险**：`project.default_track` 为空且两轨都 active 时，按 `updated_at` 取最新——这是个"最近操作优先"的启发式，用户可能没意识到看到的轨变了。建议 UI 显式显示当前轨道（已在 §6.4.1 要求）。

### P1-04 · `render_unit_shots` 唯一约束

**原文位置**：`D01-05 §4.8`、`D01-01 §3.3`

**原文**（过期文字，V3 遗留）

> （V3 原文，本轮已删除）**为什么需要 `UNIQUE(unit_id, shot_id, t_from)`**：同一镜在同一单元里被拆成多段时，`t_from` 不同才是合法多行。

这与同页上方"收紧为 `(unit_id, shot_id)`"的结论**直接矛盾**。

**修改内容**

- 删除上述整句，替换为"全篇只有一套唯一约束定义"的声明；
- `D01-01 §3.3` 的 DDL 片段从 `UNIQUE (unit_id, shot_id, t_from)` 改为 `UNIQUE (unit_id, shot_id)` + `UNIQUE (unit_id, order_no)`；
- `D01-05 §8.3` 清单保持两行（已唯一）。

**最终唯一约束（全篇唯一版本）**

```sql
UNIQUE(unit_id, shot_id)    -- 同一单元内一镜只能一行
UNIQUE(unit_id, order_no)   -- 单元内顺序不重复
```

**修改理由**

"同单元内同镜多片段"是切分算法的不变量所禁止的（劈开即关单元）。留一个永远用不到的约束口子，等于给错误实现留后门。

### P1-06 · 动作排序必须是全序

**原文位置**：`D01-06 §4.2`（payload 的 `actions`）、`§4.5`（排序规则）

**原文**

```js
.sort((a, b) => (a.tFrom - b.tFrom) || String(a.actor).localeCompare(String(b.actor)))
```

**问题**

这不是全序。三种常见情况下顺序不确定：

| 情况 | 为什么不确定 |
|---|---|
| 同一镜多个动作 `tFrom` 都是 0 | 第二键 `actor` 相同时，顺序 = 输入顺序 |
| 同一人物同一时刻两个动作（左手+右手） | 两键全相同 → 顺序 = 输入顺序 |
| 数据库 `SELECT` 无 `ORDER BY` | 返回顺序与存储引擎有关 |

后果：**同一份分镜，换个查询顺序，`sourceSpecHash` 就变**。同源证明直接失效——而这正是 V3 费大力气拆三种 hash 要保住的东西。

**修改内容**（`D01-06 §4.2.1` 新增）

```
① 排序键：(tFrom, actor, tTo, type, contentHash) —— 五项全序
② action.id 不进 hash（否则"复制一个动作换 id"会改变 hash）
③ trigger.ref / sync.parallel_with 中的动作 id → 映射为该动作的 contentHash
④ contentHash = sha256(canonicalStringify(动作去掉 id))
```

**为什么 ref 映射到 contentHash 而不是序号**：序号依赖排序结果，而排序又把 contentHash 当 tie-breaker——循环。用 contentHash 作引用目标，既与 id 无关，也与顺序无关。

**已知歧义**：同镜内两个**内容完全相同**的动作，`contentHash` 相同，ref 指向二者之一无法区分。语义上等价（两个动作一模一样），接受。

**验证算例**：`D01-03 §5.6.1`（三种输入顺序，检测结果逐字相同）、`D01-06 §4.6` R-26（hash 不变）、R-27（复制动作换 id，hash 不变）。

**未决风险**：`contentHash` 的计算依赖 `canonicalStringify`，若其规范化规则变动（如浮点精度），所有 ref 映射会一起变。这是可接受的（`specVersion` 会 +1），但要记住**改规范化 = 改 hash 契约**。

### P1-07 · `meta` 缺省的判定

**原文位置**：`D01-04 §5.2` 末段

**原文**

> **`meta` 的 key 是……** **B 的风险与约束**：缺省 = `known` 是**有意的默认**，因为绝大多数字段确实确定。

**问题**

"绝大多数字段确实确定"这句话对文本成立，对几何/状态字段不成立。

具体后果：历史 66 条分镜**没有一条**有 `norm_xyz`。若"缺 `meta` 即 known"，程序会认为"位置是确定的（只是没填）"，求差时 `undefined` 与 `[1.80,3.50]` 相比：

- 运气好：抛错 / `NaN` → 崩；
- 运气不好：差值算成 0 → "无跳变" → **PASS**。

后者就是"缺失被伪造成确定"，是这套模型最危险的失效模式。

**修改内容**（`D01-04 §5.2.1` 新增）

| 输入形态 | 类 A（描述/带默认枚举） | 类 B（几何/姿态/持物/道具状态） |
|---|---|---|
| 键缺失 / `undefined` | `known` | **`unknown`** |
| `null` | `known` | **`unknown`** |
| `''` / `[]` / `{}` | `known` | **`unknown`** |
| 有值 + `meta.src` | 按 src | 按 src |
| 有值 + 无 meta | `known` | `spec_source='manual'` → known；否则 **inferred** |
| 显式 `rel='unknown'` | `unknown` | `unknown` |

**类 A 白名单**（16 个字段）：`purpose` `visual_content` `composition` `lighting` `dialogue` `narration` `sfx` `music_cue` `cam_note` `is_cut_point` `time_jump` `speed_ramp` `movement` `shot_size` `cam_direction` `cam_height`

**类 B**（其余全部，尤其 `cam_pos` `norm_xyz` `position_abs` `posture` `facing` `hand_state` `occlusion` `in_frame`，以及道具 `state`/`owner`/`condition`）

附 `normalizeRel()` 统一入口 + 三条硬规则 + 置信度衰减（`carried` 每镜 ×0.9，`conf<0.5` 自动降 `inferred`）。

**修改理由**

"没有"和"不知道"是两件事。文本字段没有就是没有；坐标没有意味着"我们不知道他站在哪"，不是"他站在原点"。

**验证算例**：`D01-04 §5.7`（四镜：missing / null / 显式 unknown）

期望：3 条 `STATE_UNKNOWN`(INFO) + 1 条 `INCONSISTENT_INFERRED`(WARN)，**0 条 FAIL**。并对照说明 V3 会怎样把它算成 PASS。

**未决风险**：
- 类 A / 类 B 的划分是设计判断，不是从数据推出。若实施中发现某字段被误分类，只需改白名单（`CLASS_A`），不需改算法；
- 置信度衰减系数 0.9 / 阈值 0.5 是估值，未经真实数据校准（列入 `D01-07 R-6` 同类）。

### P1-08 · `tailHoldMax` 的权威配置

**原文位置**：`D01-01 §七`、`D01-05 §4.14`、`D01-06 §3.4`

**原文**

```js
if (pad > (u.tailHoldMax ?? 1.0) + 0.01)
  errors.push({ code: 'UNIT_PADDING_EXCESS', ..., allowed: u.tailHoldMax ?? 1.0, ... });
```

**问题**

`UNIT_PADDING_EXCESS` 是 **FAIL 级**校验，但它的阈值来自 `?? 1.0`——一个写在校验代码里的常量。

后果：同一个适配方案，在 A 版程序里 `allowed=1.0` 判 FAIL，在 B 版程序里 `allowed=2.0` 判 PASS。而 `compiledHash` 认为两者产物相同（因为 hash 里没有这个阈值）。**校验结论随程序版本漂移，而哈希看不出来。**

**修改内容**

| 问题 | 答案 | 落点 |
|---|---|---|
| 权威归属 | **TargetProfile**（`target_profiles.tail_hold_max`） | `D01-05 §4.14.1` |
| 是否属于 TargetProfile | **是**，与 `max`/`shortFloor`/`minSlice` 同级 | 同上 |
| 是否进快照 | **是**：`render_adaptations.profile_tail_hold_max` | `D01-05 §4.14` DDL |
| 是否进 hash | **是**：`adaptationHash.profileParams.tailHoldMax` | `D01-06 §4.3` |
| 旧方案能否独立复算 | **能**，只读快照不读当前 profile | 同上 |

代码改为：

```js
const tailHoldMax = u.profileTailHoldMax;
if (tailHoldMax == null) {
  warnings.push({ code: 'ADAPT_PROFILE_SNAPSHOT_MISSING', field: 'profile_tail_hold_max' });
} else if (pad > tailHoldMax + 0.01) {
  errors.push({ code: 'UNIT_PADDING_EXCESS', allowed: tailHoldMax });
}
```

**禁止清单**（写进 `D01-05 §4.14.1`）：不得 `?? 1.0`；缺列报 WARN 不猜；默认值只在创建 profile 时给一次。

**修改理由**

校验阈值必须是**数据**，不是**代码常量**。否则"同输入同结论"这个最基本的要求都不成立。

**验证算例**：把 `h3.v1` 的 `tail_hold_max` 从 1.0 改成 2.0 → 新建的 `render_adaptations` 的 `profile_tail_hold_max=2.0`、`adaptationHash` 变；旧方案仍是 1.0、hash 不变 → 两版可分别复算。

**未决风险**：`tail_hold_max` 的真实合理取值未经实测（哪个模型能接住多长的定格），列入 `D01-07 R-4`。

## 八、一句话总结

V4 修的都是**"看起来算过、其实算错"的地方**：切点只看自己不看别人（劈断并行动作）、排序了两套东西却按下标配对、把占用率当时间需求、同一文件里写着双写又写着不双写、投影不带轨道把两套单元混成一列、列数因为最后一行没逗号就少一个、音色有两个权威、hash 排序不是全序、缺省值被当成确定值、校验阈值藏在代码里。

改法统一为一句：**每个结论都要能被第三方用同一份数据重算出同样的结果**。算不出的输出 `UNVERIFIED`，不作假设。
